# TS-049 · 재측정 도중 상태 조회가 T0+22분부터 240 ms로 느려졌다 — Redis(t4g.micro) CPU 크레딧 고갈

- 슬라이스: S10(부하 측정) · 관련: [[IMP-031]](비교 대상), [[TS-042]](같은 Redis, 다른 현상), ADR-012 §5(부하 측정은 비버스터블)
- 날짜: 2026-10-10 (세션 `artifacts/loadtest/20261010-1440`, run `re1`)
- 유형: 측정 조건 결함(측정 환경이 결과에 개입) — 코드 결함 아님
- 상태: **원인 확인** — 측정 전제에 크레딧 확인을 추가. 비버스터블 Redis 전환은 미결정

## 1. 증상 (실측)
최신 이미지(d7db33b — TS-043~047 반영)로 IMP-031과 같은 조건의 통합 run을 1회 돌렸다. 사전 등록 기준은 모두 충족했지만 상태 조회 경로가 IMP-031보다 크게 느렸다.

| 지표(실측) | IMP-031 pf-r1 / r2 / r3 | re1 |
|---|---|---|
| ALB 상태 조회 대상 처리 p95(전 구간) | 8 / 8 / 8 ms | 320 ms |
| 폭증 k6 p95 | 63~65 / 33~35 / 69~73 ms | 531~543 ms |
| 폭증 dropped(합) | 84,996 / 30,122 / 89,685 | 208,801 |
| 입장 인지 지연 p95 | 2.23 / 2.23 / 2.26 s | 6.01 s |

ALB 로그를 T0 기준 분 단위로 나누면(`re1`, 상태 조회만):
- T0 ~ T0+14분: p50 3 ms, p95 4~11 ms — IMP-031과 같다.
- T0+15~18분(폭증 시작, 확장 공백): p95 0.5~1.7 s → T0+19~21분 p95 5~8 ms로 회복. IMP-031에도 있던 확장 공백이다.
- **T0+22분 ~ 폴링 끝(T0+28분): p50이 약 240 ms로 뛰어 그대로 유지** — 폭증이 끝난(T0+23분) 뒤에도 내려오지 않았다.

같은 구간 Prometheus(`re1/prom/`): 모든 api 파드의 Tomcat busy 스레드가 T0+23분에 200(최대)에 닿고 이후 80~150, **api CPU는 0.5 → 0.18코어로 떨어짐**,
승격 틱 p95 7 ms → 1~1.8 s(Redis Lua만 부르는 작업), GC·노드 CPU 이상 없음. 파드가 일하지 않고 같은 곳을 기다리는 모양이었다.

## 2. 원인 (CloudWatch, 실측)
ElastiCache 주 노드 `flowticket-redis-001`(`cache.t4g.micro`, 버스터블):
- `CPUCreditBalance`(5분 최소): run 전 6.72(16:00 KST) → 6.61 → 5.74 → 4.83 → 2.92 → **0.006(16:25 KST = T0+22분 구간)** → 0.006 → 0.41.
- `CPUUtilization`(1분 최대): 폭증 중 약 39% → T0+23분부터 **9.6% 안팎에 고정** — t4g.micro 기준 성능(약 10%)으로 묶인 모양.
- 같은 부하에서 엔진 CPU는 IMP-031과 같다: 폭증 구간 평균 53.3%(re1) vs 49.6~52.1%(pf-r1~r3), 폴링만 구간 22.4% vs 22.5~22.7%.
- IMP-031 run 동안 크레딧은 274~288(최대 288)이었다 — 바닥난 적이 없다.

→ 지연 시작 시각이 크레딧 0과 겹치고, 같은 부하의 Redis 엔진 CPU는 코드 변경 전후로 같다. **차이는 크레딧 잔량 하나**다.
클러스터를 새로 만들면 Redis도 새로 만들어져 크레딧이 거의 없이(기동 직후 1.06, 관측) 시작한다. IMP-031은 오래 떠 있던 클러스터라 288이 차 있었다.
- 이번 run이 쓴 크레딧: 진입~폭증 30분 동안 5분당 1.1~3.9, 합 약 13(관측, 1회). 유휴 때 순증 약 +0.7/5분(관측 — 적립 약 12/시간과 맞는다, 추정).

ADR-012 §5는 크레딧이 결과에 개입하지 않게 **노드**를 `m6i.large`(비버스터블)로 바꿨는데, Redis는 `t4g.micro` 그대로였다. 지금까지 드러나지 않은 것은 크레딧이 가득 찬 상태에서만 쟀기 때문이다.

## 3. 영향
- re1의 T0+22분 이후 수치(상태 조회 꼬리, 폭증 p95·dropped, 입장 인지 지연)는 **IMP-031과 같은 조건의 비교가 아니다**. 코드 변경(TS-043~047)의 비용 차이로 읽지 않는다.
- 판정 기준(상태 조회 p95 ≤ 1 s, 폭증 실패 0, 정합성 0)은 크레딧이 바닥난 상태에서도 충족했다 — 1회 관측.
- [[TS-042]](분 경계 정지)와는 별개다: TS-042의 워밍업 run 때 크레딧은 288이었다(`20261007-platform/redis-cloudwatch.txt`).

## 4. 조치
- 측정 전제에 추가: **run 직전 `CPUCreditBalance`(주 노드)를 조회해 기록하고, run 1회 소비량(약 13 — 관측 1회)의 3배인 40 미만이면 시작하지 않는다**
  (배수는 운영 여유 — 측정 근거 아님). 새 클러스터는 이 값에 닿기까지 수 시간 걸린다(적립 약 12/시간 추정) — `loadtest-100k-plan` §4, `loadtest-diag-runbook` §6.
- 미결정: 측정 프로파일(`loadtest.tfvars`)에서 Redis를 비버스터블 타입으로 바꿀지 — 비용과 IMP-031 비교 가능성(같은 t4g.micro)의 교환이다.

## 5. 검증
- 분별 지연: `scratchpad` ALB 로그 분석(상태 조회 GET `/api/queue/status`, 대상 처리 시간), 결과는 session.log `[re1 분석]`.
- 크레딧·CPU: `aws cloudwatch get-metric-statistics --namespace AWS/ElastiCache --metric-name CPUCreditBalance|CPUUtilization|EngineCPUUtilization --dimensions Name=CacheClusterId,Value=flowticket-redis-001`.
- IMP-031 비교 구간은 각 run의 `start-at.txt`(UTC) 기준 T0+5~13분(폴링만)·T0+15~23분(폭증).
- 확인하지 못한 것: 크레딧을 채운 상태에서 같은 이미지로 다시 재는 것(이번 세션 범위 밖 — 사용자 결정).
