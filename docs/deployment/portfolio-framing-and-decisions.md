# 배포·아키텍처 판단 & 면접 프레이밍

- 상태: 판단 기록(실행 무관, 상시 참조).
- 목적: "기술을 많이 쌓았다"가 아니라 **"고르고 근거 대는 엔지니어"** 로 보이게 하는 최종 스코프·서사·결정 기록.
- 관련: [EKS 배포 계획](aws-eks-deploy-plan.md), [앱 변경사항](app-changes-for-k8s-kafka.md)

## 1. 원칙 — 면접관을 납득시키는 것

기술의 **양**이 아니다. 다음 4개다.

1. **작동하는 데모 URL** — 만져볼 수 있는 것이 가장 강하다.
2. **날카로운 논지** — "동시성 하에서 정확히 한 번"(초과판매·이중결제·이중환불 0).
3. **실증(증거)** — 부하·페일오버·대시보드로 효과를 보여준다.
4. **트레이드오프를 설명하는 판단력** — 무엇을 골랐고 무엇을 **의도적으로 안 했는지**.

> 기술을 계속 쌓으면 "인상적"에서 "부엌 싱크대(다 때려넣음)"로 뒤집힌다. 시니어 백엔드가 제일 높이 사는 건 **절제와 판단력**.

## 2. 최종 스코프 — 하는 것 / 안 하는 것

**할 것**
- 라이브 데모 URL(**EKS**) — 제일 큰 레버.
- **멀티브로커 Kafka(Strimzi)** — 단, §3의 실증 조건을 지킬 때만.
- **모듈러 모놀리스 유지**(MSA 안 함) + 왜 안 했는지 문서화.
- **전부 증거로 실증**: k6 부하→HPA 확장, 브로커 종료→서비스 지속, Consumer Lag 대시보드.
- **판단 기록**(이 문서) — 면접관이 읽으면 "안다"가 됨.

**안 할 것**
- MSA 물리 분리(§4 기각).
- 추가 버즈워드 쌓기.

## 3. 납득의 조건 — "실증 or 다운그레이드"

> **멀티브로커 Kafka를 페일오버·파티션·랙으로 보여줄 거면 → 강점.
> 안 보여줄 거면 → 단일/매니지드 브로커로 낮추고 HA를 주장하지 말 것.**

"구성만 하고 실증 못 함"이 곧 면접관이 잡아내는 오버엔지니어링이다. **실증이 있느냐가 "과함"을 "역량"으로 뒤집는 유일한 스위치.**

## 4. 결정 기록

### 4-1. EKS + Strimzi 멀티브로커 — 채택(의도된 과잉)
- 맥락: 앱은 스테이트리스 2개 + 매니지드 데이터 → 실부하엔 ECS+단일 매니지드 브로커가 적정.
- 결정: 그럼에도 **라이브 K8s + 멀티브로커 Kafka를 의도적으로 채택**.
- 근거: (a) 분산/K8s/Kafka 운영 역량 **시연 목적**, (b) 선착순 티켓팅=폭주+정합성 도메인이라 확장·복제가 **실제로 의미 있음**, (c) **부하·페일오버로 실증**해 "과함"을 상쇄.
- 조건: 실증 못 하면 다운그레이드(§3).

### 4-2. MSA(마이크로서비스) — **고려 후 기각**
- 맥락: "요즘 MSA 많이 쓴다"는 키워드 압박.
- 결정: **물리적 서비스 분리를 하지 않는다. 모듈러 모놀리스 유지.**
- 근거(기각 사유):
  1. **정합성 논지 훼손** — "정확히 한 번"은 좌석·주문·결제가 **한 DB 트랜잭션**에서 조건부 UPDATE로 원자화될 때 가장 깔끔하다(ADR-003/006). 쪼개면 분산 트랜잭션(saga/outbox)이 필요해져 강점이 약점이 된다.
  2. **오버엔지니어링 신호** — 이 규모에 MSA는 명백히 과하고, 무지성 분리는 면접관이 간파한다. 모놀리스를 **의도적으로 택하고 이유를 설명**하는 편이 더 성숙해 보인다.
  3. **MSA 인접 역량은 이미 커버** — 비동기 메시징·디커플링(Kafka), 복원력(DLQ·재시도), 독립 스케일(HPA), 결과적 일관성(AFTER_COMMIT·멱등). 즉 **이벤트 드리븐으로 알맹이는 이미 증명**된다. 물리 분리는 리스크만 추가.
- 뒤집는 조건: 특정 JD가 MSA를 필수로 요구하면, **코어(좌석·주문·결제)는 그대로 두고** KOPIS 동기화/알림 컨슈머처럼 **공유 트랜잭션이 없는 워커 1개만** 자연 추출(비동기, Kafka 통신). "산산조각"이 아니라 "1개 자연 추출".

### 4-3. 스케일 실증의 정직한 분리
- 컨슈머 작업이 가벼워(SSE 브로드캐스트) **컨슈머-랙 오토스케일은 억지로 만들지 않는다.**
- **스케일 데모 = API 티어 HPA(HTTP 부하)**, **Kafka = HA(페일오버)·파티션 병렬·랙 관측.** 억지 컨슈머 스케일은 오히려 오버엔지니어링으로 보인다.

## 5. 면접 30초 서사

> "선착순 티켓팅은 오픈 순간 폭주와 정합성이 걸리는 도메인이라, **대기열·좌석·결제를 원자 연산으로 초과판매·이중결제를 0으로** 만들었습니다(IMP-003/004/007/008). 이벤트는 **Kafka 백본 + DLQ**로 비동기화하고, **EKS에 배포해 부하 시 HPA로 수평 확장, 브로커를 죽여도 RF 3로 살아남는 걸 실증**했습니다. **모듈러 모놀리스는 의도적으로 유지**했는데 — 정합성 논지가 단일 트랜잭션에서 가장 깔끔하고, 이 규모에 MSA는 과하다고 판단했기 때문입니다. 나눈다면 여기가 경계고 saga/outbox로 풀 겁니다."

→ **기술 역량 + 판단력**이 한 문단에 다 담긴다.

## 6. 이 서사를 뒷받침할 실증 체크리스트

- [ ] 공개 HTTPS 데모 URL(EKS)에서 예매→결제→관리자 콘솔 동작
- [ ] k6 부하 → **api HPA 수평 확장**(RPS/p95 곡선 캡처)
- [ ] **브로커 1대 강제 종료** → RF 3로 서비스 지속(캡처)
- [ ] Grafana **Kafka·Consumer Lag·HPA** 대시보드
- [ ] IMP: 초과판매·이중결제·이중환불 0(기존) + 클라우드 부하 재측정
- [ ] 이 판단 문서(§4)로 "MSA·과잉을 의도적으로 다뤘음" 기록

## 7. 한 문장

EKS+멀티브로커 Kafka는 **가되 반드시 실증**하고, **MSA는 안 하되 "왜 안 했나"를 설명**할 수 있게 — 이게 "많이 한 사람"이 아니라 **"판단하는 엔지니어"** 로 보이는 최종 형태다.
