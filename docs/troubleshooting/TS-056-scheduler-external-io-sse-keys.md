# TS-056 · 외부 API 호출이 대기열 승격과 같은 스레드에서 돌고, SSE 레지스트리 키가 지워지지 않았다

- 날짜: 2026-11-02
- 영역: 스케줄러(`SchedulingConfig`), SSE(`SeatSseRegistry`·`OrderSseRegistry`)
- 결과: **수정**. 테스트로 확인했다. 실제 PG 장애나 운영 부하로 재현한 것은 아니다.
- 관련: [[TS-054]](공용 스케줄러 스레드), [[TS-055]], [[ADR-011]](정산), [[ADR-015]](하트비트), [[TS-031]](KOPIS 동기화 소요 시간)

## 증상
외부 코드 리뷰가 지적한 경로를 코드로 확인했다. 운영에서 관측한 장애는 아니다.

- 스케줄러 풀 크기를 정하지 않아 모든 `@Scheduled`가 스레드 하나에서 돈다. 여기에 대기열 승격(1.5초), 아웃박스 릴레이(1초), 만료 sweep과 함께 PG 정산 2개, KOPIS 동기화가 올라가 있었다.
- PG가 응답하지 않으면 정산 한 틱이 조회만으로 최대 500초(50건 × 읽기 시간 초과 10초, 계산)까지 간다. 그동안 그 Pod의 승격과 릴레이가 멈춘다.
- `/sse/**`는 공개이고 공연 ID 존재 여부를 보지 않는다. 연결이 끝나도 레지스트리에서 emitter만 빠지고 빈 Set과 키는 남았다. 맵은 접속이 지나간 ID 수만큼 커졌다. 주문 레지스트리도 같은 구조라 주문 수만큼 커졌다.

## 수정
- 전용 스케줄러 `externalIoScheduler`(스레드 3개)를 두고 결제 정산, 환불 정산, KOPIS 동기화만 옮겼다. 작업 수와 스레드 수가 같아 서로 기다리지 않는다.
- 공용 스케줄러는 스레드 하나를 그대로 둔다. 풀을 늘리면 승격·릴레이·sweep이 한 Pod 안에서 서로 동시에 도는 조합이 새로 생긴다.
- 스케줄러 빈을 직접 만들면 Boot 기본 빈이 물러난다. `taskScheduler`를 같은 설정으로 함께 만들고, 스케줄러도 Executor라 함께 물러나는 `applicationTaskExecutor`도 되살렸다. 두지 않으면 스케줄러가 켜진 운영에서만 이 빈이 없어, 비동기 MVC 등을 쓰게 될 때 상한 없는 기본 실행기로 조용히 떨어진다(지금은 사용처가 없다).
- 레지스트리는 마지막 구독자가 빠질 때 키도 지운다. 추가와 제거를 `compute`로 묶었다. 나눠 하면 제거가 빈 Set을 지운 뒤 새 구독자가 떨어져 나간 Set에 들어가 이벤트를 받지 못한다.

## 하지 않은 것
- **없는 공연 ID의 구독을 거절하지 않았다.** 처음에는 거절하려 했다. 키를 지우면 없는 ID가 메모리에 남기는 것은 살아 있는 연결뿐이고, 같은 연결은 실제 공연 ID로도 열 수 있어 거절로 막히지 않는다. 얻는 것 없이 구독마다 DB 의존이 생긴다(DB가 느리면 SSE 연결까지 늦어진다).
- **연결 수 상한과 하트비트는 넣지 않았다.** 아래 트레이드오프의 남은 문제이고, 하트비트는 [[ADR-015]] ②에서 비용과 함께 따로 다루는 주제다.

## 트레이드오프
- **옮긴 작업 3개는 이제 짧은 작업과 동시에 돈다.** 멀티 Pod에서는 이미 Pod 사이에 겹치던 조합이라 새 유형의 동시성은 아니다(추론). 정산 2개는 PG 대기 중 커넥션을 쥐지 않아 짧은 조회와 쓰기만 한다(코드 확인). KOPIS 동기화는 수집분 전체를 한 트랜잭션으로 넣어 커넥션을 오래 쥘 수 있다(`KopisUpserter.upsertAll`, 수동 실행에서 1,931건에 약 3분 45초, [[TS-031]]). 세 작업과 공용 작업이 겹치는 최악의 경우 Pod의 커넥션 5개 중 4개를 스케줄러가 쓴다(계산). KOPIS는 새벽 4시 하루 한 번이라 상시 상황은 아니다.
- **DB·Redis가 느릴 때 공용 스레드가 밀리는 것은 그대로다.** 이번 변경은 외부 API 대기만 분리한다.
- **끊긴 연결의 emitter는 시간 초과(기본 30분)나 전송 실패 때 정리된다.** 이벤트가 오지 않는 ID는 시간 초과가 유일한 정리 경로다. 내장 Tomcat 로컬 시험에서 클라이언트가 소켓을 닫아도 30초 동안 키가 남았고 첫 전송 뒤 사라졌다(ALB·Next를 거친 경우는 재지 않았다). 연결 수 상한도 앱에는 없어, 레지스트리 크기의 상한은 최근 30분 연결 수로 볼 수 있다(추론).
- **정산 락 시간은 그대로다.** `lockAtMostFor=PT5M`보다 한 틱이 길어지면 다른 Pod가 함께 돌 수 있다. 취소는 승인 단위 멱등키로 나가고 조회 표시는 덮어써도 되어 결과는 같다(코드 확인, 실 PG 미확인).

## 재발 방지
- 외부 API를 부르는 스케줄 작업은 `@Scheduled(scheduler = SchedulingConfig.EXTERNAL_IO)`를 쓰고, 전용 스케줄러의 스레드 수도 함께 늘린다.
- 공개 경로에서 받은 값을 키로 쓰는 맵은 항목이 언제 사라지는지 함께 정한다.

## 검증
- `SchedulingConfigTest`: 통합테스트는 스케줄러를 끄고 돌아 이 배선이 실행되지 않으므로 설정만 띄워 본다. 외부 작업이 멈춰도 짧은 작업이 계속 돌고, 각각 다른 스레드에서 돌며, 공용 스레드는 하나이고, 세 작업이 전용 스케줄러를 지정하고, `applicationTaskExecutor`가 유지된다.
- `SseRegistryCleanupTest`: 전달 실패 경로의 키 제거, 구독자가 남은 경우 유지, 제거와 새 구독이 겹치는 경우.
- `SseRegistryTimeoutIntegrationTest`: 실제 서블릿 컨테이너에서 시간 초과로 끝난 연결의 키가 사라진다.
- 실제 PG 장애 상황과 운영 부하에서는 확인하지 않았다.
