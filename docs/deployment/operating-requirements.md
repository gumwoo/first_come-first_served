## 2. 요구사항 후보

### 2-1. 가용성 — 무엇을 잃어도 핵심 경로가 계속 도는가
핵심 경로 = 대기열 진입·상태 조회, 좌석 선점·주문·결제(이미 입장한 사용자).
| 후보 | 뜻 | 필요한 것(설계 영향) | 근거·대가 |
|---|---|---|---|
| G0 | 단일 파드 장애 시 짧은 중단 허용 | 최소 복제본 1 가능 | 비용 최소. 대기열 1개가 죽으면 새 진입이 막힌다([workload-responsibilities.md](workload-responsibilities.md) §3) — 상용 기본값으로는 약함 |
| **G1(출발점 제안)** | **노드 1대 장애 때 핵심 경로가 계속 돈다** | api·대기열 각각 최소 2(서로 다른 노드), PDB가 퇴거 1개를 허용, 남은 파드가 평시 부하를 감당 | 노드 장애에 대비하는 것은 일반적인 운영 가정이다(이 프로젝트의 발생 빈도 측정은 없음). 2개라도 남은 1개의 처리 용량을 검증해야 의미가 있다. 비용: 파드 1100m 그대로면 api 2 + 대기열 2 = 노드 4대 |
| G2 | 가용 영역 1곳 장애 때도 계속 돈다 | AZ 분산을 강제(`DoNotSchedule` 등), 영역마다 복제본, 남은 2개 영역의 용량 | 비용·스케줄 실패 위험 증가. 지금은 선호만 한다. G1과 함께 목표로 할지, 별도 검증 목표로 둘지는 선택 사항 |

### 2-2. 지연 — 무엇을 얼마나 빨리
예매와 대기열을 **따로** 정한다. 아래 실측은 출발점일 뿐 목표가 아니다 — 목표는 사용자 경험·비즈니스 요구로 정한다.
| 경로 | 지금 알고 있는 실측 | 후보 정하는 방법 |
|---|---|---|
| 좌석 선점·주문·결제 | B 폭증 중 p95 184~272ms, A' 1.6~2.6초([[IMP-033]], 각 2회), 입장자 100명 동시 p95 hold 0.54~0.93초·주문 0.47~0.88초·결제 0.40~0.83초([[IMP-030]], 초기 구성) | 예: "폭증 중에도 p95 X ms 이하" — X는 B 실측과 사용자 체감 사이에서 선택 |
| 대기열 상태 조회 | 폭증 중 p95 A' 13~18ms, B 259~523ms, p99 양쪽 0.9~2.2초([[IMP-033]]) | 순번 표시가 몇 초 늦어도 되는가(입장 인지 지연)로 정한다. 폴링 주기(`retryAfterMs`)와 같이 본다 |
| 대기열 진입 | 단일 공연 10만 명 / 10초 진입 100,000건 처리([[IMP-031]]) | 진입 p95 목표는 아직 없다 |

### 2-3. 부하 범위 — 어디까지를 설계 대상으로
| 후보 | 뜻 | 영향 |
|---|---|---|
| L1 | 공연 1개 오픈(검증된 범위) | 예매 동시 입장 상한 100 |
| L2 | 공연 N개 동시 오픈(N 후보: 2·3·5) | 예매 동시 입장 상한 100 × N, 진입·폴링도 합산. **미검증** |
| L3 | 예정된 오픈 + 예측하지 못한 추가 폭증(v2의 오픈 10분 뒤 폭증) | 사전 확장만으로는 부족 — HPA·부하 제한이 필요한지 |
- 예매 외 api 트래픽(공연 목록·상세, 로그인, 예매 내역·환불)의 오픈 중 양은 **측정한 적 없다**.
- 폭증 발생기(`infra/k6/queue-status-rate.js`, 세션 드라이버의 `RATE=2334` × 3)는 고정 도착률로 보낸다 — 서버의 `retryAfterMs`를 따르는 폴링이 아니라 "지시를 따르지 않는 클라이언트" 최악 가정이다. 실제 폴링 모델을 따로 정할지 선택한다.

### 2-4. 복구 목표 — RTO / RPO 후보
| 장애 | 실측 | RTO 후보 | RPO(데이터 손실) |
|---|---|---|---|
| RDS 페일오버 | 실패 창 약 11초, 실패 1.05%, 파드 재시작 0([[TS-037]]) | 예: 30초 이내 자동 복구 | Multi-AZ 동기 복제 — 커밋된 주문·결제 손실 0이 목표(설계 성질, 이 시험에서 따로 검증하지 않음) |
| Redis 페일오버 | 실패 창 약 33초, 실패 4.97%, 파드 재시작 0([[TS-037]]) | 예: 60초 이내 | 비동기 복제 — 대기열 상태 일부 손실 **가능성**(관찰한 토큰 1개는 보존, 전체 무손실은 검증 안 됨 — TS-037 §7). 손실되면 사용자는 재진입 |
| api·대기열 파드 1개 | 롤링·드레인 실측은 있음([[IMP-015]]·[[IMP-017]]) — 갑작스런 종료는 없음 | 예: 남은 복제본이 즉시 받음(G1) | 상태 비저장(대기열 상태는 Redis) |
| Kafka 브로커 1대 | RF 3·min.insync 2라 쓰기 유지(설정) | — | 아웃박스로 재발행(at-least-once) |

### 2-5. 평시와 오픈의 운영 정책
오픈 시각이 정해진 서비스라, **평시 최소 구성**과 **오픈 전 사전 확장**을 따로 정한다(api 쪽은 [[ADR-025]]로 이미 운영 — B에서는 대기열 쪽이 비어 있다).
| 평시 후보(api + 대기열) | 장점 | 단점 | 메모 |
|---|---|---|---|
| 1 + 1 | 자원 최소 | 양쪽 단일 장애점, PDB(api 2·대기열 1)가 드레인을 막음 | 시연용 |
| 2 + 1 | api 가용성 | 대기열 단일 장애점(새 진입 중단) | api HPA `minReplicas: 3`과 PDB(api 2)를 함께 바꿔야 함 |
| **2 + 2(G1 출발점)** | 양쪽 복제본 | 1100m 그대로면 노드 4대 | requests 재산정과 한 쌍, api HPA 하한·PDB 변경 필요 |
| 3 + 3 | AZ마다 1개(G2 후보) | 평시 비용 | AZ 분산 강제 필요 |
- 오픈 전 정책 후보: 대기열·api 둘 다 사전 확장 + 실제 요청 경로 워밍업까지 끝낸 뒤 오픈(근거: IMP-033 §6 — 폭증 중 새로 생긴 파드의 서버 처리 시간이 길었다. 원인이 JIT라는 것은 추론).

## 3. 정해야 할 것 (사용자 선택)
1. 가용성: G0 / **G1(제안)** / G2 — G2는 별도 검증 목표로 둘지.
2. 지연: 예매 p95 목표 X, 대기열 상태 조회의 허용 지연(또는 입장 인지 지연) Y — 정하기 어려우면 "B 실측을 넘지 않음"을 임시 기준으로 할지.
3. 부하 범위: L1만 / L1 + L2(N=?) / L3 포함.
4. 평시 최소 구성: 2-5 표에서.
5. 폭증 부하 모델: 지금처럼 `retryAfterMs` 무시 최악 가정을 유지할지, 지시를 따르는 폴링 모델을 추가할지.

## 4. 이 선택 뒤에 재야 할 것 (다음 측정 세션)
- 예매 경로 CPU-ms/req·메모리(분리 뒤 api의 1100m 재산정 근거), 지속 예매 부하(정원 교체) 모델
- 현 구성(1100m·B)과 대기열 파드의 Hikari active·idle·total·pending(풀 크기 차등화 근거 — 이번 IMP-033 세션은 pending만 내보냈다)
- 노드 1대 비자발적 장애(G1 검증), 서블릿 진입 전 대기(Tomcat 연결·accept) 지표

## 5. 결정 (2026-10-14 20:22 KST, 사용자 선택)
| 항목 | 결정 | 조건·단서 |
|---|---|---|
| 가용성 | **G1 — 노드 1대 비자발적 장애에도 핵심 경로(대기열 진입·상태 조회, 입장자의 선점·주문·결제) 지속** | 파드를 서로 다른 노드에 분산하고, **남은 파드의 실제 처리 용량과 복구 시간을 검증**한다. 오픈 중 장애는 장애 직후 허용할 오류율·지연·복구 시간과 필요한 예비 용량을 **따로 정한다** — 장애 중에도 10만 명/10초 처리량을 유지한다고 미리 가정하지 않는다 |
| 가용성(후속) | **G2 — 후속 검증 목표** | AZ 1곳 장애 시 서비스 지속 여부·데이터 정합성·성능 저하·복구 시간을 측정해 다음 개선 여부를 정한다. G1 검증 뒤 진행 |
| 평시 최소 구성 | **api 2 + 대기열 2 — 출발 후보**(확정 아님) | 자원 산정(업무별 requests·메모리·Hikari·HPA·PDB, 노드 배치) 뒤 확정한다. api HPA 하한 3과 PDB(api 2)는 이때 함께 바꾼다 |
| 부하 범위 | **L1 + L3** | 공연 1개 오픈(검증된 범위) + 예정된 오픈 뒤 예측하지 못한 추가 폭증. 여러 공연 동시 오픈(L2)은 나중 과제 |
| 지연 목표 | **기존 B 실측을 임시 기준** | 예매 p95는 B 실측(폭증 중 184~272ms)을 넘지 않기, 대기열 상태 조회 p95는 B 실측(259~523ms)보다 개선. 사용자 체감 기반 목표는 나중에 확정 |
| 폭증 부하 모델 | 아직 정하지 않음 | 지금의 `retryAfterMs` 무시 최악 가정을 유지할지, 지시를 따르는 폴링 모델을 추가할지 — 측정 계획에서 정한다 |

| 평시 운영 방식(대안) | **B 상시 + 오픈 전 사전 확장을 기본으로 한다.** "평시 A'(통합) → 오픈 직전 B로 전환"은 비교 대안으로 남긴다 | 전환은 파드 수 변경이 아니라 요청 경로 변경이다. 오픈마다 Git component 토글 → ArgoCD 동기화(배포 1회)가 들어가고, 전환 중 대상 파드 등록·해제 때의 사용자 오류는 **측정한 적 없다**(이번 세션의 `ab-switch.sh`는 자동 동기화를 끈 세션 전용 방식). 노드 하한(AZ당 1·Kafka 3)이 이미 3대라 절감이 작을 수 있다 — 자원 산정의 노드 배치 시뮬레이션에서 "평시 A'"와 "평시 B 2+2"의 노드 수를 같이 계산해 차이가 크면 다시 검토한다 |

다음 과제의 목표 문장: **기존 B에서 확인한 예매 성능과 정합성을 유지하면서, DB 커넥션 예산 안에서 대기열 지연과 노드 비용을 개선하고, 노드 1대 장애 시 가용성(G1)을 검증한다. AZ 장애(G2)는 후속.**
별도 우선 과제: 랭킹 감쇠가 한 주기에 여러 번 실행될 가능성(ShedLock `lockAtLeastFor = PT0S`, 곱셈 감쇠 — [workload-responsibilities.md](workload-responsibilities.md) §2) — 자원 최적화와 분리해 재현 시험·수정부터 한다.
