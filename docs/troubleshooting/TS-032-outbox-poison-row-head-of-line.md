# TS-032 · 아웃박스 행 하나가 모든 주문 이벤트를 영구 정지시킬 수 있었다 — 소비자에는 있던 실패 분류가 생산자에는 없었다

- 슬라이스: S08(아웃박스/이벤트)
- 날짜: 2026-08-20
- 유형: 가용성 결함(실패 분류 누락) + **같은 원칙이 파이프라인 한쪽에만 적용된 사례**
- 관련: [[ADR-010]](트랜잭셔널 아웃박스), [[TS-020]](소비자 독성 메시지), [[TS-026]](DLQ 재처리 확인),
  [[IMP-011-outbox-delivery]](브로커 장애 = 일시적 실패)
- 상태: **해결** — 역직렬화 실패를 `DEAD`로 격리하고 차단 범위를 해당 aggregate로 한정(PR #248).
  운영 조회·재처리 창구는 아직 없다(§7)

## 0. 무엇이 문제였나

`OutboxRelay`는 미발행분을 오래된 순으로 가져와 한 건이라도 실패하면 남은 배치를 중단한다.

```java
for (OutboxEvent row : batch) {
    if (!publishOne(row)) {
        break;                      // ← 남은 배치 중단
    }
}
```

**이 판단은 브로커 장애에서는 옳다.** 배치 전체가 타임아웃으로 트랜잭션을 오래 붙잡는 걸 막고,
같은 주문의 후속 이벤트가 앞 이벤트를 추월하지 않게 한다. 다음 틱에 재시도하면 복구된다.

문제는 `publishOne()`이 **두 종류의 실패를 하나로 뭉갰다는 것**이다.

```java
try {
    OrderEvent event = mapper.readValue(row.getPayload(), OrderEvent.class);  // ①
    kafkaTemplate.send(...).get(sendTimeoutMs, MILLISECONDS);                 // ②
    row.markPublished();
    return true;
} catch (Exception e) {          // ①과 ②를 구분하지 않는다
    row.markAttemptFailed();
    return false;
}
```

①이 실패하면 다음 틱에도 결과가 같다. 그런데 `PENDING`을 유지하므로 정렬 선두에 **다시 온다.**

```
readValue 실패 → false → break
      ↓ 다음 틱
findByStatusOrderByCreatedAtAsc 가 같은 행을 또 맨 앞에 → 같은 실패 → …
```

**뒤따르는 모든 주문 이벤트가 영구 정지한다.** 막을 장치는 없었다 — `attempts`는 증가만 하고
상한이 없고, `OutboxStatus`에 격리 상태가 없고, 별도 보관함도 없었다.

## 1. 왜 오래 안 보였나 — 에러율에 나타나지 않는다

결제 API는 200을 반환한다. 아웃박스 행은 **결제와 같은 커밋**으로 이미 들어갔고, 사용자 응답은
릴레이를 기다리지 않는다. 그러니 사용자도, HTTP 5xx 지표도, HPA도 아무 이상을 못 본다.

멈추는 것은 이벤트뿐이다. 그리고 이벤트는 **안 온다고 누가 항의하지 않는다.**

> 조용히 실패하는 결함은 관측 설계가 없으면 발견 경로 자체가 없다.

## 2. 결함을 어떻게 찾았나 — 코드에서 먼저, 그다음 실행으로

부하나 장애로 만난 게 아니라 **장애 대응·지연·처리량 관점의 코드 훑기**에서 나왔다. 그래서
"실제로 그렇게 되는가"를 증명할 책임이 남았다. 재현 테스트를 먼저 올려 **CI에서 RED를
확인**했다([run 32321014147](https://github.com/gumwoo/first_come-first_served/actions/runs/32321014147)).

```
203 tests completed, 2 failed        ← 새 테스트 2개만, 기존 201개는 통과

[브로커는 정상이다. 앞의 한 행이 깨졌다는 이유로 뒤의 3건이 멈추면 안 된다]
expected: 3L
 but was: 0L                          ← 5틱을 돌려도 0건
```

**브로커를 죽이지 않은 것이 요점이다.** 죽이면 "당연히 안 나간다"가 되어 head-of-line 차단을
증명하지 못한다. Kafka는 정상이고 정상 이벤트 3건은 발행에 아무 문제가 없는 payload인데,
깨진 행 하나가 앞에 있다는 이유만으로 전부 멈췄다.

⚠️ 재현 테스트에서 **정렬 동률**을 막아야 했다. 정렬 키가 `created_at` 하나뿐이라 같은 순간에
저장하면 순서가 결정적이지 않다. 독성 행을 먼저 저장하고 10ms 띄웠다 — 안 그러면 테스트가
간헐적으로 통과해 재현 테스트로서 무의미해진다.

## 3. 진짜 문제 — 원칙은 이미 있었는데 한쪽에만 있었다

이 저장소는 **소비자 쪽에서 같은 것을 이미 배웠다.**

[[TS-020]]에서 역직렬화 실패 메시지가 리스너에 도달조차 못 해 DLQ로 못 가는 결함을 고쳤고,
`DlqConsumer`는 그 교훈을 주석으로 못박아 두었다.

> DLT에는 두 종류가 들어온다: 리스너에서 실패한 **정상 이벤트의 JSON**과, 애초에 역직렬화에
> 실패한 **원본 바이트**다. […] **DLT에는 다시 보낼 곳이 없어** 그 자리에서 무한 재시도가 된다.
> 즉 독성 메시지가 원본 토픽에서 DLT로 이사할 뿐 아무것도 해결되지 않는다.

`AdminDlqService.retry()`는 더 직접적이다 — payload 역직렬화 실패는 `VALIDATION_ERROR`,
Kafka 전송 실패는 `INTERNAL_ERROR`로 **애초에 나눠서** 다룬다.

즉 **"결정적 실패는 재시도로 안 풀린다"는 원칙이 프로젝트에 이미 있었다.**
`OutboxRelay`만 `catch (Exception)` 하나로 뭉개고 있었다.

### 이 대칭은 처음이 아니다

[[TS-026]]은 정확히 **반대 방향**이었다. DLQ 재처리가 브로커 확인 없이 `RETRIED`로 기록했는데,
같은 문제를 `OutboxRelay`는 이미 `.get()`으로 확인하고 있었다.

| | 생산자(`OutboxRelay`) | 소비자(DLQ) |
|---|---|---|
| 확인 전 상태 확정 ([[TS-026]]) | **옳았음** | 틀렸음 |
| 결정적/일시적 실패 분류 (본 건) | 틀렸음 | **옳았음** |

**같은 파이프라인의 양쪽이 서로 다른 것을 알고 있었고, 어느 쪽도 옮겨지지 않았다.**
두 번 같은 모양으로 걸렸다면 이건 우연이 아니라 **구조**다.

## 4. 해결 — 실패를 두 종류로 나누고, 차단 범위를 좁힌다

```
                    ┌─ 역직렬화 실패 → DEAD (배치 계속, 같은 aggregate만 보류)
PENDING ─ relay ────┤
                    └─ 성공 → Kafka send ─┬─ 성공 → PUBLISHED
                                          └─ 실패 → PENDING 유지 + break → 다음 틱
```

- `OutboxStatus.DEAD` 추가 — **"발행 실패"가 아니라 "재시도가 무의미함"** 을 뜻한다
- 역직렬화를 발행에서 분리. 실패하면 `break` 없이 그 행만 격리
- 선행 `DEAD`가 있는 aggregate의 **후속 이벤트만** 보류
- Kafka 전송 실패는 **기존 그대로** `PENDING` + `break`

### ㉠ 왜 `attempts` 상한으로 DEAD 전환하지 않는가

리뷰에서 "N회 실패하면 DEAD"를 검토했고 **기각했다.** 브로커가 30분 죽어 있었다는 이유로
멀쩡한 이벤트를 영구 실패로 보내면, [[IMP-011-outbox-delivery]]가 실측으로 증명한
"복구 후 전량 재발행 → 유실 0"이라는 아웃박스의 존재 이유가 그대로 깨진다.

분류 기준은 **횟수가 아니라 "재시도로 결과가 달라질 수 있는가"** 다.

### ㉡ 왜 격리해도 같은 aggregate는 막는가

초안은 "역직렬화 실패는 발행 대상이 아니므로 건너뛰어도 **순서 보장을 훼손하지 않는다**"였다.
**이 판단은 틀렸고 리뷰에서 잡혔다.**

발행된 것들끼리의 상대 순서와 **도메인 인과 순서는 다른 문제다.** 같은 주문에서

```
E1  order.paid      ← payload 손상 → 격리
E2  order.refunded  ← 정상 → 발행
```

이 되면 소비자는 PAID를 한 번도 못 본 채 REFUNDED부터 받는다. 릴레이가 `aggregateId`를 Kafka
파티션 키로 쓰는 것도 같은 aggregate의 순서 보존이 목적이다.

⚠️ **이 시나리오는 현재 도달 불가능하다.** 아웃박스 생산 경로는
`PaymentService.appendOutbox("order.paid", ...)` 하나뿐이고 환불은 SSE로만 나가므로, 한 주문에서
아웃박스 이벤트가 연속으로 만들어지지 않는다. 그럼에도 불변식으로 고정한 이유는, head-of-line
차단을 없애면서 순서 성질을 실수로 깨뜨리기 쉬운데(전부 건너뛰면 되니까) **이벤트 종류가 늘어난
뒤에는 깨진 것을 알아채기 어렵기 때문**이다.

### ㉢ 왜 기존 `dlq_messages`로 옮기지 않았는가

소비자 DLQ 테이블을 재사용하는 안을 먼저 제안했다가 **철회했다. 설계가 성립하지 않는다.**

`DlqMessage`의 필드는 `topic / payload / errorMessage / status / createdAt / retriedAt`뿐이라
**`aggregate_id`가 없다.** 격리한 행을 그리로 옮기면 ㉡의 "같은 aggregate 후속을 보류한다"를
판정할 근거를 **조회할 수단 자체가 사라진다.** 또 `AdminDlqService.retry()`는
`message.getTopic()`으로 Kafka에 직접 재발행하므로, 아웃박스 행을 넣으면 발행 책임이
`OutboxRelay` 밖으로 샌다.

> 소비자 DLQ에서 배운 **원칙**은 재사용하되, **저장 모델**까지 공유할 이유는 없다.

### ㉣ `last_error`의 수명

일시적 실패에도 원인을 기록한다. 초안은 성공 시 이를 지우지 않아 **`PUBLISHED`인데 오류가
붙어 있는** 상태가 남을 수 있었다(리뷰 지적). 운영자가 미해결로 오해한다.

```java
public void markPublished() {
    this.status = OutboxStatus.PUBLISHED;
    this.publishedAt = LocalDateTime.now();
    this.lastError = null;   // attempts는 남긴다 — "몇 번 만에 나갔는지"는 가시성
}
```

## 5. 검증

| 단계 | 근거 |
|---|---|
| RED | [run 32321014147](https://github.com/gumwoo/first_come-first_served/actions/runs/32321014147) — `203 tests, 2 failed`. 정상 3건 기대 → **실측 0건**, PENDING 후보에 독성 행 잔존 |
| GREEN | [run 32325256007](https://github.com/gumwoo/first_come-first_served/actions/runs/32325256007) — 전 잡 통과 |

회귀 테스트 6건: 독성 행이 다른 주문을 막지 않음 / 릴레이 후보에서 빠짐(+`DEAD`·근거 보존) /
같은 aggregate 후속은 보류 · 다른 aggregate는 발행 / `lastError` 수명 3건(단위).

**무중단 배포**: V18은 추가만 한다. `status`는 CHECK 없는 `VARCHAR(20)`이라 값 추가에 DDL이
필요 없고 `last_error`는 nullable이다. 롤링 중 구버전 Pod는 `DEAD`를 모르지만 릴레이는
`status='PENDING'`만, purge는 `status='PUBLISHED'`만 조회하므로 `DEAD` 행을 적재하지 않는다.

## 6. 테스트를 잘못 쓴 일 — 한 번 더

`last_error` 수명을 기존 `OutboxDeliveryIntegrationTest`에 단언으로 넣었다가 **CI에서 10/10
실패**했다. 코드가 아니라 **단언이 틀렸고, 두 겹으로 틀렸다.**

1. 그 테스트의 장애용 릴레이는 `new OutboxRelay(...)`로 만든 평범한 객체다 —
   `@Transactional` 프록시가 아니라 dirty checking이 돌지 않아 `attempts` 변경이 영속화되지 않는다.
2. 설령 됐어도 `break` 때문에 **첫 행만** 시도된다. 나머지 9건은 `attempts == 0`이 정상이다.

검증 대상이 발행 파이프라인이 아니라 **엔티티 계약**이었다. 컨테이너 없는 단위 테스트
(`OutboxEventTest`)로 옮겨 로컬에서 실행 확인했다.

> [[TS-015]]·[[TS-030]]과 같은 계열이다 — **테스트가 무엇을 검증하는지 착각한 것.**
> 다만 이번에는 거짓 통과가 아니라 거짓 실패라 CI가 즉시 알려 줬다.

## 7. 남은 것

- **`DEAD` 행의 운영 창구가 없다.** purge되지 않고 계속 남는 것은 의도지만(유실 방지), 조회·재처리·
  폐기는 현재 DB 직접 조회로만 가능하다. 격리만 하고 창구가 없으면 **"조용히 멈추는 문제"를
  "조용히 쌓이는 문제"로 옮긴 것**에 가깝다. 관리자 API가 후속 작업이다.
- **`DEAD` 발생을 알려 주는 수단이 없다.** Alertmanager는 수신처가 없어 의도적으로 꺼 뒀다
  (`k8s/monitoring/kube-prometheus-stack.values.yaml`). §1에서 말한 "발견 경로가 없다"가
  격리 이후에도 그대로 남아 있다.
- **`attempts` 무한 증가는 그대로다.** 브로커 장애가 길어지면 계속 오른다. ㉠의 판단상 코드로
  막을 문제가 아니라 관측으로 볼 문제라고 보고 범위에 넣지 않았다.
- **운영에서 이 결함이 실제로 발생한 적은 없다.** 코드 검토에서 찾아 테스트로 증명한 것이며,
  프로덕션 로그로 확인한 사건이 아니다.

## 8. 배운 것 — 결론보다 절차

**같은 원칙이 파이프라인 양쪽에 필요한데, 한쪽에서 배운 것이 자동으로 옮겨가지 않는다.**
[[TS-026]]과 본 건이 정반대 방향으로 같은 모양이었다. 두 번 걸렸으면 다음에도 걸린다.

그래서 실패를 다룰 때 물어야 할 질문은 "재시도할까 말까"가 아니라 **"이 실패는 재시도로 결과가
달라지는 종류인가"** 다. 그 구분이 없으면 재시도는 복구 장치가 아니라 **정지 장치**가 된다.

| | 재시도로 달라지는가 | 조치 |
|---|---|---|
| Permanent (역직렬화·스키마 불일치) | 아니오 | 즉시 격리, 진행은 계속 |
| Transient (브로커·타임아웃·네트워크) | 예 | 상태 유지, 중단 후 재시도 |

그리고 **차단 범위는 정합성이 요구하는 최소로 좁힌다.** 전역 중단은 안전해 보이지만,
결정적 실패와 만나는 순간 안전장치가 아니라 단일 장애점이 된다.
