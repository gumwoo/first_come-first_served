# 대기열 평시·피크 모양 전환 — 클러스터 검증 계획(사전 등록 초안)

- 작성: 2026-10-27
- 상태: 초안. 판정 기준·run 횟수는 세션 전에 세션 폴더의 사전 등록 파일로 확정한다(이 문서의 기준은 후보).
- 대상: [[ADR-031]](평시 3대·피크 9대 전환), [[IMP-049]](kwok 시뮬레이션·로컬 측정으로 확인한 범위)
- 관련: `docs/testing/loadtest-diag-runbook.md` §2b(전환 절차), `docs/testing/traffic-profile.md`(가정 부하), [[IMP-035]](B 10만 진입 판정), [[IMP-033]](폭증 중 예매 지연 비교 방법)

## 1. 목적
[[IMP-049]]는 배치를 kwok(실제 kube-scheduler, CA는 흉내)으로, 평시 동거를 로컬 상대 비교로 확인했다. 실제 클러스터에서만 확인할 수 있는 것을 잰다.
1. 실제 Cluster Autoscaler가 평시 3대로 줄이고, 피크 중 api 노드를 지우지 않는가.
2. 사전 확장 전환(대기열 롤링 + 노드 추가)이 오픈 전 여유(15분) 안에 끝나는가.
3. 평시 동거의 EKS 값이 로컬 판정과 같은 방향인가.
4. 예매 api 200m에서 오픈 부하 중 예매 지연이 1100m 때와 비슷한가(이번 변경에서 성능 쪽으로 재지 않은 유일한 차이).

## 2. 준비(클러스터 없이)
- 사전 등록 파일: 아래 기준·run 횟수·순서·무효 조건을 측정 전에 적고 시각을 `date`로 남긴다.
- 전환 기록 스크립트: Pod(Pending·Running·Ready)·노드(추가·Ready·삭제) 이벤트와 ArgoCD 동기화 리비전을 1초 단위로 남긴다. 전환 시간은 이 기록으로만 잰다.
- 전환 PR 3개를 미리 만들어 둔다: ① queue-peak 켜기 + 대기열 하한 6 + event·off-by, ② 하한 2, ③ queue-peak 끄기 + event·off-by `-`.
- 부하 도구(있음): 평시 조회 `infra/k6/browse-mix.js`, 예매 묶음 `infra/k6/booking-e2e.js`, 진입 `infra/loadgen/run-entry.sh`, 폴링 `infra/loadgen/poll-hold.mjs`, 정합성 `scripts/loadtest/check-correctness.sh`·`check-booking.sh`.
- V4의 api 1100m 비교 조건은 세션 한정으로 ArgoCD 자동 동기화를 끄고 api Deployment requests만 바꾼다(런북 §0 절차, 끝나면 동기화 재개·리비전 확인).

## 3. 단계와 판정 기준(후보)

| 단계 | 하는 일 | 확인 항목 | 통과 기준(후보) |
|---|---|---|---|
| V1 평시 배치 | 클러스터를 올리고 CA 축소(10분 대기)가 끝날 때까지 둔다 | 노드 수, 노드별 Pod, Pending | 노드 3, api 노드당 1, 대기열 노드당 1, Pending 0 |
| V2 평시 동거 | 평시 조회 100 req/s(web 경유) + 예매 묶음 100명, run 3회 | api Pod별 p95(대기열과 같은 노드 2개 vs 혼자인 1개, Prometheus `http_server_requests` Pod 라벨) | 비율 < 1.30(로컬과 같은 기준), 5xx 0 |
| V3 사전 확장 전환 | 평시 부하를 건 채 PR ① 머지 | 머지 → 대기열 6 Ready·노드 9까지 시간, 동거, web Ready, ALB 5xx | 15분 안, 동거 0, web Ready ≥ 1, 5xx 0 |
| V4 오픈 부하 | 진입 10,000/s × 10초 + 대기자 폴링 + 예매 묶음(① 오픈 전, ② 폴링 중) | 진입·대기열은 [[IMP-035]] 축, 예매 p95 ②(hold·주문·결제) | 진입·대기열 [[IMP-035]] 기준 충족, 예매 p95 ②가 같은 세션 api 1100m 대비 1.30배 미만 |
| V5 피크 유지 | 오픈 뒤 피크 모양으로 15분 이상 | 실제 CA의 api 노드 축소 여부 | 노드 9 유지, api 노드당 1 |
| V6 되돌림 1 | PR ② 머지 | HPA 축소(안정화 300초)·CA 축소 시간 | 노드 5, 동거 0 |
| V7 되돌림 2 | 대기자 0 확인 뒤 PR ③ 머지 | 평시 모양 롤링, CA 축소 시간, 롤링 직후 HPA 일시 증가 | 노드 3, Pending 0, api 노드당 1 |

- V2: Pod 위치가 고정이라 같은 run 안에서 노드별로 비교한다. 순서를 바꿔 가며 반복할 수 없고, 노드 사이 차이(AZ·DB 거리)가 섞인다. 이 한계를 결과에 적는다.
- V4: api 200m와 1100m를 같은 세션에서 번갈아 잰다(200 → 1100 → 1100 → 200). 예매 묶음 ①·②는 [[IMP-033]] v2와 같은 방식(워밍업 뒤 ①, 부하 중 ②)이다.
  폴링은 traffic-profile §3 가정(3,200~3,500/s)으로 두고, 폭증 시험(7,000/s)은 넣지 않는다. 1100m 조건에서는 queue-peak가 켜진 상태라 대기열 구성은 같다.
- 무효 조건(후보): 발생기 CPU 1초 최대 ≥ 80%, 진입 dropped > 0, 측정 중 재시작, 도구 오류. 무효 run은 같은 자리에서 다시 재고 기록을 남긴다.

## 4. 실패하면
- V1·V7에서 3대가 안 되면: CA 로그에서 축소를 막은 이유(PDB·사용률·시스템 Pod·safe-to-evict)를 확인한다. 시뮬레이션이 흉내 내지 못한 부분이면 IMP-049에 덧붙인다.
- V3이 15분을 넘거나 동거가 생기면: 사전 확장 시점을 앞당기거나 PR ①을 둘(queue-peak 먼저, 하한 다음)로 나누는 안을 시뮬레이션으로 다시 본다.
- V4에서 예매 p95가 기준을 넘으면: queue-peak가 켜질 때 예매 api requests도 올리는 안을 따로 검토한다(피크 api 노드는 9대 안에서 이미 따로 있다).
- 전체 되돌리기: #470을 revert하면 이전 구성(api·대기열 1100m, 평시 5대)으로 돌아간다.

## 5. 예상 시간·비용(예측)
