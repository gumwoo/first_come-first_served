## 1. 상황 (Context)
Kafka를 앱에서 뺀 뒤(P2b — [[ADR-028]]) 처음으로 Kafka 없이 클러스터를 기동했다(#415 스크립트). 이 세션의 목적은 셋이다.
1. **B₁** — 기존 B 설정(api 3 고정·대기열 2~6·requests 1,100m·풀 5·5) 그대로의 같은 세션 기준선.
2. **B′** — 대기열 쪽 자원만 바꿔 노드-시간을 줄일 수 있는가(P1 대기열 풀 축소 → P3 대기열 requests 축소 + 노드 분산 → P2 대기열 상한).
3. **가용성 G1** — 최종 후보에서 노드 1대를 갑자기 잃어도 핵심 경로가 계속 도는가.

판정식·허용 폭·목표는 각 단계의 결과를 보기 전에 사전 등록했다(B′의 허용 폭·노드-시간 목표는 설계대로 B₁ 결과를 본 뒤, 첫 B′ run 전에 정했다)(각 문서의 변경 기록과 `session.log`의 사용자 결정 시각).

## 2. 문제 정의 + 분류
**대기열 쪽 자원(커넥션 풀·CPU 요청·상한)을 줄이거나 다시 나눠, 예매·대기열 지연을 B₁보다 나쁘게 하지 않으면서 노드-시간을 줄일 수 있는가.**
- 계층: 커넥션 풀(DB 예산 56)·CPU requests(노드 자리, HPA 기준선)·스케줄링(topologySpread)·자동 확장(HPA·CA).

## 6. 원인·관찰(실측과 추론을 나눠 적는다)
- **B₁이 B₀보다 예매가 느렸다**(② hold 417~510 vs B₀ 256~272ms). 확인한 것(실측):
  - 서버 쪽 p95가 늘었다(예매 ① 구간 max hold 385 vs B₀ 69ms). CPU 0.02~0.08코어·커넥션 대기 0(15초 표본)·Tomcat 바쁨 0·GC 0 — 자원은 놀았다.
  - 단독 요청은 빨랐다(경합 없는 hold 55~61ms·해제 45ms — api 파드 직결로 잰 값, `session.log`).
  - DB 왕복이 AZ에 따라 다르다: RDS 주 AZ(2c) 0.235~0.377ms, 2a 0.99~1.48ms, 2b 1.25~1.50ms(실측 — `SELECT 1` p50, 노드 고정 psql, 7회). 같은 시각 측정끼리의 비는 2a/2c 2.6~5.7배, 2b/2c 3.5~6.0배(계산). 이 세션의 api 파드는 모두 2c 밖(2a 1·2b 2).
  - RDS CPU ≤ 10.7%·크레딧 증가, Read/WriteLatency는 B₀ 세션과 같았다.
  - **추론(검증 안 함):** 100명 동시 예매가 api 3개 × 풀 5 = 15 커넥션을 기다릴 때 대기 시간은 트랜잭션 길이(DB 왕복 수 × 왕복 시간)에 비례하므로, api 파드의 AZ 배치가 예매 지연을 크게 좌우한다. B₀ 때 RDS 주 AZ는 확인하지 못했다(인스턴스를 다시 만들었고 생성 기록에 AZ가 없다).
  - 처리(사용자 결정): 배치를 고정하지 않고 run마다 AZ 구성·AZ별 DB 왕복을 기록했다. 모든 B′ run의 api AZ 구성은 B₁과 같았다.
- **P1(풀 3)에서 커넥션 타임아웃·대기(pending) 신호는 없었다**(기록 — 판정 항목 아님): 타임아웃 0·pending 0(15초 표본), 폭증 중 예매 사용자 진입 p95 430·433ms(B₁ 576·683ms — 실측). 대기열 파드 커넥션 획득 시간 최댓값은 오히려 늘었다(798·219ms, B₁ 650·132ms — 실측) — 획득 시간 증가도 대기 신호일 수 있어, 풀 3이 진입에 영향이 없다고 단정하지 않는다. 첫 run 값이 큰 것은 폭증 중 새로 뜬 파드의 연결 생성이 섞인 것으로 본다(추론).
- **P3에서 노드당 대기열 2개는 한 번도 생기지 않았다**(실측 — `app_pod_nodes` 10초 표본): 대기열이 최대 6개일 때도 노드당 1개. hostname topologySpread(maxSkew 1·`DoNotSchedule`)가 대기열을 받을 수 없는 노드(api 노드 등)도 도메인으로 세는 쪽과 맞는다(추론 — Kubernetes PodTopologySpread는 nodeAffinity/nodeSelector를 만족하는 노드(기본은 taint 무시)를 자원과 무관하게 도메인으로 센다고 알려져 있다, 이 클러스터에서 따로 확인하지 않음). 그래서 P3는 사실상 "노드당 1개"였고, 노드 최대는 9 → 8로 줄었지만 노드-시간 절감은 2%에 그쳤다(계산). requests가 작아져 HPA가 더 일찍 확장할 것이라는 계산은 run마다 첫 확장 시각이 달라(T0 + 40~80초, 일부 run은 폭증 시작 때) 일관되게 관측되지 않았다(실측 — `hpa_desired`).

가벼운 부하(진입 6명/초 + 대기자 폴링, 예매 100명 묶음 둘)에서 EC2 인스턴스를 종료했다(승인 2회 — 둘 다 사용).

- **G1 결과: 두 run 모두 통과 → G1 통과**(가벼운 부하 — 폭증 중 G1은 말하지 않는다).
- 복구 경로가 달랐다(실측 — 이벤트):
  - g1-api: 대체 api 파드가 7초 만에 web 파드 하나를 **선점**(web priorityClass -1 — 설계)해 자리를 얻었다. 밀려난 web은 다른 노드에서 생성 3초 뒤 컨테이너 시작·약 7초 뒤 Ready 표본(web 가용 1이 약 5초).
  - g1-queue: 선점 없이 **CA 증설**(17초 뒤 노드 그룹 2→3, 새 인스턴스 17:45:14Z) → 새 노드에 약 52초 뒤 배치(이벤트 17:45:37Z) → 82초에 Ready.
- 종료된 인스턴스는 두 run 모두 **ASG가 대체**했다(실측 — ASG 활동: 종료 약 77·80초 뒤 새 인스턴스 시작). g1-api의 Ready 노드 6→5→6(17:10:59Z)이 이 대체 노드다. 대체 노드는 약 10분 뒤 CA가 줄였다(17:20:52Z·17:56:41Z). 복구(파드 Ready)는 두 run 모두 이 대체보다 먼저 끝났다.
- g1-api의 종료 +180초 묶음(②)은 p95 hold 1,217·주문 1,300·결제 1,234ms였다(기록 — 판정 항목 아님). 이 묶음은 api 복구(+54초)와 대체 노드 Ready(+122초)가 끝난 **뒤**에 돌았고, 실제 장애 구간의 묶음(① +30초)은 362·392·331ms로 더 빨랐다. ②가 느린 원인(예: 데우지 않은 대체 api 파드)은 확인하지 않았다(추론 후보).
- 대상 선정 규칙은 측정·복구 장치(Prometheus·kube-state-metrics·cluster-autoscaler)와 시스템 워크로드가 몰린 노드를 뺐다. 그래서 아래 위험은 **시험하지 않았고 계산으로만** 남는다.

## 8. 트레이드오프 / 한계 / 다음 개선
- 남은 G1 위험(계산·사실 — 시험 안 함):
  - web 파드 2개가 한 노드에 놓일 수 있다(web Deployment에 분산 규칙·affinity가 없다 — 사실). 그 노드를 잃으면 web이 전멸한다(사이트 중단 — 추론).
  - coredns 2개·Prometheus·kube-state-metrics가 한 노드에, cluster-autoscaler(1개)가 다른 한 노드에 있었다 — 그 노드 상실의 영향은 시험하지 않았다.
  - 다음 개선 후보: web hostname 분산(또는 anti-affinity), coredns 분산 확인.
- 노드-시간 절감 목표는 대기열 쪽 조정만으로 닿지 않았다. 다음 후보는 api 쪽(예매 경로 CPU-ms/req·api 2+2 구성, 계획 §2.2) 또는 노드 크기 — 별도 사전 등록이 필요하다.
- 예매 지연이 api 파드 AZ 배치(RDS 주 AZ와의 거리)에 크게 좌우될 수 있다는 추론은 검증하지 않았다. 확인하려면 api를 RDS 주 AZ에 둔 run과 아닌 run을 같은 조건으로 비교해야 한다.
- 모든 판정은 후보당 2회 관측이고 부하 모델은 최악 가정(D2)이다.

## 9. 배운 점 (면접 답변용 한 줄)
"requests를 줄이면 노드당 파드가 늘 것"이라는 계산은 스케줄러의 분산 규칙(도메인 계산) 앞에서 성립하지 않았다 — 자원 최적화는 계산 뒤에 배치를 실측으로 확인해야 하고, 결과를 보기 전에 판정식을 고정해야 개선을 과장하지 않는다.
