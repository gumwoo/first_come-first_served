# TS-034 · knee를 다시 재려다 세 번 어긋났다 — 경로·발생기·노드를 통제하지 못하면 부하 측정은 자기 자신을 잰다

- 슬라이스: S10(부하·확장)
- 날짜: 2026-08-22
- 유형: **측정 방법론 실패 회고** (결과 문서가 아니다)
- 관련: [[IMP-020]] §9(측정을 망칠 뻔한 다섯 가지), [[ADR-012]] §5(부하테스트용 인스턴스),
  [[TS-021]](HPA × 커넥션 풀), `docs/testing/loadtest-plan.md`
- 상태: **미해결** — knee를 재측정하지 못했다. 무엇을 통제해야 하는지만 확정했다

## 0. 하려던 것

2026-08-11 측정의 `capacity knee 600~650 rps`는 그 뒤 [[IMP-018]](KOPIS 핫패스 제거)·캐시 실험·
폴링 백오프가 들어가면서 **낡았다.** 클러스터가 떠 있는 김에 다시 재려 했다.

콜드 스타트·파드 수 변동·측정 중첩은 [[IMP-020]] §9에서 이미 겪어 절차에 반영했다.
**그런데 이번엔 그 목록에 없던 것 셋에 걸렸다.**

## 1. 첫 번째 — 경로를 우회했다

k6를 클러스터 **안에서** `http://flowticket-api`(API Service)로 쐈다. `k6-job.yaml` 주석이
권하는 방식이다 — *"로컬에서 쏘면 인터넷 RTT와 TLS가 섞이고 집 회선이 먼저 포화된다."*

결과는 근사해 보였다.

| 도착률 | p95 | 실패 |
|---|---|---|
| 600 | 13.4ms | 0% |
| 1000 | 32.6ms | 0% |
| 1400 | 170.6ms | 0% |

2026-08-11에는 600 rps에서 실패 4.06%·p95 10초였으니 **"knee가 2.5배 이동했다"**로 보였다.

**틀렸다.** CloudWatch를 열어보니

```
지난 1시간 ALB RequestCount: 5.0
```

**170만 건이 ALB를 하나도 지나가지 않았다.** api Service로 직접 쏘면 ALB와 web(Next.js) 티어가
경로에서 빠진다. 그런데 **2026-08-11의 knee는 정확히 그 ALB→web 구간이었다**
(`TargetConnectionError 457 / Target_5XX 0`).

> 병목이던 구간을 빼고 잰 뒤 "좋아졌다"고 한 것이다. 개선이 아니라 **다른 것을 잰 것**이다.

⚠️ `k6-job.yaml`의 조언은 옳다. 다만 **그 방식이 ALB·web을 경로에서 제거한다는 대가**가
적혀 있지 않았고, 나도 확인하지 않고 썼다.

## 2. 두 번째 — 부하 발생기가 먼저 죽었다

경로를 `https://flow-ticket.com/api`로 바꾸자(발생기는 클러스터 안에 그대로 둬서 집 회선
변수는 없앤 채) 응답이 느려졌고, 도착률을 유지하려 k6가 VU를 계속 늘렸다.

```
0976/3103 VUs → 1143 → 1375 → 1723 → 2187 …
→ OOMKilled (memory limit 1Gi)
```

**측정이 아니라 내 도구가 터진 것이다.** 앞선 400 rps 단계의 `dropped_iterations 3,331`도
서버가 못 받은 것인지 k6가 VU를 못 늘린 것인지 **구분할 수 없다.**

`loadtest-plan.md`는 이미 경고하고 있었다 — *"preAllocated가 부족하면 k6가 스스로 병목이 되어
도착률을 못 채운다."* 스크립트는 `preAllocatedVUs`를 넉넉히 잡았지만, **VU를 늘릴 메모리가
없으면 결과는 같다.** 컨테이너 자원 제한이 그 역할을 했다.

## 3. 세 번째 — 부하 발생기가 측정 대상과 CPU를 나눠 썼다

메모리를 3Gi로 올려 다시 쟀다. 이번엔 죽지 않았지만 결과가 이상했다.

| 관측 지점 | p95 | p99 |
|---|---|---|
| k6(클라이언트) | 9.9s | 19.2s |
| **앱(api 히스토그램)** | **1.95s** | 4.65s |

2026-08-11의 패턴(k6 2,769ms vs 앱 27ms = 100배 차이 → 병목은 앞단)과 **다르다.**
이번엔 앱 자체가 느렸다. 그런데 원인 후보가 차례로 탈락했다.

- **NAT 아님** — `ErrorPortAllocation 0`, `PacketsDropCount 0`
- **DB 커넥션 풀 아님** — `hikaricp_connections_pending`이 구간 내내 **0**
- **CPU 스로틀링 아님** — api·web에 CPU limits가 없어 스로틀 자체가 없다

남은 것은 **노드 CPU 경합**이었다.

```
노드 전체 CPU (core, 분당): 0.4 → 2.69 → 5.01 → 5.41 → 4.02 → 2.07
allocatable 5.79 core → 정점 93%
```

`web-hpa.yaml`이 적어 둔 예산 계산이 실제로 닿은 것이다.

```
api 7×300 + web 4×300 + 기타 1,650 = 4,950m (85%)
```

**HPA는 정상 작동했다** — api 3→7, web 2→4로 늘었다. 그 결과가 오히려 노드를 채웠고,
거기에 **k6가 같은 노드에서 최대 0.59 core를 더 썼다.**

> 요청당 CPU가 싼 경로(api 직접)에서는 드러나지 않았다. web 티어가 끼면서 총량이 한계에
> 닿자, **부하 발생기의 CPU 사용이 결과를 오염시켰다.**

## 4. 그래서 무엇을 말할 수 있나

**knee는 재측정하지 못했다.** 두 경로가 서로 다른 답을 주고, 양쪽 다 오염되었다.

| 구간 | 노드 CPU | 판정 |
|---|---|---|
| api 직접, ~1000 rps | 최대 3.3 core (57%) | **비교적 깨끗** |
| api 직접, 1400~1800 rps | 최대 4.79 core (83%) | 오염 |
| 전 경로, 400 rps | 최대 5.41 core (93%) | 오염 |

말할 수 있는 것은 여기까지다.

- **api 티어 단독**(ALB·web 우회)은 1000 rps까지 p95 33ms 이하를 유지했다
- 그 경로의 1800 rps 시도에서 `hikaricp_connections_active`가 **파드당 5(풀 상한)**에 붙고
  `pending`이 **116**까지 쌓였다 — 그 구간의 제약은 CPU가 아니라 커넥션 풀이었다
  ([[TS-021]]에서 RDS 슬롯 때문에 10→5로 낮춘 결정이 처리량 상한으로 나타난 것)
- **전 경로의 knee는 알 수 없다.** 400 rps에서 무너진 것은 시스템이 아니라
  "k6와 앱이 3노드를 나눠 쓰는 구성"이다

## 5. 도중에 내가 틀린 판단 하나

`[pods] api=3 web=2`를 보고 **"HPA가 안 늘었다"**고 적었다. 그건 **k6 Job이 끝난 뒤의
스냅샷**이었고, 시계열을 보니 구간 내내 7과 4였다.

```
api replicas: 3 3 3 7 7 7 7 7 7 7 7 3 3 3 3 3
web replicas: 2 2 2 4 4 4 4 4 4 4 4 2 2 2 2 2
```

[[IMP-020]] §9가 *"구간 내 파드 수 min/max를 검증하라"*고 적어 둔 항목인데,
**종료 시점 한 번만 찍어 정반대 결론에 갔다.** 절차를 알고도 구현에서 어긋난 사례다.

## 6. 다음에 이 측정을 하려면

**[[ADR-012]] §5에 이미 답이 있었다.**

> 부하테스트 때는 `m6i.large` 등 비버스터블로 바꾼다.

현재 `t3.large`(2 vCPU) × 3은 ADR이 **"기능·배포·페일오버 검증용"**이라고 명시한 구성이다.
**부하 측정에는 처음부터 부적합했고**, 나는 그 문장을 읽고도 그대로 쟀다.

통제해야 할 것을 정리하면:

| 통제 대상 | 방법 |
|---|---|
| **경로** | 무엇을 재는지 먼저 정한다. api 단독인가, 전 경로인가 — 둘은 다른 실험이다 |
| **발생기 자원** | 메모리·CPU를 넉넉히. VU 증가 추이와 `dropped_iterations`를 함께 본다 |
| **발생기 격리** | 전용 노드(taint/nodeSelector) 또는 클러스터 밖. **같은 노드는 안 된다** |
| **노드 여유** | 구간 내 노드 CPU가 70%를 넘으면 그 구간은 버린다 |
| 파드 수 | 구간 **내** min/max (종료 스냅샷 아님) |

## 7. 배운 것

세 번 다 같은 모양이었다 — **측정 장치가 측정 대상에 섞였다.**

1. 경로에서 **빼서** 다른 것을 쟀고
2. 발생기가 **먼저 죽어** 서버 한계처럼 보였고
3. 발생기가 **자원을 나눠 써** 대상을 느리게 만들었다

> "몇 rps 나왔다"보다 **"그 숫자를 만든 조건이 통제됐는가"**가 먼저다.
> 통제되지 않은 측정은 시스템이 아니라 **측정 환경을 잰다.**

[[IMP-020]] §9의 다섯 가지에 이 세 가지를 더한다. 그 문서가
*"수치가 이상하면 시스템을 의심하기 전에 측정 조건이 고정됐는지 먼저 본다"*로 끝나는데,
이번에는 **수치가 이상하지 않아서 더 오래 못 알아봤다** — 첫 결과는 "2.5배 개선"으로
그럴듯했다.

## 8. 한계

- **재측정하지 않았다.** 노드 교체는 비용이 들고, 끝나도 `m6i.large` 기준이라 2026-08-11
  수치와 또 비교되지 않는다. 그 판단으로 여기서 멈췄다.
- 전 경로 측정은 **NAT를 지난다**(k6가 클러스터 안 → 인터넷 → ALB). 실제 사용자 경로와
  같지 않다. 이번에는 NAT가 병목이 아님을 확인했지만, 규모가 커지면 달라질 수 있다.
- **`hikaricp_connections_pending` 116**은 api 직접 경로의 1800 rps 시도에서 나온 값이고,
  그 구간도 노드 CPU 83%로 오염돼 있다. "풀이 병목"이라는 해석은 **정황이지 확정이 아니다.**
