# TS-021 · 파드를 늘렸더니 DB가 한계였다 — HPA 최대치 × 커넥션 풀 > RDS 슬롯

- 슬라이스: S09(배포/운영)
- 날짜: 2026-08-09
- 유형: 용량 결함(설정) — **스케일아웃이 스스로를 깨뜨림**
- 관련: [[TS-019]](HPA·metrics-server), [[IMP-015]](롤링 무중단), `k8s/base/api-hpa.yaml`, `application.yml`
- 상태: **원인 규명 완료, 수정 미결** — 방안별 트레이드오프가 갈려 §6에 정리

## 1. 어떻게 발견했나 — 성능 측정을 하려다 걸렸다

관측 스택([[IMP-013]] 계열 작업)으로 `/events/{id}`의 p95가 높은 것을 찾아 원인(외부 API 동기
호출)까지 좁힌 뒤, 개선 전후를 비교하려고 **AS-IS 기준선을 재려던 참**이었다.

k6를 50 VU로 돌렸는데 값이 이상했다. 같은 프로파일을 30분 전에 돌렸을 때와 4~8배 차이가 났다.

```
30분 전 50 VU : p95 417ms   p99 980ms    388 req/s
방금  50 VU   : p95 807ms   p99 9.88s    120 req/s   max 30.15s
```

측정 오차로 볼 수 있는 폭이 아니었다. 파드 상태를 봤다.

```
flowticket-api-...-8b66n   CrashLoopBackOff
flowticket-api-...-pcswv   CrashLoopBackOff
```

**9개 중 2개가 죽어 있었다.** 부하는 7개가 받고 있었고, 그래서 수치가 나빴다.

## 2. 증상 — 파드가 기동조차 못 한다

```
Startup probe failed: connect: connection refused
Back-off restarting failed container api
Exit Code: 1
```

이전 컨테이너 로그의 끝:

```
org.postgresql.util.PSQLException: FATAL: remaining connection slots are reserved for
  roles with privileges of the "rds_reserved" role
	at HikariPool.checkFailFast(HikariPool.java:550)
	at FlywayExecutor.execute(...)
	at FlywayMigrationInitializer.afterPropertiesSet(...)
```

**Flyway가 마이그레이션을 하려고 첫 커넥션을 여는 지점에서 죽었다.** 애플리케이션 로직에
닿기도 전이라 부분 동작조차 없다 — 완전한 기동 실패다.

## 3. 원인 — 산술이 애초에 맞지 않았다

DB에 직접 물어봤다.

```sql
select name, setting from pg_settings
 where name in ('max_connections','superuser_reserved_connections');
```

| 항목 | 값 | 출처 |
|---|---|---|
| `max_connections` | **79** | db.t4g.micro의 실제 값(추정 아님) |
| `superuser_reserved_connections` | 3 | |
| 앱이 쓸 수 있는 실질 한도 | **76** | |
| 조사 시점 총 커넥션 | 71 | 앱 64 + rdsadmin 3 + 기타 4 |

그리고 우리 쪽 설정:

| 항목 | 값 | 비고 |
|---|---|---|
| HPA `maxReplicas` | **9** | `k8s/base/api-hpa.yaml` |
| Hikari `maximum-pool-size` | **10** | `application.yml`에 **설정이 없어 기본값** |

```
9 파드 × 10 커넥션 = 90  >  76
```

**최대로 스케일아웃하면 반드시 터지는 구조다.** 7개까지는 70으로 버티고, 8번째부터 슬롯을 얻지
못한다. 실측된 파드별 점유가 정확히 그 모양이었다.

```
6kszh 10   q92ks 10   f8n5k 10   tklq5 10   dffzl 10   grzp2 10   ppk48 7   → 합계 67
(나머지 2개는 CrashLoopBackOff — 슬롯을 못 얻음)
```

**이번 배포가 만든 결함이 아니다.** HPA max 9와 풀 기본값 10이 공존한 시점부터 있었고, 오늘
처음으로 부하가 9까지 밀어올려서 드러났다. [[TS-019]]에서 HPA 스케일업을 실증했을 때는 3→4까지만
올라가 40 커넥션이었다 — **그 실증이 통과했다는 사실이 안전을 보장하지 않았다.**

## 4. 왜 아무도 미리 몰랐나

세 가지가 겹쳤다.

1. **한쪽만 보면 둘 다 합리적이다.** HPA max 9는 트래픽 대비 타당하고, 풀 10은 Hikari 기본값이다.
   문제는 **곱**인데, 그 곱을 계산하는 자리가 없었다.
2. **설정이 두 저장소 영역에 흩어져 있다.** `maxReplicas`는 `k8s/`, 풀 크기는 `application.yml`,
   `max_connections`는 **AWS 콘솔 바깥의 인스턴스 클래스에서 파생**된다. 셋을 한 화면에서 본 적이 없다.
3. **부하를 최대치까지 밀어본 적이 없었다.** 기존 실증은 3→4 스케일업 확인에서 멈췄다.

## 5. 측정으로 본 커넥션 사용 실태

수정 방향을 정하려고 부하 구간(30분)의 최댓값을 뽑았다.

| 지표 | 값 |
|---|---|
| 점유 커넥션 합계 | **67** |
| 동시 `active` 합계 최대 | **21** |
| 한 파드의 `active` 최대 | **10** (풀을 다 씀) |
| `pending`(대기) 최대 | **16** |

이 표는 한 방향으로 읽히지 않는다. **처음에는 "점유 67인데 실제 사용은 21이니 풀을 줄이면
된다"고 봤는데, 뒤의 두 줄이 그 결론을 흔든다.** 어떤 파드는 풀 10개를 전부 쓰고도 16건이
대기했다. 풀을 5로 줄이면 그 파드는 더 나빠진다.

다만 이 `pending`은 **파드 2개가 죽어 7개가 부하를 받던 구간**의 값이라 정상 상태의 수치가
아니다. 정상 9개 상태에서 다시 재야 판단할 수 있다 — **아직 재지 못했다.**

## 6. 수정 방안 — 아직 고르지 않았다

| 방안 | 총 커넥션 | 장점 | 대가 |
|---|---|---|---|
| Hikari 풀 10 → 5 | 9×5 = 45 | 코드 한 줄, 여유 확보 | 파드당 동시 처리량 감소. §5의 `pending`을 악화시킬 수 있음 |
| HPA max 9 → 7 | 7×10 = 70 | 산술이 맞음 | **확장 여력을 포기** — 부하가 커지면 그대로 막힌다 |
| RDS 인스턴스 상향 | 한도 자체 증가 | 근본적 | 비용. 데모 환경에 상시 부담 |
| RDS Proxy / pgbouncer | 앱-DB 사이에서 다중화 | 스케일아웃과 DB 한도를 **분리** | 구성 요소 추가, 비용 |

**교과서적 정답은 커넥션 풀러(RDS Proxy·pgbouncer)다.** 무상태 계층의 확장과 DB 커넥션 수를
분리하는 것이 이 문제의 본질이기 때문이다. 다만 데모 환경의 비용/복잡도와 견줘야 하므로
별도 결정(ADR)으로 다룬다.

**어느 방안을 고르든 지켜야 할 불변식은 하나다.**

```
HPA maxReplicas × Hikari maximum-pool-size  ≤  max_connections − reserved
```

이 식이 코드 어디에도 표현돼 있지 않다는 것이 진짜 문제다. 하네스 규칙으로 강제할 수 있는
형태인지 검토한다(세 값 중 `max_connections`가 저장소 밖이라 그대로는 어렵다 — 인스턴스
클래스별 값을 상수로 두고 검사하는 방법을 고려).

## 7. 측정에 미친 영향

이 사고로 **오늘의 AS-IS 기준선은 무효다.** 파드 2개가 죽은 상태에서 잰 값이라 개선 전후
비교에 쓸 수 없다. 수정 후 정상 9개 상태에서 다시 재야 한다.

성능 측정을 하려다 성능이 아닌 결함을 찾았고, 그 결함이 다시 측정을 막았다.

## 8. 교훈

1. **스케일아웃은 공짜가 아니다.** 무상태 계층을 늘리면 그 뒤의 상태 있는 자원(DB 커넥션,
   파일 핸들, 외부 API 쿼터)에 **비례해서** 압력이 간다. 늘어나는 쪽만 보면 놓친다.
2. **"실증했다"의 범위를 정확히 말해야 한다.** [[TS-019]]에서 확인한 것은 "3→4 스케일업이
   동작한다"였지 "최대치까지 안전하다"가 아니었다. 부분 실증을 전체 보장으로 읽으면 이런 게 남는다.
3. **곱셈으로 결정되는 한도는 곱하는 자리가 코드에 있어야 한다.** 두 값이 각자 합리적이어도
   곱이 한도를 넘을 수 있고, 그 계산은 아무 파일에도 적혀 있지 않았다.
4. **같은 측정을 두 번 해서 값이 크게 다르면 시스템 상태부터 의심하라.** 재실행으로 넘겼다면
   이 결함을 놓치고 잘못된 기준선으로 개선폭을 주장했을 것이다.
5. **기본값은 선택이 아니다.** Hikari 풀 10은 우리가 고른 값이 아니라 안 고른 결과였다.
   [[TS-020]]의 직렬화기, [[TS-019]]의 metrics-server와 같은 계열 — **정하지 않은 것이 정해진다.**
