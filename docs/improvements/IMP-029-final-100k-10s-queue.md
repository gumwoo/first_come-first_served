## 1. 상황 (Context)
[[ADR-023]]은 10만 burst를 두 축으로 나눠 고치고(축 ① 진입 경로: [[ADR-024]]·[[IMP-025]]~[[IMP-027]], 축 ② 대기 상태 전달: [[IMP-028]]·폴링 주 경로),
마지막에 합쳐서 재기로 했다(시험 ⑤, 10만 burst → 대기 → 입장 → 좌석·주문). 이 문서는 그중 대기열 부분(진입 → 대기·폴링 → 입장 제어)의 결과이고, 좌석·주문은 범위 밖이다.
"100K를 검증했다"고 쓸 수 있는 조건은 [loadtest-100k-plan](../testing/loadtest-100k-plan.md) §8의 7축이다.

## 2. 문제 정의 + 분류
100,000명이 10초 동안 진입할 때(target 10,000 req/s) 대기열 계층이 진입을 모두 받고, 대기자 전원의 상태 폴링을 오류 없이 처리하며,
정원(100) 이상을 downstream으로 내보내지 않는지 확인한다. 그 결과가 발생기 한계와 분리된 시스템 결과인지도 함께 확인한다.
- 계층 분류: 애플리케이션 처리 용량(api CPU) / Redis(단일 스레드) / 네트워크(ALB) / 부하 발생기(측정 도구) / 동시성(입장 정원)
- 범위: 대기열 진입 + 대기(상태 폴링) + 입장 제어 + 정합성. 좌석·주문·결제는 범위 밖이다(§8).

## 3. 증상 (측정된 증거): 측정 방법
- 구성(세션 한정 사전 확장, [[IMP-027]]과 같다, Git 변경 아님): 노드 9(m6i.large, AZ당 3), api 9(노드당 1, 노드 단위 분산 패치), web 2,
  HPA api 9/9 고정, `requests.cpu` 300m. Redis `cache.t4g.micro`(단일 스레드), RDS `db.t4g.micro`.
- 부하: 공개 ALB, 발생기 c6i.xlarge 3대, 공통 시작 시각 T0(START_AT 장벽), T0 전 30초 동안 연결 미리 맺기(#347),
  발생기당 constant `--rate 3400` → 몫 33,333~33,334명이 약 9.8초에 소진(계산), 겹치지 않는 사용자 100,000명.
  진입 응답이 WAITING인 토큰 전부를 대기자 폴링 발생기(`poll-hold.mjs`)가 받아 첫 토큰부터 420초 동안 프론트와 같은 규칙
  (`max(2초, retryAfterMs)` + jitter 20%, 오류 시 2→30초 백오프)으로 상태를 묻는다. 420초 = 입장 TTL 300초 + 여유로, 정원이 한 번 회수돼 폴링 중 승격을 볼 수 있다.
- 도착 판정은 ALB access log의 `request_creation_time`으로 한다. k6의 iteration 시작은 클라이언트 의도라 서버 도착 증거로 쓰지 않는다([[IMP-027]] §8).
  창은 시험 전에 고정한 [T0, T0+10.000s)이며, 가장 잘 나온 창을 고르지 않는다.
- run: 워밍업 1회(판정 제외) + 판정 3회, run마다 대기열 키 리셋(삭제 확인)·재사용 공연.

## 4. 가설 (사전 등록, 결과 보기 전)
축 ①·② 개선과 사전 확장(api 9·노드 9)으로, 10,000/s × 10초 진입과 대기 10만 명의 폴링을 함께 받아도 6축(Traffic·Queue·Protection·대기 상태 전달·Correctness·Generator)이
판정 3회 모두 충족한다. Platform 축(반응형 확장·축소)은 판정 run과 분리해 시연한다(§5).

## 5. 검증: 사전 등록 버전과 그 사이에 바뀐 것
판정 기준이나 측정 도구를 바꿀 때마다 사전 등록 문서를 새 버전으로 남기고, 바꾼 것과 이유·시점을 기록했다. 이 문서의 판정은 v3 기준 3회만 쓴다.

- 판정 run 전 결정: 워밍업 run(`INVALID-f-100k-warm-30k`)에서 HPA가 10으로 늘었다 줄며 10번째 파드를 지워, 그 파드의 감사 로그가 빠지고
  사후 검사가 판정 불가가 됐다. 그래서 판정 3회는 HPA 9/9로 고정하고 Platform 축은 별도로 시연한다(사용자 결정).
- v1(`final-prereg.md`, `f2-100k-r1~r3`, `--rate 3350`): 2개 축 미충족.
  - Traffic: r2의 ALB 창 안 진입이 99,982건이었다(18건이 T0+10s 뒤). 발생기 마지막 송신은 T0+9,951~9,953ms(k6)로 창 끝까지 여유가 약 47ms였다.
  - 대기 상태 전달: r1 폴링 네트워크 오류 2건(연결 오류, 재사용 keep-alive 소켓 경합으로 추정).
- v2(`final-prereg-v2.md`, `f3-100k-r1~r3`): `--rate 3400`(송신 여유 약 200ms, 계산)으로 올리고, 폴링 발생기가 재사용 소켓 `ECONNRESET`이면
  다른 소켓으로 1회 재시도하게 했다(#355, 브라우저의 자동 재전송을 흉내). 재시도가 실패를 가리지 않도록 발생기별 재시도 ≤ 그 발생기 조회의 0.01%(약 42건, 계산)를
  충족 조건에 더했다(사용자 결정). v1의 두 축은 충족했고(ALB 창 안 100,000×3, 폴링 오류 0, 재시도 0), 2개 축이 미충족이었다.
  - Traffic 초별: 마지막 bucket 8,233 / 8,371 / 8,228이 "10,000 ± 15%" 밖이었다. `--rate 3400`이면 몫이 약 9.8초에 소진돼 마지막 초가 부분 초가 되는데,
    v2 기준의 마지막 bucket 기대치에 이것이 반영되지 않았다.
  - Generator: 발생기 g3 CPU 1초 최대 80 / 82 / 81%(기준 < 80%). 피크는 진입 burst 구간이다(확인).
- v3(`final-prereg-v3.md`, `f4-100k-r1~r3`, 사용자 결정, 판정 run 전 확정):
  ① 초별 기준을 계획 도착 곡선 기준으로 바꿨다. bucket 0~8 기대 10,200, bucket 9 기대 약 8,200(계산), 각 ±15%(v1·v2와 같은 폭).
  ② 발생기 k6 출력 줄이기(#356, 읽지 않는 태그·check 제거). 진단 run `d-lean-cpu`(판정 제외)에서 발생기 CPU 1초 최대 54 / 53 / 69%, JSON −26%를 확인한 뒤 확정.
  그 밖의 구성·기준·무효 조건·run 수는 v2와 같다. v1·v2의 판정은 각 버전 기준의 미충족 그대로 둔다.

  창이 :00을 지난 이전 run(f2-r1·f2-r2·f3-r3)에서는 그 순간 진입 지연(100ms 평균)이 약 0.2~0.3s로 튀었다(실측). 6축 충족은 분 경계를 지나지 않는 창에서의 결과다.
  분 경계 현상은 [[TS-042]]에서 다룬다.
- Redis 메인 스레드는 burst 중 2초 표본 최대 0.885~0.887코어였다(run별 범위는 §7 표, 단일 스레드 `cache.t4g.micro`). 도착률이 더 높아지면 Redis가 다음 한계 후보가 된다.
- 진입 지연 꼬리는 run마다 다르다(r3 진입 p99 204.5ms).
- 입장 인지 지연 p95 약 2.3초는 폴링 최소 간격(앞쪽 2초) + jitter에서 오는 값으로 본다(추론). 표본은 run마다 200명(앞쪽 순번)이고, 뒤쪽 순번(최대 30초 간격)은 표본에 없다.
- 발생기는 3대·c6i.xlarge·vCPU 쿼터 안에서 맞췄고, 1초 최대 CPU는 74%였다.

## 9. 배운 점 (면접 답변용 한 줄)
10만 명 / 10초를 ALB access log의 서버 도착 시각으로 고정 창 안에서 세고, 대기자 10만 명의 폴링·입장 인지 지연·정원 초과·발생기 한계까지 축별 기준을 먼저 정해
판정했다. 기준에 못 미친 원인(송신 여유·소켓 경합·마지막 초 기대치·발생기 CPU)을 원시 데이터로 나누고, 바꾼 것을 사전 등록 버전으로 남긴 뒤 v3에서 6축을 3회 모두 충족했다.
