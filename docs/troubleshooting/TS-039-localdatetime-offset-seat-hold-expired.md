# TS-039 · 좌석을 고르자마자 "만료" — 응답 시각에 오프셋이 없어 브라우저가 9시간 과거로 읽었다

- 슬라이스: S04(좌석) — 배포 환경에서 발견
- 날짜: 2026-08-09
- 유형: 결함 수정 — 로컬에서 재현되지 않는 환경 의존 버그
- 관련: `JacksonConfig`, 하네스 backend 규칙 16 · k8s 규칙 7, 커밋 `b623080`
- 상태: **해결** — 직렬화에 오프셋을 붙이고 정적 규칙으로 막았다

## 1. 증상

배포 환경에서 좌석을 고르고 '선택 완료'를 누르면 곧바로 만료 화면으로 넘어갔다.
남은 시간 표시는 5분에서 정상적으로 줄어들고 있었고, 에러 응답도 없었다.

## 2. 원인

응답의 `LocalDateTime`이 오프셋 없이 직렬화됐다.

```
"expiresAt": "2026-08-09T06:56:54"      ← 타임존 정보 없음
```

JS의 `new Date("2026-08-09T06:56:54")`는 오프셋이 없는 날짜-시각 문자열을 **브라우저 로컬 시간**으로
해석한다(ES 명세). 서버 컨테이너는 UTC, 사용자는 KST라 만료 시각이 9시간 과거가 되고,
프론트는 "이미 만료"로 판정했다.

로컬에서는 재현되지 않는다. JVM과 브라우저가 둘 다 KST라 차이가 0이다.

같은 원인이 마이페이지 날짜에도 있었다. 서버 시각 문자열을 `slice(0, 10)`으로 잘라 쓰면
서버 존(UTC)의 날짜가 나와, KST 자정~09시에 결제한 예매가 하루 전날로 표시된다.

## 3. 해결

- `JacksonConfig`가 `LocalDateTime`을 **서버 시스템 존의 오프셋을 붙여** 내보낸다
  (`2026-08-09T06:56:54Z` 형태). 엔티티가 `LocalDateTime.now()`(시스템 존)로 값을 만들므로
  되돌릴 때도 같은 존을 써야 한다. 전 엔드포인트가 한 번에 정상화된다.
- 서버 시각 문자열을 잘라 쓰던 프론트 두 곳을 `Date` 파싱으로 바꿨다.
- 요청 바디에는 `LocalDateTime` 필드가 없어 역직렬화 쪽은 영향이 없다.

더 원칙적인 수정은 "순간"을 뜻하는 필드를 `Instant`/`timestamptz`로 바꾸는 것이다.
DTO·매퍼·스키마를 동시에 건드려야 해서 나가는 표현만 먼저 고쳤다.

## 4. 재발 방지

로컬 테스트로는 잡히지 않으므로 정적 규칙으로 막는다.

- **backend 규칙 16**: `LocalDateTime` 전용 직렬화기가 존 오프셋을 붙이는 설정이 있어야 통과
  (위반 fixture `be-naive-datetime`).
- **k8s 규칙 7**: API 컨테이너의 `TZ`가 UTC로 고정돼 있어야 통과(위반 fixture `k8s-no-tz-pin`).
  DB에는 UTC 벽시계가 쌓여 있으므로, 컨테이너 존이 바뀌면 이미 저장된 행의 절대 시각이
  통째로 이동한다. 존을 바꾸려면 `Instant`/`timestamptz` 전환이 선행돼야 한다.

## 5. 한계

- 당시 브라우저 콘솔·네트워크 응답을 캡처해 두지 않았다. 위 증상과 원인은 수정 커밋
  메시지와 코드 변경을 근거로 다시 정리한 것이다.
