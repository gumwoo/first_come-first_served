# TS-055 · 결제·좌석 경합 경로 4건: 순서가 어긋나면 승인이 남거나 새 선점이 풀렸다

- 날짜: 2026-11-02
- 영역: 결제(`PaymentService`·`PaymentReconciliationService`), 좌석(`SeatService`)
- 결과: **수정**. 통합 테스트로 순서를 고정해 수정 전 실패를 CI에서 확인했다. 실제 PG와 운영 부하로 재현한 장애는 아니다.
- 관련: [[TS-011]](좌석 만료가 먼저인 경합), [[ADR-006]](조건부 전이), [[ADR-011]](정산), `RefundService.rejectIfKeyBelongsToAnotherOrder`

## 증상
외부 코드 리뷰가 지적한 경로를 코드로 확인했다. 운영에서 관측한 장애가 아니라 코드에서 도출한 실행 경로다.

| # | 순서 | 결과 |
|---|---|---|
| 1 | PG 응답을 기다리는 동안 주문 만료 sweep이 먼저 돈다 → 승인 성공 → `markPaid` 0행 | 결제 `APPROVED`, 주문 `EXPIRED`로 커밋. 즉시 보상 취소 없음 |
| 2 | 해제 요청이 `HELD`를 읽음 → 만료 sweep → 다른 사용자가 같은 좌석 선점 → 해제가 이어서 실행 | 새 선점의 좌석이 `AVAILABLE`이 되고, 끝난 홀드가 `RELEASED`로 덮어써진다 |
| 3 | 정산이 오래된 순으로 첫 50건만 조회, 확인 표시 없음 | 51번째 이후의 미아 승인은 앞쪽이 소급 한계를 벗어날 때까지 조회되지 않는다 |
| 4 | 다른 주문의 멱등키로 결제 요청 | PG 호출 없이 다른 주문의 결제 ID·상태를 응답 |

독립 리뷰에서 같은 유형을 두 건 더 찾았다.
- `markVbankWaiting` 0행을 넘겨, 발급 중 주문이 끝나도 입금 대기 응답과 계좌를 돌려줬다(Mock 경로에서만 도달한다. 실제 Toss의 `issueVbank`는 예외를 던진다).
- 보상 취소의 결과를 보지 않았다. 게이트웨이는 실패를 예외가 아니라 결과로 돌려주므로 실패 로그가 찍히지 않았고, 확정 롤백으로 `pg_tid`도 지워져 PG에 남은 승인의 단서가 DB에 없었다.

## 원인
1. `finalizePaid`가 `markPaid` 1행일 때만 처리하고 0행은 그대로 정상 종료했다. [[TS-011]]은 좌석 만료가 먼저인 순서(주문은 아직 `PENDING`, `sellSeats` 0행)를 막았고, 주문 만료가 먼저인 순서는 테스트에도 없었다. 주문과 좌석은 sweep이 따로 돌아 어느 쪽이든 먼저 될 수 있다.
2. `SeatHold`에는 `@Version`이 없어 `release()`가 읽은 상태를 다시 확인하지 않고 덮어썼다. `releaseSeats`는 좌석 ID와 `HELD`만 보므로 어느 홀드의 `HELD`인지 구분하지 못한다. `Seat`의 `@Version`은 bulk UPDATE에 적용되지 않는다.
3. 환불 정산은 `checked_at`으로 순회하도록 이미 고쳤고(ADR-011 추가 결정 6), 결제 정산은 같은 문제를 남겨 둔 상태였다.
4. `startPayment`가 멱등키로만 찾고 주문을 비교하지 않았다. 환불 쪽에는 같은 검사가 있다.

## 수정
1. `markPaid`가 0행이면 예외를 던진다. 승인 경로는 기존 `settle`이 보상 취소 후 결제를 `FAILED`로 남긴다. 단, 입금 경로에서 주문이 이미 `PAID`면 같은 입금이 동시에 두 번 들어온 것이라 그대로 끝낸다. 이 구분이 없으면 웹훅 재전송이 겹칠 때 뒤쪽이 실패로 돌아간다.
2. 해제를 조건부 UPDATE(`releaseHold`, `WHERE status='HELD'`)로 바꾸고 1행일 때만 좌석을 푼다. 만료 sweep도 같은 방식이므로, 홀드 전이에 이긴 쪽만 좌석을 푼다.
3. `orders.reconcile_checked_at`을 추가해(V22) 한 번도 안 본 주문부터 순회하고, 조회한 주문은 재조회 간격(기본 60분) 동안 건너뛴다. 조회·취소에 실패한 건도 표시한다. 표시하지 않으면 그 건이 매 틱 선두로 돌아온다.
4. 멱등키의 주인이 다른 주문이면 `VALIDATION_ERROR`로 거절한다. 존재 확인과 UNIQUE 충돌 경로 둘 다 본다. 충돌 경로는 앞 요청이 커밋되기 전이라 존재 확인을 지나친다.
5. `markVbankWaiting`이 0행이면 예외를 던지고 결제를 `FAILED`로 남긴다. 계좌는 응답하지 않는다.
6. 보상 취소의 결과를 확인해 실패면 ERROR 로그를 남긴다. 확정하지 못한 승인은 취소 성공 여부와 무관하게 `FAILED` 결제 행에 승인 번호(`pg_tid`)를 기록한다. 그래서 `pg_tid`가 있어도 취소 실패를 뜻하지 않으며, 실패 여부는 ERROR 로그로 구분한다.

## 트레이드오프
- **정산이 다시 묻는 간격이 늘었다.** 전에는 앞쪽 50건 안의 취소 실패를 10분마다 다시 시도했고, 이제는 재조회 간격(60분) 뒤에 시도한다. 환불 정산과 같은 선택이다. 대신 뒤쪽 후보가 굶지 않는다.
- **처리량 상한은 그대로다.** 배치 50 · 주기 10분이면 시간당 300건, 소급 한계 24시간 안에 7,200건이다(계산). 만료 주문이 그보다 많으면 일부는 조회 전에 한계를 벗어난다. `PAYMENT_RECONCILE_BATCH`로 늘릴 수 있고 PG 조회량이 그만큼 는다.
- **입금 처리와 주문 만료가 겹치면 입금이 확정되지 않는다.** 이전에는 결제가 `APPROVED`로 남았고, 이제는 롤백돼 `READY`로 남으며 그 웹훅은 409를 받는다. 재전송과 이미 만료된 뒤 온 웹훅은 주문 상태 검사에서 200 no-op으로 끝난다. PG에 남은 입금은 정산이 조회해 취소를 시도한다. 가상계좌 반환의 의미는 ADR-011의 한계 그대로 별도 검토 대상이다.
- **PAID 주문의 늦은 승인은 자동으로 회수하지 못한다.** 보상 취소까지 실패하면 ERROR 로그와 결제 행의 승인 번호로 사람이 처리한다. 정산 후보에 넣지 않았다. PAID는 승인이 남아 있는 게 정상이라 주문 기준 조회로는 구분되지 않는다. 실제 Toss가 한 주문번호에 승인 두 건을 내주는지는 확인하지 못했다(거절할 것으로 추측).

## 재발 방지
- 결제·좌석 경로의 조건부 전이는 0행의 뜻을 호출부가 정한다. 그냥 넘어가는 분기를 두지 않는다.
- 게이트웨이 호출은 예외뿐 아니라 결과도 확인한다. 실패를 결과로 돌려주는 계약이다.
- 상태를 읽고 쓰는 경로는 쓰기에서 상태를 다시 확인한다. 좌석처럼 소유자를 모르는 행은 소유 관계를 가진 행(홀드)의 전이에 이긴 쪽만 건드린다.
- 경합 테스트는 sleep이 아니라 행 잠금으로 세운다. 요청을 쓰기 직전에 세우고 `pg_stat_activity`로 대기를 확인한 뒤 끼어드는 작업을 실행하면 순서가 매번 같다.
