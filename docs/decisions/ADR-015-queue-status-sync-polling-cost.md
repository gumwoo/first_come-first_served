# ADR-015 · 대기열 상태 동기화 — onopen 재동기화로 복구를 만들고 폴링을 안전망으로 내린다

- 상태: **Partially Accepted** — ① 구현(#236) + **회귀 검증 완료**(#238).
  ③은 파라미터화까지(운영값 미변경), ②는 미착수
- 날짜: 2026-08-16
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-008]](SSE는 트리거, 진실원은 서버), [[TS-024]](승격 원자성),
  [cache-experiment-plan](../testing/cache-experiment-plan.md)

## 맥락

대기 화면(`useQueue`)은 SSE와 **2초 폴링을 함께** 돌린다. 대기자 수에 비례해 상태 조회가 붙는다.

| 대기 인원 | `/queue/status` 도착률 |
|---|---|
| 10,000 | 5,000 rps |
| 100,000 | **50,000 rps** |

⚠️ **폴링 주기로 나눈 산수이지 측정이 아니다.** 실제로 그만한 동시 대기를 만들어 본 적이 없다.

### 폴링을 그냥 뺄 수 없는 이유 — 지금은 그게 유일한 복구 경로다

승격은 Redis Lua로 **먼저 확정**되고(wait ZSET pop + admitcount 증가 + admitExp 등록이 원자,
[[TS-024]]), SSE는 그 뒤에 붙는 **알림**이다. 그런데 그 알림에 복구 장치가 없다.

```java
/** 이 Pod의 로컬 연결로만 전달(연결 없으면 무시 — 폴링 폴백이 커버). */
public void deliverLocal(String token, String event, Object data) {
    SseEmitter emitter = emitters.get(token);
    if (emitter == null) {
        return;          // ← 이벤트가 사라진다
    }
```

| 복구 장치 | 현재 |
|---|---|
| Last-Event-ID 재전송 | 없음 |
| 접속 시 현재 상태 push | 없음 (`subscribe()`는 emitter 등록만) |
| 하트비트 | 없음 |
| 프론트 `onopen` 재조회 | **없음 — 대기열만 예외** |

그래서 알림을 놓치면 이렇게 된다.

```
워커가 승격 → 슬롯 소비 → 알림 소실 → 사용자는 대기 화면 그대로
→ admit-ttl(300초) 소진 → reclaim이 회수 → 순번을 잃었는데 본인은 이유를 모른다
```

**"내 차례가 조용히 날아간다"** — 선착순에서 가장 나쁜 실패다. 2초 폴링이 지금 이걸 막고 있다.
따라서 **부하를 줄이려고 폴링을 먼저 걷어내면 정확성이 무너진다.**

⚠️ 알림 소실이 실제로 발생한 기록은 찾지 않았다. 코드 구조로 확인한 것이다.

### 대기열만 예외라는 점이 핵심이다

`useOrder`·`useSeats`는 이미 같은 문제를 다른 방식으로 풀고 있다.

```js
// useOrder.ts — 이미 있는 코드
// 둘 다 "구독이 성립한 시점"에 다시 읽으면 닫힌다. 그래서 최초/재연결을 구분하지 않고
// 모든 onopen에서 재조회한다 — 마운트 시 GET이 한 번 중복되지만 그 대가가 더 싸다.
// SSE는 트리거이고 진실원은 서버다(ADR-008).
es.onopen = () => refresh();
```

`useQueue`에는 그 줄이 없고, 주석이 이유를 밝히고 있다 — *"여기만 onopen 재조회가 없다 —
아래 2초 폴링이 재연결 공백을 이미 메우기 때문이다."*

즉 **[[ADR-008]]이 세운 원칙("SSE는 트리거, 진실원은 서버")을 대기열에서만 폴링으로
대신하고 있었다.** 이 ADR은 새 설계를 도입하는 것이 아니라 **이미 있는 패턴을 대기열에도
적용하는 것**이다.

## 결정

세 단계로 나눈다. **순서가 중요하다 — 복구를 먼저 만들고 폴링을 줄인다.**

### ① `onopen` 재동기화 (프론트만, 백엔드 변경 0)

> **구현됨**(`useQueue.ts`, #236) + **회귀 검증 완료**(#238). 다만 그 과정에서
> **`onopen`이 아예 불리지 않던 것**을 발견해 함께 고쳤다 — 아래 §① 검증 경과.

```
SSE 연결/재연결 성공 → onopen → GET /queue/status 1회
  → 이미 ADMITTED/EXPIRED면 즉시 복구
  → 이후는 SSE push 사용
```

**서버 `subscribe()`에서 초기 상태를 push하는 안은 채택하지 않는다.** `QueueSseRegistry`는
현재 순수 전송 계층이고(생성자가 `tokenTtl`과 `SsePubSub`만 받는다), 상태 조회를 넣으면
**전송이 도메인을 알게 된다.** `QueueSseController`도 `registry.subscribe(token)`만 반환하는
단순한 구조를 유지할 수 있다.

⚠️ 정확히 하자면 이건 **순환 의존 문제는 아니다** — `QueueService`는 registry를 주입받지 않으므로
사이클은 생기지 않는다. 순전히 **결합도** 판단이고, 프론트 한 줄이 더 싸다는 것이 결정 근거다.

### ② 하트비트

ALB idle timeout에 끊기지 않도록 주기적으로 코멘트 프레임을 보낸다.

⚠️ **하트비트는 공짜가 아니다.** 연결 10만 개에 15초 주기면 **초당 약 6,667회 write**다.
payload가 작아도 servlet write·네트워크·ALB 커넥션 처리 비용이 붙는다.
"폴링 50,000 HTTP rps보다 가벼울 가능성이 크다"까지가 말할 수 있는 선이고, 주기는 §측정으로 정한다.

### ③ 폴링을 저빈도 안전망으로 완화 (후보: 30초, **최종 주기는 측정 후 결정**)

> **부분 착수** — 주기를 `NEXT_PUBLIC_QUEUE_POLL_INTERVAL_MS`로 **파라미터화**했다(#238).
> **운영 기본값은 2000ms 그대로**이고, 실제 완화는 측정 후다. E2E만 600000을 주는데
> 그건 운영 후보가 아니라 ①을 격리 검증하기 위해 폴링을 테스트 시간 밖으로 민 값이다.

①이 재연결 공백을 닫으므로 폴링은 "SSE가 아예 안 열리는 경우"의 최종 안전망으로 격하된다.
**제거하지 않는다** — SSE가 차단된 네트워크(일부 프록시)에서는 여전히 유일한 경로다.

⚠️ **30초는 결정이 아니라 후보값이다.** `/queue/status`의 요청당 비용도, 주기를 늘렸을 때의
사용자 반응성(SSE가 안 열리는 사용자가 승격을 얼마나 늦게 아는가)도 아직 재지 않았다.
이 ADR이 결정하는 것은 **"복구를 먼저 만들고 그다음 폴링을 완화한다"는 순서**이지 숫자가 아니다.

## 검토했으나 채택하지 않은 대안

| 대안 | 이유 |
|---|---|
| 폴링 제거 | 위 §맥락 — 지금은 유일한 복구 경로다. ①② 없이 빼면 "차례가 조용히 날아간다" |
| 서버 `subscribe()` 초기 push | 전송 계층이 도메인을 알게 된다. 프론트 `onopen` 한 줄이 더 싸다 |
| Last-Event-ID 재전송 | 이벤트 로그를 보관해야 한다. 대기열 이벤트는 2종(admitted/expired)뿐이라 **상태 재조회가 같은 일을 더 싸게 한다** |
| 순번별 적응형 폴링 주기 | 뒤쪽 대기자는 길게 — 아이디어는 유효하나 순번이 변할 때의 경계 처리·반응성을 안 재봤다. ①②③ 이후 재검토 |

## 미확정 — 확인 전에는 단정하지 않는다

- ~~**ALB idle timeout.**~~ **2026-08-16 실측으로 확정 — 60초.**

  ```
  $ aws elbv2 describe-load-balancer-attributes --load-balancer-arn <arn>       --query "Attributes[?Key=='idle_timeout.timeout_seconds'].Value"
  60
  ```

  저장소에 override가 없다는 관찰과 일치한다(기본값 그대로). ②의 하트비트 주기는 이 값보다
  **충분히 짧아야** 한다.

  ⚠️ **다만 "60초마다 끊긴다"는 뜻이 아니다.** idle timeout은 **바이트가 흐르지 않을 때**만
  적용된다. 폴링이나 SSE 이벤트가 그 사이에 흐르면 연결은 유휴가 아니다. 따라서
  **재연결 빈도는 여전히 미실측**이고, 하트비트의 필요성 자체는 이 값만으로 결론나지 않는다.
- **`/queue/status`의 요청당 비용.** Redis 전용이라 조회(DB 경유)보다 쌀 것으로 **추정**하나
  **한 번도 재지 않았다.** 이 값에 따라 "폴링 주기를 줄이는 것"과 "수평 확장" 중 무엇이
  답인지 갈린다.
- **캐시 실험과의 우선순위.** 조회 캐시는 *browsing 워크로드*의 병목을, 이 항목은 *대기자
  규모*의 트래픽을 다룬다. **서로 다른 부하 모델이라 현재 자료로 어느 쪽이 큰지 결론낼 수 없다.**
  "동시에 몇 명이 browsing 중이고 몇 명이 waiting 중인가"라는 가정이 있어야 비교된다.

## 측정 계획

목표는 **폴링 HTTP RPS**와 **SSE 연결 자원**을 따로 재는 것이다. 둘은 성격이 다르다.

| 재는 것 | 방법 | 비고 |
|---|---|---|
| `/queue/status` 요청당 증분 CPU | 고정 도착률 부하 + idle 차감 | 캐시 실험 0단계와 같은 정규화 |
| 연결당 자원(메모리·fd) | 연결 수를 늘리며 api 파드 메모리·fd 관측 | **포화 이전 구간의 증가 추세만** 재고 그 범위 안에서만 외삽한다(아래 ⚠️) |
| ①②③ 적용 전후 도착률 | 같은 대기자 수에서 실측 | 주기를 N배로 늘리면 산술적으로 N배 감소지만 실제로 확인 |

⚠️ **"연결당 비용은 선형"이라고 가정하지 않는다.** 연결 수가 커지면 fd 한도, heap,
스레드·컨테이너 limit, ALB, NAT 같은 지점에서 **임계를 넘은 뒤 비선형으로 무너질 수 있다.**
그래서 증가 추세는 **포화 이전 구간에서만** 재고, 외삽도 그 범위 안에서만 한다.
범위 밖은 "여기부터는 재지 않았다"로 남긴다.

### ⚠️ 10만 동시 연결은 노트북 한 대로 못 만든다

소스 IP 하나당 ephemeral port가 약 64k라 그 위에서 막히고(Linux 기본 범위는 약 28k),
fd 한도도 걸린다. 50,000 rps HTTP 부하도 노트북에서 인터넷 경유로는 현실적이지 않다.

**선택지:**

1. **실현 가능한 규모에서 단가를 재고 명시적으로 외삽한다** (권장) — 연결당 메모리·fd,
   요청당 CPU를 구하면 천장을 **추정**할 수 있다. "10만을 실증했다"가 아니라 **"측정한 구간에서
   연결당 비용이 X였고, 그 추세가 유지된다면 현재 구성의 천장은 Y로 추정된다"** 로 말한다.
   조건절("그 추세가 유지된다면")을 빼지 않는다 — 위 ⚠️의 비선형 붕괴 가능성이 그 조건이다.
2. 같은 리전 EC2 여러 대에서 부하 생성 — 실제 규모에 가까워지지만 비용·설정이 붙는다.
   **클러스터 안에서 돌리지 않는다**([[TS-021]] §7 자원 경합).

**1번을 기본으로 한다.** 이 항목의 가치는 "10만을 버텼다"는 시연이 아니라 **복구가 없던
구조를 고치고 그 비용 구조를 아는 것**이기 때문이다.

### ① 검증 경과 — 첫 시도가 실패했고, 그 실패가 진짜 결함을 찾아냈다

폴링을 600초로 밀어 격리한 뒤(#238) 회귀 테스트를 돌렸더니 **복구되지 않았다.**
CI trace 근거:

```
+ 484ms  GET /api/sse/queue/{token}  net::ERR_FAILED   ← 의도적 차단
+3509ms  GET /api/sse/queue/{token}  net::ERR_FAILED   ← 3초 뒤 재시도(정상)
+6512ms  GET /api/sse/queue/{token}  (실패 없음, 계속 열림)  ← 차단 해제 후 연결됨
그 뒤 /api/queue/status 요청 0건
```

**재연결 자체는 됐다.** 그런데 상태 재조회가 일어나지 않았다 — 즉 `onopen`이 불리지 않았다.

⚠️ **가설(미확인):** `subscribe()`는 emitter만 만들고 **아무것도 보내지 않는다.** 하트비트도
초기 이벤트도 없다. 응답이 첫 전송 시점에 커밋된다면 브라우저는 헤더를 받지 못해
`readyState`가 OPEN이 되지 않고, `onopen`은 영영 불리지 않는다.

스파이크 측정에서 `queue.admitted`가 정상 도착했던 것과 모순되지 않는다 — **이벤트가 실제로
나갈 때 비로소 헤더가 흐른다**는 것과 정합적이다.

#### 두 문제를 분리한다 — 초기 프레임 ≠ 주기적 하트비트

한때 이것을 "②(하트비트)가 ①의 전제 조건"으로 적으려 했으나 **그 묶음이 부정확하다.**
목적도 주기도 다르다.

| | 목적 | 필요한 것 |
|---|---|---|
| **초기 프레임** (①의 전제) | 응답을 커밋해 `EventSource`를 OPEN으로 만든다 → `onopen` 발생 | **연결 직후 1회** |
| **주기적 하트비트** (②) | 오래 유휴한 연결이 프록시(ALB 등)에 끊기는 것을 막는다 | 주기 = idle timeout에 의존 |

①에 필요한 것은 **초기 flush뿐**이다. 하트비트 주기를 여기에 엮으면 나중에
"왜 15초 주기가 ①의 필수조건인가"라는 설명이 성립하지 않는다.

**그래서 초기 프레임 1회만 먼저 넣어 가설을 격리 검증했다.** 하트비트는 ALB idle timeout
실제값을 확인한 뒤 별도로 결정한다.

#### 결과 — 가설 확정

`subscribe()`에 코멘트 프레임 1회 전송을 넣은 것 **하나만** 바꿔 같은 테스트를 다시 돌렸다.

```
before  ✗ SSE가 끊긴 사이 승격돼도 재연결하면 복구된다   (30초 대기 후 실패)
after   ✓ SSE가 끊긴 사이 승격돼도 재연결하면 복구된다   (7.5s)
```

초기 프레임 추가만으로 동일 회귀 테스트가 RED → GREEN으로 전환되어,
**실패 원인이 초기 응답 미커밋에 있었다는 가설을 재현 테스트로 확인했다.**
`onopen`은 응답이 커밋되기 전에는 불리지 않고, 커밋은 첫 전송에서 일어난다.

그리고 이는 **#236의 ①이 main에 들어간 뒤로 실제로는 발동하지 않고 있었다**는 뜻이기도
하다. 2초 폴링이 가려주고 있어 드러나지 않았고, 폴링을 격리한 이 테스트가 아니었으면
계속 몰랐을 것이다.

#### 같은 결함이 주문·좌석 SSE에도 있었다 (#239)

`OrderSseRegistry`·`SeatSseRegistry`도 `subscribe()`에서 아무것도 보내지 않았다.
`useOrder`·`useSeats`도 `onopen`에서 재조회하므로 **그 복구 역시 발동하지 않고 있었다.**

**대기열보다 나쁘다** — 두 훅에는 **폴링이 없다**(`setInterval` 0건). 대기열은 2초 폴링이
가려주고 있었지만, 여기는 재연결 뒤 **자동** 복구 경로가 `onopen` 재조회뿐이다. 이 경로가
발동하지 않으면 **사용자가 새로고침하거나 페이지를 다시 열기 전까지** 끊긴 사이의 상태
변경을 화면이 반영하지 못한다 — 좌석맵이 낡은 채로 남아 이미 선점된 좌석을 고르게 되고,
주문 상태가 갱신되지 않아 결제 완료를 화면이 모른다.

셋 다 같은 방식(연결 직후 코멘트 프레임 1회)으로 고쳤고, **세 경로 모두 회귀 테스트로
고정**했다 — 대기열은 `queue-waiting.spec.ts`, 좌석·주문은 `sse-reconnect-resync.spec.ts`.

주문 경로는 가상계좌 흐름을 쓴다. 입금이 **서버 밖에서** 확정되는(실서비스는 PG 웹훅)
구조라 "UI가 스스로 알 수 없는 상태 변경"을 그대로 재현한다.

### ⚠️ 그리고 원래의 관측 한계도 여전하다

①이 메우는 공백을 **2초 폴링이 이미 메우고 있다.** 게다가 둘은 같은 엔드포인트
(`/queue/status`)를 쓰므로 요청만 봐서는 어느 쪽이 복구했는지 구분되지 않는다.
즉 **①을 넣어도 오늘의 관측 가능한 동작은 바뀌지 않는다.**

서버 쪽 복구 능력은 이미 회귀 테스트가 있다 — `QueueAdmitVisibilityIntegrationTest`의
`승격이_확정됐으면_admit키가_없어도_ADMITTED로_판정한다`. 비어 있는 것은 **클라이언트가
재연결 시 그걸 실제로 호출하는가**이고, 그게 ①이다.

E2E로 고정하기도 지금은 비싸다. 대기 화면을 보려면 대기자가 정원(기본 100)을 넘겨야 하는데
E2E는 `queue.capacity` 오버라이드 없이 단일 백엔드를 공유하므로, 그 값을 낮추면 다른
E2E(`seedAdmittedUser`에 의존하는 예매·결제·환불 전부)가 깨진다.

**따라서 ①의 회귀 테스트는 ③과 함께 만든다.** 폴링을 저빈도로 내리면 그때부터
"빠른 복구"는 onopen 경로로만 설명되므로 관측이 성립한다.

### 측정이 필요 없는 부분

①의 **정확성 효과는 부하 테스트가 아니라 재현 테스트로 검증한다.** 승격 알림이 소실된 상황을
만들고(연결 끊긴 사이 승격), 재연결 시 사용자가 ADMITTED를 인지하는지 본다.
**이건 클러스터 없이 통합테스트로 가능하다.**
