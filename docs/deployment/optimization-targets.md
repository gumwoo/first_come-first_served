# 최적화 대상과 바꿀 때 지켜야 할 제약 — 설정값 근거 재검토의 출발점

- 상태: **출발점(최적화 전)**. 무엇을 다시 볼지와, 바꿀 때 깨면 안 되는 조건만 정한다. 확정된 값마다의 상세 근거(기존 값 → 변경 값 → 선택 근거 → 검증 결과 → 비용 차이 → 남은 한계)는 최적화가 끝난 뒤 이 문서를 갱신해 쓴다.
- 날짜: 2026-10-20
- 범위: **측정 프로필**(`loadtest.tfvars` — m6i.large·Redis cache.m7g.large)의 분리 구조(B, [[ADR-027]]). 운영 프로필(`variables.tf` 기본값 — t3.large·Redis t4g.micro)은 10만/10초를 잰 적이 없다(미검증).
- 진행 방식: 새 AWS 비용 없이 진행한다 — **기존 세션 원자료의 재분석 + 로컬 실험 + 스케줄링 시뮬레이션**. 여기서 나오는 값은 "후보"이고, 클라우드에서 검증하지 않은 값은 확정값으로 쓰지 않는다.
- 표기: **사실**(출처 있음) / **사후 분석**(보존된 세션 원자료를 다시 계산 — CPU는 내보낸 질의 그대로 `rate[1m]`, 10초 표본이라 1분 평균의 최댓값) / **계산** / **추론**.

## 2. 기존 원자료에서 다시 계산한 값 (사후 분석 — 후보 산정의 입력)
출처: 레포 밖 `artifacts/loadtest/_inventory/README.md`(세션별 보유 지표·재계산 스크립트, 독립 검증 3차 통과). 세션 20261015-nok(IMP-034 B — 세션 8 run 중 역할 분석은 같은 형식의 6 run)·20261017-b100k(IMP-035)·20261014-ab(IMP-033)·20261007-platform·20261010-1440(IMP-031).

- **노드 할당 가능량(사실 — `kube_node_status_allocatable`)**: m6i.large CPU 1.93코어 · 메모리 6.94GiB.
- **노드별 flowticket 밖 CPU 요청량(사후 분석)**: Kafka 제거 뒤 0.10~0.58코어(IMP-034 8 run), 0.18~0.66코어(IMP-035).
- **예매 api**: CPU run별 최대 0.03~0.08코어(IMP-034 — 입장 100명 예매 묶음 포함, 요청량의 약 3~7%), 메모리 working set 최대 498~527MiB·힙 166~172MiB.
  DB 풀 5는 한 run에서 상한에 3표본 닿았다(대기 최대 25) → 줄일 근거 없음.
- **대기열**: 폴링 폭증(7,000/s) 초반에 CPU 1.58~1.95코어 + Tomcat 바쁨 200(확장이 끝나기 전 — 이후 파드당 약 0.7코어). 메모리 working set 최대 820~1,083MiB·힙 426~604MiB(모두 폭증이 끝난 뒤 최대).
  10만/10초 진입(IMP-035)에서 DB 풀 3이 진입 10초 시점 한 파드에서 상한(active 3·대기 12, 1표본)에 닿았다.
- **진입 순간 Pod별 처리 시간(ALB access log, 요청 단위)**: 대기열 6개가 Pod당 초당 약 1,700건을 받는 동안 Pod별 p50 3~8ms·p99 42~189ms(IMP-035). 통합 구조는 api 9개가 Pod당 약 1,130건/초에서 p50 2~33ms·p99 13~191ms(IMP-031 3 run).
  같은 조건 비교가 아니다 — IMP-031은 Redis t4g.micro(버스터블)·TS-045/047 이전 코드, IMP-035는 Redis m7g.large·이후 코드.
- **Tomcat 스레드만 포화된 표본(CPU 1분 평균 0.56 이하)**: 주로 통합 구조(IMP-031 pf-r1·pf-r3, 재측정 re1)에서 보였고, 분리 구조는 IMP-034 p3-1에서 1표본. 통합 구조 중 re1은 Redis CPU 크레딧 고갈([[TS-049]])과 시점이 겹치고, 나머지 두 run은 크레딧이 충분했던 때라 원인 미확인. 스레드 증설 효과는 이 데이터로 판단할 수 없다.
- **확장 반응 시간**: 폭증 실행 뒤 대기열 replicas 첫 증가 +40~70초, Ready 노드 증가 +100~150초([[ADR-012]] CA 110초 실측과 맞음). 10초 오픈 폭주에는 반응할 수 없다는 판단(추론)이 Git 사전 확장([[ADR-025]] 결정 3)의 근거를 뒷받침한다.
- **다시 계산할 수 없는 것**: 폭주 몇 초의 순간 CPU(모든 세션이 `rate[1m]`), 예매 api의 DB 커넥션 획득 시간(히스토그램 #432 이후 예매 부하 없음), 대량 예매 부하에서의 api 용량(시험은 입장 100명 단위).

## 2.1 로컬 실험 결과 ([[IMP-036]] — 같은 로컬 환경의 상대 비교, 칸마다 1회)
- **Tomcat 스레드**: 하위 의존성(Redis)만 느리게 하자 CPU는 그대로(0.93 → 0.84코어)인데 바쁜 스레드가 11 → 198, p95 2.3 → 56ms. 그 상태에서 스레드 400은 개선이 없었다(p95 63ms). → **200 유지**(늘릴 근거 없음).
- **예매 api 순간 CPU**: 입장자 100명 예매 묶음이 1~2초 동안 코어 2개를 거의 다 썼다(1초 최대 1.85코어). 구간 합 4.8코어·초를 60초로 펴면 약 0.08코어(묶음 2초만 약 0.04코어, 계산)로 AWS 1분 평균 최대와 같은 규모(추론). → 1분 평균만 보고 요청량을 크게 낮추지 않는다. 낮추려면 노드 합치기 설계와 함께.
- **api DB 풀 5**: 예매 묶음 시작 순간 포화(active 5·pending 16, 연속 표본 2개 ≤2초 — 두 번째는 게이지 캐시일 수 있음, 추론). → 줄일 근거 없음, 늘릴 후보. 단 하네스 규칙 17은 기본 구성(base HPA 상한 9)도 검사해 (9+1) × 8 = 80 > 56 — 풀 8은 base 상한을 6 이하로 낮추는 결정과 함께여야 한다(계산, 미검증).

## 2.2 노드 합치기 스케줄링 시뮬레이션 ([[IMP-037]] — kwok, 배치 가능성만)
- 시뮬레이터 검증: 현재 구성 평시 5 / 사전 확장 9대(평시는 실측 5~6의 하단, 9는 CA 상한과 같아 약한 근거), IMP-034 P3 재현(노드당 대기열 2개 안 생김 — 노드 단위 강제 분산이 대기열 0개인 api 노드도 도메인으로 센다는 의미론과 일치, 추론). 단 P3 노드 수는 시뮬레이션 9 vs 실측 최대 8 — 시뮬레이션이 1대 많게 볼 수 있다.
- 후보: api 300m(대기열 1100m 그대로)이면 평시 4 / 사전 확장 8대, api 300m + 대기열 850m(노드당 대기열 2개 허용)이면 3 / 5대(평시 노드 비용 −20% / −40%, 상시 운영 가정 계산).
- 위험(추론): api 300m는 줄어든 1대가 api와 대기열이 한 노드에 함께 놓인 결과라 예매 묶음과 폴링 폭증이 겹치면 경합·그 노드 상실 시 api와 대기열 동시 손실(분리 구조에서만 유효한 후보), 대기열 850m은 폭증 초반 노드당 2개가 2 vCPU를 나눠 포화·노드 하나 상실 시 대기열 2개 동시 손실. 둘 다 검증 전에는 채택하지 않는다.
