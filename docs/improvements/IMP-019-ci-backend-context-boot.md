# IMP-019 · CI 백엔드 9m46s → 3m08s — 컨텍스트 부트를 붙잡던 KafkaAdmin

- 슬라이스: 전반(CI)
- 날짜: 2026-08-16
- 유형: 정량(CI wall-clock 실측) — 테스트 인프라
- 관련: [[TS-020]](에러 없이 조용히 멈추는 실패), `apps/api/src/test/.../TestContainers.java`(Kafka 미공유 결정)
- 측정 원본: 이 문서 §3·§7 (GitHub Actions 실행 로그·JUnit XML 아티팩트)

> 흐름: 문제 정의 → 증상(수치) → 가설 → 도구로 검증 → 해결 → 재측정 → 한계.

## 1. 상황 (Context)

CI 백엔드 잡이 **약 10분**이었다. backend·frontend·E2E는 병렬이라 가장 느린 잡이 전체
CI 시간을 결정하는데, E2E가 3m47s인 반면 backend가 9~10분으로 **critical path**였다.

리뷰에서 "테스트를 빼는 방향 말고 같은 검증을 더 빨리 끝내는 방향"으로 보자는 제안이 나왔고,
그 원칙을 그대로 따랐다 — **이 개선으로 빠진 테스트는 하나도 없다**(193개 그대로).

## 2. 문제 정의 + 분류

- 계층 분류: **테스트 인프라**(애플리케이션 성능이 아니다 — 운영 코드는 바뀌지 않았다).
- 무엇을 재야 하는지부터 몰랐다. "느리다"는 알았지만 **어디가** 느린지는 아무도 재지 않았다.

## 3. 증상 (측정된 증거)

### 3-1. 잡·태스크 단위

```
backend 잡 (6표본)   568 572 581 586 592 601      median 586s = 9m46s
└ gradle build 스텝                                551~558s
```

`gradle build` 안을 로그 타임스탬프로 갈랐다.

```
   0s  > Task :compileJava      ┐
   0s  > Task :bootJar          │
   0s  > Task :jar              ├ build 고유 비용 ≈ 4s
   3s  > Task :assemble         │
   0s  > Task :check            ┘
  30s  > Task :testClasses
 501s  > Task :test             ← 91%
```

### 3-2. `:test` 안 — testcase는 11%뿐이었다

성공 실행의 JUnit XML을 아티팩트로 남겨(#229) 클래스별 시간을 얻었다.

```
:test wall-clock          526s
├─ XML testcase 귀속       58.1s  (11%)   43 suite / 193 테스트
└─ testcase 미귀속        467.9s  (89%)
```

⚠️ **미귀속 = 초기화라고 단정할 수 없다.** XML은 테스트별 시간이지 컨테이너·컨텍스트 시간이
아니다. 그래서 그 안을 다시 쟀다.

### 3-3. 미귀속 468초의 정체

측정 게이트(`-PciTiming`)로 컨텍스트 캐시 통계와 Testcontainers 로그를 한 번 켰다.

```
Spring 컨텍스트 부트 14회   446.3s   ← 미귀속의 95%
컨테이너 기동 15개           18.3s
나머지                        ~3s
```

부트 시간이 **극단적으로 갈렸다.**

```
41초대  9회 → 372.8s   비-Kafka 통합테스트
1~4초   4회 →   8.6s   Kafka 통합테스트
65.2초  1회           첫 부트(JVM 워밍업 포함)
```

**Kafka를 쓰는 테스트가 빠르고, 안 쓰는 테스트가 느렸다.**

## 4. 가설 (검증 전)

비-Kafka 그룹은 `IntegrationTestSupport`가 bootstrap을 **연결 불가 주소**로 박는다
(`localhost:59092` — 로컬에 떠 있는 Kafka에 얹히지 않게 하려는 의도). 그런데도 Kafka
클라이언트가 뜨면서 붙지 못해 41초를 쓴다.

## 5. 검증 (도구로 확인 → 확정 원인)

**두 번 틀리고 세 번째에 맞혔다. 그 과정을 그대로 남긴다.**

### 5-1. 첫 시도 — 옳은 가설을 잘못된 측정으로 기각했다

"40초짜리 고정 대기 아닐까"로 시작해 부트 구간의 타임스탬프 갭을 찾았는데 **0.8초 이상 갭이
하나도 없었다.** 그래서 "정체가 아니라 분산된 작업"으로 결론내고 가설을 버렸다.

**측정 범위가 틀렸다.** 부트 완료 지점에서 260줄만 거슬러 봤는데, 40초 갭은 그 창 **밖**에
있었다. 창을 잘못 잡고 가설을 죽인 것이다.

### 5-2. 두 번째 — 재시도 루프로 갈아탔고 그것도 틀렸다

로거별로 집계하니 부트 구간 1,325줄 중 **869줄이 `NetworkClient`**였다. "컨슈머 재연결 루프가
부트를 붙잡는다"로 보고 `spring.kafka.listener.auto-startup=false`를 넣어 CI를 돌렸다.

```
NetworkClient 로그   20,987 → 13,935줄   (-34%)
컨텍스트 부트 합       446.3s → 443.1s   (-0.7%)
```

**로그는 3분의 1이 줄었는데 시간은 안 줄었다.** 재시도는 CPU를 거의 안 쓰는 배경 작업이었다.
이 커밋은 되돌렸다 — 이득이 없는데 테스트 동작(리스너 비활성)만 바꾸기 때문이다.

### 5-3. 세 번째 — 마일스톤 타임라인으로 30초 만에 갈렸다

로거 집계·시간대 버킷 같은 간접 지표를 버리고, **부트 마일스톤의 절대 시각**을 나열했다.

```
+ 0.0s  Starting EventIntegrationTest
+ 0.2s  Bootstrapping Spring Data JPA repositories
+ 0.4s  HikariPool-4 - Start completed
+ 0.5s  HHH000204: Processing PersistenceUnitInfo
+ 0.6s  Initialized JPA EntityManagerFactory     ← JPA·Flyway·Hikari·Repository 전부 0.6초
+ 1.4s  Kafka version 3.7.1  (client.id=flowticket-api-admin-N)
+41.4s  Kafka version 3.7.1                      ← 40.0초 단일 공백
+41.4s  Started in 41.443 seconds
```

**범인은 `KafkaAdmin`이었다.** `KafkaConfig`에 `NewTopic` 빈이 둘 있어
(`order-events`, `order-events.DLT`) Spring Boot가 부팅 시 브로커에 붙어 토픽을 만들려 한다.
붙지 못한 채 재시도하다 **약 40초 뒤에 포기**한다.

`listener.auto-startup`이 안 통한 이유도 여기서 설명된다 — 멈추는 주체가 **리스너가 아니라
admin 클라이언트**다.

## 6. 조치 (해결)

`IntegrationTestSupport`의 `@TestPropertySource`에 한 줄.

```java
"spring.kafka.admin.auto-create=false",
```

**넣기 전에 이 프로퍼티가 Boot 3.3.5에 실제로 있는지 확인했다** —
`spring-configuration-metadata.json`에서 `spring.kafka.admin.auto-create (Boolean, 기본 true)`.
존재하지 않는 키는 조용히 무시돼 CI 한 번을 날린다.

Kafka를 실제로 쓰는 테스트 4개는 이 베이스를 상속하지 않아 **토픽 생성이 유지된다.**

## 8. 트레이드오프 / 한계 / 다음 개선

- **기각한 후보 넷.** 흔히 권장되는 최적화가 이 저장소에선 표적이 아니었다.

  | 후보 | 근거 |
  |---|---|
  | `gradle build` → `test` | build 고유 비용 ~4s. 바꾸면 `check`가 빠져 검증만 줄어든다 |
  | 개별 느린 테스트 최적화 | XML 합이 58.1s. 가장 느린 것도 13s(타임아웃을 일부러 재는 테스트) |
  | Testcontainers 컨테이너 공유 | 기동 총 18.3s. 전부 공유해도 절감 상한 **13.8s**(:test의 2.6%) |
  | Kafka 리스너 재시도 루프 | 로그 −34%인데 시간 −0.7% |

- ⚠️ **Kafka 컨테이너 공유를 뒤집지 않았다.** 처음엔 그것을 최대 표적으로 봤으나,
  `TestContainers` 클래스 주석에 **토픽·컨슈머 그룹 오염으로 기각한 기록**이 있었고
  실측(11.4s)이 그 판단을 뒷받침했다. **기록된 결정을 데이터 없이 뒤집지 않는다.**
- ⚠️ **컨텍스트는 여전히 14개다.** 코드로 센 추정(8개)이 틀렸음이 실측으로 드러났지만,
  부트가 1초대가 된 지금 14개여도 41초라 우선순위가 낮다. 줄이려면 테스트별
  `@TestPropertySource` 차이를 합쳐야 하는데 그중 일부는 [[TS-024]]에서 **플래키를 피하려
  일부러 분리한 것**이다.
- ⚠️ **첫 부트 21.7s는 남아 있다**(측정 모드 기준 63.9s→21.7s). JVM 워밍업·클래스 로딩이라
  줄이기 어렵고 1회뿐이다.
- **운영 코드는 안 바뀌었다.** 프로덕션에서는 브로커가 있으므로 토픽 자동 생성이 그대로
  동작한다. 이 변경은 **테스트 전용 프로퍼티**다.
- 다음 후보는 **job 분할**이다. backend가 3분대가 된 지금은 E2E(3m47s)와 비슷해져
  critical path가 옮겨갔다 — 더 줄이려면 그쪽을 봐야 한다.

## 9. 배운 점 (면접 답변용)

> CI 백엔드가 10분이라 줄이려 했는데, 흔한 조언(테스트 병렬화·컨테이너 공유·빌드 태스크 축소)이
> 전부 표적이 아니었습니다. 먼저 `gradle build` 안을 갈라 `:test`가 91%임을 확인하고, JUnit
> XML로 **테스트 코드는 58초뿐이고 468초가 그 밖**이라는 걸 봤습니다. 다시 그 안을 재니
> **Spring 컨텍스트 부트 14회가 446초**였고, 마일스톤 타임라인을 찍으니 **JPA·Flyway·Hikari는
> 다 합쳐 0.6초인데 Kafka admin 클라이언트에서 40초가 통으로** 비어 있었습니다.
> `NewTopic` 빈 때문에 부팅 시 토픽을 만들려다 브로커가 없어 40초를 기다린 것이었고,
> 테스트 프로퍼티 한 줄로 **9분 46초 → 3분 8초(-68%)**가 됐습니다. 테스트는 하나도 안 뺐습니다.
>
> 과정에서 두 번 틀렸습니다. 처음엔 옳은 가설을 세우고도 **로그 창을 260줄만 봐서** 갭을 못 찾고
> 기각했고, 다음엔 로그 개수가 많다는 이유로 재시도 루프를 범인으로 몰았는데 고쳐 보니 **로그는
> 34% 줄었는데 시간은 0.7%**만 줄었습니다. 간접 지표(로그 줄 수, 로거 분포)로 원인을 추정한 게
> 실패의 공통점이었고, **시작·종료 시각을 직접 찍는 것**이 답이었습니다.
