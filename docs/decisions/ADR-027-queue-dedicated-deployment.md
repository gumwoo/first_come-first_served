# ADR-027 · 대기열 전용 Deployment(같은 이미지) — 분리 1단계, Service 대상 전환으로 A'/B를 같은 날 비교

- 상태: **Accepted(구조)** — 기본은 A'(지금과 같은 동작). B(분리)의 효과는 측정 전이다(다음 클러스터 세션, 사전 등록)
- 날짜: 2026-10-13
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-014]](모듈러 모놀리스), [[ADR-024]](대기열 두 경로 직결), [[ADR-025]](api 1100m·HPA 3~9·사전 확장),
  [[IMP-026]](진입 경로 판매 상태 캐시 — DB 획득 1.01 → 0.011/req), [[IMP-031]](폴링 폭증이 api 전체를 3→9로 늘림), [[TS-021]](DB 커넥션 상한),
  [[TS-047]](입장 판정 단일 규칙), [[TS-049]](공유 Redis 크레딧 고갈)

## 1. 맥락
대규모 선착순 서비스에서는 대기열을 본 서비스 앞의 별도 입장 제어 계층으로 두는 구조가 흔하다(외부 리뷰 2026-10-13).
이 프로젝트는 대기열이 api와 같은 파드 안에 있고, ALB에서 경로만 나눠 api로 직결한다(ADR-024).
- 폴링 폭증(7,000/s)이 api **전체**를 HPA 3→9로 늘렸다(IMP-031, 실측) — 좌석·주문을 처리하는 파드가 대기열 때문에 같이 늘고, 같은 Tomcat 스레드 풀을 나눠 쓴다.
- ADR-014의 "확장은 Pod replica"는 확장 요구가 다른 기능을 한 덩어리로 함께 늘리는 지금 구조에서 비효율이 될 수 있다.

## 2. 결정
**같은 이미지로 대기열 전용 Deployment를 둔다(분리 1단계).** 전환은 Ingress가 아니라 Service 대상(selector)으로 한다.
- base: Ingress의 대기열 두 경로 → `flowticket-api-queue` Service. 이 Service는 기본으로 **api 파드**를 가리킨다(A' — 지금과 같은 동작).
- `k8s/components/queue-split`(B): 대기열 전용 Deployment·HPA·PDB를 더하고, 그 Service가 대기열 전용 파드를 가리키게 바꾼다.
  overlay `components:`에 한 줄을 넣고 빼는 것으로 A'와 B를 오간다. Ingress는 바꾸지 않는다(하네스 k8s 규칙 2-b 유지).
- **파드 예산은 A'와 같은 9**: B에서 api HPA 상한을 3으로 묶고(component 패치), 대기열은 2~6. 목표·확장 정책은 api와 같다(CPU 60%).
  DB 커넥션 상한(하네스 backend 규칙 17): (3+1)×5 + (6+1)×5 = 55 ≤ 가용 56(db.t4g.micro max_connections 79 − 예약 3 − 앱 외 여유 20, 계산).
  상한을 그대로 두고 대기열만 더하면 (9+1)×5 + (6+1)×5 = 85 > 56이라 확장된 파드가 기동에 실패한다(TS-021).
- 관측: 두 Service의 job 라벨을 같은 값(`flowticket-api`)으로 수집해(ServiceMonitor `jobLabel`) 알림 규칙과 대시보드가 그대로 두 종류 파드를 본다.
  수집 라벨은 B에서만 대기열 Service에 붙는다 — A'에서 붙이면 같은 api 파드를 두 번 수집한다.
- 측정 도구: 로그 수집·정합성 검사는 두 파드 공통 라벨(`flowticket.io/app=api`)로 고른다 — 대기열 파드도 승격 감사 줄을 남긴다.

## 3. 하지 않은 것과 이유
- **서명된 입장 토큰(좌석이 Redis 대신 토큰만 검증)**: 회수된 슬롯의 토큰을 만료 전에 무효화할 수 없다. 슬롯이 다음 사람에게 넘어간 뒤에도
  이전 토큰이 유효해 "동시 입장 ≤ 정원"(실측으로 지켜 온 불변식, TS-047의 단일 판정 규칙)이 깨질 수 있다. 좌석이 Redis를 보는 것은 결함이 아니라 정원 보장 장치다.
- **별도 서비스(코드 분리)**: 위 결합이 그대로라 독립 배포·코드 소유 외에 측정되는 이익이 ①보다 없다. 여러 팀·여러 서비스가 대기열을 공유할 때 다시 본다.
- **대기열 전용 Redis**: 공유 Redis 병목(TS-049)은 파드를 나눠도 격리되지 않는다 — 진짜 격리가 목표면 ①보다 효과가 클 수 있으나 비용과 정합성 경계를 다시 봐야 한다. 측정 뒤 판단.
- **진입 경로 DB 제거**: 이미 했다 — 판매 상태 캐시 운영 TTL 1초(IMP-026). 대기열 파드도 같은 이미지라 DB 커넥션 풀은 가진다(거의 쓰지 않음).

## 4. 대가 · 남은 것
- **평상시 파드**: A' api 3 → B api 3 + 대기열 2 = 5. 요청 1100m라 노드가 늘 수 있다(계산 — 측정 세션에서 노드-시간으로 확인).
- **사전 확장**: event-prescale.yaml은 api HPA 대상이다. B를 켠 동안 하한을 올리면 하한 9 > 상한 3이 된다 — 하네스 k8s 규칙 11이 막는다.
  대기열 쪽 사전 확장(오픈 순간 몰리는 곳)은 측정 뒤 정한다.
- 대기열 파드도 같은 이미지라 스케줄러(승격·아웃박스 릴레이·만료 정리 등)와 Kafka 리스너가 함께 돈다. 승격은 Lua 원자, 나머지는 ShedLock·멱등이라 정합성 문제는 없다.
  폭증 때 대기열 파드의 CPU를 조금 나눠 쓴다.
- 장애 시험 스크립트(rds/redis-failover-test, diag.sh 등)는 api Deployment만 본다 — B에서 쓸 때 대상 확인이 필요하다.

## 5. 검증 계획(다음 클러스터 세션)
같은 세션·같은 Redis(측정 프로파일 비버스터블)에서 A'와 B를 비교한다. 질문 하나: **폴링 폭증 중에도 좌석·주문 지연이 지켜지는가.**
판정식·비용 계산식은 run 전에 사전 등록한다. 결과는 1회 관측으로 쓰고, 시간이 남으면 조건을 늘리지 않고 반복한다(A' → B → A').
