# ADR-022 · 아웃박스 릴레이: 한 틱을 임차 안에 가두고, 먼저 재본다

- 상태: **Accepted** (틱 예산·지표 적용 / 트랜잭션 경계 변경은 **측정 후 결정** — 아래 §다음)
- 날짜: 2026-09-21
- 슬라이스: S08(정합성 보강)
- 관련: [[ADR-010]](트랜잭션 아웃박스), [[TS-032]](DEAD 격리), [[TS-026]](브로커 확인), [[TS-021]](커넥션 풀), [[IMP-020]](측정 후 판단한 선례)

## 맥락

릴레이에는 세 가지 문제가 있다. 성격이 달라 한 덩어리로 다루면 안 된다.

| # | 문제 | 성격 |
|---|---|---|
| 1 | Kafka ACK를 기다리는 동안 DB 트랜잭션을 연 채로 둔다 | 커넥션 점유([[TS-021]]) |
| 2 | 일시적 실패 하나에서 `break` — 뒤 이벤트는 다음 틱으로 | head-of-line 지연 |
| 3 | **한 틱이 ShedLock 임차보다 길 수 있다** | 전제 붕괴 |

3번이 이번에 새로 드러났다.

```
batch-size 100 × send-timeout 3초 = 한 틱 최대 300초
lockAtMostFor                     = 60초
```

**느리지만 성공하는 ACK**가 쌓이면 임차가 먼저 끝난다. 그러면 다른 파드가 같은 PENDING을 집어
릴레이가 둘이 된다. 실패는 `break`로 틱을 끝내주지만, 느린 성공은 계속 진행하므로 오히려 더
위험하다.

**증상이 없다는 것이 이 문제의 핵심이다.** 소비자가 `eventId`로 멱등을 걸어 두어([[ADR-010]])
중복 발행이 사고로 번지지 않는다. 깨지는 것은 `OutboxRelay` 주석이 선언한 전제("한 인스턴스만
돈다")이고, 코드보다 주석이 먼저 틀린 상태였다.

## 결정

### 1. 한 틱을 임차 안에 가둔다

틱 예산(`outbox.tick-budget-ms`, 기본 45초)을 두고, 예산을 넘기면 남은 건을 PENDING 그대로 두고
다음 틱에 넘긴다. **임차를 늘리는 쪽은 택하지 않았다** — 임차를 300초로 늘리면 죽은 파드가 락을
5분 동안 붙잡아 발행이 그만큼 멈춘다. 임차는 "죽은 파드를 얼마나 기다릴까"의 값이지 "한 틱이
얼마나 걸릴까"의 값이 아니다.

지켜야 하는 관계는 이것이다.

```
tick-budget + send-timeout ≤ lockAtMostFor
     45초    +      3초     ≤     60초
```

마지막 한 건이 예산 직전에 시작될 수 있어 `send-timeout`을 더한다. 세 값이 서로 다른 곳
(어노테이션·설정 파일 두 줄)에 적혀 있어 **하네스 규칙 ㉒로 관계를 못박았다.** 이런 종류의 드리프트는
런타임에 드러나지 않으므로 정적으로 잡는 편이 싸다.

### 2. 고치기 전에 잰다

1·2번은 **측정 없이 손대지 않는다.** 구조를 바꿀 근거가 숫자로 있어야 하고([[IMP-020]]에서 같은
순서를 따랐다), 무엇을 고쳐야 하는지도 지표가 갈라 준다.

| 지표 | 무엇을 가리키나 |
|---|---|
| `flowticket.outbox.relay.tick` | 3번 — 한 틱이 임차에 얼마나 다가가는가 |
| `flowticket.outbox.publish.ack` | 틱이 길어진 이유가 브로커인가 |
| `flowticket.outbox.publish.lag` | 2번 — 생성부터 발행까지 실제 지연(p95·p99) |
| `flowticket.outbox.oldest_pending.age` | 2번 — 특정 건이 뒤를 막고 있는가 |
| `hikaricp_connections_*`(부트 기본) | 1번 — 릴레이가 풀을 먹는가 |

적체 **개수**(`flowticket.outbox.events{status=PENDING}`)는 이미 있었지만 그것만으로는 부족하다.
100건이 1초 만에 빠지는 것과 3건이 10분째 남아 있는 것은 개수로 구분되지 않는다.

## 다음 — 측정 뒤에 고를 두 갈래

측정 결과를 보고 **하나만** 고른다. 지금 확정하지 않는다.

**(가) 릴레이 하나를 유지한다.** Kafka I/O만 트랜잭션 밖으로 빼고 마킹만 짧은 트랜잭션으로 한다.
발행 성공 후 마킹 전에 죽으면 다음 틱이 재발행하므로 at-least-once는 그대로다([[ADR-010]]).
변경이 작고 되돌리기 쉽다.

**(나) 릴레이를 여럿 돌린다.** `PENDING → PROCESSING` claim + `SKIP LOCKED` + 임차 만료 회수.
처리량은 늘지만 상태와 회수 잡이 함께 늘어난다. 지금 규모(릴레이 1개 + ShedLock)에서 이 비용을
낼 이유가 있는지는 측정이 답한다.

## 결과 / 한계 (정직)

- **이번 변경으로 1·2번은 그대로다.** 트랜잭션은 여전히 ACK를 기다리는 동안 열려 있다.
- **틱 예산은 상한이지 목표가 아니다.** 기본값 45초는 임차 60초에서 역산한 값이고, 실제 틱이
  거기 근접한 적이 있는지는 아직 모른다 — 그걸 보려고 지표를 넣었다.
- **예산 초과는 WARN으로만 남는다.** 알림 규칙은 만들지 않았다. 임계를 정하려면 평시 분포가 먼저다.
- **겹쳐 돌았던 적이 있는지는 확인할 수 없다.** 지금까지 증상이 없었고 기록도 없다. 앞으로는
  틱 지표로 임차에 다가가는지 볼 수 있다.
- **측정 자체는 아직 하지 않았다.** 이 ADR은 잴 준비까지다.
