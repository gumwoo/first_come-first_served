# TS-037 · RDS·Redis 페일오버 중 앱은 어떻게 깨지는가 — 30초 대기 후 500

- 슬라이스: S09(EKS 배포) — 인프라·가용성
- 날짜: 2026-08-26
- 유형: 장애 주입 실증(ADR-012가 A 범주로 약속한 항목)
- 관련: [[ADR-012]] §10(Multi-AZ를 A로 둔다), `docs/deployment/terraform-design.md`(관찰 항목 표),
  `scripts/rds-failover-test.sh`, `scripts/redis-failover-test.sh`
- 상태: **실증 완료 · 결함 후보 1건 도출** — 개선은 별도(§8). 각 1회 측정

## 1. 배경 — 설계는 있었고 측정이 없었다

ADR-012 §10이 RDS·Redis Multi-AZ를 **A(실증) 범주**에 넣었다.

> 이건 NAT와 달리 **실증할 수 있다.** … 이 항목은 **B가 아니라 A**로 둔다 —
> 켜 두기만 하는 것이 아니라 **눌러 보고 앱의 거동을 측정**한다.

`terraform-design.md`는 관찰 항목까지 표로 지정했고, 마지막에 이렇게 적었다.

> 켜 두기만 하고 누르지 않으면 **비용만 늘어난 것이다.**

2026-08-26에 확인한 결과 **설정은 켜져 있었고**(`MultiAZ=True`, `AutomaticFailover=enabled`)
**실증 문서는 없었다.** 같은 세션에서 Cluster Autoscaler도 같은 상태였다([[IMP-021]]) —
**설계는 있고 측정이 빠지는 패턴**이 반복됐다.

## 2. 측정 방법

두 실험을 **분리**했다. 같이 주입하면 원인이 섞인다.

```
공통   EKS 1.35 · m6i.large · 클러스터 안 k6 · open model · 25 rps
       장애 전 워밍업으로 기준선 0을 확인한 뒤 주입

RDS    aws rds reboot-db-instance --force-failover
       부하: /events/{id}/seats (DB를 타는 조회)
       관찰: HikariCP 지표 1초 간격 + k6 실패 시각 + 파드 restartCount

Redis  aws elasticache test-failover --node-group-id 0001
       부하: /queue/status?token=... (대기열 ZSet — Redis가 진실원)
       관찰: 대기열 status 보존 여부 + k6 실패 시각 + 파드 restartCount
```

⚠️ **Redis를 좌석 조회로 재면 의미가 없다.** 그 경로는 DB·캐시를 타지 대기열 자료구조를
타지 않는다. 유실을 보려면 **Redis가 진실원인 경로**를 때려야 한다.

## 3. 결과

| | RDS | Redis |
|---|---|---|
| 총 요청 | 8,817 | 5,287 |
| 실패 | **93 (1.05%)** | **263 (4.97%)** |
| p95 | **22ms** | **19,498ms** |
| p99 | 30,004ms | 30,008ms |
| max | 30,050ms | 60,000ms |
| 실패 창 | 약 11초 | 약 33초 |
| 전환 | AZ `2b → 2c` | primary `002 → 001` |
| 파드 재시작 | **0** | **0** |
| 데이터 유실 | — | **0** (대기열 `ADMITTED` 보존) |

⚠️ **중앙값(p50)은 재지 않았다.** k6의 `handleSummary`가 기본 요약을 대체해 p95·p99만 남겼다.
그래서 *"절반이 느려졌다"* 같은 서술은 할 수 없다.

정확히 말할 수 있는 것은 이것이다 — **Redis 페일오버에서는 지연이 일부 극단값에만 머물지
않고 p95까지 19.5초로 올라갔다.** RDS는 p95가 22ms로, 대부분의 요청이 정상 속도였고
일부만 30초를 기다렸다.

## 4. 관찰 항목별 답 (terraform-design의 표)

### 커넥션 풀 — RDS에서 실제로 고갈됐다

```
12:05:09Z  force-failover
12:05:18Z  active=1 idle=4 timeout_total=0    (정상)
12:05:50Z  실패 시작
12:06:00Z  active=3 idle=1 timeout_total=57   ← 커넥션 획득 타임아웃 57건
12:06:03Z  active=1 idle=4 timeout_total=0    ← 파드 교체 없이 복귀
```

**고갈됐지만 재연결됐다.** `hikaricp_connections_timeout_total`이 57까지 올랐다가 0으로 돌아왔다.

### 오류 형태 — 두 경우를 나눠 적는다

⚠️ **같은 30초라도 원인 계층이 다르다. 묶으면 안 된다.**

| | 관측 | 원인 |
|---|---|---|
| RDS | 30초 대기 후 500(`dur=30,004~30,050ms`) | **Hikari 기본 `connection-timeout=30s`와 일치.** `application.yml`에 이 값이 **설정돼 있지 않아** 기본값이 그대로 적용된다(확인함) |
| Redis | 30초 안팎 지연 후 500 다수, 일부 60초 | ⚠️ **어느 타임아웃 계층이 지배했는지 분리하지 못했다.** Lettuce 명령 타임아웃·HTTP 클라이언트·상위 계층 중 무엇인지 미확정 |

### 중단 시간

RDS 약 11초(12:05:50~12:06:00), Redis 약 33초(12:35:58~12:36:31).

### 자동 복구 — 둘 다 성공

**파드 재시작 0회.** `restartCount`가 모두 0이었고 서비스는 스스로 정상화됐다.

### 유실 — Redis 대기열은 보존됐다

`ADMITTED` 상태의 토큰이 페일오버를 넘어 유지됐다(상태 유실 **0건**).
ADR-012가 우려한 *"비동기 복제라 최근 쓰기가 유실될 수 있다"*는 **이 조건에서 발생하지 않았다.**

**잃은 것은 데이터가 아니라 가용성이다.**

## 5. 결함 후보 — `connection-timeout`이 설정돼 있지 않다

`terraform-design.md`가 미리 적어 둔 그대로다.

> 여기서 설정 결함(검증 쿼리 미설정, **과도한 타임아웃**, 재시도 부재)이 드러나면
> 그 자체가 **TS 또는 IMP 문서 한 편**이 된다.

`application.yml`의 hikari 블록에는 `maximum-pool-size`만 있다. `connection-timeout`이 없어
**Hikari 기본 30초**가 적용된다. 커넥션을 못 얻는 상황이 명백한데도 30초를 다 쓴 뒤 500을 준다.

⚠️ **"30초를 줄이면 낫다"는 아직 추론이다.** 줄이면 빨리 실패하지만 **실패 건수는 늘 수 있다.**
개선으로 인정하려면 최소한 넷을 함께 봐야 한다.

```
사용자 최대 대기시간 감소
+ 장애 구간 실패율이 허용 가능한가
+ DB 복구 후 자동 정상화 유지
+ Hikari가 장시간 고갈되지 않는가
```

이 실험은 §8로 분리한다. **설정을 바꾸면 이후 장애 실험의 기준선이 달라지므로**,
baseline을 모두 확보한 뒤에 손대는 순서를 지켰다.

## 6. 측정 도구가 만든 문제 — 4번 만에 성공했다

이 실험 하나에서 함정이 **일곱 개** 나왔다. 전부 *"측정이 조용히 틀리는"* 방향이었다.

| # | 함정 | 안 잡았으면 |
|---|---|---|
| 1 | `MSYS_NO_PATHCONV` 누락 | SSM `ParameterNotFound`로 즉시 실패 |
| 2 | 응답 필드가 `position`이 아니라 `rank` | 모든 응답을 유실로 카운트 |
| 3 | `ADMITTED`면 `rank=0` | rank로는 유실 판정 불가 → `status`가 신호 |
| 4 | `admit-ttl(300초)` < `duration(360초)` | 토큰 자연 만료를 페일오버 유실로 오독 |
| 5 | 사후 조회 `jq` 오류로 종료 | **4분짜리 측정 로그를 통째로 잃었다**(실제 발생) |
| 6 | 정상 승격(`WAITING→ADMITTED`)을 유실로 셈 | 워밍업 45초에 **1,188건** 오탐(실제 발생) |
| 7 | AWS 재동기화 중 `test-failover` 거부 | 워밍업을 태우고 나서 두 번 막힘(실제 발생) |

### ⑤가 가장 나빴다 — trap이 증거를 지웠다

부수적인 단계(사후 상태 조회)의 오류로 스크립트가 죽었고, `trap cleanup`이 k6 Job을 지워
**주 측정 로그가 사라졌다.** 오늘 `trap`으로 복원 안전성은 계속 챙겼는데 **증거 보존은
챙기지 않았다.**

고친 뒤 **바로 다음 실행에서 그 salvage가 실제로 로그를 건졌다.**

### AZ 판정도 오판했다

RDS 실험에서 `DBInstanceStatus=available`만 보고 루프를 빠져나가, AZ 필드가 아직 갱신되기
전 값을 읽어 **"페일오버 안 됨"으로 기록**했다. 실제로는 AWS 이벤트에 `Multi-AZ instance
failover completed`가 있었고 AZ는 `2b → 2c`로 바뀌어 있었다.
**결과 해석이 뒤집힐 뻔했다.** 이제 AZ 전환 **또는** 이벤트 중 하나를 확인할 때까지 기다린다.

이 계열은 [[TS-036]]과 같다 — **판정 근거가 부족해 정상 상태를 잘못 읽는 측정 도구 결함.**

## 7. 한계

- **각 1회 측정**이다.
- **Redis는 토큰 1개로만 관찰했다.** *"대기열 전체가 보존된다"*는 뜻이 아니다.
- **중앙값을 재지 않았다**(§3).
- **완전 회복 시점을 정밀하게 재지 않았다.** Redis 실험에서 12:37~12:38에 산발적 실패
  (`status=0`, 60초)가 있었는데 **원인을 확인하지 않았다.**
- **Redis 30초의 타임아웃 계층을 분리하지 못했다**(§4).
- **`test-failover` 재동기화 대기 로직은 이번에 검증되지 않았다.** 넣은 뒤 성공한 실행에서는
  이미 대기가 끝나 있었다.
- 부하 25 rps다. 선착순 피크와 거리가 멀다.

## 8. 남은 것 — 개선 실험(별도 IMP)

**아직 열지 않는다.** 지금은 *"장애 시 이렇게 깨진다"*까지가 확인된 상태이고,
개선은 설정을 바꾼 뒤 **동일 조건 재측정으로 AS-IS/TO-BE를 비교**해야 성립한다.

- **RDS**: `connection-timeout` 조정 → 같은 `force-failover` 재측정
- **Redis**: 타임아웃·재연결 정책 조정 → 같은 `test-failover` 재측정
- 비교 기준: 실패율 / 최대 대기시간 / 자동 복구 / 풀 고갈 지속시간 (§5의 네 항목)

AS-IS 기준선은 이 문서의 §3이다.
