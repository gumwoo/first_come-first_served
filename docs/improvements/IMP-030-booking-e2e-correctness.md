## 1. 상황 (Context)
대기열 최종 시험([[IMP-029]])은 진입 → 대기 → 입장 제어까지였다. 입장한 사용자가 좌석 선점 → 주문 → 결제를 하는 downstream은 실행한 적이 없었다
([[ADR-023]] 시험 ④, [loadtest-100k-plan](../testing/loadtest-100k-plan.md) §2.1 "E2E 입장자 시험"). 이 시험은 **정합성 중심이다**(loadtest-plan Phase 3 — 성능 시험이 아니다).
규모는 공연당 좌석 100석·입장 정원 100명이라 run당 사용자 100명이다 — 10만 명을 끝까지 입장시키는 E2E는 계산상 약 83시간이라 하지 않는다(§2.1).

## 2. 문제 정의 + 분류
입장자 100명이 동시에 예매할 때 경합·중복 요청·결제 실패·1인 한도에서 좌석·주문·결제·이벤트 상태가 설계대로 수렴하는가.
- 계층 분류: 동시성(좌석 경합·중복 요청) / DB 정합성(조건부 UPDATE·부분 UNIQUE·멱등 키) / 이벤트(아웃박스 → Kafka → 소비자 멱등)
- 기존 근거: 단위·통합 테스트(`SeatQuotaIntegrationTest`·`PaymentIdempotencyIntegrationTest` 등)와 1석 대 100명 hold 경합(2026-08-11). 실제 경로에서 입장 → 결제를 잇고 시나리오를 겹친 적은 없다.

## 3. 측정 방법 (사전 등록 `e2e-prereg.md` — 결과 보기 전 고정)
- 구성: 클러스터 Git 상태(노드 3·HPA api 3–7·web 2–4), 발생기 c6i.xlarge 1대. preflight에서 자원 포화가 없으면 그대로 판정한다는 규칙으로 정했다
  (preflight: 발생기 CPU 1초 최대 7%, 노드 CPU 사용률 최대 23% — 1분 평균).
- 결제: 세션 한정 `PAYMENT_GATEWAY=mock`. `TossPaymentGateway.approve()`는 서버 단독 승인을 막고 `confirm()`은 결제창 `paymentKey`가 필요해
  k6 서버 부하로는 결제를 결정론적으로 만들 수 없다. `MockPaymentGateway`는 멱등 키가 `FAIL`로 시작하면 거절한다 — 실패 시나리오를 이걸로 만든다.
- 흐름: VU 하나 = 사용자 하나. T0 20초 전에 대기열에 들어가 ADMITTED까지 상태를 묻고, T0에 100명이 함께 예매를 시작한다. 공연은 run마다 새로(좌석 100석 전부 AVAILABLE).
- 역할(사용자 100명·좌석 84석):
  | 역할 | 인원 | 동작 |
  |---|---|---|
  | A 정상 | 30 | 1석 hold → 주문 → 결제 |
  | B 경합 | 40 | 좌석 4석을 10명씩 같은 좌석 hold → 이긴 사람만 주문 → 결제 |
  | C 더블클릭 | 10 | 같은 좌석 hold 2회 동시 → 같은 hold 주문 2회 동시 → 같은 멱등 키 결제 3회 동시 |
  | D 실패 후 재시도 | 10 | `FAIL-` 키 결제(거절) → 새 키로 재결제 |
  | E 실패 후 포기 | 5 | `FAIL-` 키 결제 후 중단 — hold TTL 300초 뒤 만료 회수 |
  | F 1인 한도 | 5 | 4석 hold → 주문 → 결제 → 다른 1석 hold(한도 4 초과) |
- 판정(run마다 전부, 3회 모두): ① 클라이언트 기대값(역할별 응답, 모든 요청 5xx 0) ② DB 기대값 13개(만료 회수 뒤 — T0 + 360초 이후)
  ③ 기존 사후 검사 `check-correctness.sh`(초과판매·일시적 이중 판매·결제·좌석 불일치·멱등 위반·미발행 아웃박스·이벤트 유실·대기열 순서·실효 입장 초과) + 실시간 감시.
- 무효: T0에 ADMITTED가 100명이 아님, 401, 파드 재시작, 발생기 CPU 1초 최대 ≥ 80%, mock이 아닌 결제, 공연 사전 상태 불일치.

## 4. 가설 (설계가 보장한다고 본 것 — 검증 전)
- B 패자의 hold는 좌석 조건부 UPDATE가 0행이라 409 `SEAT_CONFLICT`로 롤백된다(남은 좌석이 있으므로 `SOLD_OUT`이 아니다).
- C의 동시 hold 둘은 (사용자, 공연) advisory lock으로 직렬화돼 하나는 200, 하나는 `SEAT_CONFLICT`. 동시 주문은 부분 UNIQUE(`uq_orders_active_hold`)로 같은 주문,
  같은 멱등 키 결제는 `uq_payments_idem`과 승자 대기로 같은 결제를 돌려준다.
- D·E의 실패 결제는 결제만 FAILED이고 주문은 PENDING이라 재결제할 수 있다. E는 hold·주문 만료 회수로 좌석이 AVAILABLE로 돌아온다.
- F의 5번째 hold는 PAID 좌석까지 세는 1인 한도 검사가 좌석 UPDATE보다 먼저라 409 `MAX_PER_USER_EXCEEDED`.

## 6. 조치 (해결)
코드 변경은 없다 — 이 시험은 기존 정합성 장치(조건부 UPDATE·advisory lock·부분 UNIQUE·멱등 키·아웃박스·소비자 멱등)를 실제 경로에서 겹쳐 확인한 것이다.
만든 것은 측정 도구(#358)다: 역할별 기대값을 설계에서 정하고(결과에서 거꾸로 만들지 않음 — B 승자만 "좌석마다 정확히 한 명"), DB 기대값은 SELECT만 하는 SQL로 판정한다.

## 7. 결과
사전 등록한 세 판정(클라이언트 기대값·DB 기대값·기존 사후 검사)이 판정 3회 모두 통과했다. 위 §4의 설계 가정은 이 시나리오·규모에서 반증되지 않았다.

## 8. 트레이드오프 / 한계 / 다음 개선
- **규모**: run당 입장자 100명(정원)·좌석 100석이다. 처리량 시험이 아니고, 10만 명 E2E도 아니다. hold 응답 p95가 0.5~0.9초·최대 1.46초로
  100명 동시 시작치고 느린 편이지만 원인(advisory lock 직렬화·DB 커넥션 풀·web 홉 등)은 확인하지 않았다 — 처리량·지연을 주장하지 않는다.
- **결제는 mock이다**: 실제 PG(Toss) 승인·취소·지연·결과 불명(timeout) 경로는 이 시험 밖이다. 결제 실패는 mock의 결정론적 거절로 만든 것이다.
- **범위 밖**: vbank(입금 대기·웹훅 콜백 중복), 환불, 슬롯 회전(leave로 정원 반환 후 다음 입장자), 결과 불명 결제의 정산(`PaymentReconciliationService`).
  loadtest-plan Phase 3의 "콜백 중복 0"은 재지 않았다.
- **경합 강도**: B는 좌석당 10명이다. 같은 사용자가 여러 좌석을 섞어 다투는 교착 가능 시나리오는 넣지 않았다(F 좌석은 아무도 다투지 않는다).
- **preflight에서 측정자 실수**: 세션 스크립트가 이전 세션의 활성 공연(1767)을 지우지 않아 preflight의 check-correctness가 판정 불가였다(판정 run 전에 고침 — 사전 등록 확정 절).
- **세션 한정 변경**은 원복했다(결제 mock 끔·ArgoCD 자동 동기화 켬). mock은 공개 사이트 결제에도 적용되므로 측정 직후 껐다(IMP 기록 전).

## 9. 배운 점 (면접 답변용 한 줄)
입장자 E2E는 처리량보다 "동시에 겹친 시나리오가 설계대로 수렴하는가"가 핵심이라, 경합·더블클릭·결제 실패·1인 한도를 역할로 나눠 한 run에 겹치고 기대값을 결과가 아니라 설계에서 미리 고정해
응답·DB·이벤트 세 층에서 판정했다 — 실패 결제를 만들려고 결정론적 mock 게이트웨이를 세션 한정으로 걸고, 끝나자마자 되돌렸다.
