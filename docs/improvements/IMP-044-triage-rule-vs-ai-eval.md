# IMP-044 · 장애 초기 분석 평가(로컬): 규칙 분류기 vs AI(Claude Haiku 5.5), 장애 주입 23회

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-22(로컬 실험실 `infra/triage-lab`, 결과 `artifacts/triage-lab/eval/`, 레포 밖)
- 유형: 평가(로컬 실측, 유효 run 23회). 같은 로컬 환경 안의 비교다.
- 관련: [[ADR-029]](AI를 쓰는 범위), [[IMP-043]](측정 환경 판정의 출처), `scripts/triage/`(eval.mjs·rules.mjs·analyze.mjs)
- 벤치 파일: 레포 밖 `artifacts/triage-lab/eval/`: 사전 등록 `prereg-eval.md`, 실행 순서 `plan.txt`, 측정 기록 `runs.txt`·`notes.txt`, 채점 결과 `result/`(run별 JSON, `rows.json`, `summary.json`). 라벨은 `artifacts/triage-lab/labels.jsonl`

## 1. 상황 (Context)
부하 테스트 run의 원인 후보를 내는 도구를 만들었다([[ADR-029]]). 같은 요약 JSON을 두 방식으로 판정한다.
- 규칙 분류기: 주입 확인 run으로 정한 원인별 기준값(Redis 지연 5ms, PostgreSQL 활성 0.5, 커넥션 점유 20ms).
- AI: Claude Haiku 5.5(프롬프트 v3). 정상 run 3회의 지표 범위만 받고, 원인별 기준값은 받지 않는다.

원인을 알고 주입한 새 run으로 두 방식의 정답 수를 비교했다.

## 2. 문제 정의 + 분류
- 계층: 운영 도구(분석). 서비스 코드와 무관하다.
- 질문: 같은 요약에서 AI가 규칙 분류기보다 원인을 더 많이 맞히는가. 정상 run을 원인으로 잘못 판정하지 않는가.

## 3. 측정 방법
- 판정 기준은 측정 전에 등록했다(`prereg-eval.md`, 2026-10-22 10:22:36).
- 실험실: api(코어 2개, 풀 5)·대기열·PostgreSQL·Redis, 입장자 100명이 같은 순간 예매(선점·주문·결제).
- 장애 주입:
  - redis: Redis 컨테이너 네트워크 지연 30ms(강도 1) / 60ms(강도 2)
  - db: PostgreSQL CPU 할당 0.05코어 / 0.03코어
  - cpu: api CPU 할당 0.4코어 / 0.25코어
- 계획: 장애 3종 × 강도 2 × 3회 = 18회, 정상 6회. 실행 순서는 무작위다.
- 측정 무효(디스크 프로브 중앙값 10ms 초과, 지표가 분석 구간을 감싸지 못함 등)인 run은 같은 조건으로 다시 찍었다(최대 2회).
- 채점: 판정이 라벨과 같으면 정답. 판단 불가는 오답으로 세되 따로 집계한다. AI는 유효 run 전부에 불렀고, 근거 수치 대조에 실패한 답은 판단 불가로 처리했다.

측정 경과는 다음과 같다(`notes.txt`).
- 유효 run 23회: 장애 17회, 정상 6회.
- db 강도 2의 한 칸은 3회 모두 "api 누적 지표가 분석 구간을 감싸지 못한다"로 무효라, 사전 등록대로 결과에서 뺐다. 같은 조건의 다른 두 칸은 유효였다.
- 측정 환경 문제로 무효였던 run 4회는 다시 찍었다(디스크 지연 2회, 디스크 포화 중 k6 사전 준비가 예매 시작 전에 못 끝난 2회). 같은 PC의 다른 작업이 디스크를 포화시킨 구간은 측정을 멈췄다가 디스크 프로브가 3분 연속 정상일 때 재개했다.
- 측정 루프 두 개가 잠깐 겹친 구간의 run 1회는 제외하고 다시 찍었다.
- 실험실을 한 번 다시 띄웠다. 유효 run 2회는 재기동 전, 21회는 재기동 후다.

- **판정(사전 등록): 규칙 우세.** 장애 정답이 규칙 13, AI 11이다. 사례가 23회라 2건 차이는 우연과 구분되지 않는다.
- AI 호출 23회의 평균 토큰은 입력 3,818·출력 3,123이고, 비용은 합계 $0.0447(호출당 약 $0.002)이다(공개 단가로 계산).

### 4.1 CPU 장애
- 규칙은 6회 중 2회를 맞혔다. 틀린 4회 중 redis 3회는 Redis 명령 완료 평균이 5.2~14.9ms로 Redis 기준(5ms)을 넘었고, db 1회는 PostgreSQL 활성 세션 평균이 0.66으로 DB 기준(0.5)을 넘었다. 앱이 CPU를 못 받으면 Redis 응답 처리와 트랜잭션도 함께 늦어진다(추론).
- AI는 6회 모두 틀렸다(db 3회, redis 3회). 예를 들어 한 run에서 AI는 "api CPU 평균 0.21·최대 0.43코어로 정상 기준보다 낮아 CPU 부족은 뒷받침되지 않는다"는 근거를 들었다. 6회의 CPU 최댓값은 0.25~0.6코어로 정상 기준(0.76~1.76코어)보다 낮다.
- 이 실험실의 CPU 장애는 할당량(0.4·0.25코어)으로 주입한다. 할당량에 막힌 컨테이너는 CPU 사용량이 낮게 찍힌다. 요약에는 할당량에 막힌 정도(cgroup throttling) 지표가 없어, CPU 사용량만으로는 CPU 부족을 알아볼 수 없다(추론).

### 4.2 정상 run의 판단 불가 3회
- 2회는 AI가 "정상"으로 답했지만, 근거로 `validity.valid`(참·거짓 값)를 인용했다. 대조기(`verify.mjs`)는 숫자 필드만 대조해 "경로 없음"으로 실패 처리했다.
- 1회는 WAL 동기화 1회 평균이 2.91ms로 정상 기준 범위(0.73~0.82ms)를 벗어나 판단을 보류했다. 정상 기준은 run 3회의 범위라 좁다(추론).

### 4.3 판정 근거
- AI가 맞힌 run에서는 근거마다 정상 범위와의 차이를 적었다. 예를 들어 Redis 지연 33ms를 정상 범위(0.31~0.64ms)와 비교했다. 반대 지표(DB 활성 세션, CPU 최댓값)도 함께 적었다.
- 근거 수치 대조 실패는 4.2의 2회뿐이다. 나머지 21회는 인용한 수치가 모두 요약과 일치했다.

## 5. 조치
- 원인 판정은 규칙 분류기를 기준으로 둔다. AI는 판정과 함께 근거, 반대 지표, 다음에 확인할 항목을 정리하는 데 쓴다.
- 기본 모델(Haiku 5.5)과 요청 형식은 그대로 둔다.
- `infra/triage-lab/lab.sh`: 측정용 psql `-c` 호출이 표준 입력을 읽지 않게 했다. 반복문 안에서 부르면 반복문의 입력을 읽어 첫 칸 뒤로 진행하지 않았다.

## 6. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대 비교다. 장애는 세 종류이고, 각 장애를 하나씩만 주입했다.
- 다음 개선(각각 새 평가 run으로 다시 잰다):
  - 요약에 CPU 할당량에 막힌 정도(cgroup `cpu.stat`의 throttling)를 넣는다. 4.1의 오판정에 직접 관련된 지표다.
  - 대조기가 참·거짓 근거를 다루거나, 프롬프트에서 숫자 필드만 근거로 쓰게 한다(4.2).
  - 정상 기준을 더 많은 정상 run으로 잡는다(4.2).
- 기준값과 프롬프트는 이번 평가 run을 보기 전에 고정했다. 위 개선을 이번 run에 맞춰 조정하면 평가가 아니게 되므로, 고친 뒤에는 새 run으로 평가한다.
