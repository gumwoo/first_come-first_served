# 좌석맵 Redis 캐시 — 개선 결과 요약

`GET /events/{id}/seats`에 Redis TTL 캐시를 적용하고, 캐시 hit이 트랜잭션·커넥션을
잡지 않도록 조회를 트랜잭션 밖으로 뺐다.

측정: **400 rps · 90초 · seats 단독 워크로드** (EKS 3AZ, api HPA 3~7 / web 2~4)

## 결과

| 지표 | before | after | 변화 |
|---|---|---|---|
| **API CPU** | 2.55 ms/req | **1.56 ms/req** | **-39% (1.63배)** |
| **노드 CPU** | 5.39 ms/req | **3.89 ms/req** | **-28% (1.38배)** |
| **서버 p95** | 11.1 ms | **4.2 ms** | **-62%** |
| **서버 p99** | 24.5 ms | **9.7 ms** | **-60%** |
| **DB 커넥션/요청** | 1.005 회 | **0.025 회** | **-97% (40배↓)** |
| 같은 부하 처리 파드 수 | 7 | **5~6** | |

**이론 상한은 1.89배**(API 계산 비용이 0이 된다는 가정). 실측 1.38배가 그 아래인 것은
캐시 조회·역직렬화 비용과 **엔드포인트와 무관한 web 계층 비용(약 2.1 ms/req)**이 남기 때문이다.

### 커넥션 40배 감소가 핵심이었다

캐시를 넣은 것만으로는 커넥션이 **전혀** 줄지 않았다(요청당 1.005회). 서비스가 클래스 레벨
`@Transactional(readOnly = true)`라 **캐시 hit이어도 프록시가 트랜잭션을 열고 커넥션을 잡았기**
때문이다. 조회를 트랜잭션 밖으로 빼고 miss일 때만 트랜잭션을 열도록 바꿔 0.025회가 됐다.

## ⚠️ 한계 — 이 숫자를 읽을 때 함께 봐야 할 것

- **after는 1회 측정이다.** before는 5회 반복해 수렴을 확인했지만(336 → 156 → 114 → 98.0 → 99.7)
  after는 워밍업을 300초로 늘린 1회다. **비대칭이다.**
- **before/after의 파드 수가 다르다**(7 vs 5~6). idle CPU를 파드당 상수로 환산해 보정했으나
  그 자체가 **가정**이다.
- **중간 단계 값을 유실했다.** "캐시만 넣은 상태"의 CPU 수렴값이 측정 겹침으로 오염됐고 코드가
  이미 머지돼 재측정이 불가능하다. 따라서 **"캐시 효과"와 "트랜잭션 경계 제거 효과"를 나눠
  말할 수 없고, 합산만 말할 수 있다.**
- **절대 성능이 아니다.** 부하는 노트북에서 인터넷 경유로 걸었다. 판단은 서버 지표로 했고,
  이 값은 **동일 조건 비교용**이지 시스템의 최대 처리량이 아니다.
- **운영에는 적용하지 않았다.** 성능이 아니라 **정확성** 때문이다 — 좌석은 재고성 상태라
  TTL 동안 이미 선점된 좌석이 `AVAILABLE`로 보인다. 이벤트 기반 무효화 + single-flight를
  갖춘 뒤에야 켤 수 있고, **1.38배를 위해 그 복잡도를 감수할지는 별도 판단이다.**
