# IMP-047 · 대기열 Pod의 api Pod 회피 규칙(required anti-affinity) 스케줄링 시뮬레이션(kwok)

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-26(시뮬레이션 `artifacts/loadtest/kwok-20261020/`, 레포 밖)
- 유형: 시뮬레이션(실제 kube-scheduler, 가짜 노드·Pod). 클러스터에서 재지 않았다.
- 관련: [[IMP-037]](같은 도구·입력), [[IMP-038]](api·대기열 동거 경합), [[ADR-026]](B1 노드당 하나 명시 규칙 후보), [[ADR-027]](대기열 전용 Deployment)
- 벤치 파일: 레포 밖 `artifacts/loadtest/kwok-20261020/`: 사전 등록 `prereg-AA.md`, 시나리오 `scen-AA/*.json`, 결과 `out-AA/*.json`

## 1. 상황 (Context)
api와 대기열이 한 노드를 나눠 쓰면 폴링 p99가 10ms대에서 0.6~1.3초로 늘었다([[IMP-038]]). 지금 둘이 떨어져 놓이는 것은 CPU 요청량 1100m가 노드(m6i.large)에 하나만 들어가는 부수 효과다([[ADR-026]]).
요청량을 낮추면 동거가 돌아온다. [[IMP-037]]의 S2(api 300m)는 노드를 하나 줄였지만, 줄어든 노드는 api와 대기열이 한 노드를 나눠 쓰는 배치였다.

## 2. 문제 정의 + 분류
- 계층: 쿠버네티스 배치 규칙.
- 질문: 대기열 Pod에 "api Pod가 있는 노드에는 놓이지 않는다"는 규칙을 더하면 지금 노드 수가 그대로인가, 요청량을 낮춰도 동거가 막히는가.

## 3. 측정 방법
- 판정 기준은 시뮬레이션 전에 등록했다(`prereg-AA.md`, 2026-10-26 14:00:30).
- 도구·입력은 [[IMP-037]]과 같다: kwok 클러스터(`registry.k8s.io/kwok/cluster:v0.7.0-k8s.v1.33.0`, 실제 kube-scheduler), 실제 클러스터 스냅샷(시스템 Pod·데몬셋·노드 명세), 렌더링한 매니페스트, CA 흉내(배치 못 한 Pod가 있으면 노드가 가장 적은 AZ에 1대 추가, AZ당 3대 상한).
- 규칙: 대기열 Pod에 `podAntiAffinity.requiredDuringSchedulingIgnoredDuringExecution`(`app: flowticket-api`, `topologyKey: kubernetes.io/hostname`).
- 시나리오: AA-V0(지금 요청량 + 규칙), AA-S2(api 300m + 규칙). 평시는 api 3·web 2·대기열 2, 사전 확장은 대기열 6이다.

## 4. 결과 (시뮬레이션)

| 시나리오 | 평시 노드 | 사전 확장 노드 | Pending | api·대기열이 같은 노드 |
|---|---|---|---|---|
| V0(지금, IMP-037) | 5 | 9 | 0 | 0 |
| AA-V0(지금 + 규칙) | 5 | 9 | 0 | 0 |
| S2(api 300m, IMP-037) | 4 | 8 | 0 | 1 |
| AA-S2(api 300m + 규칙) | 5 | 9 | 0 | 0 |

- 판정(사전 등록): (a) AA-V0은 V0와 같다 — 충족. (b) AA-S2에서 api·대기열이 같은 노드 0 — 충족.
- AA-S2의 노드 수는 S2보다 하나씩 많다(평시 5, 사전 확장 9). S2가 줄인 노드는 동거로 얻은 것이었다는 [[IMP-038]]의 결론과 맞는다.
- 같은 규칙을 api 쪽에 둔 [[IMP-038]]의 S2a(api 300m, 대기열 회피)도 평시 5·사전 확장 9·동거 0이었다. 규칙을 어느 쪽에 두어도 배치가 같았다.

## 5. 조치
- `k8s/components/queue-split/queue-deployment.yaml`에 규칙을 더했다. required anti-affinity는 kube-scheduler가 기존 Pod의 규칙도 새 Pod에 적용해 양방향으로 지키므로, 나중에 놓이는 api Pod도 대기열 Pod가 있는 노드에 놓이지 않는다(스케줄러 동작. 이번 시뮬레이션은 api를 먼저 놓아 이 방향을 직접 재지 않았고, 위 S2a가 간접 근거다).
- 하네스 k8s 규칙: ⑩-b 허용 목록에 대기열 쪽 `affinity`를 더하고(api 쪽에 두면 불일치), ⑩-d가 규칙의 모양을 검사한다(위반 fixture `k8s-queue-no-api-anti-affinity`).

## 6. 트레이드오프 / 다음 개선
- 시뮬레이션은 롤링 surge를 다루지 않는다. 대기열 surge Pod는 api가 없는 노드가 필요하다. 지금은 요청량 1100m 때문에 원래도 빈 노드가 필요해 차이가 없을 것으로 본다(추론).
- CA가 anti-affinity를 모의해 노드를 붙이는 동작은 이 구성에서 실측하지 않았다([[ADR-026]]). 시뮬레이터의 CA 흉내는 Pending이면 노드를 더하는 단순 규칙이다.
- 요청량 자체를 낮추는 일(ADR-026 B1의 나머지)은 HPA 기준선이 바뀌어 별도 측정이 필요하다. 이 규칙은 그때도 동거를 막는 바닥이 된다.
- [[IMP-039]]의 평시 동거 안(채택 보류)은 이 규칙과 맞지 않는다. 다시 검토하려면 평시에 규칙을 푸는 방법까지 함께 정해야 한다.
- 클러스터가 떠 있을 때 머지되면 ArgoCD 동기화로 대기열 Pod 템플릿이 바뀌어 대기열 Deployment가 한 번 롤링된다.

## 7. 배운 점 (면접 답변용 한 줄)
요청량의 부수 효과로만 지켜지던 "api와 대기열은 다른 노드" 조건을 실제 스케줄러 시뮬레이션으로 확인한 뒤 anti-affinity 규칙과 하네스 검사로 고정해, 요청량을 바꿔도 동거 경합이 돌아오지 않게 했다.
