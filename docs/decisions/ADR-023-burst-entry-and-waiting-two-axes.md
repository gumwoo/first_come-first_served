# ADR-023 · 10만 burst 대비 — 진입 경로와 대기 유지를 두 축으로 나눠 고친다

- 상태: **Proposed** — 합의(2026-10-06, 사용자 결정): 두 병목을 분리해 다룬다, 축 ② 대기 상태는 폴링 주 경로로 옮긴다, 사전 확장·requests 현실화를 운영 방향으로 둔다. 축 ①의 세부 변경과 모든 수치는 아래 §실행 순서의 측정을 거쳐 별도 PR·IMP로 확정한다
- 날짜: 2026-10-06
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-002]](대기열 — ZSet·배치 승격·Lua), [[ADR-008]](SSE 라스트홉), [[ADR-015]](대기 상태 동기화 — **이 ADR이 결정을 뒤집는다**, §2),
  [[IMP-023]](api 메모리), [[IMP-024]](liveness), [loadtest-100k-plan](../testing/loadtest-100k-plan.md)
- 근거 데이터: 측정 세션 `20261005-1440`(원시 데이터는 레포 밖 `artifacts/loadtest/20261005-1440/`, 운영 기록 `session.log`).
  수치 출처는 둘이다 — 측정 run 게이트(G3)가 원시 데이터로 다시 계산한 값, 그리고 G3가 판정하지 않은 run
  (`step5api-4pod-sr_1400aps-r1·r2`, `step8pre-n5d_10k_constant-r1·r2`)과 G3가 HPA 반응 시점을 재계산하지 않은 run(`step9b-10k_constant-r3`·
  `diag-10k_constant-r1·r2`)의 운영 기록 실측값(이 ADR의 PR 검증에서 원시 데이터·k8s 이벤트로 다시 확인).

> 시나리오 표기: 이 문서의 "10만 burst"는 **100,000 users arriving over 10 seconds (target 10,000 req/s)**다.
> 같은 10만 명도 창이 60초면 평균 1,667 req/s, 5초면 20,000 req/s라 burst 창을 빼고 쓰지 않는다.

## 맥락

S-10K(10,000명이 10초 동안 진입, Constant 1,000/s, SSE 50초 유지)를 m6i.large 노드 3대 기본 구성에서 쟀다. 진입 지연이 수 초~20초였고
일부 run에서 진입 요청이 실패했다. 사후 정합성을 판정할 수 있었던 run은 전부 위반 0이었다(정원 초과·순서 위반 — 실측). 단 step6·step9는
api 재시작으로 승격 기록이 빠져, diag-r1은 run 중 재시작·로그를 읽지 못한 파드로 파드 대조가 불완전해, step9b-r2는 리셋 위반으로 판정 불가였고, 입장 → 좌석 → 주문 경로는 실행하지 않아 초과판매·downstream 보호는 검증되지 않았다.
측정에서 성격이 다른 한계 두 개가 따로 드러났다.

### 축 ① 진입 경로 — 진입 POST 처리 CPU (SSE와 별개)

| 관측(실측) | 값 |
|---|---|
| SSE **없이** 진입 POST만 1,400/s(api 4·web 4 고정, 워밍업 뒤 4회) | p95 3.96~9.80s(반복 편차 큼). api 파드가 있는 노드에서 버스트 중 CPU ≥0.9 표본이 반복됐다(api 1개+web 1개 노드는 1~2표본으로 짧았다) |
| api 파드 수만 늘림(1→2→4, 노드 3대) | 지연이 뚜렷이 줄지 않음. 단 도착률이 다르고(api1 1,200/s, 나머지 1,400/s) 반복 편차·조건 차이로 효율 곡선은 확정 못 함 |
| 지연 위치 | ALB 대상 응답 시간 p95 ≈ 클라이언트 p95 → ALB 뒤(web·api) |
| Redis 서버 / RDS | CloudWatch 1분 평균 기준 Redis 서버 명령 지연 ≤52μs, RDS CPU ≤8%(S-10K run·단계 5 유효 run·사전 확장 비교 run 범위) — 포화 신호 없음 |
| 부하 중 Redis 클라이언트 대기 | Lettuce 명령 완료 평균 16~53ms(서버는 μs) — CPU 포화 노드의 프로세스 내부 대기로 보인다(추론) |
| web(Next 프록시) CPU | `step5diag-2pod-8web_1400aps-r2`의 포화 노드(47-44)에서 api 약 12.2 vs web 3개 약 12.9 cpu-s(cadvisor 추정). 비율은 run마다 다르다 |
| S-10K 사전 확장(api 7·web 4 고정, 워밍업 뒤) 노드 3대 vs 5대 | 앱 노드 3대 2/2 run에서 ALB→web 연결 실패(TargetConnectionError 317·54), 노드 5대 6/6 run 0건. 진입 p95 노드 3대 9.21·10.00s, 노드 5대 0.29~6.11s. 노드 5대 6회 중 2회는 B 구성(노드 분산 함께 변경), 2회는 앱이 4대에만 올라갔다 |
| HPA 반응 시점(반응형 S-10K run 7개 중 api가 확장된 6개) | api의 첫 확장 이벤트(`SuccessfulRescale`)가 첫 도착 뒤 14~26초 — 10초 버스트가 끝난 뒤(step9 14초도 마지막 도착 뒤). step6은 api가 늘지 않았고 web만 약 35~45초 뒤 확장 |
| requests 대 실사용 | api `requests.cpu` 300m, 버스트 중 실사용은 파드당 약 1~2코어(cadvisor 추정) |

**해석(추론)**: 진입 버스트의 첫 병목은 요청 처리 CPU × 노드 CPU 총량이다. 노드 수를 바꾸면 메모리·파드 밀도도 함께 바뀌어
CPU만 분리하지는 못했다. 노드 5대 안에서도 p95가 20배 벌어졌고, 그 편차는 api 2개와 web이 같이 앉은 노드의 쏠림과 함께
나타났다(상관). requests가 실사용보다 훨씬 작아서, HPA가 파드를 늘려도 스케줄러는 기존 노드에 들어간다고 보고 Pending이
생기지 않는다 — Cluster Autoscaler는 Pending을 보고 노드를 늘리므로 노드가 늘 계기가 없다.

### 축 ② 대기 유지 — 대기자 전원의 SSE 연결

| 관측(실측) | 값 |
|---|---|
| 파드당 SSE 연결과 메모리 | 1Gi에서 약 3,300~3,500 연결 시점 OOM(IMP-023) |
| 연결 등록 락 | 덤프 직전 표본 톰캣 연결 2,003개인 파드에서 요청 스레드 199개가 `ConnectionHandler.register`(JMX) 대기, 이어 liveness 재시작(IMP-024) |
| 끊긴 연결 정리 | 클라이언트가 닫은 뒤에도 서버 emitter가 남아 리셋 때 파드를 재생성해야 했다(반복 재현) |
| 연결 개설 속도 | 구성과 무관하게 약 110건/s로 일정 — 원인 미확인(발생기 또는 ALB 앞단 후보, 추론) |

이 한계는 연결 계층의 문제다. **SSE를 없애도 축 ①은 남는다**(SSE 없는 run에서도 노드 CPU 포화).

## 결정

확정하는 것은 상태 줄의 합의 범위다 — 두 병목을 분리해 다룬다, 축 ② 대기 상태는 폴링 주 경로로 옮긴다(§2), 사전 확장·requests 현실화를
운영 방향으로 둔다(§1 (c)(d)). 축 ①의 세부 변경((a)(b)(e))은 "검증 후보"로 두고 측정으로 고르며, 모든 수치는 측정으로 정한다.

### 0. 유지한다

- 대기열 핵심: Redis ZSet + Lua 원자 발급·승격([[ADR-002]]).
- 기존 입장 제어: 이벤트당 **동시 입장 정원** `capacity 100`, 승격 주기 1.5초, 입장 유효시간 300초. 새로 만들지 않고 처리량과 보호 효과를 검증·강화한다.
  `capacity`는 **동시 입장자 수**의 상한이지 초당 처리량이 아니다.
- 승격 워커(`QueueAdmissionService.runOnce`, `@Scheduled`)는 의도적으로 모든 파드에서 락 없이 돈다 — Lua가 원자적이라 다중 파드 동시 실행이
  안전하고, 단일 리더로 묶으면 처리량이 준다(ADR-002/006, 코드 주석). 배포 단위를 나누더라도 정합성 장치를 새로 둘 문제가 아니라
  "워커를 어느 배포에 둘지, 파드 수에 따라 승격 빈도가 달라지는 효과"를 정할 문제다.
- 구매 정합성 계층: 좌석 조건부 UPDATE, Kafka + Outbox/DLQ. 주문 SSE([[ADR-017]])는 이 ADR의 범위 밖이다(대기자 수와 비례하지 않는다).

### 1. 축 ① 진입 경로 — 검증 후보와 확정 사항

목표 경로는 `Browser → ALB → 진입 API → Redis`처럼 얇은 경로다. 아래 (a)(b)는 **검증 후보**이고, 어느 것을 할지는 §실행 순서 ①의 분리 측정으로 정한다.

- (a) **요청당 비용 축소(검증 후보)** — 진입 요청은 발급 Lua 뒤에 입장 여부·순번·전체 수를 따로 조회한다(순번은 두 번, `QueueService.tokenResponse`).
  이를 한 번의 Lua로 묶는 것, 판매 여부 DB 조회(`requireBookable`)를 짧은 캐시로 바꾸는 것. 둘 다 CPU 핫패스로 확인된 것은 아니다(JFR로 확인 후 결정).
- (b) **Next 홉 우회(검증 후보)** — ALB가 진입·상태 경로를 api로 직접 보낸다. ALB 경로 라우팅은 접두어를 떼지 않으므로(`ingress.yaml` 주석)
  api 쪽 경로 처리와 인증·쿠키 영향 확인이 필요하다. SSE 없는 같은 조건에서 web→api와 api 직접을 비교한 뒤 정한다.
- (c) **용량 운영(확정 방향, 수치는 단계 10)** — 오픈 시각이 정해진 이벤트이므로 이벤트 전에 노드·파드 용량을 사전 확장하고, 종료 후 축소한다.
  HPA는 예상 초과 부하에 대한 보조 수단으로 검증한다. 이번 측정 조건에서는 노드 5대 run 6회 모두 오류가 없었고(그중 B 2회의 5대는 리셋 재생성에
  Cluster Autoscaler가 반응해 생긴 노드라 사전 확장 수단으로 만든 것은 아니다), 노드 3대 조건 2회에서는
  모두 오류가 났다. 다만 노드 5대에서도 p95 편차가 커서 사전 확장은 오류 억제에 유효한 운영 전략으로 보고, 지연 변동 원인은 따로 분석한다.
  지금 구조(AZ별 노드 그룹 min 1/max 3 + Cluster Autoscaler)로 할 수 있다 — Karpenter 전환은 필요가 측정될 때만 검토한다.
  HPA에는 예약 확장 기능이 없으므로 사전 확장 수단(노드 그룹 예약 작업, HPA 하한 조정 자동화 등)은 단계 10에서 정한다.
- (d) **requests 현실화(확정 방향, 수치는 단계 10)** — api `requests.cpu`를 실사용 근거로 다시 정한다. 함께 정할 것 두 가지:
  HPA 목표(60%)는 requests 대비 비율이라 requests를 올리면 확장 시점이 크게 늦어진다(지금은 300m의 60%인 180m만 써도 확장 대상이 되고, 반응형 S-10K run에서 api가 버스트 직후 3→6~7로 올랐다 — step6 제외).
  Cluster Autoscaler의 축소 판단도 requests 기준이라, requests가 작으면 바쁜 노드도 한가하게 보일 수 있다(추론).
- (e) **배치 쏠림 방지(후보)** — api의 노드 단위 분산. 근거가 상관 수준이라 단계 10에서 함께 판단한다(보류 브랜치 `perf/api-node-spread`).

### 2. 축 ② 대기 상태 전달을 폴링 주 경로로 옮긴다 — ADR-015를 뒤집는다

[[ADR-015]]는 "SSE를 주 경로로 두고, `onopen` 재동기화로 복구를 만든 뒤 폴링을 저빈도 안전망으로 내린다"로 결정했다. 이 ADR은 그 결정을
**반대로 바꾼다** — 대기 상태 전달은 폴링을 주 경로로 하고, SSE는 제거하거나 보조 경로(예: 입장 알림)로 줄인다. 근거는 축 ②의 실측이다.
ADR-015의 상태 갱신은 이 ADR이 Accepted될 때 함께 한다.

단순히 고정 주기 폴링으로 바꾸면 안 된다 — 대기자 10만 명이 15초마다 조회하면 약 6,667 req/s, 20초면 5,000 req/s가 대기 내내 이어진다(계산값).
조건은 셋이고, 구현 세부는 측정으로 정한다.

1. **서버가 다음 조회 시각을 정한다** — 응답에 `retryAfterMs`(또는 `Retry-After`)를 담아 순번·정원에 따라 서버가 주기를 늘리거나 줄인다.
2. **jitter** — 클라이언트가 ±무작위 폭을 더해 같은 시각에 몰리지 않게 한다. 평균이 같아도 주기가 맞물리면 주기마다 작은 버스트가 생긴다.
3. **조회 경량화** — 상태 조회를 Redis 왕복 1회 수준(한 번의 Lua: 메타·입장 여부·순번)으로 줄이고, 가능하면 축 ①(b)와 같이 Next 홉을 거치지 않는다.

### 3. 스케일링 단위를 나눈다(후보)

진입·상태와 구매(좌석·주문)를 같은 이미지라도 배포 단위로 나눠 따로 늘리는 것을 검토한다. 근거는 설계상 판단이다(추론) —
구매 트래픽을 섞어 잰 적은 없다. 나눌 때 정할 것은 §0의 승격 워커 위치다.

### 4. 표현 규칙

- 입장 판정은 지금 Redis 상태(UUID 토큰 + `admit`/`admitExp`)다. 서명 토큰(JWT 등)을 구현하기 전에는 "입장 토큰 구조"라고 쓰지 않는다.
- "10만 처리", "SLO 달성", "병목 확정"은 아래 시험 ⑤를 통과하기 전에 쓰지 않는다.

## 목표

> 100,000 users arriving over 10 seconds (target 10,000 req/s)의 대기열 진입을 수용하면서 대기열 정합성 위반 0,
> 대기 상태 조회를 안정적으로 제공하고, 구매 계층에 들어간 **동시 입장자 수를 capacity 이하로** 유지하며, 좌석 초과판매 0을 검증한다.

## 실행 순서 — 축을 떼어 재고, 마지막에 합친다

| # | 시험 | 조건 | 보는 것 |
|---|---|---|---|
| ① | 진입 | SSE 없음, 진입 POST만 | 노드 3 vs 5(CPU), web→api vs api 직접, 버스트 중 CPU 프로파일(JFR) → 축 ①(a)(b) 중 무엇을 할지 |
| ② | 상태 조회 | 대기자 N명, 폴링(서버 주기·jitter) | 지속 조회 부하, 조회당 비용 |
| ③ | 입장 제어 | 대기자 충분 | 동시 입장자 ≤ capacity, 설정한 주기대로 통과하는가 |
| ④ | downstream | 입장 → 좌석 → 주문 | 초과판매 0, DB·Kafka 안정성(지금까지 미실행) |
| ⑤ | 최종 E2E | 10만 burst → 대기 → 입장 → 좌석·주문 | 위 목표 전체 |

- 지금의 S-10K 사전 확장 결과는 SSE가 섞여 있어 진입만의 scaling 근거로 쓰지 않는다 — "노드 5대에서 오류가 사라지는가, 배치 쏠림과 지연이 함께 움직이는가"를 보는 자료다.
- 100K/10s 검증 전에 분산 발생기로 목표 10K req/s를 독립 검증한다. 이번 세션의 발생기 1대는 1,400/s까지 유효했고 2,800/s는 maxVUs 부족·발생기 CPU ≥95%로
  무효였다(그 사이는 미측정). 계획서 §4는 발생기 구성을 c6i.xlarge 최대 3대·대당 약 3,333/s(계산값)로 정해 두었다 — 이번 실측의 1대 유효 범위
  (1,400/s까지)로는 3대로 10K req/s가 되는지 알 수 없으므로(추론), 측정 도구 단계에서 1대 상한 → 3대 합산 → 실제 ALB 경로 순으로 다시 확인한다.
- SQS/Lambda 같은 버퍼 계층은 지금 붙이지 않는다. 현재 구조를 경량화해 목표를 실측하고, 그걸로 안 될 때 검토한다.

## 실행 순서 ① 결과 — 진입 분리 측정 (2026-10-06)

판정 규칙·측정식·임계치는 run 전에 고정했다(`artifacts/loadtest/20261005-1440/step2-prereg.md`, 변경 1건 기록 — 아래 한계).
조건: SSE 없음, constant 60초, 발생기 1대, HPA api 3/3·web 2/2 고정, 노드 m6i.large 3대(축소 방지 표시, 할당 가능 1,930m × 3), 이미지 f2ab573,

칸마다 같은 rate 워밍업 1회(제외) 뒤 판정 3회, web·api 경로는 첫 run을 번갈아 뒀다. 판정 run 15회와 워밍업 5회 모두 유효(오류 0, dropped 0, 사후 정합성 검사 통과).

**사전 등록 판정**:

- D2(측정 일관성): D1이 쓰는 r_ns(100/s)에 적용했다 — api 중앙값 P-web 2.088 vs P-api 1.834, 13.8% ≤ 15% → 통과. 사전 등록 문구에는 rate가 명시돼 있지 않다.

  web 비중은 47.0%(100/s)·56.4%(1,000/s)로 30% 이상이다(계산).
- D1(Next 홉 우회, 100/s P-web web 비중 ≥ 30%): **44.1% → §1 (b) Next 홉 우회를 개선 후보로 올린다.** 착수는 경로 규칙·Spring 접두어·
  하네스 k8s 규칙 2·actuator 노출을 함께 정하는 별도 ADR로 한다. web을 거치면 api 비용도 늘어난다(1,000/s 1.078 → 1.483, 원인 미확인).
- D3(연결 칸): P-alb가 P-web 대비 api +1.2%, web −1.4%(±20% 안) → 진단 NLB 결과를 공개 ALB 경로의 대표로 본다.

  api 직접은 0.35 이하였다.

**§1 (a) 갱신**: "순번 두 번"은 실측(ZRANK 2.00/요청)으로 확인됐다. 판매 여부 DB 조회는 대기는 없지만(pending 0) JFR에서 7.6~11.9%를 쓴다.
다만 Redis 쪽 CPU(Lettuce·Netty)는 10% 안팎이라 Redis 왕복을 줄이는 효과는 CPU보다 **지연**(약 5ms 대기) 쪽이 크다(추론).

**필요 코어(계산값, 판정 아님)**: 1,000/s 중앙값을 10,000 req/s에 그대로 적용하면 P-web (1.483 + 1.397) × 10 = 약 28.8코어,
P-api 1.078 × 10 = 약 10.8코어. 지금 앱 노드 할당 가능 합계는 5.79코어다. 요청당 비용이 10,000/s에서도 같은지는 재지 않았다.

**한계**: preflight 1,000/s(20초, 예열 덜 됨)는 p95 1.1s·노드 1.0으로 "포화"였으나 예열 뒤 같은 rate는 포화하지 않았다 — 분류가 예열 상태(그리고 run 길이 20초 vs 60초)에 좌우됐다(추론).
CPU-ms/req는 rate가 낮을수록 크다(api 1.8@100/s vs 1.1@1,000/s) — 시간에 비례하는 비용(승격 tick 등, 100/s에서 요청당 EVALSHA·DB +0.1회)이
적은 요청 수에 나뉘는 효과로 보인다(추론). 사전 등록의 노드 CPU "15초 rate"는 node-exporter 수집 주기(30초)로 잴 수 없어 1초 표본의
15초 이동 평균으로 바꿨다(첫 preflight 뒤, 판정 run 전, 임계치 그대로). 1초 최대로 읽었다면 300/s preflight가 "포화"(0.92~0.99)가 되어
r_s가 300/s였을 것이다 — 그러면 1,000/s 칸(표의 두 행, 필요 코어 계산, D2의 r_s 값, web 비중 범위의 상한)을 재지 않았다.
D1~D3에는 영향이 없다(1초 최대로도 100/s preflight는 0.49·p95 20ms로 비포화라 r_ns=100/s는 같다). 노드 3 vs 5 검산 칸은 노드 포화가 나오지 않아 하지 않았다. 10초 burst에서의 비용은 이 표로 말하지 않는다.

## 검토했으나 채택하지 않은 대안

- **SSE 유지 + 연결 전용 계층으로 10만 연결** — 가능하지만, 대기 상태 전달에 그 비용·복잡도를 들일 이유가 적다. 축 ①은 그대로 남는다.
- **고정 주기 폴링으로 단순 전환** — 대기 내내 수천 req/s가 이어지고(계산값) 상태 조회가 지금처럼 무거우면 CPU를 더 쓴다.
- **노드만 늘려 통과** — 노드 5대에서 진입 오류가 사라졌지만(실측) 지연 편차가 크고 SLO(p95 ≤ 300ms)를 만족한 것은 1회다. 요청당 비용과
  requests를 근거로 정하지 않고 늘리기만 하면, 계획서 §1이 고치려는 "근거 없는 숫자를 다른 근거 없는 숫자로" 바꾸는 일이 된다.
- **Karpenter·Spot 전환** — 지금 Cluster Autoscaler 구조로 사전 확장과 축소를 모두 해 봤다. 필요가 측정될 때 검토한다.

## 한계 / 미확정

- 축 ①의 원인을 노드 CPU로 **분리하지 못했다**(노드 수와 함께 메모리·밀도가 바뀜). 반복은 조건당 2~6회이고 같은 조건에서도 p95 편차가 크다.
- 진입 경로에서 web 홉과 api의 CPU 비율 — 시험 ①의 분리 측정으로 web 비중 43~49%를 쟀다(§실행 순서 ① 결과). 위 근거 표의 비율(`step5diag-2pod-8web_1400aps-r2`)은 노드 포화 중의 값이다.
- 실사용 CPU(파드당 1~2코어)는 cadvisor 추정이다.
- SSE 개설 속도 약 110건/s의 원인은 확인하지 않았다.
- 폴링 부하 수치는 계산값이다. 실측 전에는 표·결과에 실측처럼 쓰지 않는다.
- SLO(핵심 API p95 ≤ 300ms)는 근거가 적혀 있지 않은 기존 규칙이다(계획서 §3.4). 버스트 진입에 같은 기준을 쓸지 다시 정한다.
