# IMP-043 · 예매 묶음의 커넥션 대기 원인(로컬): 동시 도착과 커밋 WAL 동기화

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-21(로컬 실험 `artifacts/loadtest/local-20261021-l7/`, 레포 밖)
- 유형: 진단(로컬 실측, 묶음 43회 + 디스크 프로브 4회). 같은 로컬 환경 안의 비교다.
- 관련: [[IMP-036]](예매 묶음 순간 DB 풀 포화), [[IMP-042]](풀 5 vs 8), [[IMP-041]](같은 측정 도구)
- 벤치 파일: 레포 밖 `local-20261021-l7/`: 사전 등록 `prereg-L7.md`~`prereg-L11.md`·`prereg-probe2.md`, 구성 `compose.yml`, 실행 `run-l7.sh`·`run-l9.sh`·`run-l10.sh`·`run-l11.sh`, PostgreSQL 세션 수집 `pgwatch2.sql`, 디스크 프로브 `probe.sh`·`iosampler.sh`, 요약 `analyze-l7.mjs`·`analyze-l9.mjs`, 결과 `out/`(실행 기록 `out/runs.log`)

## 1. 상황 (Context)
[[IMP-042]]에서 예매 api의 풀을 5에서 8로 늘려도 묶음 시작 순간 Hikari pending이 38~52로 남았고, 묶음 사이 편차가 커서 풀 크기 효과를 판정하지 못했다.
같은 도구로 잰 [[IMP-041]]의 J8에서는 api 지표 응답이 14~26초 걸렸다. 커넥션 대기가 어디서 생기는지, 묶음 사이 편차가 어디서 오는지 DB 쪽 지표를 더해 나눠 봤다.

## 2. 문제 정의 + 분류
- 계층: DB 연결(HikariCP) → PostgreSQL 트랜잭션 → WAL 동기화 → 저장 장치.
- 질문 1: 풀 8에서도 남는 pending은 무엇인가.
- 질문 2: 같은 조건 묶음의 예매 지연이 수 배~수십 배 달라지는 원인은 무엇인가.

## 3. 측정 방법
- 구성: api 1개(코어 2·3, 풀 5, 메모리 2Gi), 대기열 1개(코어 8·9, 풀 3), PostgreSQL 16(코어 6·7), Redis(코어 4), 예매 k6(코어 10·11).
- 묶음: 입장자 100명이 같은 순간 예매(선점·주문·결제)를 시작한다. 기본 역할 구성은 같은 좌석 경합(40명이 4석)·중복 클릭·결제 실패 후 재시도·1인 한도를 포함한다. 묶음마다 새 공연.
- 수집:
  - api: Hikari active·pending(1초 표본), 커넥션 점유 시간·획득 대기(누적 sum/count라 표본 시각과 무관), Redis 명령 완료 시간(Lettuce), CPU.
  - PostgreSQL: `pg_stat_activity` 0.2초 표본(활성, 잠금 대기, idle in transaction, 활성 세션의 대기 이벤트), `pg_stat_wal` 묶음 전후(WAL 동기화 횟수·시간, full page image 수).
  - 디스크: 별도 컨테이너에서 0.2초마다 8KB 쓰기 + fdatasync 지연, Docker VM 안 cgroup별 쓰기 바이트, 호스트에서 8KB 쓰기 + FlushFileBuffers 지연.
- 단계마다 가설과 판정 기준을 측정 전에 등록했고, 비교는 순서를 교차(ABBA)했다.

| 단계 | 질문 | 설계 |
|---|---|---|
| L7 | 행 잠금 대기인가, 트랜잭션 안 DB 외 작업인가 | 기본 구성 3회 + 경합 없는 구성(100명 모두 다른 좌석) 2회 |
| L8 | 점유 시간이 원래 긴가, 동시성·CPU로 늘어나는가 | 입장자 5명 기준선 2회, api 코어 2개 vs 4개 교차 4회 |
| L9 | 체크포인트 직후 묶음이 느린가 | 예매 20초 전 CHECKPOINT vs 없음, 교차 8회 |
| L10 | 점유 시간이 커밋의 WAL 동기화에 묶이는가 | `synchronous_commit` on vs off(진단 전용), 교차 8회 |
| probe2~4 | 디스크 동기화 지연은 어디서 오는가 | 호스트 쓰기 부하 켜고 끄기, VM 안 쓰기량, 호스트 직접 flush |
| L11 | 디스크가 정상인 묶음만으로 풀 5 vs 8 | 풀 재기동 교차 8회, WAL 동기화 1회 평균 5ms 초과 묶음은 무효 후 재측정 |

## 4. 결과 (로컬 실측)

### 4.1 행 잠금 대기는 대기의 원인이 아니었다 (L7·L9·L10)
- L7 5회 모두 예매 구간의 잠금 대기 세션 0(0.2초 표본 85~86개씩). 40명이 4석을 다투는 기본 구성도 같았다.
- 대기 이벤트까지 기록한 L9·L10 16회에서도 잠금 대기 표본은 묶음당 0~4개였다(0.2초 표본 85개 중).
- 경합 없는 구성의 커넥션 획득 대기 평균(363·316ms)이 기본 구성(203·110ms)보다 짧지 않았다.

### 4.2 pending은 같은 순간 도착한 요청 수로 보인다 (추론)
- pending 54·68이 찍힌 묶음 시작 표본에서 Tomcat 바쁜 스레드는 60·74개, Hikari active는 4·5였다(L7 M1·W). 바쁜 스레드 대부분이 커넥션을 기다렸다.
- 100명이 한 순간에 시작하면 풀이 5든 8이든 시작 순간에는 나머지 요청이 기다린다(추론).
- 사전 기준 H3(동시성만으로 생기는 대기: 경합 없는 구성 U의 pending 최대가 기본 구성 M의 절반 초과)는 U 18·1, M 54·28로 충족하지 못했다. 다만 U2는 pending 최대 1인데 획득 대기 평균이 316ms였다. 1초 표본인 pending 최대는 대기 규모를 나타내지 못해, 이번 진단부터는 누적 지표인 획득 대기 평균으로 비교했다.
- L9·L10의 디스크 정상 동기 커밋 묶음 9회에서 묶음 하나의 커넥션 사용은 470~488회, WAL 동기화는 224~254회였다.

### 4.3 커넥션 점유 시간은 WAL 동기화 지연을 따라 움직였다 (L8~L10)
- 경합 없는 기준선(입장자 5명) 2회의 커넥션 1회 점유 평균은 2.8ms와 62.2ms였다. 62.2ms 묶음은 PostgreSQL 트랜잭션 최장 0.41초로 아래 디스크 지연 묶음과 같은 양상이었다(WAL 지표 수집 전이라 추론). L8 사전 기준(점유 증폭: 기준선 점유가 같은 코어 100명 묶음 M2c의 1/3 이하)은 충족하지 못했다. 2.8ms 묶음은 M2c1(8.5ms) 대비로만 1/3 이하이고 M2c2(7.6ms) 대비로는 넘었으며, 62.2ms 묶음은 미충족이다.
- 100명 묶음은 WAL 동기화 1회 평균 5ms 이하인 동기 커밋 묶음 9회(L9·L10)에서 6.0~11.4ms였다.
- L7에서 idle in transaction 3개 이상인 표본이 묶음마다 3~14개 있어 사전 기준 H2(트랜잭션 안 DB 외 작업)를 충족했다. 그 몫은 §6에서 계산했고, 주원인은 아래 WAL 동기화로 판정했다.
- api 코어 2개 → 4개(L8)는 두 쌍이 +58%·−36%로 엇갈려 기준(두 쌍 모두 40% 이상 감소)을 충족하지 못했다. WAL 지표 수집 전 단계라 디스크 상태를 가리지 못했다.
- 체크포인트 가설은 기각했다: 네 쌍 중 한 쌍만 2배 이상이었고, full page image는 묶음당 5~81개였다(L9).
- 동기 커밋 묶음 12회(L9·L10)에서 WAL 동기화 1회 평균과 커넥션 점유 평균의 순위 상관은 0.94였다.

| 묶음 | WAL 동기화 1회 평균 | 커넥션 점유 평균 | 획득 대기 평균 | 선점 p95 |
|---|---|---|---|---|
| L10-S0d | 1.2ms | 6.0ms | 82ms | 369ms |
| L9-N2 | 3.9ms | 11.4ms | 143ms | 700ms |
| L9-N1 | 11.2ms | 25.1ms | 351ms | 2,378ms |
| L9-C1 | 39.3ms | 68.2ms | 1,053ms | 5,903ms |
| L10-S0c | 476ms | 306ms | 5,004ms | 17,547ms |

- 느린 묶음의 활성 세션 대기 이벤트는 `LWLock:WALWrite`·`IO:WALSync`가 대부분이었다(L10-S0c 0.2초 표본에서 각 270·74회, L9-C1 91·32회).
- `synchronous_commit` off(커밋이 WAL 동기화를 기다리지 않음) 교차 4쌍. on 쪽 묶음의 WAL 동기화 1회 평균은 S0a 1.7ms, S0b 1.8ms, S0c 476ms, S0d 1.2ms였다.
  - off 쪽 점유 평균 변화: −16%(S0a·S1a), −42%(S1b·S0b), −94%(S0c·S1c), −18%(S1d·S0d). 획득 대기는 S0c 5,004ms → S1c 243ms.
  - 사전 기준(점유·획득 대기 모두 0.6배 이하)을 충족한 쌍은 S0c·S1c(디스크 느림)와 S1b·S0b(디스크 정상, 0.58·0.57배) 두 쌍이다. 네 쌍 모두는 아니어서 사전 등록 문구대로 "WAL 동기화가 느린 묶음에서만 주원인"으로 판정했다.
  - 디스크 정상 묶음에서도 WAL 동기화는 점유 시간의 일부다(−16~−42%).
- L10-S0c는 선점·주문 p95가 17.5·16.8초로, [[IMP-041]] J8의 10~18초와 같은 규모다(그 묶음은 PostgreSQL 지표가 없어 같은 원인인지는 추론).

### 4.4 디스크 동기화 지연은 호스트 저장 경로의 flush 지연과 함께 나타났다 (probe2~4)
- 프로브는 예매 묶음(L9·L10)이 끝난 뒤 따로 돌렸다. 묶음 중에 호스트 flush를 함께 재지는 않았으므로, 묶음의 WAL 동기화 지연을 아래 flush 지연에 귀속하는 것은 추론이다.
- Docker VM 안 쓰기가 180초 동안 12MB뿐인 창에서도 fdatasync가 200ms를 넘은 초가 45초(표본 52개) 있었다. VM 안 쓰기량과 지연은 겹치지 않았다(probe3).
- 같은 2분 동안 VM 안 fdatasync와 호스트 직접 flush를 함께 쟀다(probe4).

| 프로브 | p50 | p95 | p99 | 최대 |
|---|---|---|---|---|
| VM 안 fdatasync | 2ms | 84ms | 236ms | 652ms |
| 호스트 FlushFileBuffers | 0.8ms | 82ms | 223ms | 477ms |

- 호스트 flush가 200ms를 넘은 5초는 모두 VM 안 fdatasync도 200ms를 넘었다(5/5). 같은 프로브에서 sleep 200ms의 실제 경과는 최대 221ms라 VM 전체가 멈춘 것은 아니다(probe4).
- 호스트 `FlushFileBuffers`는 NTFS를 포함한 호스트 저장 경로 전체를 거치므로, SSD 장치만의 몫으로 분리하지는 않았다.
- 호스트 쓰기 부하를 켜면 fdatasync 중앙값이 휴지 구간 2~17ms에서 21~23ms로 올랐지만, 사전 기준(인접 휴지 구간 둘 다의 5배 이상)은 두 번 모두 충족하지 못했다. 휴지 구간에도 최대 0.8~3.6초의 지연이 있었다(probe2). 호스트 쓰기량만으로 설명되지는 않는다.
- Docker 가상 디스크(`docker_data.vhdx`)가 있는 C: 드라이브는 보급형 SATA SSD 한 개다. flush 지연이 간헐적으로 수백 ms가 되는 것은 이 장치의 특성으로 보인다(추론).

### 4.5 AWS 측정 세션의 RDS 쓰기 지연
- 측정 세션 `20261005-1440`의 CloudWatch `WriteLatency`(1분 평균), run별 내보내기에서 겹친 시각을 뺀 536개: p50 1.69ms, p90 19.3ms, p99 29.0ms, 최대 68.4ms. 24%가 10ms를 넘었다.
- 이 지표는 WAL을 포함한 RDS 디스크 쓰기 전체의 평균이다. 운영에서도 쓰기 지연이 튀는 구간에 예매 묶음이 겹치면 같은 기전으로 대기가 길어질 수 있다(추론, 묶음 단위로 겹침을 재지는 않았다).

### 4.6 디스크 정상 묶음만으로 본 풀 5 vs 8 (L11)
- [[IMP-042]]와 같은 판정 기준(예매 p95 = 선점·주문·결제 p95의 중앙값)으로 다시 쟀다. 풀은 같은 컨테이너 자리에서 재기동으로 바꾸고, 재기동마다 예열 1회를 판정에서 뺐다.
- WAL 동기화 1회 평균이 5ms를 넘은 판정 묶음 3개(J4 41.3ms, J7 6.2ms, J8 21.2ms)는 무효로 두고 같은 자리를 다시 쟀다(재측정 3.6·4.6·1.9ms). 예열 W52(42.8ms)·W82(120ms)도 5ms를 넘었지만 예열은 판정에서 제외한다.

| 쌍 | 풀 5 예매 p95 | 풀 8 예매 p95 | 풀 8 쪽 차이 | 커넥션 점유 평균 5 / 8 | 획득 대기 평균 5 / 8 |
|---|---|---|---|---|---|
| (J1, J2) | 876ms | 1,009ms | +15% | 16.3 / 27.5ms | 206 / 193ms |
| (J4, J3) | 698ms | 707ms | +1% | 13.6 / 20.7ms | 175 / 160ms |
| (J5, J6) | 587ms | 1,055ms | +80% | 11.3 / 25.9ms | 142 / 198ms |
| (J8, J7) | 771ms | 796ms | +3% | 14.2 / 26.0ms | 180 / 170ms |

- **판정: 차이 없음.** 4쌍 중 3쌍이 ±20% 안이고, 풀 8이 20% 이상 낮은 쌍은 없다.
- 풀 8에서는 커넥션 1회 점유가 길어졌다(11.3~16.3ms → 20.7~27.5ms). 풀 크기를 점유 평균으로 나눈 초당 처리 가능 횟수는 풀 5가 307~442회, 풀 8이 291~386회로 겹친다(계산). 커넥션을 늘려도 뒤쪽(CPU 코어 2개, WAL 동기화)이 같아 한 번에 처리되는 양이 늘지 않았다(추론).

## 5. 조치
- **api DB 풀은 5를 유지한다.** [[IMP-042]]의 "판단 불가"를 디스크 지연 묶음을 걸러낸 재측정으로 "차이 없음"으로 판정했다.
- 로컬 측정의 유효 조건에 WAL 동기화 1회 평균을 더한다. 묶음마다 `pg_stat_wal`을 함께 기록하고, 5ms를 넘으면 그 묶음을 무효로 두고 다시 잰다.
- 애플리케이션 코드와 매니페스트는 바꾸지 않는다.

## 6. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대 비교, api 하나가 묶음 전체를 받는 조건(운영은 api 3개에 나뉨).
- `synchronous_commit` off는 진단에만 썼다. 결제·주문 커밋 유실 위험이 있어 운영 설정 후보가 아니다.
- 선점 트랜잭션은 입장 검증(Redis 2회)을 트랜잭션 안에서 하고, 좌석 알림 발행(Redis 1회)은 커밋 뒤 커넥션 반환 전에 한다. 디스크 정상 묶음의 Redis 명령 완료 평균이 0.3~0.6ms라, 선점 커넥션 1회에 1~2ms, 커넥션 사용 전체(사용자당 약 4.7회) 평균에는 0.3ms 안팎이다(계산). 측정 편차보다 작아 이번에는 바꾸지 않았다.
- 다음 개선: AWS 측정 세션에서 `pg_stat_wal`과 RDS `WriteLatency`를 예매 묶음 구간에 맞춰 함께 기록해, 운영 환경의 WAL 동기화 지연이 예매 지연에 얼마나 실리는지 잰다.

## 7. 배운 점 (면접 답변용 한 줄)
"풀이 포화됐다"는 지표에서 시작해 잠금 대기, 체크포인트, WAL 동기화 순으로 가설을 하나씩 세우고 개입 실험으로 확인해 묶음 사이 편차를 WAL 동기화 지연으로 좁혔고, 그 지연이 호스트 저장 경로의 flush 지연과 함께 나타나는 것을 프로브로 확인했다.
