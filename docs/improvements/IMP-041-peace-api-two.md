# IMP-041 · 평시 예매 api 3 → 2(P5) — 노드 절감은 2회 중 1회, 예매 묶음은 판단 불가로 보류

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-20(시뮬레이션 `artifacts/loadtest/kwok-20261020/`, 로컬 실험 `artifacts/loadtest/local-20261020-l5/` — 레포 밖)
- 유형: 시뮬레이션(kwok, 2회) + 정량(로컬 실측, 판정 묶음 8회). **로컬 실험은 같은 로컬 환경 안의 상대 비교**다.
- 관련: [resource-sizing-plan.md](../deployment/resource-sizing-plan.md) §3 P5(평시 2+2), [operating-requirements.md](../deployment/operating-requirements.md) G1, [[IMP-039]](시뮬레이터·평시 동거), [[IMP-040]](세션 비용 분해)
- 벤치 파일: 레포 밖
  - 시뮬레이션: `kwok-20261020/prereg-P5.md`, `sim-cycle.mjs`(`peakApi`·`pdbApi` 추가), `scen-T/P5cyc.json`, `out-T/P5cyc*.json`
  - 로컬: `local-20261020-l5/prereg-L5.md`, `compose.yml`, `booking-split.js`(booking-e2e.js 복사 — 대기열 호출과 예매 호출을 나눔), `run-l5.sh`, `sampler3.mjs`, `summarize-l5.mjs`, `out/`(실행 기록 `out/runs.log`, 첫 시도 무효분 `out/INVALID-attempt1/`)

## 1. 상황 (Context)
`resource-sizing-plan.md`의 P5 후보는 평시 api를 2개(HPA 하한 2, PDB 1)로 두고, 오픈 때 사전 확장으로 3개로 올리는 운영이다.
[[IMP-039]]에서 막혔던 두 문제가 이 후보에는 없다.
- 큰 Pod(1100m)가 노드마다 하나라 api와 대기열이 한 노드에 함께 놓이지 않는다.
- 사전 확장은 롤링 없이 Pod를 하나 더할 뿐이고, 오픈 때 api 3 + 대기열 6 = 9대로 지금과 같다.

예상 절감은 평시 노드 5 → 4대(큰 Pod 4개가 노드 하나씩, 계산)이고, 대가는 평시 예매를 api 2개가 받는 것이다.

## 2. 문제 정의 + 분류
- 질문 1(시뮬레이션): 평시 노드가 실제로 4대가 되는가, 사전 확장·되돌림·CA 축소 한 바퀴 뒤에도 그런가.
- 질문 2(로컬): 입장자 100명 예매 묶음을 api 2개가 받으면 3개일 때보다 얼마나 느린가.
  - 정원 100은 어느 때든 동시에 예매하는 사람 수의 상한이라 평시 최악값으로 썼다.
  - 2개면 api당 50명, 전체 DB 연결 10개(풀 5 × 2)다.

## 3. 측정 방법
### 3.1 시뮬레이션
- 도구: [[IMP-039]]의 `sim-cycle.mjs`에 두 가지를 더했다.
  - `peakApi`: 사전 확장 때 api Pod를 더하고, 되돌릴 때 지운다.
  - `pdbApi`: api PDB의 minAvailable(P5 정의대로 1).
- 한 바퀴: 평시(api 2 + 대기열 2) → 사전 확장(api 2 → 3과 대기열 2 → 6을 한 번에) → 되돌림 → CA 축소 흉내.
- 판정(사전 등록 16:25):
  - (a) 사전 확장 뒤 노드 ≤ 9, Pending 0, 동거 0, 노드당 대기열 ≤ 1.
  - (b) 평시(처음)와 축소 뒤 평시 노드가 V0(5대)보다 적다(예측 4).
- 2회차 첫 실행은 kwok의 etcd 요청 시간 초과로 중단됐다. 로컬 스택 기동과 겹친 탓으로 본다. 무효로 보관하고 다시 돌렸다(`out-T/INVALID-P5cyc-r2-etcd-timeout.err`).

### 3.2 로컬 L5
- 구성:
  - 같은 이미지 api 3개(코어 2·3 / 12·13 / 14·15, 메모리 2Gi, 풀 5).
  - 대기열 1개(8·9, 풀 3): 진입과 상태 조회만 받는다.
  - 예매 k6(10·11)가 VU마다 api 하나를 고정 배정한다(VU 번호 % 개수 — 연결 단위 분산 흉내).
- api 개수 전환: 컨테이너는 그대로 두고 k6의 api 목록만 바꿨다. 쉬는 api는 자기 코어에서 대기한다.
- 순서: [[IMP-039]] L4에서 같은 조건끼리 변동이 70~80%였으므로, 짧은 묶음을 번갈아 돌리는 ABBA로 정했다.
  - 예열 2회 뒤 판정 묶음 8회: 3, 2, 2, 3, 3, 2, 2, 3.
  - 쌍은 (1,2)(3,4)(5,6)(7,8)이고, 묶음마다 새 공연과 다른 사용자 100명을 썼다.
- 판정(사전 등록 16:28), 지표는 예매 p95(선점·주문·결제 세 단계 p95의 중앙값)다.
  - **악화 있음**: 4쌍 중 3쌍 이상에서 2개 쪽이 30% 이상 나쁘다.
  - **차이 작음**: 3쌍 이상에서 2개 쪽 악화가 30% 미만이고, 중앙값 차이도 30% 미만이다.
  - **판단 불가**: 그 밖의 경우.
- 첫 시도는 무효다. 시작 여유(+30초)가 모자라 k6 setup이 진입 시각을 넘기면서 10회 중 5회가 실행되지 않았고, 쌍이 성립하지 않았다.
  - 시작 여유를 +45초로 고친 것을 사전 등록에 적은 뒤, 같은 순서와 판정식으로 새 공연·사용자를 써서 다시 돌렸다.
  - 첫 시도의 유효 run 수치는 판정에 쓰지 않았다.

## 4. 결과
### 4.1 시뮬레이션 (2회)

| run | 평시(처음) | 사전 확장 뒤 | Pending / 동거 / 노드당 대기열 | 축소 뒤 평시 |
|---|---|---|---|---|
| 1회차 | **5** | 9 | 0 / 0 / 1 | **5** |
| 2회차 | 4 | 9 | 0 / 0 / 1 | 4 |

- (a)는 두 번 모두 충족했다. 사전 확장이 Pod 추가뿐이라 롤링 정체가 없다.
- (b)는 2회차만 충족했다(사전 등록 판정으로 1회차는 미충족).
  - 1회차에서는 시스템 Pod 일부와 web 1개가 모인 노드(사용률 0.51)에 큰 Pod가 들어가지 못해 5번째 노드가 생겼다.
  - 축소 흉내에서도 그 노드는 CA 축소 기준(사용률 0.5 미만)을 넘어 남았다.
  - 시스템 Pod(데몬셋 제외 22개)의 CPU 요청은 합계 1,000m다(스냅샷 계산).
- 즉 P5의 절감 1대는 web과 시스템 Pod가 어느 노드에 모이느냐에 걸린다. 큰 Pod 수만으로 계산한 "4대"는 하한이다.

- 쌍별 비교(2개 쪽이 3개 쪽보다): J1–J2 +142%, J4–J3 +157%, J5–J6 +22%, J8–J7 −93%.

- **J8은 세 단계 p95가 10~18초**로 다른 묶음과 자릿수가 다르다. 첫 시도(무효)의 J3도 약 10초였다.
  - 두 경우 모두 PostgreSQL 주기 체크포인트 구간과 겹쳤다(J8: 예매 시작 07:58:46Z, 체크포인트 07:58:57~07:59:42Z / 첫 시도 J3: 07:39:08Z, 07:38:57~07:39:35Z — `out/postgres.log`).
  - 그러나 체크포인트가 쓴 양은 작았고(288·160버퍼), 체크포인트와 겹친 J4는 느려지지 않았다. 원인은 확인하지 못했다(추론).
- 사후 참고(판정 아님): J8을 빼면 남은 3쌍 모두 2개 쪽이 느렸다(+142%, +157%, +22%). 2개면 예매 묶음이 느려지는 쪽을 가리키지만, 사전 등록 판정으로 확정한 것은 아니다.

## 5. 조치
- **P5는 채택을 보류한다.** 설정은 바꾸지 않는다.
  - 노드 절감은 2회 중 1회만 나왔다(시뮬레이션).
  - 예매 묶음 영향은 판단 불가였고, 사후 참고로는 느려지는 쪽이었다(로컬).
  - 절감액 자체가 작다. 평시 노드 1대는 $0.121/h로 측정 세션 비용의 약 6%다([[IMP-040]]).
- P5를 다시 볼 조건은 세 가지다.
  - web과 시스템 Pod 배치를 고정하는 장치(예: 시스템 Pod 노드 지정)로 4대를 안정적으로 만들 수 있을 때.
  - 로컬 환경의 간헐적 정지(체크포인트와 겹친 지연)를 없앤 설계로 예매 묶음을 다시 잴 때.
  - 노드 1대 장애 때 api 1개만 남는 상황(G1)을 검증할 수 있을 때.
- 채택하려면 사전 확장 파일이 대기열 HPA와 함께 api HPA 하한도 올려야 한다. 지금 `event-prescale.yaml`은 대기열 HPA 하나를 겨누고, 하네스 k8s 규칙 11은 그 하한·기한을 검사한다. 대상이 둘일 때 규칙이 그대로 동작하는지는 확인하지 않았다.

## 6. 트레이드오프 / 한계
- 시뮬레이션은 [[IMP-037]]·[[IMP-039]]의 한계를 그대로 갖는다(배치 가능성만, CA 근사). 2회뿐이다.
- 로컬 실험의 한계:
  - VU 고정 배정은 실제 경로(ALB → web → api Service)의 분산과 다르다.
  - 평시 동시 예매 규모는 모르므로 정원 100을 상한으로 썼다.
  - DB 연결 수(10 vs 15)와 api 수의 효과를 가르지 않았다.
  - 노드 1대 장애 때 api 1개만 남는 상황은 재지 않았다.
- ABBA로 묶음을 늘렸어도 한 번의 정지(J8)가 판정을 흔들었다. 로컬 Docker 환경의 간헐적 지연이 이 크기의 비교에서는 가장 큰 잡음이다.

## 7. 배운 점 (면접 답변용 한 줄)
"평시 api 2개면 노드 4대"라는 계산을 실제 스케줄러로 돌려 보니 web과 시스템 Pod 배치에 따라 5대가 남는 경우가 있었다. 예매 묶음 비교는 ABBA로 설계했지만 환경 정지 한 번에 판정이 흔들렸다. 그래서 판정 기준을 사후에 바꾸지 않고 "판단 불가·보류"로 기록했다.
