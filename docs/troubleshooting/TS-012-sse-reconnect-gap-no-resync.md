# TS-012 · SSE 구독 공백의 이벤트를 영영 놓침 — 복구 주석은 있고 복구 코드는 없음

- 슬라이스: S04/S05 (좌석·주문 화면) — 발견 경로는 S09(배포)
- 날짜: 2026-08-05
- 유형: 클라이언트 상태 최신성 결함(FE) — **서버 정합성 문제가 아니다**(§5 참조)
- 상태: 해결
- 관련: [[ADR-008]](Kafka 백본 — SSE는 보조, DB가 진실원),
  [`docs/deployment/zero-downtime-deployment.md`](../deployment/zero-downtime-deployment.md)

## 1. 증상

**사용자 신고로 발견한 것이 아니다.** S09 배포 준비 중 "매니페스트를 갖추면 무중단 롤링이
가능한가"를 따지다가, 롤링 배포 시 **Pod 교체로 SSE 연결이 반드시 끊긴다**는 사실에서 출발했다.

그렇다면 끊긴 뒤 화면이 어떻게 복구되는지 확인해야 했다. 코드에는 복구된다고 적혀 있었다.

```ts
// apps/web/src/features/order/hooks/useOrder.ts (수정 전)
es.onerror = () => {
  /* 폴링/재조회로 커버 */
};
```

**그런데 이 훅에는 폴링이 없다.** 주석이 사실이 아니었다.

## 2. 재현

배포와 무관하게 재현된다 — 네트워크가 잠깐 끊기면 된다.

```
1. 주문 상세 화면을 연다 (useOrder → SSE 연결)
2. 네트워크를 3~5초 끊는다 (또는 API Pod를 재시작한다)
3. 그 사이 결제를 완료시킨다 → 서버는 order.paid 를 발행
4. 네트워크 복구 → 브라우저 EventSource가 자동 재연결
5. 화면은 여전히 "결제 대기" 상태
```

**5번에서 멈춘 채 영영 갱신되지 않는다.** `order.paid`는 **종료 상태 이벤트**라 다시 오지 않기
때문이다. 사용자는 결제가 끝났는데 화면상으로는 미결제로 보인다.

## 3. 조사

세 SSE 훅의 재연결 대응을 전부 확인했다.

| 훅 | SSE | 재연결 시 상태 복구 | 근거 |
|---|---|---|---|
| `useQueue` | ✓ | ✅ **2초 폴링**이 따로 돈다 | `setInterval(... getQueueStatus, 2000)` |
| `useSeats` | ✓ | ❌ 없음 | `onerror` 빈 함수, `onopen` 핸들러 없음 |
| `useOrder` | ✓ | ❌ 없음 | 동일 |

`useQueue`만 폴링을 갖고 있었고, **그 사실이 다른 두 훅의 주석에 잘못 옮겨져 있었다.**
"폴링/재조회로 커버"라는 문구가 실제로는 아무것도 가리키지 않는 상태였다.

## 4. 근본 원인

**SSE의 이벤트는 재전송되지 않는데, 구독이 성립한 뒤 상태를 다시 읽는 코드가 없었다.**

```
Pod 종료 / 네트워크 단절
  → EventSource 끊김
  → (브라우저가 약 3초 뒤 자동 재연결 — 여기까지는 정상 동작)
  → 그 공백 동안 발생한 이벤트는 사라짐
  → onopen에서 아무것도 하지 않음
  → 화면이 낡은 상태로 고정
```

조사 단계에서는 이 경로(재연결)만 보였다. **초안을 리뷰받고 나서야 같은 성질의 공백이
마운트 시점에도 있다는 것을 알았다** — 자세한 내용은 §5.

설계 자체는 옳았다 — 이 프로젝트는 **SSE를 트리거로만 쓰고 진실원은 서버**로 두었다(ADR-008).
실제로 모든 이벤트 핸들러가 `refresh()`를 호출해 서버에서 다시 읽는다. **그 원칙을 "연결이
끊겼다 붙는 경우"에는 적용하지 않은 것**이 원인이다. 즉 설계 결함이 아니라 **적용 누락**이다.

`onerror`에 복구를 넣지 않은 판단은 옳았다(EventSource는 스스로 재연결하므로 `onerror`에서
할 일이 없다). 다만 **복구를 넣어야 할 자리가 `onopen`이라는 점을 놓쳤다.**

## 5. 해결

**구독이 성립한 시점마다** 현재 상태를 다시 읽어 공백을 메운다.

```ts
es.onopen = () => refresh();  // 최초 연결·재연결을 구분하지 않는다
es.onerror = () => {};        // EventSource가 스스로 재연결한다 — 여기서 할 일은 없다
```

### 구독 공백은 두 군데다 (초안에서 한쪽을 놓쳤다)

처음에는 `opened` 플래그로 **최초 `onopen`을 건너뛰었다.** "마운트 시 `refresh()`가 이미
처리했으니 중복"이라는 이유였는데, 리뷰에서 **그 사이에도 공백이 있다**는 지적을 받았다.

```
① refresh() 응답 ~ 구독 성립 사이   ← 초안이 놓친 구간
② 연결 끊김 ~ 자동 재연결 사이       ← 초안이 막은 구간
```

`refresh()`와 `new EventSource()`는 **완료 순서가 보장되지 않는다.** 상태를 응답받은 직후
구독이 맺어지기 전에 이벤트가 발행되면 그대로 사라지고, 최초 `onopen`을 건너뛰면 복구되지 않는다.

특히 **주문 상세 화면은 PG 리다이렉트 직후 마운트**되는데, 그 시점이 결제 승인 확정 시점과
겹친다. 이론적 창이 아니라 **실제로 부딪히기 쉬운 창**이다.

`opened` 플래그는 GET 한 번을 아끼려는 최적화였고, **그 대가로 정확성 구멍을 만들었다.**
제거하고 모든 `onopen`에서 재조회한다. 마운트 시 GET이 한 번 중복되지만 그 대가가 훨씬 싸다.

> 마운트 시 `refresh()`는 **없앨 수 없다.** SSE가 아예 열리지 않는 환경(차단·미지원)에서
> 화면이 영영 비기 때문이다. 즉 두 호출의 역할이 다르다 —
> **마운트 refresh = 폴백 / onopen refresh = 구독 성립 후의 권위 있는 조회.**

- `useOrder`·`useSeats`에 적용.
- `useQueue`는 **넣지 않았다.** 2초 폴링이 이미 공백을 메우고 있어 중복이다.
  대신 "왜 여기만 다른가"를 주석으로 남겨 다음 사람이 누락으로 오해하지 않게 했다.

### 그리고 겹친 재조회의 응답 역전 (리뷰에서 추가로 드러남)

`onopen` 재조회를 넣자 **마운트 조회(A)와 구독 성립 조회(B)가 동시에 뜨는** 구간이 생겼다.
리뷰에서 "응답 순서가 뒤집히면?"이라는 지적을 받고 확인하니 실제로 뚫린다.

```
t0  A 발신 (마운트)
t1  구독 성립 → B 발신
t2  주문 PAID 전이
t3  B 응답(PAID) 도착 → 화면 PAID
t4  A 응답(PENDING) 도착 → 화면이 다시 PENDING   ← 낡은 값이 최신을 덮음
```

**A가 먼저 나갔다고 먼저 도착하지 않는다.** A는 첫 요청이라 커넥션을 새로 맺느라 느릴 수 있고,
B는 그때 이미 데워진 커넥션을 쓴다. 그리고 `order.paid`는 종료 이벤트라 다시 오지 않으므로
결과는 앞의 결함과 **동일한 영구 고착**이다.

**이건 이번 수정으로 생긴 결함이 아니다.** `refresh()`는 원래 겹칠 수 있는 자리가 여럿이었다 —
좌석 이벤트 3종이 연달아 올 때, 그리고 `refresh`가 반환값으로 노출되어 화면에서 직접 부를 때.
`onopen` 추가가 그 잠재 결함을 **더 자주 만나게 했을 뿐**이다.

해결은 순번 가드다. 마지막에 시작한 요청의 응답만 반영한다.

```ts
const latest = useRef(0);

const refresh = useCallback(async () => {
  const seq = ++latest.current;
  try {
    const next = await api.get(...);
    if (seq !== latest.current) return;   // 낡은 응답은 버린다
    setState(next);
    setError(false);                      // 일시 실패 후 성공하면 에러를 푼다
  } catch {
    if (seq !== latest.current) return;
    setError(true);
  } finally {
    if (seq === latest.current) setLoading(false);
  }
}, [...]);
```

### useQueue는 순번만으로 부족했다 (리뷰 3차)

`useQueue`에 같은 순번 가드를 넣었는데, **그것만으로는 못 막는다는 지적을 받고 확인하니 맞았다.**
순번은 **폴링끼리만** 비교하고 **SSE 이벤트는 순번을 올리지 않기** 때문이다.

```
t0  폴링 요청 발신 (seq=1)
t1  SSE queue.admitted 도착 → phase = admitted   ← 순번은 그대로 1
t2  t0의 응답 WAITING 도착 → seq(1) === latest(1) → apply
    → phase가 waiting으로 되돌아감
```

`admitted`·`expired`는 **되돌아가지 않는 종료 상태**이므로, 순번이 아니라 **종료 여부**로
막아야 한다. `settle()`을 두어 종료 시 (a) `terminal` 플래그로 진행 중인 응답을 무효화하고
(b) `clearInterval`로 이후 폴링도 멈춘다 — 종료 뒤에는 폴링할 이유가 없다.

```ts
let terminal = false;
const settle = (next: "admitted" | "expired") => {
  terminal = true;
  if (poll) { clearInterval(poll); poll = null; }
  if (!cancelled) setPhase(next);
};
```

`apply`가 폴링 응답에서 종료 상태를 발견한 경우에도 같은 경로를 타게 해, SSE로 알든
폴링으로 알든 동작이 같다.

**`catch`에도 같은 검사를 넣었다.** 다만 이쪽은 **재현 가능성이 낮다** — 만료는 단조롭기
때문에 먼저 발신한 요청이 `QUEUE_EXPIRED`를 받았다면 나중 요청이 `WAITING`을 받을 수 없다.
실제 버그라기보다 **성공·실패 경로에 같은 규칙을 두어 다음 수정자가 한쪽만 보고 오해하지
않게 하는** 목적이다.

> 세 훅이 **같은 결함 종류**라 하나도 빼놓지 않았다 — "왜 여기만 다른가"가 이번 사건 원인의
> 절반이었기 때문이다. 다만 `useQueue`는 상태 기계(종료 상태)가 있어 **필요한 가드가 하나 더**
> 있었다는 점이 다르다.

### 심각도가 두 훅에서 다르다
- `useOrder`: 종료 상태 이벤트를 놓치면 **영구히 복구되지 않는다**(후속 이벤트가 없다) → 심각.
- `useSeats`: 좌석맵이 낡아 이미 팔린 자리를 선택 가능한 것처럼 보여준다. 다만 **다음 이벤트가
  오면 `refresh()`가 돌아 자가 치유**되고, **초과판매로도 이어지지 않는다** — 서버의 조건부
  UPDATE가 막고 사용자는 409로 튕긴다(ADR-003).

### ⚠️ 이 사건은 "정합성 결함"이 아니다
이 프로젝트에서 **정합성**은 초과판매 방지·주문 상태 전이 원자성 같은 **서버 측 불변식**을
가리키는 말이다(ADR-003/006, TS-007·008·011). 이번 건은 **DB 상태가 틀어진 적이 없고**
화면이 낡았을 뿐이다. 같은 단어를 쓰면 진짜 정합성 사건과 섞여 심각도를 오독하게 되므로,
**클라이언트 상태 최신성 결함**으로 분류한다.

## 6. 재발 방지

- **주석이 가리키는 대상이 실제로 존재하는지 확인한다.** 이번 원인의 절반은 "폴링이 커버한다"는
  문구를 다른 훅에서 복사해 온 것이었다. 문서·주석의 거짓이 코드의 거짓보다 오래 산다.
- **하네스가 강제한다.** `new EventSource(`가 있으면 `onopen` 재조회 또는 폴링 중 **하나는 필수**로
  검사한다(`harness/frontend/check.mjs` 규칙 7, meta fixture `fe-sse-no-resync`).
  이 사건의 원인이 "규칙이 주석에만 있었던 것"이라, 규칙을 **주석에서 CI로 옮겼다.**
  의도적 예외는 `// harness:allow-sse-no-resync: <사유>`로 근거를 남긴다.
- **롤링 배포 실측 시 확인 항목으로 넣었다** — 배포 중 SSE 재연결 시간과 상태 복구 여부를
  측정한다([zero-downtime-deployment.md](../deployment/zero-downtime-deployment.md)).

## 7. 한계 (정직)

- **하네스는 "복구 경로의 부재"만 잡는다.** 경로가 있어도 그것이 **올바르게 동작하는지**는
  정적으로 알 수 없다 — 이번에 리뷰로 드러난 세 겹(최초 구독 공백·응답 역전·종료 상태 역전)은
  전부 정적 검사 밖이다. `apps/web`에는 단위 테스트 프레임워크가 없고, Playwright E2E로
  "연결을 끊었다 붙이는" 상황을 재현하는 것은 비용이 크다. 실제 확인은 S09 롤링 실측에서 한다.
- **재연결 자체는 브라우저에 맡긴다.** `EventSource`의 자동 재연결 주기·횟수를 제어하지 않는다.
  서버가 204를 주거나 Content-Type이 어긋나면 재연결이 멈추는데, 그 경우는 다루지 않았다.
- **인증 쿠키가 재연결 요청에 실려 가는지는 별도 확인이 필요하다.** 쿠키 기반이라 정상 동작할
  것으로 보지만 실측하지 않았다.
