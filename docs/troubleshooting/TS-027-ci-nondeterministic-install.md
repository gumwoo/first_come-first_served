# TS-027 · 결정론을 내세우면서 의존성 설치는 비결정적이었다

- 슬라이스: 전반(CI) — 발견은 2026-08-13 리뷰
- 날짜: 2026-08-13
- 유형: 프로세스 결함 — **검증의 토대**
- 관련: [[TS-025]](같은 계열 — 규칙이 자기 사각지대를 못 봤다)
- 상태: **해결** — fallback 6곳 제거. 제거 시점에 lockfile 3개 모두 정상임을 확인했다

## 0. 무엇이 문제였나

CI의 의존성 설치가 전부 이 형태였다.

```yaml
run: npm ci || npm install
run: pnpm install --frozen-lockfile || pnpm install
```

`npm ci`와 `--frozen-lockfile`은 **lockfile이 `package.json`과 어긋나면 실패하는 것이 목적**이다.
그 실패를 `||`가 받아 **lockfile을 무시한 설치로 넘어간다.** 즉 이 두 줄은 서로를 상쇄한다.

이 저장소는 하네스·메타테스트·계약 검증을 앞세워 **"검증은 결정적이어야 한다"**를 계속 주장해
왔다. 그런데 **가장 아래 토대인 의존성 설치가 비결정적**이었다.

## 1. 왜 나쁜가 — 초록불의 의미가 사라진다

lockfile이 깨진 채 fallback이 동작하면:

- CI는 **로컬과 다른 의존성 트리**로 빌드·테스트한다
- 그런데 **결과는 초록불**이다
- 따라서 그 초록불은 "이 커밋이 정상"이 아니라 **"어떤 트리에선가 정상"**을 뜻한다

하네스가 코드↔계약을 아무리 정확히 잡아도 **무엇을 대상으로 검사했는지가 흔들리면** 그 판정의
근거가 남지 않는다. 그리고 이 실패는 **조용하다** — 로그를 뒤지지 않으면 fallback이 발동했는지
알 수 없고, 아무도 그걸 뒤지지 않는다.

## 2. 제거 시점의 실제 상태 — 아무것도 덮고 있지 않았다

고치기 전에 셋 다 직접 확인했다. **fallback을 떼면 CI가 빨개질 가능성**을 먼저 봐야 했기 때문이다.

```
harness   npm ci --dry-run                → up to date
e2e       npm ci --dry-run                → up to date
apps/web  pnpm install --frozen-lockfile  → Done in 2.2s
```

**세 lockfile 모두 정상이었다.** 즉 이 fallback은 당시 아무것도 숨기고 있지 않았고,
**앞으로 깨질 때만 조용히 덮었을 자리**다. 지금 제거해도 잃는 것이 없다는 뜻이고,
동시에 **지금까지 운이 좋았을 뿐**이라는 뜻이기도 하다.

⚠️ 이 확인은 **제거 시점의 스냅샷**이다. 과거 어느 커밋에서 fallback이 실제로 발동했는지는
확인하지 않았다 — 로그를 소급 조회하지 않았다.

## 3. 조치

`|| npm install` 4곳, `|| pnpm install --frozen-lockfile`의 fallback 2곳, 총 **6곳 제거**.

| 잡 | 설치 |
|---|---|
| `harness-meta` | `npm ci` |
| `backend` | `npm ci` |
| `frontend` | `npm ci` · `pnpm install --frozen-lockfile` |
| `e2e` | `pnpm install --frozen-lockfile` · `npm ci` |

이제 lockfile이 어긋나면 **CI가 그 자리에서 실패한다.** 그것이 원래 의도된 동작이다.

## 4. 부수적으로 드러난 것 — 규칙 ⑮가 워크플로를 안 본다

`ci.yml` 주석에 이 문서 번호(`TS-027`)를 적었는데 **하네스가 아무 말도 하지 않았다.**
규칙 ⑮(끊어진 문서 참조)는 스캔 대상이 `javaFiles`와 `migrationFiles`뿐이다.

```js
for (const file of [...javaFiles, ...migrationFiles]) {
```

즉 **워크플로·매니페스트·문서에 적은 `TS-###`는 검사되지 않는다.** [[TS-026]] 때는 자바 파일에
적어서 규칙이 정확히 잡아줬는데, 같은 실수를 yml에 하면 통과한다.

**이번에는 문서를 실제로 썼으므로 끊어진 참조가 아니다.** 다만 규칙의 사각지대는 사실이라
기록해 둔다 — [[TS-025]]에서 본 것과 같은 형태다(규칙은 있는데 보는 범위가 좁다).
당장 넓히지는 않았다. 스캔 대상을 늘리면 오탐 검토가 따라오고, 그 판단은 [[TS-025]] §3에서
세 번 좁혀야 했던 경험대로 별도로 다뤄야 한다.

## 5. 배운 점

**안전장치에 fallback을 달면 안전장치가 아니다.** `npm ci`의 존재 이유는 "실패하는 것"인데
`||`가 그 실패를 흡수하면 남는 것은 `npm install`뿐이다. 이름만 엄격하고 동작은 느슨한 상태가
되고, 그 사실이 명령 한 줄 안에 숨는다.

> 검사 도구를 도입할 때는 **그 도구가 실패했을 때 무슨 일이 일어나는지**를 함께 정해야 한다.
> "일단 통과시키고 나중에 보자"는 기본값은, 나중이 오지 않는다.

[[TS-025]]와 묶으면 형태가 같다 — 거기서는 규칙이 **한쪽 방향만** 봤고, 여기서는 규칙이
**실패해도 넘어가게** 돼 있었다. 둘 다 "검사가 있다"는 사실이 "검사가 작동한다"를 가려 준 경우다.
