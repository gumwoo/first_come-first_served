# ADR-014 · 모듈러 모놀리스와 계층 경계 — DDD 전술 패턴은 선택적으로만

- 상태: **Accepted (사후 정리)** — 아래 §0 참조
- 날짜: 2026-08-07
- 슬라이스: 횡단(아키텍처)
- 관련: [[ADR-003]](재고 원자성), [[ADR-006]](주문 상태 전이), [[ADR-005]](결제 포트-어댑터),
  [[ADR-010]](아웃박스), [[TS-013]](집계 불변식), `contracts/layer-rules.yaml`

## 0. 이 문서의 성격 (정직)

**결정 시점에 작성된 문서가 아니다.** 코드와 기존 ADR·TS에서 **역으로 정리한 사후 문서**다.
그래서 "언제 무엇을 보고 이렇게 정했는가"의 시간 순서는 재구성하지 않았다 — 기억에 의존해
쓰면 그 부분만 검증되지 않는 서술이 된다.

대신 **코드에서 확인되는 구조**와, **저장소에 이미 근거가 남아 있는 결정**만 적는다.
판단이 바뀐 이력이 문서로 남아 있는 경우(ADR-008 → ADR-010, TS-013)는 그대로 인용한다.

이 문서가 필요한 이유: `contracts/layer-rules.yaml`이라는 **강제 규칙은 이미 있는데 근거 문서가
없었다.** 규칙만 있고 왜인지가 없으면 언젠가 "이거 왜 있지?" 하고 풀리게 된다.

## 1. 맥락

이 서비스의 논지는 **선착순 상황의 동시성·정합성**이다. 기능 개수나 도메인 복잡도가 아니라,
같은 좌석을 동시에 노리는 요청에서 **초과판매·중복결제·유령 알림이 나지 않는가**가 전부다.

그래서 아키텍처 선택의 기준도 하나로 좁혀진다.

> **불변식을 어디에 두고, 누가 그것을 강제하는가.**

나머지(모듈 경계·계층·패턴 채택 여부)는 이 질문의 답에서 파생된다.

## 2. 결정

### 2-1. 배포 단위 — 모듈러 모놀리스

Spring Boot 앱 하나. 기능별 패키지로 경계를 긋되 **같은 프로세스**에서 돈다.

```
auth/  seat/  order/  queue/  event/  admin/  alert/  dlq/  outbox/  global/
   └ controller · service · repository · domain · dto
```

확장은 서비스 분리가 아니라 **Pod replica + Kafka 파티션 병렬**로 얻는다.
HPA도 API 티어에만 건다 — 컨슈머 작업이 가벼워 랙이 CPU를 따라가지 않으므로
"컨슈머 랙 오토스케일"은 이 프로젝트에서 억지다.

**"모듈러"가 붙는 이유**: 모놀리스가 무너지는 것은 크기 때문이 아니라 **경계가 없어서**다.
경계 없이 커지면 나중에 어디를 잘라야 할지 알 수 없다. 경계가 있으면 필요할 때 그 선을 따라
자르면 된다.

### 2-2. 코드 구조 — 계층형, 그리고 **CI가 강제**

```
controller → service → repository → domain
```

계층을 나눈 것 자체는 특별하지 않다. **차별점은 그것이 지켜지는 수단**이다.
`contracts/layer-rules.yaml`을 하네스가 import 정적 검사로 강제하고, 위반하면 CI가 실패한다.

| 규칙 | 안 지키면 실제로 |
|---|---|
| `controller ↛ repository` | 컨트롤러가 SQL을 짜기 시작한다 |
| `controller ↛ domain` | 엔티티를 그대로 응답 → **DB 컬럼 추가가 API 스펙 변경**이 된다 |
| `domain ↛ service·controller` | 순환 참조 → 도메인 테스트에 스프링 컨텍스트 전체가 필요해진다 |
| `@Transactional`은 service만 | 컨트롤러에 붙으면 **응답 직렬화까지 트랜잭션 안**에 들어가 커넥션을 잡는다 |
| 필드 주입 금지 | 생성자 주입이면 의존이 많아질 때 **파라미터 개수로 보인다** |

**규칙마다 `reason`을 함께 둔 것도 결정의 일부다.** 근거 없는 규칙은 결국 풀린다.

### 2-3. 도메인 모델 — 상태 전이는 엔티티에, **불변식은 DB에**

두 층을 나눈다.

**(a) 상태 전이는 엔티티 메서드로만**

```java
SeatHold.release()   SeatHold.expire()   Payment.approve(pgTid)   Payment.fail()
private SeatHold(...)   // 생성자 private, 빌더로만
// @Setter · @Data 없음
```

아무 데서나 `setStatus()`를 부를 수 있으면 **어디서 상태가 바뀌었는지 추적이 불가능**해진다.
메서드로 모으면 진입점이 유한해지고 잘못된 전이를 그 안에서 막을 수 있다.

**(b) 동시성 불변식은 DB 조건부 UPDATE로** ([[ADR-003]]·[[ADR-006]])

```sql
UPDATE seats SET status='HELD' WHERE id IN (...) AND status='AVAILABLE'
-- 영향 행 수 != 요청 수 → 예외로 롤백
```

**이것이 이 문서에서 가장 중요한 선택이다.** 도메인 객체가 아무리 잘 만들어져 있어도
**애플리케이션 메모리의 불변식은 프로세스가 하나일 때만 유효하다.**

```
Pod A: 좌석 조회 → AVAILABLE → 저장
Pod B: 좌석 조회 → AVAILABLE → 저장     → 이중 판매
```

읽고→검사하고→쓰는 사이의 틈은 도메인 모델로 막을 수 없다. 데이터가 있는 곳에서 원자적으로
판정해야 한다.

### 2-4. 가장자리 두 곳만 다른 패턴

- **포트-어댑터는 결제 하나에만** ([[ADR-005]]) — 전면 헥사고날은 인터페이스만 배로 늘고
  실제로 갈아끼울 일은 없다. 예외는 **테스트할 수 없고, 통제할 수 없고, 실패가 돈과 직결되는**
  외부 시스템이다. PG가 정확히 그것이고, 덕분에 실패·타임아웃·미아 승인 보상을 테스트로 검증한다.
- **이벤트 발행은 아웃박스** ([[ADR-010]]) — DB 커밋과 메시지 발행은 원자적이지 않다.

## 3. 채택하지 않은 것 (그리고 이유)

| 안 한 것 | 이유 |
|---|---|
| **마이크로서비스** | 마이크로서비스는 **조직 문제를 푸는 도구**다. 팀이 여럿이고 배포 주기가 달라 서로를 기다리는 비용이 클 때 그 비용을 없앤다. 1인 프로젝트에는 그 문제가 없고, 대가(로컬 트랜잭션 소멸·분산 추적·서비스 수만큼의 인프라)만 남는다. 게다가 **좌석·주문·결제는 하나의 트랜잭션 불변식을 공유**한다 — 분리하면 조건부 UPDATE 한 번이 Saga가 되고 이중 판매 위험이 오히려 는다. |
| **Aggregate · Value Object · Domain Event** | 핵심 불변식이 DB에 있어 **Aggregate 경계로 지킬 대상이 아니다.** 도메인 복잡도도 이 패턴들의 비용을 낼 만큼은 아니다. |
| **Repository 추상화(도메인 인터페이스 ↔ 인프라 구현 분리)** | JPA를 걷어낼 계획이 없다. 인터페이스만 늘고 이득이 0이다. |
| **CQRS · 이벤트 소싱** | 읽기와 쓰기 부하를 나눠야 할 규모가 아니다. |
| **Redis 분산락** | 리스 만료와 트랜잭션 수명이 따로 놀아 **만료 후 소유자가 둘이 될 수 있다.** 조건부 UPDATE가 데이터와 같은 시스템에서 판정하므로 더 안전하고 싸다. |

> **"DDD를 적용했다"고 쓰지 않는다.** rich domain model 하나로 DDD가 되지 않고,
> 그렇게 주장하면 Aggregate 경계·Bounded Context·Ubiquitous Language에 답할 것이 없다.
> **무엇을 가져오고 무엇을 안 가져왔는지, 왜인지**가 정확한 서술이다.

## 4. 이 선택의 한계 — 실제로 뚫린 곳

**조건부 UPDATE는 만능이 아니다.** [[TS-013]]에서 확인했다.

> 조건부 UPDATE는 **단일 행에 표현되는 불변식**만 지킨다.
> **1인 구매 한도는 집계 규칙**이라 원자화할 대상 행이 없다 → 두 요청이 각자 통과했다.

원인은 "읽고→검사하고→행위"가 다시 나타난 것이고, 대상 행이 없어 조건부 UPDATE로 접을 수 없었다.
그래서 **그 경로만** `pg_advisory_xact_lock`으로 (사용자, 공연) 단위 직렬화했다.
좌석 총량을 늘리는 진입점이 `SeatService.hold()` 하나라 거기만 잠그면 충분하다.

같은 패턴을 전수 점검해 **주문 생성에서도 같은 결함을 찾았다**([[TS-014]]) — 부분 UNIQUE 인덱스로
최종 방어선을 DB에 뒀다.

## 5. 판단이 바뀐 이력

사후 문서지만, **문서로 남아 있는 변경**은 그대로 인용한다.

- **AFTER_COMMIT 발행 → 아웃박스**: [[ADR-008]]이 AFTER_COMMIT이었고 [[ADR-010]]이 대체했다.
  코드 주석에 이력이 남아 있다 — *"구 AFTER_COMMIT 발행은 커밋 후 크래시/브로커 다운 시
  이벤트가 영구 유실됐다."* IMP-011에서 도달 0/10 → 유실 0으로 실증했다.
- **SSE 발송을 커밋 후로**: 트랜잭션 안에서 broadcast하던 6곳을 레지스트리(팬아웃 입구)에서
  일괄로 커밋 후로 미뤘다. 롤백된 상태를 알리면 그 알림으로 재조회한 화면이 오히려 옛 상태를 본다.

## 6. 결과 / 한계 (정직)

- **아키텍처를 한 곳에서 설명할 문서가 생겼다.** 그전에는 ADR 13개를 훑어 조합해야 했다.
- **`layer-rules.yaml`의 근거가 문서화됐다.** 규칙을 풀려는 사람이 이유를 먼저 읽게 된다.
- ⚠️ **시간 순서는 재구성하지 않았다**(§0). "이 판단을 언제 왜 했는가"의 일부는 이 문서에 없다.
- ⚠️ **모듈 경계는 패키지 수준이다.** 컴파일 단위로 분리(Gradle 멀티모듈)하지 않았으므로
  경계 위반을 막는 것은 하네스의 정적 검사뿐이다. 하네스를 끄면 경계도 사라진다.
- ⚠️ **"나중에 쪼갤 수 있다"는 주장은 검증되지 않았다.** 실제로 쪼개 본 적이 없다.
