## 0. 목표 (Goal)

> **티켓 오픈 시 10초 이내 최대 100,000명의 사용자가 진입하는 burst workload를 대상으로,
> 대기열을 통해 downstream을 보호하면서 안정적으로 서비스할 수 있는 시스템을 구축하고 그 한계를 실측한다.**

**이 문장은 목표이지 주장이 아니다.** README·포트폴리오에서 "100,000명 규모 트래픽을 부하 테스트로
검증했다"고 쓸 수 있는 조건은 §8에 따로 둔다. 그 조건을 채우기 전에는 이 숫자를 결과처럼 쓰지 않는다.

이 문서는 단순 절차서가 아니다. 이 문서가 정한 측정 결과로 **requests·limits·HPA min/max·노드 용량을
다시 산정**한다. 지금의 인프라 수치는 그 근거가 없기 때문이다(§1).

## 1. 왜 다시 재는가

지금의 용량 수치는 **성능에서 나온 값이 아니다.** 레포가 스스로 그렇게 적고 있다.

| 근거 | 내용 |
|---|---|
| `k8s/base/api-hpa.yaml` | `maxReplicas: 7` — "노드 예산에 들어가는 최대값이다(**성능상 충분하다는 판단은 아니다**)" |
| `k8s/base/web-hpa.yaml` | api·web 최대 + 롤링 겹침 = 5,550m / 5,790m, 여유 240m |
| 노드 그룹(`variables.tf`, `loadtest.tfvars`) | 기본 AZ당 1~2대(총 3~6대, `t3.large`), 측정 프로파일 AZ당 최대 3대(총 9대, `m6i.large`). "노드 3대"가 아니다 |
| [[TS-034]] | 2026-08-11의 knee 600~650 rps는 이후 변경(IMP-018·캐시 실험)으로 **무효**. 재측정은 **미해결** |

즉 문제는 "600 rps밖에 안 나온다"가 아니라 **현재 시스템의 capacity knee를 모른다**는 것이다.
그 상태에서 replica 수를 바꾸면 근거 없는 숫자를 다른 근거 없는 숫자로 바꾸는 것에 불과하다.

## 2. Workload 정의

**"10만 사용자 테스트"라는 표현은 쓰지 않는다.** 같은 10만 명이어도 시간 축에 따라 전혀 다른 부하다.

**진입 부하의 단위는 queue-entry arrivals/s다** — 초당 시작되는 대기열 진입(토큰 발급 iteration) 수.
HTTP rps와 같은 값이 아니다. 한 iteration이 진입 외에 상태 조회·SSE 연결 등을 함께 하면 시스템 전체의
HTTP rps는 이보다 커진다. 둘은 따로 기록한다(§2.3).

| 정의 | 목표 queue-entry arrival rate(계산값) |
|---|---|
| 100,000명 / 100초 | 1,000 /s |
| **100,000명 / 10초** ← 이 문서의 목표 | **10,000 /s** |
| 100,000명 / 1초 | 100,000 /s |

모든 시험은 **(사용자 수, 진입 시간, 도착 분포, 동시 대기 연결 수)** 네 값으로 표기한다.

**도착 분포는 시험에서 통제하는 변수다.** 같은 100,000명/10초라도 일정한 속도로 진입시키는 것과 티켓 오픈
직후 첫 수 초에 집중시키는 것은 서로 다른 workload다. `constant-arrival-rate`는 설정한 arrival rate로
iteration 시작을 일정하게 분산시키는 기준 시험에 쓰고, **실제 발생한 arrival rate와 peak 1초 arrival rate는
별도로 측정한다.** 설정값은 목표이지 측정값이 아니다 — 스케줄링, VU 부족(`dropped_iterations`), 집계 구간에
따라 실측은 달라진다. 티켓 오픈 순간의 집중 부하는 별도 시나리오로 검증한다.

| 분포 | 목적 | 정의 |
|---|---|---|
| **Constant** | 순수 capacity 비교 — 단계 간·개선 전후 비교의 기준 | `constant-arrival-rate`, 목표 10,000 arrivals/s × 10초 |
| **Front-loaded** | 티켓 오픈 직후 집중 특성 | 총 100K / 10초, 초반 집중. `ramping-arrival-rate` stage로 정의(예: 초당 25K → 20K → 15K → …, 합계 100K) |

**Front-loaded 분포는 실제 티켓 오픈 트래픽 데이터에서 나온 것이 아니다.** "현실적인 분포"라고 주장하지 않고
**프로젝트가 정의한 stress workload**라고 쓴다. 구체 stage는 스크립트를 쓸 때 확정해 결과와 함께 남긴다.

### 2.1 사용자 행동 모델과 시험의 경계

```
진입 POST /events/{id}/queue/token
  │
  ├─ SSE 구독 (대기 중 순번·입장 알림)
  │     └─ SSE 실패 시 폴링 (현재 2초 → 성공 구독 시 15초까지 백오프, ADR-015)
  │
  ▼  Admission Control (동시 정원 queue.capacity = 100)
 ─────────────────────────────────────────────  ← 여기까지가 100K 부하의 대상
  ADMITTED ≤ capacity
  │
  ▼
좌석 조회 → 선점(hold) → 주문 → 결제            ← 정원 이하로만 내려온다
```

("정원 이하"를 어떻게 판정하는지와 실시간 지표가 보지 못하는 창은 §3.3에 있다.)

**10만 명이 이 전체 경로를 끝까지 수행하는 시험이 아니다.** 이 시스템의 설계가 애초에 대기열로
downstream을 보호하는 것이므로, 100K 부하가 닿는 곳은 진입·대기·SSE·입장 제어 계층이다.
그래서 시험을 둘로 나눈다.

| 시험 | 대상 | 묻는 것 |
|---|---|---|
| **대기열 진입 시험** | 진입 → WAITING + SSE → 입장 제어 | 10만 명의 진입을 대기열 계층이 수용하는가, downstream으로 정원 이상이 새지 않는가 |
| **E2E 입장자 시험**(별도) | ADMITTED 이후 좌석 → 선점 → 주문 → 결제 | 입장한 사용자의 처리량·지연·정합성 |

**두 축을 섞지 않는다.** 시험의 경계(대기열 진입 / E2E 입장자)와 도착 분포(Constant / Front-loaded)는
서로 다른 축이다. Constant·Front-loaded는 대기열 진입 시험 안의 두 변형이다. "burst"는 §0 목표 문장의
일반 표현으로만 쓰고 시험 이름으로 쓰지 않는다.

대기열 진입 시험에서도 입장한 사용자는 downstream으로 내려보낸다. 그래야 "downstream 부하가 정원에
묶이는가"(§8 Protection)를 실제 흐름으로 확인할 수 있다. 다만 그 경로의 처리량·정합성 판정은 E2E 시험에서 한다.

**full journey를 10만 명 끝까지 돌릴 수 없는 이유**(코드 확인 + 계산값):

- 승격은 **빈 슬롯(`capacity - admitted`)만큼만** 일어난다(`QueueAdmissionService`).
- 슬롯이 비는 경로는 **명시적 `leave` 호출과 입장 TTL(300초) 만료뿐**이다. 좌석 선점·주문·결제는 슬롯을
  반환하지 않는다. SSE 연결이 끊겨도 emitter만 지워지고 대기 토큰은 남는다(`QueueSseRegistry`).
- 따라서 10만 명이 모두 입장하려면 최악의 경우 100,000 / 100 × 300초 ≈ **83시간**(계산값), 세션이 60초에
  끝난다고 가정해도 **약 17시간**(계산값)이 걸린다.

> 결제를 마친 사용자도 TTL까지 슬롯을 쥐고 있는 점은 **정원 활용률 문제일 수 있다**(추론, 미측정).
> 이 문서의 범위 밖이며, E2E 입장자 시험에서 드러나면 별도로 다룬다.

### 2.2 단계

진입 시간은 10초로 고정하고 사용자 수만 키운다. 단계 사다리는 **Constant 분포**로 진행한다 — 단계마다
같은 형태의 부하여야 결과를 비교할 수 있다. 계산값과 실측값을 **열로 분리**한다 — 실측 칸은 시험 후 채운다.

| 단계 | 사용자 | 목표 arrival rate(계산값, /s) | peak 1초 arrival rate(실측) | 최대 WAITING(계산값) | 최대 WAITING(실측) | 최대 SSE 연결(실측) |
|---|---|---|---|---|---|---|
| S-10K | 10,000 | 1,000 | — | 약 9,900 | — | — |
| S-30K | 30,000 | 3,000 | — | 약 29,900 | — | — |
| S-100K | 100,000 | 10,000 | — | 약 99,900 | — | — |

"최대 WAITING(계산값)"은 사용자 수에서 ADMITTED 정원(100)을 뺀 값이다. §2.1대로 슬롯은 `leave`나
300초 TTL로만 돌아오므로, 10초 진입 구간 동안에는 첫 100명이 입장한 뒤 추가 승격이 거의 없다고 본 계산이다.
발생기가 `leave`를 호출하지 않는 한 이 가정은 코드상 성립하지만, 실측으로 확인하는 것이 §8 Queue 축이다.

S-30K와 S-100K 사이의 중간 단계와 실패 시 구간 축소 규칙은 §6 "단계 7의 증분·구간 축소 규칙"에 둔다.

### 2.3 결과에 기록할 부하 지표

"10K"라고 쓸 때 그것이 **걸어 준 arrival rate**인지, **실제 시작된 진입**인지, **처리된 진입**인지,
**HTTP rps**인지 구분할 수 있어야 한다.

| 지표 | 뜻 | 출처 |
|---|---|---|
| offered arrivals | 발생기가 시작하려 한 진입 iteration 수 | k6 설정(rate × 시간) |
| achieved arrivals | 실제 시작된 진입 iteration 수 | k6 `iterations` |
| `dropped_iterations` | 시작하지 못한 진입 | k6 — arrival-rate executor에만 있다. 0이 아니면 §3.1 무효 |
| 평균 arrival rate | achieved arrivals / 진입 시간 | k6 |
| **peak 1초 arrival rate** | 1초 창에서의 최대 진입 시작 수 | **k6 원시 출력만** — 아래 참고 |
| 처리된 진입 | 토큰 발급이 성공(200)한 수 | k6 check · `http_server_requests`(진입 URI) |
| HTTP 요청 수 · HTTP rps | 진입 외 요청을 포함한 전체 | k6 `http_reqs` · `http_server_requests` |

**1초 단위 peak는 서버 쪽 지표로 잴 수 없다.** Prometheus 수집 주기가 15초(`servicemonitor-api.yaml`)이고,
ALB CloudWatch 지표는 1분 단위다. 서버 쪽 지표는 15초·1분 해상도의 처리량 확인에만 쓰고, 1초 peak는
k6의 요청별 타임스탬프 출력(JSON/CSV)에서 집계한다.

### 2.4 발생기 쪽 전제 — 지금 스크립트로는 안 된다

**① 기존 스파이크 스크립트는 arrival rate를 통제하지 못한다.** `infra/k6/spike-queue.js`는
`per-vu-iterations`로 VU 하나를 사용자 하나에 묶는다(`exec.vu.idInTest`로 사용자 매핑). VU를 한꺼번에 띄우는
closed model이라 도착률을 정할 수 없고 `dropped_iterations`도 나오지 않는다. Constant·Front-loaded 시험에는
arrival-rate executor로 새 스크립트를 쓴다. 이때 VU는 iteration 사이에 재사용되므로, 1인 1토큰을 지키려면
사용자 매핑을 **iteration 번호(`exec.scenario.iterationInTest`) 기준**으로 바꾼다.

사용자 인증 토큰도 사용자 수만큼 미리 있어야 한다. 지금의 `seed-issue-tokens.js`는 **120개 고정**(`N=120`)이고
로그인으로 받으므로, 10만 계정 시드와 발급 방식을 따로 준비해야 한다. 액세스 토큰 유효기간(`access-token-ttl`
1,800초) 안에 시험이 끝나도록 발급 시점도 맞춘다.

**② 진입 iteration에 SSE를 넣지 않는다.** 레포의 k6 스크립트는 어느 것도 SSE를 쓰지 않고, k6 코어에는 SSE
클라이언트가 없어 확장(xk6-sse 등)이 필요하다(외부 지식, 이 문서 작성 시 미확인). 또 iteration이 SSE를 붙든 채
대기하면 VU가 대기 시간 내내 묶여, 필요한 VU 수가 동시 대기 수(S-100K 약 99,900, 계산값)에 육박한다 —
발생기가 측정 대상보다 먼저 무너질 가능성이 크다(추론). 그래서 진입 iteration은 토큰 발급까지로 끝내고,
**SSE 동시 연결 부하는 진입으로 발급된 대기 토큰을 넘겨받아 같은 시험 창에서 별도 발생기로 만든다.**
§6 단계 4를 API와 SSE로 나눈 것과 같은 이유다. 실제로 어느 쪽이 한계인지는 단계 2에서 확인한다.

### 2.5 폴링 폭증 시나리오(별도)

SSE가 실패해 대기자가 폴링으로 넘어가면 부하 형태가 바뀐다. 9,900명이 2초 주기면 상태 조회 API에
**약 4,950 HTTP rps**, 99,900명이면 **약 49,950 HTTP rps**(둘 다 계산값)가 걸린다. 대기열 진입 시험과 다른 시험으로 둔다.

## 3. 판정 조건 — 세 갈래로 나눈다

**한 목록에 섞지 않는다.** 섞으면 "발생기가 죽어서 멈춘 것"과 "시스템이 한계에 닿은 것"이 같은
결과로 기록된다. [[TS-034]]가 정확히 그 상태로 끝났다.

### 3.1 시험 무효 — Test Invalid → 결과 폐기, 환경 수정 후 재시험

| 조건 | 왜 무효인가 |
|---|---|
| 발생기 CPU·메모리 포화 | 발생기가 목표 부하를 못 만든다 |
| k6 `dropped_iterations` > 0 | open model(arrival-rate executor, §2.4)에서 VU 부족 = 의도한 도착률이 안 나왔다 |
| 발생기 네트워크 포화 | 위와 같다 |
| 발생기와 측정 대상의 자원 경합 | 측정 대상의 CPU를 발생기가 쓴다([[TS-034]]: k6가 같은 노드에서 최대 0.59 core) |
| ALB → web → api가 아닌 경로 | api Service 직접 호출은 ALB·web을 우회한다([[TS-034]] ①) |

### 3.2 시스템 한계 — **판정**과 **진단**을 분리한다

**판정 조건**은 "어디까지 처리 가능한가"를 정하고, **진단 신호**는 "왜 거기서 무너졌는가"를 가리킨다.
진단 신호를 판정에 넣으면 일시적 스파이크 하나로 "한계를 찾았다"가 된다.

**판정 (Knee)** — 둘 다 만족할 때 knee 후보로 본다.

- 목표 arrival rate를 올렸는데 처리된 진입(§2.3)이 따라오지 않는다
  (예: 6,000 → 8,000 → 10,000 arrivals/s를 걸었는데 처리된 진입이 5,900 → 7,600 → 7,700/s)
- 같은 구간에서 SLO가 악화된다(§3.4)

**진단 신호** — knee가 잡힌 뒤 원인을 특정하는 데 쓴다.

| 신호 | 가리키는 병목 |
|---|---|
| 노드 CPU 포화 · Pod CPU / request 비율 | 연산 |
| `hikaricp_connections_pending` 증가 | DB 커넥션([[TS-021]]) |
| Redis 명령 지연 · `used_memory` | Redis |
| 열린 FD 수 · 톰캣 커넥션 수 | 연결 자원(SSE) |
| GC 일시정지 · 힙 사용량 | JVM 메모리 |
| ALB 5xx · TargetResponseTime | 진입 계층 |

> **CPU throttling은 판정에도 진단에도 쓰지 않는다.** 현재 api·web 컨테이너는 `limits.cpu`가 없어
> 해당 컨테이너의 limit 기반 CFS throttling이 일어나지 않는다. 의도된 설정이다(`api-deployment.yaml`:
> "limit을 걸면 스로틀링으로 p99가 튀고, 부하 실증에서 측정하려는 것이 바로 그 지연이다").
> 노드나 다른 계층의 throttling 가능성까지 부정하는 것은 아니다.

### 3.3 정합성 실패 — Correctness Defect → 성능 문제가 아니다

**실시간 판정과 사후 판정을 나눈다.** 모든 정합성을 지표로 만들 필요는 없다. 운영에도 쓸 만한 것은
지표로, 순서·횟수처럼 정확히 세야 하는 것은 시험 종료 후 SQL·로그로 검증한다.

| 조건 | 판정 방식 | 근거 |
|---|---|---|
| over-admit (정원 초과 입장) | **실시간** — 등록된 입장 토큰 수(`admitExp` 원소 수) > `queue.capacity` | §5.1 지표 |
| 입장 카운터 어긋남 | **실시간** — `admitcount` ≠ `admitExp` 원소 수. **두 값은 한 Lua 스크립트로 같은 시점에 읽는다** | §5.1 지표 · [TS-024](../troubleshooting/TS-024-queue-admit-visibility-gap.md)(슬롯 누수) |
| 좌석 초과판매 | **실시간** — PAID 주문 둘 이상에 걸린 좌석 수 > 0(주기 질의) | §5.1 지표 · [ADR-003](../decisions/ADR-003-inventory-atomicity.md) |
| 실효 입장 초과 | **사후** — 토큰마다 유효 구간을 재구성하고, 어느 시점이든 구간이 겹치는 **토큰 수**(합이 아니라 토큰 단위 합집합)가 정원을 넘는지 본다. 시작 = 승격 시각, 끝 = admit 키 만료·이탈·토큰 메타 만료(발급 + `token-ttl`) 중 가장 이른 것 | 아래 "한계". 폴백은 토큰 메타의 `eventId`가 있어야 통과하므로 메타 만료 뒤는 세지 않는다 |
| 일시적 이중 판매 | **사후** — 같은 좌석에 결제된(`orders.paid_at` 있음) 주문이 둘 이상이면, 앞 주문의 환불 완료(`refunds.created_at`) 전에 뒤 주문이 결제됐는지 | 주기 질의 사이에 생겼다 사라지는 경우. 두 시각은 출처가 다르다(`paid_at`은 DB 시계, `refunds.created_at`은 앱 시계) — 비교할 때 시계 차이를 감안한다. 앞 주문이 CANCELLED인데 refund 행이 없으면(PG 결과 불명, [ADR-021](../decisions/ADR-021-refund-tx-boundary.md)) 위반이 아니라 **판정 보류**로 기록한다 |
| 결제·좌석 상태 불일치 | **사후** — PAID 주문의 좌석이 SOLD가 아니거나, SOLD 좌석에 PAID·CANCELLED 주문이 모두 없는 경우(CANCELLED + SOLD는 환불 진행 중의 정상 상태다, ADR-021) | 역방향 불일치는 재판매 전까지 실시간 식에 안 걸린다 |
| 대기열 순서 위반 | **사후** — 진입 순번 vs 승격 순서 대조 | 실시간 감지 어려움 |
| 주문·결제·환불 멱등 위반 | **사후** — 주문당 결제/환불 행 수 | IMP-008·TS-030 |
| 이벤트 유실 | **사후** — 아웃박스 PUBLISHED 수 vs 소비 기록 | ADR-010 |

실시간 조건에 걸리면 **즉시 중단**한다. 사후 조건에 걸리면 그 단계의 결과를 **정합성 실패**로 기록한다.

**판정식은 "막는 장치가 유지하는 값"으로 세우지 않는다.** 같은 값으로 재면 장치가 깨져도 판정식은 계속 참이다.

- `admitcount`는 승격 Lua가 `free > 0`일 때만 올리는 카운터라 **구조상 정원을 넘지 않는다.** 그래서
  over-admit은 입장 토큰이 등록되는 별도 구조(`admitExp` ZSet)의 원소 수로 보고, 두 값의 어긋남을 따로 본다.
- `seats.status`는 좌석 행마다 하나뿐이라 "SOLD 수 ≤ 총 좌석 수"는 **항상 참**이다. 초과판매는 한 좌석이
  둘 이상의 결제 완료 주문에 팔린 상태이므로, `order_items`를 PAID 주문 기준으로 좌석별로 세어 판정한다.
- **두 값을 따로 읽지 않는다.** 승격·회수·이탈 스크립트는 각각 카운터와 집합을 원자적으로 함께 바꾸지만,
  관측이 둘을 따로 읽으면 그 사이에 다른 파드의 승격이 끼어 순간적으로 어긋나 보이고, 그대로 오탐 중단이 된다.
- **정원을 측정 중에 바꾸지 않는다.** 정원은 파드마다 넘기는 설정값이라, 롤링 중에 바꾸면 비교 기준이 파드마다 달라진다.

**한계 — 실시간 식이 잡지 못하는 것.**

- `admitExp`도 카운터를 바꾸는 세 스크립트(승격·회수·이탈)가 카운터와 함께 바꾸므로 **완전히 독립된 값은 아니다.** 또 카운터 ≤ 정원이 구조상
  참이라, over-admit이 성립하면 어긋남도 반드시 함께 성립한다. 실시간 식이 실제로 잡는 것은
  "카운터와 집합이 갈라지는 결함"까지다.
- 입장 게이트(`QueueService.isAdmitted`)는 `admitExp`뿐 아니라 **admit 키도 받아들인다.** 회수 스크립트는 admit 키를
  지우지 않고, admit 키의 TTL은 승격 처리 뒤에 시작돼 `admitExp`의 만료보다 늦게 끝난다. 그래서 회수 직후 짧은 창에서는
  빈 슬롯이 다른 사용자에게 승격된 상태로 이전 사용자의 admit 키가 살아 있어, **실효 입장자가 정원을 넘을 수 있다**
  (코드 판독 추론, 미측정). 이 창은 `admitExp` 원소 수에 보이지 않으므로 사후 검증("실효 입장 초과")으로 본다.
  [TS-024](../troubleshooting/TS-024-queue-admit-visibility-gap.md)는 "admit 키 TTL과 `admitExp` score는 같은 시점에 지난다"고
  적었지만, 코드상 admit 키 TTL은 승격 스크립트 뒤에 시작하고 `admitExp` 만료 시각은 스크립트 전에 초 단위로 내림해 계산한다.
- **현재 코드로는 단계 6의 "실효 입장 초과 0"을 통과하지 못할 수 있다**(추론, 미측정). 정원이 찬 부하에서는 회수 직후 같은
  틱에서 빈 슬롯이 재승격되므로 이 창이 자주 생긴다. 그렇다면 측정 전에 시스템을 고쳐야 한다(예: 회수할 때 admit 키도 지운다).
  이것은 판정 기준을 바꾸는 것이 아니라 시스템을 고치는 것이다.

### 3.4 SLO — 출처를 구분한다

| 출처 | 값 | 상태 |
|---|---|---|
| **도메인 설정** | 승격 주기 1.5초(`admit-interval-ms`) | 근거 있음 — 제품이 정한 값 |
| **도메인 설정** | 입장 유효기간 300초(`admit-ttl`) | 근거 있음 — 단, **사용자가 그 안에 좌석 선점을 시작해야 한다는 제품 제약**이다. "300초 안에 화면 도달" 같은 시스템 지연 SLO가 자동으로 나오지는 않는다 |
| **기존 규칙** | 핵심 API p95 ≤ 300ms, 에러율 ≤ 0.5% | [`performance-rules.md`](../rules/performance-rules.md) §1. **근거가 적혀 있지 않다** — baseline(§6 단계 4) 뒤에 유지 근거를 남기거나 수정한다 |
| **미정** | SSE 연결 성공률·유지율, 알림 전달 지연 | baseline 측정 후 확정 |

새 숫자를 근거 없이 박지 않는다. 그게 이 문서가 고치려는 문제와 같은 종류다.

## 5. 관측 가능성 확보 — 측정 전에 붙일 계측

**계측이 없으면 §3의 중단 조건은 발동하지 못한다.** 지금 애플리케이션이 내보내는 커스텀 지표는
아웃박스·DLQ 관련뿐이고 **대기열 지표가 하나도 없다.**

### 5.1 추가할 것

| 지표 | 용도 | 비고 |
|---|---|---|
| 대기 수(WAITING) | 대기열 규모 · 보호막 검증 | Redis `ZCARD` |
| 입장 수(ADMITTED) | **over-admit 실시간 판정** | `queue:admitexp:{eventId}` ZSet 원소 수(`ZCARD`) — 등록된 입장 토큰 수. 입장 게이트의 admit 키 폴백은 포함하지 않는다(§3.3 한계) |
| 입장 카운터 · 정원 | 카운터 어긋남 판정 · 비교 기준 | `queue:admitcount:{eventId}` 값, `queue.capacity`. 대기 수·입장 수·카운터는 **한 Lua로 같은 시점에** 읽는다 |
| 승격·회수·이탈 기록 | 실효 입장 초과 사후 재구성 | 토큰별 시각 로그. 승격 시각은 admit 키를 쓴 시각으로 남긴다(키 TTL이 그때 시작한다). 시험 전체 승격 수는 입장한 사용자 수만큼이고, 시간당 양은 정원과 입장 TTL로 묶인다(추론) |
| 입장 게이트 폴백 통과 수 | 실효 입장 초과의 직접 신호(사후 판정 보조) | **이미 회수돼 `admitExp`에 점수가 없는** 토큰이 admit 키로 통과한 횟수. 만료됐지만 아직 회수 전인 토큰(점수가 있고 현재 이하)의 폴백은 세지 않는다 — 그 토큰은 카운터와 `admitExp`에 남아 슬롯을 쥔 상태라 정원 초과가 아니다. 0보다 크면 §3.3의 창이 실제로 쓰였다는 뜻이다 |
| 승격 지연 | 1.5초 주기를 지키는가 | 승격 워커 1회 소요 시간 |
| SSE 활성 연결 수 | SSE capacity | 레지스트리 크기 |
| SSE 전송 실패 수 | 연결 유지율 · 폴링 전환 원인 | |
| 톰캣 커넥션·스레드 | SSE의 연결 자원 진단 | **`server.tomcat.mbeanregistry.enabled=true` 필요** — 현재 꺼져 있어 `tomcat_*` 지표가 안 나온다 |
| 초과판매 좌석 수 | **초과판매 실시간 판정** | PAID 주문이 둘 이상 걸린 좌석 수. 주기 질의 게이지(§3.3) |

## 6. 단계

순서를 바꾸지 않는다. 앞 단계가 뒤 단계의 해석 근거다.

| # | 단계 | 무엇을 얻나 | 완료 기준 |
|---|---|---|---|
| 1 | Workload 정의 | §2 확정 | 이 문서 머지 |
| 2 | 측정 환경 검증 | §4의 통제가 실제로 지켜지는지 | 소규모 부하에서 §3.1 무효 조건 0건 |
| 3 | 관측 가능성 확보 | §5.1 계측 | 지표가 Prometheus·대시보드에 노출 |
| 4 | **단일 Pod baseline — API와 SSE를 따로** | Pod 1개의 진입 처리 한계(arrivals/s), Pod 1개의 SSE 연결 한계 | 각각 knee와 최초 병목 |
| 5 | scale-out 효율 — 1 → 2 → 4 → … | 처리량이 Pod 수에 얼마나 선형으로 느는가, 깨지는 지점의 공유 병목 | 효율 곡선 + 병목 자원 |
| 6 | **downstream 보호 검증** | 대기자가 늘어도 좌석·주문·결제로 정원 이상이 내려가지 않는가 | S-10K에서 over-admit 0(실시간) **그리고** 실효 입장 초과 0(사후, §3.3) |
| 7 | S-10K → … → S-100K (대기열 진입 시험, 아래 증분 규칙) | 진입 부하 · 동시 SSE · HPA/CA 반응 | 단계마다 §3 판정 기록, 실패 시 구간 축소 |
| 8 | 최초 병목 개선 | 원인 제거 | 변경 사항 + 근거 |
| 9 | **동일 조건 재시험** | 개선 효과 | 같은 workload로 before/after |
| 10 | right-sizing | Pod capacity 측정값으로 requests·HPA min/max·노드 수를 재산정하되, 아래 제약을 함께 검증 | HPA 주석의 근거를 측정값으로 교체 |

### 단계 4를 둘로 나누는 이유

API 요청 처리와 장시간 유지되는 SSE 연결은 **병목 자원이 다를 수 있다.** API는 CPU·DB 커넥션 쪽이고,
SSE는 소켓·FD·메모리·Redis 팬아웃 쪽이다. 섞어서 재면 어느 쪽이 먼저 깨졌는지 분리할 수 없다.

SSE capacity는 **설정값으로 추정하지 않는다.** 톰캣 기본 `maxConnections`(8,192)는 받아들이기를 멈추는
지점이지 감당할 수 있다는 보증이 아니다. 그 전에 메모리·FD·GC·팬아웃 중 하나가 먼저 걸릴 수 있으므로,
1,000 → 2,000 → 4,000 → 8,000 연결로 올리며 **성공률·유지율·메모리·FD·GC·팬아웃 지연**을 잰다.

### 단계 6을 앞에 두는 이유

대기열이 downstream을 막지 못하면 그건 용량 문제가 아니라 **설계 실패**다. 그 상태로 10만을 넣으면
좌석 DB가 먼저 무너지고, 무엇이 한계였는지 알 수 없다. 1만에서도 검증되는 성질이므로 가장 작은 규모에서
먼저 확인한다.

**E2E 입장자 시험**(§2.1)은 단계 6 이후 별도로 수행한다. 입장한 사용자의 좌석·주문·결제 처리량과
정합성을 보는 시험이라 사용자 수가 아니라 정원·세션 길이가 변수이고, 단계 7의 사다리와 섞지 않는다.

### 단계 7의 증분·구간 축소 규칙

목적은 "100K 도전"만이 아니라 **capacity knee를 찾는 것**이다. 고정 세 단계로는 30K PASS, 100K FAIL일 때
한계가 30K~100K 어디인지 알 수 없다.

- **기본 사다리**: 10K → 30K → 50K → 75K → 100K. 사다리는 **Constant**로 진행한다.
- **Front-loaded**: 같은 규모의 Constant가 PASS한 뒤에 추가로 건다. 그래야 두 결과의 차이가 분포 차이만 남는다.
- **건너뛰기**: 직전 단계가 PASS이고 SLO 여유가 정해 둔 기준 이상일 때만 다음 칸을 건너뛴다.
  기준은 baseline(단계 4) 뒤에 숫자로 확정한다. 기준 없이 "여유로워 보여서" 건너뛰지 않는다.
- **FAIL 시 구간 축소**: 다음 숫자로 가지 않고, 직전 PASS와 FAIL 사이를 반으로 나눠 다시 잰다.
  예: 30K PASS · 50K FAIL → 40K → (PASS면) 45K / (FAIL면) 35K → …
- **멈추는 폭**: 구간이 정해 둔 해상도(예: 5K, 비용과 함께 확정) 이하가 되면 멈추고 그 구간을 knee로 기록한다.

구간 축소가 의미를 가지려면 세 조건이 필요하다.

| 조건 | 이유 |
|---|---|
| **회차마다 초기 상태 리셋** — replica 수·노드 수·Redis 대기열 키(카운터 `admitcount`와 집합 `admitexp`는 **함께** 지운다 — 한쪽만 지우면 시작하자마자 카운터 어긋남으로 중단된다)·좌석/주문 데이터·워밍업 | HPA·CA가 이미 늘어난 상태로 다음 회차에 들어가면 같은 부하가 아니다 |
| **경계 판정은 반복 측정** — 같은 규모에서 최소 2회(잠정) 같은 결과일 때만 구간을 좁힌다 | 측정 잡음 한 번에 이분 탐색이 엉뚱한 구간으로 수렴한다 |
| **knee 탐색의 주 무대는 단계 4·5** | 단일 Pod·scale-out 시험이 싸다. 단계 7은 전체 클러스터에서 그 결과가 맞는지 확인하는 자리로, 회차마다 분산 발생기 비용이 든다(§9) |

### 확장의 역할 — 사전 확장과 반응형 확장

**10초 진입 구간은 HPA/CA가 흡수하지 못한다.** HPA는 지표 수집 → 판단 → Pod 생성 → 기동·readiness를
거쳐야 하고, 노드가 모자라면 CA가 EC2를 붙이는 시간이 더해진다. 이 레포의 CA 실측은 **3 → 4 노드 110초**다
([[IMP-021]]). 그래서 역할을 나눈다.

| 구간 | 담당 | 시험에서 확인할 것 |
|---|---|---|
| **티켓 오픈 순간(10초 진입)** | **오픈 전 사전 확장된 용량** | 사전 확장한 용량으로 진입 부하를 수용했는가 |
| **이후 대기·SSE 지속 부하**, 예상보다 긴 고부하 | **HPA/CA 반응형 확장·축소** | 정의한 정책대로 늘고 줄었는가 |

**사전 확장은 지금 수단이 없다.** 레포에 예약 확장 구성(KEDA cron 등)이 없고, ArgoCD가 `selfHeal: true`라
HPA `minReplicas`를 `kubectl`로 올리면 Git 상태로 되돌린다(`k8s/argocd/application.yaml`. selfHeal을 켠 이유가
[[TS-021]] §6-1의 수동 HPA 패치 드리프트다). 사전 확장은 **Git 변경으로 하거나 예약 확장 수단을 따로 둬야** 하고, 노드 증설까지
필요하면 CA 반응 시간(위 110초는 1대 기준)만큼 **앞서** 시작해야 한다. 방식은 단계 10에서 정한다.

**확장 지표도 재검토 대상이다.** 지금 HPA는 CPU 60% 기준이다. 측정 결과 SSE 병목이 메모리·FD·연결 수 쪽이고
CPU와 상관성이 낮으면 CPU 기반 HPA만으로는 반응하지 못할 수 있다. 그 경우 활성 SSE 연결 수 같은
workload-specific 지표나 API/SSE 배포 분리를 검토한다. **이것은 도입 확정이 아니라 측정 결과에 따른 후보다.**

### 단계 10에서 함께 검증할 제약

Pod 수에서 노드 수를 바로 계산하지 않는다. 레포에 이미 걸려 있는 상한들이 먼저 닿을 수 있다.

| 제약 | 내용 | 근거 |
|---|---|---|
| **RDS 커넥션 상한** | `maxReplicas × maximum-pool-size + 앱 외 세션 + 여유 ≤ max_connections − reserved`. API `maxReplicas`는 노드뿐 아니라 **DB 커넥션으로도 묶여 있다** — Hikari pending이 병목이면 Pod를 늘리는 것이 오히려 악화시킨다 | `application.yml`, 하네스 `be-db-conn-ceiling`, [[TS-021]](HPA 확장이 RDS 커넥션을 소진한 사건) |
| **클러스터 내 Kafka** | 브로커가 앱과 같은 노드 예산을 쓴다 | `k8s/kafka/kafka.yaml` |
| **롤링 surge · 시스템 Pod · 여유** | 배포 중 겹치는 Pod와 DaemonSet·모니터링 Pod를 포함해야 한다 | `web-hpa.yaml`의 기존 계산 방식 |
| **AWS vCPU 쿼터** | 현재 32 vCPU — 2 vCPU 노드 기준 이론상 16대가 상한. 필요 노드가 넘으면 **쿼터 증설 요청이 선행 조건**이다 | `variables.tf`·`loadtest.tfvars` 주석 |

| 결과 | 문서 |
|---|---|
| 단계별 측정값·knee·병목 | `docs/improvements/IMP-XXX` |
| 측정이 어긋난 사건 | `docs/troubleshooting/TS-XXX` |

knee에서 멈춘 것은 **실패가 아니다.** "S-100K 목표로 부하를 걸었고 X에서 SSE 연결 성공률이 떨어졌으며
최초 병목은 Y였다"는 유효한 결과다. 반대로 발생기가 죽어서 멈춘 것은 아무것도 말해 주지 않는다(§3.1).

## 8. "100K를 검증했다"고 쓸 수 있는 조건

아래가 **모두** 증명돼야 한다. k6가 "100,000 users completed"를 출력하는 것으로는 부족하다.

| 축 | 증명할 것 |
|---|---|
| Traffic | 목표 100K arrivals / 10초를 선언한 분포(Constant 또는 Front-loaded)로 걸었고 `dropped_iterations` = 0, achieved arrivals·peak 1초 arrival rate·처리된 진입·HTTP rps를 구분해 기록했다(§2.3) |
| Queue | WAITING/ADMITTED가 의도대로 유지됐다 |
| Protection | 정원 이상이 downstream으로 새지 않았다 — 실시간 over-admit 0과 사후 실효 입장 초과 0을 모두 만족(§3.3) |
| SSE | 목표 동시 연결과 알림 전달 특성을 만족했다 |
| Correctness | 초과판매·over-admit 등 정합성 위반이 없었다 |
| Platform | 티켓 오픈 전 사전 확장으로 진입 부하를 수용할 용량을 확보했고, 이후 지속 부하 구간에서는 HPA/CA가 정의한 정책대로 확장·축소했다(§6 "확장의 역할") |
| Generator | **발생기가 병목이 아니었다** |

하나라도 빠지면 README 문구는 "100K를 목표로 측정했다"까지다.

**"100K 검증"의 범위는 §2.1의 대기열 진입 시험이다.** 어느 분포(Constant / Front-loaded)였는지도 함께 쓴다. 10만 명이 동시에 결제했다는 뜻이 아니다. 10만 명의 동시
진입을 대기열 계층이 수용하고 입장 제어로 downstream 부하를 정원 안에 묶었다는 뜻이며, 좌석·주문·결제는
E2E 입장자 시험의 결과로 따로 쓴다.

## 9. 범위 밖

- **최대 RPS 경쟁.** 목표는 숫자가 아니라 knee와 병목이다.
- **새 기술 도입**(Rancher·직접 만든 Operator 등). 지금 필요한 것은 기술 추가가 아니라 이미 있는 구성의
  근거를 측정으로 채우는 일이다.
- **비용 예산.** 단계 7~9는 클러스터 확장과 분산 발생기로 실제 AWS 비용이 든다. 예산과 실행 시점은 이
  문서 밖에서 정하고, 단계마다 실험 후 철거한다([[ADR-012]] §8 "상시 운영하지 않는다").
