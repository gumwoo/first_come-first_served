# TS-035 · 롤링 배포 중 502/504 — preStop이 등록 해제 **전파**를 덮지 못했다

- 슬라이스: S09(EKS 배포) — 인프라
- 날짜: 2026-08-25
- 유형: 결함 규명(재현 → 요인 분리 → 수정 효과 확인)
- 관련: [[IMP-015]](§5 미검증 조건·§8 재현 절차), `k8s/base/web-deployment.yaml`, `scripts/rolling-deploy-test.sh`
- 상태: **주요 원인 규명 및 수정 효과 확인** — 수정 전 4/4 실행 실패 → 수정 후 2/2 무결. §7의 한계를 함께 읽을 것

## 1. 배경

[IMP-015](../improvements/IMP-015-rolling-zero-downtime.md)는 롤링 배포 중 3,600건 무중단을 실측했지만,
**다른 조건에서 난 502 1건은 원인을 규명하지 못한 채** 남겨 두었다. §5가 지목한 가설은 둘이었다.

- 이미지 태그가 바뀌면 노드가 **image pull**을 하느라 Ready가 늦어진다
- **web·api가 함께** 롤링되면 web이 프록시하는 대상도 흔들린다

§8이 그 재현을 후속 과제로 남겼고, 이 문서가 그 결과다. **두 가설은 모두 틀렸다.**

## 2. 재현

`scripts/rolling-deploy-test.sh`로 §8의 미검증 조건을 그대로 돌렸다.
표본은 168건에서 6,001건으로 키웠다(25 rps × 4분).

```
조건   이미지 변경(fa46616 → 06030d2, 다이제스트 상이) + web·api 동시 롤링
결과   6,001건 중 16건 실패 (502 × 15, 504 × 1)
분포   T0+14s ~ T0+28s에 집중. 롤링 전 45초 기준선은 0건
```

**재현됐다.** 1건이 아니라 16건이었고, 한 창에 몰려 있어 롤링이 원인이라고 말할 수 있다.

## 3. 요인 분리

§8의 계획대로 변수를 하나씩 갈랐다. 모두 25 rps · 6,001건 내외 · open model.

| 실험 | 이미지 | 범위 | 실패 |
|---|---|---|---|
| 재현 | 변경 | web + api | 16 |
| A | 변경 | **web 단독** | **64** |
| C | **동일**(rollout restart) | web 단독 | **13** |

**A**: web 단독인데 4배 나빠졌다 → **"동시 롤링"은 원인이 아니다.**
(web은 replica가 2개라 하나가 빠지면 용량의 50%가 사라진다 — api는 3개라 33%다. 이는 **추론**이다.)

**C**: `rollout restart`만 해도 13건 → **"이미지 변경"도 원인이 아니다.**

C는 **IMP-015 §3과 명목상 같은 조건**이다(restart · web 단독 · 25 rps · 같은 좌석 조회).
그때는 3,600건 0실패였다. 즉 **원래의 "무중단 실측"이 재현되지 않는다.**

## 4. 기전 — 앱은 5xx를 한 번도 내지 않았다

세 실험 모두 ALB 지표가 같은 방향을 가리켰다.

| 실험 | ELB 502 | ELB 504 | **Target_5XX** | TargetConnectionError |
|---|---|---|---|---|
| 재현 | 15 | 1 | **0** | 10 |
| A | 12 | 52 | **0** | 56 |
| C | 7 | 6 | **0** | 7 |

`Target_5XX = 0`은 **애플리케이션이 5xx를 반환한 적이 없다**는 뜻이다. 전부 ALB가 만든 응답이고,
`TargetConnectionError`가 504 수와 거의 일치한다. k6가 잰 `dur`도 **정확히 10,000ms**에 몰렸다.

Ingress에 idle timeout 어노테이션은 없다(기본 60초). 이 10초는 **ALB가 타깃에 연결을 맺지
못할 때의 연결 타임아웃**이다(ALB 기본값).

⚠️ **`deregistration_delay`와 혼동하면 안 된다.** 두 값이 우연히 모두 10초지만 서로 다른 것이다.
- `deregistration_delay(10s)` — 타깃이 `deregistering`이 된 **뒤**, 이미 진행 중인 연결을
  마무리해 주는 **드레이닝 시간**이다. 이 시간 동안 ALB는 **새 요청을 그 타깃으로 보내지 않는다.**
- 실패한 요청들이 걸린 10초 — ALB가 **아직 등록돼 있는** 타깃에 TCP 연결을 시도하다 포기한 시간.

즉 문제 구간은 드레이닝 중이 아니라 **`deregistering`이 되기 전**이다.

```
target-type: ip   → ALB가 파드 IP를 직접 등록한다

파드 종료 시작
  ├─ 컨테이너: preStop 동안 계속 응답 → 끝나면 SIGTERM → 응답 중단
  └─ 등록 해제 전파: 파드 Terminating → Endpoint(Slice)에서 제거
                     → LB 컨트롤러가 조정 → ALB 타깃이 deregistering으로 전환

  preStop 5s: 전파가 끝나기 전에 컨테이너가 먼저 죽는 구간이 생긴다
              ⟶ ALB는 아직 그 IP를 **정상 타깃으로 보고 새 요청을 보낸다**
              ⟶ 연결 실패 → 10초 연결 타임아웃 → 504 / 502

  preStop 25s: 그 전파 시간을 덮는다 → 실패 0건
```

**원인은 처음부터 매니페스트 안에 있었다.** `preStop`이 **등록 해제가 ALB에 반영되는 시간**을
덮지 못했다.

⚠️ 그러므로 `deregistration_delay`를 줄이는 것은 해법이 아니다 — 오히려 드레이닝을 짧게 만들어
진행 중이던 연결을 일찍 끊는다. 늘려야 할 것은 **컨테이너가 살아 있는 시간**이다.

## 5. 수정과 검증

`k8s/base/web-deployment.yaml`만 고쳤다. **ALB의 타깃은 web뿐이다**(`/ → flowticket-web` 확인).

```diff
- terminationGracePeriodSeconds: 30
+ terminationGracePeriodSeconds: 60
-   exec: { command: ["sh", "-c", "sleep 5"] }
+   exec: { command: ["sh", "-c", "sleep 25"] }
```

`grace`를 함께 올린 이유: `preStop(25) + 종료 시간`보다 작으면 preStop 도중 SIGKILL이 나서
**오히려 더 나빠진다.**

| 실험 | web preStop | 행위 | 범위 | 요청 | 실패 |
|---|---|---|---|---|---|
| C | 5s | restart | web | 6,001 | 13 |
| **E** | **25s** | restart | web | 6,001 | **0** |
| 재현 | 5s | 이미지 변경 | web + api | 6,001 | 16 |
| **F** | **25s** | **이미지 변경** | **web + api** | 6,001 | **0** |

**C→E와 재현→F는 각각 변수가 `preStop` 하나다. 13→0, 16→0.**

F는 실제 배포 경로 조건이다 — api·web 다이제스트가 모두 달라 실제 pull이 일어났고,
태그가 `fa46616 → 06030d2`로 교체됐으며, 새 ReplicaSet이 2/2 Ready가 된 것을 확인했다.

**api의 `preStop`은 5s 그대로 두었는데도 0건이었다.** 변수를 하나만 바꾼 덕에
api 쪽 경로는 문제가 아니었다는 것도 함께 확인됐다.

## 6. 왜 2026-08-08에는 0이었나 — 미해결

C가 IMP-015 §3을 재현하지 못한 이유는 **밝히지 못했다.**

의심한 것은 생성기 모델이다. §3은 "병렬 6워커"(closed model)였고, 이번은
`constant-arrival-rate`(open model)다. `infra/k6/read-load-rate.js` 헤더가 적어 둔 대로
closed model은 응답이 느려지면 부하가 스스로 줄어 장애 창을 덜 때린다.

이를 확인하려 6 VU closed model로 돌렸으나(실험 D) **대조군이 되지 못했다.**
§3의 6워커는 집 PC에서 쏴 RTT가 커 25 rps였는데, 클러스터 안에서는 RTT가 45ms라
같은 6 VU가 **238 rps**를 만들었다. 부하량이 10배 달라 비교할 수 없다.

부수적으로 얻은 것: 그 조건에서도 closed model이 56건을 잡았다. **"closed는 못 본다"만으로는
설명되지 않는다.** 제대로 된 대조군은 6 VU에 pacing을 넣어 25 rps로 맞춰야 한다.

## 7. 한계

- **조건별로는 1회씩이다.** 다만 수정 전후로는 4회 대 2회다 — 결함이 **4/4로 재현**된 뒤
  `preStop` 하나를 바꿔 **2/2가 무결**해졌으므로, 운으로 0이 나왔다고 보기는 어렵다.
  그렇더라도 같은 조건의 반복 측정은 하지 않았다.
- **부하가 25 rps다.** 이 구간에서는 파드 하나가 빠져도 남은 파드가 여유 있게 받는다.
  선착순 피크에서는 남은 파드가 포화돼 **다른 실패 모양**이 나올 수 있다 — 검증하지 않았다.
- **web 티어 롤링만 봤다.** api 단독 롤링, 노드 드레인과의 동시 발생은 측정하지 않았다.
- **25s의 최소 필요값을 모른다.** 10s나 15s로도 되는지 재지 않았다.
  더 근본적으로 **등록 해제 전파에 실제로 얼마가 걸리는지를 재지 않았다** — 25s는 여유를 크게
  잡은 값일 뿐이다. 전파 시간(파드 Terminating → ALB 타깃 `deregistering`)을 측정해야
  근거 있는 값을 정할 수 있다.
- **§6이 미해결이다.** 옛 측정이 왜 0이었는지 설명하지 못한 채 남았다.
- api 쪽 종료 경로(`web → ClusterIP Service`)는 **이번에 문제가 되지 않았을 뿐**
  검증한 것은 아니다. 부하나 replica 수가 달라지면 드러날 수 있다.

## 8. 남는 것

- §6의 제대로 된 대조군(6 VU + pacing 25 rps)
- `preStop` 최소 필요값 탐색
- 등록 해제 전파 시간 실측 — 파드 Terminating부터 ALB 타깃이 `deregistering`이 되기까지.
  이 값을 알아야 `preStop`을 근거로 정할 수 있다(지금은 여유를 크게 잡은 것뿐이다).
- 이 계열을 정적으로 막을 수 있는가 — 다만 `preStop` vs `deregistration_delay` 크기 비교로는
  안 된다(둘은 다른 구간을 가리킨다). 전파 시간이 기준이라 정적 규칙으로 만들기 어렵다.
