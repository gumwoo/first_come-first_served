# IMP-015 · 롤링 배포 무중단 실측 — 3,600건 중 5xx 0건 (조건 한정)

- 슬라이스: S09(EKS 배포) — 인프라
- 날짜: 2026-08-08
- 유형: 정량(가용성 실측)
- 관련: [[TS-035]](이 문서의 미검증 조건을 규명한 후속), [[ADR-012]](3AZ 인프라), `k8s/base/api-deployment.yaml`, [[TS-016]]·[[TS-017]](같은 배포에서 나온 결함)
- 상태: **종결** — §5의 미검증 조건은 2026-08-25에 재현하고 주요 원인을 규명해 수정 효과까지 확인했다([[TS-035]], §9)

## 1. 배경

매니페스트에 무중단을 위한 값들을 **짝으로** 맞춰 두었지만, 실제로 통하는지는 확인하지 않았다.
PR #179에 이렇게 적어 두었다.

> "5초가 그 창을 덮는다고 보장할 수는 없다 — 실제로 충분한지는 롤링 중 무중단 실측으로 확인해야 한다."

이 문서가 그 확인이다.

## 2. 검증 대상 — 짝을 맞춘 값들

| 설정 | 의도 |
|---|---|
| `maxUnavailable: 0` / `maxSurge: 1` | 새 Pod가 Ready된 **뒤에만** 옛 Pod를 뺀다 |
| `preStop: sleep 5` | SIGTERM 전에 멈춰 ALB 등록 해제가 **시작될** 시간을 번다 |
| `deregistration_delay = 10s` | 등록 해제 중 기존 연결을 드레이닝 |
| `terminationGracePeriodSeconds: 30`(web) | 위 둘보다 커야 SIGKILL이 앞지르지 않는다 |
| readiness `periodSeconds: 5`, `failureThreshold: 3` | 준비되지 않은 Pod로 트래픽이 가지 않게 |

## 3. 측정 방법

```
대상   https://flow-ticket.com/api/events/1678/seats   (좌석 100석 — DB를 실제로 타는 조회)
부하   병렬 6워커, 약 25 req/s
행위   부하 중 kubectl rollout restart deployment/flowticket-web
기록   요청별 (시각, 워커, HTTP 상태코드)
```

빈 목록 조회가 아니라 **좌석 조회**를 쓴 이유: DB를 거의 타지 않는 요청은 무중단의 증거로 약하다.

## 4. 결과

```
총 요청   3,600
200       3,600  (100%)
5xx           0
rollout   23:22:54 → 23:23:00  (web 파드 2개 교체, 새 ReplicaSet 확인)
```

**롤링이 실제로 일어났는지도 확인했다** — 새 ReplicaSet이 생기고 파드 2개가 교체됐다.
(첫 시도에서 `rollout status`가 6초 만에 끝나 의심스러워 ReplicaSet 이력으로 검증했다.)

## 5. 검증 범위 — 통과한 조건과 남은 조건

**"무중단이 확인됐다"고 일반화할 수 없다.** 직전에 다른 조건에서 **502가 1건** 났다.

| | 502가 난 배포 | 이 측정 |
|---|---|---|
| 방식 | `kubectl apply` — **이미지 태그 변경** | `rollout restart` — 이미지 동일 |
| 범위 | **web + api 동시** | web 단독 |
| 부하 | 2.5 req/s (168건) | 25 req/s (3,600건) |
| 결과 | **502 × 1** | 0 |

이미지가 바뀌면 노드가 **이미지를 pull**하느라 Ready까지 더 걸리고, api까지 함께 롤링되면
web이 프록시하는 대상도 흔들린다. **그 조합에서만 나는 것일 수 있다.**

정확히 말할 수 있는 것은 두 가지다.
- **이미지 동일 + web 단독 롤링**: 25 req/s에서 3,600건 무중단
- **이미지 변경 + web·api 동시 롤링**: 168건 중 1건 502

**후자는 원인을 규명하지 않았다.** 재현 조건을 좁히려면 이미지를 다시 바꿔 롤링해야 한다.

## 6. 한계

- **측정 지점이 인터넷 밖**이다(내 PC → ALB). 네트워크 요인을 배제하지 못한다.
- **부하가 낮다.** 25 req/s는 선착순 트래픽과 거리가 멀다 — S10 부하테스트에서 다시 봐야 한다.
- **web만 롤링했다.** api 롤링 중 무중단은 별도로 확인해야 한다.
- **단발 측정**이다. 502는 168건에 1번 났다 — 3,600건 0건이 "0%"를 뜻하지 않는다.

## 8. 후속 과제 — 미검증 조건 재현

§5의 미검증 조건(**이미지 태그 변경 + web·api 동시 롤링**)을 §3과 같은 부하(25 req/s)에서 재현한다.
직전 관측은 2.5 req/s·168건이었으므로, 표본을 §3 수준으로 키우는 것이 전제다.

**가설** — 이미지가 바뀌면 노드가 이미지를 pull 하느라 Ready까지 더 걸리고, api까지 함께 롤링되면
web이 프록시하는 대상도 동시에 교체된다. 둘 중 어느 쪽이 502를 만드는지는 아직 가른 적이 없다.

**판정 기준**
- 재현되면 → 두 요인을 분리 측정(이미지 변경 + web 단독 / 이미지 동일 + web·api 동시)해 원인을 좁힌다.
- 재현되지 않으면 → **원인 규명이 아니라 표본 크기의 한계로 기록한다.** 168건 중 1건은
  재현 없이 원인을 단정할 근거가 못 된다.

이 항목이 닫히기 전까지 §1의 "무중단"은 §5의 검증된 조건에 한정된 서술이다.

## 9. 후속 결과 (2026-08-25) — §8이 닫혔다

§8의 재현을 실행했고 **§5의 두 가설은 모두 틀렸다.** 상세는 [[TS-035]].

| 실험 | web preStop | 행위 | 범위 | 요청 | 실패 |
|---|---|---|---|---|---|
| 재현 | 5s | 이미지 변경 | web + api | 6,001 | **16** |
| A | 5s | 이미지 변경 | web 단독 | 5,964 | **64** |
| C | 5s | restart | web 단독 | 6,001 | **13** |
| E | **25s** | restart | web 단독 | 6,001 | **0** |
| F | **25s** | 이미지 변경 | web + api | 6,001 | **0** |

원인은 이미지 변경도 동시 롤링도 아니었다. **`preStop: sleep 5`가 등록 해제가 ALB에
반영되는 시간을 덮지 못했다** — 파드 Terminating → EndpointSlice 제거 → LB 컨트롤러 조정
→ ALB 타깃 `deregistering` 전환이 끝나기 전에 컨테이너가 먼저 죽었고, 그 구간에서 ALB는
그 IP를 아직 정상 타깃으로 보고 요청을 보냈다(`target-type: ip`).
네 번의 측정에서 **`Target_5XX`가 계속 0**이었던 것이 그 신호였다 — 앱은 5xx를 낸 적이 없다.

⚠️ `deregistration_delay(10s)`와 혼동하지 말 것. 그것은 타깃이 `deregistering`이 **된 뒤**
진행 중인 연결을 마무리하는 드레이닝 시간이며, 그 동안 ALB는 새 요청을 보내지 않는다.
줄인다고 해결되지 않는다. 상세는 [[TS-035]] §4.

`k8s/base/web-deployment.yaml`의 `preStop`을 25s(+ `grace` 60s)로 올리자
**실제 배포 경로 조건에서 6,001건 전량 2xx**가 됐다.

### 이 문서의 §3·§4를 어떻게 읽어야 하나

⚠️ **§3의 조건(restart · web 단독 · 25 rps)을 2026-08-25에 다시 재면 13건이 실패한다**(실험 C).
§4의 "3,600건 5xx 0"이 왜 나왔는지는 **아직 설명하지 못했다** — 생성기 모델 차이(closed vs
open)를 의심했으나 대조 실험이 성립하지 않았다(TS-035 §6).

따라서 §4의 숫자는 **삭제하지 않고 그대로 둔다.** 다만 그것을 "무중단이 확인됐다"의 근거로
쓰지 않는다. 이 문서에서 지금 근거로 쓸 수 있는 것은 **§9의 E·F**다.
