# ADR-012 · 3AZ EKS 운영 유사 인프라 — 이중화 범위와 비용 통제 전략

- 상태: **Accepted** (2026-08-10 기준 3AZ EKS 클러스터가 실제로 기동 중 — 노드 t3.large 3대,
  RDS·ElastiCache·ALB 연결 확인. 비용 통제를 위한 apply/destroy 운용은 그대로 유지)
- 날짜: 2026-08-04
- 슬라이스: S09(배포·운영 준비) Phase 3 — 인프라 트랙
- 관련: [[ADR-009]](GitOps CD), [[ADR-008]](Kafka 백본),
  **[[ADR-013]](IaC 소유 경계·비밀·접근 통제 — 이 결정을 코드로 옮기며 나온 결정들)**,
  구현 상세 → [`docs/deployment/terraform-design.md`](../deployment/terraform-design.md)

## 맥락

S09는 "실제로 도는 분산 시스템"을 실증하는 트랙이다. Phase 2(ECR 이미지 파이프라인)까지 끝났고,
이제 **인프라를 실제로 만드는 단계**라 되돌리기 어려운 결정이 몰려 있다 — AZ 개수, NAT 배치,
노드그룹 구조, 인스턴스 계열, 그리고 **상시 운영 여부**.

여기엔 긴장 관계가 하나 있다.

- 개인 포트폴리오라 **비용이 실제 제약**이다. 상시 운영하면 월 $240 수준(EKS 컨트롤플레인 $73 +
  노드 + RDS + ElastiCache + ALB + NAT).
- 그런데 **비용 최소화가 목표였다면 EKS 자체가 모순**이다. 그 목표면 EC2 한 대 + Docker Compose가 맞다.

즉 "싸게 만든다"가 아니라 **"검증 목적에 필요한 것은 쓰고, 목적에 기여하지 않는 상시 비용만 제거한다"**로
문제를 다시 세워야 한다. 이 프로젝트가 EKS를 쓰는 이유는 **다중 Pod에서만 드러나는 문제**를 재현하기
위해서다 — SSE 연결 Pod ≠ 소비 Pod 팬아웃(ADR-008), `@Scheduled` 중복 실행(ShedLock),
Kafka 브로커 장애 복구, HPA 수평 확장.

## 결정

### 1. 단일 리전 `ap-northeast-2`, **3 AZ**
Kafka 브로커 3개를 **서로 다른 장애 도메인**에 하나씩 두기 위한 최소 구성이다.

### 2. NAT Gateway는 **AZ별 1개(zonal ×3)**
근거는 "정석이라서"가 아니라 **이 서비스의 아웃바운드가 결제 경로**이기 때문이다.

| 아웃바운드 | 끊기면 |
|---|---|
| PG 승인·조회·취소(Toss) | **결제 불가** |
| KOPIS 동기화 | 공연 데이터 갱신 중단 |
| ECR 이미지 pull | 신규 Pod 기동 실패 |

단일 NAT면 그 NAT가 있는 AZ 장애가 **정상 AZ의 Pod까지 결제 불가**로 만든다. 그러면
"3 AZ로 장애를 격리했다"는 주장이 **절반은 거짓**이 된다. AZ 개수와 NAT 개수를 일치시켜야
주장과 구성이 어긋나지 않는다.

추가로 **S3 Gateway 엔드포인트(무료) + ECR API/DKR Interface 엔드포인트**를 둬서
AWS 서비스 트래픽을 NAT 경로에서 분리한다. 없어도 동작하므로 필수가 아니라 **개선**이다.

### 3. 노드는 **AZ별 Managed Node Group ×3**, 각 `min=1 / desired=1 / max=2`
하나의 노드그룹에 3개 AZ 서브넷을 주는 대신 **AZ마다 노드그룹을 분리**한다. 이유는 EBS다.

- EBS 볼륨은 **특정 AZ에 종속**된다.
- 노드가 죽어 ASG가 **다른 AZ에 대체 노드**를 띄우면, 그 브로커의 EBS는 원래 AZ에 있어
  **붙지 못한다** → 브로커가 영구 Pending.
- AZ별 노드그룹이면 대체 노드가 **항상 같은 AZ**에 뜬다.

즉 "노드 1대를 죽여도 복구된다"는 실증이 성립하기 위한 전제 조건이다.

원문(2026-08-06 판단):
HPA는 **Pod 개수**를 늘릴 뿐 **노드 용량**을 늘리지 못한다. 노드를 3대로 고정하면
부하 시 HPA가 Pod를 늘려도 자리가 없어 **Pending**에 걸리고, "HPA를 적용했다"는 사실이지만
**"확장됐다"는 거짓**이 된다. 결정 2와 같은 원칙(주장과 구성의 일치)이다.

`max=2 × 3 AZ = 최대 6노드`. — 측정 프로파일(`loadtest.tfvars`)에서는 **AZ당 3 = 최대 9노드**로
올린다. 기본값에서는 HPA 상한까지 늘려도 예산 안에 들어가 CA가 발동하지 않기 때문이다.

### 5. 인스턴스 계열을 **목적별로 전환**한다
- **기능·배포·페일오버 검증**: `t3.large` (2 vCPU / 8 GiB)
- **부하테스트(S10)**: `m6i.large` 등 **비버스터블 계열**

T 계열은 버스터블이라 지속 부하에서 **CPU 크레딧 상태가 결과에 개입**한다. `t3.large`의 기준 CPU는
vCPU당 30%라 크레딧 소진 후 지속 성능이 크게 떨어진다. 그러면 k6 그래프의 처리량 저하가
**코드 때문인지 크레딧 때문인지 구분할 수 없어** 측정 자체가 무효가 된다. 이 프로젝트의 논지가
성능·동시성 실측(IMP 문서)이라 **비버스터블이 측정의 전제**다. Terraform 변수로 전환한다.

### 6. Kafka — **rack awareness와 topology spread를 별개로** 둔다
```
rack.topologyKey: topology.kubernetes.io/zone
  → Kafka에 broker.rack 제공 → 파티션 레플리카를 AZ에 걸쳐 배치
  → 해당 label이 있는 노드로 제한하는 node affinity 추가

topologySpreadConstraints (maxSkew=1, DoNotSchedule)
  → Kubernetes가 브로커 Pod를 AZ별 1개씩 실제 배치
```
**rack awareness만으로는 브로커 Pod가 AZ에 균등 분산되지 않는다.** 둘 다 필요하다.
`RF=3`, `min.insync.replicas=2`, `acks=all` → 브로커 1대가 죽어도 ISR 2개가 남아 쓰기가 지속된다.

### 7. 스토리지 — `volumeBindingMode: WaitForFirstConsumer`
`Immediate`면 PVC가 Pod 스케줄링 **전에** 임의 AZ에 볼륨을 만들어, 그 AZ에 자리가 없으면
Pod가 영구 Pending이 된다. `WaitForFirstConsumer`는 **Pod 배치가 정해진 뒤** 같은 AZ에 만든다.
결정 3(AZ별 노드그룹)과 **짝을 이뤄야** 의미가 있다.

### 8. 운영 모델 — **상시 운영하지 않는다**
필요할 때 `terraform apply` → 실증·촬영 → Kubernetes 종속 리소스 제거 → `terraform destroy`.
비용 통제는 **이중화를 깎는 방식이 아니라 실행 시간으로** 한다. 데모 4시간 기준 약 $1.5~2 수준
(근사치 — 실제 청구는 AWS 요금 기준).

안전망(**설정 완료** — 상세는 terraform-design §7):
- **Budgets** 월 $50, 실제 $5·$20·$50 + 예상 $50 = 4단계 알림
- **Cost Anomaly Detection** 임계값 $3, 일일 요약

**자동 종료 작업은 두지 않는다.** 예산 초과로 리소스를 자동 정지하면 EKS가 불완전하게 멈춰
(노드만 죽고 컨트롤플레인·EBS·NAT는 잔존) 오히려 정리가 어려워진다. 알림만 받고 종료 판단은
사람이 하며, destroy는 정해진 순서를 따른다.

### 9. Terraform state를 **2계층으로 분리**한다
- **bootstrap(영속)**: ACM, ECR, IAM/OIDC — `destroy` 대상이 아님.
  **Route53 Hosted Zone은 Terraform이 소유하지 않고 `data`로 참조만 한다** — Registrar가 이미
  생성했고, 재생성하면 NS가 바뀌어 도메인 설정을 다시 해야 하는 가장 되돌리기 어려운 자원이다.
  (자원마다 `data`/`import`/신규 생성을 가르는 기준은 [[ADR-013]] §1.)
- **platform(휘발)**: VPC, NAT, EKS, RDS, ElastiCache, ALB — 매번 만들고 지움

`platform destroy`가 도메인·인증서·이미지까지 날리지 않게 하기 위한 분리다.

### 10. 데이터 계층(RDS·ElastiCache)도 **Multi-AZ**로 둔다

결정 2(AZ별 NAT)와 같은 일관성 논점이 여기에도 걸린다. 오히려 파급은 더 크다.

| | 단일 NAT의 AZ 장애 | 단일 AZ RDS의 AZ 장애 |
|---|---|---|
| 앱 Pod | 살아있음 | 살아있음 |
| DB | 정상 | **소멸** |
| 결과 | 결제 등 외부 연동만 마비 | **전면 중단** |

NAT 이중화를 받아들였으면 RDS는 그 귀결이다. 안 두면 "3 AZ로 장애를 격리했다"는 주장이
NAT 때보다 **더 크게** 어긋난다.

**두 계층의 근거는 다르다 — 문서에도 나눠 적는다.**

- **RDS = 진실원**: 이 프로젝트의 정합성 설계 전체(ADR-003 조건부 UPDATE, ADR-006 상태 전이,
  ADR-010 아웃박스)가 "DB가 살아있다"를 전제로 선다. 그 전제를 단일 AZ에 걸 수 없다.
- **ElastiCache = 보조**: Redis가 죽어도 초과판매·주문 상태는 깨지지 않는다(ADR-008 — 진실원은 DB).
  대신 **대기열 순번과 SSE 팬아웃이 사라진다.** 선착순 대기열이 이 서비스의 간판 기능이라
  "정합성은 무사한데 서비스는 멈춘" 상태가 된다. **가용성이 근거이지 정합성이 근거가 아니다.**

**그리고 이건 NAT와 달리 실증할 수 있다.** RDS는 강제 페일오버(`reboot --force-failover`),
ElastiCache는 `test-failover`로 장애를 직접 주입할 수 있다. 그래서 이 항목은 아래 분류의
**B가 아니라 A**로 둔다 — 켜 두기만 하는 것이 아니라 **눌러 보고 앱의 거동을 측정**한다.
관찰 대상은 인프라가 아니라 **애플리케이션의 회복력**이다(커넥션 풀 재연결, 페일오버 구간의
오류 형태, 자동 정상화 여부).

⚠️ **Multi-AZ는 무손실이 아니다.** RDS 페일오버는 통상 수십 초~2분 쓰기가 막히고,
Redis 복제는 **비동기**라 최근 쓰기 일부가 유실될 수 있다. "켰으니 안전"이 아니라
**"중단 시간이 짧아진다"**가 정확한 표현이다.

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **1 AZ** | 브로커 3개가 한 장애 도메인 → AZ 장애 실증 불가. 3 AZ의 의미 자체가 사라짐 |
| **2 AZ + 브로커 3개** | 비둘기집 원리로 **한 노드/AZ에 브로커 2개**가 몰린다. 그게 죽으면 ISR이 1개만 남아 `min.insync=2`에서 **쓰기 중단** → "1대 장애에도 지속"이라는 실증이 성립하지 않음 |
| **단일 NAT** | 비용은 데모 기준 무시할 수준(4시간 약 $0.5)인데, 한 AZ 장애가 **정상 AZ의 PG 승인까지 차단**한다. 3 AZ를 쓰면서 NAT를 공유하면 격리 주장과 구성이 어긋남 |
| **AZ 서브넷 3개를 가진 단일 노드그룹** | 대체 노드가 다른 AZ에 뜨면 EBS가 붙지 못해 브로커 복구 실패 |
| **고정 3노드(CA 없음)** | 당시 근거: HPA가 Pod를 늘려도 수용할 노드가 없어 Pending → HPA 실증이 무효. **→ 그 근거는 절반만 맞았다.** replica 상한을 예산에 맞추면(api 7 / web 4 = 4,950m / 5,790m) 평시에는 Pending이 나지 않는다. 다만 **상한을 넘는 상황에서는 노드가 필요하고**, 2026-08-26에 CA를 도입해 그 구간을 실측했다([[IMP-021]]) |
| **t3로 부하테스트** | CPU 크레딧이 측정 결과를 오염시켜 개선 수치의 인과를 주장할 수 없음 |
| **단일 AZ 데이터 계층** | 데모 기준 추가 비용이 **시간당 약 $0.05**(4시간 +$0.2)인데, 앱·Kafka를 3 AZ로 분산해 놓고 DB가 단일 AZ면 AZ 장애 시 결국 전면 중단이다. 절감액이 일관성을 깨는 값어치에 못 미친다 |
| **상시 운영** | 월 $240 수준. 실증에 기여하지 않는 유휴 시간 비용이라 제거 대상 |
| **환경 분리(dev/stage/prod)** | 환경마다 EKS·NAT 3개·RDS Multi-AZ가 통째로 복제돼 **비용 3배**. 사용자 1명·트래픽은 k6로 자체 생성·릴리스는 본인 머지라 **stage에서 발견할 대상이 없다**. "검증 안 된 게 나가면 안 된다"는 우려는 CI 게이팅(workflow_run)과 ArgoCD가 이미 담당한다 → 상세·되돌릴 조건: [terraform-design §10](../deployment/terraform-design.md) |
| **EC2 1대 + Docker Compose** | 가장 싸지만 **다중 Pod에서만 나타나는 문제**(SSE 팬아웃·스케줄러 중복·브로커 페일오버·HPA)를 재현할 수 없음 → 이 트랙의 목적 자체를 잃음 |
| **Karpenter** | Cluster Autoscaler보다 현대적이지만, AZ별 노드그룹 + EBS 종속 설계와 개념이 겹쳐 관리 포인트가 는다. 우선 CA로 갔고(2026-08-26 도입·실증), 필요해지면 그때 재검토한다 |

## 이중화의 두 종류 (이 ADR의 판단 기준)

모든 구성을 장애 주입으로 검증해야 하는 것은 아니다. 두 종류를 구분한다.

**A. 프로젝트의 핵심 주장 → 반드시 실증한다**
HPA 수평 확장, Kafka 브로커 장애 복구, ArgoCD self-heal, 다중 Pod SSE 팬아웃,
스케줄러 중복 억제, 초과판매 방지, **RDS·ElastiCache 페일오버 중 앱 거동**.

> A와 B를 가르는 실질 기준은 "중요한가"가 아니라 **"장애를 주입할 수단이 있는가"**다.
> 그래서 RDS Multi-AZ는 A(강제 페일오버 API가 있다)이고 AZ별 NAT는 B(AZ를 죽일 수 없다)이다.
> **같은 이중화라도 실증 가능성이 다르면 다루는 방식이 달라진다.**

**B. 기본 운영 안전장치 → 설계 근거와 한계를 명시하는 것으로 충분하다**
프라이빗 서브넷, 최소 권한 IAM, RDS/Redis 비공개, TLS, **AZ별 NAT**.

보안 그룹을 썼다고 침투 테스트를 해야 하는 것은 아니듯, B를 전부 실증할 필요는 없다.
**"실증하지 못하면 전부 오버엔지니어링"까지 밀면 지나치다.** 정확한 원칙은
**"핵심 주장에 해당하는 기술은 실증하고, 기본 안전장치는 근거와 한계를 설명한다"**이다.

## 결과 / 한계 (정직)

- ~~**아직 Proposed다.** `plan`·`apply`는 미실행이다.~~ → **Accepted (2026-08-10 승격).**
  `apply`/`destroy`를 반복 수행했다. 가장 최근은 2026-08-25로, `apply` 74개 생성 →
  측정 6회 → `destroy` 74개 전량 삭제(잔여 점검 11항목 모두 0)였다.
  비용 통제 운용(`apply`/`destroy` 왕복)이 문서상의 계획이 아니라 **실제 절차**임을
  `scripts/bring-up.sh`·`scripts/tear-down.sh`가 뒷받침한다.
- **AZ 장애는 실증하지 않는다.** NAT 3개·3 AZ는 위 분류의 **B**에 해당한다. AZ 전체 장애 주입은
  실증 범위 밖이며, 이 문서가 근거를 남기는 것으로 대신한다.
- **평시에는 노드가 늘지 않는다.** HPA 상한(api 7 / web 4)이 예산 안에 있어 CA가 발동할 일이
  없다. CA는 그 상한을 넘는 상황을 위한 안전망이다 — "무한히 수평 확장된다"는 뜻이 아니다.
- **Cluster Autoscaler의 노드 기동 지연**(EC2 부팅 + 클러스터 조인)은 **110초로 실측됐다**
  ([[IMP-021]] §3). HPA 반응(초 단위)과 자릿수가 다르다는 서술이 숫자로 확인됐다.
  부하 급증 직후 Pending 구간이 생기는 것은 버그가 아니라 구조적 특성이다.
  오버프로비저닝(낮은 priority pause Pod)은 여전히 개선 항목이다.
- **CA scale-down이 Kafka 브로커를 옮길 수 있다** — 2026-08-26 측정에서는 **발생하지 않았다**
  ([[IMP-021]] §4, [[IMP-016]] §7). ⚠️ 다만 **축소와 부하를 동시에 건 조건은 재지 않았다.**
  `cluster-autoscaler.kubernetes.io/safe-to-evict`를 브로커에 적용하는 것은 여전히 미검토다.
- **단일 리전이다.** 리전 장애는 범위 밖.
- **Multi-AZ가 무손실을 뜻하지 않는다.** RDS 페일오버 구간에는 쓰기가 막히고, Redis는 비동기
  복제라 최근 쓰기가 유실될 수 있다. 실증에서 **얼마나 멈추고 무엇을 잃는지 수치로** 남긴다.
- **데이터 계층 Multi-AZ는 apply/destroy를 느리게 한다.** 데모 모드가 apply/destroy 반복이라
  이 비용은 매번 발생한다 — 금액(시간당 약 $0.05)보다 이 시간 마찰이 실질 대가다.
- **Regional NAT Gateway는 이 설계에서 검토하지 않았다.** 검증이 잘 된 zonal NAT로 간다.
- **데모 전용이라 상시 접속 URL이 없다.** 대신 실증 증거(영상·대시보드 캡처·부하 그래프)를
  상시 보관하고, 라이브는 필요 시 기동한다.
- **비용 수치는 근사치**다. 리전·인스턴스 가격은 변동하므로 실제 청구액으로 갱신한다.
- **되돌리기**: NAT 1개, 2 AZ, 고정 노드로 축소하는 것은 Terraform 변수 수준의 변경이다.
  축소할 경우 **이 ADR을 새 ADR로 대체**하고, 어떤 실증이 함께 빠지는지 명시한다.
