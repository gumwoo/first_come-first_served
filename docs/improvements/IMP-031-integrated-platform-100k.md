## 1. 상황 (Context)
[[IMP-029]]는 §8 7축 중 6축을 판정 3회 충족했지만 **Platform**을 증명하지 못했다 — 사전 확장이 세션 kubectl(HPA 고정·노드 분산 패치)이었고,
반응형 확장·축소는 별도 시연(세션 한정 설정, 시연 부하 run 무효)에서만 봤다. 사용자 결정으로 마지막 목표를 "Platform까지"로 두고,
정책을 Git으로 현실화한 뒤([[ADR-025]]) **한 run 안에서** 7축을 함께 판정했다.

## 2. 문제 정의 + 분류
오픈 전 사전 확장(Git PR) → 10만 명 / 10초 진입 → 사전 확장 끄기(Git PR) → HPA·CA 정책대로 축소 → 대기자 폴링 폭증에 정책대로 확장 → 다시 축소까지,
운영 설정 그대로 오류 없이 이어지는지 — 그리고 그 동안 IMP-029의 6축(진입·대기열·정원 보호·대기 상태 전달·정합성·발생기)이 그대로 유지되는지.

- 계층 분류: 애플리케이션 처리 용량(api CPU·requests) / 스케줄링·노드 확장(HPA·CA·PriorityClass) / 배포 파이프라인(Git → ArgoCD) / 부하 발생기
- 왜 이 계층인가: IMP-029의 빈칸이 "정책대로 확장·축소"였고, 그 앞단 원인이 requests 300m(HPA %·CA Pending의 기준이 실제 비용과 무관)와 세션 kubectl 사전 확장이었다([[ADR-025]] 맥락).

## 3. 측정 방법 (사전 등록 `platform-prereg.md` — 결과 보기 전 고정, 변경은 변경 기록에 남김)
- 구성(운영 설정 그대로 — Git): api `requests.cpu` 1100m(노드당 api 1), HPA 3~9(CPU 60%), 노드 그룹 AZ당 최대 3(합 9), web PriorityClass −1,
  ArgoCD 자동 동기화 켬(세션 kubectl로 HPA·노드 그룹을 바꾸지 않음). 측정 장치만 세션 한정: ALB access log.
- run 한 회(시각은 T0 = 오픈):
  1. 사전 확장 켜기 PR(`event-prescale.yaml` 하한 3 → 9, `# event`·`# off-by`) — CI(규칙 11)·G1 → 머지 → ArgoCD → api 6개 Pending → CA 노드 추가.
  2. 확인: HPA min 9·api Ready 9·노드 9·web Ready ≥ 1. 새 파드 예열(별도 공연 3,000/s × 20초, 판정 제외) → 리셋 → 150초.
  3. T0: 진입 100,000명 / 10초(발생기 3대 `--rate 3400`, 연결 미리 맺기 30초) + 대기자 폴링(poll-hold) T0 + 28분까지.
  4. T0 + 60초: 미리 CI·G1을 끝낸 끄기 PR(하한 3) 머지 → 이후 HPA·CA 정책에 맡긴다.
  5. T0 + 15분 ~ + 23분: **폴링 폭증** — 이 공연의 대기 토큰으로 상태 조회 7,000/s × 480초(발생기 3대 합, 연결 미리 맺기 20초).
  6. T0 + 50분까지 축소 관찰. 사후: export-prom → `check-correctness --api-logs`(축소로 지워진 파드의 감사 로그 포함).
- 판정: 6축은 IMP-029 v3 기준 그대로 + 폭증 조회 5xx·네트워크 오류 0. Platform은 P1(Git 사전 확장 반영·api 9·노드 9) / P2(오픈 수용) / P3(Git 인계 반영) /
  P4(폭증 전 HPA 축소·CA 노드 1대 이상 감소) / P5(폭증 중 HPA 확장·Pending ≥ 1·CA 노드 추가·Running) / P6(폭증 뒤 HPA 축소·T0+50분까지 CA 노드 1대 이상 감소) / P7(그 동안 오류 0).
- 워밍업 1회(판정 제외) + 판정 3회, run마다 새 공연·대기열 키 리셋, run 사이에는 정책 상태(HPA 3·노드 4)로 돌아온 뒤 시작.

- 폭증에서 첫 Pending → 전부 Running 약 80~145초(20초 해상도). 그 공백 동안 폭증 목표의 0.9~2.7%를 보내지 못했고(dropped ÷ 3,360,000), 응답 꼬리가 수 초까지 늘었다 — 오류는 0.

## 8. 트레이드오프 / 한계 / 다음 개선
- **§8 기준 결론**: **사전 등록 기준 7축(6축 + Platform)을 판정 3회 모두 충족했다 — 100K/10s(Constant, 대기열 진입·대기·입장 제어 + 확장 정책) 검증**(사용자 결정).
  단서를 같은 문장으로 붙인다: 진입 창은 분 경계(:00)를 지나지 않게 배치했고([[TS-042]] — 창이 :00을 지난 워밍업은 진입이 무너졌다, 원인 미확정 — **정각 오픈은 미검증**),
  폭증 dropped를 무효로 보지 않은 해석은 pf-r1 결과를 본 뒤 정했다. 좌석·주문·결제는 범위 밖이다([[IMP-030]]).
- **측정 이미지 이후 변경(2026-10-09)**: 이 결과는 api 이미지 `419c96b`의 결과다. 이후 대기열 정합성 수정 — 토큰 소유권([[TS-043]]),
  재발급·이탈 경합([[TS-044]]), 대기 토큰 수명주기([[TS-045]], 상태 조회마다 `TTL` 1회 추가 등 뜨거운 경로 비용 변화) — 과 Kafka AZ 분산,
  ALB 계층 알람 스택이 들어갔다. 정합성은 통합 테스트(CI)로 검증했고, **바뀐 코드로 부하를 다시 재지는 않았다**.
- **분 경계 단서([[TS-042]])**: 판정 run의 진입 창은 사용자 결정으로 :00을 피해 배치했다. 실제 오픈은 보통 정각이라 운영에서는 바로 그 순간에 몰린다.
  워밍업처럼 창이 :00을 지나면 같은 구성에서도 진입이 무너질 수 있다(1회 관찰, 원인 미확정). 이 결과는 "분 경계를 지나지 않는 창"에서의 결과다.
- **결과를 본 뒤 정한 해석이 하나 있다**: 폭증 dropped를 무효로 보지 않기로 한 것은 pf-r1 결과를 본 뒤의 사용자 결정이다(사전 등록 변경 기록 6). 문구 그대로 읽으면 세 run 모두 무효가 된다.
- **확장 공백의 대가**: CA 노드 추가(약 40~60초)와 파드 기동 동안 api 3~6개가 CPU(requests 대비) 135~150%로 버티며 응답 꼬리가 4~5초까지 늘었다. 폭증 시점을 알면 사전 확장(Git)이,
  모르면 HPA 하한을 올리거나 CA 여유 노드를 두는 비용과의 교환이다(미측정).
- **사람 판단 지연이 정책 위반을 만들었다**: pf-r1 켜기 PR은 CI 시점에는 기한(off-by)이 미래였지만 머지 시점에는 지나 있었다(#367로 갱신). 규칙 11은 CI 시점에만 검사한다
  (상시 검사·예약 워크플로는 두지 않기로 한 사용자 결정) — 머지 직전 기한 확인이 운영 절차에 필요하다.
- **web 선점의 대가**: 사전 확장 때 api가 web 노드를 차지하면 web이 다른 노드로 밀린다([[ADR-025]] 보충). 세 run 모두 web Ready 2를 확인했다.
- **범위**: 대기열 진입·대기·입장 제어 + 확장 정책이다. 좌석·주문·결제는 [[IMP-030]](입장자 100명 정합성)으로 따로 쓴다. Redis(`cache.t4g.micro`)·RDS는 고정 크기다.
- 판정 run 사이 구성: 같은 클러스터에서 연속 3회. run마다 노드 8대가 붙고 빠졌다(사전 확장 4→9로 +5, 폭증 6→9로 +3).

## 9. 배운 점 (면접 답변용 한 줄)
"오토스케일링이 된다"를 시연이 아니라 판정으로 만들려면, 사전 확장을 Git PR로 켜고 끄는 것까지 운영 절차 그대로 한 run 안에 넣고 축소·확장 단계마다 기준을 먼저 적어야 했다 —
그 과정에서 노드 하나가 web에 막혀 사전 확장이 8/9에서 멈추는 것, 축소로 지워진 파드의 감사 로그가 사라지는 것, 그리고 진입 창이 분 경계에 걸리면 진입이 무너지는 것(Redis 분 경계 지연과 겹침 — 인과 미확정)을 찾았다.
