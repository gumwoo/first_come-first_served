# IMP-032 · 자동 확장 정책의 노드-시간 효과 — 통합 판정 run의 실측 노드 곡선으로 "피크 용량 고정" 대비 계산

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-10
- 유형: 정량(계산) — 새 측정 없이 [[IMP-031]]의 실측 노드 수(20초 간격)를 시간으로 적분해 비교한다. **비용·절감 수치는 모두 계산값**이다
- 관련: [[ADR-025]](api 1100m·HPA 3~9·Git 사전 확장), [[IMP-031]](통합 판정 run), [[IMP-021]](CA 실측), `k8s/cluster-autoscaler/values.yaml`(`scale-down-unneeded-time: 10m`)
- 벤치 파일: 레포 밖 `artifacts/loadtest/20261007-platform/` — run별 `platform-timeline.log`(Ready 노드 20초 간격), `prescale-ready.txt`(켜기 머지 직후 노드 Ready, 15초 해상도),
  계산 스크립트 `nodehours.js`

## 1. 상황 (Context)
ADR-025 정책은 "오픈 순간만 Git으로 사전 확장(노드 9), 오픈 뒤는 HPA·CA가 부하에 맞춰 줄이고 늘린다"이다. IMP-031은 이 정책이 7축을 지키는지 판정했다.
이 문서는 같은 run에서 **정책이 노드를 얼마나 덜 썼는지**를 계산한다. 비교 대상은 사전 확장 없이 피크 용량(노드 9)을 그대로 유지하는 운영이다.

## 2. 문제 정의 + 분류
같은 부하·같은 판정 결과에서, 자동 확장 정책이 "피크 용량 고정" 대비 노드-시간을 얼마나 줄였고, 줄이지 못한 부분은 어디인가.
- 계층: 인프라 비용(노드 수 × 시간) — 노드 타입은 모두 m6i.large(2 vCPU)라 노드-시간이 곧 비용에 비례한다.

## 3. 측정 방법(계산 방법) — 새 측정 없음
- 노드 곡선(실측): 켜기 PR 머지 ~ 타임라인 시작은 `prescale-ready.txt`(15초 해상도), 이후 T0 + 50분까지는 `platform-timeline.log`의 Ready 노드(20초 간격).
  각 표본 값을 다음 표본까지 유지하는 계단 적분 → **정책 노드-시간**(계산, 실측 표본 기반).
- 비교: 같은 창(켜기 머지 ~ T0 + 50분) 내내 노드 9 → **고정 노드-시간**(계산).
- 구간: 오픈 전(T0 − 약 3분 ~ T0 + 60초), 인계·축소(~ T0 + 900초), 폭증(~ T0 + 1,380초), 폭증 뒤(~ T0 + 3,000초).
- "필요 노드"는 **가정**으로 api 수 + 1(web·시스템 몫 — 평시 실측 노드 4 = api 3 + 1)로 두고, Ready 노드가 이를 넘는 부분을 "초과 노드-시간"으로 센다.

## 4. 가설 (계산 전)
- 오픈 뒤 HPA가 줄이면 CA가 노드를 줄여 노드-시간이 줄어든다. 다만 폭증 구간에서 다시 9까지 늘고, CA 축소는 `scale-down-unneeded-time` 10분을 기다리므로
  절감폭은 시나리오의 폭증 길이와 CA 대기에 좌우된다(예측).

## 5. 결과 — run 3회(계산, 실측 노드 곡선 기반)
| 지표 | pf-r1 | pf-r2 | pf-r3 |
|----|----|----|----|
| 창(켜기 머지 ~ T0 + 50분) | 75.7분 | 64.7분 | 64.0분 |
| 정책 노드-시간 | 10.09 | 8.51 | 8.39 |
| 노드 9 고정 노드-시간 | 11.36 | 9.71 | 9.59 |
| 절감(고정 대비) | 11.2% | 12.3% | 12.6% |

- pf-r1은 켜기 PR의 기한(off-by) 갱신으로 사전 확장이 T0 전 23분 유지돼(다른 run은 약 12분) 창이 길다(IMP-031 §8).
- **구간별 노드-시간**(타임라인 구간, 계산): 오픈 전 0.56~0.61, 인계·축소 1.97~2.01, 폭증 1.08~1.11, 폭증 뒤 3.08~3.15.
- **초과 노드-시간**(필요 노드 가정 대비, 계산): 인계·축소 0.71~0.79, 폭증 0.02, 폭증 뒤 0.85~0.93 — run당 합 1.58~1.74로 정책 노드-시간의 약 16~21%.
- **어디서 남았나**: 폭증이 끝나고 HPA가 api를 3으로 줄인 시각(T0 + 1,706~1,727초)부터 노드가 4가 된 시각(T0 + 2,372~2,394초)까지 **약 11분**(666~677초, 실측 타임라인).
  CA 기본값 `scale-down-unneeded-time: 10m`(노드가 10분 동안 불필요해야 줄인다)과 맞는 지연이다(추론). 인계 직후 HPA가 9 → 3으로 줄 때도 노드는 T0 + 약 770초에 6으로 줄었다.

### 하루 단위 환산(계산, 가정 포함)
- 가정: 하루에 오픈 1회(위 곡선 그대로), 나머지 시간은 평시 노드 4(실측 — 세 run 모두 T0 + 50분에 Ready 4).
- 정책: 8.4 + 4 × (24 − 64/60) ≈ **100 노드-시간/일** · 피크 용량 상시 유지(노드 9 × 24): **216 노드-시간/일** → 약 **54% 적다**(계산).
- 이 환산은 오픈 빈도·평시 부하·폭증 유무에 크게 좌우된다. 위 run 표의 11~13%는 폭증까지 넣은 50분 시나리오 안의 값이고, 하루 54%는 평시가 길다는 가정의 값이다.

## 6. 조치
- 새 설정 변경 없음(이 문서는 계산). ADR-025 정책이 이미 운영 설정이다.

## 7. 결과 해석
- 자동 확장 정책은 같은 7축 판정을 통과하면서, 이 시나리오(오픈 + 폭증 + 축소, 64~76분)에서 노드-시간을 고정 9 대비 11~13% 덜 썼다(계산).
- 남은 초과의 절반 이상(0.85~0.93 노드-시간/run)은 폭증 뒤 CA 축소 대기(약 11분)에서 나온다.

## 8. 트레이드오프 / 한계 / 다음 개선
- **계산이다**: 노드 수는 실측이지만 노드-시간·절감률·하루 환산은 계산값이다. 청구서(CUR)로 확인한 금액이 아니다.
  금액은 노드-시간 × m6i.large 서울 온디맨드 단가로 바로 환산된다(노드 타입이 하나라 비율은 금액에서도 같다).
- **"필요 노드 = api + 1"은 가정**이다. web·시스템 파드 배치에 따라 실제 필요 노드는 다를 수 있다.
- **다음 개선(검증 필요)**: CA `scale-down-unneeded-time`을 10분 → 5분으로 줄이면 폭증 뒤 초과(약 0.9 노드-시간/run)의 절반가량을 줄일 수 있다(예측).
  대가는 짧은 부하 변동에 노드가 빠졌다 다시 붙는 흔들림과 CA 노드 추가 대기(실측 110초, IMP-021)다. 측정 프로파일은 기본값을 유지하기로 했다(values.yaml 주석).
- 노드 타입·스팟·Graviton 비교처럼 "같은 품질에서 더 싼 구성"은 클러스터를 다시 올려 재야 한다(이번 범위 밖).

## 9. 배운 점 (면접 답변용 한 줄)
"오토스케일링으로 비용을 줄였다"를 감으로 말하지 않고, 판정 run의 실측 노드 곡선을 시간으로 적분해 고정 용량 대비 노드-시간을 계산했다 —
그리고 남은 낭비가 CA 축소 대기(약 11분)에 몰려 있다는 것까지 찾아 다음 조정 후보와 그 대가를 함께 적었다.
