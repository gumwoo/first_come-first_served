# IMP-015 · 롤링 배포 무중단, preStop 25s에서 6,001건 중 5xx 0건

- 슬라이스: S09(EKS 배포), 인프라
- 날짜: 2026-08-08
- 유형: 정량(가용성 실측)
- 관련: [[TS-035]](502 조건의 원인을 규명한 후속), [[ADR-012]](3AZ 인프라), `k8s/base/api-deployment.yaml`, [[TS-016]]·[[TS-017]](같은 배포에서 나온 결함)
- 상태: **종결** — §5의 미검증 조건은 2026-08-25에 재현하고 주요 원인을 규명해 수정 효과까지 확인했다([[TS-035]], §9)

## 1. 배경

매니페스트에 무중단을 위한 값들을 짝으로 맞춰 두었다. PR #179에서는 `preStop` 5초가 등록 해제 구간을
덮는지를 롤링 중 무중단 실측으로 확인하기로 했다. 이 문서는 그 실측 기록이다.

## 2. 검증 대상: 짝을 맞춘 값들

| 설정 | 의도 |
|---|---|
| `maxUnavailable: 0` / `maxSurge: 1` | 새 Pod가 Ready된 뒤에만 옛 Pod를 뺀다 |
| `preStop: sleep 5` | SIGTERM 전에 멈춰 ALB 등록 해제가 시작될 시간을 번다 |
| `deregistration_delay = 10s` | 등록 해제 중 기존 연결을 드레이닝 |
| `terminationGracePeriodSeconds: 30`(web) | 위 둘보다 커야 SIGKILL이 앞지르지 않는다 |
| readiness `periodSeconds: 5`, `failureThreshold: 3` | 준비되지 않은 Pod로 트래픽이 가지 않게 |

## 3. 측정 방법

```
대상   https://flow-ticket.com/api/events/1678/seats   (좌석 100석, DB를 실제로 타는 조회)
부하   병렬 6워커, 약 25 req/s
행위   부하 중 kubectl rollout restart deployment/flowticket-web
기록   요청별 (시각, 워커, HTTP 상태코드)
```

DB를 실제로 타는 요청으로 확인하기 위해 좌석 조회를 대상으로 했다.

## 4. 결과

```
총 요청   3,600
200       3,600  (100%)
5xx           0
rollout   23:22:54 → 23:23:00  (web 파드 2개 교체, 새 ReplicaSet 확인)
```

롤링 발생은 ReplicaSet 이력으로 확인했다(새 ReplicaSet 생성, 파드 2개 교체). `rollout status`가
6초 만에 끝나 이력을 따로 확인했다.

## 5. 검증 범위

직전에 다른 조건으로 배포했을 때는 502가 1건 났다.

| | 502가 난 배포 | 이 측정 |
|---|---|---|
| 방식 | `kubectl apply`, 이미지 태그 변경 | `rollout restart`, 이미지 동일 |
| 범위 | web + api 동시 | web 단독 |
| 부하 | 2.5 req/s (168건) | 25 req/s (3,600건) |
| 결과 | 502 × 1 | 0 |

이 시점에 측정된 조건은 두 가지다.
- 이미지 동일 + web 단독 롤링: 25 req/s에서 3,600건 5xx 0건
- 이미지 변경 + web·api 동시 롤링: 168건 중 1건 502

502 조건의 원인은 §8에서 재현 계획을 세우고 §9에서 규명했다.

## 6. 측정 조건

- 측정 지점: 로컬 PC → ALB(인터넷 경유).
- 부하: 25 req/s. 선착순 피크 부하는 S10 부하테스트에서 다룬다.
- 범위: web 단독 롤링, 1회 측정. api 롤링은 별도 측정 대상이다.

## 8. 후속 과제: 502 조건 재현

§5의 502 조건(이미지 태그 변경 + web·api 동시 롤링)을 §3과 같은 부하(25 req/s)에서 재현한다.
직전 관측은 2.5 req/s·168건이었으므로 표본을 §3 수준으로 키운다.

**가설**: 이미지가 바뀌면 노드가 이미지를 pull 하느라 Ready까지 더 걸리고, api까지 함께 롤링되면
web이 프록시하는 대상도 동시에 교체된다. 두 요인 중 어느 쪽이 502를 만드는지 가른다.

**판정 기준**
- 재현되면 두 요인을 분리 측정(이미지 변경 + web 단독 / 이미지 동일 + web·api 동시)해 원인을 좁힌다.
- 재현되지 않으면 표본 크기 문제로 기록하고 원인을 단정하지 않는다. 168건 중 1건만으로는
  원인을 단정할 근거가 되지 않는다.

## 9. 후속 결과 (2026-08-25)

§8의 재현 실험을 실행했다. 상세는 [[TS-035]].

| 실험 | web preStop | 행위 | 범위 | 요청 | 실패 |
|---|---|---|---|---|---|
| 재현 | 5s | 이미지 변경 | web + api | 6,001 | 16 |
| A | 5s | 이미지 변경 | web 단독 | 5,964 | 64 |
| C | 5s | restart | web 단독 | 6,001 | 13 |
| E | 25s | restart | web 단독 | 6,001 | 0 |
| F | 25s | 이미지 변경 | web + api | 6,001 | 0 |

이미지 변경과 동시 롤링은 원인에서 제외됐다(실험 C는 둘 다 없이도 실패). 원인은 `preStop: sleep 5`가
등록 해제가 ALB에 반영되는 시간을 덮지 못한 것이다. 파드 Terminating → EndpointSlice 제거 →
LB 컨트롤러 조정 → ALB 타깃 `deregistering` 전환이 끝나기 전에 컨테이너가 먼저 종료됐다.
그 구간에서 ALB는 그 IP를 아직 정상 타깃으로 보고 요청을 보냈다(`target-type: ip`).
네 번의 측정에서 `Target_5XX`가 계속 0이었던 것(앱은 5xx를 낸 적이 없다)이 이를 뒷받침한다.

`deregistration_delay`(10s)는 타깃이 `deregistering`이 된 뒤 진행 중인 연결을 마무리하는
드레이닝 시간이고, 그 동안 ALB는 새 요청을 보내지 않는다. 따라서 이 값을 줄여서는 해결되지 않는다.
상세는 [[TS-035]] §4.

`k8s/base/web-deployment.yaml`의 `preStop`을 25s(+ `grace` 60s)로 올리자
실제 배포 경로 조건(이미지 변경 + web·api 동시)에서 6,001건 전량 2xx가 됐다.

판정 근거: 수정 전 4회 실행(재현·A·C·D)은 모두 실패했고, 수정 후 2회(E·F)는 모두 실패 0건이다.
결함은 요청 단위로는 간헐적이지만 실행 단위로는 4회 모두 재현됐으므로, 수정 후 0건을 우연으로 보기는 어렵다.

측정 조건: web 티어 롤링, 25 rps. 선착순 피크 부하와 api 단독 롤링은 이 실험 범위 밖이다.

### §3·§4 수치의 위치

§3의 조건(restart · web 단독 · 25 rps)을 2026-08-25에 다시 재면 13건이 실패한다(실험 C).
따라서 이 문서에서 무중단의 근거는 §9의 E·F이고, §4의 수치는 당시 측정 기록으로 남긴다.
