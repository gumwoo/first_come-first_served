# IMP-013 · CI 백엔드 잡 23.5분 → 9.35분 — 통합테스트 컨테이너·컨텍스트 공유

- 슬라이스: 인프라(하네스/CI) — 기능 슬라이스 아님
- 날짜: 2026-08-03
- 유형: 정량(CI 잡 시간 실측) — 개발 피드백 속도
- 관련 커밋/PR: PR #147
- 벤치 파일: [`benchmarks/ci-backend-job-before.json`](../../benchmarks/ci-backend-job-before.json)
  → [`benchmarks/ci-backend-job-after.json`](../../benchmarks/ci-backend-job-after.json)
- 관련: [docs/HARNESS.md](../HARNESS.md), [[ADR-008]]·[[ADR-010]](Kafka 테스트 구조)

> 흐름: 문제 정의 → 증상(수치) → 가설 → 도구로 검증 → 해결 → 재측정 → 한계.

## 1. 상황
PR마다 CI가 **약 23분**이 걸렸다. 검증 체계(계약·정적 가드·메타테스트·통합테스트·풀스택 E2E)를 줄이지 않고
피드백 시간을 줄이는 것이 목표였다.

## 2. 문제 정의 + 분류
- 계층 분류: **개발 파이프라인 성능**(제품 성능 아님).
- 흔한 진단은 "중복 설치·중복 빌드·Playwright 설치·E2E 직렬화"였다. 실제로 **중복은 존재했다**
  (npm 설치 4회, 프론트 build 2회, 백엔드 build 2회, 매 실행 Playwright·psql 설치, paths 필터 없음).
- 그러나 **어느 것이 느린지**는 별도 문제였다.

## 3. 증상 (측정된 증거)
잡별 소요시간을 API로 실측했다. 잡이 병렬이므로 **전체 CI 시간 = 가장 느린 잡**이다.

| Job | 시간(최근 3런) |
|---|---|
| **백엔드** | **23.07 / 23.92 / 23.42분** |
| E2E | 3.9분 |
| 프론트 | 0.9분 |
| 메타테스트 | **0.22분(13초)** |

→ **23분은 곧 백엔드 잡**이다. E2E·프론트·메타를 아무리 최적화해도 전체 시간은 그대로다.
(메타테스트 조건부 실행은 13초 절감, E2E artifact 재사용은 임계경로 밖이라 **전체 0초**.)

## 4. 가설 (검증 전)
백엔드 23분이 **테스트가 기다리는 시간**인지 **인프라를 띄우는 시간**인지 갈랐다.
- 테스트 내 **고정 `sleep` 합계 = 15.5초**, Awaitility는 조건 충족 시 조기 종료.
- 컴파일·테스트 로직을 빼면 **약 1,150~1,250초, 클래스당 45초**가 남는다.
→ 가설: **클래스마다 인프라를 새로 띄우는 비용**이 대부분이다.

## 5. 검증 (도구로 확인 → 확정 원인)
- `@SpringBootTest` **26개 전부가 자기 `@Container`로** Postgres/Redis(+Kafka)를 선언하고 있었다.
  `@Container`는 **클래스 단위 수명**이라 개선 전에는 26세트가 뜨고 내려갔다.
- 클래스당 45초는 `Postgres(~5s) + Redis(~2s) + Spring 컨텍스트(JPA·Flyway·Redis·Kafka·Security·QueryDSL,
  ~20s) + Kafka(4개 클래스, ~25s)`로 설명된다 → 원인 확정.

## 6. 해결 + 재측정
1. **컨테이너 싱글톤화** — `@Container` 대신 static 초기화로 기동해 **JVM 수명 동안 공유**.
   최종 상태는 **비-Kafka 22개가 공통 1세트**(Postgres·Redis)를 쓰고 **Kafka 4개는 독립 유지** —
   전체가 한 세트로 합쳐진 것은 아니다(§7-3).
2. **컨텍스트 재사용** — 컨테이너만 공유하면 절반만 빨라진다. Spring 컨텍스트 캐시 키에는
   `@DynamicPropertySource` **메서드 집합**이 들어가므로(런타임 값이 아니라), 클래스마다 자기 메서드를
   선언하면 값이 같아도 새 컨텍스트가 뜬다 → **공통 베이스에서 상속**시켜 같은 커스터마이저를 공유.
3. **튜닝 값은 `@TestPropertySource`로** — 동적 프로퍼티가 우선순위가 더 높아 베이스에 넣으면 하위가
   값을 덮지 못한다. 상속 병합 + 하위 우선인 `@TestPropertySource`로 두고 예외 클래스만 재선언.
4. **커넥션 풀 축소**(`hikari.maximum-pool-size=4`) — 캐시된 컨텍스트가 각자 풀을 들고 살아 있어
   공유 DB의 최대 커넥션을 넘겼다.
5. **Kafka 4개는 공유 제외** — 아래 §7 참조.

- after:
  | Job | 시간 |
  |---|---|
  | **백엔드** | **9.35분** |
  | E2E | 3.77분 |
  | 프론트 | 0.9분 |
  | 메타테스트 | 0.18분 |
  | **전체 CI** | **9.4분** |

**백엔드 23.47분 → 9.35분(-60%), 전체 CI 23.5분 → 9.4분.** 검증 범위는 하나도 줄이지 않았다
(테스트 수·계약·메타테스트·E2E 전부 그대로).

## 7. 공유로 드러난 숨은 결합 3종 (회고)
컨테이너를 나눠 쓰던 시절엔 **격리가 결합을 가려주고 있었다.** 공유로 바꾸자 CI가 35건 실패했고,
원인은 전부 "원래 있었지만 보이지 않던" 문제였다.

1. **테이블 간 FK 결합** — 클래스별 `deleteAll()`은 JPA 지연 플러시 탓에 다른 테스트가 남긴 자식 행
   (seats·orders)과 충돌해 **엉뚱한 줄에서** 터졌다. → 베이스 `@BeforeEach`에서 `TRUNCATE ... CASCADE`
   일괄 초기화(+Redis flush). 단 **마이그레이션이 시드하는 테이블**(`alert_settings`)은 제외 —
   지우면 기본값이 사라져 시드 의존 테스트가 깨진다.
2. **커넥션 고갈** — 캐시된 컨텍스트가 동시에 살아 있어 풀이 누적된다. 컨텍스트 캐시의 대가다.
3. **Kafka 컨슈머 그룹 충돌** — 캐시된 여러 컨텍스트의 컨슈머가 같은 그룹이라 **서로 메시지를 가져갔다.**
   그룹을 클래스별로 격리하니 이번엔 새 그룹이 `earliest`부터 **다른 클래스가 남긴 메시지를 다시 소비**했다.
   → **Kafka 테스트 4개는 공유 대상에서 제외**(각자 브로커). 절감의 대부분은 나머지 22개에서 나오므로
   추적 비용 대비 이득이 없다고 판단.

> 교훈: **"컨테이너 수명은 길게, 데이터 상태는 매번 초기화."** 그리고 공유가 드러낸 실패는 새 버그가
> 아니라 **원래 있던 결합**이므로, 가리지 말고 고치는 편이 맞다.

## 8. 한계
- **컨텍스트를 1개로 줄이진 못한다.** `@MockBean`/`@SpyBean` 조합(7개)·`webEnvironment=RANDOM_PORT`(5개)·
  프로퍼티 예외(4개)가 캐시 키를 가르므로 **6~8개**가 현실적 하한이다.
- **Kafka 4개는 여전히 각자 컨테이너**를 띄운다(토픽 분리까지 하면 더 줄지만 ROI가 낮다고 판단).
- **병렬 포크와 함께 설계해야 한다.** `maxParallelForks`를 올리면 포크마다 싱글톤이 따로 떠서 공유가 깨진다.
- **여전히 임계경로는 백엔드(9.35분)** 다. 코드가 바뀌는 PR에서는 이 시간을 더 줄이기 어렵다 —
  이 프로젝트의 논지가 동시성·정합성이라 통합테스트를 빼는 건 안전망을 깎는 일이다.
  대신 **불필요한 실행을 없애는 쪽**을 택했다:
  - **paths 필터 적용(후속 PR)** — 변경 영역에 해당하는 잡만 실행. 문서만 고친 PR은 백엔드·프론트·E2E가
    모두 건너뛰어져 **13초**로 끝난다. main push는 항상 전체 검증(회귀 안전망).
  - **테스트 태스크 분리(`test`/`integrationTest`)는 보류.** 백엔드 테스트의 대부분이 통합테스트라
    분리해도 PR에서 통합을 빼지 않는 한 절감이 작고, 빼면 이 프로젝트가 지키려는 불변식(초과판매·멱등·
    상태 전이)의 회귀를 PR에서 못 잡는다. 테스트 수가 더 늘어 9분이 부담이 될 때 재검토.
  - E2E artifact 재사용·Playwright 이미지는 임계경로 밖이라 전체 시간엔 영향이 없고 러너 비용만 준다.
- 측정은 **GitHub Actions 러너 기준**이라 러너 성능·캐시 적중에 따라 분 단위 변동이 있다.
