- 날짜: 2026-10-26(시뮬레이션 `artifacts/loadtest/kwok-20261020/`, 로컬 `artifacts/peace-coloc/`, 모두 레포 밖)

## 1. 상황 (Context)
평시 노드 5대는 api 3개와 대기열 2개가 모두 1100m라 Pod 하나가 노드 하나를 쓰는 배치다. [[IMP-048]]에서 예매 api만 낮추는 것으로는 평시가 줄지 않거나 오픈 순간 동거가 생겼다.
평시에는 열린 대기열이 없어(`traffic-profile.md` §2) 대기열 Pod도 평시에 1100m가 필요 없다. 그래서 대기열 Pod를 평시 모양(200m·api 회피 preferred)으로 두고, 오픈 사전 확장 PR에서 피크 모양(1100m·api 회피 required, 지금 측정한 구성)으로 바꾸는 운영을 검토했다.

## 2. 문제 정의 + 분류
- 계층: 스케줄링·자동 확장(배치와 노드 수) + CPU 공유(평시 동거).
- 질문 1(시뮬레이션): 평시 → 사전 확장 → 피크 중 CA 축소 → 되돌림 → CA 축소 한 바퀴에서 평시 3대, 사전 확장 9대 이하, 피크 동거 0, 되돌린 뒤 3대가 되는가. 사전 확장 PR의 적용 순서와 무관하게 되는가.
- 질문 2(로컬): 평시 부하에서 놀고 있는 대기열 Pod가 예매 api와 같은 코어를 쓰면 평시 조회·예매 묶음이 느려지는가.

- C:
  - 피크 중 축소 흉내가 6회 모두 api 노드 하나(사용률 0.43~0.44, flowticket Pod는 api만 3회·api와 web 3회)를 비웠다. 그 api는 다른 api 노드로 옮겨졌다.
  - 되돌린 뒤 4대 2회는 그 제거로 해당 AZ에 노드 1대만 남아(AZ당 최소 1) 더 줄지 않은 경우다.
- C-s:
  - api에 hostname 분산(DoNotSchedule)을 더하자 피크 중 축소가 노드를 하나도 지우지 못했다. 대기열 노드는 api 0개인 도메인이라, api를 옮기면 skew 2가 된다.
  - 되돌린 뒤 4대 2회의 남은 노드는 둘 다 평시 대기열 2개가 함께 놓인 노드였다. 되돌림 롤링 때 새 평시 대기열이 비어 가는 노드에 놓였다.
  - 그 노드를 비우려면 대기열 둘을 함께 빼야 해 PDB(minAvailable 1)에 막혔다. 1회는 사용률 0.48로 축소 후보였는데 PDB에 막혔고, 1회는 web까지 들어와 0.52로 후보에서 빠졌다.
- C-s2: 대기열 hostname 분산(DoNotSchedule)을 더해 대기열이 노드마다 하나가 되자, 6회 모두 되돌린 뒤 3대였다.
- C-s2d:
  - 하한만 2로 내린 단계에서는 피크 대기열 2개가 각자 노드를 써서 5대(api 노드 3 + 대기열 노드 2)에 머물렀다. 동거는 0이었다.
  - 대기열이 빈 뒤 모양을 바꾸자 3대가 됐다. 대기열이 비기 전까지는 5대 비용이 남는다는 뜻이다.
- 세 순서 모두 사전 확장 정체가 없었다. [[IMP-039]]의 동시 전환 정체는 롤링 대상(api 1100m)이 10번째 노드를 요구해서 생겼다. 여기서는 옛 평시 대기열이 api 노드에 얹혀 있어 노드를 따로 쓰지 않는다.
- 적용 매니페스트의 렌더링(`kubectl kustomize`, queue-peak 끔·켬)이 C-s2·C-s2d 시나리오의 api·대기열 requests·affinity·분산과 같은 것을 확인했다. 그 렌더링으로 시뮬레이션을 다시 돌리지는 않았다.

## 5. 조치

- 하네스:
  - k8s ⑩-b·⑩-d와 규칙 11을 바꾸고 ⑩-e(예매 api 노드 단위 분산)를 더한다.

- 절감(계산, 평시가 하루 종일이라는 가정, 노드 EC2만): (5 − 3) × 24 × 30 × $0.118/h([[IMP-032]] 단가) ≈ 월 $170.

  - 2026-10-27에 확인했다([[IMP-050]]): 평시 3 → 사전 확장 9(6분 26초) → 5 → 3을 실제 CA로 확인. 평시 동거는 EKS에서 "악화 있음"(노드 차이와 섞임, V2b 1회에서 예매 p95의 느린 쪽이 대기열을 따라감, 조회는 방향 섞임).

같은 Deployment는 requests가 같다는 제약을 "오픈 전에 대기열 모양을 바꾸는 PR"로 풀고, 실제 스케줄러로 한 바퀴를 흉내 내 api 노드가 피크 중에 합쳐지는 것과 PDB가 축소를 막는 것을 찾아 분산 규칙 두 개로 막았다. 평시 동거는 사전 등록 판정으로 확인했고, 평시 노드를 5대에서 3대로 줄였다(월 약 $170, 계산).
