# 조회 캐시 실험 계획 — 인과 분리 → 비용 비중 → 캐시 효과

- 상태: **계획(미측정)** — 스크립트·프로토콜만 준비됐다. 숫자는 클러스터에서만 나온다.
- 선행: [phase1-saturation](../../benchmarks/phase1-saturation/README.md) (2026-08-11, knee 600~650 rps)
- 관련: [loadtest-plan.md](loadtest-plan.md), [[TS-021]](Hikari 풀 축소 판단)

## 0. 이 실험이 답하려는 것

Phase 1이 **명시적으로 미확정으로 남긴 질문**이 출발점이다.

> ⚠️ 인과 방향은 확정하지 않았다. 노드 CPU가 90%라 스레드가 느려져 커넥션을 오래 잡은 것인지,
> 커넥션이 부족해 요청이 밀려 CPU를 쓴 것인지 이 자료로는 갈리지 않는다.

| # | 질문 | 없으면 생기는 문제 |
|---|---|---|
| ① | 650 붕괴에 **CPU와 커넥션 중 어느 쪽 민감도가 큰가** | 캐시가 맞는 처방인지조차 모른다 |
| ② | 엔드포인트별 **비용 비중** | "X% 빨라졌다"의 상한을 설명 못 한다 |
| ③ | 캐시 전후 **knee 이동** | ①②가 없으면 왜 그만큼인지 못 말한다 |

**순서를 지켜야 한다.** ③만 하면 숫자는 나오지만 해석이 안 된다.

### 이 실험이 답하지 **않는** 것 — 범위를 먼저 못 박는다

"10만 명이 몰려도 버티는가"는 이 실험으로 답할 수 없다. **조회(browsing)는 그 상황에서
지배적인 부하가 아니기 때문이다.**

대기 화면은 SSE와 **2초 폴링을 함께** 돌린다(`apps/web/src/features/queue/hooks/useQueue.ts`
— 폴링은 SSE 재연결 공백을 메우는 의도된 설계다). 그러면 대기자 수에 비례해 상태 조회가 붙는다.

| 대기 인원 | `/queue/status` 도착률 (2초 폴링) |
|---|---|
| 10,000 | 5,000 rps |
| 100,000 | **50,000 rps** |

⚠️ **이 표는 폴링 주기로 나눈 산수이지 측정이 아니다.** 실제로 그만한 동시 대기를 만들어
본 적이 없다.

즉 10만 규모에서 부하의 크기 순서는 **① 상태 폴링 → ② SSE 커넥션 유지 → ③ 조회 →
④ 좌석·결제**로 추정되고, **이 실험이 다루는 것은 ③뿐이다.** 좌석·결제(④)가 가장 작은 이유는
대기열이 정원만큼만 통과시키기 때문이고, 그건 이미 스파이크 측정에서 확인했다.

따라서 이 실험 결과로 **"우리 서비스는 N명을 감당한다"고 말하지 않는다.** 말할 수 있는 것은
"조회 경로의 비용 구조와 캐시가 그중 어디에 듣는지"까지다. ①②는 별도 과제다.

## 1. 재현해야 하는 조건 (Phase 1과 동일)

비교값이 되려면 **환경이 같아야 한다.** 다르면 캐시 효과인지 환경 차이인지 못 가른다.

```
api HPA 3~7 / web HPA 2~4, requests 각 300m
노드 t3.large × 3 (allocatable 합 5.79 core)
Hikari 풀 = 파드당 5 (TS-021 판단)
k6는 클러스터 **밖**에서 실행 (TS-021 §7 자원 경합 회피)
```

⚠️ **k6를 클러스터 밖에서 돌리는 것은 의도된 선택이지 한계가 아니다.** 다만 클라이언트 p95에는
RTT·TLS·ALB·Next proxy가 포함되므로, **판단은 서버 p95와 서버 지표로 한다.**
(Phase 1 근거: 600 구간에서 클라 159ms vs 서버 0.05s로 경로 오버헤드는 작고 일정했다.
650에서 서버 p95가 0.05s→5.58s로 뛴 것은 경로로 설명되지 않는다.)

## 2. 고정 절차

콜드 스타트가 결과를 오염시킨 전례가 있어 Phase 1에서 고정한 절차를 그대로 쓴다.

```
각 측정마다:
  1) 워밍업  read-load-rate.js  RATE=300  RUN_FOR=45s   ← HPA를 올려 시작 조건 통일
  2) 측정    (해당 스크립트)     RUN_FOR=90s
  3) 서버 지표는 측정 구간(90초)의 값으로 읽는다
```

워밍업을 **별도 실행**으로 두는 이유: 같은 실행에 넣으면 k6 요약(p95·실패율)에 워밍업이 섞인다.

## 3. 단계별 설계

### 0단계 — 엔드포인트별 비용 (② 답)

동일 도착률에서 하나씩 떼어 잰다. **포화 아래**에서 재야 큐잉이 비용을 부풀리지 않는다.

#### 도착률은 pilot으로 정한다 — 400을 그냥 못 쓴다

⚠️ 초안은 400 rps를 바로 고정했는데 **근거가 약했다.** "혼합 부하가 550까지 통과했다"는
사실은 **혼합**에 대한 것이다. 단일 엔드포인트가 훨씬 비싸면 400에서도 이미 큐잉이 생긴다
(seats는 좌석 100행 + 등급 집계라 list/detail보다 비쌀 여지가 있다).

```
엔드포인트마다:
  1) pilot   RATE=200  RUN_FOR=30s
       → p95 / Hikari pending / dropped 이상 없으면
  2) 본측정  RATE=400  RUN_FOR=90s
       → 400에서 이상 징후가 보이면 그 엔드포인트는 낮춘 도착률로 재고 **그 값을 기록한다**
```

도착률이 엔드포인트마다 달라져도 된다 — 아래 정규화가 그걸 흡수한다. **중요한 것은
모든 측정이 포화 아래에서 나오는 것**이지 도착률이 같은 것이 아니다.

```bash
# pilot (엔드포인트마다 선행)
k6 run -e K6_BASE_URL=<base> -e EP=seats -e RATE=200 -e RUN_FOR=30s infra/k6/read-load-endpoint.js
# 본측정
k6 run -e K6_BASE_URL=<base> -e EP=seats  -e RATE=400 -e RUN_FOR=90s infra/k6/read-load-endpoint.js
k6 run -e K6_BASE_URL=<base> -e EP=list   -e RATE=400 -e RUN_FOR=90s infra/k6/read-load-endpoint.js
k6 run -e K6_BASE_URL=<base> -e EP=detail -e RATE=400 -e RUN_FOR=90s infra/k6/read-load-endpoint.js
```

#### 정규화 — idle을 빼야 엔드포인트 비용이 된다

읽을 값: **api CPU(core), Hikari active/pending, DB 쿼리량, 서버 p95.**

```
요청당 증분 CPU = (부하 중 api CPU − idle api CPU) ÷ 실제 rps
```

⚠️ **idle을 빼지 않으면 안 된다.** 스케줄러, 헬스체크, Kafka 컨슈머 폴링 같은 **고정 비용**이
엔드포인트 비용에 섞여 들어간다. 부하가 낮을수록 그 왜곡이 커진다.

그래서 **측정 전에 무부하 구간의 api CPU를 먼저 기록**한다(워밍업 후 부하 정지 30초).

### 1단계 — 자원 민감도 개입 실험 (① 접근)

650 구간에서 자원을 한쪽씩 풀어 **어느 쪽 민감도가 큰지** 본다.

⚠️ **"원인 확정 실험"이 아니다.** 초안에서는 아래 표를 "CPU가 원인이면 / 커넥션이 원인이면"으로
단정했는데, 현실에서 그렇게 깔끔히 갈리지 않는다.

- Hikari 풀을 늘리면 DB 동시성이 올라 **CPU 사용도 함께 변한다**
- 노드를 늘리면 CPU만 느는 게 아니라 **스케줄링 여유·파드 배치·HPA 동작이 같이 변한다**

즉 두 변수는 독립이 아니다. 이 실험이 주는 것은 **"어느 자원을 풀었을 때 knee가 더 움직이는가"**
라는 민감도이지, 인과의 확정이 아니다. 결과를 쓸 때 그 범위를 넘지 않는다.

| 실험 | 푸는 자원 | 읽는 값 |
|---|---|---|
| 1-A | Hikari 풀 5 → 10 (파드당) | knee 이동폭, pending 변화, **api CPU 변화**(같이 변하는지) |
| 1-B | 노드 3 → 4대 | knee 이동폭, 노드 CPU 여유, **pending 변화**(같이 변하는지) |

**knee가 더 크게 움직인 쪽이 더 지배적인 제약**이라고만 말한다.
둘 다 비슷하게 움직이면 **서로를 악화시키는 구조**라는 것이 답이다.

#### ⚠️ 1-A는 DB 쪽에 새 병목을 만들 수 있다 — 실행 전 확인

RDS는 `db.t4g.micro`다(terraform 모듈 기본값, 환경에서 오버라이드하지 않음. 커스텀 parameter
group도 없어 기본 공식이 적용된다).

| 항목 | 값 | 근거 |
|---|---|---|
| max_connections | 약 112 | `LEAST(DBInstanceClassMemory/9531392, 5000)` **계산값** |
| 인스턴스 RAM | 1 GB | `db.t4g.micro` 사양 |
| 1-A의 커넥션 수 | `api 7파드 × 10 = 70` | maxReplicas 기준 |

⚠️ **max_connections는 공식으로 계산한 값이고 실제 인스턴스에서 읽지 않았다.** `apply` 후
`show max_connections`로 먼저 확인한다.

⚠️ **숫자상 70 < 112로 통과하지만, 그게 안전하다는 뜻은 아니다.** PostgreSQL은 커넥션마다
백엔드 프로세스를 띄우고 각각 수 MB를 쓴다. **RAM 1GB에 70커넥션은 메모리 압박을 만들 수
있고**, 그러면 1-A는 "커넥션을 풀었더니 DB가 새 병목이 된" 측정이 되어 **해석이 오염된다.**

대응: 1-A 실행 중 **DB 쪽 지표(FreeableMemory·CPU·커넥션 수)를 함께 기록**한다. DB가
말라가는 징후가 보이면 그 측정은 "풀 크기 효과"가 아니라 **"DB 인스턴스 한계"** 로 기록한다.
필요하면 인스턴스 클래스를 올린 뒤 다시 재되, 그때는 **Phase 1과 환경이 달라지므로**
knee 절대값을 Phase 1과 직접 비교하지 않는다.

### 2단계 — 캐시 AS-IS/TO-BE (③ 답)

0단계에서 비중이 큰 엔드포인트부터 캐시한다(무엇을 캐시할지는 **0단계 결과가 정한다**).

| 시나리오 | 스크립트 | 목적 |
|---|---|---|
| A. 기존 혼합 50:30:20 | `read-load-rate.js` | Phase 1과 직접 비교 가능한 유일한 값 |
| B. browsing-only | `read-load-endpoint.js EP=browsing` | 캐시가 가장 잘 듣는 상한 |
| C. seat-map-only | `read-load-endpoint.js EP=seats` | 실시간성이 요구되는 경로의 하한 |

각 시나리오에서 **도착률을 550 → 600 → 650 → 700**으로 올려 knee 이동을 본다(Phase 1과 동일 격자).

`EP=browsing`은 list:detail을 **60:40**으로 섞는다 — **A의 비좌석 부분과 동일한 list:detail
상대비율**(30:20)을 유지한다는 뜻이다. 임의로 50:50을 쓰면 A의 browsing 부분과 다른
워크로드가 되어 "캐시가 browsing에 얼마나 들었나"를 A와 이어 붙일 수 없다.

⚠️ **A와 B는 apples-to-apples가 아니다.** A는 seats 50%를 포함한 전체 혼합이고 B는 그것을
뺀 부분집합이다. B의 knee가 A보다 높게 나오는 것은 당연하며, **그 차이를 캐시 효과로 읽으면
안 된다.** B는 "좌석맵을 뺐을 때 어디까지 가는가"라는 상한을 보는 것이고, 캐시 효과는
**각 시나리오의 AS-IS와 TO-BE를 짝지어** 읽는다.

## 4. 수집 지표 · 쿼리

클러스터가 떠 있는 시간이 곧 비용이므로 **쿼리를 미리 확정해 둔다.**

| 지표 | 출처 |
|---|---|
| 컨테이너 CPU(core) | `container_cpu_usage_seconds_total` — Phase 1과 같은 것을 써야 비교된다 |
| Hikari active/pending | Micrometer `hikaricp_connections_active` / `hikaricp_connections_pending` |
| 서버 p95 | 서버 측 HTTP 지표(Grafana 기존 패널) |
| 클라 rps·실패율·p95 | k6 요약 JSON |

⚠️ **`container_cpu_usage_seconds_total`(cgroup 합)과 `kubectl top nodes`(노드 전체)는 재는
대상이 다르다.** Phase 1에서 5.23 core vs 6.00 core로 갈렸고 차이 0.77이 시스템 몫이다.
**표에 섞어 적지 않는다.**

⚠️ node-exporter는 Phase 1 시점에 **3대 중 1대만 수집**되고 있었다. 노드 CPU를 교차 확인하려면
먼저 이것부터 확인한다.

## 4-1. 2단계에서 반드시 함께 볼 것 — 만료 버스트

실험용 캐시에는 **single-flight/lock이 없다.** TTL이 짧고 도착률이 높으면 키 만료 순간
여러 요청이 동시에 miss를 보고 전부 DB로 간다(cache stampede).

```
평소 cache hit → TTL 만료 → 수십~수백 요청이 동시 DB 조회 → pending·latency 스파이크
```

**평균 CPU만 보면 이 비용이 안 보인다.** 그래서 TO-BE에서는 아래를 함께 본다.

| 지표 | 버스트를 잡는가 |
|---|---|
| `hikaricp_connections_pending`(게이지) | ❌ **스크레이프 30초** — TTL 2초 버스트는 샘플 사이로 빠진다 |
| `http_server_requests_seconds_bucket`(히스토그램) | ✅ 누적이라 **모든 요청이 반영**된다 → p99가 드러낸다 |
| `hikaricp_connections_acquire_seconds_max` | ✅ 커넥션 대기 피크 |

⚠️ **게이지로 "pending 0"을 확인해도 버스트가 없었다는 뜻이 아니다.** 30초 간격 샘플이
2초 주기 버스트를 놓칠 수 있다. 판정은 히스토그램(p99)과 acquire max로 한다.

## 4-2. 캐시 hit도 트랜잭션 프록시를 통과한다

`SeatService`가 클래스 레벨 `@Transactional(readOnly = true)`이라 **캐시 hit이어도 트랜잭션
진입 비용이 남는다.** 따라서 "캐시 = DB 경로 완전 회피"로 해석하면 안 되고, TO-BE 개선폭이
이론 상한에 못 미치는 이유의 후보다.

⚠️ 실제로 커넥션까지 빌리는지는 **확인하지 않았다.** TO-BE에서 `hikaricp_connections_active`가
캐시 hit 구간에도 유지되는지로 간접 관측한다.

## 6. 비용 관리

클러스터 가동 시간 = 비용이다.

```
1. (클러스터 없이) 스크립트·프로토콜·쿼리 확정   ← 이 문서가 그 산출물
2. terraform apply
3. 0단계 → 1단계 → 2단계 연속 실행
4. 결과 기록 후 즉시 destroy
```

**올라간 뒤에 무엇을 잴지 정하지 않는다.** 그 시간이 전부 비용이다.

## 7. 아직 정하지 않은 것

- **캐시 무효화 방식.** 좌석맵은 SSE로 실시간 반영되는 경로라 TTL만으로는 부족할 수 있다.
  기존 Redis Pub/Sub 팬아웃을 재사용하는 안이 있으나 **유실 시 낡은 재고가 남는다** —
  TTL 병행이나 직접 eviction이 필요하다. 0단계 결과로 좌석맵을 캐시할지부터 정한 뒤 설계한다.
- **캐시 대상 확정.** 0단계 전에 정하지 않는다.
- **상태 폴링 부하(§0 범위 밖).** 2초 주기를 늘리면 도착률이 비례해 줄지만, 폴링이 SSE
  재연결 공백을 메우고 있어 **주기를 늘린 만큼 입장 알림이 늦어질 수 있다.** 순번에 따라
  주기를 달리하는 안(뒤쪽 대기자는 길게)이 있으나 **아직 재보지 않았다.** 이 실험과 별개 과제다.
