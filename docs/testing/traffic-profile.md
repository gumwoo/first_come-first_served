# 가정 트래픽 프로파일

FlowTicket은 실제 운영 트래픽이 없다. 자원 산정(CPU requests, 노드 수, HPA 목표)과 비용 계산은 이 문서의 가정 부하를 기준으로 하고, 결과는 "가정 프로파일 기준 측정"으로 적는다.
가정 숫자는 다음 측정의 결과를 보기 전에 정했고, 실제 트래픽이 생기면 그 분포로 다시 맞춘다.

- 작성: 2026-10-26
- 관련: [[ADR-023]](대기열 폴링 주기), [[ADR-025]](api requests·HPA), [[ADR-027]](대기열 전용 Deployment), `docs/testing/loadtest-100k-plan.md`

## 1. 구간별 가정

| 구간 | 받는 쪽 | 가정 부하 | 근거 |
|---|---|---|---|
| 평시 | 예매 api(web 경유) | 조회 100 req/s | §2 |
| 오픈 순간 | 대기열 | 진입 10,000/s × 10초 = 10만 명 | 프로젝트 목표. 판정 시험은 Constant 형태로 했다([[IMP-031]]·[[IMP-035]]) |
| 오픈 뒤 정상 | 대기열 | 상태 조회 약 3,200~3,500/s | §3 계산 |
| 예매 | 예매 api | 입장 정원 100명 단위의 예매 묶음 | §4 |

## 2. 평시 100 req/s의 의미

1인당 초당 요청 = 화면당 api 호출 수 ÷ 화면에 머무는 시간이다. 동시 접속자 = 100 ÷ 1인당 초당 요청이다.

- 화면당 api 호출 수(프론트 코드 기준 계산, React Query 캐시·재조회는 반영하지 않음. 메인의 실시간 랭킹은 60초마다 다시 부르는데 이것도 넣지 않았다):

  | 화면 | 호출 | 수 |
  |---|---|---|
  | 메인(`/`) | 인기, 전체 목록, 오픈 예정 목록, 실시간 랭킹 | 4 |
  | 공연 상세(`/events/[id]`) | 공연 상세 | 1 |
  | 검색(`/search`) | 인기 검색어, 검색 결과 | 2 |
  | 내 예매(`/me/orders`) | 목록(+ 고르면 상세) | 1~2 |
  | 앱 첫 로드 | 토큰 재발급, 내 정보 | 2(로그인 세션 기준, 세션당 1회. 비로그인은 재발급 실패로 1) |

- 가정: 한 사용자가 화면 하나에 평균 10초 머물고, 화면당 평균 2회 호출한다(위 표의 대략적인 평균). 1인당 0.2 req/s다.
- 그러면 평시 100 req/s는 **동시 접속 약 500명**이다(계산).
- 부하 시험에서는 화면 가중을 메인 25%·상세 40%·검색 20%·내 예매 15%로 둔다(화면당 약 1.95회, [[IMP-048]]에서 정한 가정, `infra/k6/browse-mix.js`).
- 평균 체류 5분을 가정하면 시간당 방문자 약 6,000명에 해당한다(리틀의 법칙: 동시 접속 = 시간당 방문자 × 체류 시간, 계산).
- 예매 api 3개가 나눠 받으면 Pod 하나는 약 33 req/s다. 이 부하에서 예매 api CPU는 평균 0.07~0.39코어였다([[IMP-048]], 로컬 실측).
- 평시에는 열린 대기열이 없다고 보고, 대기열 Pod의 부하는 0에 가깝게 둔다.
- [[IMP-039]]의 평시 폴링 300/s·1,000/s는 오픈 실험(3,000/s)의 1/10 수준과 경향 확인용으로 잡은 가정이다. 이 프로파일 기준으로는 평시 가정보다 높은 조건이다.

## 3. 오픈 뒤 정상 폴링 3,200~3,500/s

오픈 10초 동안 들어온 10만 명이 대기 화면을 띄워 둔 채 서버가 정한 간격으로 상태를 묻는 상태다.

- 간격 규칙(`QueueService.retryAfterMs`, `application.yml`의 `queue.*`):
  - 순번 200 안(정원 100 × 2)은 2초.
  - 그 뒤는 ⌈순번 ÷ 정원⌉ × 승격 주기 1.5초를 2~30초로 자른다. 순번 2,000 이후는 30초다.
- 클라이언트는 그 간격에 0~20%를 더해 묻는다(`useQueue.ts`의 `JITTER_RATIO`).
- 대기자 10만 명 전원이 이 규칙대로 물으면 초당 약 3,507건, 지터를 균등분포로 반영하면 약 3,197건이다(계산, 이탈 미반영).
- 입장자 한 명이 최대 5분 자리를 잡고 정원이 100명이라 10만 명이 다 입장하는 데는 계산상 약 83시간이 걸린다([[ADR-023]]). 실제로는 대기자가 떠나면서 이 부하는 줄어든다.

[[IMP-031]]의 폴링 7,000/s × 480초는 이 구간의 가정이 아니라 자동 확장 경로(HPA → CA)를 일부러 일으키려고 계산한 시험 부하다(A′ 구성에서 api 7~8개 분량, [[IMP-031]] §4 계산). 이 프로파일에는 넣지 않는다.

## 4. 예매

- 대기열이 입장 정원(100명)만큼만 승격시키므로, 예매 api에 동시에 들어오는 예매 사용자는 정원이 상한이다. 대기열 진입·상태 조회는 예매 api로 오지 않는다.
- 오픈 직전·순간에 공연 상세를 새로고침하거나 탭으로 돌아와 다시 부르는 요청(web 경유 `GET /events/{id}`)은 예매 api로 온다. 이 요청은 이 프로파일에 넣지 않았고 규모는 측정하지 않았다([[IMP-035]] §8 범위 밖).
- 운영 기본값 B에서 예매 api는 3개 고정이다(base HPA 하한 3, queue-split이 상한을 3으로 묶는다).
- 예매 묶음은 짧은 순간 CPU를 많이 쓰고 그 밖에는 적게 쓴다. 로컬 실험실의 정상 run 6회(입장자 100명 동시 예매, 코어 2개 고정)에서 예매 api CPU는 분석 구간 평균 0.06~0.31코어, 표본 사이 최대 0.41~1.68코어였다([[IMP-045]] 2차 평가 정상 run, 로컬 실측).

## 5. 이 프로파일을 쓰는 곳
- 예매 api requests: 평시 조회 + 예매 묶음 기준으로 다시 정한다(대기열과 따로). 오픈 순간의 공연 상세 재조회는 따로 재서 반영한다.
- 대기열 requests·피크 Pod 수: 오픈 순간 기준([[ADR-025]]).
- 대기열 HPA 목표: 오픈 뒤 정상 폴링 구간의 확장·축소 기준.
