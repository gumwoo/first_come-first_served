# ADR-025 · api 요청 CPU를 진입 burst 실측 비용으로 정하고(1100m), HPA를 3~9로 — 반응형 확장을 노드(CA)까지 잇고, 오픈 사전 확장은 Git으로

- 상태: **Accepted**(2026-10-07)
- 날짜: 2026-10-07
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-023]](사전 확장·requests 현실화를 운영 방향으로 둔다 — (d)), [[ADR-012]](노드 예산 기반 HPA 상한 — 이 ADR이 대체),
  [[IMP-026]]·[[IMP-027]](진입 비용·10,000/s 용량), [[IMP-029]](최종 시험 — Platform 미증명), [[IMP-021]](CA 실증), [[TS-021]](HPA × 커넥션 풀 ≤ RDS 슬롯),
  [loadtest-100k-plan](../testing/loadtest-100k-plan.md) §6 "확장의 역할"

## 맥락
- 지금 api는 `requests.cpu: 300m`, HPA 3~7(CPU 60%)이다. 7은 "api 7×300 + web 4×300 + 기타가 노드 3대 allocatable 안"이라는 노드 예산에서 나왔다
  (ADR-012, web-hpa.yaml) — CA가 노드를 붙이는 것을 전제로 하지 않았다.
- 10,000/s 진입 burst의 api CPU 실측(IMP-027 §7, 판정 3회)은 1.338 / 0.826 / 0.768 ms/req, 중앙값 **0.826**이다. api 9개가 나누면 파드당 약 1,111 req/s → 약 0.92코어(계산).
  300m 기준 HPA 60%(180m)는 처리 용량과 동떨어진 지점에서 반응하고, 노드 하나에 api가 여럿 들어가 Pending(→ CA)이 생기지 않는다.
  최종 시험의 Platform 시연은 그래서 requests를 세션 한정으로 1000m로 바꿔야 했다(IMP-029 §7).
- 계획서 §8 Platform 축은 "사전 확장으로 진입을 받고, 이후 지속 부하에서는 HPA/CA가 정의한 정책대로 확장·축소"를 요구한다. 정책과 사전 확장이 모두 Git에 있어야 한다
  — 세션 kubectl patch는 ArgoCD selfHeal이 되돌리고 기록도 남지 않아 IMP-029에서 Platform을 닫지 못한 약점이었다(사용자 결정).

## 결정
1. **api `requests.cpu` 1100m** — 0.826 ms/req(burst 실측 중앙값) × 1,111 req/s × 여유 1.2 ≈ 1.10코어(계산값, 사용자 결정).
   m6i.large(allocatable 1,930m)에 api가 하나만 들어가(2 × 1,100 > 1,930) **api 확장이 곧 노드 확장**이 된다. memory(1536Mi)·limits는 그대로.
2. **HPA api 3~9, CPU 60%**(목표 파드 평균 660m — HPA 기본 허용 오차 0.1이라 실제 확장은 평균 약 726m를 넘을 때부터(계산), behavior 그대로 — 확장 즉시, 축소 안정화 300초). 9는 10,000/s 진입의 계산 용량(api 9·노드 9)이고
   측정 프로파일의 노드 그룹 상한(AZ당 3, `loadtest.tfvars`)과 같다. web HPA(2~4)는 그대로.
3. **오픈 순간은 Git으로 사전 확장한다** — `k8s/overlays/demo-local/event-prescale.yaml`(HPA 하한 패치, 평소 3 = 효과 없음)을 오픈 전에 9로 올리는
   PR을 머지하면 ArgoCD가 하한을 맞추고, 늘어난 api가 Pending → CA가 노드를 붙인다(노드 그룹 설정은 건드리지 않는다). 오픈이 지나면 3으로 되돌리는 PR을
   머지해 이후는 HPA 정책(3~9)에 맡긴다. 켤 때는 `# event:`·`# off-by:`(되돌릴 시각)를 적는다.
   하네스 k8s 규칙 11이 하한 범위(base 3~9)·표기·namespace·kustomization 참조·off-by 경과를 검사한다. 단 k8s 하네스는 CI backend job에서만 돌고 그 job은
   `apps/api`·`contracts`·`harness`·`k8s`·`ci.yml`이 바뀐 PR에서만 실행된다 — 그 밖의 PR이나 PR이 없는 기간에는 off-by가 지나도 막지 않는다.
   상시 검사 job·예약 워크플로는 두지 않는다(사용자 결정 — 기한 검사는 Platform 검증 세션 안에서 하고, 시험 뒤 사전 확장을 되돌린다).
   예약 확장 도구(KEDA 등)는 새 의존성이라 두지 않는다. k8s 매니페스트만 바뀌는 머지는 이미지를 다시 빌드하지 않아(`image.yml`의 변경 판별에 `k8s/`가 없음)
   HPA 하한만 바뀌고 api 파드를 다시 띄우지 않는다.

## 계산 근거(계산값 — 측정 아님)
- 여유: 1100m는 burst 실측 중앙값 기준 약 1.2배다. 실측 최댓값(1.338 ms/req)이면 1,111 req/s에 약 1.49코어로 requests를 넘는다 — 오픈은 사전 확장(9)으로 받는다.
- DB 커넥션(TS-021, 하네스 backend 규칙): (maxReplicas 9 + maxSurge 1) × 풀 5 = 50 ≤ 가용 56(db.t4g.micro 79 − reserved 3 − 앱 외 여유 20).
  api 9개는 최종 시험(IMP-027·029)에서 모두 Running이었다.
- 평상시 배치(api 3): 노드별 flowticket 밖 CPU 요청이 410·600·750m(측정 세션 20261007-e2e 실측 — 레포 밖 기록)라 api를 놓고 남는 자리는 420·230·80m다.
  web(300m)은 한 노드에만 들어가므로 web 2개 중 하나는 **4번째 노드**가 필요하다(계산) — 평상시 노드가 3에서 4로 늘 수 있다.
- vCPU 쿼터 32: 노드 최대 9 × 2 + 발생기 3 × 4 = 30.

## 결과·대가
- **평상시 노드가 늘 수 있다**(위 계산 — 3 → 4). web 확장, api 롤링 배포의 surge(+1,100m)는 들어갈 자리가 없으면 노드 추가(CA 실측 110초, IMP-021)를 기다릴 수 있다
  (4번째 노드가 web·데몬셋뿐이면 surge가 거기 들어갈 수 있다 — 계산).
- **CA가 api 노드를 줄이지 못한다**: CA 축소 기준(요청 50% 미만 — CA 기본값으로 본다, 값을 따로 두지 않았다)에서 api가 있는 노드는 api 하나만으로 57%(1,100/1,930)라
  축소 대상이 아니다. 노드가 api보다 많으면 api 없는 노드가 반드시 있고, 그 노드는 flowticket 밖 요청만이면 21~39%라 축소 대상이 된다(계산). 그래도 줄지 않는 것은
  (a) 그 노드에 web(300m) 등이 있어 50% 이상이거나(예: 750 + 300 = 54%), (b) 그 노드의 파드(web, flowticket 밖 파드, AZ에 묶인 볼륨을 쓰는 파드 등)를 옮길 자리가
  다른 노드에 없을 때다(api 노드의 남는 자리는 최대 420m — 계산, 그 밖의 조건은 추론). IMP-029 §7에서 롤아웃 서지로 붙은 노드를 CA가 지우지 못해 운영자가 drain했다(관찰).
  기본값은 바꾸지 않고(IMP-021 원칙) 남은 노드는 런북 §2b의 drain 절차로 정리한다(사용자 결정) — 옮길 자리가 없으면 drain해도 Pending → CA가 노드를 다시 붙인다.
- **확장 시점이 늦어진다**(ADR-023 (d)의 경고): 300m 때는 180m만 써도 확장했지만 이제 목표가 파드 평균 660m(허용 오차 포함 약 726m부터 확장 — 계산)이고, 파드 하나마다 노드 추가가 따른다.
  지속 부하(대기자 폴링 등)에서 부하에 맞춰 늘고 주는지는 예측이다 — 통합 판정 run(Platform 축)에서 확인한다. 이 ADR은 수치를 주장하지 않는다.
- **HPA 9(또는 사전 확장 중)에 롤링하면 멈춘다**: surge 파드가 10번째 노드를 얻지 못하고(노드 그룹 상한 9) maxUnavailable 0이라 롤아웃이 진행되지 않는다(계산).
  사전 확장 중에는 이미지가 바뀌는 PR을 머지하지 않는다.
- 노드 상한은 Terraform 프로파일에 달렸다: 측정 프로파일(m6i.large·AZ당 3)은 노드 9라 HPA 9와 맞지만, 기본 프로파일(t3.large·AZ당 2)은 노드 6이라
  api가 6을 넘으면 Pending으로 남는다(계산) — 기본 프로파일에서 사전 확장(9)을 켜면 api 3개가 Pending이다.

## 보충(2026-10-08) — 사전 확장 9가 web 전용 노드에 막혔다 → web을 낮은 우선순위로
- 관찰(측정 세션 20261007-platform pf-warm): 사전 확장 켜기(하한 9) 머지 뒤 노드 9대가 Ready였지만 api는 8개만 Running, 1개 Pending.
  평상시 web만 올라 있던 노드(요청 1,050m = 기타 750 + web 300)에는 api(1,100m)가 들어가지 못하고, 노드 그룹 3개가 상한(합 9)에 닿아
  CA가 "max size reached"로 노드를 더 붙이지 못했다. 위 계산의 "api 9 = 노드 9"는 web이 노드 하나를 따로 차지하는 경우를 빠뜨렸다.
- 결정(사용자): web에 낮은 우선순위(PriorityClass `flowticket-web-low`, -10, 자신은 선점하지 않음)를 주고 web PDB(minAvailable 1)를 둔다.
  Pending인 api(기본 0)가 web 파드를 밀어내고, 밀려난 web은 새 api 노드의 남는 자리(1,930 − 1,100 − 기타 약 180 ≈ 650m — 계산)로 옮긴다.
  api를 높이지 않은 이유: 같은 기본 우선순위인 Kafka·Prometheus·ArgoCD 파드까지 선점 대상이 된다.
- 대가: 기본 우선순위 파드가 Pending이면 web이 밀려날 수 있다(PDB로 한꺼번에 비는 것을 줄인다 — 선점은 PDB를 최대한 지키지만 보장하지 않는다).
  web 파드 템플릿이 바뀌어 web 롤링이 한 번 일어난다(api는 그대로).

## 대안
- **300m 유지 + HPA 상한만 상향**: 노드 하나에 api가 여럿 들어가 CA가 동작하지 않는다(Pending이 생기지 않음). 반응형 확장이 노드까지 이어지지 않는다.
- **1000m**: burst 실측 중앙값 대비 여유가 약 1.09배라 1.2배 여유 기준에 못 미친다. 평상시 배치는 조금 덜 빡빡하다(사용자 결정으로 1100m).
- **노드 단위 분산 규칙(hostname DoNotSchedule)으로 노드당 1개 강제**: requests를 그대로 두면 HPA 기준선(60%)이 처리 용량과 동떨어진다. 분산 규칙은 별도 판단(`perf/api-node-spread`).
- **세션 kubectl로 사전 확장**: selfHeal이 되돌리고(자동 동기화를 꺼야 함) 언제 무엇을 바꿨는지 Git에 남지 않는다 — IMP-029가 Platform을 닫지 못한 약점.
- **예약 확장 도구(KEDA cron 등)**: 시각으로 켜고 끌 수 있지만 새 의존성이다. PR 두 번(켜기·끄기)으로 충분해 두지 않는다.
- **CronJob이 HPA를 patch**: Git이 소유한 필드라 selfHeal과 싸운다.
- **CA 축소 기준(scale-down-utilization-threshold) 상향**: api 노드도 줄일 수 있지만 CA 기본값 변경이라 두지 않는다(IMP-021).
