## 판정

**무릎은 450~600 rps 사이.** 450까지는 도착률을 다 채우고 실패 0이었으나, 600에서 처음으로
도착률을 못 채웠고(551) 실패·지연이 동시에 급등했다.

**첫 포화 자원은 web 티어다.** 근거 셋이 같은 방향을 가리킨다.

1. `ELB_5XX 457 == TargetConnectionError 457`이고 `Target_5XX = 0`
   → 앱이 에러를 낸 것이 아니라 **ALB가 web 파드에 연결하지 못했다**
2. 같은 시점 **서버 p95는 15ms** — api는 여유가 있었다
3. `Hikari pending = 0` (전 구간) — **DB도 병목이 아니다**

web CPU는 부하에 비례해 계속 올랐고(0.31 → 1.18 core), 2파드 고정이라 그 이상 흡수할 수단이 없었다.

## 이 수치를 어떻게 읽어야 하는가

- **클라이언트 p95와 서버 p95는 다른 것을 잰다.** 600 rps에서 각각 10,006ms / 15ms다.
  클라이언트 값에는 인터넷 RTT·TLS·ALB·Next 프록시가 모두 포함된다
- **k6를 노트북에서 돌렸다.** 별도 dev 서버는 비용상 만들지 않았다. 절대 처리량이 아니라
  **AS-IS/TO-BE 비교의 기준선**으로 쓴다
- **`api CPU`가 600 rps에서 오히려 낮다**(2.02 core). 요청이 web에서 막혀 api까지 도달하지
  못했기 때문으로 **추정**한다 — 직접 확인하지는 않았다
- 각 단계 1회씩만 측정했다. 반복 측정은 하지 않았다
