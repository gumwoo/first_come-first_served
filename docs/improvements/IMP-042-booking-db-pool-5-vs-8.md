# IMP-042 · 예매 api DB 커넥션 풀 5 vs 8(로컬): 차이가 일관되지 않아 5 유지

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-21(로컬 실험 `artifacts/loadtest/local-20261021-l6/`, 레포 밖)
- 유형: 정량(로컬 실측, 판정 8묶음). 같은 로컬 환경 안의 상대 비교다.
- 관련: [[IMP-036]](예매 묶음 순간 DB 풀 포화), [[IMP-041]](같은 측정 도구), 하네스 backend 규칙 17(DB 연결 예산)
- 벤치 파일: 레포 밖 `local-20261021-l6/`: 사전 등록 `prereg-L6.md`, 구성 `compose.yml`, 실행 `run-l6.sh`, 수집기 `sampler3.mjs`, 요약 `summarize-l5.mjs`, 결과 `out/`(실행 기록 `out/runs.log`)

## 1. 상황 (Context)
[[IMP-036]]에서 입장자 100명 예매 묶음이 시작되는 순간 api DB 풀 5가 1~2초 동안 포화됐다(active 4~5, pending 16~32). 운영 구조(대기열 분리)는 api 3개 고정이라
풀을 8로 올려도 DB 연결 예산 안에 든다((3+1) × 8 + (6+1) × 3 = 53 ≤ 56, 계산). 풀을 늘리면 예매 지연이 줄어드는지 확인했다.

## 2. 문제 정의 + 분류
- 계층: DB 연결(HikariCP 풀 크기).
- 질문: 예매 묶음을 받는 api의 풀을 5에서 8로 늘리면 예매 p95가 줄어드는가.

## 3. 측정 방법
- 같은 이미지 api 2개(api-a 코어 2·3, api-b 12·13, 메모리 2Gi), 대기열 1개(코어 8·9, 풀 3, 진입·상태 조회 전용), PostgreSQL(코어 6·7), Redis(코어 4), 예매 k6(코어 10·11).
- 묶음마다 입장자 100명의 예매(선점·주문·결제, 같은 좌석 경합·중복 클릭·결제 실패 후 재시도·1인 한도 포함)를 api 하나로 보낸다.
- 컨테이너·코어 차이를 상쇄하려고 전반부는 a=풀 5·b=풀 8, 후반부는 재기동해 a=풀 8·b=풀 5로 바꿨다(재기동 뒤 예열).
- 판정 묶음 8개, 쌍 (J1, J2) (J4, J3) (J5, J6) (J8, J7)은 각각 풀 5 한 번, 풀 8 한 번이다. 묶음마다 새 공연·다른 사용자 100명.
- 판정(측정 전 등록): 예매 p95(선점·주문·결제 세 단계 p95의 중앙값) 기준.
  - 개선: 4쌍 중 3쌍 이상에서 풀 8 쪽이 20% 이상 낮고, Hikari pending 최대도 3쌍 이상에서 낮음.
  - 차이 없음: 4쌍 중 3쌍 이상에서 차이가 ±20% 안.
  - 그 밖: 판단 불가. 개선이 아니면 풀 5를 유지한다.
- 도구 오류가 난 묶음(J2~J4, 실행 스크립트 중복 실행)은 판정에서 제외하고 같은 배정으로 다시 측정했다. 재측정은 후반부(J5~J8) 뒤에 전반부 배정으로 다시 재기동·예열해 진행했으므로, (J1, J2) 쌍은 같은 컨테이너 수명 안의 비교는 아니다.

|---|---|---|---|---|---|

| J2 | 8 | 1,141 · 1,009 · 564ms | 1,009ms | 0.37 / 1.76코어 | 40 |
| J3 | 8 | 1,005 · 818 · 595ms | 818ms | 0.32 / 2.01코어 | 38 |
| J4 | 5 | 1,170 · 1,065 · 663ms | 1,065ms | 0.41 / 2.13코어 | 0 |
| J5 | 5 | 901 · 943 · 763ms | 901ms | 0.36 / 2.34코어 | 23 |
| J6 | 8 | 1,037 · 801 · 516ms | 801ms | 0.32 / 1.44코어 | 52 |

| J8 | 5 | 3,801 · 3,145 · 2,594ms | 3,145ms | 0.77 / 2.17코어 | 38 |

모든 묶음에서 100명이 입장했고 5xx는 0이었다. J4의 pending 0은 묶음 시작 순간에 걸린 수집 표본이 하나뿐이고 그 응답이 1.6초 걸렸기 때문으로, 대기가 없었다는 뜻으로 보지 않는다. J8은 짝인 J7보다 약 5.5배 느렸고(지표 응답 최대 4.1초) −82% 쌍을 결정했지만, 이 쌍을 빼도 판정은 같다.

- 쌍별 비교(풀 8 쪽이 풀 5 쪽보다): J1·J2 +16%, J4·J3 −23%, J5·J6 −11%, J8·J7 −82%.
- **판정: 판단 불가.** 20% 이상 낮은 쌍이 2개(개선 기준 3개 미달), ±20% 안인 쌍도 2개(차이 없음 기준 3개 미달)다.
- pending 최대는 풀 8에서도 38~52였다. 풀을 늘려도 커넥션 대기가 남았으므로, 예매 묶음의 대기는 풀 크기만으로 정해지지 않는다(추론).

## 5. 조치
- **api DB 풀은 5를 유지한다.** 풀 8의 효과가 쌍마다 일관되지 않았다.
- 하네스 backend 규칙 17(DB 연결 예산)과 매니페스트는 바꾸지 않는다.

## 6. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대 비교, 묶음은 api 하나가 받는 조건(운영은 api 3개에 나뉨), 예매 시나리오는 같은 좌석 경합(40명이 4석)을 포함한다.
- 후속([[IMP-043]]): 풀 8에서도 남은 pending은 100명이 같은 순간 도착한 요청 수였고, 행 잠금 대기는 원인이 아니었다. 묶음 사이 편차는 저장 장치의 flush 지연으로 WAL 동기화가 길어진 묶음에서 나왔다. 이런 묶음을 걸러내고 다시 잰 결과 풀 5 vs 8은 "차이 없음"(4쌍 중 3쌍 ±20% 안)이었다.

## 7. 배운 점 (면접 답변용 한 줄)
"풀이 포화됐으니 늘리면 빨라진다"는 가설을 같은 이미지 두 컨테이너의 배정을 중간에 바꾸는 교차 설계로 검증했고, 효과가 쌍마다 일관되지 않아 설정을 바꾸지 않았다.
