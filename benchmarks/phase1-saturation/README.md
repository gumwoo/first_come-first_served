# Phase 1 — 포화점 탐색 (2026-08-11)

TO-BE(`../tobe-web-hpa/`)가 600 rps를 통과한 뒤, **다음 무릎이 어디이고 무엇이 먼저 마르는지**를
찾는다.

## 측정 절차

이전 측정에서 **콜드 스타트가 결과를 오염시킨 것**을 겪어(아래 §무효 측정) 절차를 고정했다.

```
각 단계마다:
  1) 워밍업 300 rps · 45초   ← HPA를 최대치로 올려 시작 조건을 통일
  2) 목표 도착률 · 90초       ← 측정
```

구성은 TO-BE와 동일하다 — api HPA 3~7 / web HPA 2~4, requests 각 300m,
노드 t3.large × 3 (allocatable 합 **5.79 core**).

## 판정

**capacity knee는 600~650 rps 사이다.** 600은 두 번(TO-BE, Phase 1) 통과했고 550도 통과했다.
650에서 처음으로 도착률을 못 채우고(604) 실패·지연이 급등한다.

**병목이 이동했다.**

| 시점 | 첫 포화 자원 |
|---|---|
| AS-IS (web 2파드 고정) | **web 티어** — ALB→web 연결 실패 |
| **Phase 1 (650 이상)** | **노드 CPU + DB 커넥션 풀** |

- 노드 CPU 합이 **5.23 core = allocatable(5.79)의 90%**
- `Hikari pending`이 **611**로 폭발. AS-IS·TO-BE 전 구간에서 0이던 값이다
- 서버 p95가 **5.58초** — AS-IS에서 15ms로 여유롭던 그 api다
- **web CPU는 1.08~1.28로 변화 없음** — web은 더 이상 병목이 아니다

즉 web을 고쳐(#216) 부하가 api와 DB까지 도달하게 되자, 다음 한계가 드러났다.

⚠️ **인과 방향은 확정하지 않았다.** 노드 CPU가 90%라 스레드가 느려져 커넥션을 오래 잡은 것인지,
커넥션이 부족해 요청이 밀린 것인지 이 자료로는 갈리지 않는다. 서로를 악화시키는 구조일 수도 있다.

**한계 자원이 애플리케이션이 아니라 인프라다.** 앱을 더 튜닝해도 6 vCPU로는 이 지점을 넘지 못한다.
넘으려면 노드를 늘려야 한다.

## TS-021과의 관계

TS-021에서 Hikari 풀을 10→5로 줄이고 `api 7 × 5 = 35 커넥션`으로 계산했다.
**그 판단은 600 rps까지 유효했고 650에서 한계에 닿았다.** 당시 "트래픽이 커져 파드당 5로
부족해지면 다시 부딪힌다. 그때가 커넥션 풀러를 도입할 시점이고 판단 근거는 pending 실측"이라고
적어두었는데, **그 실측이 지금 나왔다**(650에서 pending 611).

다만 위에 적었듯 노드 CPU 포화와 분리되지 않으므로, 이 수치만으로 풀러 도입을 결정하기에는
근거가 부족하다.

## 무효였던 측정 (기록)

첫 시도(750·900 rps)는 **세 요인이 겹쳐 무효**였다. 숨기지 않고 남긴다.

1. **콜드 스타트** — api 3 / web 2에서 시작. 이전 TO-BE는 100부터 점진적으로 올려 이미 데워진
   상태였다
2. **새 이미지 롤아웃과 겹침** — 측정 중 `8b5c0dc5` 배포가 진행돼 구·신 파드가 공존했다
3. **스케줄 실패** — `FailedScheduling: 0/3 nodes are available: 3 Insufficient cpu`

세 번째는 #216의 예산 계산에 구멍이 있었음을 드러냈다. 총합은 4,950m / 5,790m = 85%로 맞았지만
**노드별 분포를 보지 않았다** — 실제로는 한 노드가 98%였고, 파드는 한 노드에 들어가야 한다.

그 결과 api 파드가 Startup probe 실패로 **재시작 루프**에 빠졌고(누적 8회), 750 rps 측정에서는
실제 9 rps / 실패 100%가 나왔다. 부하를 멈추자 약 40초 만에 11/11 정상으로 회복됐다.

## 한계

- **각 단계 1회 측정**(600만 TO-BE 포함 2회). 반복 측정은 하지 않았다
- 650·700의 대소 관계가 뒤집혀 있다(p95 12.6초 vs 7.6초). 붕괴 구간의 변동성으로 **추정**하며
  확인하지 않았다
- k6를 노트북에서 인터넷 경유로 돌렸다. 클라이언트 p95에는 RTT·TLS·ALB·Next 프록시가 포함된다
- **워밍업 절차가 AS-IS/TO-BE와 다르다**(그쪽은 100부터 점진 상승). 따라서 이 표의 550·600은
  TO-BE 표와 직접 비교하기보다 **Phase 1 내부 비교**로 읽어야 한다
