## 1. 상황 (Context)
[[ADR-023]]은 10만 burst를 두 축으로 나눠 고치고(축 ① 진입 경로 — [[ADR-024]]·[[IMP-025]]~[[IMP-027]], 축 ② 대기 상태 전달 — [[IMP-028]]·폴링 주 경로),
마지막에 합쳐서 재기로 했다(시험 ⑤ — 10만 burst → 대기 → 입장 → 좌석·주문). 이 문서는 그중 **대기열 부분**(진입 → 대기·폴링 → 입장 제어)의 결과다 — 좌석·주문은 재지 않았다. "100K를 검증했다"고 쓸 수 있는 조건은 [loadtest-100k-plan](../testing/loadtest-100k-plan.md) §8의 7축이다.

## 2. 문제 정의 + 분류
100,000명이 10초 동안 진입할 때(target 10,000 req/s) 대기열 계층이 진입을 모두 받고, 대기자 전원의 상태 폴링을 오류 없이 처리하며,
정원(100) 이상을 downstream으로 내보내지 않는지 — 그리고 그 판단이 발생기 한계가 아닌 시스템 결과인지 확인한다.
- 계층 분류: 애플리케이션 처리 용량(api CPU) / Redis(단일 스레드) / 네트워크(ALB) / 부하 발생기(측정 도구) / 동시성(입장 정원)
- 범위: 대기열 진입 + 대기(상태 폴링) + 입장 제어 + 정합성. **좌석·주문·결제는 범위 밖**(§8 — 10만 명이 결제했다는 뜻이 아니다).

## 3. 증상 (측정된 증거) — 측정 방법
- 구성(세션 한정 사전 확장 — [[IMP-027]]과 같다, Git 변경 아님): 노드 9(m6i.large, AZ당 3), api 9(노드당 1 — 노드 단위 분산 패치), web 2,
  HPA api 9/9 고정, `requests.cpu` 300m. Redis `cache.t4g.micro`(단일 스레드), RDS `db.t4g.micro`.
- 부하: 공개 ALB, 발생기 c6i.xlarge 3대, 공통 시작 시각 T0(START_AT 장벽), T0 전 30초 동안 연결 미리 맺기(#347),
  발생기당 constant `--rate 3400` → 몫 33,333~33,334명이 약 9.8초에 소진(계산), 겹치지 않는 사용자 100,000명.
  진입 응답이 WAITING인 토큰 전부를 대기자 폴링 발생기(`poll-hold.mjs`)가 받아 첫 토큰부터 420초 동안 프론트와 같은 규칙
  (`max(2초, retryAfterMs)` + jitter 20%, 오류 시 2→30초 백오프)으로 상태를 묻는다. 420초 = 입장 TTL 300초 + 여유 — 정원이 한 번 회수돼 폴링 중 승격을 볼 수 있다.
- 도착 판정은 k6가 아니라 **ALB access log의 `request_creation_time`**으로 한다(k6의 iteration 시작은 클라이언트 의도라 서버 도착 증거가 아니다 — [[IMP-027]] §8).
  창은 시험 전에 고정한 [T0, T0+10.000s)이며, 가장 잘 나온 창을 고르지 않는다.
- run: 워밍업 1회(판정 제외) + 판정 3회, run마다 대기열 키 리셋(삭제 확인)·재사용 공연.

## 4. 가설 (사전 등록 — 결과 보기 전)
축 ①·② 개선과 사전 확장(api 9·노드 9)으로, 10,000/s × 10초 진입과 대기 10만 명의 폴링을 함께 받아도 6축(Traffic·Queue·Protection·대기 상태 전달·Correctness·Generator)이
판정 3회 모두 충족한다. Platform 축(반응형 확장·축소)은 판정 run과 분리해 시연한다(아래 §5 "1차 전 변경").

## 5. 검증 — 세 번의 사전 등록과 그 사이에 바뀐 것
판정 기준을 결과 뒤에 바꾸면 통과할 때까지 기준을 옮긴 것과 구분되지 않는다. 그래서 시도마다 결과를 지우지 않고, 바꾼 것과 그 이유·시점을 남긴다.

- **1차 전 변경**(1차 판정 run 전): 워밍업이 세션 스크립트 버그로 30,000/s가 걸려 무효(`INVALID-f-100k-warm-30k`). 같은 run에서 HPA가 10으로 늘었다 줄며
  10번째 파드를 지워 감사 로그가 사라져 사후 검사가 판정 불가였다 → 사용자 결정: **판정 3회는 HPA 9/9 고정, Platform 축은 별도 시연**.
- **1차**(`final-prereg.md`, `f2-100k-r1~r3`, `--rate 3350`): 미충족 2건.
  - Traffic: r2의 ALB 창 안 **99,982**(18건이 T0+10s 뒤). 발생기 마지막 송신은 T0+9,951~9,953ms(k6)로 창 끝까지 여유가 약 47ms뿐이었다.
    r2는 T0+8~9초 구간에서 k6가 시작한 요청 10,045건 중 ALB 기록은 8,947건(다음 초 10,690건)으로, 약 1,100건이 k6 시작보다 늦게 ALB에 기록됐다
    — 60ms 지연이면 넘어갈 수 있는 건수는 약 600건이라(계산) 경계 부근 지연은 적어도 약 110ms였다(계산). 마지막 요청은 ALB 기준 10,013ms.
    늦어진 쪽이 발생기 송신인지 ALB 수신인지는 확인하지 않았다(1차 판정 줄의 "8초째 응답 지연 구간"과 시점이 겹친다). (2차 사전 등록 문서의 "최대 60ms"는 마지막 요청 한 건 기준이라 틀린 서술이다.)
  - 대기 상태 전달: r1 폴링 네트워크 오류 **2건**(시간 초과·본문 끊김이 아닌 연결 오류, 코드 미기록 — 재사용 keep-alive 소켓 경합으로 추정).
- **2차**(`final-prereg-v2.md`, `f3-100k-r1~r3`): 바뀐 것 — `--rate 3400`(송신 여유 약 200ms, 계산), 폴링 발생기가 재사용 소켓 `ECONNRESET`이면
  다른 소켓으로 1회 재시도(#355 — 브라우저의 자동 재전송을 흉내). 재시도가 실패를 가리지 않게 **발생기별 재시도 ≤ 그 발생기 조회의 0.01%(약 42건, 계산)**를
  충족 조건에 더했다(사용자 결정). 결과: 1차 미충족 둘은 해소(ALB 창 안 100,000×3, 폴링 오류 0, 재시도 0). 대신 미충족 2건.
  - Traffic 초별: 마지막 bucket 8,233 / 8,371 / 8,228이 "10,000 ± 15%" 밖. `--rate 3400`이면 몫이 약 9.8초에 소진돼 마지막 초가 부분 초가 된다 —
    **2차 사전 등록에서 마지막 bucket 기대치를 다시 계산하지 않은 측정자 실수**.
  - Generator: 발생기 g3 CPU 1초 최대 80 / 82 / 81%(기준 < 80%). 피크는 진입 burst 구간이다(확인). 그 CPU가 k6 몫이라는 것은 프로세스별 근거 없이 아래 `d-lean-cpu` 결과로 본 추론이다.
- **3차**(`final-prereg-v3.md`, `f4-100k-r1~r3`) 전에 바꾼 것(사용자 결정, 결과 보기 전 확정):
  ① 초별 기준을 계획 도착 곡선 기준으로 — bucket 0~8 기대 10,200, bucket 9 기대 약 8,200(계산), 각 ±15%(1·2차와 같은 폭).
  ② 발생기 k6 출력 줄이기(#356 — 읽지 않는 태그·check 제거). 진단 run `d-lean-cpu`(판정 제외)에서 발생기 CPU 1초 최대 54 / 53 / 69%, JSON −26%를 확인한 뒤 확정.
  그 밖의 구성·기준·무효 조건·run 수는 2차와 같다.
- ①은 2차 결과를 본 뒤 바꾼 기준이다. 기대치를 계산 곡선에 맞춘 것이고 폭(±15%)은 그대로다. 사후 재평가로는 2차 값(bucket 0~8 9,544~10,894, bucket 9 8,228~8,371)도
  새 기준 안이지만, **2차 사전 등록 기준의 판정은 Traffic·Generator 2건 미충족 그대로**다(이 문서의 판정은 3차만 쓴다).

  (별도 시연에서 세션 한정 설정으로 HPA·CA 확장·축소를 관찰했지만 시연 부하 run은 무효). 나머지 6축은 3차 사전 등록 판정 3회 모두 충족.
- **표현 범위**: 사전 등록 v3 기준으로 6축(Traffic·Queue·Protection·대기 상태 전달·Correctness·Generator)은 판정 3회 모두 충족했다.
  Platform은 사전 확장 부분(판정 run에서 진입 오류 0)과, 별도 시연에서의 HPA·CA 확장·축소 관찰(세션 한정 설정, 시연 부하 run은 무효)로 나뉜다.
  §8의 "정책대로 확장·축소"를 운영 설정 그대로 판정 run 안에서 보인 것은 아니다.
- **세 번째 시도의 결과다.** 1·2차 결과와 그 사이에 바뀐 기준·도구는 §5에 모두 남겼다. 3차의 초별 기준은 2차 결과를 본 뒤 계산 곡선에 맞춘 것이다.
- **범위**: 좌석·주문·결제(ADR-023 시험 ④·⑤의 downstream)는 이번에 재지 않았다. 입장자는 run마다 300명(정원 100 × 3회)이라 downstream 부하는 작다.
- **구성은 세션 한정 사전 확장**이다(노드 9·api 9·HPA 고정·노드 분산 패치 — Git 변경 아님). 운영에 반영하려면 Git의 HPA 하한·노드 그룹으로 옮기는 별도 결정이 필요하다.
- **Redis 메인 스레드가 burst 중 2초 표본 최대 0.885~0.887코어**였다(run별 범위는 §7 표, 단일 스레드 `cache.t4g.micro`). 여유가 작다 — 이보다 높은 도착률은 Redis가 먼저 막힐 수 있다(추론, 미측정).
- **순간 지연**: r3 진입 p99 204.5ms처럼 run마다 지연 꼬리가 다르다. 원인은 확인하지 않았다([[IMP-028]] §8과 같은 현상인지도 미확인).
- 입장 인지 지연 p95 약 2.3초는 폴링 최소 간격(앞쪽 2초) + jitter에서 오는 값으로 본다(추론). 표본은 run마다 200명(앞쪽 순번)이고 뒤쪽 순번(최대 30초 간격)의 지연은 표본이 없다.
- 발생기는 3대·c6i.xlarge·vCPU 쿼터 안에서 맞췄다. 1초 최대 CPU 74%로 여유가 크지 않다.

## 9. 배운 점 (면접 답변용 한 줄)
10만 명 / 10초를 "k6가 다 보냈다"가 아니라 ALB access log의 서버 도착 시각으로 고정 창 안에서 세고, 대기자 10만 명의 폴링·입장 인지 지연·정원 초과·발생기 한계까지 축별 기준을 먼저 정해
판정했다 — 두 번 기준에 못 미친 원인(송신 여유·소켓 경합·마지막 초 기대치·발생기 CPU)을 원시 데이터로 가르고, 바꾼 것을 남긴 채 세 번째 사전 등록에서 6축을 3회 모두 충족했다.
