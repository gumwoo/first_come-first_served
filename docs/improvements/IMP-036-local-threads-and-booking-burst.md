# IMP-036 · 로컬 실험: Tomcat 스레드만 포화되는 조건과 200 vs 400, 예매 묶음의 순간 CPU·DB 풀

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-20(로컬 실험 `artifacts/loadtest/local-20261020/`, 레포 밖)
- 유형: 정량(로컬 실측). 같은 로컬 환경 안의 상대 비교이며, 칸마다 1회 관측이다.
- 관련: [optimization-targets.md](../deployment/optimization-targets.md)(최적화 대상과 제약, 이 실험이 답하려는 두 질문), [[TS-049]](Redis 크레딧 고갈 중 스레드만 포화), [[IMP-030]](예매 묶음 시나리오), [[IMP-034]](분리 구조 원자료)
- 벤치 파일: 레포 밖 `artifacts/loadtest/local-20261020/`. 사전 등록 `prereg-L1.md`·`prereg-L2.md`, 구성 `compose.yml`, 실행 `run-cell.sh`, 수집기 `sampler.mjs`, 요약 `summarize.mjs`·`summarize-book.mjs`, 칸별 결과 `out/`, 실행 기록 `out/cells.log`

## 1. 상황 (Context)
기존 AWS 원자료 재분석([optimization-targets.md](../deployment/optimization-targets.md) §2)에서 남은 두 질문을 AWS 비용 없이 로컬에서 확인한다.
1. **Tomcat 스레드**: 통합 구조에서 "CPU는 남는데 스레드만 200"인 표본이 있었다. 한 번은 Redis 크레딧 고갈([[TS-049]])과 겹쳤다. 하위 의존성이 느려지면 이런 모양이 되는가, 그때 스레드를 400으로 늘리면 나아지는가.
2. **예매 api 요청량**: AWS의 예매 api CPU는 1분 평균으로 0.03~0.08코어였다. 1분 평균은 입장자 100명의 예매 묶음(수 초)을 희석한다. 그 순간 실제로 얼마를 쓰고, DB 풀 5는 포화되는가.

## 2. 문제 정의 + 분류
- 계층: 스레드·커넥션 풀(Tomcat 요청 스레드, Hikari) / CPU 요청량 산정.
- 1번은 "스레드 수를 늘릴 근거가 있는가", 2번은 "1분 평균만 보고 예매 api 요청량을 낮춰도 되는가"다.

## 3. 측정 방법
- 구성(`compose.yml`): 최신 main 이미지의 단일 api, 코어 2개 고정(`cpuset` 방식이라 쓰로틀링이 없으며, EKS Pod에 CPU limit이 없는 것과 같은 성격), 메모리 상한 2Gi. PostgreSQL 16(코어 2개)·Redis 7.4(코어 1개) 각각 다른 코어. k6 0.54는 같은 Docker 네트워크의 다른 코어에서 실행(Windows 포트 포워딩을 거치지 않음).
- 수집: 1초마다 api `/actuator/prometheus`에서 누적 CPU 시간(`process_cpu_time_ns_total`)의 차분, Tomcat 바쁨·현재 스레드, Hikari active·pending을 읽는다. 수집 시각은 요청과 응답의 중간값이다(L2 b2부터 적용, §5).
- 시드: CI E2E와 같은 공연·좌석 시드(`e2e/ci/seed.sql`), 시드 사용자 5,000명, 토큰은 로컬 시험용 서명 키로 발급(`infra/loadgen/mint-tokens.mjs`).
- **L1(스레드)**: 사전 등록 `prereg-L1.md`. 대기 상태 조회 고정 도착률 2,000/s × 45초, 칸마다 같은 rate로 20초 예열(결과 제외). Redis 감속은 `docker update --cpus 0.1`.
  칸: C1 스레드 200·Redis 정상 / C2 200·감속 / C3 400·감속 / C4 400·정상.
  판정: (a) 재현 = C2 바쁨 최대 200·CPU 중앙값 < 1.0코어·C1 바쁨 최대 < 50, (b) 개선 = C3이 C2 대비 처리율 +10% 이상 또는 p95 30% 이상 감소, (c) C4가 C1보다 p95 30% 이상 나쁘면 "정상 조건 악화".
  도착률은 사전 등록 전 Redis 정상 조건 탐색(1,000·2,000·3,000/s, `out/cells.log` 00:25~00:31, 2,000/s에서 바쁨 최대 12·p95 1.8ms)으로 골랐고, C1 기준 "< 50"도 이 탐색에 맞춰 정했다. 감속 조건은 탐색하지 않았다.
- **L2(예매 묶음)**: 사전 등록 `prereg-L2.md`(측정, 비교 아님). IMP-030과 같은 `booking-e2e.js`(입장자 100명, 역할 6종: 정상·경합·더블클릭·실패 후 재시도·포기·1인 한도) 2회, 회마다 새 공연(100석).

## 4. 결과: L1 (로컬 실측, 칸별 1회)

| 칸 | 스레드 | Redis | p95 | p99 | Tomcat 바쁨 최대 | api CPU 중앙값 / 최대 (1초) |
|---|---|---|---|---|---|---|
| C1 | 200 | 정상 | 2.3ms | 5.8ms | 11 | 0.93 / 1.20코어 |
| C2 | 200 | 감속 | 56.3ms | 100.7ms | 198 | 0.84 / 1.14코어 |
| C3 | 400 | 감속 | 63.4ms | 119.4ms | 191 | 0.85 / 1.36코어 |
| C4r | 400 | 정상 | 9.4ms | 267.7ms | 201(1초) | 1.04 / 1.49코어 |
| (사후 추가) C1r · C1r2 | 200 | 정상 | 2.9 · 3.1ms | 8.1 · 8.2ms | 15 · 13 | 0.98 / 1.27 · 1.04 / 1.23코어 |
| (사후 추가) C4r2 | 400 | 정상 | 2.3ms | 6.0ms | 16 | 0.96 / 1.23코어 |

모든 칸에서 도착률 2,000/s를 그대로 받았다(상태 조회 90,001~90,002건/45초, 실패 0·dropped 0). 처리율 차이는 없었고, 차이는 지연과 스레드에서만 났다.
CPU 중앙값은 수집기 60초 전체(부하 약 50초 + 앞뒤 무부하)의 1초 값이다. 부하 구간만 쓰면 C1 0.93·C2 0.89코어로, 방향과 (a)의 "< 1.0" 판정은 같다. p95·p99는 연결 미리 맺기 요청(1,500건, 전체의 1.6%)을 포함한 전체 지연이다.
C1r은 C4r 뒤 스레드를 200으로 되돌리며 돌린 기준선이다.

- **(a) 재현**: 사전 기준(바쁨 최대 200)에 2 모자란 198로 미충족이다. Redis만 느리게 했을 때 CPU는 0.93 → 0.84코어로 조금 줄었고, 바쁜 스레드는 11 → 198, p95는 2.3 → 56ms로 24배가 됐다. CPU에 여유가 있는 상태에서 스레드가 쌓이는 모양은 나타난 것으로 본다.
- **(b) 개선 없음**: Redis가 느린 상태에서 스레드를 400으로 늘려도(C3) 처리율은 같고 p95는 56 → 63ms로 나빠졌다. 병목이 Redis라 스레드를 늘려도 기다리는 줄만 길어진다(추론).
- **(c) 정상 조건**: 사전 등록 칸 C4r은 "정상 조건 악화"로 판정됐다(p95 9.4ms > C1 2.3ms × 1.3). 22초 시점 1초 동안의 스파이크(바쁨 201)가 p95를 올렸다. 사후 추가한 C4r2는 p95 2.3ms로 기준선과 같았다.
- 도구 오류가 난 run은 판정에서 제외하고 다시 측정했다(첫 C4 → C4r, 기준 변경 없음, `out/cells.log`).

## 5. 결과: L2 (로컬 실측, 2회)

| 회 | 1초 CPU 최대 | 예매 구간 CPU 합 | Hikari active 최대 / pending 최대(지속) | 단계별 p95: 선점 · 주문 · 결제 | 진입 p50 |
|---|---|---|---|---|---|
| b1 (이 api 인스턴스의 첫 예매 경로 실행) | 무효(수집기 시각 오류) | 6.4코어·초 | 4 / 32 (표본 2개, ≤2초) | 1,194 · 984 · 656ms | 373ms |
| b2 | 1.85코어 | 4.8코어·초 | 5(풀 상한) / 16 (표본 2개, ≤2초) | 565 · 632 · 423ms | 46ms |

두 회 모두 5xx 0. 구간(START_AT − 2초 ~ + 60초) CPU 합은 창의 첫·끝 표본 누적 CPU 시간의 차다(6.35·4.77코어·초). b1은 스레드를 200으로 되돌리며 api를 다시 띄운 뒤(00:45경, C1r2 시작 때) C1r2 폴링 부하를 받고 난 첫 예매 묶음이고, b2는 새 공연(event 3)이다.
b1의 1초 CPU 최대는 수집기 시각 오류로 무효 처리했고, 수집 시각을 요청·응답 중간값으로 바꾼 뒤 b2를 쟀다(b2 지표 응답 시간 최대 226ms).

- 예매 묶음은 1~2초 동안 코어 2개를 거의 다 쓴다(b2 1초 최대 1.85코어). 구간 합 4.8코어·초 중 묶음 시작 2표본이 약 2.4코어·초이고, 나머지는 이후 예매 처리와 기저(1초 수집 비용 포함)다.
  - 60초로 펴면 전체 약 0.08코어, 묶음 2초만 약 0.04코어(계산)로, AWS 1분 평균 최대 0.03~0.08코어와 같은 규모다(추론. AWS는 api 3개가 묶음을 나눠 받았다).
  - 1분 평균은 1~2초의 포화를 가린다.
- DB 풀 5는 묶음 시작 순간 포화됐다(b2 active 5·pending 16, b1 active 4·pending 32, 각각 연속 표본 2개, ≤2초).
- b1은 이 api 인스턴스가 예매 경로를 처음 실행한 회다. 진입 p50 373 vs 46ms, 선점 p95 1,194 vs 565ms, CPU 합 6.4 vs 4.8코어·초로 무거웠다. 첫 실행 비용(JIT 등)과 맞는 모양이다(1쌍 관찰).

## 6. 조치
설정은 바꾸지 않는다. 이 결과는 후보·유지 근거로만 쓴다([optimization-targets.md](../deployment/optimization-targets.md)에 반영).
- **Tomcat 스레드 200 유지**: 스레드만 포화되는 경우는 하위 의존성(이 실험은 Redis)이 느릴 때였고, 그때 400은 개선이 없었다. 늘릴 근거가 없다(로컬 1회 관측).
- **예매 api CPU 요청량**: 1분 평균만 보고 크게 낮추지 않는다. 예매 묶음은 순간적으로 코어 2개 가까이 쓴다. CPU limit이 없어 요청량을 낮춰도 그 순간 CPU를 쓸 수는 있지만, 같은 노드에 다른 Pod를 함께 놓으면 그 순간 서로 경합한다(추론). 요청량을 낮추려면 노드 합치기 설계와 함께 판단한다.
- **api DB 풀 5**: 줄일 근거 없음. 오히려 늘릴 후보다. DB 연결 예산(하네스 backend 규칙 17, 가용 56)으로 보면 분리 구조 (B)는 api 3 고정이라 (3+1) × 8 + (6+1) × 3 = 53 ≤ 56이다. 규칙 17은 기본 구성 (A)도 검사하며, base HPA 상한 9면 (9+1) × 8 = 80 > 56으로 실패한다. 풀을 8로 올리려면 base `maxReplicas`를 6 이하로 낮추거나((6+1) × 8 = 56) 규칙 17(A)를 바꾸는 결정이 함께 필요하다(계산).

## 7. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대 비교다. k6·DB·Redis가 같은 PC 자원을 나눠 쓰고(코어는 나눠 고정), DB 왕복이 AWS(실측 0.24~1.5ms, [[IMP-034]])보다 짧다. Redis 감속은 CPU 할당량으로 크레딧 고갈 때의 성능 묶임을 흉내 냈다.
- L1은 칸마다 1회(사후 추가 3회 별도), L2는 2회다. 결론은 "스레드 증설의 이득이 보이지 않았다"는 범위로 쓴다.
- 수집 간격은 1초다. b2의 1.85코어는 1초 평균이다.
- 다음 개선: api DB 풀 상향(§6)은 [[IMP-042]]·[[IMP-043]]에서 5 vs 8을 비교했다. 디스크 지연 묶음을 걸러낸 재측정에서 차이가 없어 5를 유지한다.

## 8. 배운 점 (면접 답변용 한 줄)
"스레드가 200에서 꽉 찼다"를 스레드 부족으로 읽지 않고, CPU가 같이 찼는지부터 나눴다. 하위 의존성만 느리게 만든 로컬 실험에서 CPU는 그대로인데 스레드만 쌓였고, 그때 스레드를 400으로 늘려도 나아지지 않아 200을 유지했다. 1분 평균 0.08코어였던 예매 api가 실제로는 1~2초 동안 코어 2개를 거의 다 쓴다는 것도 1초 수집으로 확인해, 평균만 보고 요청량을 줄이지 않았다.
