## 1. 상황 (Context)
README의 "10만 명 / 10초 진입" 수치는 [[IMP-031]] 기준이었다. 그때는 Kafka가 있었고 api 하나가 진입·폴링·예매를 함께 받는 A′ 구성이었다(진입을 api 9개가 받음).
그 뒤 두 가지가 바뀌었다.
- Kafka를 앱에서 뺐다([[ADR-028]]).
- 대기열 전용 Deployment(B)를 운영 기본값으로 정했다([[ADR-027]], #434). 평시에는 api 3 + 대기열 2로 돌고, 오픈 전에 Git PR로 대기열만 6으로 늘린다.

진입을 받는 파드가 api 9개에서 대기열 6개로 바뀌었으므로, 같은 기준으로 다시 재야 README 수치를 B 구성에 붙일 수 있다.

## 2. 문제 정의 + 분류
**운영 기본값인 B 구성(오픈 전 대기열 6)이 공연 오픈 10초 동안 10만 명 진입을 받으면서 정원 초과·정합성 위반 없이 대기 상태를 전달하는가.**
- 계층: 네트워크(ALB 도착)·애플리케이션(대기열 진입·상태 조회)·동시성(입장 정원)·자동 확장(Git 사전 확장 → HPA·CA 인계).

## 5. 판정 도구 종료 코드 2 — 원인과 해석(결과를 본 뒤 내린 해석)
`check-correctness`가 rc=2(판정 불가)로 끝났다. 위반 검사는 모두 0이었고, 실시간 감시기 조회 오류 11틱이 rc를 2로 만들었다.
- 오류 시각: 10:02:00~10:02:50Z. 판정 구간(since ~ until + 30초 = 10:01:43Z)이 끝난 뒤, 감시기가 늦게 종료되던 구간이다.
- 원인(로그로 확인):
  1. 끄기 PR 뒤 대기열이 줄었다.
  2. CA가 노드 `ip-10-0-118-246`을 비웠다(drain 10:02:02~10:03:03Z, `ca.log` "All pods removed").
  3. 그 노드에 있던 Prometheus 파드(1개)가 옮겨지는 동안 감시기 조회가 `fetch failed`로 실패했다.
- 해석: 판정 구간 안 226틱은 모두 값이 있고 위반 0이다. 사후 재확인 109점도 위반 0이다. 그래서 Correctness·Protection을 충족으로 봤다.
  - 이 해석은 **결과를 본 뒤** 내렸다. 사전 등록에는 "판정 구간 밖 조회 오류" 처리가 없었다. `session.log`에 원인과 해석을 시각과 함께 남겼다.
- 같은 drain으로 coredns 1개도 옮겨졌다. 다른 1개는 다른 노드에 있었다(#431 분산).

## 8. 트레이드오프 / 한계 / 다음 개선
- **1회 관측**이다. 통계적 반복이 아니다(사용자 결정).
- 폴링 폭증·예매 묶음을 함께 돌리지 않았다. B의 폴링 폭증 확장과 그때의 예매 지연은 [[IMP-033]]·[[IMP-034]]의 결과(각 2회, 진입 10만이 아니라 대기 인구 6만)다.
- 이벤트 페이지 진입 시 브라우저가 web을 거쳐 api를 부르는 부하(새로고침·포커스 재요청)는 이번 시험에 없다. 발생기는 진입·상태 조회 API를 바로 부른다.
  - 대기열 화면 쪽 web 부하는 #436(정적 경로·prefetch)에서 줄였지만, 클러스터에서 10만 규모로 재지는 않았다.
- 노드 축소가 느리다. 폴링이 끝나고(T0 + 900초) 노드 9 → 7까지 약 8분 더 걸렸다(CA 축소 대기, 실측). 노드-시간 영향은 [[IMP-032]]의 계산 방식으로 따로 계산해야 한다(이번에는 계산하지 않음).
- 실시간 감시기가 Prometheus 단일 파드에 의존한다. CA drain 같은 정상 운영 이벤트에도 판정 도구가 "판정 불가"를 낼 수 있다(§5).
  - 판정 구간 밖 조회 오류를 사전 등록에서 어떻게 다룰지 다음 세션 전에 정해야 한다.

## 9. 배운 점 (면접 답변용 한 줄)
진입을 받는 구조가 바뀌면(api 9 → 대기열 6) 이전 수치를 그대로 붙이지 않고, 같은 판정식을 먼저 등록해 서버가 실제로 받은 요청(ALB 로그)으로 다시 쟀다. 판정 도구가 "판정 불가"를 낸 원인(CA drain → Prometheus 이동)은 로그로 확인하고, 결과를 본 뒤의 해석임을 그대로 남겼다.
