# IMP-033 · 대기열 전용 Deployment(B) vs 통합(A') — 폴링 폭증 중 예매 지연 비교, 측정 절차를 고쳐 다시 잰 A'·B 각 2회

- 날짜: 2026-10-14
- 유형: 정량(실측) — 비용은 계산값. 결과는 **A'·B 각 2회 관측**(v2)이며 통계적 반복은 아니다
- 관련: [[ADR-027]](대기열 전용 Deployment·A'/B 전환), [[IMP-031]](폴링 폭증이 api 전체를 3→9로), [[IMP-026]](판매 상태 캐시), [[IMP-030]](예매 E2E 시험),
  [[TS-050]](세션 기동 장애 — metrics-server 애드온), #398·#399(구조·비용 도구), #401(예매 k6 토큰 SharedArray)
- 벤치 파일: 레포 밖 `artifacts/loadtest/20261014-ab/` — 사전 등록 `platform-prereg.md`(v1)·`platform-prereg-v2.md`(v2), 드라이버 `ab-run.sh`·`ab-run-v2.sh`·`ab-switch.sh`,
  run별 디렉터리(k6·Prometheus 내보내기·API 로그·정합성·비용), 분석 `a1r-vs-a2-analysis.txt`·`b1r-vs-b2-analysis.txt`, `session.log`

## 1. 상황 (Context)
IMP-031에서 폴링 폭증(상태 조회 7,000/s)이 api **전체**를 HPA 3→9로 늘렸다. 좌석·주문·결제를 처리하는 파드가 대기열 때문에 같이 늘고 같은 Tomcat을 나눠 쓴다.
ADR-027은 같은 이미지로 대기열 전용 Deployment를 두고(B), Service 대상만 바꿔 지금 구조(A')와 같은 날 비교할 수 있게 했다. 이 문서는 그 비교다.

## 2. 문제 정의 + 분류
**폴링 폭증 중에도 좌석 선점·주문·결제 지연이 지켜지는가 — 그리고 그 대가(대기열 지연·비용)는 얼마인가.**
- 계층: 스레드·커넥션 풀·파드 확장(HPA·Cluster Autoscaler) — 같은 파드 예산(9)을 어떻게 나누느냐의 문제.

## 3. 측정 방법
- 같은 세션·클러스터·이미지(`2f1f7ff`)·Redis(`cache.m7g.large`, TS-049 조치)·판매 상태 캐시 TTL 1초. 파드 예산 9: A' api 3~9 / B api 3 고정 + 대기열 2~6.
- run 하나(T0 기준): 대기 인구 60,000 진입(1,000/s × 60초) → 전원 폴링 25분, 예매 ①(폭증 전 기준) 100명, 폴링 폭증 7,000/s × 480초, 예매 ②(폭증 중) 100명
  (booking-e2e — 입장→선점→주문→결제, 역할 6개, 결제는 세션 한정 mock). 정합성은 check-correctness(대기열)·check-booking(DB 13개 기대값).
- 1차 판정(사전 등록): run마다 `R = p95(②) / p95(①)`(hold·주문). v2는 **가장 보수적인 쌍** `min(R_A') / max(R_B) ≥ 2`(hold·주문 둘 다)면 "B 개선".

## 4. v1 — 측정 절차의 왜곡을 찾은 1차 시도 (결과는 판정에 쓰지 않음)
| run | 정합성 | hold p95 ①→② | 주문 p95 ①→② | R hold/주문 |
|---|---|---|---|---|
| A' a1r | 판정 불가 | 1,067 → 702 | 1,130 → 1,076 | 0.66 / 0.95 |
| B b1r | 판정 불가 | 511 → 299 | 268 → 283 | 0.585 / 1.06 |
| A' a2 | 위반 없음 | 329 → 915 | 319 → 1,149 | 2.78 / 3.60 |
| B b2 | 위반 없음 | 292 → 248 | 211 → 218 | 0.85 / 1.03 |

같은 A'의 R이 0.66과 2.78로 갈렸다. 원시 데이터로 나눴다 — 아래 각 줄에서 관측(실측)과 원인 귀속(추론)을 구분한다.
- **a1r 예매 ①은 예매 경로 첫 실행**: 직전 hold 0건, JIT 7~9초/파드, Hikari 대기 8~35초 → ①이 3배 느려 R이 작아졌다.
- **a2 예매 ②는 폭증 대비 시점이 밀림**: 폭증 토큰 배포 89초로 폭증이 50초 늦게 시작 → ②(T0 고정)가 HPA 새 파드 Ready 직후에 걸려 R이 커졌다.
- **b1r 폭증 p95 483ms(b2 7ms)**: 관측(실측) — 폭증 +22초에 대기열 파드가 3→2로 줄었고(HPA 이벤트·ALB 대상별 요청), 남은 웜 파드 2개가 Tomcat busy 200·CPU 약 1.9코어,
  ALB 기준 지연은 Spring 타이머 밖(서블릿 진입 전), 부하·Redis·GC는 같았다. 원인 귀속(추론) — 그 축소가 폭증과 겹친 것(300초 축소 안정화 창 만료)이 주원인, B 구조 자체가 아니라 폭증을 맞은 순간의 파드 수. 1회 관측이다.
- 측정 절차 사고: a1 무효(예매 k6가 10만 명 토큰을 VU마다 파싱 → 발생기 메모리 고갈 → #401), a1r·b1r 정합성 판정 불가(드라이버의 리셋 간격·감시 시간 실수).

## 5. v2 — 절차를 고쳐 다시 잰 A'·B 각 2회 (1차 판정)
바꾼 것(사전 등록, v1 결과를 **본 뒤** 설계): 시작 api 파드만 워밍업(폭증 중 새 파드는 그대로), 폭증 토큰 미리 배포·예매 ②는 폭증 실행 + 200초,
각 구조가 스스로 안정된 상태(최소 파드 Ready·HPA 최소·CA 후보 없음 3분 유지)에서 시작. 순서 B → A' → A' → B. v2 사전 등록 확정 13:40 KST, 첫 run 시작 13:44.
**4 run 모두 유효**(정합성 위반 0, check-booking 통과, 워밍업 rc 0·① 진입 전 종료). 워밍업의 사전 등록 사후 확인(① 구간 파드별 JIT 시간)은 **하지 못했다**(JIT 지표를 내보내지 않음) —
간접 근거(같은 지표끼리): hold p95 — ① 194~236ms, 워밍업 묶음 242~324ms, v1 콜드 ①(a1r) 1,067ms. ①이 워밍업보다도 빠르고 콜드 ①보다 훨씬 낮아 워밍업 뒤 상태로 본다.

| | v2-b1 (B) | v2-a1 (A') | v2-a2 (A') | v2-b2 (B) |
|---|---|---|---|---|
| 시작 노드 | 6 | 4 | 4 | 5 |
| hold p95 ① → ② (ms) | 212 → 256 | 236 → 2,400 | 231 → 2,017 | 194 → 272 |
| 주문 p95 ① → ② | 180 → 260 | 216 → 2,602 | 211 → 1,559 | 188 → 211 |
| 결제 p95 ① → ② | 195 → 224 | 202 → 1,633 | 254 → 1,954 | 178 → 184 |
| R hold / 주문 | 1.21 / 1.44 | 10.2 / 12.0 | 8.73 / 7.39 | 1.40 / 1.12 |
| 예매 오류 | 0 | 0 | 0 | 0 |
| 폭증 상태 조회 p95 / p99 | 259ms / 2.1s | 18ms / 2.2s | 13ms / 1.4s | 523ms / 0.9s |
| 폭증 실제 송신(송신 ÷ (송신+dropped)) | 315.7만(93.9%) | 325.5만(96.8%) | 328.2만(97.6%) | 330.0만(98.1%) |
| 노드-시간 · 노드 비용(계산) | 3.17 · $0.37 | 2.70 · $0.32 | 2.74 · $0.32 | 3.45 · $0.41 |

**1차 판정(사전 등록 규칙)**: `min(R_A')` hold 8.73·주문 7.39 / `max(R_B)` hold 1.40·주문 1.44 = **6.2배·5.1배 ≥ 2** → **"B 개선"(A'·B 각 2회 관측, 운영 관점)**.
오류 조건은 4 run 모두 오류 0이라 해당 없음, 악화 조건 불성립, 상충 없음.

## 6. 원인 검증 — A'의 폭증 중 예매 지연은 어디서 오나 (실측, 출처 주의)
Prometheus 파드별 서버 시간(예매 ② 구간: 폭증 실행 + 170~500초, hold·주문·결제 경로).
- 기존 파드·B 값과 구간 정의·처리량: `perpod-analysis.mjs`(`increase()` 방식, 세션 당시 진본).
- 새 파드 값: 위 방식은 새 시계열의 첫 수집 전 값을 세지 않아 새 파드가 빠졌다 — 그 뒤 **원시 누적 카운터**로 다시 셌다(새 파드는 폭증 뒤 생겨 누적값 = 받은 예매 요청 전체).
  이 명령은 실행 당시 파일이 아니었고, 원문과 출력을 대화 기록에서 옮겨 `perpod-raw-counter.sh`로 보존했다.
**출처: 세션 중 조회 결과를 `session.log`("[분석 — 파드별 예매 ②(실측)]")에 기록 — 원시 조회 응답은 보존하지 않았고 클러스터 철거로 재조회할 수 없다.**
분모는 Spring이 센 예매 경로 요청(A' 288건, B 296건)이다(클라이언트 기준 비대기열 요청은 run마다 283건 — 집계 정의가 다르다).
| | 새 파드(폭증 중 생성) | 기존 파드(워밍업됨) |
|---|---|---|
| A' v2-a1 | 새 파드 6개 중 예매를 받은 5개, 예매 요청 176건(약 61%), 서버 평균 197~1,289ms | 112건, 24~37ms |
| A' v2-a2 | 6개, 175건(약 61%), 242~891ms | 113건, 36~53ms |
| B v2-b1·b2 | 예매 파드는 늘지 않음 — 0건 | 296건씩, 46~117ms |
→ A'에서는 폭증으로 늘어난 **새 파드가 예매 요청의 약 61%를 받아** 느렸다. 새 파드가 "차가워서"(JIT 미완) 느렸다는 것은 v1 분석(a2 새 파드 JIT·Tomcat)에 근거한 추론이다 — v2에서 JIT는 재지 않았다.
B는 예매 파드가 고정이라 이 경로가 없다. 참고로 B 예매 파드의 서버 평균(46~117ms)은 A' 기존 파드(24~53ms)보다 높다 — B는 api 3개가 예매를 전부 받는다.
폭증 480초 서버 처리량(상태 조회, `sum(rate(http_server_requests_seconds_count{uri=~".*queue/status.*"}[480s]))`를 폭증 실행 + 500초 시점에 조회 — `perpod-analysis.mjs`)은 네 run 모두 8,396~8,681/s로 비슷했다(기본 폴링 포함 — 내보낸 `rate[1m]`의 구간 평균과는 방법이 달라 값이 다르다).

**사후 분석(2026-10-19) — 새 파드가 왜 느렸나, 자원 지표로 좁히기.** 같은 v2 run의 보존된 내보내기(`prom/`, 10초 간격, CPU는 `rate[1m]`)로 예매 ② 구간(폭증 실행 + 200~500초)의 파드별 자원을 새·기존 파드로 나눠 봤다(`v2-newpod-resources.cjs` → `v2-newpod-resources.txt`, 레포 밖 세션 폴더).

| A' 예매 ② 구간 (v2-a1·a2) | 기존 파드 3개 | 새 파드 6개 |
|---|---|---|
| CPU 평균 / 최대 (코어, 요청 1.1) | 0.45~0.50 / 0.57~0.68 | 0.37~0.63 / 0.45~1.62 |
| Hikari 대기(`hikaricp_connections_pending` 최대) | 0 | 0 |
| Tomcat 바쁨 스레드 평균 / 최대 | 1~2 / 3~5 | 2~11 / 4~27 (v2-a1의 1개만 한 표본 200) |
| GC 정지 비율(`rate[1m]`) | 0.0009~0.0024 | 0.0012~0.0033 |

- 관측(실측): 새 파드와 기존 파드의 CPU는 같은 범위(요청의 약 절반)이고, DB 커넥션 대기는 양쪽 모두 0, GC는 양쪽 모두 미미했다. 기존 파드도 같은 대기열 폴링을 함께 받았는데 예매 서버 평균은 24~53ms였다.
- 그래서 **CPU·DB 커넥션·GC는 새 파드만 느린 것(197~1,289ms)을 설명하지 못하고, "대기열과 예매가 같은 파드 자원을 나눠 써서(경합) 느렸다"도 이 데이터와 맞지 않는다.** 원인은 "새로 뜬 파드"라는 점으로 좁혀진다.
- 남는 후보(추론, 미검증): 새 파드의 첫 실행 비용(JIT 등 — v1 a1r에서 예매 경로 첫 실행 파드의 JIT 7.2~9.2초/파드, Hikari 대기 합 8~35초를 관측한 간접 근거). JIT 지표는 내보내지 않아 직접 확인하지 못했다. 10초 표본·1분 rate라 짧은 순간 포화는 놓칠 수 있고, 새 파드의 노드·AZ 배치 영향([[IMP-034]] §6의 DB 왕복 차이)도 배제하지 않았다.
- B의 예매 파드(api 3)는 같은 구간 CPU 평균 0.01코어·Hikari 대기 0·Tomcat 바쁨 0이었다(v2-b1·b2).

## 7. 판정 결과 해석과 한계
- **이 결과가 답하는 질문은 운영 관점이다**: 현재 설정(파드 예산 9·HPA 정책·구조별 기본 노드)대로 운영했을 때 이 2회씩의 관측에서는 폭증 중 예매 지연을 B가 지켰다.
  대기열 분리만의 순수 효과가 몇 배인지는 이 설계로 분리하지 않았다(노드 수·확장 시점까지 같게 만든 별도 실험 필요). "분리가 N배 빠르게 한다"로 쓰지 않는다.
- **설계가 B 쪽으로 기운다(사전 명시)**: 시작 파드만 워밍업한 결정은 A'에 유리했던 왜곡(a1r)을 없애고, 새 파드를 그대로 둔 결정은 A'에 불리한 동작(a2)을 남긴다.
  둘 다 근거가 있지만(앞은 측정 절차의 왜곡, 뒤는 A' 구조의 실제 동작) 합치면 "B 개선" 쪽으로 기운다.
- **B의 대가**: 폭증 상태 조회 p95 A' 13~18ms vs B 259~523ms(대기열 HPA 상한 6 도달). p99는 양쪽 모두 0.9~2.2초. 노드 비용 약 +15~28%(계산, B는 기본 노드 1~2대 추가).
- **B 두 run의 시작 노드가 6·5로 달랐다** — 대기열 파드 배치에 따라 5/6대에서 안정되고 CA가 더 줄이지 않는다. 같은 초기 조건의 반복으로 보지 않는다.
- **사전 등록을 결과를 본 뒤 바꾼 것(공개)**: v1에서 a1r·b1r·a2 결과와 a1r 기준 1차 판정("차이 주장 안 함")을 본 뒤, 정합성 판정 불가 run을 빼는 해석을 엄격히 적용해(b2 결과 전) v1 판정이 "B 개선(1회)"으로 바뀌었다.
  v1은 최종 판정에서 제외했으므로 결론에는 영향이 없다. v2 설계는 v1 결과 전체를 본 뒤 만들었고 첫 run 전에 확정했다.
  사전 등록 파일의 일부 변경 시각을 짐작으로 잘못 적었다가 정정했다(파일 수정 시각 기준 — 모든 v2 변경은 첫 run 전).
- 2차 관찰 중 폭증 시작 시점 Ready 파드 수·확장 속도(HPA desired→Ready)·처리 요청당 비용은 이 문서에 정리하지 않았다(데이터는 run 디렉터리의 `prom/hpa_desired.json`·`pod_ready.json`에 있음).
- 표본은 구조별 2회다.

## 8. 함께 확인한 것
- **판매 상태 캐시(IMP-026, TTL 1초)**: 진입 구간 [T0, T0+75초] DB 커넥션 획득 ÷ 진입 요청 = 0.012~0.021(v1 a1r·a2·b2 — 세션 중 조회한 세 run, 스케줄러 사용 포함) — 캐시 없을 때 1.01 대비 약 1/48~1/84(계산). 진입 요청 수(6.1만~6.9만)는 `increase()` 외삽값이라 클라이언트 송신(61,020)과 조금 다르다.

## 10. 배운 점 (면접 답변용 한 줄)
