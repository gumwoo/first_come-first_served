# IMP-020 · 좌석맵 조회 캐시, 그리고 캐시만으로는 커넥션이 줄지 않았다

- 슬라이스: `S04`(좌석) / `S10`(부하)
- 날짜: 2026-08-17
- 유형: 정량
- 관련 PR: #242(스위치) → #243(활성화) → #244(트랜잭션 밖으로) → 본 문서
- 벤치 파일: `benchmarks/cache-experiment/README.md`

## 1. 상황

"조회 캐시를 넣으면 얼마나 빨라지나"를 재려고 했다. 캐시 대상을 근거로 정하기 위해, 캐시를
넣기 전에 엔드포인트별 비용부터 쟀다(0단계).

## 2. 문제 정의 + 분류

- 계층 분류: 애플리케이션 코드 + DB(조회 비용), 그리고 측정 중 드러난 트랜잭션·커넥션 풀
- 왜 그 계층인가: 0단계에서 `/events/{id}/seats`가 요청의 50%인데 API CPU 비용의 57%를
  차지했다. 요청 비율과 비용 비율이 다르다는 것이 이 개선의 출발점이다.

## 3. 증상 (측정된 증거)

측정 방법: k6 `constant-arrival-rate` 400 rps · 90초, 클러스터 밖(노트북)에서 실행.
CPU는 `increase(container_cpu_usage_seconds_total[구간])`를 구간 끝에서 평가해
실제 완료 요청 수로 나눈다. idle은 같은 파드 수 기준으로 뺀다.

before (캐시 없음, 5회 측정으로 수렴 확인):

| 지표 | 값 |
|---|---|
| api CPU | 2.55 ms/req |
| node CPU | 5.39 ms/req |
| 서버 p95 / p99 | 11.1ms / 24.5ms |
| api 파드(400 rps 처리) | 7 |

0단계에서 잰 엔드포인트별 비용(요청당 증분 CPU, 2회 평균):

| EP | api | web | node |
|---|---|---|---|
| **seats** | **2.57** | 2.08 | **4.99** |
| list | 2.06 | 2.09 | 4.51 |
| detail | 1.71 | 2.19 | 4.33 |

web 계층은 엔드포인트별 편차가 작다(2.08~2.19). 엔드포인트 작업과 독립적으로 보이는 공통 web 계층
비용이 있다는 뜻이다(프록시·TLS·직렬화·런타임 단위로는 분해하지 않았다).

그래서 캐시 효과에는 상한이 있다. 혼합 요청당 node 4.71ms 중 api는 2.24ms(48%)다.

## 4. 가설

`seats` 조회의 DB 왕복과 객체 생성을 없애면 api CPU가 줄어든다. 상한은
api 비용이 0이 되는 가정에서 1.89배(seats 단독 워크로드 기준, 계산).

## 5. 해결

`seat.map-cache-ttl-ms`(기본 0=꺼짐) 스위치로 Redis TTL 캐시를 넣었다.
같은 바이너리에서 설정만 바꿔 AS-IS/TO-BE를 재기 위해서다.

### 캐시 hit에도 커넥션을 빌리던 트랜잭션 경계

캐시를 켜고 커넥션 획득 횟수를 쟀다.

```
DB 커넥션 획득 36,173회 / 요청 36,002건  ≈  1.005 회/요청
```

캐시가 hit해도 커넥션을 요청당 1회씩 빌리고 있었다. `SeatService`가 클래스 레벨
`@Transactional(readOnly = true)`라, 캐시에서 값을 돌려주더라도 그 전에 프록시가 트랜잭션을
열고 Hibernate가 커넥션을 획득한다.

`getSeats`를 `@Transactional(propagation = NOT_SUPPORTED)`로 빼서 트랜잭션 밖에서 돌게 하고,
miss일 때만 프록시를 거쳐 `loadSeatMap`을 부르도록 고쳤다(#244).

## 6. 재측정

| | AS-IS | 캐시 ON + tx 밖 | 감소 | 배수 |
|---|---|---|---|---|
| **api CPU** | 2.55 ms/req | **1.56** | 39% | **1.63배** |
| **node CPU** | 5.39 ms/req | **3.89** | 28% | **1.38배** |
| **서버 p95** | 11.1 ms | **4.2** | 62% | |
| **서버 p99** | 24.5 ms | **9.7** | 60% | |
| **DB 커넥션/요청** | - | **0.025** | | (tx 안 대비 40배↓) |
| **api 파드** | 7 | **5~6** | | |

같은 400 rps에서 HPA replica가 7 → 5~6으로 줄었다. HPA가 CPU 지표로 replica를 정하므로,
CPU 감소와 같은 신호에서 나온 관측이다.

이론 상한 1.89배와 실측 1.38배의 차이는 캐시 조회·역직렬화 비용과 web 공통 비용이 남는 몫이다.

### stampede 관측

```
TTL 2초 × 90초 = 45회 만료
897.6 acquire / 45 ≈ 20회/만료   ← 단순 환산값
```

전체 커넥션 획득을 TTL 만료 횟수로 나눈 계산값이다(최초 fill 등 다른 miss 포함 가능,
burst 크기를 직접 추적한 값은 아니다). single-flight가 없는 구조에서 예상되는 방향이며,
서버 p99는 9.7ms였다.

## 7. 측정 조건

- AS-IS는 5회 측정으로 수렴을 확인했고, TO-BE는 1회 측정이다. 워밍업은 300초이며, AS-IS가
  0단계 seats 값(2.57)과 일치한다.
- 파드 수가 다르다(7 vs 5~6). idle은 파드당 상수로 환산해 보정했다.
- 표의 TO-BE는 캐시와 트랜잭션 경계 변경(#244)을 함께 적용한 값이다. 두 효과를 따로 나눈
  값은 없다.
- 노트북에서 인터넷 경유로 부하를 걸었고, 판단은 서버 지표로 했다.
- 부하 발생기 문제가 난 run 1회는 판정에서 제외했다.

## 8. 다음: 운영에 켜려면 무엇이 필요한가

운영 적용의 조건은 정확성이다. 그래서 측정 후 `SEAT_MAP_CACHE_TTL_MS`를 0으로 되돌렸다.

설정으로 캐시 기능만 비활성화했고, #244의 트랜잭션 경계 변경은 유지된다. 캐시가 꺼진 경우에도
DB 조회는 짧은 read-only 트랜잭션 안에서 수행된다(실험 전에는 `getSeats()` 자체가 클래스 레벨
트랜잭션 안이었다).

```
현재(캐시 OFF)                                   실험 전
SeatQueryService.getSeats  NOT_SUPPORTED        getSeats  @Transactional(readOnly)
   └ SeatMapLoader.load  @Transactional(read)      └ (같은 트랜잭션 안에서 DB 조회)
```

> 클래스 구성은 [[ADR-019]] 3단계에서 바뀌었다. 위 §5·§6의 `SeatService`·`self.loadSeatMap`은
> 측정 당시(#244)의 이름이다. 지금은 조회가 `SeatQueryService`(캐시) → `SeatMapLoader`(읽기
> 트랜잭션)로 나뉘어 있고, 트랜잭션 경계와 캐시 동작은 그대로다.

좌석은 단순 조회 데이터와 달리 재고성 상태다. TTL 동안 이미 선점된 좌석이 `AVAILABLE`로
보인다. 최종 선점은 조건부 UPDATE가 막지만([[ADR-003]]) 사용자가 고른 뒤 거절당하는 충돌이
늘어난다. 이 동작은 테스트로 고정해 두었다
(`SeatMapCacheIntegrationTest.TTL_동안_좌석_상태_변경이_보이지_않는다`).

운영으로 올리려면:

```
read → hit → return
     → miss → DB → put (짧은 TTL)

seat.held / released / expired → 해당 eventId 캐시 invalidate
이벤트 유실                    → TTL 만료로 최종 복구
```

그리고 single-flight를 함께 본다(위 stampede).

1.38배와 무효화·single-flight 복잡도 중 무엇을 택할지는 별도 판단이다. 이 문서는 그 판단에
필요한 수치를 제공하며, 도입을 권하지는 않는다.

## 9. 측정 절차에서 고정한 조건

측정 중 수치를 흔든 요인과 이를 고정한 방법이다.

| 요인 | 관측 | 조치 |
|---|---|---|
| 콜드 스타트 | seats @200이 p95 4.65초 → 재실행 30.9ms(150배) | 엔드포인트별 자기 경로 워밍 |
| 파드 수 변동 | `increase()`가 60% 높게, pending 191 | 구간 내 파드 수 min/max 검증 |
| 측정 동시 실행 | 두 k6가 각 400 rps → p95 20초 | 배경 작업 종료 확인 후 시작 |
| 게이지 순간값 | pending "0" → 실제 구간 최대 215 | `max_over_time` |
| 중첩 백그라운드 | 워밍업 k6 유실 → 무한 대기 | 워밍업을 전경 고정 시간으로 |

수치가 예상과 다르면 시스템보다 측정 조건이 고정됐는지 먼저 확인한다.
