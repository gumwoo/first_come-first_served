# IMP-011 · 브로커 장애 중 이벤트 유실 — 트랜잭셔널 아웃박스

- 슬라이스: `S08`(정합성 보강 — 1단계 아웃박스)
- 날짜: 2026-07-31
- 유형: 정량(통합 테스트로 측정) — 정합성·내구성
- 관련 커밋/PR: PR #138(데이터 계층)·#139(릴레이·발행 이관)
- 벤치 파일: [`benchmarks/outbox-delivery-before.json`](../../benchmarks/outbox-delivery-before.json)
  → [`benchmarks/outbox-delivery-after.json`](../../benchmarks/outbox-delivery-after.json)
- 관련: [[ADR-010]](아웃박스 설계), [[ADR-008]](Kafka 백본·한계 2 해소), [[IMP-008]](결제 멱등)

> 흐름: 문제 정의 → 증상(수치) → 가설 → 도구로 검증 → 해결 → 재측정 → 한계.

## 1. 상황
결제가 커밋되면 `order.paid`를 Kafka로 발행하고 소비자가 SSE로 알린다. 불변식은 **"결제가 커밋됐으면
그 사실을 알리는 이벤트는 반드시 전달된다"**(적어도 한 번). 그런데 발행이 커밋 **밖**에서 일어나
브로커 장애·프로세스 크래시가 이 불변식을 깰 수 있었다.

## 2. 문제 정의 + 분류
- 계층 분류: **정합성/내구성**(DB 커밋과 외부 발행이 서로 다른 원자 단위).
- 구 구조: `finalizePaid` → `@TransactionalEventListener(AFTER_COMMIT)` → `kafkaTemplate.send(...)`,
  그리고 **발행 실패는 로그만 남기고 삼켰다**(결제를 되돌릴 수 없으니 알림은 best-effort로 감수).
- 결과: 커밋 직후 크래시하거나 브로커가 죽으면 **재발행할 근거가 DB 어디에도 없어 영구 유실**.
  ADR-008이 "한계 2 — 알림 유실 가능"으로 명시했던 바로 그 구멍.

## 3. 증상 (측정된 증거)
- 측정: `OutboxDeliveryIntegrationTest.IMP011_브로커_장애중_이벤트_유실_before_after` —
  발행이 실패하는 장애 창을 결정적으로 만든 뒤(스텁), **복구 후 소비자에 실제 도달한 건수**를 카운트.
- before:
  | 지표 | 값 |
  |------|----|
  | 시행(trials) | 10 |
  | 발행 성공 | **0** |
  | 소비자 도달 | **0** |
  | 복구 가능(재발행 근거 보유) | **0** |
  | **유실** | **10** |

## 4. 가설 (검증 전)
- 발행이 트랜잭션 밖 부수효과라, **커밋된 사실이 DB에 남지 않은 채** 네트워크로만 전달된다 →
  전달이 실패하는 순간 복구 수단이 사라진다. 이벤트를 **커밋 안으로 끌어오면** 실패는 "유실"이 아니라
  "재시도 대상"이 된다.

## 5. 검증 (도구로 확인 → 확정 원인)
- 도구: Testcontainers(Postgres·Redis·Kafka) 통합 테스트. `KafkaTemplate.send`를 실패시켜 장애를 재현하고,
  같은 장애 창에 두 경로(naive/outbox)를 나란히 넣어 **복구 후 도달 건수 차이**로 원인을 특정.
- 결과: naive는 10/10 유실, 복구해도 재발행할 대상이 0건 → "발행이 커밋 밖"이 확정 원인.

## 6. 해결 + 재측정
1. **같은 트랜잭션에 적재** — `finalizePaid`가 `outbox_events`에 INSERT(롤백되면 행도 사라져 유령 이벤트 0).
2. **릴레이가 발행 책임** — PENDING을 배치로 발행하고 **성공을 확인한 뒤** PUBLISHED로 마킹
   (publish-then-mark). 실패하면 `attempts++`·PENDING 유지 → 다음 틱 재시도. `@SchedulerLock`으로 단일 실행.
3. **소비자 멱등** — 재발행으로 생기는 중복은 `eventId`(= 아웃박스 행 PK) 기반 Redis SETNX가 흡수.
- after:
  | 지표 | 값 |
  |------|----|
  | 시행 | 10 |
  | 장애 중 보존(PENDING) | **10** |
  | 복구 후 발행 | **10** |
  | 소비자 도달 | **10** |
  | **유실** | **0** |

**브로커 장애 중 이벤트 유실 10 → 0.** 정합성은 "전달을 잘하기"가 아니라 **커밋 경계 안에 사실을 남기고
재시도 가능하게 만드는 것**이 보장한다 — 분산 트랜잭션(XA) 없이 DB↔Kafka 정합성을 얻는 방식(ADR-010).

## 7. 한계
- **at-least-once의 대가는 중복**: 릴레이 재시도·리밸런스로 같은 이벤트가 두 번 전달될 수 있다 →
  SETNX 멱등으로 흡수하되, 멱등 저장소(Redis) 장애 시엔 fail-open이라 중복 broadcast가 가능(SSE라 무해).
- **발행 지연**: 즉시 발행 → 릴레이 주기(기본 1s)만큼 늦다. 실시간성이 더 필요하면 주기를 줄이거나
  CDC(Debezium)로 전환(ADR-010에서 인프라 무게 때문에 현 규모엔 기각).
- **장애 재현은 결정적 스텁**: 실제 브로커 다운/네트워크 파티션이 아니라 발행 실패를 강제해 측정한다.
  실 클러스터에서의 페일오버 거동은 S09 배포 후 브로커 종료 실증에서 별도 확인.
- **범위는 `order.paid` 1종**: 좌석·큐 SSE는 여전히 best-effort 직접 전달(ADR-008 점진 이관 계승).
- **아웃박스가 못 닫는 클래스**: PG 승인 성공 후 크래시로 트랜잭션이 롤백되면 DB에 행 자체가 없다 →
  이건 정산(Reconciliation)·보상의 몫으로 **S08 2단계**에서 다룬다.
