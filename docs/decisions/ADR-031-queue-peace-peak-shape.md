# ADR-031 · 대기열 Pod를 평시·피크 모양으로 나누고 사전 확장 PR에서 바꾼다: 평시 노드 5 → 3대

- 상태: Accepted
- 날짜: 2026-10-26
- 슬라이스: `S10`(부하·확장)
- 관련: [[ADR-025]](1100m·Git 사전 확장), [[ADR-026]](배치 정책과 requests 분리), [[ADR-027]](대기열 전용 Deployment), [[IMP-038]](오픈 부하의 동거 경합), [[IMP-039]](평시 합치고 오픈 전 떼기), [[IMP-047]](api 회피 규칙), [[IMP-048]](예매 api 평시 기준 200m), [[IMP-049]](이 결정의 시뮬레이션·로컬 측정), `docs/testing/traffic-profile.md`

## 1. 맥락
운영 기본값 B에서 평시 노드는 5대였다. api 3개와 대기열 2개가 모두 requests 1100m라 Pod 하나가 노드 하나를 쓴다.
- 1100m는 오픈 순간 진입 burst를 받는 Pod의 값이다([[ADR-025]]). 평시에는 열린 대기열이 없어 대기열 Pod의 부하가 0에 가깝고(`traffic-profile.md` §2), 예매 api의 평시 조회 CPU는 1초 p90 0.081~0.139코어였다([[IMP-048]]).
- requests는 Pod 템플릿에 있어 같은 Deployment는 같은 값을 쓴다. 예매 api만 낮추면 대기열 1100m가 api 노드에 들어가지 못해 평시가 줄지 않았고, 대기열 회피 규칙을 풀면 오픈 순간에 동거가 생겼다([[IMP-048]]).
- 오픈 부하에서 api·대기열 동거는 예매 p95를 41~87% 늘리고 대기열 Tomcat 스레드를 포화시켰다([[IMP-038]]). 오픈 순간에는 분리가 필요하다.

## 2. 결정
1. **B의 예매 api**: requests 200m(평시 기준, [[IMP-048]]), 노드마다 하나(hostname 분산 maxSkew 1·DoNotSchedule). `components/queue-split`이 base 값을 바꾼다. A'(통합)에서는 base 1100m 그대로다.
2. **대기열 평시 모양**(`components/queue-split/queue-deployment.yaml`): requests 200m, api 회피는 preferred(weight 100), 대기열 hostname 분산(maxSkew 1·DoNotSchedule).
3. **대기열 피크 모양**(`components/queue-peak`): requests 1100m, api 회피 required. 오픈 사전 확장 때만 overlay에서 켠다.
4. **절차**(`docs/testing/loadtest-diag-runbook.md` §2b, 한 단계에 PR 하나):
   - 오픈 최소 15분 전: queue-peak를 켜고 대기열 HPA 하한을 6으로 올린다.
   - 오픈 뒤: 하한만 2로 되돌린다. 피크 모양은 유지하고, HPA가 폴링 부하에 맞춰 줄인다.
   - 대기열이 빈 뒤(대기자 0): queue-peak를 끈다. CA가 평시 3대로 줄인다.
5. **하네스**:
   - k8s ⑩-d: 평시 대기열은 api 회피 term이 preferred나 required로 있어야 하고, queue-peak는 required로 바꿔야 한다.
   - k8s 11: 대기열 하한을 올리면 queue-peak도 켜야 한다. 하한을 올렸거나 queue-peak가 켜져 있으면 event·off-by가 있어야 하고, off-by가 지나면 실패한다. queue-split 없이 queue-peak만 켤 수 없다.
   - ⑩-b 허용 목록에 대기열의 preferred 회피 term을 더한다.

## 3. 근거
- **피크 구성이 측정한 구성과 같다.** queue-peak를 켠 렌더링은 대기열 1100m·required 6개, api 3개(노드마다 하나)로 지금까지 오픈 성능을 측정한 배치(api 3 + 대기열 6 = 노드 9, 동거 0)와 같다. 그래서 [[IMP-035]]·[[IMP-047]] 근거를 그대로 쓴다.
  예매 api만 200m로 바뀌었는데, CPU limit이 없어 api 노드의 남는 CPU를 쓸 수 있고 api 노드에는 api와 web만 있다.
- **전환 한 바퀴가 된다**(kwok, [[IMP-049]], 세 적용 순서 × 2회 모두):
  - 평시 3대, 사전 확장 9대에서 정체·동거 0.
  - 피크 중 CA 축소 흉내에도 api 노드를 지우지 못했다.
  - 오픈 뒤 다시 3대.
  - [[IMP-039]]에서 한 PR 전환이 막힌 것은 롤링 대상이 api였기 때문이다(새 1100m api가 10번째 노드를 요구). 여기서는 롤링 대상이 대기열이고, 옛 평시 Pod는 api 노드에 얹혀 있어 노드를 따로 쓰지 않는다.
- **분산 규칙 두 개는 시뮬레이션에서 나온 실패를 막는다.**
  - api 분산이 없으면 피크 중 CA가 사용률 0.43~0.44인 api 노드를 비워 api 둘이 한 노드에 모였다(6/6).
  - 대기열 분산이 없으면 평시 대기열 둘이 한 노드에 놓여, 그 노드를 비울 때 PDB(minAvailable 1)에 막혀 오픈 뒤 4대에 머문 경우가 있었다(2/6).
- **평시 동거 영향은 30% 기준 안이었다**(로컬, [[IMP-049]]). 평시 조회 33 req/s와 예매 묶음 100명을 걸고 대기열을 api와 같은 코어에 두었다. 4쌍 모두 예매 p95 비율 0.83~1.23, 조회 p95 비율 0.81~1.19였다(사전 등록 판정 "차이 작음"). 대기열 CPU는 0.01코어였다.
- **DB 커넥션 예산은 그대로다.** Pod 수(api 3, 대기열 2~6)와 풀(5, 3)이 같아 (3+1)×5 + (6+1)×3 = 41 ≤ 56이다(하네스 backend 규칙 17).
- **절감**(계산, 평시가 하루 종일이라는 가정, 노드 EC2만): (5 − 3) × 24시간 × 30일 × $0.118/h([[IMP-032]] 단가) ≈ 월 $170.

## 4. 대안
- **현행 유지(평시 5대)**: 측정 근거는 가장 많지만 평시 노드 2대가 열린 대기열 없이 대기열 Pod 하나씩만 담는다.
- **Deployment를 평시용·피크용 둘로**: HPA는 0개로 줄일 수 없어 평시에도 큰 Pod가 남는다. 크기가 다른 Pod가 한 Service 뒤에 섞이고, 전환 순서를 두 Deployment에 걸쳐 맞춰야 한다.
- **Pod 크기를 작게 고정하고 개수만 늘리기**: 대기열 12개면 DB 커넥션이 (3+1)×5 + (12+1)×3 = 59 > 56이 되어 풀을 다시 나눠야 하고(계산), 피크 처리량을 새 Pod 크기로 다시 재야 한다.
- **평시 대기열 1개**: 1대만 줄고 평시 대기열이 단일 Pod가 된다.
- **평시에 api만 줄이고 오픈 전 api를 롤링([[IMP-039]])**: 한 PR에서 바꾸면 롤링이 노드 상한에 막혀 두 PR로 나눠야 했다. 당시 평시 가정(폴링 300/s)에서는 동거 판정이 "경합 있음"이었다.

## 5. 결과와 남는 것
- 사전 확장 PR에 queue-peak 한 줄이 더해지고, 되돌림이 두 단계(하한 → 모양)가 된다. 모양을 늦게 끄면 그만큼 노드 비용이 남는다. off-by와 하네스 규칙 11이 잊힘을 잡지만 CI backend job이 도는 PR에서만 막는다.
- 대기자가 남은 채 평시 모양으로 돌리면 HPA가 늘린 작은 대기열 Pod가 api 노드에 함께 놓일 수 있다(추론, 오픈 부하의 동거 경합 [[IMP-038]]). 그래서 대기열이 빈 뒤에 끈다.
- 피크 모양에서 노드가 9대면 이미지가 바뀌는 PR을 머지하지 않는다([[ADR-025]]와 같다). 예매 api는 노드마다 하나라 그때 롤링 surge도 새 노드가 필요하다.
- 확인하지 못한 것:
  - 실제 클러스터에서의 전환 시간(롤링·노드 추가)과 CA 축소. 시뮬레이션은 CA를 흉내 낸 근사다([[IMP-039]]와 같은 규칙).
  - 평시 동거는 로컬 상대 비교이고, 평시 부하는 가정이다.
  - 이 둘은 다음 클러스터 세션에서 확인한다.
