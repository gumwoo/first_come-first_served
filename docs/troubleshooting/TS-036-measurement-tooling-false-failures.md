# TS-036 · 측정을 막은 것은 시스템이 아니라 측정 도구였다 — 오탐 3건

- 슬라이스: S09/S10 — 인프라·측정
- 날짜: 2026-08-26
- 유형: 측정 도구 회고(오탐 분석)
- 관련: [[IMP-021]](이 도구들로 얻은 측정), [[TS-034]](측정 방법론 실패 3건 — 그때는 조건이 문제였다)
- 상태: 3건 모두 수정·검증 완료

## 1. 배경

Cluster Autoscaler를 도입하고 실증하는 세션에서 **측정이 세 번 막혔다.** 세 번 모두
**측정 대상의 결함이 아니라 측정 도구의 결함**이었다.

[[TS-034]]와 성격이 다르다. 그때는 **조건을 잘못 잡아 틀린 값을 얻었고**, 이번에는
**멀쩡한 시스템을 고장으로 판정**했다.

## 2. 오탐 ① — 로그 문자열로 상태를 판정했다

`bring-up.sh`가 CA 설치 후 노드그룹 인식을 확인하는데, 로그에서 `"Registering Node Group"`을
찾았다. **CA 1.35에는 그 문구가 없다.**

```
==> 4/7 cluster-autoscaler / ...
    cluster-autoscaler 차트 9.59.0 (앱 1.35.0) ↔ k8s 1.35     ← 버전 게이트는 통과
cluster-autoscaler가 노드그룹을 하나도 인식하지 못했다 — 중단한다.
```

**CA는 멀쩡했다.** 같은 로그에 노드 인식 흔적이 있었다.

```
Skipping ip-10-0-75-205... - node group min size reached (current: 1, min: 1)
```

### 원인

로그 메시지는 **구현 세부**다. 버전마다 바뀌므로 판정 근거가 될 수 없다.

### 수정

CA가 스스로 발행하는 상태 ConfigMap(`kube-system/cluster-autoscaler-status`)을 읽는다.
이건 CA의 **공개 인터페이스**다.

```yaml
autoscalerStatus: Running
nodeGroups:
- health: { maxSize: 3, minSize: 1, ... }
  name: eks-flowticket-ap-northeast-2a-...
```

초판이 보지 않던 `autoscalerStatus: Running`도 함께 본다 — 노드그룹이 보여도 오토스케일러가
멈춰 있으면 의미가 없다.

## 3. 오탐 ② — 형제 스크립트를 놓쳤다

①을 `bring-up.sh`에서 고치고 `node-autoscale-test.sh`를 **그대로 두었다.** 같은 문자열을
쓰고 있어 측정이 시작조차 못 했다.

```
==> 0/6 전제 확인
CA가 노드그룹을 하나도 인식하지 못했다 — ASG 태그를 확인하라
```

### 원인

**고칠 대상만 보고 같은 패턴이 어디 또 있는지 찾지 않았다.** 이 세션에서만 네 번째로 같은
실수를 했다(#268 §6 누락, #271 PR 본문 절 누락, #275 주변 문장 미검증, 그리고 이것).

### 수정

`grep -rn "Registering Node Group" scripts/`로 전수 확인한 뒤 고쳤다. 두 스크립트가 **같은
기준**을 쓰도록 맞췄다 — 다른 기준을 쓰면 한쪽만 통과하는 상태가 생긴다.

## 4. 오탐 ③ — `curl ... || echo 000`이 `000000`을 만들었다

측정 스크립트가 전제 확인으로 로컬에서 `curl https://flow-ticket.com`을 한다. 로컬 리졸버가
도메인을 못 풀어 측정이 막혔다.

```
로컬        0/10 실패 (전부 000)
클러스터 안  200
```

**부하는 클러스터 안 k6가 만든다.** 로컬 curl은 전제 확인과 이벤트 조회 두 줄에만 쓰였는데,
그 두 줄 때문에 **동작하는 시스템을 못 재는 상태**가 됐다.

로컬 실패 시 클러스터 안에서 재시도하는 헬퍼(`scripts/lib/cluster-http.sh`)를 만들었는데,
**그 헬퍼가 정확히 그 상황에서 깨졌다.**

```bash
c="$(curl -s -o /dev/null -w '%{http_code}' "$url" --max-time 15 2>/dev/null || echo 000)"
[ "$c" != "000" ] && { printf '%s' "$c"; return 0; }
```

curl은 DNS 실패에서도 `-w` 때문에 `"000"`을 **출력하면서** non-zero로 끝난다. 그래서
`|| echo 000`이 덧붙어 **`"000000"`**이 되고, `[ "$c" != "000" ]`가 참이 되어
**폴백이 영영 실행되지 않는다.** 재현했다.

```
stdout='000'  exit=6
'|| echo 000' 적용 후 = '000000' (길이 6)
```

### ⚠️ 증거는 이미 화면에 있었다

DNS를 점검하며 `000000`을 열 번 출력해 놓고 **"000이 열 번"으로 읽었다.** 자릿수를 세지 않았다.

### 수정

종료 코드와 HTTP 코드를 분리한다. curl이 실패하면 그 자체로 재시도/폴백으로 간다.

```bash
if c="$(curl -s -o /dev/null -w '%{http_code}' "$url" --max-time 15 2>/dev/null)"; then
  [ -n "$c" ] && [ "$c" != "000" ] && { printf '%s' "$c"; return 0; }
fi
```

폴백을 **강제로 태워** 검증했다(`LOCAL_TRIES=0`). `http_code → 200`, `http_body → eventId 1754`.

⚠️ 그 전 커밋에서 *"로컬 DNS가 죽은 상태에서 200을 확인했다"*고 적은 것은 **틀렸다.**
그 시점에 로컬 DNS가 잠깐 살아난 것이고, 폴백 경로는 한 번도 실행된 적이 없었다.

## 5. 공통점 — 셋 다 "검사할 수 없음"을 잘못 처리했다

| 오탐 | 검사가 못 읽은 것 | 잘못된 처리 |
|---|---|---|
| ① | CA 상태(문자열이 없음) | **없음 = 고장**으로 단정 |
| ② | — (①의 복제본) | 전수 확인 안 함 |
| ③ | HTTP 코드(네트워크 실패) | **실패를 성공값으로 오인** |

①②는 fail-closed(막았다), ③은 **fail-open에 가까웠다** — 폴백을 건너뛰고 잘못된 값을
그대로 반환했다.

### 이 세션에서 "공허한 통과"를 다섯 번 잡았다

리뷰에서 지적받아 고친 것까지 합치면 같은 계열이 다섯이다.

| 건 | 형태 |
|---|---|
| #270 | wrapper 버전 파싱 실패 시 통과 |
| #276 | k8s 마이너를 못 읽으면 통과 |
| #276 | CA가 없어도 경고만 하고 진행 |
| #276 | `resilience-test.sh`가 CA 없이도 성공으로 종료 |
| #278 | `000000`으로 폴백을 건너뜀 |

**공통 원인은 하나다** — 검사를 쓸 때 정상 경로만 보고 **"이 검사가 아무것도 못 읽으면
어떻게 되는가"**를 따지지 않았다.

## 6. 얻은 것

- **fail-closed가 기본이어야 한다.** ①②는 측정을 막았지만 **틀린 데이터를 만들지는 않았다.**
  ③이 더 위험했다 — 잘못된 값을 반환했다.
- **판정은 공개 인터페이스로 한다.** 로그 문자열이 아니라 상태 ConfigMap, 종료 코드가 아니라
  구조화된 상태.
- **폴백은 강제로 태워 봐야 한다.** "그 상황이 왔을 때 되겠지"는 검증이 아니다.
- **한 곳을 고치면 `grep`으로 형제를 찾는다.**

## 7. 남은 것

- 상태 ConfigMap 판정도 **버전 무관을 보장하지 않는다.** 이름과 YAML 들여쓰기에 의존한다.
  바뀌면 다시 fail-closed로 드러날 것이다.
- `seed-demo-data.sh`가 **같은 로컬 DNS 문제로 두 번 죽었다**(exit 6, 2026-08-25·26).
  아직 `cluster-http.sh`를 쓰지 않는다.
- 이 계열을 **CI에서 잡을 방법이 없다.** 클러스터가 있어야 도는 스크립트라 하네스 밖이다.
