# ADR-023 · 10만 burst 대비 — 진입 경로와 대기 유지를 두 축으로 나눠 고친다

- 상태: **Proposed** — 방향 합의(2026-10-06). 각 변경은 아래 §실행 순서의 측정을 거쳐 별도 PR·IMP로 확정한다
- 날짜: 2026-10-06
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-002]](대기열 — ZSet·배치 승격·Lua), [[ADR-008]](SSE 라스트홉), [[ADR-015]](대기 상태 동기화·폴링 비용),
  [[IMP-023]](api 메모리), [[IMP-024]](liveness), [loadtest-100k-plan](../testing/loadtest-100k-plan.md)
- 근거 데이터: 측정 세션 `20261005-1440`(원시 데이터는 레포 밖 `artifacts/loadtest/20261005-1440/`, 운영 기록 `session.log`).
  아래 수치는 측정 run 게이트(G3)가 원시 데이터에서 다시 계산한 값이다.

> 시나리오 표기: 이 문서의 "10만 burst"는 **100,000 users arriving over 10 seconds (target 10,000 req/s)**다.
> 같은 10만 명도 창이 60초면 평균 1,667 req/s, 5초면 20,000 req/s라 burst 창을 빼고 쓰지 않는다.

## 맥락

S-10K(10,000명이 10초 동안 진입, Constant 1,000/s, SSE 50초 유지)를 m6i.large 노드 3대 기본 구성에서 쟀다. 대기열 정합성은
지켰지만(유효 run 전부 사후 정합성 위반 0, 실측) 진입 지연이 수 초~20초였고 일부 run에서 진입 요청이 실패했다.
측정에서 성격이 다른 한계 두 개가 따로 드러났다.

### 축 ① 진입 경로 — 진입 POST 처리 CPU (SSE와 별개)

| 관측(실측) | 값 |
|---|---|
| SSE **없이** 진입 POST만 1,400/s(api 4·web 4 고정, 워밍업 뒤 4회) | api 파드가 있는 노드가 버스트 중 CPU ≥0.9, p95 3.96~9.80s(반복 편차 큼) |
| api 파드 수만 늘림(1→2→4, 노드 3대 그대로) | 지연이 뚜렷이 줄지 않음 — 반복 편차·조건 차이로 효율 곡선은 확정 못 함 |
| 지연 위치 | ALB 대상 응답 시간 p95 ≈ 클라이언트 p95 → ALB 뒤(web·api) |
| Redis 서버 / RDS | 서버 쪽 명령 지연 ≤47μs, RDS CPU ≤7.6% — 포화 신호 없음 |
| 부하 중 Redis 클라이언트 대기 | Lettuce 명령 완료 평균 16~53ms(서버는 μs) — CPU 포화 노드의 프로세스 내부 대기로 보인다(추론) |
| web(Next 프록시) CPU | 포화 노드에서 api와 비슷한 수준인 run도 있었다(api 약 12.2 vs web 3개 약 12.9 cpu-s, cadvisor 추정). 비율은 run마다 다르다 |
| S-10K 사전 확장(api 7·web 4 고정) 노드 3대 vs 5대 | 노드 3대 2/2 run에서 ALB→web 연결 실패(TargetConnectionError 317·54), 노드 5대 6/6 run 0건. 진입 p95 노드 3대 9.21·10.00s, 노드 5대 0.29~6.11s |
| HPA 반응 시점 | 버스트 시작 17~28초 뒤에 확장 — 10초 버스트가 끝난 뒤 |

**해석(추론)**: 진입 버스트의 첫 병목은 요청 처리 CPU × 노드 CPU 총량이다. 노드 수를 바꾸면 메모리·파드 밀도도 함께 바뀌어
CPU만 분리하지는 못했다. 노드 5대 안에서도 p95가 20배 벌어졌고, 그 편차는 api 2개와 web이 같이 앉은 노드의 쏠림과 함께
나타났다(상관).

### 축 ② 대기 유지 — 대기자 전원의 SSE 연결

| 관측(실측) | 값 |
|---|---|
| 파드당 SSE 연결과 메모리 | 1Gi에서 약 3,300~3,500 연결 시점 OOM(IMP-023) |
| 연결 등록 락 | 톰캣 연결 약 6,000개 파드에서 요청 스레드 199개가 `ConnectionHandler.register`(JMX) 대기, 이어 liveness 재시작(IMP-024) |
| 끊긴 연결 정리 | 클라이언트가 닫은 뒤에도 서버 emitter가 수 분 유지(반복 재현) |
| 연결 개설 속도 | 구성과 무관하게 약 110건/s로 일정 — 원인 미확인(발생기 또는 ALB 앞단 후보, 추론) |

이 한계는 연결 계층의 문제다. **SSE를 없애도 축 ①은 남는다**(SSE 없는 run에서도 노드 CPU 포화).

## 결정

### 0. 유지한다

- 대기열 핵심: Redis ZSet + Lua 원자 발급·승격([[ADR-002]]). 유효 run 전부 정원 초과·순서 위반 0(실측).
- 기존 입장 제어: 이벤트당 **동시 입장 정원** `capacity 100`, 승격 주기 1.5초, 입장 유효시간 300초.
  새로 만들지 않고 처리량과 보호 효과를 검증·강화한다. `capacity`는 **동시 입장자 수**의 상한이지 초당 처리량이 아니다.
- 구매 정합성 계층: 좌석 조건부 UPDATE, Kafka + Outbox/DLQ.

### 1. 축 ① 진입 경로를 얇게 한다

목표 경로: `Browser → ALB → 진입 API → Redis`. 후보는 셋이고, **어느 것부터 할지는 §실행 순서의 분리 측정으로 정한다.**

- (a) **요청당 비용 축소** — 진입 요청은 발급 Lua 뒤에 입장 여부·순번·전체 수를 따로 조회한다(순번은 두 번, `QueueService.tokenResponse`). 이를 한 번의 Lua로 묶고,
  판매 여부 DB 조회(`requireBookable`)를 짧은 캐시로 바꾼다.
- (b) **Next 홉 우회** — ALB가 진입·상태 경로를 api로 직접 보낸다. ALB 경로 라우팅은 접두어를 떼지 않으므로
  (`ingress.yaml` 주석) api 쪽 경로 처리와 인증·쿠키 영향 확인이 필요하다.
- (c) **사전 확장** — 오픈 시각이 정해진 이벤트이므로 오픈 전에 노드·파드를 미리 늘리고, HPA는 예상 초과 시의
  2차 방어선으로 둔다(계획서 §6 "사전 확장과 반응형 확장"). 수치는 단계 10(right-sizing)에서 측정값으로 정한다.
- (d) **배치 쏠림 방지** — api의 노드 단위 분산. 근거가 상관 수준이라 단계 10에서 함께 판단한다(보류 브랜치 `perf/api-node-spread`).

### 2. 축 ② 대기 상태 전달을 폴링 주 경로로 옮긴다

SSE를 주 경로에서 내리고 폴링을 주 경로로 한다. 단순히 고정 주기 폴링으로 바꾸면 안 된다 —
대기자 10만 명이 15초마다 조회하면 약 6,667 req/s, 20초면 5,000 req/s가 대기 내내 이어진다(계산값).
조건은 넷이다.

1. **서버가 다음 조회 시각을 정한다** — 응답에 `retryAfterMs`를 담고, 순번·정원에 따라 서버가 늘리거나 줄인다.
2. **jitter** — 클라이언트가 ±무작위 폭을 더해 같은 시각에 몰리지 않게 한다. 평균이 같아도 주기가 맞물리면 주기마다 작은 버스트가 생긴다.
3. **조회 경량화** — 상태 조회를 Redis 왕복 1회 수준(한 번의 Lua: 메타·입장 여부·순번)으로 줄이고, 가능하면 축 ①(b)와 같이 Next 홉을 거치지 않는다.
4. **복구 경로 유지** — 폴링이 진실원 재조회 경로가 된다([[ADR-015]]의 "폴링이 유일한 복구 경로" 원칙과 같은 방향). SSE를 남길지(입장 알림 전용 등)는 측정 후 결정.

### 3. 스케일링 단위를 나눈다(후보)

진입·상태(`queue-entry`/`queue-status`)와 구매(`purchase`·seat·order)를 같은 이미지라도 Deployment로 나눠 따로 늘리는 것을
검토한다. 근거는 설계상 판단이다(추론) — 구매 트래픽을 섞어 잰 적은 없다. 나누면 승격 워커(`@Scheduled`)가 어느 쪽에서
한 번만 도는지를 정해야 한다.

### 4. 표현 규칙

- 입장 판정은 지금 Redis 상태(UUID 토큰 + `admit`/`admitExp`)다. 서명 토큰(JWT 등)을 구현하기 전에는 "입장 토큰 구조"라고 쓰지 않는다.
- "10만 처리", "SLO 달성", "병목 확정"은 아래 시험 ⑤를 통과하기 전에 쓰지 않는다.

## 목표

> 100,000 users arriving over 10 seconds (target 10,000 req/s)의 대기열 진입을 수용하면서 대기열 정합성 위반 0,
> 대기 상태 조회를 안정적으로 제공하고, 구매 계층에 들어간 **동시 입장자 수를 capacity 이하로** 유지하며, 좌석 초과판매 0을 검증한다.

## 실행 순서 — 축을 떼어 재고, 마지막에 합친다

| # | 시험 | 조건 | 보는 것 |
|---|---|---|---|
| ① | 진입 | SSE 없음, 진입 POST만 | 버스트 수용 능력, 노드 3 vs 5(CPU), web 홉 유무, 버스트 중 CPU 프로파일(JFR) |
| ② | 상태 조회 | 대기자 N명, 폴링(서버 주기·jitter) | 지속 조회 부하, 조회당 비용 |
| ③ | 입장 제어 | 대기자 충분 | 설정한 정원·주기대로만 통과하는가 |
| ④ | downstream | 입장 → 좌석 → 주문 | 초과판매 0, DB·Kafka 안정성(지금까지 미실행) |
| ⑤ | 최종 E2E | 10만 burst → 대기 → 입장 → 좌석·주문 | 위 목표 전체 |

- ①은 축 ①의 (a)(b)(c) 중 무엇부터 할지를 정하는 분리 측정이다. 지금 S-10K 결과는 SSE가 섞여 있어 진입만의 scaling을 정하지 못한다.
- 초당 1만 건은 발생기 한 대로 만들 수 없다(이번 세션 발생기 1대는 지연이 클 때 1,400/s가 실효 한계였고, 2,800/s run은 VU 부족으로 무효). ①·⑤는 분산 발생기를 전제로 한다(계획서 §2.4).
- SQS/Lambda 같은 버퍼 계층은 지금 붙이지 않는다. 현재 구조를 경량화해 목표를 실측하고, 그걸로 안 될 때 검토한다.

## 검토했으나 채택하지 않은 대안

- **SSE 유지 + 연결 전용 계층으로 10만 연결** — 가능하지만, 대기 상태 전달에 그 비용·복잡도를 들일 이유가 적다. 축 ①은 그대로 남는다.
- **고정 주기 폴링으로 단순 전환** — 대기 내내 수천 req/s가 이어지고(계산값) 상태 조회가 지금처럼 무거우면 CPU를 더 쓴다.
- **노드만 늘려 통과** — 노드 5대에서 진입 오류가 사라졌지만(실측) 지연 편차가 크고 SLO(p95 ≤ 300ms)를 만족한 것은 1회다. 요청당 비용을 줄이지 않고 늘리기만 하면 계획서의 "근거 없는 증설"과 같다.

## 한계 / 미확정

- 축 ①의 원인을 노드 CPU로 **분리하지 못했다**(노드 수와 함께 메모리·밀도가 바뀜). 반복은 조건당 2~6회이고 같은 조건에서도 p95 편차가 크다.
- 진입 경로에서 web 홉과 api의 CPU 비율은 run마다 다르다 — 순서를 정하려면 ①의 분리 측정이 필요하다.
- SSE 개설 속도 약 110건/s의 원인은 확인하지 않았다.
- 폴링 부하 수치는 계산값이다. 실측 전에는 표·결과에 실측처럼 쓰지 않는다.
- SLO(핵심 API p95 ≤ 300ms)는 근거가 적혀 있지 않은 기존 규칙이다(계획서 §3.4). 버스트 진입에 같은 기준을 쓸지 다시 정한다.
