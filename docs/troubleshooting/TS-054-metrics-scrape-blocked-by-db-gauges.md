# TS-054 · DB가 느려지자 api 지표가 통째로 끊겼다: 지표 응답이 게이지마다 DB 쿼리를 돌렸다

- 날짜: 2026-11-01(관측 2026-10-29~30, 로컬 실험실)
- 영역: 관측(Micrometer 게이지·Prometheus 긁기)
- 결과: **수정**. 운영 지표 4개를 전용 스레드가 10초마다 세어 두고, 게이지는 그 값만 읽는다. 값이 얼마나 묵었는지 새 지표로 낸다. 단위 테스트로 확인했고, 실험실·클러스터에서 다시 재지는 않았다.
- 관련: [[IMP-054]](관측한 측정), [[TS-032]](DEAD 행 지표), [[ADR-022]](미발행 최장 대기), [[TS-041]](운영 actuator 관리 포트), `OperationalMetrics`

## 증상 (로컬 실측, IMP-054 §5.2)
- 장애 알림 경로를 실험실에서 확인하는 동안, PostgreSQL CPU를 0.05코어로 줄인 run에서 api 지표 긁기(1초 시간 초과)가 예매 요청이 들어오기 전부터 실패했다(`up=0`).
- 긁기가 실패하는 동안에는 CPU·커넥션·요청 지연 같은 api 지표가 모두 없었다. 그래서 알림 분석 훅이 예매 구간을 찾지 못해 원인 분석을 하지 못했다.

## 원인
- api의 `/actuator/prometheus` 응답은 `OperationalMetrics`의 게이지 값을 채우려고 스크랩마다 DB 쿼리 4개를 돌렸다. 아웃박스 DEAD 수, PENDING 수, 가장 오래 기다린 미발행 행, 초과 판매 좌석 수다(코드로 확인).
- DB가 CPU를 못 받으면 이 쿼리가 늦어지고, 지표 응답 전체가 함께 늦어진다. 예매 요청이 없을 때부터 긁기가 실패한 것은 이 쿼리 때문으로 본다(추론, 쿼리 시간을 직접 재지는 않았다).
- 운영은 긁기 간격이 15초이고 시간 초과도 더 길어 실험실보다 덜 드러나지만, 의존 관계는 같다. 쿼리는 예매 요청과 같은 커넥션 풀(5개)에서 커넥션을 빌린다.

## 수정
- 값은 전용 스레드(`ops-metrics-refresh`)가 10초마다 DB에서 세어 두고, 게이지는 그 값만 읽는다. 스크랩은 DB를 부르지 않는다.
- 갱신을 공용 `@Scheduled` 스레드에 올리지 않았다. 이 앱은 스케줄러 스레드 풀 크기를 정하지 않아 기본값(스레드 하나)을 쓰고, 그 스레드에서 대기열 승격(1.5초)과 아웃박스 릴레이(1초)가 돈다. DB가 느릴 때 갱신이 그 스레드를 붙잡으면 승격·릴레이까지 밀린다.
- 질의마다 실패를 따로 삼켜 그 값만 값 없음(NaN)으로 둔다. 이전과 같은 뜻이다(0으로 두면 "적체 없음"과 "수집 실패"가 구분되지 않는다).
- 가장 오래 기다린 행은 생성 시각을 세어 두고 나이는 읽을 때 계산한다. 갱신 주기만큼 나이가 덜 찍히지 않는다.
- 새 지표 `flowticket_metrics_snapshot_age_seconds`: 마지막으로 센 뒤 지난 시간. 갱신이 DB에서 막히면 이 값이 10초보다 크게 벌어진다.
- 통합테스트처럼 배경 작업을 끈 환경(`flowticket.scheduling.enabled=false`)에서는 갱신 스레드를 띄우지 않는다.
- 부하 시험 정합성 감시(`watch-correctness.mjs`)와 사후 재확인용 내보내기(`export-prom.mjs` → `prom-recheck.mjs`)의 신선도 식에서, 초과판매 샘플 나이에 이 지표를 더한다. 스크랩이 성공해도 값이 묵었으면 관측 공백(판정 불가)으로 잡기 위해서다. 이 지표가 없는 이전 이미지는 0으로 본다(promtool로 두 경우 확인). 정상일 때도 초과판매 나이에 갱신 주기(10초)가 더해져, 감시·재확인 스크립트의 `--max-sample-age` 기본값을 30초에서 40초(스크랩 15 + 갱신 주기 10과 갱신 시간 + 스크랩 한 번 누락 15, 잠정값)로 올렸다. 재확인 꼬리도 30초에서 45초로 늘렸다. run 종료 뒤에 센 값이 스크랩돼 내보내기 점에 찍히기까지 갱신 대기 10 + 갱신 시간 + 스크랩 15 + step 10초가 걸린다(계산, 내보내기는 이미 run 종료 + 45초를 덮는다).
- 값이 묵은 시간은 세기 시작한 시각부터 잰다. 끝난 시각으로 찍으면 앞 질의의 값이 뒤 질의를 기다린 만큼 덜 묵어 보인다.

## 트레이드오프
- 갱신이 제때 끝나면 값은 최대 10초 묵는다(긁기 간격과 더하면 최대 약 25초, 계산). 알림은 5~10분 지속을 보므로 영향이 작다. 부하 시험의 초과판매 실시간 감시는 그만큼 늦게 알게 된다.
- DB가 느려 갱신이 막히면 그동안 값이 멈춘다. 이 저장소는 `statement_timeout`과 Hikari 커넥션 대기 시간을 따로 정하지 않아, 풀이 마르면 질의 하나가 기본 대기 30초까지 기다릴 수 있다(순차 4개면 최대 약 120초, 계산). 그동안 `flowticket_metrics_snapshot_age_seconds`가 커지고, 위 감시 식은 기준(40초)을 넘는 구간을 판정 불가로 본다.
- 쿼리 횟수는 파드마다 10초에 한 번이다. 이전에는 긁기(운영 15초)마다였으므로 운영에서는 1.5배가 된다(계산). 아웃박스 세 질의는 부분 인덱스(상태별)를 쓰고, 초과판매는 결제 완료 주문과 주문 항목을 묶는 집계다.
- DB가 계속 느리면 갱신 스레드가 커넥션 하나를 붙잡고 기다리는 점은 이전과 같다. 다른 점은 지표 응답과 공용 스케줄러가 그 기다림에 묶이지 않는다는 것이다.

## 재발 방지
- 스크랩 경로에서 DB·외부 호출을 하는 게이지를 두지 않는다. 값이 필요하면 미리 세어 두고, 센 뒤 지난 시간을 함께 낸다.
- 신선도를 샘플 시각으로 판단하는 소비처(감시·재확인 스크립트)는 앱이 미리 센 값이면 센 뒤 지난 시간도 더해 본다.

## 검증
- `OperationalMetricsTest`: 스크랩은 DB를 부르지 않는다(첫 갱신 전 값은 NaN), 지표 이름·라벨, 갱신 사이 나이 증가, 값이 묵은 시간, 질의별 실패 격리, 초과판매 값·실패.
- 실험실에서 DB 0.05코어 run을 다시 돌려 긁기가 살아 있는지는 재지 않았다.
