# TS-031 · KOPIS 수동 동기화가 ALB idle timeout보다 오래 걸린다 — 좌석 0을 실패로 오해했다

- 슬라이스: S04(좌석)·S09(운영) — 2026-08-16 클러스터 재기동 중
- 날짜: 2026-08-16
- 유형: 운영 절차 — **오래 걸리는 동기 API가 프록시 타임아웃 뒤에 있는 구조**
- 관련: [[ADR-015]](ALB idle timeout 60초 실측), `docs/deployment/aws-eks-deploy-plan.md`(bring-up)
- 상태: **원인 확인** — 구조는 그대로 두고 관측 방법을 기록한다(아래 §4)

## 0. 무엇이 있었나

클러스터를 새로 올린 뒤 RDS가 비어 있어 `POST /admin/sync/kopis`로 데이터를 채웠다.
동기화 직후 확인했더니 이벤트는 들어왔는데 **좌석이 0석**이었다.

```
GET /api/events?status=ON_SALE  → total 198
GET /api/events/1636/seats      → {"grades":[],"seats":[]}
```

`basePrice`도 전부 `null`이었다(좌석 시딩이 채우는 값이다). **시딩이 실패했다고 판단할 뻔했다.**

로그를 봐도 `[seat]`으로 시작하는 줄이 성공·실패 어느 쪽도 없었다. `seedSellable()`은
`if (seeded > 0)`일 때만 로그를 남기므로, "0건 처리"와 "아직 안 끝남"이 **로그상 구분되지 않는다.**

## 1. 실제로는 아직 돌고 있었다

몇 분 뒤 다시 보니 좌석이 채워져 있었고, 그때서야 완료 로그가 나왔다.

```
12:16:01  [kopis] upsert 완료 1931건(수집 2111건, 조회 1회)
12:17:01  [kopis] 상세 동기화 300건 채움(대상 300건)
12:19:46  [seat] 자동 좌석 시딩 1931건
```

**서버측 소요 약 3분 45초.** 규모를 보면 당연하다.

| 항목 | 값 |
|---|---|
| 대상 이벤트(ON_SALE + SCHEDULED) | 198 + 1,733 = **1,931건** |
| 생성 좌석 행 | 1,931 × 100 = **약 193,100행** |
| 이벤트별 트랜잭션 | 1,931개(`seedSellable`이 건별로 분리) |

## 2. 그런데 ALB idle timeout은 60초다

같은 날 실측했다([[ADR-015]] §미확정 참고).

```
idle_timeout.timeout_seconds = 60
```

`sync()`는 upsert → 상세 동기화 → 좌석 시딩을 **한 요청 안에서 동기로** 처리하고, 그동안
응답 바이트가 흐르지 않는다. **3분 45초짜리 동기 요청이 60초 타임아웃 뒤에 있는 구조다.**

⚠️ **클라이언트가 실제로 끊겼는지는 이 기록에서 확인하지 않았다.** 서버측 소요 시간과
idle timeout 값은 각각 실측이지만, 그 요청의 클라이언트 응답은 관측하지 못했다.
다만 서블릿 스레드는 클라이언트가 끊겨도 계속 돌기 때문에, **끊겼더라도 작업은 완료된다** —
실제로 데이터는 온전히 들어왔다.

## 3. 무엇이 오해를 만들었나

세 가지가 겹쳤다.

| 요인 | 결과 |
|---|---|
| 응답을 못 받거나 늦게 받음(추정) | "실패했나?" |
| 완료 전에는 로그가 **한 줄도** 안 남음 | "안 돌고 있나?" |
| 좌석이 이벤트별 트랜잭션이라 **부분적으로만 보임** | "일부만 되고 멈췄나?" |

특히 두 번째가 크다. `if (seeded > 0)` 조건 때문에 **진행 중과 0건 완료가 같아 보인다.**

## 4. 조치 — 구조는 두고 관측 방법을 남긴다

이 엔드포인트는 **운영자가 가끔 누르는 수동 트리거**이고 스케줄 동기화와 같은 락을 공유한다.
비동기(202 Accepted + 작업 조회)로 바꾸는 것이 정석이지만, **지금 필요한 것은 그게 아니라
"기다리면 된다는 것을 아는 것"이다.** 그래서 구조를 바꾸지 않고 관측 방법만 적는다.

응답을 기다리지 말고 **로그로 완료를 확인한다.**

```bash
kubectl logs -n flowticket -l app=flowticket-api --tail=2000 | grep "자동 좌석 시딩"
```

또는 **좌석이 채워지는지로 확인한다**(진행 중에는 이벤트마다 다르게 보인다).

```bash
curl -s "https://<host>/api/events?status=ON_SALE&size=5" | grep -o '"basePrice":[^,]*'
```

`basePrice`가 `null`이면 그 이벤트는 아직 차례가 오지 않은 것이다.

## 5. 남은 것 (하지 않기로 한 것)

- **비동기 전환.** 202 + 작업 상태 조회로 바꾸면 타임아웃 문제가 사라지고 진행률도 보인다.
  다만 지금은 수동 운영 트리거 하나뿐이라 **비용 대비 이득이 작다.** 자동화가 이 API에
  의존하게 되면 그때 바꾼다.
- **진행 로그.** `seedSellable()`이 시작·진행을 남기면 "진행 중"과 "0건 완료"가 구분된다.
  한 줄이면 되지만 **이 문서를 남기는 것으로 충분하다고 판단**했다 — 로그를 늘리는 것도
  비용이고, 재기동은 드물다.

⚠️ 두 항목 모두 **의도적으로 하지 않은 것**이지 빠뜨린 것이 아니다.

## 6. 배운 점

**"로그가 없다"는 "안 돌고 있다"가 아니다.** 완료 시에만 로그를 남기는 코드에서는
진행 중과 무처리가 구분되지 않는다. 그 구분이 필요하면 로그를 늘리든지, **아니면 이번처럼
다른 관측 지점(데이터 자체)을 쓴다.**

그리고 **오래 걸리는 동기 API 앞에 프록시가 있으면 타임아웃 값을 함께 봐야 한다.**
이번에는 같은 날 다른 목적(SSE 하트비트)으로 잰 ALB idle timeout이 이 해석에 그대로 쓰였다.
