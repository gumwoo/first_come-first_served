# TS-042 · 진입 창이 분 경계(:00)를 지나면 9개 api가 함께 느려진다 — Redis 쪽 분 경계 지연이 의심된다(원인 미확정)

- 슬라이스: S10(부하·확장) — 통합 판정 run 워밍업(pf-warm)에서 발견
- 날짜: 2026-10-08
- 유형: 공유 의존의 주기적 지연(의심) — 원인 미확정, 시험 설계로 우회하고 한계로 기록
- 관련: [[IMP-029]], [[IMP-031]], [[ADR-025]], ElastiCache `cache.t4g.micro`(단일 스레드)
- 상태: **원인 미확정 · 한계로 기록** — 판정 run은 진입 창이 분 경계를 지나지 않게 T0를 :10~:45초에 두었다(사용자 결정). 클러스터 철거로 후속 확인은 하지 않는다.
- 증거(레포 밖 `artifacts/loadtest/20261007-platform/`): ALB access log 원본, `pf-warm/redis-diag.txt`(SLOWLOG·INFO), `redis-idle-latency.txt`, `redis-cloudwatch.txt`, `pf-warm/prom/`

## 1. 증상 (실측 — ALB access log `request_creation_time`)
pf-warm(T0 = 2026-10-07T16:09:54Z, 진입 10,000/s × 10초)의 창 [T0, T0+10s) 도착이 **90,644건**(기준 ≥ 100,000)이었다.

| 초(UTC) | 진입 도착 | 대상 처리 최대 | 비고 |
|---|---|---|---|
| 16:09:54 ~ :59 | 10,178 ~ 10,202 | 0.053 ~ 0.105s | 정상 |
| 16:10:00 | 9,906 | 1.491s | 1초 넘는 응답 562건 |
| 16:10:01 | 5,412 | 1.405s | 도착 감소 — 발생기 VU가 느린 응답에 묶인 것으로 본다(추론. run 전체 dropped 5,476) |
| 16:10:02 | 6,152 | 0.697s | |
| 16:10:03 | 8,006 | 62.5s | **504 250건**(대상 처리 시간 −1 — ALB 유휴 시간 초과 60초) |

- 느려짐은 **16:10:00.0부터** 시작했다. 100ms 단위로 보면 16:10:00.0에 9개 api 대상이 함께 최대 0.35~0.47초로 늘었고, 16:10:00.6부터는 함께 1.4초대였다 —
  한 파드가 아니라 공유 의존을 가리킨다(추론).
- ALB → api 연결 수(`tomcat_connections`)가 파드당 약 7 → **약 1,000**으로 늘었다(v3 판정 run은 약 20). 느려진 결과로 ALB가 연결을 더 연 것으로 본다(추론).
- 같은 시각 api 로그에 WARN·ERROR 없음, GC 정지 파드별 최대 0.0042 s/s(미미), hikari pending 0, RDS·Redis 1분 지표(CPU·크레딧·메모리·스왑)에 변화 없음.

## 2. 조사
1. **분 경계에 맞춘 지연인가** — 이전 측정의 ALB 로그를 같은 방식으로 다시 봤다(실측, 100ms 평균 지연 최고값).
   - 1차 f2-r1(창 04:32:54~:33:04): 04:33:00.0에 평균 0.004 → **약 0.19s**, 약 2초 뒤 회복.
   - 1차 f2-r2(창 04:48:53~:49:03): 04:49:00.1에 0.003 → **약 0.29s**.
   - 2차 f3-r3(창 07:25:56~:26:06): 07:26:00에 초 평균 0.265s(100ms 평균 최고 약 0.30s, 최대 0.367s), :01 0.152s, 약 3초 뒤 회복. 도착은 유지.
   - 2차 워밍업 f3-warm(06:35:57 시작)도 창이 :00을 지났지만 :00 전부터 이미 1~4초로 무너져 있어 분 경계 효과를 가를 수 없어 뺐다.
   - 3차 v3 판정 3회(f4-r1~r3)는 창이 분 경계를 **지나지 않았다**(08:28:21·08:44:37·09:01:12 시작) — IMP-029 6축 충족은 이 조건에서의 결과다.
2. **Redis 명령이 느려지는가** — `SLOWLOG LEN` 128 중 최근 30개(`SLOWLOG GET 30`, id 290~319 = 16:21~16:34)만 받았다(그 앞 98개는 조회하지 않음 — pf-warm T0 부근은 보지 못했다).
   그 30개는 14개 분 중 11개 분의 :00 무렵(과 16:30:30)에 몰려 있고, `HGET`·`ZCARD`·`EXISTS` 같은 O(1) 명령 실행 시간이 **10~30ms**였다.
   O(1) 명령이 그만큼 걸린 것은 명령 자체가 아니라 Redis 프로세스가 멈춘 것으로 본다(추론).
3. **부하 없이도 느려지는가** — 클러스터 안 임시 파드에서 `redis-cli --latency-history -i 1` 150초(실측, `redis-idle-latency.txt`): 1초 창 148개 중 116개가 최대 2ms 이하,
   3~14ms 31개, 35ms 1개. 가장 큰 35ms·14ms 창은 분 경계 근처였지만(출력 버퍼링 때문에 창 시각은 시작 시각 + 창 번호로 맞춘 근사), 분 경계가 아닌 창에도 13ms·10ms가 있었다.
   **유휴 측정만으로는 분 정렬을 확정하지 못한다**(분 경계 표본 2회).
4. **진입이 아닌 부하에서도 보이는가** — pf-r1 폭증(상태 조회 약 10,000/s, api 9개 — 확장이 끝난 20:41:30 이후)의 ALB 상태 조회를 10초 단위로 묶으면(실측),
   :00이 든 10초 구간만 대상 처리 최대가 0.167·0.185·0.350·0.648·0.214s(20:42~20:46), 나머지 구간은 0.015~0.028s였다.
5. Redis 노드 상태(CloudWatch, 실측 — `redis-cloudwatch.txt`): `cache.t4g.micro`, `SwapUsage` 약 171MB(2026-10-06 18시 KST께 94MB → 141MB로 늘어 그 뒤 유지 — v3 판정 run 때도 같은 수준),
   `CPUCreditBalance` 288(최대), `Evictions` 0, `SaveInProgress` 0.

## 3. 근본 원인 — **미확정**
- 확인한 것: 부하 중 :00이 든 구간에서 api 9개가 함께 느려진다(ALB 실측 — 진입 4개 run, 폭증 1개 run). Redis slowlog의 O(1) 명령 10~30ms 기록이 :00 무렵에 몰려 있다(받은 30개 기준).
- 추측(확인 못 함): ① 0.5GiB 노드의 스왑(171MB) 상태에서 ElastiCache 쪽 분 단위 작업(지표 수집 등)이 페이지 폴트·CPU 경합을 일으킨다.
  ② active defrag(`INFO`의 `total_active_defrag_time` 463,537 — 언제 돌았는지는 모름). 앱 쪽 분 정렬 작업은 없다
  (`@Scheduled`는 모두 fixedRate — 파드 기동 시각 기준이라 9개 파드가 같은 :00에 맞춰지지 않는다. cron은 03:00·04:00뿐).
- 미확정: 수십 ms 지연이 왜 pf-warm에서만 4초 붕괴·60초 매달림으로 번졌는지(f2·f3에서는 2~3초 안에 회복).
- 확정하려면: `latency-monitor-threshold`로 정지 이벤트를 모으고, 스왑 없는 큰 노드 타입에서 같은 유휴·진입 측정을 분 경계에 걸쳐 재는 것 — 사용자 결정으로 이번에는 하지 않는다(시간·비용, 측정 대상 구성 변경, 철거 예정).

## 4. 조치
- 통합 판정 run(pf-r1~r3)은 진입 창 [T0, T0+10s)이 :00을 지나지 않게 T0 초를 :10~:45에 두었다(사전 등록 변경 기록 5, 결과 보기 전).
- 이것은 **시험 설계로 피한 것**이지 고친 것이 아니다. 실제 오픈 시각은 보통 정각(:00)이라 운영에서는 정확히 이 순간에 몰린다 — 실서비스라면 우선 확인할 위험이다.

## 5. 재발 방지 · 남는 일
- 판정 창 선택 규칙: 공유 의존의 주기적 지연이 의심되면 창 배치를 사전 등록에 적고, 결과 표현에 "분 경계 밖 창"을 붙인다([[IMP-031]]).
- [[IMP-029]] §8에 단서 추가: 6축 충족은 분 경계를 지나지 않는 창에서의 결과이며, 분 경계를 지난 이전 run은 그 순간 진입 지연이 약 0.2~0.3s로 튀었다.
- 후속(이번 범위 밖): Redis 노드 타입 상향 후 유휴·부하 분 경계 재측정, `latency-monitor-threshold`로 정지 원인 이벤트 수집.
