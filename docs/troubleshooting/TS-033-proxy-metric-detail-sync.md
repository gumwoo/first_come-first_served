# TS-033 · 대리값으로 진행을 셌더니 완료를 못 알아봤다 — 21분을 낭비하고 거짓 경고까지 냈다

- 슬라이스: S02(KOPIS) / 횡단(운영 자동화)
- 날짜: 2026-08-22
- 유형: **관측 지표 오선정** + 부수적으로 드러난 두 가지(선언 순서, 관측의 부작용)
- 관련: [[TS-031]](KOPIS 동기화 3분 45초 vs ALB 60초), [[IMP-018]](KOPIS 속도 제한),
  PR #259(기동 자동화) → #260(상세 반복 수집)
- 상태: **해결** — `detailSyncedAt`을 그대로 내려주는 읽기 전용 엔드포인트를 만들고
  스크립트가 그 값으로 판정한다. 재실행 25분 → **16초**

## 0. 무엇이 문제였나

클러스터를 재생성하면 DB가 빈다. KOPIS 상세는 **회차당 300건 상한**이라 공연 1,919건을 채우려면
여러 번 돌려야 해서, 기동 스크립트에 반복 루프를 넣었다. **"얼마나 남았는지"를 밖에서 볼
수단이 없다는 것**이 문제였다 — `detailSyncedAt`은 어떤 API로도 나가지 않았다.

그래서 **공개 API에 있는 필드로 대신 셌다.**

```bash
# 초안: runningTime이 비었으면 "상세 미수집"으로 간주
jq -r 'if ((.data.runningTime // "") == "") then 1 else 0 end'
```

결과는 이랬다.

```
[1] 1385 → [2] 1037 → [3] 742 → [4] 453 → [5] 165 → [6] 53 → [7] 53 (정지)
⚠️ 상세 없음 53건 남음 — KOPIS 원본에 상세가 없는 공연일 수 있다
```

**이 53건은 실패가 아니었다.** 상세는 이미 다 받았고 `runningTime`만 원래 없는 공연이었다.

## 1. 대리값이 왜 틀렸나 — 조건부 갱신 vs 무조건 갱신

`Event.updateDetail()`이 두 값을 다르게 다룬다.

```java
if (runningTime != null && !runningTime.isBlank()) this.runningTime = runningTime;  // 조건부
if (ageLimit != null && !ageLimit.isBlank())       this.ageLimit    = ageLimit;      // 조건부
...
this.detailSyncedAt = LocalDateTime.now();                                           // 무조건
```

둘 다 이유가 있다. 조건부인 쪽은 **"상세 응답에 그 필드가 없다고 목록에서 받아둔 값을 지우면
안 되기"** 때문이고, 무조건인 쪽은 **"갱신하지 않으면 매번 같은 공연을 다시 호출하기"**
때문이다(둘 다 코드 주석에 적혀 있다).

그래서 **"상세는 받았는데 `runningTime`은 비어 있는 공연"이 정상적으로 존재한다.**
그런 공연은 `detailSyncedAt`이 찍혀 다음 회차 대상에서 빠지므로, 대리값 카운터는
**영원히 0에 도달하지 못한다.**

| | 진실원 | 대리값 |
|---|---|---|
| 의미 | 상세를 받았는가 | 그 필드에 값이 있는가 |
| 갱신 | 무조건 | 값이 있을 때만 |
| 0이 되는가 | 된다 | **되지 않는다** |

## 2. 실측 — 배포 후 같은 시점에 두 값을 나란히 잰 것

```
도메인 값 : {"totalEvents":1919, "detailMissing":0}     ← 이미 100% 완료
대리값    : 표본 60건 중 runningTime 없음 2건            ← "미수집"으로 오판
```

즉 루프는 **6회차에 이미 끝나 있었다.** 7회차를 한 번 더 돌고 정지 판정으로 종료한 것이고,
그 마지막 회차와 매 회차의 카운팅(1,919건 건별 조회 ≈ 40초)이 낭비였다.

## 3. 무엇을 잃었나

- **시간**: 재실행 **25분 → 16초**. 회차당 약 3분 × 불필요한 회차 + 매 회차 40초 카운팅
- **거짓 경고**: `⚠️ 상세 없음 53건 남음`이 stderr로 나갔다. 실제로는 0건이다
- **거짓 서술 직전까지 갔다**: PR 본문에 *"KOPIS 상세 조회가 실패하는 공연"* 이라고
  적을 뻔했다. **확인하지 않았다고 명시해 둔 덕에 문서에 거짓이 박히지는 않았다.**

## 4. 해결 — 진실원을 그대로 내보낸다

```
GET /admin/sync/kopis/status → { totalEvents, detailMissing }
```

**건별 DTO에 `detailSyncedAt`을 노출하는 대신 카운트를 택했다.** 1,919건을 매 회차 조회하면
1회 세는 데만 40초가 걸린다 — 실제로 그러고 있었다. 카운트는 한 번의 요청으로 끝난다.

**`findIdsNeedingDetail`과 조건을 일부러 다르게 했다.** 그쪽은 "오래된 것"도 대상에 넣어
순환 갱신하므로 **0이 될 수 없다**(7일이 지나면 다시 대상이 된다). 이 값이 답해야 하는 질문은
"초기 수집이 끝났는가"라서 `detailSyncedAt IS NULL`만 센다.

의미는 테스트로 고정했다(`EventDetailSyncMarkerTest`) —
*"runningTime이 비어도 상세를 받았으면 detailSyncedAt이 찍힌다"*.

## 5. 곁가지로 드러난 두 가지

### ㉠ 관측이 상태를 바꾸면 안 된다

초안은 "동기화가 끝났는지"를 **`POST /admin/sync/kopis`를 다시 호출해 409면 실행 중**으로
판정하려 했다. 그런데 **409가 아니면 그 호출이 새 동기화를 시작해버린다.** 확인하려는 행위가
관찰 대상을 바꾼다. 읽기 전용 폴링과 시간 대기(TS-031의 3분 45초 근거)로 바꿨다.

### ㉡ 선언 순서가 쿼리를 갈아치웠다

카운트 메서드를 추가하면서 **`@Query` 애너테이션과 원래 메서드 사이에** 끼워 넣었다.
그러자 `findIdsNeedingDetail`이 파생 쿼리로 해석되어 **Spring 컨텍스트 전체가 기동 실패**했다.

```
No property 'findIdsNeedingDetail' found for type 'Event'
```

⚠️ **로컬 컴파일은 통과했다**(문법은 옳다). 새로 쓴 단위 테스트도 컨텍스트를 띄우지 않아
못 잡았다. **CI의 통합테스트가 잡았다** — Testcontainers를 로컬에서 못 돌리는 환경이라
이런 종류는 CI가 유일한 그물이다.

## 6. 배운 것

**대리값을 쓰기 전에 "이 값이 0이 될 수 있는가"를 물어야 한다.** 진행률 지표는 완료를 표현할 수
있어야 하는데, 대리값은 그 성질을 보장하지 않는다. 여기서는 *조건부 갱신* 하나 때문에 그
성질이 깨졌고, 겉으로는 "거의 다 됐다"처럼 보여서 **오답이 그럴듯했다.**

> 관측 지표를 고를 때 "있는 것 중에 가장 가까운 값"을 쓰면, 가까운 만큼 틀린 것을 오래 못
> 알아본다. 없으면 **만들어서 내보내는 편이 싸다** — 이번엔 엔드포인트 하나였다.

그리고 이 저장소에서 반복되는 주제가 또 한 번 확인됐다 — **[[TS-030]]의 "테스트가 예외를
삼켜 결함을 가림", [[TS-032]]의 "조용히 멈추는 실패"와 같은 계열이다.** 셋 다 *신호를 잘못
읽어서* 문제를 오래 못 본 사례다.

## 7. 한계

- **53건이 정확히 무엇이었는지는 개별 확인하지 않았다.** `detailMissing: 0`이 나온 것으로
  "상세는 다 받았다"까지만 확정했고, 그 공연들의 KOPIS 원본에 `prfruntime`이 왜 없는지는
  보지 않았다. 이 문서의 주장은 **"대리값이 틀렸다"**이지 "KOPIS 데이터가 이렇다"가 아니다.
- **`detailMissing`이 0을 유지한다는 보장은 없다.** 새 공연이 들어오면 다시 늘어난다 —
  이 값은 "지금 이 순간 초기 수집이 끝났는가"이지 완료 상태의 영구 표식이 아니다.
