# IMP-026 · 대기열 진입 1건의 DB 조회·Redis 왕복 줄이기 — DB 획득 1.01 → 0.011/req, Redis 명령 7.03 → 2.03/req

- 날짜: 2026-10-07

- 관련 커밋/PR: #345(판매 상태 캐시, 머지 `4a1fb37`) · #346(발급 Lua가 순번·전체 수를 함께 반환, 머지 `2c01c0f`)

## 1. 상황 (Context)
[[IMP-025]]로 진입 요청이 web을 거치지 않게 된 뒤, 10,000 req/s 10초 burst에 필요한 용량을 정하려고(단계 6, 사전 등록 `step6-prereg.md`)
공개 ALB 경로에서 진입 rate를 올려 가며 api 파드 하나가 감당하는 rate(R_pod)를 쟀다.
첫 램프(api 3·노드 3)에서 R_pod는 2,000÷3 ≈ 667 req/s였고, 계산상 api 18개가 필요해 노드 그룹 상한(합 9)을 넘었다(계산값).
증설 전에 요청 1건이 쓰는 비용부터 줄이기로 했다(사용자 결정 "요청당 비용 먼저 줄임").

## 2. 문제 정의 + 분류
진입 POST 1건이 DB에서 공연을 PK 단건으로 매번 읽고(DB 커넥션 획득 1.01회/req), Redis를 7번 왕복한다(명령 7.03/req).
- 계층 분류: DB(반복 조회) / 캐시·외부 저장소 왕복(Redis)
- 근거: 단계 2·6a 측정의 Hikari 획득 수·Redis 명령 수(Prometheus `hikaricp_connections_acquire_seconds_count`·`lettuce_command_completion_seconds_count` 증가분 ÷ 서버 진입 요청 수), 코드 경로(`QueueService.issue` → `requireBookable` → `EventRepository.findById`, 발급 Lua 뒤 순번·전체 수를 따로 조회)

## 3. 증상 (측정된 증거)
- 측정 방법: 공개 ALB, 진입 POST constant, SSE 없음, HPA api 3/3·web 2/2 고정, m6i.large 3대(api 노드당 1), run마다 새 공연·리셋. CPU-ms/req 식은 [[IMP-025]] §3과 같다.
  2,000·3,000/s는 30초·발생기 1대, 4,000/s는 20초·발생기 3대(START_AT 장벽 — 토큰 10만 개 제약으로 20초).
- before(#345 전, 칸별 1회):
  | 지표 | 2,000/s | 3,000/s |
  |------|----|----|
  | api CPU-ms/req | 1.105 | 1.159 |
  | DB 커넥션 획득/req | 1.01 | 1.01 |
  | Hikari pending 최대 | 5 | 0 |
  | p95 | 30.4 ms | 139.5 ms |
  | 노드 CPU 15초 평균 최대(세 노드) | 0.47~0.49 | 0.68~0.75 |
- before(#346 전 — #345 반영 뒤, 4,000/s, 1회): Redis 명령 7.03/req, Redis 메인 스레드(`INFO cpu` 2초 간격) 부하 중 0.71~0.75코어 → **0.172 ms/req**, api 0.941 ms/req, p95 117.5 ms.

## 4. 가설 (원인 추측 — 검증 전)
- 가설 1: 같은 공연의 판매 상태를 요청마다 DB에서 읽는 비용이 api CPU와 DB 커넥션 대기(2,000/s pending 5)로 나타난다.
- 가설 2: 단일 스레드 Redis(`cache.t4g.micro`, TLS)의 메인 스레드가 10,000/s 앞에서 먼저 찬다 — 요청당 왕복 수에 비례한다.

## 5. 검증 (도구로 확인 → 확정된 원인)
- 가설 1: 단계 2의 JFR 표본(`s2jfr` — ADR-024 반영 전 web 경유 구조, 판정 run과 분리, JFR 부담 포함이라 참고용)에서 이 조회가 api CPU의 7.6~11.9%였다. pending은 2,000/s 표본 하나에서만 보였다(3,000/s 0) — DB를 병목으로 확정한 것은 아니다.
- 가설 2: 4,000/s Redis 메인 스레드 0.172 ms/req → 계산상 10,000/s에 1.72코어가 필요하다(단일 스레드 상한 약 5,800/s, 계산값). 앱 노드를 늘려도 넘을 수 없는 상한이라 왕복 수를 줄이는 쪽을 택했다.

## 6. 조치 (해결)
- #345 `BookableEventCache`: 공연 판매 상태를 파드 메모리에 짧게(운영 TTL 1초 — ConfigMap `QUEUE_BOOKABLE_CACHE_TTL_MS=1000`, 기본 0 = 꺼짐) 기억한다. 없는 공연은 기억하지 않는다.
  대가: 관리자가 판매를 멈추거나 재개하면 최대 TTL 동안 파드별로 이전 상태로 진입 토큰을 발급할 수 있다(좌석 선점·주문은 이 캐시를 쓰지 않는다).
- #346 발급 Lua(`ISSUE_LUA`)가 성공 시 `{1, ZRANK+1, ZCARD}`를 함께 돌려줘 신규 진입 응답을 그 자리에서 만든다. 신규 진입 Redis 왕복은 EVALSHA 1 + JWT 블랙리스트 EXISTS 1.
  재진입(이미 토큰 있음) 경로는 바꾸지 않았다. 통합 테스트로 발급 응답의 순번·전체 수가 바로 뒤 `status()`와 같은지 확인한다(CI).

## 7. 결과 (재측정 — before와 같은 조건)
- 같은 rate·시간·발생기 수·api 파드 수·api 배치(노드당 1)로 비교했지만 **이미지 말고도 다른 것이 있다**:
  web 파드 위치(`s6b`·`s8`은 39-203·84-43, `s7`·`s7d`는 84-43·126-121 — 진입은 web을 거치지 않아 영향이 없다고 본다, 추론),
  직전 부하 이력(`s7` 램프는 1,000/s 60초 워밍업 직후, `s6b`는 그런 워밍업 없음 / `s8-r2` 앞에는 워밍업과 `s8-alb-4000`, `s7d` 앞에는 `s7`의 2,000·3,000·4,000/s).
  **칸별 1회**라 [[IMP-025]]의 사전 등록 합격식(판정 3회 중앙값)을 적용하지 않았다 — 아래 CPU 변화는 1회 비교로 참고값이다.
  DB 획득 수·Redis 명령 수는 코드 경로에서 결정되는 값이라 1회로도 변화가 분명하다.
- #345(before → after):

  | DB 커넥션 획득/req(2,000 / 3,000/s) | 1.01 / 1.01 | **0.013 / 0.011** | −99% |
  | api CPU-ms/req(2,000/s) | 1.105 | 0.997 | −9.8%(1회) |
  | api CPU-ms/req(3,000/s) | 1.159 | 0.987 | −14.8%(1회) |
  | p95(2,000 / 3,000/s) | 30.4 / 139.5 ms | 50.6 / 47.3 ms | 2,000/s는 나빠짐(1회) |
  | 노드 CPU 15초 최대(3,000/s) | 0.68~0.75 | 0.60~0.65 | — |
  | 3,000/s 분류(단계 2 기준) | 중간 | **비포화** | — |
- #346(4,000/s·20초·발생기 3대; before `s7d`, after `s8-r2`):
  | 지표 | before | after | 변화 |
  |------|--------|-------|------|
  | Redis 명령/req | 7.03 | **2.03** | −71% |

- 반영 직후 첫 4,000/s(`s8-alb-4000`)는 dropped 409·p95 562 ms였다. 롤아웃 직후 워밍업 1회 뒤라 예열 부족으로 보고(추론) 같은 조건으로 다시 쟀고(`r2`) 꼬리가 사라졌다 — 첫 run을 버린 근거는 이 재측정뿐이다.
- 6a 최종: 5,000/s(`s8-alb-5000`) 오류·dropped 0·p95 77.1 ms·노드 0.69~0.72 → 중간, 4,000/s 비포화(**2회 중 1회** — 첫 `s8-alb-4000`은 중간) → R_pod = 4,000÷3 ≈ 1,333 req/s/파드.
  Redis 0.098~0.104 ms/req(4,000·5,000/s 세 run) → 10,000/s에 메인 스레드 약 1코어(계산값 — 경계선).
- 파드당 처리 한계(R_pod = 비포화로 분류된 가장 높은 rate ÷ 3)의 변화 — 단서와 함께 읽는다:
  | 시점 | 비포화 최고 rate | 다음 칸(분류) | R_pod |
  |------|----|----|----|
  | 두 변경 전(`s6b`) | 2,000/s | 3,000/s(중간 — 오류 0이지만 노드 0.75 ≥ 0.7) | 667 |
  | #345 뒤(`s7`) | 3,000/s | 4,000/s(중간 — 노드 0.76) | 1,000 |
  | #346 뒤(`s8`) | 4,000/s(2회 중 1회) | 5,000/s(중간 — 노드 0.69~0.72, p95 77 ms) | 1,333 |
  - 램프 간격이 1,000/s라 각 값은 **하한**이다(실제 한계는 before 667~1,000 미만, after 1,333~1,667 미만 사이 — 계산).
  - "처리량"이 아니라 비포화 기준이다: before의 3,000/s도 오류·dropped 0으로 처리했다(분류만 중간).
  - 칸이 같지 않다: 2,000·3,000/s는 발생기 1대·30초, 4,000·5,000/s는 발생기 3대·20초(사전 등록의 30초와 다름 — 토큰 10만 개 제약).
  - 667 → 1,333은 #345·#346 두 변경의 **누적**이다.
- 사후 정합성 검사(`check-correctness`) 위 run 모두 위반 없음.

## 8. 트레이드오프 / 한계 / 다음 개선
- 칸별 1회 측정이다. 같은 이미지·같은 rate의 run 간 차이는 4,000/s에서 0.941(`s7d`) 대 1.002(`s7-alb-4000` — 실시간 감시 구간 결함으로 사후 검사가 판정 불가로 끝난 run, SQL·정원·순서 재확인은 위반 없음), #346 뒤 0.778(`s8-alb-4000`) 대 0.696(`r2`)로 6.5~11%였다. #345의 −9.8~−14.8%는 이 범위와 겹쳐 1회로는 판단하기 어렵고, #346의 −26%는 그보다 크지만 역시 1회다.
- 캐시 TTL 동안 판매 상태 변경이 진입 발급에 늦게 반영된다(파드별 최대 1초). 기본값은 꺼짐이라 운영 ConfigMap이 켠 환경에서만 해당한다.
- Redis 메인 스레드는 여전히 다음 한계다 — 10,000/s burst에서 0.86~1.02코어까지 찼다([[IMP-027]]).
- 재진입 경로·상태 조회(폴링)는 이번에 줄이지 않았다 — 폴링 전환(ADR-023 §2)에서 상태 읽기 비용을 따로 잰다.

## 9. 배운 점 (면접 답변용 한 줄)
파드를 18개로 늘리자는 계산이 나왔을 때 증설하지 않고 요청 1건의 DB 조회·Redis 왕복을 세어 보니 반복 조회와 따로 도는 순번 조회가 있었고, 이를 줄여 같은 노드 3대에서 비포화로 처리한 최고 rate를 2,000 → 4,000/s(파드당 667 → 1,333, 램프 간격 1,000/s의 하한값)로 올렸다(4,000/s 비포화는 2회 중 1회) — 다음 한계(단일 스레드 Redis)도 요청당 비용으로 계산해 미리 짚었다.
