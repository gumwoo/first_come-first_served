# ADR-025 · api 요청 CPU를 진입 실측 비용으로 정하고(1000m), HPA를 3~9로 — 반응형 확장을 노드(CA)까지 잇는다

- 상태: **Accepted**(2026-10-07)
- 날짜: 2026-10-07
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-023]](사전 확장·requests 현실화를 운영 방향으로 둔다), [[IMP-027]](10,000/s 진입 용량 계산 6b), [[IMP-029]](최종 시험 — Platform 미증명),
  [[IMP-021]](CA 실증), [[TS-021]](HPA × 커넥션 풀 ≤ RDS 슬롯), [loadtest-100k-plan](../testing/loadtest-100k-plan.md) §6 "확장의 역할"

## 맥락
- 지금 api는 `requests.cpu: 300m`, HPA 3~7(CPU 60%)이다. 7은 "api 7×300 + web 4×300 + 기타가 노드 3대 allocatable 안"이라는 노드 예산에서 나왔다
  (web-hpa.yaml 주석) — CA가 노드를 붙이는 것을 전제로 하지 않았다.
- 진입 burst 실측 비용은 0.70 ms/req이고(IMP-027), 10,000/s를 api 9개가 나누면 파드당 약 1,111 req/s → 약 0.78코어(계산)다.
  300m 기준 HPA 60%(180m)는 처리 용량과 동떨어진 지점에서 반응하고, 노드 하나에 api가 여럿 들어가 Pending(→ CA)이 생기지 않는다.
  최종 시험의 Platform 시연은 그래서 requests를 세션 한정으로 1000m로 바꿔야 했다(IMP-029 §7).
- 계획서 §8 Platform 축은 "사전 확장으로 진입을 받고, 이후 지속 부하에서는 HPA/CA가 정의한 정책대로 확장·축소"를 요구한다. 그 "정책"이 Git에 있어야 한다.

## 결정
1. **api `requests.cpu` 1000m** — 0.70 ms/req × 1,111 req/s × 여유 1.2 ≈ 0.93코어를 올림(계산값). m6i.large(allocatable 1,930m)에 api가 하나만 들어가
   **api 확장이 곧 노드 확장**이 된다. memory(1536Mi)·limits는 그대로.
2. **HPA api 3~9, CPU 60%**(behavior 그대로 — 확장 즉시, 축소 안정화 300초). 9는 10,000/s 진입의 계산 용량(api 9·노드 9)이고
   노드 그룹 상한(AZ당 3, `loadtest.tfvars`)과 같다. web HPA(2~4)는 그대로.
3. **오픈 순간은 Git으로 사전 확장한다** — `k8s/overlays/demo-local/event-prescale.yaml`(HPA 하한 패치, 평소 3 = 효과 없음)을 오픈 전에 9로 올리는
   PR을 머지하면 ArgoCD가 하한을 맞추고, 늘어난 api가 Pending → CA가 노드를 붙인다(노드 그룹 설정은 건드리지 않는다). 오픈이 지나면 3으로 되돌리는 PR을
   머지해 이후는 HPA 정책(3~9)에 맡긴다. 켤 때는 `event`·`off-by`(되돌릴 시각)를 적고, 하네스 k8s 규칙 11이 정책 범위·표기·기한을 검사한다
   (off-by가 지났는데 켜져 있으면 다음 PR의 CI가 실패 — 켜 둔 채 잊어 노드 9대 비용이 나가는 것을 막는다).
   세션 kubectl patch는 쓰지 않는다 — ArgoCD selfHeal이 되돌리고 기록도 남지 않아 IMP-029에서 Platform 축을 닫지 못한 이유 중 하나였다(사용자 결정).
   예약 확장 도구(KEDA 등)는 새 의존성이라 두지 않는다. k8s 매니페스트만 바뀌는 머지는 이미지를 다시 빌드하지 않아(`image.yml` 변경 판별) api 파드를 다시 띄우지 않는다.

## 계산 근거(계산값 — 측정 아님)
- DB 커넥션(TS-021, 하네스 backend 규칙): (maxReplicas 9 + maxSurge 1) × 풀 5 = 50 ≤ 가용 56(db.t4g.micro 79 − reserved 3 − 앱 외 여유 20).
  api 9개는 최종 시험(IMP-027·029)에서 모두 Running이었다.
- 평상시 노드(api 3·노드 3): api 3×1000 + web 2×300 + 기타 약 1,760(측정 세션 20261007-e2e, 노드별 410~750m) = 5,360m / 5,790m.
- vCPU 쿼터 32: 노드 최대 9 × 2 + 발생기 3 × 4 = 30.

## 결과·대가
- 평상시 노드 수는 지금과 같다(3, 계산). 대신 **노드 여유가 거의 없다**: web이 4로 늘거나 api 롤링 배포 surge(+1000m)가 겹치면 CA가 노드를 붙여야
  새 파드가 뜬다 — 롤링 배포가 CA 반응 시간(IMP-021 실측 110초)만큼 길어질 수 있다(추론, 미측정).
- 노드 상한은 Terraform 프로파일에 달렸다: 측정 프로파일(`loadtest.tfvars`, m6i.large·AZ당 3)은 노드 9라 HPA 9와 맞지만, 기본 프로파일(t3.large·AZ당 2)은
  노드 6이라 api가 6을 넘으면 Pending으로 남는다(계산). 기본 프로파일에서 HPA 상한까지 쓰려면 노드 상한을 함께 올려야 한다.
- HPA는 파드 CPU 600m에서 반응한다. 진입 실측 비용 기준이라 burst 중에는 9에 바로 닿고(상한), 지속 부하(대기자 폴링 등)에서는 부하에 비례해 늘고 준다.
- 이 정책으로 확장·축소가 실제로 일어나는지는 통합 판정 run(Platform 축)에서 확인한다 — 이 ADR은 수치를 주장하지 않는다.

## 대안
- **300m 유지 + HPA 상한만 상향**: 노드 하나에 api가 여럿 들어가 CA가 동작하지 않는다(Pending이 생기지 않음). 반응형 확장이 노드까지 이어지지 않는다.
- **노드 단위 분산 규칙(hostname DoNotSchedule)으로 노드당 1개 강제**: requests를 그대로 두면 HPA 기준선(60%)이 여전히 처리 용량과 동떨어진다. 분산 규칙은 별도 판단(`perf/api-node-spread`).
- **세션 kubectl로 사전 확장**: selfHeal이 되돌리고(자동 동기화를 꺼야 함) 언제 무엇을 바꿨는지 Git에 남지 않는다 — IMP-029가 Platform을 닫지 못한 약점.
- **예약 확장 도구(KEDA cron 등)**: 시각으로 켜고 끌 수 있지만 새 의존성이다. PR 두 번(켜기·끄기)으로 충분해 두지 않는다.
- **CronJob이 HPA를 patch**: Git이 소유한 필드라 selfHeal과 싸운다.
