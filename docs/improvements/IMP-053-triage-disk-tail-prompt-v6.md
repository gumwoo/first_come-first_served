- 관련: [[IMP-052]](4차 평가), [[ADR-029]](AI를 쓰는 범위), `scripts/triage/`(normalize.mjs·analyze.mjs), `infra/triage-lab/`
- 벤치 파일: 레포 밖 `artifacts/triage-lab/eval6/`: 사전 등록 `prereg-eval6.md`, 실행 순서 `plan.txt`(시드 202610286), 측정 기록 `runs.txt`·`warmup.txt`, 채점 결과 `result-v6/`·`result-v5/`(Haiku 5.5), 집계 `analysis.txt`

## 1. 상황 (Context)
4차 평가([[IMP-052]])에서 두 가지가 남았다.
- 디스크 프로브 fdatasync p95가 100ms를 넘는 run이 72회 중 39회였고, AI 오답 8회 중 6회와 정상 오탐 1회가 그 run에 있었다(사후 분석, [[IMP-052]] §5.4).
  - 같은 72회에서 예매 전 구간(예매 시작 전) p95가 100ms 이상인 run은 34회로, 분석 구간(39회)과 비슷했다. run 단위로 둘 다 100ms 이상인 run은 19회라 꼬리 지연은 run 안에서도 구간마다 나타났다 사라진다(`eval5/disk-prepost.txt`).
  - 예매 부하가 만든 지연이라면 예매 전 구간에는 적어야 하므로, 측정 환경 잡음으로 봤다(추론).
  - 유형별로는 dbnet이 예매 전 4회·분석 구간 9회, db가 8회·10회로 분석 구간 쪽이 더 많았다. 이 유형에서는 장애가 꼬리 지연을 키웠을 가능성을 가르지 못한다.
- AI는 DB 네트워크 지연(dbnet)의 의심 원인으로 네트워크 경로를 한 번도 적지 않았다(0/12). 프롬프트의 `idle_in_tx_mean` 설명("트랜잭션 안에서 앱 쪽 작업을 기다리는 세션 평균")이 앱 쪽으로 이끌었을 수 있다고 봤다(추측).

이번 평가는 꼬리 지연 run을 측정 유효성에서 빼고, 남은 run을 프롬프트 v5와 v6으로 함께 채점해 설명 문구의 영향만 짝지어 본다.

## 2. 문제 정의 + 분류
- 계층: 운영 도구(분석). 서비스 코드와 무관하다.
- 질문 1(주 질문): dbnet 16회에서 v6가 v5보다 경로 지연을 더 의심하는가.
- 질문 2: 알려진 장애 18회·정상 6회에서 v6가 v5보다 나빠지지 않는가.
- 질문 3: 디스크 꼬리 지연 조건으로 무효가 되는 run은 얼마이고, 유효 run에서 정상 오탐이 사라지는가.
- 질문 4: dbnet에서 사람 확인 표시가 계속 붙는가.

## 3. 바꾼 것 (측정 전 고정, 커밋 739eb156)
- 측정 유효성(`normalize.mjs`): 분석 구간 디스크 프로브 fdatasync p95가 100ms를 넘으면 무효로 둔다(사유 "디스크 프로브 fdatasync p95 …"). 기존 중앙값 조건은 그대로다.
  - 100ms는 4차 72회의 p95 분포가 65ms 이하(33회)와 108ms 이상(39회)으로 갈린 틈에서 골랐다.
- 프롬프트 v6(`analyze.mjs`, `triage-prompt/v6`): v5와 `db.idle_in_tx_mean` 설명 한 줄만 다르다.
  - v5: "트랜잭션 안에서 앱 쪽 작업을 기다리는 세션 평균"
  - v6: "트랜잭션을 연 채 다음 명령을 기다리는 세션 평균(PostgreSQL state idle in transaction)"
  - 정답을 암시하지 않도록 네트워크·왕복 같은 낱말은 넣지 않고 PostgreSQL 상태 정의만 남겼다.
- 실험실 호스트 포트를 `LAB_API_PORT`·`LAB_QUEUE_PORT`로 바꿀 수 있게 했다(기본 18080·18081). 이번 측정은 다른 컨테이너가 18080을 써서 28080·28081로 돌렸다. 측정 경로는 같다.
- 그대로인 것: 규칙(`rules.mjs`), 대조(`verify.mjs`), 파이프라인, 출력 형식 v5, 모델 Haiku 5.5, 정상 기준, 장애 주입 값(redis 30·60ms, db 0.05·0.03코어, cpu 0.4·0.25코어, dbnet 3·10ms).
- v6으로 이전 run을 미리 채점해 보지 않았다.

## 4. 측정 방법
- 판정 기준은 측정 전에 등록했다(`prereg-eval6.md`, 2026-10-28 20:17:06).
- 계획: dbnet × 강도 1·2 × 8회 = 16회, redis·db·cpu × 강도 1·2 × 3회 = 18회, 정상 6회. 합계 40회, 실행 순서는 무작위(시드 고정).
- 예열 run 1회 뒤 시작했다. run마다 직전에 디스크 확인(10초 프로브 중앙값 5ms 이하)을 통과한 뒤 시작했다.
- 채점: 같은 유효 run 40회를 두 번 채점했다. v6은 이 브랜치의 `eval.mjs`, v5는 main(0c84828b)의 `scripts/triage`를 내보낸 복사본이다. 규칙·파이프라인은 두 채점이 같다.
- 경로 지연 언급: 의심 원인 1~3순위의 이름·이유에 정규식 `네트워크|왕복|패킷|network|round[- ]?trip|packet|(?<![a-z_])rtt`(대소문자 무시)가 맞으면 센다. 4차에서 입력 필드 이름 `scrape_rtt_ms`가 걸린 것을 빼려고 `rtt` 앞에 영문자·밑줄이 없을 때만 센다.

측정 경과(`runs.txt`, 20:22~22:38): 40칸 모두 유효 run을 얻었다. 시도는 57회였고 무효 17회는 사전 등록 규칙대로 다시 찍었다.
- 측정 환경 사유(상한 없이 재측정): 디스크 프로브 p95 기준 초과 13회, 중앙값 기준 초과 1회
- 그 밖의 사유(같은 조건 최대 2회 더): 디스크 프로브 표본 부족 3회. 첫 dbnet 10ms 칸에서 2회, dbnet 3ms 한 칸에서 1회 나왔다. 첫 칸은 재측정 2회를 모두 썼고, 마지막 시도에서 유효 run을 얻었다.
- p95 조건 무효를 유형별로 보면 정상 11회 시도 중 5회, dbnet 26회 중 6회, 알려진 장애 20회 중 2회다.
- 예열 run은 예매 결과 0건·프로브 표본 부족으로 무효였다. 예열은 결과에 쓰지 않는다.

### 5.3 디스크 꼬리 지연 조건 (질문 3)
- **판정(사전 등록): 조건 유지.** 유효 run에서 규칙·v5의 정상 오탐은 모두 0이다.

## 6. 조치
- 측정 유효성에 디스크 프로브 fdatasync p95 100ms 조건을 둔다(`normalize.mjs`). 측정 환경 사유라 무효 run은 상한 없이 다시 찍는다.
- 프롬프트는 v6을 쓴다. 경로 지연 언급은 v5와 같았고(질문 1), 알려진 장애·정상 판정은 나빠지지 않았다(질문 2). 필드 설명이 원인을 앞서 말하지 않는 PostgreSQL 상태 정의라서 v6을 둔다.
- 최종 판정은 규칙 기준으로 유지한다([[ADR-029]] 결정 9). 규칙, 원인 범주, 출력 형식, 모델은 그대로 둔다.

## 7. 트레이드오프 / 다음 개선
- 측정 시간: 유효 40회에 시도 57회가 들었다(약 2시간 16분). 꼬리 지연이 잦은 날에는 더 걸린다.
- 경로 지연: 설명 문구만 바꿨을 때 AI는 경로 지연을 의심 원인으로 적지 않았다(사전 등록 범위인 의심 원인 이름·이유 기준). 앱에서 잰 쿼리 시간과 DB에서 잰 실행 시간을 함께 주면 그 차이로 경로 지연을 가를 수 있다(추론). 입력 필드를 늘리는 변경이라 따로 정하고 새 평가 run으로 잰다.
- dbnet 3ms는 예매 p95가 이상 기준 아래라 규칙이 정상으로 보고 AI를 부르지 않는다. Slack에도 오지 않는다.
- 짝지은 비교는 프롬프트마다 한 번씩 부른 결과다. 같은 입력에 다른 답이 나오는 변동과 문구 효과를 가르지 못한다. 알려진 장애는 칸당 3회라 v5·v6의 1회 차이는 우연과 구분되지 않는다.
- 측정 조건: 로컬 상대 비교다. 장애는 하나씩만 주입했다.

## 8. 배운 점 (면접 답변용 한 줄)
AI 오답이 몰린 디스크 꼬리 지연 run을 측정 유효성에서 빼고, 같은 run을 프롬프트 두 판으로 짝지어 채점해 필드 설명 한 줄의 영향만 따로 쟀다. 설명을 바꿔도 경로 지연 언급은 0으로 같았다. 경로 지연을 가르려면 앱에서 잰 쿼리 시간 같은 입력 필드가 필요하다고 본다(추론).
