# IMP-054 · 장애 알림에 원인 분석 붙이기(로컬): 알림이 울리면 Prometheus 지표로 분석해 Slack 메시지를 만든다

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-29~30(로컬 실험실 `infra/triage-lab`, 결과 `artifacts/triage-lab/alert1~3/`, `artifacts/triage-lab/alerts/`, 레포 밖)
- 유형: 기능 + 경로 확인(로컬 실측 31회). 운영(EKS) 클러스터에서는 돌리지 않았다.
- 관련: [[IMP-052]](Slack 알림), [[IMP-053]](5차 평가), [[ADR-029]](AI를 쓰는 범위, 결정 11 추가), [[TS-041]](운영 actuator 관리 포트)
- 벤치 파일: 레포 밖 `artifacts/triage-lab/alert1/`·`alert2/`·`alert3/`(사전 등록 `prereg.md`, 측정 기록 `runs.txt`, 집계 `analysis.txt`·`alert3/table.txt`), 분석 결과 `alerts/<시각>-<알림>/`

## 1. 상황 (Context)
장애 초기 분석 도구는 부하 시험 run이 끝난 뒤 사람이 돌려야 했다. 운영 알림(Prometheus·Alertmanager → Slack)과는 이어져 있지 않았다.
장애가 나면 알림이 오고, 그 알림에 원인 후보와 확인 방법이 함께 붙어야 한다. 이 경로를 실험실에서 먼저 만들고, 장애를 넣어 실제로 울리는지 확인했다.

## 2. 문제 정의 + 분류
- 계층: 운영 도구(관측·분석). 서비스 코드는 바꾸지 않았다.
- 질문 1: 장애를 넣으면 알림이 울리고, 알림마다 분석 메시지가 하나씩 만들어지는가.
- 질문 2: 알림 경로(Prometheus 지표)의 규칙 판정이 같은 run의 run 수집(sampler·psql·cgroup 파일) 판정과 같은가.
- 질문 3: 장애를 넣지 않은 run에서는 알림이 울리지 않는가.

## 3. 바꾼 것
| 구성 | 내용 |
|---|---|
| Prometheus(실험실, 1초 긁기) | api·대기열 actuator, PostgreSQL 세션·WAL(postgres-exporter 사용자 쿼리, run 수집의 `pgwatch.sql`과 같은 항목), api cgroup CPU(cAdvisor와 같은 이름) |
| 알림 규칙(실험실) | `FlowticketBookingSlow`: 예매 세 단계 서버 p95 > 1.5초 5초 지속 / `FlowticketBookingStalled`: 처리 중인 POST 요청 중 가장 오래된 것 > 5초 / `FlowticketApiUnresponsive`: api 지표 긁기 실패(`up=0`) 5초 지속 |
| Alertmanager | 모든 알림을 호스트의 분석 훅으로 보낸다 |
| 분석 훅 `alert-hook.mjs` | 알림 앞에서 예매 구간을 찾아 요약을 만들고(`prom-summary.mjs`, run 요약과 같은 형식), 규칙 → AI → 수치 대조 → Slack 메시지. 결과는 알림마다 폴더 하나 |
| 메시지 `alertSlackText` | 규칙과 AI가 같아도 보낸다. 갈리면 사람 확인을 부탁한다. 지표가 모자라면 분석하지 못한 이유와 먼저 볼 곳을 보낸다(`alertInvalidText`) |

- 예매 구간은 run 요약과 같은 식으로 잡는다. 시작은 예매 요청이 끝나기 시작한 초(또는 처리 중인 POST가 생긴 초)이고, 지표 구간은 시작 −2초 ~ 시작 + min(30, max(15, 마지막 응답까지 + 2))초다. 예매 p95와 5xx는 마지막 응답까지(최대 90초) 본다.
- run 수집과 다른 점
  - 예매 p95는 서버 히스토그램 값이다(상한 10초라 넘으면 10,000ms로 찍힌다).
  - PostgreSQL 표본이 1초 간격이고, 디스크 프로브가 없다.
  - 지표 응답 최대(`api.scrape_rtt_ms_max`)는 긁기 시간 초과(1초)에서 잘린다. 3차 유효 요약은 모두 1,002~1,003ms였고 같은 run의 run 수집 값은 1,194~5,081ms였다. 규칙의 앱 CPU 예비 갈래(점유 값이 없을 때 1,000ms 초과)와 AI가 보는 값의 뜻이 run 요약과 다르다.
- 알림이 이미 이상을 알렸으므로 규칙이 이상 없음으로 봐도 측정이 유효하면 AI를 부른다([[ADR-029]] 결정 11).
- 규칙(`rules.mjs`), AI 프롬프트(v6)·출력 형식, 수치 대조는 그대로다.

## 4. 측정 방법
- 세 차례 나눠 돌렸다. 차례마다 측정 전에 질문과 판정을 적었다(`prereg.md`, 2026-10-29 16:43:43 · 17:23:43 · 2026-10-30 00:01:31). 앞 차례에서 나온 문제를 고친 뒤 다음 차례를 돌렸다.
- 주입: redis 30ms(강도 1), db 0.05코어(강도 1), cpu 0.4·0.25코어, dbnet 10ms(강도 2), 정상. 순서는 손으로 섞어 고정했다. 재측정은 하지 않았다.
- 훅은 미리 보기로 돌렸다(Slack 전송 없음). 2·3차는 run마다 디스크 확인(10초 프로브 중앙값 5ms 이하)을 통과한 뒤 시작했다.
- 같은 run에서 run 수집 요약도 만들어(`normalize.mjs`) 규칙 판정을 비교했다. 알림은 (예매 시작 − 45초, 주입 시점)이 알림 시각보다 앞선 run 중 가장 늦은 run의 것으로 셌다.

### 5.2 차례마다 나온 문제와 고친 것
1. **긁기 시간 초과로 지표가 끊김(1차).** api가 바쁘면 `/actuator/prometheus` 응답이 1초를 넘어 긁기가 실패하고, 그 사이 시계열이 끊긴다(stale). 첫 구현은 끊긴 뒤 처음 보인 점을 예매 시작으로 잡아 구간이 묶음 뒤로 밀렸다(1차 전 시험 run aa051e95, redis 30ms의 서버 p95가 221ms로 계산됨). 끊긴 뒤 요청 수가 늘었으면 끊기기 직전 점 다음을 시작으로 본다. 같은 run을 다시 계산하면 서버 p95가 hold 2,371ms·order 2,128ms로 클라이언트 값(2,756·2,130ms)에 가까워졌다.
2. **멈춘 요청은 p95 알림으로 못 잡음(1차).** db 0.05코어 run 두 회는 응답이 30~60초 걸렸는데 p95 알림이 울리지 않았다. p95는 끝난 요청만 센다. 처리 중인 요청의 나이로 보는 `FlowticketBookingStalled`를 더했다.
   - 이 알림은 2·3차에서 한 번도 울리지 않았다(pending도 없음). 멈춘 동안에는 api 긁기도 실패해 처리 중 요청 지표가 보이지 않았던 것으로 본다(추론). 2차 db 0.05코어 두 회는 알림이 없었고, 3차 두 회는 5.2-3의 긁기 실패 알림으로만 잡혔다.
   - 훅이 처리 중인 POST로 예매 구간 시작을 잡는 분기는 처음에 없는 지표 이름(`_active_count`)을 읽어 동작하지 않았다. 실제 이름(`_gcount`, 처리 중 요청 타이머도 히스토그램 설정 접두어에 걸린다)으로 고친 뒤 세 차례 알림을 다시 계산했다. 알림 2개(081843, 152900)에서 구간 시작이 1~2초 앞당겨져 일부 수치가 바뀌었지만, 유효성과 규칙 판정은 바뀌지 않았다.
3. **지표가 통째로 없음(2차).** dbnet 10ms run에서 api 긁기가 19초 연속 실패해 그동안 지표가 없었고, 알림 두 개 모두 울릴 수 없었다. 긁기 실패 자체를 신호로 쓰는 `FlowticketApiUnresponsive`를 더했다. 같은 차례에 응답이 30초를 넘은 run은 분석 구간 안에 끝난 요청이 없어 p95가 비었다. 예매 p95를 마지막 응답까지 보게 바꿨다.
4. **DB가 느리면 api 지표 요청도 늦어짐(3차).** db 0.05코어 run에서 `FlowticketApiUnresponsive`는 예매 시작 39초 전(주입 직후)부터 울렸지만, api 지표가 계속 끊겨 훅이 예매 구간을 찾지 못했다.
   - api의 지표 응답은 게이지 값을 채우려고 매번 DB 쿼리 4개(아웃박스 DEAD·PENDING 수, 가장 오래 기다린 행, 초과 판매 좌석)를 돌린다(`OperationalMetrics`, 코드로 확인). 예매 요청이 들어오기 전부터 긁기가 실패한 것은 이 쿼리가 늦어졌기 때문으로 본다(추론, 직접 잰 증거는 없다).
   - 3차 뒤 훅이 이 경우를 "긁기가 끊겨 예매 구간을 찾지 못했다"로 가르고, 메시지에 "api 요청 스레드와 DB 상태를 같이 보라"를 붙이게 고쳤다(5.1의 다시 계산). 게이지를 DB에서 떼는 일은 서비스 코드 변경이라 따로 다룬다.

### 5.4 메시지 (미리 보기, 3차)
규칙과 AI가 같은 run(d7dca392)과 갈린 run(e59abf3f)의 메시지다. 확인 방법은 AI 답의 첫 문장이다.

```

규칙으로는 Redis 지연으로 나와요. Redis 명령 완료가 평균 34.08ms였거든요.
AI도 같은 쪽("Redis 응답 지연(입장 검증·토큰 블랙리스트·좌석 알림 명령)")으로 봤어요.
• Redis 서버 측 slowlog·latency 지표와 명령별 지연을 확인하고, 같은 시각에 Redis 완료 시간이 올라간 것이 예매 지연과 시간적으로 겹치는지 보기
```
```
[장애 알림 분석] FlowticketBookingSlow 알림 구간에서 예매가 느려졌어요. p95가 2,384ms까지 올라갔고, 커넥션 하나 받는 데 평균 803ms 기다렸어요.
규칙으로는 앱 CPU 부족으로 나와요. 커넥션을 한 번 잡으면 평균 60.1ms씩 쥐고 있었는데, Redis랑 DB 수치는 괜찮았거든요.
그런데 AI는 "api 프로세스 내부 정지(JVM 일시 정지 또는 스레드 블로킹)로 Hikari 커넥션을 트랜잭션 안에 쥔 채 멈춤" 쪽을 더 의심하고 있어서 한번 봐주시면 좋겠어요. AI도 확정은 못 했대요.

```

### 5.5 비용
세 차례 분석 24회 중 AI 호출 19회(나머지는 측정 무효라 부르지 않음), 입력 합 100,339·출력 합 77,094토큰, 약 $0.049(공개 단가 입력 $0.10·출력 $0.50 / 100만 토큰으로 계산). 대조 실패 2회. 1차 전 시험 run(aa051e95) 분석 1회는 빼고 셌다.

## 6. 조치
- 실험실에 알림 경로(Prometheus·Alertmanager·exporter)와 분석 훅을 둔다(`lab.sh alerting`, `alert-hook.mjs`).
- 알림에 붙이는 분석은 규칙과 AI가 같아도 보내고, 갈릴 때만 사람 확인을 부탁한다. 지표가 모자라면 이유와 먼저 볼 곳을 보낸다([[ADR-029]] 결정 11).
- 실험실 run 수집기(`sampler.mjs`)는 `127.0.0.1`로 접속한다. 이 PC에서 `localhost`가 IPv6로 풀려 Docker 포트 전달이 연결을 끊어, 지표를 하나도 못 읽은 run이 있었다.

## 7. 트레이드오프 / 다음 개선
- 운영 연결: 운영 클러스터는 띄우지 않아 EKS에서는 돌리지 않았다. 운영 Alertmanager는 지금 Slack으로만 보내므로 훅을 웹훅 수신처로 더해야 하고, PostgreSQL 세션 지표는 RDS에서 따로 모아야 한다(실험실은 postgres-exporter). 규칙 기준값은 실험실에서 정한 값이다.
- 지표 응답의 DB 의존: api 지표 응답이 DB 쿼리를 돌려, DB가 느릴 때 지표가 통째로 사라진다(5.2-4). 게이지 값을 주기적으로 미리 세어 두는 방식을 따로 검토한다.
- 실험실 긁기는 요청과 같은 포트(8080)다. 운영은 관리 포트(8081)를 따로 둬 요청 스레드가 밀려도 긁기는 덜 막힌다([[TS-041]]). 실험실 run 수집기의 "지표 응답 시간"이 이 포트에 기대고 있어 바꾸지 않았다.
- 알림 규칙은 지연이 생겨야 울린다. CPU 할당량에 막혔지만 p95가 기준 아래인 run(cpu 0.4코어)은 알림이 없다.
- 멈춤 알림(`FlowticketBookingStalled`)은 실험실에서 울린 적이 없다. 긁기와 요청이 같은 포트를 쓰는 동안은 긁기 실패 알림이 멈춤을 대신 잡는다. 관리 포트를 따로 둔 운영에서 다시 본다.
- 알림이 예매 시작 전에 울리면(주입 직후 긁기 실패) 훅이 알림 앞만 봐서 예매 구간을 찾지 못한다.
- 같은 구간의 두 번째 알림이 첫 분석이 도는 동안 오면 건너뛴다. 그 뒤 첫 분석이 실패하면 그 구간은 메시지가 없다(실패 뒤에 오는 알림은 다시 분석한다).
- 디스크가 느린 시간대에는 정상 run에서도 지연 알림이 울렸다. 알림 경로에는 디스크 프로브가 없다.
- 한 장애에 긁기 실패 알림이 여러 번(해제 뒤 다시) 울리면 예매 구간을 못 찾은 분석이 겹쳐 나온다. 같은 구간은 한 번만 분석하지만, 구간을 못 찾은 알림끼리는 묶지 않는다.
- Slack 실제 전송은 이번 확인에서 하지 않았다(미리 보기). 전송 함수와 웹훅 확인은 [[IMP-052]]와 같다.

## 8. 배운 점 (면접 답변용 한 줄)
알림이 울리면 그 구간 지표로 원인 후보와 확인 방법을 붙이는 경로를 실험실에서 만들고, 장애를 넣어 세 차례 돌렸다. 긁기 시간 초과로 지표가 끊기는 구간, 끝나지 않는 요청, DB 쿼리를 도는 지표 응답처럼 "지표가 가장 필요할 때 지표가 없는" 경우가 차례마다 나와, 긁기 실패 자체를 알림 신호로 쓰고 구간 계산과 유효성 조건을 그에 맞춰 고쳤다.
