# IMP-051 · 장애 초기 분석 3차 평가(로컬): 할당량 갈래 선행, 규칙 기준 최종 판정과 사람 확인 표시, 규칙이 모르는 장애(DB 네트워크 지연) 포함 30회

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-28(로컬 실험실 `infra/triage-lab`, 결과 `artifacts/triage-lab/eval4/`, 레포 밖)
- 유형: 평가(로컬 실측, 유효 run 30회). 같은 로컬 환경 안의 비교다.
- 관련: [[IMP-045]](2차 평가·보완 합산), [[ADR-029]](AI를 쓰는 범위), `scripts/triage/`(rules.mjs·triage.mjs·eval.mjs), `infra/triage-lab/lab.sh`
- 벤치 파일: 레포 밖 `artifacts/triage-lab/eval4/`: 사전 등록 `prereg-eval4.md`, 실행 순서 `plan.txt`(시드 20261028), 측정 기록 `runs.txt`·`warmup.txt`, 채점 결과 `result/`(Haiku 5.5). dbnet 강도를 정한 개발 run은 `artifacts/triage-lab/dev-v5/`

## 1. 상황 (Context)
2차 평가와 보완 합산([[IMP-045]] §8)에서 규칙이 놓친 run은 CPU 강도 1이었다. 할당량에 막힌 주기 비율은 0.23·0.21로 기준(0.2)을 넘었지만, 예매 p95 중앙값(1,408·999ms)이 이상 판단 기준(1,500ms) 아래라 규칙이 먼저 "정상"으로 끝냈다.

이 갈래를 고치면 알려진 세 장애에서는 규칙만으로도 맞힐 수 있다. 그러면 AI를 쓰는 이유는 규칙이 갈래를 갖고 있지 않은 장애에서 드러나야 한다. 그래서 이번 평가에는 규칙 분류기를 만들 때 없던 장애를 하나 넣었다.

## 2. 문제 정의 + 분류
- 계층: 운영 도구(분석). 서비스 코드와 무관하다.
- 질문 1: 할당량 갈래를 예매 p95 이상 판단보다 먼저 보면, CPU 강도 1을 놓치지 않으면서 정상 오탐이 생기지 않는가.
- 질문 2: 규칙이 모르는 장애(dbnet: api와 PostgreSQL 사이 네트워크 지연)에서 규칙·AI·파이프라인은 각각 어떻게 답하는가. AI가 규칙과 다른 답을 내고, 파이프라인이 그 run을 사람이 확인하도록 표시하는가.

## 3. 바꾼 것 (측정 전 고정, 커밋 25a0f2ce)
- 규칙(`rules.mjs`): 할당량에 막힌 주기 비율(> 0.2) 갈래를 예매 p95 이상 판단보다 먼저 본다. 기준값은 그대로다.
- 파이프라인 최종 판정(`triage.mjs` `pipelineVerdict`):
  - 규칙이 정상이면 AI를 부르지 않고 정상으로 끝낸다.
  - 규칙이 원인을 내면 규칙 판정을 최종으로 쓴다. 근거 수치 대조를 통과한 AI 판정이 이와 다르면(원인이 다르거나 판단 불가) "사람 확인"으로 표시한다.
  - 규칙이 이상은 보았지만 어느 갈래에도 해당하지 않으면(판단 불가) 대조를 통과한 AI 판정을 쓴다.
  - 보고서에 "최종 판정" 줄과 표시 문구를 넣었다.
- 실험실(`lab.sh`): dbnet 주입. PostgreSQL 컨테이너 eth0에 `tc netem` 지연을 건다. 측정용 psql도 같은 네트워크로 접속한다.
- 그대로인 것: 프롬프트 v4(원인 범주 redis·db·app_cpu 세 가지, dbnet 설명 없음), 모델 Haiku 5.5, 요약(`normalize.mjs`), 대조(`verify.mjs`), 정상 기준, 다른 장애 주입 값.

dbnet 강도는 개발 run 3회(평가에 쓰지 않음)를 보고 정했다. 3ms에서 예매 p95 중앙값 2,352ms, 10ms에서 3,050ms(같은 시기 대조군 1,162ms)였고, 두 run 모두 규칙은 커넥션 점유 갈래로 app_cpu였다. 강도 1 = 3ms, 강도 2 = 10ms로 정했다. 규칙의 dbnet 판정을 이때 보았지만 규칙·프롬프트는 바꾸지 않았다.

## 4. 측정 방법
- 판정 기준은 측정 전에 등록했다(`prereg-eval4.md`, 2026-10-28 11:26:50).
- 계획: redis·db·cpu × 강도 1·2 × 3회 = 18회, 정상 6회, dbnet × 강도 1·2 × 3회 = 6회. 합계 30회, 실행 순서는 무작위(시드 고정). 이전 평가·개발 run은 쓰지 않았다.
- 실험실 재기동 뒤 예열 run 1회(유효)를 먼저 돌렸다. run마다 직전에 디스크 확인(10초 프로브 중앙값 5ms 이하)을 통과한 뒤 시작했다.
- 채점(`eval.mjs`): AI는 유효 run 전부에 불렀다(AI 단독). 같은 요약으로 규칙·파이프라인을 함께 판정했다.
  - 알려진 장애 24회는 2차와 같은 방식으로 센다.
  - dbnet은 가장 가까운 범주를 db(앱이 본 DB 접근 지연)로 두고 db·판단 불가·그 밖의 판정(오판)을 센다. 정상 판정도 오판으로 센다.

측정 경과(`runs.txt`, 11:31~12:43): 30칸 모두 유효 run을 얻었다. 디스크 프로브 중앙값 47ms로 무효였던 run 1회(dbnet 강도 1 첫 시도)는 사전 등록대로 같은 조건으로 다시 찍었다.

- 강도 2(10ms) 3회:
  - 규칙은 커넥션 점유 평균(63.5~65.0ms, 기준 20ms)과 지표 응답 최대(3,442~5,208ms, 기준 1,000ms)로 app_cpu를 냈다.
  - AI는 3회 모두 원인을 단정하지 않았다. 3회 모두 할당량에 막힌 주기 비율 0을 들어 CPU 부족 근거가 없다고 적었고, DB 실행 세션은 거의 없는데 트랜잭션 안 앱 대기(`idle_in_tx_mean` 1.42~1.75, 정상 상한 0.28)가 크다고 적었다. 앞의 것은 규칙의 app_cpu 판정과 맞지 않는 지표다.

  - 1회(e2dbe159)는 후보로 db(확신도 low)를 냈다.
- 강도 1(3ms) 3회:
  - 예매 p95 중앙값이 844~1,144ms로 이상 판단 기준(1,500ms) 아래였다. 규칙은 정상으로 판정했고, 파이프라인은 규칙이 정상이면 AI를 부르지 않으므로 세 run 모두 정상으로 끝났다.
  - AI 단독은 2회 정상, 1회(246ec9ca, p95 1,144ms로 정상 기준 상한 1,069ms를 넘음) 판단 불가였다.
  - 개발 run의 3ms(p95 2,352ms)와 차이가 크다. 그 개발 run은 실험실 재기동 뒤 예열이 실패한 상태에서 돌았고, 평가는 예열 run 1회 뒤 시작했다(차이의 원인은 추론).
- 세 판정자 모두 dbnet을 db로 판정하지 못했다. 프롬프트의 원인 범주(redis·db·app_cpu)는 "DB 쿼리가 느리다"를 db로 보는데, dbnet에서는 DB 실행 세션이 거의 없어 AI가 db 근거를 약하다고 적었다.
- dbnet은 6회라 차이는 우연과 구분되지 않을 수 있다.

## 6. 조치
- 규칙의 할당량 갈래를 예매 p95 이상 판단보다 먼저 두는 변경을 채택한다(5.1).
- 파이프라인의 최종 판정은 규칙 기준으로 두고, AI 판정이 다르면 사람 확인으로 표시한다([[ADR-029]] 결정 9).
  - 알려진 장애에서는 표시가 0회라 사람이 볼 run이 늘지 않았다.
  - 규칙이 모르는 장애에서 규칙이 원인을 낸 3회는 모두 표시됐다.
- 원인 범주·프롬프트·모델은 그대로 둔다.

## 7. 트레이드오프 / 다음 개선
- 규칙이 정상으로 판정한 run은 AI를 부르지 않는다. dbnet 강도 1처럼 예매 p95가 기준 아래인 장애는 파이프라인에서 보이지 않는다. 이 run들은 AI 단독으로도 2/3이 정상이었다.
- 사람 확인 표시는 "AI가 규칙과 다르다"만 알린다. 이번 dbnet에서 AI는 원인을 단정하지 않았고, 근거·반대 지표·확인할 항목만 남겼다.
- 측정 조건: 로컬 상대 비교다. 규칙이 모르는 장애는 한 종류(dbnet)이고, 장애는 하나씩만 주입했다.
- 다음 개선 후보(각각 새 평가 run으로 다시 잰다):
  - 원인 범주에 "DB까지 가는 경로 지연"을 더할지(트랜잭션 안 앱 대기는 크고 DB 실행 세션은 적은 경우).
  - 규칙이 정상이어도 정상 기준을 벗어난 지표가 있으면 AI를 부를지(246ec9ca의 경우). 이때는 알려진 정상 run의 오탐을 함께 잰다.

## 8. 배운 점 (면접 답변용 한 줄)
규칙을 고쳐 알려진 장애에서 규칙과 AI가 모두 18/18이 된 뒤, AI를 쓰는 이유를 확인하려고 규칙이 모르는 DB 네트워크 지연을 평가에 넣었다. 규칙은 이를 앱 CPU 부족으로 잘못 판정했고, AI는 CPU 할당량 막힘이 0이고 트랜잭션 안 앱 대기가 크다는 지표를 들어 원인을 단정하지 않았다. 파이프라인은 그 3회를 모두 사람 확인으로 표시했고, 알려진 장애에서는 헛표시가 0회였다.
