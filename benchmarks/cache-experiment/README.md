# 캐시 실험 0단계 — 엔드포인트별 비용 (2026-08-16)

캐시로 얻을 수 있는 개선의 **상한(Amdahl 분모)**을 구한다. 계획: [cache-experiment-plan](../../docs/testing/cache-experiment-plan.md)

## 측정 방법

**구간을 못박고 그 구간의 CPU seconds 증분을 실제 완료 요청 수로 나눈다.**

```
요청당 CPU = (구간의 CPU seconds 증분 − 같은 길이 idle 구간의 증분) ÷ 완료 요청 수
```

`rate()` 순간 샘플이 아니라 `increase(...[D초])`를 구간 끝 시각에 평가한다 — 분자와 분모가
**같은 구간**을 가리키게 하기 위해서다.

```
엔드포인트마다:
  1) 본측정과 같은 도착률로 60초 워밍   ← HPA를 미리 최대로 올려 측정 중 파드 수를 고정
  2) 본측정 90초, 시작·종료 시각 기록
  3) 그 구간의 CPU 증분 / Hikari max_over_time / 파드 수 min·max 수집
```

**파드 수가 구간 내내 7로 불변임을 min/max로 확인**했다 — 파드가 뜨고 지면 기동 비용이
CPU 증분에 섞인다(아래 §바로잡은 것 ②).

`idle`은 3파드에서 재고 **파드당 상수로 환산**했다. HPA를 고정하려 했으나 ArgoCD가
`selfHeal: true`로 되돌린다 — 매니페스트를 고치지 않는 한 파드 수는 못 박는다.
파드당 idle을 두 번 쟀을 때 0.0120 / 0.0114 core로 일치해 **환산 가정이 데이터로 뒷받침된다.**

## 조건

```
api HPA 3~7 / web HPA 2~4, requests 각 300m
노드 t3.large × 3 (allocatable 합 5.79 core)
측정 시점 파드: api 7 / web 4 (불변 확인)
k6는 클러스터 밖(노트북)에서 인터넷 경유
```

## 결과 — 요청당 증분 CPU (400 rps · 90초 · **2회**)

세 측정 모두 도착률 100% 달성(36,003건), 실패 0%, dropped 0, **Hikari pending max ≤ 1**.

| EP | api r1 | api r2 | **api 평균** | 편차 | **node 평균** | **web 평균** |
|---|---|---|---|---|---|---|
| seats | 2.70 | 2.45 | **2.57** | 9.8% | **4.99** | 2.08 |
| list | 2.16 | 1.96 | **2.06** | 9.9% | **4.51** | 2.09 |
| detail | 1.75 | 1.66 | **1.71** | 5.3% | **4.33** | 2.19 |

단위 ms/req. ⚠️ **반복 간 편차가 5~10%다.** 소수 둘째 자리까지 유효하다고 읽으면 안 된다.

## 판정 ① — 요청 비율 ≠ 비용 비율

혼합 50:30:20에서의 **api CPU 비용** 비중:

| EP | 요청 비율 | api CPU 비중 |
|---|---|---|
| seats | 50% | **57.3%** |
| list | 30% | 27.5% |
| detail | 20% | 15.2% |

seats 한 건은 detail 한 건보다 api CPU를 **약 1.5배**(2.57 / 1.71) 쓴다. 그래서 요청의 절반인
seats가 비용의 57%를 차지한다.

**"요청이 가장 많은 API부터 최적화한다"가 아니라 "트래픽 비율 × 요청당 비용으로 봐야 한다"**는
것을 이 시스템에서 직접 확인했다.

## 판정 ② — web 계층 비용은 엔드포인트별 편차가 작다

```
seats 2.08 / list 2.09 / detail 2.19   (ms/req)
```

api 계층이 2.57 ~ 1.71로 **1.5배** 벌어지는 동안 web 계층은 거의 평평하다.

⚠️ **원인은 분해하지 않았다.** Next.js 프록시·TLS/HTTP 처리·직렬화·Node 런타임·공통
미들웨어 중 무엇인지 나누지 않았다. 여기서 말할 수 있는 것은 **"엔드포인트 작업과
독립적으로 보이는 공통 web 계층 비용이 존재한다"**까지다.

그래도 상한 계산에는 충분하다 — **API에 캐시를 넣어도 이 몫은 줄지 않는다.**
혼합 요청당 node 4.71ms 중 **api는 2.24ms(48%)뿐**이다.

## 캐시 개선 상한 (⚠️ 계산이며, 강한 가정 위에 있다)

| 캐시 대상 | **최대 배수** |
|---|---|
| seats만 | **1.38배** |
| 셋 다 | **1.91배** |

**깔린 가정 네 가지 — 하나라도 깨지면 이 숫자는 성립하지 않는다.**

1. 처리량의 지배 병목이 여기서 잰 **CPU**다
2. 캐시 적용 후 **다른 병목은 동일**하다
3. 캐시가 해당 API의 계산 비용을 **이상적으로 전부 제거**한다(실제로는 조회·역직렬화가 남는다)
4. 트래픽 믹스가 **50:30:20 그대로**다

그래서 말할 수 있는 것은 이 범위다.

> **현재 관측한 CPU 비용 구조만 놓고 보면, API 응답 캐시만으로 CPU 한계가 10배 개선되는 것은
> 불가능하다. 이상적으로 API 계산 비용을 전부 제거해도 node CPU 기준 상한은 약 1.9배다.**

실제 개선폭은 2단계(AS-IS/TO-BE)에서만 나온다.

## ⚠️ 측정 중 바로잡은 것 ① — 콜드 스타트를 포화로 오판했다

```
관측    seats @200 rps 첫 실행 → p95 4.65s, dropped 86, Hikari pending max 215
가설    이 엔드포인트가 200 rps에서 포화한다
반증    같은 200 rps 재실행 → p95 30.9ms, dropped 0, pending 0
원인    혼합 워밍업이 seats 경로의 애플리케이션 상태를 충분히 워밍하지 못했다
절차    엔드포인트별로 **자기 경로를 워밍**한 뒤 본측정
```

**150배 차이는 측정 노이즈가 아니라 완전히 다른 시스템 상태다.** 여기서 멈췄다면
"seats는 200 rps에서 포화한다"는 잘못된 결론을 계획서에 박았을 것이다.

⚠️ **콜드 상태의 내부 원인(JIT·DB 버퍼 캐시·커넥션 수립 중 무엇인지)은 분해하지 않았다.**
확인된 것은 warm/cold 상태 차이지 그 안의 기전이 아니다.

다만 콜드 구간에서 **Hikari pending이 215까지 갔다**는 것은 확인했다(정상 구간은 0).
p95 4.65초는 커넥션 대기가 동반된 상태였다.

## ⚠️ 측정 중 바로잡은 것 ② — 파드 기동 비용이 창에 섞였다

`increase()` 방식으로 처음 잰 값이 `rate[1m]` 방식보다 60% 높게 나왔다. 파드 수를 보니
구간 내에 6 → 7로 변하고 있었고, **새 파드의 기동 비용이 CPU 증분에 포함**됐다.
같은 실행에서 `pending max 192`도 함께 나왔다(새 파드가 콜드 상태로 커넥션을 물었을 가능성).

워밍업을 **본측정과 같은 도착률**로 바꿔 HPA를 미리 최대로 올리고, 구간 내 파드 수
min·max가 같은지 확인하도록 절차를 고쳤다.

## ⚠️ 측정 중 바로잡은 것 ③ — pending은 순간값이 아니라 구간 최대여야 한다

처음에는 실행 직후 `sum(hikaricp_connections_pending)` **순간값**을 읽고 "pending 0"이라고
적었다. 구간 최대로 다시 보니 **콜드 구간에서 215**였다. 순간값이 0인 것과 구간 내내 0인 것은
다르다. 지금은 `max_over_time(...[구간])`으로 본다.

## 남은 한계

- **절대 성능이 아니다.** 노트북에서 인터넷 경유로 쐈고 판단은 서버 지표로 했다.
- **반복 2회다.** 편차 5~10%를 관측했을 뿐 분포를 안다고 할 수 없다.
- **web 계층 비용의 내부 구성을 모른다**(§판정 ②).
- **캐시 상한은 계산이다.** 위 네 가정 위에 있다.

# 2단계 — 캐시 AS-IS/TO-BE (2026-08-17)

## 결과 (seats 단독 워크로드, 400 rps · 90초)

| | AS-IS (캐시 OFF) | 캐시 ON + tx 밖 | 감소 | 배수 |
|---|---|---|---|---|
| **api CPU** | 2.55 ms/req | **1.56** | 39% | **1.63배** |
| **node CPU** | 5.39 ms/req | **3.89** | 28% | **1.38배** |
| 서버 p95 | 11.1 ms | **4.2** | 62% | |
| 서버 p99 | 24.5 ms | **9.7** | 60% | |
| DB 커넥션/요청 | — | **0.025** | | |

**이론 상한은 1.89배**(이 워크로드에서 api 비용이 0이 된다는 불가능한 가정). 실측 1.38배가
그 아래인 것은 자연스럽다 — 캐시 조회·역직렬화 비용과 web 공통 비용이 남는다.

## 중간 단계에서 발견한 것 — 캐시만으로는 커넥션이 안 줄었다

처음 캐시를 넣었을 때(트랜잭션 안):

```
DB 커넥션 획득 36,173회 / 요청 36,002건  ≈  1.005 회/요청
```

`SeatService`가 클래스 레벨 `@Transactional(readOnly = true)`라, **캐시에서 값을 돌려주더라도
그 전에 프록시가 트랜잭션을 열고 커넥션을 잡았다.** `getSeats`를 `NOT_SUPPORTED`로 빼고
miss일 때만 프록시를 거치게 고친 뒤:

```
0.025 회/요청   ← 40배 감소
```

## 부수 관측

**HPA가 7 → 5~6으로 내려갔다.** 같은 400 rps를 더 적은 파드로 처리한다 — CPU 부담 감소와
정합적인 관측이다.

⚠️ **독립적인 증거는 아니다.** HPA가 CPU 지표를 보고 replica를 정하므로 같은 신호에서 나온다.

**stampede가 수치로 잡혔다.**

```
TTL 2초 × 90초 = 45회 만료
897.6 acquire / 45 ≈ 20회/만료   ← 단순 환산값   ← 만료마다 약 20개 요청이 동시에 miss
```

⚠️ **전체 커넥션 획득을 TTL 만료 횟수로 단순 환산한 값이다.** 최초 fill이나 다른 miss도
섞일 수 있고, burst 크기를 직접 추적한 것은 아니다.

single-flight가 없으니 방향은 예상대로다. 다만 **서버 p99가 9.7ms로 낮아 사용자 체감으로는
드러나지 않았다.**

## ⚠️ 이 결과의 한계

- **③은 1회 측정이다.** AS-IS는 5회 수렴 확인했는데 비대칭이다. 워밍업을 300초로 늘렸고
  AS-IS 값이 0단계 seats 측정(2.57 ms/req)과 일치해 기준선은 신뢰할 만하다.
- **파드 수가 다르다**(AS-IS 7 / TO-BE 5~6). idle을 파드당 상수로 환산해 보정했으나 **가정이다.**
- **중간 단계(캐시 ON + tx 안)의 CPU 수렴값은 유실됐다.** 측정이 겹쳐 오염됐고 코드가 머지돼
  재측정이 불가능하다. 따라서 **"캐시 자체 효과"와 "트랜잭션 경계 제거 효과"를 분리하지
  못한다** — ①→③ 합산만 말할 수 있다.
- **직전 1회는 부하 발생기 쪽 문제로 버렸다**(클라 p95 5.35초 / 서버 27ms, 가용 메모리 2.6GB,
  k6 VU 1,487개까지 증가).

## ⚠️ 이 세션에서 측정을 망칠 뻔한 것들 — 전부 같은 교훈

| 사건 | 증상 | 조치 |
|---|---|---|
| 콜드 스타트(3회) | seats @200이 p95 4.65초 → 재실행 30.9ms(**150배**) | 엔드포인트별 자기 경로 워밍 |
| 파드 수 변동(2회) | `increase()`가 60% 높게 나옴, pending 191 | 구간 내 파드 수 min/max 검증 |
| 측정 동시 실행(1회) | 두 k6가 각 400 rps → p95 20초 | 배경 작업 종료 확인 후 시작 |
| 게이지 순간값 | pending "0"으로 읽음 → 실제 구간 최대 **215** | `max_over_time` |
| 중첩 백그라운드 | 워밍업 k6 유실 → 무한 대기 | 워밍업을 전경 고정 시간으로 |

**한 번은 "seats는 200 rps에서 포화한다"는 틀린 결론 직전까지 갔다.** 재측정하지 않았으면
그대로 계획서에 박혔을 것이다.
