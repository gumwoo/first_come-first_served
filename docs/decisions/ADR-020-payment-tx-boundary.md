# ADR-020 · 결제 승인은 DB 트랜잭션 밖에서 한다

- 상태: **Accepted** (승인 경로 적용 / 환불은 후속, 가상계좌 입금 경로는 범위 밖 — 아래 §범위)
- 날짜: 2026-09-21
- 슬라이스: S05(결제)
- 관련: [[TS-021]](커넥션 풀 상한), [[TS-028]](PG 타임아웃), [[TS-011]](만료 경쟁·보상), [[ADR-011]](정산), [[IMP-008]](결제 멱등)

## 맥락

`payTx`는 하나의 트랜잭션에서 주문 검증 → 결제 행 생성 → **`gateway.approve()`** → 주문·좌석·홀드
확정을 처리했다. 외부 호출이 트랜잭션 안에 있다는 뜻이다.

```
BEGIN
  payments INSERT
  ── PG 승인 요청 ──────── 최대 10초(toss.read-timeout-ms) ────────
  orders / seats / seat_holds / outbox
COMMIT
```

그동안 **Hikari 커넥션을 쥔 채로 기다린다.** 풀은 파드당 5다([[TS-021]]). PG가 느려지면 결제 경로가
커넥션을 다 쓰고, 결제와 무관한 조회까지 커넥션을 얻지 못한다. [[TS-028]]에서 타임아웃을 걸어 상한을
만들었지만, 그 상한 동안 커넥션이 묶이는 것 자체는 그대로였다.

## 결정

승인 경로(`pay`·`confirm`)를 세 구간으로 나눈다.

```
TX1   주문 검증 + READY 결제 행            커밋
(밖)  PG 승인 요청                          커넥션 없음
TX2   결제 APPROVED + 주문 PAID + 좌석 SOLD + 홀드 CONVERTED + 아웃박스
```

1. **READY 행을 먼저 커밋한다.** 승인 직후 프로세스가 죽어도 "시도했다"는 사실이 남는다. 예전에는
   한 트랜잭션이라 롤백되면 결제 행까지 사라져, 미아 승인을 주문 상태로만 추적해야 했다([[ADR-011]]).
2. **보상 취소도 트랜잭션 밖으로 옮긴다.** 좌석이 만료 sweep에 풀려 TX2가 실패하면 PG 승인만 남는다.
   그 취소는 또 다른 외부 호출이라 예전에는 **롤백 직전 트랜잭션 안에서** 불렀다([[TS-011]] §7).
   지금은 TX2가 롤백된 뒤 경계 밖에서 부르고, 결제 행은 FAILED로 남긴다.
3. **동시 중복 요청은 승자의 최종 결과를 기다린다.** 아래 §깨질 뻔한 불변식.
4. **가상계좌 입금 확정은 그대로 둔다.** `confirmVbankDeposit`·`handleVbankDepositWebhook`은
   들어오는 방향이라 트랜잭션 안에 나가는 외부 호출이 없다. 확정 실패 시의 보상만 예전 위치에
   남긴다(`finalizePaidWithVoid`) — 취소 대상이 실제 PG 승인이 아니라 입금 식별자라 얻을 것이 없다.

## 깨질 뻔한 불변식 · 동시 더블클릭

[[IMP-008]]이 보장하는 것은 두 가지다. **부수효과는 한 번만**, 그리고 **모든 호출이 같은 결과를
돌려받는다**(더블클릭한 쪽이 에러나 다른 답을 보면 안 된다).

예전에는 승인까지 한 트랜잭션이라, 패자는 멱등키 UNIQUE 인덱스에서 **승자가 커밋할 때까지
블록**됐다가 최종 상태(APPROVED/FAILED)를 읽었다. 구간을 나누면 패자가 UNIQUE에 걸리는 시점에
승자는 아직 PG 응답을 기다리는 중이고, 그 순간의 결제 행은 **READY**다. 그대로 돌려주면 두 번째
보장이 깨진다.

그래서 패자는 승자의 행이 종료 상태가 될 때까지 짧게 재확인한 뒤 답한다.

- **기다리는 시간 자체는 예전과 같다.** 어차피 승자의 PG 응답까지였다.
- **달라진 것은 기다리는 동안 DB 커넥션을 쥐지 않는다는 점이다.** 이 ADR의 목적과 같은 방향이다.
- 상한(`payment.duplicate-wait-ms`, 기본 5초)을 넘기면 진행 중 상태를 그대로 돌려준다.
  무한 대기보다 낫고, 그 경우 WARN을 남긴다.

## 고려한 대안

- **중복 요청에 "진행 중"을 그대로 돌려준다.** 기다리지 않아 단순하고 정직하다. 대신 [[IMP-008]]의
  두 번째 보장을 포기하고 프론트에 폴링을 넣어야 한다. 더블클릭 한 번에 화면이 "처리 중"으로
  갈라지는 UX 변경이라, **동작을 바꾸지 않는다**는 이 작업의 전제를 넘는다. 폴링 UI를 감수할 수
  있다면 이쪽이 더 깔끔하다 — 그때는 이 ADR을 다시 본다.
- **결제 전체를 비동기 사가로 만든다.** 요청은 접수만 하고 결과는 이벤트로 알린다. 지금 규모에서
  얻는 것보다 바꿀 것이 훨씬 많다(응답 계약·프론트·정산 전부).
- **PG 호출만 별도 스레드로 옮긴다.** 트랜잭션은 그대로 열려 있어 커넥션 점유가 해결되지 않는다.

## 결과 / 한계 (정직)

- **커넥션 점유 감소는 측정하지 않았다.** 구조상 PG 응답 시간만큼 줄어드는 것이 분명하지만,
  이 변경으로 얼마나 줄었는지는 재지 않았다. 재려면 [[IMP-020]]처럼 부하 측정이 필요하다.
- **중복 대기는 톰캣 스레드를 잡는다.** DB 커넥션은 놓지만 스레드는 기다린다. 예전과 같은 시간이라
  나빠지지는 않았어도, "기다림이 사라졌다"고 말할 수는 없다.
- **환불은 아직 한 트랜잭션이다.** `refundTx`에도 같은 문제가 있다. [[TS-030]]의 동시 환불 불변식과
  얽혀 있어 별도로 본다.
- **새 중간 상태가 생겼다.** READY 결제 행이 커밋된 뒤 승인 전에 크래시하면 그 행이 READY로 남는다.
  주문은 PENDING이라 만료 sweep이 정리하고, PG에 승인이 남았다면 정산이 회수한다([[ADR-011]]).
  다만 **READY 행 자체를 청소하는 잡은 없다** — 가상계좌 대기와 같은 상태라 구분해 지워야 한다.
- **로컬에서 통합테스트를 돌리지 못했다.** Docker가 없어 동시성·보상 경로는 CI 결과로 판단한다.
