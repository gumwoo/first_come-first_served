# TS-029 · 오래된 커밋이 최신 배포를 덮을 수 있었다 — concurrency는 그걸 막지 못한다

- 슬라이스: 전반(CI/CD) — 발견은 2026-08-13 리뷰
- 날짜: 2026-08-16
- 유형: 배포 정확성 — **동시성 제어와 순서 보장을 혼동하기 쉬운 자리**
- 관련: ADR-009(GitOps), [[TS-022]](ArgoCD 도입 사건)
- 상태: **해결** — concurrency를 CI/배포에 다르게 걸고, bump-tag에 **main 포함 검사(⓪) + 4-상태 조상 가드**를 넣었다

## 0. 무엇이 문제였나

`image.yml`의 `bump-tag`는 이렇게 동작한다.

```
ref: main 으로 체크아웃  →  자기가 빌드한 SHA를 overlay의 newTag 값으로 씀  →  push
```

**빌드한 코드의 SHA와, 태그를 얹는 브랜치가 분리돼 있다.** 그래서 오래된 커밋 A의 빌드가
새 커밋 B보다 **늦게 끝나면 A가 B의 태그를 덮는다.** ArgoCD는 그 태그를 진실로 보고 동기화하므로,
**최신 코드가 배포됐다가 구버전으로 되돌아간다.**

두 워크플로 어디에도 `concurrency`가 없어서 겹칠 창이 상시 열려 있었다.

⚠️ **이 역전이 실제로 발생한 기록은 찾지 않았다.** 워크플로 구조로 확인한 것이다.

## 1. concurrency로는 못 막는다 — 이 구분이 이 문서의 핵심

처음에는 `concurrency` 하나로 해결된다고 적으려 했다. **틀렸다.**

GitHub은 같은 concurrency group의 **실행 순서를 보장하지 않는다고 명시**한다. concurrency가
주는 것은 두 가지뿐이다.

| concurrency가 하는 일 | concurrency가 **안 하는** 일 |
|---|---|
| 같은 그룹이 동시에 돌지 않게 한다 | 실행 **순서**를 보장한다 |
| 대기 중인 것 중 최신만 남긴다(오래된 pending 취소) | "내 SHA가 이미 배포된 것보다 오래됐는지" 판별한다 |

**동시 실행 창을 줄이는 것과, 역전을 판별하는 것은 다른 문제다.** 전자는 확률을 낮추고
후자는 조건을 검사한다. 하나가 다른 하나를 대신하지 못한다.

## 2. 조치 ① — concurrency를 CI와 배포에 **다르게** 건다

```yaml
# ci.yml — 새 커밋이 오면 이전 CI는 의미가 없다
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

# image.yml — 배포는 중간에 죽이면 안 된다
concurrency:
  group: image-${{ github.ref }}
  cancel-in-progress: false
```

**배포에 `cancel-in-progress: true`를 쓰면 안 된다.** 진행 중인 배포를 죽이면
**이미지는 ECR에 올라갔는데 태그 커밋은 안 된** 중간 상태가 남는다. `false`면 실행 중인 것은
끝까지 가고, 대기 중인 것 중에서는 가장 최신만 살아남는다.

같은 키워드를 쓰지만 **목적이 반대**라서 값도 반대다 — CI는 낭비를 줄이는 것이고,
배포는 중단을 막는 것이다.

## 3. 조치 ② — main 포함 검사(⓪) + 4-상태 조상 가드

역전을 실제로 막는 것은 이쪽이다. `bump-tag`가 쓰기 전에 조상 관계를 본다.

```
① SHA == 현재 태그        → 같은 버전, 갱신 불필요
② SHA가 현재 태그의 조상   → 내가 stale, 덮지 않는다
③ 현재 태그가 SHA의 조상   → 내가 최신, 갱신한다
④ 둘 다 아님(무관계)      → 실패시킨다
```

### ⓪ main 히스토리 포함 검사 — 4상태보다 먼저

**초안에는 이게 없었고, 그래서 ③이 구멍이었다.**

초안은 "`workflow_dispatch`가 다른 브랜치에서 돌면 무관계(④)라 막힌다"고 봤다.
**그 예가 드문 형태였다.** 실제 feature 브랜치는 대부분 **최신 main에서 딴다.**

```
main:    A ── B ── C        (태그 = C)
feature:           └── X    ← C의 조상이 아니라 후손
```

`git merge-base --is-ancestor C X` → **참**. 그러면 **"③ 내가 최신 → 갱신"** 으로 판정돼
**머지되지도 않은 커밋이 main 배포 태그가 된다.** ④보다 흔하고 위험하다.

리뷰에서 잡혔고, git 시뮬레이션으로 재현했다(아래 §4). 그래서 4상태 **앞에** 검사를 하나 둔다.

```bash
if ! git merge-base --is-ancestor "$SHA" "$MAIN"; then
  echo "::error::⓪ 빌드 SHA가 main 히스토리에 없다"; exit 1
fi
```

**방어는 두 겹이다.** `guard` 잡에서 `workflow_dispatch`의 ref를 main으로 제한해 **ECR 빌드
비용조차 쓰지 않게** 먼저 끊고, `bump-tag`에서 히스토리 포함을 다시 본다. 트리거 설정이
나중에 바뀌어도 뒤쪽 검사가 남는다.

### ④를 조용히 통과시키지 않는 것이 핵심이다

초안은 한 줄이었다.

```bash
git merge-base --is-ancestor "$SHA" "$CURRENT_TAG_SHA" && exit 0
```

②만 본다. **④에서는 조건이 거짓이라 그냥 통과해 덮어버린다** — 가장 위험한 경우에 가드가
아무 일도 하지 않는다. 리뷰에서 잡혔다.

④도 실재한다. `image.yml`의 트리거를 보면

```yaml
on:
  workflow_run:
    workflows: ["CI"]
    branches: [main]     # ← 여기는 선형
  workflow_dispatch:      # ← 여기는 아무 브랜치에서나
```

`workflow_dispatch`는 **아무 브랜치에서나 실행할 수 있다.** main과 무관계한 SHA가 들어오면
정확히 ④다.

```
main:    A ── B ── C        (현재 태그 = C)
feature:      └── Y         (오래된 A에서 분기 → C와 무관계)
```

⚠️ **다만 이건 드문 형태다.** 흔한 것은 위 ⓪에서 다룬 "최신 main에서 딴 X"이고,
그건 ④가 아니라 ③으로 들어간다. **초안이 이 드문 예를 근거로 일반화한 것이 오류였다.**

배포에서 **"예상 밖인데 일단 진행"은 가장 나쁜 기본값**이라 실패로 둔다.

### 전제 — 조상 검사에는 히스토리가 필요하다

`actions/checkout`의 기본 `fetch-depth`는 1이라 `merge-base`가 객체를 못 찾는다.
`fetch-depth: 0`으로 바꿨다. 두 커밋이 로컬에 없으면 **판정 불가이므로 멈춘다**
(없는 것을 "관계없음"으로 처리하면 ④를 잘못 만든다).

## 4. 검증 — CI 없이 확인했다

가드 로직을 실제 git 저장소로 시뮬레이션했다. 워크플로를 돌려야만 알 수 있는 것이 아니다.

```
main:    A ── B ── C
feature:           └── X   (C에서 분기 = 흔한 형태)
old:          └── Y        (A에서 분기 = 무관계)

SHA=C 태그=C : ① 같은 버전 → skip
SHA=A 태그=C : ② stale    → skip
SHA=C 태그=A : ③ 최신     → update
SHA=X 태그=C : ⓪ main 미포함 → exit 1   ← 초안에서는 ③으로 통과하던 구멍
SHA=Y 태그=C : ⓪ main 미포함 → exit 1
```

**초안을 같은 데이터로 돌려 구멍을 먼저 재현한 뒤 고쳤다.** 초안에서 `SHA=X`는
`③ 최신 → proceed=true`가 나왔다 — 즉 배포가 진행됐을 것이다.

⚠️ **워크플로 자체는 아직 실전에서 안 돌았다.** 확인한 것은 셸 판정 로직이고, GitHub
Actions 위에서의 동작(`fetch-depth: 0`이 실제로 타 브랜치 커밋을 가져오는지 등)은
다음 배포에서 확인된다.

## 5. 남은 것

- **푸시 재시도 구간.** `git pull --rebase` 후 다른 워크플로가 더 새 태그를 썼다면 같은 줄이
  바뀌어 **리베이스가 충돌하고 실패한다** — 조용히 덮이지는 않는다(이중 방어). 다만
  그 경로를 시뮬레이션하지는 않았다.
- **`workflow_dispatch`의 남은 구멍.** 리뷰가 함께 지적한 *"정상 CI 성공 증거 없이 배포 흐름에
  진입할 수 있다"*는 여전히 남는다. main으로 제한했으므로 **아무 브랜치나 배포되는 문제는
  닫혔지만**, main에서 CI 실패 상태로 dispatch하는 경로는 그대로다.
- CI 시간 단축(테스트 컨테이너 공유 등)은 **별도 작업**이다. 이 PR은 정확성만 다룬다 —
  섞으면 AS-IS/TO-BE 측정이 오염된다.

## 6. 배운 점

**"동시에 못 돌게 한다"와 "순서를 지킨다"는 다른 보장이다.** 이름이 `concurrency`라서 후자까지
해줄 것 같지만, 공식 문서가 명시적으로 아니라고 말한다. 도구가 주는 보장을 **문서로 확인하고
그 범위 안에서만 주장해야 한다** — 이 저장소가 [[TS-022]]에서
`RespectIgnoreDifferences=true`로 이미 겪은 종류의 일이다(옵션 이름이 약속하는 것과 실제
동작이 달랐다).

그리고 가드를 쓸 때는 **"조건이 참일 때 막는다"가 아니라 "가능한 상태를 전부 나열하고 각각을
어떻게 처리할지 정한다"** 로 접근해야 한다. 초안이 ②만 보고 ④를 흘려보낸 것은 상태를
나열하지 않고 조건 하나를 떠올렸기 때문이다.

**그런데 상태를 넷으로 나열하고도 뚫렸다.** ④를 추가할 때 든 예가 "오래된 커밋에서 딴 브랜치"
였는데, **흔한 경우는 최신 main에서 딴 브랜치**라 ③으로 들어간다. 나열이 부족했던 게 아니라
**예가 대표적이지 않았다.**

> 반례를 하나 떠올려 규칙을 만들면, 그 반례의 모양에 규칙이 맞춰진다.
> **가장 흔한 경우를 먼저 그려 보고 그것이 어느 상태로 떨어지는지 확인해야 한다.**
