# TS-042 · 진입 창이 분 경계(:00)를 지나면 9개 api가 함께 느려진다 — Redis가 매 분 :00에 멈춘다(원인 미확정)

- 슬라이스: S10(부하·확장) — 통합 판정 run 워밍업(pf-warm)에서 발견
- 날짜: 2026-10-08
- 유형: 공유 의존(Redis)의 주기적 정지 — 원인 미확정, 시험 설계로 우회하고 한계로 기록
- 관련: [[IMP-029]], [[IMP-031]], [[ADR-025]], ElastiCache `cache.t4g.micro`(단일 스레드)
- 상태: **원인 미확정 · 한계로 기록** — 판정 run은 진입 창이 분 경계를 지나지 않게 T0를 :10~:45초에 두었다(사용자 결정). 클러스터 철거로 후속 확인은 하지 않는다.

## 1. 증상 (실측 — ALB access log `request_creation_time`)
pf-warm(T0 = 2026-10-07T16:09:54Z, 진입 10,000/s × 10초)의 창 [T0, T0+10s) 도착이 **90,644건**(기준 ≥ 100,000)이었다.

| 초(UTC) | 진입 도착 | 대상 처리 최대 | 비고 |
|---|---|---|---|
| 16:09:54 ~ :59 | 10,178 ~ 10,202 | 0.053 ~ 0.105s | 정상 |
| 16:10:00 | 9,906 | 1.491s | 1초 넘는 응답 562건 |
| 16:10:01 | 5,412 | 1.405s | 발생기 VU가 느린 응답에 묶여 도착이 줄었다(dropped 5,476) |
| 16:10:02 | 6,152 | 0.697s | |
| 16:10:03 | 8,006 | 62.5s | **504 250건**(대상 처리 시간 −1 — ALB 유휴 시간 초과 60초) |

- 느려짐은 **16:10:00.0부터** 시작했고, 100ms 단위로 보면 9개 api 대상이 같은 100ms 안에서 함께 1.4초대로 늘었다 — 한 파드가 아니라 공유 의존을 가리킨다.
- ALB → api 연결 수(`tomcat_connections`)가 파드당 약 7 → **약 1,000**으로 늘었다(v3 판정 run은 약 20). 느려진 결과로 ALB가 연결을 더 연 것으로 본다(추론).
- api 로그에 같은 시각 WARN·ERROR 없음, GC 정지 0, hikari pending 0, RDS·Redis 1분 지표(CPU·크레딧·메모리·스왑 변화) 이상 없음.

## 2. 조사
1. **분 경계에 맞춘 정지인가** — 이전 측정의 ALB 로그를 같은 방식으로 다시 봤다(실측).
   - 1차 f2-r1(창 04:32:54~:33:04): 04:33:00.0에 평균 지연 0.004 → **0.18s**, 약 2초 뒤 회복.
   - 1차 f2-r2(창 04:48:53~:49:03): 04:49:00.1에 0.003 → **0.28s**.
   - 2차 f3-r3(창 07:25:56~:26:06): 07:26:00~:01에 평균 0.15s(최대 0.36s), 도착은 유지.
   - 3차 v3 판정 3회(f4-r1~r3)는 창이 분 경계를 **지나지 않았다**(08:28:21·08:44:37·09:01:12 시작) — IMP-029 6축 충족은 이 조건에서의 결과다.
2. **Redis가 멈추는가** — `SLOWLOG GET`(128개 보존 — pf-warm T0 부근은 이미 밀려났다): 16:21~16:34의 매 분 :00(과 16:30:30)에
   `HGET`·`ZCARD`·`EXISTS` 같은 O(1) 명령 실행 시간 **10~30ms**. O(1) 명령이 그만큼 걸린 것은 명령 자체가 아니라 Redis 프로세스가 멈춘 것으로 본다(추론).
3. **부하 없이도 멈추는가** — 클러스터 안 임시 파드에서 `redis-cli --latency-history -i 1` 150초(실측, `redis-idle-latency.txt`):
   평소 1초 창 최대 1~2ms, **분 경계 부근 창만 35ms·14ms**(출력 버퍼링 때문에 창 시각은 시작 시각 + 창 번호로 맞춘 근사).
4. **진입이 아닌 부하에서도 보이는가** — pf-r1 폭증(상태 조회 약 10,000/s, api 9개 — 확장이 끝난 20:41:30 이후)의 ALB 상태 조회를 10초 단위로 묶으면(실측),
   :00이 든 10초 구간만 대상 처리 최대가 0.167·0.185·0.350·0.648·0.214s(20:42~20:46), 나머지 구간은 0.015~0.028s였다.
5. Redis 노드 상태(CloudWatch, 실측): `cache.t4g.micro`, `SwapUsage` 약 171MB(2026-10-06 18시 KST께 94MB → 141MB로 늘어 그 뒤 유지 — v3 판정 run 때도 같은 수준),
   `CPUCreditBalance` 288(최대), `Evictions` 0, `SaveInProgress` 0.

## 3. 근본 원인 — **미확정**
- 확인한 것: Redis 명령 실행이 매 분 :00 무렵 수~수십 ms 멈춘다(slowlog·유휴 PING 실측). 진입 10,000/s 부하에서 그 순간 9개 api가 함께 느려진다(ALB 실측, 4개 run).
- 추측(확인 못 함): 0.5GiB 노드의 스왑(171MB) 상태에서 ElastiCache 쪽 분 단위 작업(지표 수집 등)이 페이지 폴트·CPU 경합을 일으킨다. 앱 쪽 분 정렬 작업은 없다
  (`@Scheduled`는 모두 fixedRate — 파드 기동 시각 기준이라 9개 파드가 같은 :00에 맞춰지지 않는다. cron은 03:00·04:00뿐).
- 미확정: 같은 수십 ms 정지가 왜 pf-warm에서만 4초 붕괴·60초 매달림으로 번졌는지(f2·f3에서는 2초 안에 회복).
- 확정하려면: 스왑 없는 큰 노드 타입에서 같은 유휴 측정·같은 진입을 분 경계에 걸쳐 재는 것 — 사용자 결정으로 이번에는 하지 않는다(시간·비용, 측정 대상 구성 변경, 철거 예정).

## 4. 조치
- 통합 판정 run(pf-r1~r3)은 진입 창 [T0, T0+10s)이 :00을 지나지 않게 T0 초를 :10~:45에 두었다(사전 등록 변경 기록 5, 결과 보기 전).
- 이것은 **시험 설계로 피한 것**이지 고친 것이 아니다. 실제 오픈 시각은 보통 정각(:00)이라 운영에서는 정확히 이 순간에 몰린다 — 실서비스라면 우선 확인할 위험이다.

## 5. 재발 방지 · 남는 일
- 판정 창 선택 규칙: 공유 의존의 주기적 정지가 확인되면 창 배치를 사전 등록에 적고, 결과 표현에 "분 경계 밖 창"을 붙인다([[IMP-031]]).
- [[IMP-029]] §8에 단서 추가: 6축 충족은 분 경계를 지나지 않는 창에서의 결과이며, 분 경계를 지난 이전 run은 지연이 0.15~0.28s 튀었다.
- 후속(이번 범위 밖): Redis 노드 타입 상향 후 유휴·부하 분 경계 재측정, ElastiCache `latency-monitor-threshold`로 정지 원인 이벤트 수집.
