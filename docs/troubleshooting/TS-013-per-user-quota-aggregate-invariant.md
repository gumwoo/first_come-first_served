# TS-013 · 1인 구매 한도가 뚫림 — 조건부 UPDATE로는 못 지키는 불변식(집계)

- 슬라이스: S04(좌석) — 발견 경로: 설계 문답
- 날짜: 2026-08-06
- 유형: 정합성 결함(코드) — **비즈니스 규칙 위반**(초과판매는 아님)
- 상태: 해결
- 관련: [[ADR-003]](재고 원자성 — 조건부 UPDATE), [[ADR-006]](주문 상태 전이),
  [[TS-011]](만료 sweep 무가드 UPDATE)

## 1. 상황

"좌석을 조건부 UPDATE로 지킨다면 왜 Redis 분산락을 안 쓰나"라는 질문에 답하다가,
**그 방어가 닿지 않는 자리**를 확인하게 됐다.

```
좌석 4개가 한도인데, 3개 이미 산 상황에서 동시 요청이 오면?
```

## 2. 문제 정의 + 분류

**조건부 UPDATE가 지키는 것은 "단일 행의 상태"다.**

```sql
UPDATE seats SET status='HELD' WHERE id=? AND status='AVAILABLE'
```

이 문장은 **좌석 하나를 두 사람이 가져가는 것**을 막는다. 그런데 1인 한도는
**"이 사용자가 이 공연에서 가진 좌석의 합계"** 라는 집계 규칙이라, **지킬 행이 없다.**

| 불변식 | 표현되는 곳 | 조건부 UPDATE로 되나 |
|---|---|---|
| 초과판매 방지 | 좌석 행 1개의 status | ✅ |
| **1인 한도** | **현재 모델의 어느 행에도 없음(집계)** | ❌ |

> **"조건부 UPDATE를 쓰니 안전하다"가 통하는 것은 불변식이 단일 행에 표현될 때뿐이다.**

## 3. 증상 — 결함이 둘이었다

### ① 세는 대상이 틀렸다 (동시성 없이도 재현)

```java
findIdsByUser(userId, eventId, SeatHoldStatus.HELD)   // HELD 홀드만 센다
```

결제가 확정되면 홀드는 `CONVERTED`가 되어 **한도 계산에서 빠진다.**

```
4매 선점 → 결제 → 홀드 CONVERTED → 한도 계산 0
→ 또 4매 → 결제 → ...  무한 반복
```

설정에는 `# 이벤트당 1인 구매 한도`라고 적혀 있는데, **실제로는 "동시 선점 한도"만
구현돼 있었다.** 의도와 구현이 어긋난 상태였고, 사용자에게 확인해 **총 구매 한도가 맞다**는
답을 받았다.

### ② 검사와 행위 사이가 벌어져 있었다 (레이스)

```java
long current = ...;                              // 읽기
if (current + seatIds.size() > maxPerUser) ...;  // 검사
int held = seatRepository.holdIfAvailable(...);  // 행위   ← 사이에 끼어들 수 있다
```

```
T1: current=3, 1매 요청 → 3+1=4 ≤ 4  통과
T2: current=3, 1매 요청 → 3+1=4 ≤ 4  통과   ← T1 커밋 전이라 못 본다
결과: 5매
```

**격리 수준을 올려도 안 막힌다.** 막아야 할 것이 "아직 존재하지 않는 홀드의 추가 생성"이라
`REPEATABLE READ`로도 **팬텀**이 남는다. `SERIALIZABLE`이라야 잡히지만 재시도 비용이 크다.

**행 락도 답이 아니었다 — 다만 "원리적으로 불가능"해서가 아니다.** 현재 데이터 모델에
`(사용자, 공연)` 한도를 대표하는 **고정 행이 없어서** 잠글 대상이 없을 뿐이다. 쿼터 행을
따로 두면 `FOR UPDATE`나 조건부 UPDATE가 가능하다 — 그 선택지를 왜 버렸는지는 §5-㉣.

## 4. 검증 (실패를 먼저 재현)

고치기 전에 테스트 **9건**을 먼저 올려 CI에서 돌렸다.

```
결제완료_4매_뒤에는_더_선점할_수_없다        FAILED   ← ①
한도직전에_동시요청이_오면_하나만_성공한다   FAILED   ← ②
나머지 7건 통과
  ├─ 비결정적으로 통과한 경합 테스트 1건 (결제전환과_추가선점이_겹쳐도)
  └─ 회귀 가드 6건
```

**`결제전환과_추가선점이_겹쳐도`는 통과해 버렸다.** 읽기 스큐를 노린 테스트인데
타이밍이 맞지 않아 재현되지 않았다 — 이 1건을 "회귀 가드"로 세면 안 된다.

수정과 리뷰 보강을 거친 **최종 구성은 10건**이다.

| 분류 | 건수 | 목록 |
|---|---|---|
| **결함 탐지용**(타이밍 의존, 회귀 보장 안 됨) | 2 | 한도 직전 경합 · 결제 전환 경합 |
| **결정적 회귀 가드** | 8 | advisory lock 대기 · PAID 한도 · VBANK+HELD · 이중 계산 방지 · 환불 복구 · 수동 해제 복구 · 홀드 만료 복구 · 주문만 만료 시 유지 |

## 5. 해결

### ㉠ 세는 대상 — 점유의 진실원 두 곳

```
결제 전 점유 → seat_holds.status = 'HELD'
결제 후 점유 → orders.status     = 'PAID'
```

**주문의 중간 상태(`PENDING`·`VBANK_WAITING`)는 세지 않는다.** 처음에는 "보수적으로 안전하다"고
보고 포함하려 했는데, 리뷰에서 **과잉 차단**이라는 지적을 받고 코드로 확인하니 맞았다:

- `SeatService.release()`는 홀드만 `RELEASED`로 바꾸고 **주문(PENDING)은 그대로 둔다.**
  → 좌석은 이미 반납했는데 주문이 한도를 잡아 주문 만료까지 못 사게 된다.
- 홀드가 `EXPIRED`면 `convertHold`(HELD 조건부)가 0행이라 **그 주문은 영영 `PAID`가 될 수 없다.**
  좌석을 확보하지도 못하는 주문이 한도만 먹는다.

좌석을 점유 중이라면 **이미 `HELD` 홀드로 잡히므로** 주문 상태를 따로 셀 이유가 없었다.

### ㉡ 반드시 단일 SQL — 읽기 스큐

두 문장으로 나누면 `READ COMMITTED`에서 **문장마다 스냅샷이 다르다.**

```
Q1(PAID) → 결제 전 스냅샷 → 0
   [결제 커밋: Order→PAID, SeatHold→CONVERTED]
Q2(HELD) → 결제 후 스냅샷 → 0
합계 0.  실제는 4.
```

한 문장이면 **결제 전(0+4) 또는 결제 후(4+0)** 중 하나만 보므로 항상 4다.

### ㉢ UNION — 이중 계산

주문 생성 후에는 같은 좌석이 `order_items`와 `seat_hold_items` **양쪽에** 있다.
단순 합산하면 4매가 8매가 되어 **정상 사용자를 막는다.** `UNION`이 중복을 제거하므로
바깥 `DISTINCT`는 불필요하다(`UNION ALL`이면 필요).

```sql
select count(*) from (
    select oi.seat_id from orders o join order_items oi on oi.order_id = o.id
     where o.user_id = :u and o.event_id = :e and o.status = 'PAID'
    union
    select hi.seat_id from seat_holds h join seat_hold_items hi on hi.hold_id = h.id
     where h.user_id = :u and h.event_id = :e and h.status = 'HELD'
) active_seats
```

### ㉣ 직렬화 — `pg_advisory_xact_lock`

```java
quotaRepository.acquireQuotaLock(quotaLockKey(userId), quotaLockKey(eventId));
```

- **왜 행 락이 아닌가**: 현재 모델에 한도를 대표하는 **고정 행이 없다.** 기존 홀드 행을 잠가도
  새 홀드 삽입은 막지 못한다(팬텀).
  **쿼터 행을 만들었다면 `FOR UPDATE`가 답이 될 수 있었다** — 실제로 검토했고 기각했다.
  비정규화 카운터를 해제·만료·환불 경로마다 정확히 줄여야 하는데, **이 프로젝트에서 반복해서
  깨진 곳이 정확히 그 경로들**이다(TS-007 → TS-010 → TS-011, 같은 유형이 세 번). 파생 상태를
  늘리지 않고 원본에서 세는 쪽이 안전하다고 판단했다.
- **왜 Redis 분산락이 아닌가**: 리스 만료와 트랜잭션 수명이 따로 놀아 **만료 후 소유자가
  둘이 될 수 있다.** advisory lock은 **데이터와 같은 시스템**에서 잡히고 커밋·롤백과 함께 풀린다.
- **왜 `xact` 변형인가**: 세션 범위 락은 커넥션이 락을 쥔 채 풀에 반납되어 **다음 요청이
  물려받는다.** 트랜잭션 범위는 그 문제가 원천적으로 없다.
- **왜 `hold()`에만 거는가**: 좌석 총량을 늘리는 진입점이 거기 하나다. 결제는 표현 위치만
  옮기고(HELD→PAID), 환불·해제·만료는 수를 **줄인다** — 스테일하게 읽혀도 보수적(더 막는 쪽)이라
  안전하다. 주문 생성이 홀드 항목 외의 좌석을 추가하지 않는다는 것도 확인했다.
- **키 변환**: 2인자형이 `int4`라 `Math.toIntExact`로 넘긴다. 조용히 잘리는 대신 즉시 실패한다 —
  키가 겹쳐 생기는 불필요한 대기는 정합성 문제가 아니라 **더 찾기 어렵기** 때문이다.

## 6. 재발 방지

- **"집계 불변식"이라는 유형을 문서로 남긴다.** 조건부 UPDATE는 단일 행에만 통한다.
  같은 패턴(읽고 → 검사 → 행위)이 다른 곳에도 있을 수 있다 — 대기열 1인1토큰, 주문 생성 한도 등.
- **하네스로는 못 잡는다.** "이 검사가 집계 기반인가"는 정적으로 판별하기 어렵다.
  기존 `harness:allow-unguarded-status` 규칙은 **단일 행 상태 전이**를 대상으로 하며
  이 유형에는 닿지 않는다 — 하네스의 적용 한계를 보여주는 사례다.
- **테스트를 먼저 실패시키고 고쳤다.** ①은 지금 코드에서 그냥 통과해 버리는 종류라,
  실패를 재현하지 않았으면 "고쳤다"고 말할 근거가 없었다.

## 7. 한계 (정직)

- **경합 테스트 2건은 회귀 가드가 아니다.** 시작 래치는 두 스레드를 같이 출발시킬 뿐이라,
  T1이 커밋까지 끝낸 뒤 T2가 읽으면 **결함이 남아 있어도 통과한다.** 수정 전 CI에서 한 번
  결함을 잡았지만 앞으로도 잡는다는 보장이 없다. 회귀는 **advisory lock이 실제로 대기시키는지**를
  직접 확인하는 결정적 테스트가 지킨다(다른 트랜잭션이 같은 키를 쥔 동안 `hold()`가 완료되지
  않고, 락 해제 후에만 진행되는지).
- **테스트 자체에 거짓 통과 구멍이 있었고, 리뷰에서 드러났다.**
  - 동시 실행 헬퍼가 **모든 예외를 삼켰다**(기존 테스트의 패턴을 검토 없이 복사). 쿼리가 깨져
    양쪽 다 오류로 끝나도 "성공 0건"이 되어 통과한다 → 기대하는 `MAX_PER_USER_EXCEEDED`만
    정상 실패로 인정하고 나머지는 노출한다.
  - 결제 전환 테스트가 **결제 성공을 확인하지 않았다.** 좌석 수 검증이 `HELD`와 `SOLD`를 함께
    세어 **결제가 조용히 실패해도 같은 값**이 나온다 → 주문 `PAID`·홀드 `CONVERTED`·좌석 `SOLD`를
    별도로 단언한다.
  - 별도 스레드의 예외가 밖으로 나오지 않아 실패 원인이 보이지 않았다 → `AtomicReference`로 전달.

  > **"CI가 초록이다"가 "코드가 옳다"를 뜻하지 않는 경우들이었다.** 이 프로젝트에서 반복되는
  > 주제다 — `terraform validate` 통과 후 apply에서 터진 결함 4건(ADR-013), 주석이 가리키는
  > 대상이 없던 TS-012와 같은 계열이다.
- **advisory lock은 PostgreSQL 전용이다.** 다른 DB로 옮기면 재설계해야 한다.
- **id가 int4 범위를 넘으면 즉시 실패한다.** 지금은 시퀀스 값이 작아 문제없지만 영구 전제는 아니다.
- **`hold()` 트랜잭션 동안 그 사용자의 다른 선점 요청이 대기한다.** 사용자 단위라 다른
  사용자에게는 영향이 없지만, 이 트랜잭션이 느려지면 그 사용자만 느려진다.
- **부하 상황에서의 락 대기는 측정하지 않았다.** S10 부하테스트에서 확인할 항목이다.
- **별건**: `SeatService.hold()`와 `SeatHoldExpiryService`가 **커밋 전에 SSE를 발송**한다.
  롤백되면 "선점됐다"고 알려놓고 실제로는 안 된 상태가 된다. 이번 수정과 무관한 기존 결함이라
  분리한다(`afterCommit`으로 옮기는 것이 정석).
