# IMP-048 · 예매 api CPU requests를 낮춰 평시 노드를 5 → 3대로 줄일 수 있는가: 평시 조회 CPU 실측(로컬) + 배치 시뮬레이션(kwok)

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-26(로컬 실험실 `infra/triage-lab`, 측정 결과 `artifacts/requests/`·시뮬레이션 `artifacts/loadtest/kwok-20261020/`는 레포 밖)
- 유형: 로컬 실측 + 시뮬레이션. 클러스터에서 재지 않았다.
- 관련: [[ADR-025]](1100m 근거 보충), [[ADR-026]](B1), [[IMP-047]](대기열의 api 회피 규칙), [[IMP-038]](동거 경합), `docs/testing/traffic-profile.md`
- 벤치 파일: 레포 밖 `artifacts/requests/`(사전 등록 `prereg-local.md`, 부하 `browse.js`, run별 k6 요약·cgroup CPU·디스크 프로브, 기록 `runs*.txt`), `artifacts/loadtest/kwok-20261020/`(사전 등록 `prereg-PB.md`, 시뮬레이터 `sim-pb.mjs`, 시나리오 `scen-PB/`, 결과 `out-PB/`)

## 1. 상황 (Context)
운영 기본값 B에서 폭증은 대기열 Deployment가 받고, 예매 api는 입장 정원 단위의 예매 묶음과 평시 조회를 받으며 3개로 고정이다. 예매 api의 requests 1100m는 대기열과 같은 사양으로 남은 값이라 예매 부하 기준의 근거가 없었다([[ADR-025]] 보충).
평시 노드 5대는 api 3개와 대기열 2개가 각자 노드를 차지해서 생긴다. 예매 api requests를 낮추고 대기열의 api 회피 규칙을 "가능하면 분리"로 완화하면 평시에 api와 대기열이 한 노드에 같이 들어가 3대로 줄 수 있는지 확인했다.

## 2. 문제 정의 + 분류
- 계층: 자원 예약(requests)과 배치 규칙.
- 질문 1(로컬): 가정 평시 부하에서 예매 api Pod 하나가 쓰는 CPU는 얼마이고, requests 후보는 무엇인가.
- 질문 2(시뮬레이션): 그 후보와 완화한 규칙으로 평시 3대·사전 확장 9대 이하·피크 동거 0을 동시에 만족하는가.

## 3. 측정 방법
### 3.1 평시 조회 CPU (로컬)
- 사전 등록 `prereg-local.md`(2026-10-26 17:03:48). 보충 17:24:25(유효 조건), 보충 2 17:48:05(Pod당 33 req/s로 변경, m11 시작 17:48:29 전), 판정 17:57:11.
- 실험실 api 컨테이너(코어 2개 고정, 풀 5)에 k6 constant-arrival-rate로 평시 혼합 조회를 걸었다. 화면 가중 메인 25%·상세 40%·검색 20%·내 예매 15%를 요청 단위로 펼쳤다(프로파일의 화면당 약 2회).
- api 컨테이너 cgroup `cpu.stat`을 1초마다 읽어 CPU를 계산했다. 판정 중 디스크 프로브를 함께 돌렸다.
- 유효 조건: 판정 중 디스크 프로브 중앙값 10ms 이하, 버려진 요청 0.1% 이하. 이 조건은 첫 두 run을 본 뒤 더했다.
- 부하 크기: 처음에는 컨테이너 하나에 100 req/s를 걸었다. 평시 100 req/s는 예매 api 3개 전체의 부하라 Pod 하나가 받는 부하는 약 33 req/s다. 이를 사전 등록 보충에 적고 33 req/s로 다시 쟀다.
- 후보 규칙(사전 등록): 400m / 600m / 800m 중 "평시 조회 1초 p90"과 "평시 조회 평균 + 예매 묶음 분석 구간 평균 최댓값 0.31코어([[IMP-045]] 2차 평가 정상 run)" 중 큰 값 이상인 가장 작은 후보.

### 3.2 배치 시뮬레이션 (kwok)
- 사전 등록 `prereg-PB.md`(2026-10-26 17:57:26). 도구는 [[IMP-037]]과 같은 입력(실제 클러스터 스냅샷, 실제 kube-scheduler)에 B 구성을 반영해 넓혔다(`sim-pb.mjs`).
- 예매 api 3 고정, web 2, 대기열 평시 2 → 사전 확장 6, 대기열 requests 1100m.
- 시나리오: 지금(1100m·필수 회피), 예매 api 800m(판정)·600m·400m(민감도) × "가능하면 분리"(preferred) × 사전 확장 때 빈 노드 확보(우선순위 -5 pause Pod를 대기열이 늘어날 수만큼 먼저 띄움) 없음/있음.
- 판정: 평시 노드 3대, 사전 확장 노드 9대 이하·Pending 0, 사전 확장 뒤 api·대기열 동거 0.

## 4. 결과
### 4.1 평시 조회 CPU (로컬 실측)
Pod 하나 33 req/s, 유효 3회:

| run | 처리량 | p95 | CPU 평균 | 1초 p50 | 1초 p90 | 1초 최대 |
|---|---|---|---|---|---|---|
| m11 | 33.0/s | 4.9ms | 0.086 | 0.075 | 0.139 | 0.347 |
| m12 | 33.0/s | 3.1ms | 0.072 | 0.046 | 0.081 | 0.633 |
| m13 | 33.0/s | 756ms | 0.391 | 0.090 | 1.438 | 2.064 |

- m13은 유효 조건 안이었지만 08:54:41Z부터 약 30초 동안 api CPU가 코어 2개 가까이 오르고 p95가 756ms였다. 같은 시각 디스크 프로브가 200~2,100ms로 올랐다(500ms 초과 26회, m11 0회·m12 3회).
  인과는 확인하지 못했다(추론). 디스크 정체가 길어지면 프로브 표본이 덜 쌓여, 중앙값 조건은 이런 짧은 정체를 걸러내지 못한다.
- 후보 판정: 사전 등록이 run 사이 묶는 방법을 정하지 않아, 결과를 본 뒤 보수적인 쪽으로 정했다. 세 run의 1초 표본을 합친 p90 0.351코어, run 평균 최댓값 0.391 + 0.31 = 0.701코어 → **800m**.
  run별 중앙값으로 묶으면 0.396코어 → 400m다. 이것은 민감도로만 시뮬레이션했다.
  800m는 m13 평균(0.391)에서 나왔다. m13을 빼면 규칙상 후보는 400m(0.086 + 0.31 = 0.396)이고, 400m는 아래 시뮬레이션에서 판정 조건을 채우지 못해 결론은 같다.
- 평시 기준 후보(사용자 결정, 사전 등록 보충 3): 기준을 평시만으로 두면 예매 묶음 가산을 빼고 디스크 정체가 겹친 m13도 뺀다. m11·m12의 1초 p90 0.081~0.139코어 → **200m**.
- 참고(Pod 하나가 평시 전체 100 req/s를 받는 경우, 디스크 프로브를 함께 돌린 6회 m3~m8): 디스크 조건을 통과한 5회 중 4회(m4~m7)에서 버려진 요청이 0.1%를 넘었다.
  m4는 판정 내내 api CPU가 코어 2개 가까이였고(1초 p50 1.97), 커넥션 풀 획득 시간 초과(30초)가 로그에 남았다(오류 2.6%). m5~m7은 1초 p50 0.17~0.22코어에 순간 상승이 있었고 풀 시간 초과 로그는 없었다.
  밀리지 않은 m8은 CPU 평균 0.335코어, p95 21ms였다. 예매 api 3개 중 2개가 빠진 상황에 해당한다.

| 600m·가능하면 분리(민감도) | 5 | 9 | 0 | 0 |
| 600m·가능하면 분리·빈 노드 확보(민감도) | 5 | 9 | 0 | 0 |
| 400m·가능하면 분리(민감도) | 4 | 8 | 0 | 1 |

| 200m·가능하면 분리·빈 노드 확보(평시 기준) | 4 | 7 | 0 | 2 |

- **판정(사전 등록): 800m로는 평시 3대가 되지 않는다.** 평시 노드가 5대로 지금과 같다.
- **평시 기준 200m도 판정 조건을 채우지 못한다.** 평시는 4대(1대 감소)지만, 사전 확장 뒤 api·대기열이 같은 노드인 경우가 2~3대 생긴다.
  평시 4대 중 1대는 web만 있는 노드였다. web 2개가 서로 다른 노드에 놓이는데, api·대기열이 함께 있는 노드는 CPU 요청 합이 1,650~1,930m로, 남는 자리 0~280m가 web 300m보다 작아 web이 들어갈 자리가 없었다.
  200m의 평시 CPU 요청 합은 5,120m로 노드 3대 allocatable 5,790m 안이라, 3대가 안 된 것은 산술 한계가 아니라 배치 제약(web 분산, Pod 크기)이다(계산·시뮬레이션).
- 배치 순서와 무관한 하한(계산): 800m 평시의 CPU 요청 합은 1,450 + 1,600 + 1,490 + 1,280 × 2 = 7,100m로, 노드 3대 allocatable 5,790m(1,930 × 3)를 넘는다. 평시 3대가 안 된다는 판정은 시스템 Pod 배치에 좌우되지 않는다. 4대인지 5대인지는 배치 순서의 영향을 받을 수 있다.
- 시뮬레이션에서 api 노드의 CPU 요청 합은 api 800m일 때 1,450~1,600m였다. 데몬셋과 시스템 Pod, web이 함께 놓이기 때문이다. 노드 allocatable 1,930m에서 남는 자리가 330~480m라 대기열 1,100m가 api 노드에 들어가지 못했다(600m에서도 남는 자리 470~700m, 계산).
- 400m에서는 평시 4대가 됐지만 대기열이 api 노드에 들어간 채 사전 확장까지 남아, 피크 동거가 1~2대 생겼다. 빈 노드를 먼저 확보해도 평시부터 api 옆에 있던 대기열은 옮겨지지 않았다(스케줄러는 이미 놓인 Pod를 옮기지 않는다).
  두 400m 시나리오는 평시 단계 설정이 같은데 평시 배치부터 달랐다(평시 동거 1·2). 시나리오당 1회라, 피크 동거 1·2와 사전 확장 8·7의 차이는 빈 노드 확보 절차보다 이 평시 배치 차이에서 나온 것으로 본다(추론).
  참고로 새 Pod는 들어갈 노드가 없을 때만 다른 Pod를 선점한다(쿠버네티스 스케줄러의 일반 동작). 400m 두 시나리오와 200m 빈 노드 확보 시나리오의 피크 동거는 평시 동거가 남은 것이다.
  200m 빈 노드 확보 없음 시나리오에서는 사전 확장 때 새 대기열 Pod 1개가 api 노드에 들어갔다(평시 동거 2 → 피크 3). 그 노드는 남는 자리가 1,080m라 대기열 1,100m가 들어갈 수 없었는데,
  우선순위가 낮은 web Pod(-1)를 선점해 들어갔다(요청 합 850 → 1,650m, 선점 뒤 재생성 2회, 추론). "가능하면 분리"는 선점할 노드를 고를 때 api 노드를 막지 못한다.

## 5. 조치
- 예매 api requests와 대기열 api 회피 규칙은 바꾸지 않는다. 판정 후보(800m)로는 노드가 줄지 않고, 평시 기준 200m는 평시 노드를 1대 줄이지만(한 달 약 $85, m6i.large 서울 $0.118/h × 24시간 × 30일, [[IMP-032]] 단가, 노드 EC2만 계산) 오픈 순간 api·대기열 동거를 2~3대 만든다.
  오픈 순간 동거는 [[IMP-038]]에서 예매 p95 +41~87%·대기열 스레드 포화를 낸 조건이라, 이 절감과 바꾸지 않는다.
- 피크 분리를 지키면서 평시를 줄이려면 사전 확장 절차에 "빈 노드 확보 → pause 해제 → 대기열 재배치(롤링)"를 넣어야 한다. 이 절차는 시뮬레이션하지 않았고 후보로만 남긴다.
- [[ADR-026]] B1의 "평시 노드 축소" 방향은 이 조건에서 검토 후 유지로 기록한다.
- 평시 혼합 조회 부하 스크립트를 `infra/k6/browse-mix.js`로 남긴다.

## 6. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대값이고 유효 run 3회다. 예매 묶음 CPU는 기존 로컬 실측을 더했다. EKS 값은 재지 않았다.
- 오픈 순간의 공연 상세 재조회는 포함하지 않았다(`traffic-profile.md` §4).
- m13의 순간 상승(같은 시각 디스크 정체, 인과 미확인)과 Pod 하나가 100 req/s를 받을 때 m4에서 난 커넥션 풀 고갈은 원인을 확인하지 못했다. 예매 api 2개가 빠진 상황의 위험으로 남긴다.
- 다음 측정부터는 디스크 유효 조건을 짧은 정체도 잡도록(예: 500ms 초과 횟수) 바꾸고, CPU 평균은 k6 구간으로 자른다.
- 평시 노드를 줄이는 다른 길(평시 대기열 1개, 노드 크기·종류 변경)은 이번 범위 밖이다.

## 7. 배운 점 (면접 답변용 한 줄)
"예매 api가 한가하니 요청량을 낮추면 노드가 준다"는 가정을 가정 트래픽 기준 실측과 실제 스케줄러 시뮬레이션으로 확인했고, 판정 후보에서는 노드가 줄지 않으며 줄어드는 값은 피크 동거를 만든다는 것을 보고 설정을 유지했다.
