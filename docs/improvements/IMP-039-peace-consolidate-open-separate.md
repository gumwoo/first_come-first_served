# IMP-039 · 평시 합치고 오픈 전 떼기: 순서를 지키면 배치는 되고, 평시 동거 영향은 판정이 갈려 보류

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-20(시뮬레이션 `artifacts/loadtest/kwok-20261020/`, 로컬 실험 `artifacts/loadtest/local-20261020-l4/`, 모두 레포 밖)
- 유형: 시뮬레이션(kwok, 시나리오당 2회) + 정량(로컬 실측, 도착률마다 조건당 2회). 로컬 실험은 같은 로컬 환경 안의 상대 비교다.

  - 로컬 `local-20261020-l4/`: 사전 등록 `prereg-L4.md`, 구성 `compose.yml`, 실행 `run-l4.sh`, 요약 `summarize-l3.mjs`, 결과 `out/`(실행 기록 `out/runs.log`)

## 1. 상황 (Context)
[[IMP-038]]에서 예매 api 요청량을 300m로 낮추는 후보를 기각했다. 노드 1대 절감은 api와 대기열이 한 노드에 함께 놓인(동거) 결과였는데, 오픈 부하(폴링 3,000/s + 예매 묶음)에서 동거가 폴링·예매를 함께 느리게 했기 때문이다.
남은 아이디어는 평시에만 api 300m로 두어 동거를 허용하고, 오픈 전 사전 확장 PR에서 api를 1100m로 되돌려 떼는 운영이다.
1100m에서는 api와 대기열이 한 노드에 함께 들어가지 못하므로(1,100 + 1,100 > 1,750, 1,750은 데몬셋 180m를 뺀 노드 여유, 계산) 오픈 순간 구성은 지금과 같아진다.
따라서 오픈 성능은 이미 측정된 값([[IMP-035]])을 그대로 쓸 수 있다.
새로 확인할 것은 두 가지다.
- 전환이 실제로 되는가: 롤링이 노드 상한에 막히지 않는지, 오픈 뒤 평시 노드 수로 돌아오는지.
- 평시 동거가 무해한가.

## 2. 문제 정의 + 분류
- 계층: 스케줄링·자동 확장(배치와 노드 수) + CPU 공유(평시 동거).
- 질문 1(시뮬레이션): 사전 확장 때 api 롤링(maxSurge 1, maxUnavailable 0)이 노드 상한 9에 막히는가. 오픈 뒤 되돌리면 CA 축소가 평시 노드를 지금(5대)보다 적게 만드는가.
- 질문 2(로컬): 평시 수준 부하에서도 동거가 예매·폴링을 느리게 하는가.

## 3. 측정 방법
### 3.1 시뮬레이션 (kwok: 실제 kube-scheduler, 가짜 노드)
- 입력: [[IMP-037]]과 같다. 실제 클러스터 스냅샷(시스템 Pod·데몬셋·노드 명세)과 main 매니페스트 렌더링을 쓴다.
- 한 바퀴의 흐름: 평시 → 사전 확장(대기열 2 → 6, T는 api를 300m에서 1100m로 롤링) → 되돌림(대기열 6 → 2, T는 api를 300m로 롤링) → CA 축소 흉내.
- 흉내 규칙(근사):
  - **CA 증설**: IMP-037과 같다(AZ당 3대, 합계 9대 상한).
  - **롤링**: 새 Pod 1개를 놓고(필요하면 증설), 그다음 옛 Pod 1개를 지운다. 이것을 3회 반복한다. 새 Pod가 상한에서 Pending이면 정체로 기록한다.
  - **CA 축소**:
    - 사용률(요청 CPU·메모리 중 큰 값, 데몬셋 포함)이 0.5 미만인 노드를 낮은 순으로 하나씩 비워 본다.
    - 노드 추가 없이 Pod가 다 다시 놓이면 그 노드를 지운다.
    - AZ당 최소 1대는 남긴다. CA Pod가 있는 노드는 제외한다(`safe-to-evict: "false"`). PDB도 확인한다.
- 시나리오(각 2회):
  - **V0cyc**: 지금 설정.
  - **T-api1st**: api를 300m/768Mi로 두고, 사전 확장 때 api 롤링을 먼저 끝낸 뒤 대기열을 늘린다.
  - **T-sim**: api 롤링과 대기열 증가를 동시에 한다.
  - **T-q1st**: 대기열을 먼저 늘린다.
  - **T-api1st-m1536**: 추가 등록한 변형이다. 하네스 k8s 규칙 ⑩-b는 api·대기열 템플릿 차이로 `requests.cpu`·`DB_POOL_MAX`·hostname 분산만 허용하고 메모리 차이는 막으므로, 메모리는 1536Mi로 유지하고 CPU만 300m로 낮췄다.
- 판정(사전 등록):
  - (a) 적어도 한 순서에서 롤링 정체 0, 사전 확장 뒤 노드 ≤ 9, 동거 노드 0, 노드당 대기열 ≤ 1.
  - (b) 되돌린 뒤 평시 노드 4대(V0보다 1대 적음). 판정에는 등록 질문("CA 축소가 평시 4대로 돌아오는가, 조각나 5대 이상에 머무는가")의 구도대로 5대 미만을 충족으로 썼다.
### 3.2 로컬 평시 동거 실험 (L4)
- 환경·도구: [[IMP-038]]의 L3와 같다(compose 복사).
  - **분리**: api는 코어 2·3, 대기열은 12·13.
  - **동거**: 둘 다 코어 2·3(`docker update --cpuset-cpus`로 재시작 없이 바꿨다).
  - 측정 동안 kwok 컨테이너는 멈췄다.
- 부하:
  - 대기열 폴링: 평시 부하는 가정값으로 두 단계를 정했다. 300/s(오픈 실험의 1/10)와 1,000/s(경향 확인용)를 각각 90초씩 걸었다.
  - 예매: +35초에 입장자 100명이 예매를 시작한다. 입장 정원이 100이라, 어느 때든 동시에 예매하는 사람 수의 상한(평시 최악값)이다.
- 순서: 도착률마다 예열 1회(결과 제외) 뒤 분리 I1 → 동거 C1 → 동거 C2 → 분리 I2(교차). run마다 새 공연과 다른 사용자 100명을 썼다.
- 판정(사전 등록, L3와 같은 기준): 동거 쪽 폴링 p99 또는 예매 p95(선점·주문·결제 세 단계 p95의 중앙값)를 짝지은 분리 run과 비교한다.
  - **경합 있음**: 두 쌍 모두 30% 이상 나쁘다.
  - **경합 없음**: 두 지표 모두, 두 쌍 모두 30% 미만이다.
  - **판단 불가**: 그 밖의 경우.

- 순서에 따라 결과가 갈렸다.
  - 동시나 대기열 먼저면 노드 9대가 큰 Pod 9개(api 3 + 대기열 6, 각 1100m)로 찬다. 그 위에 롤링 중 새 Pod 1개(surge)가 들어갈 10번째 노드가 없다.
  - 정체된 상태에서는 api 일부가 300m로 남은 채 오픈을 맞는다(T-sim 2회차는 3개 중 2개).
  - `event-prescale.yaml` 주석이 사전 확장 중(노드 9)에는 이미지가 바뀌는 PR을 머지하지 말라고 적은 것과 같은 이유다(롤링 surge가 10번째 노드를 얻지 못해 멈춘다).
  - api 롤링을 먼저 끝내면 4회 모두 정체가 없었고, 오픈 배치는 지금과 같았다(동거 0, 노드당 대기열 1).
- **판정 (a) 충족**: api 먼저 순서에서만 충족했다.
- **판정 (b) 충족**: 되돌린 뒤 평시 노드는 4대 두 번, 3대 두 번으로 V0(5대)보다 1~2대 적었다.
  - T-api1st 1회차(3대)와 2회차(4대)는 비워진 Pod가 간 노드에서 갈렸다. CA Pod가 있는 노드(`sim-2b-1`)는 축소 후보에서 빠진다.
    - 2회차는 시뮬레이터 필터를 소거해 확인했다. 마지막 상태에서 사용률 0.39, 같은 AZ에 노드 2대, flowticket Pod가 없어 PDB와 무관한데 축소 시도 기록이 없다.
    - 1회차에서는 다른 노드를 비울 때 Pod가 이 노드로 들어가 0.86이 됐다(되돌린 직후 상태가 같아 같은 노드로 봄, 추론). 2회차에서는 `sim-2b-7`로 가서 그 노드가 0.56이 됐다. 그래서 2회차는 flowticket Pod가 없는 0.39 CA 노드와 0.56인 노드가 함께 남았다.
  - m1536 1회차(4대)는 평시 처음 배치부터 5대(대기열이 새 노드 두 대에 따로 놓임)였고, 그 배치가 이어졌다. 마지막 4대가 모두 사용률 0.5 이상이라 축소 후보가 없었다.
  - 즉 평시 노드 수는 배치 이력에 따라 달라진다.
- 3대로 줄어든 경우에는 노드 사용률이 0.82~0.98이었고, api 3개 중 2개가 한 노드에 놓였다(T-api1st 1회차, m1536 2회차). 4대로 끝난 T-api1st 2회차에서도 `sim-2b-7`에 api 2개와 web이 함께 있었다. 그 노드 하나를 잃으면 api 2개가 함께 빠진다(G1).
- api 먼저 순서에서는 롤링 중 새 api Pod 3개 중 2개가 새 노드에 놓였다(4회 중 3회). 롤링이 한 번에 하나씩 진행되므로 노드 추가(AWS 측정 재분석 100~150초)가 차례로 붙고, 사전 확장이 몇 분 길어진다(추정).

선점 p95에는 409 경합 응답이 포함되고, 결제 p95에서는 의도된 실패를 뺐다.
모든 run에서 5xx 0, 폴링 실패 0, dropped 0이었다. 폴링 요청은 300/s에서 28,000건, 1,000/s에서 91,000건이고, 둘 다 연결 미리 맺기 1,000건을 포함한다.

- **300/s 판정**: "경합 있음"(사전 등록 기준, 두 지표 모두 두 쌍에서 30% 이상 악화).
  - 예매 세 단계 중앙값: I1 929 → C1 1,512ms(+63%), I2 510 → C2 846ms(+66%).
  - 폴링 p99: 5.8 → 8.2ms(+41%), 3.5 → 5.0ms(+43%). 비율로는 기준을 넘었고 절대값은 몇 ms 차이다. 대기열 Tomcat 바쁨도 2~5로 낮았다.
- **1,000/s 판정**: "판단 불가"(두 쌍의 방향이 엇갈림).
  - 예매: 384 → 600ms(+56%), 659 → 537ms(−19%)로 방향이 반대였다.
  - 폴링 p99: +43%와 −11%였다.
- 분리 조건끼리의 차이도 30% 기준보다 컸다. 같은 분리 조건에서 예매 중앙값이 929 vs 510ms(300/s), 384 vs 659ms(1,000/s)로 갈렸다.
  - api Hikari pending 최대도 2~90으로 run마다 달랐다.
  - 300/s의 "경합 있음"은 사전 등록 판정대로 기록하며, 효과 크기는 분리 run 간 변동과 같은 규모다.
- run 수는 사전 등록 횟수 그대로다.

## 5. 조치
- "평시 합치고 오픈 전 떼기"는 채택을 보류한다. 설정은 바꾸지 않는다.
  - 배치 면에서는 된다. 사전 확장 때 api 롤링을 먼저 끝내면 정체 없이 지금과 같은 오픈 배치(9대, 동거 0)가 나왔고, 평시 노드는 3~4대로 지금(5대)보다 적었다(시뮬레이션).
  - 이 운영의 전제는 평시 동거가 무해하다는 것이다. 평시 부하를 가정한 300/s의 사전 등록 판정은 "경합 있음"(예매 p95 +63~66%), 1,000/s는 "판단 불가"였고, 분리 run 간 변동이 효과와 같은 규모였다(로컬). 이 결과로는 전제가 성립한다고 볼 수 없어 보류한다.
- 채택하려면 운영 비용도 따른다.
  - 사전 확장을 두 단계로 나눠야 한다. api 요청량을 바꾸는 PR을 머지하고 롤링 완료를 확인한 뒤, 대기열 하한을 올리는 PR을 머지한다(ArgoCD sync-wave로 순서를 강제하는 방법도 있다, 시험 전).
  - 한 PR로 함께 바꾸거나(동시) 대기열을 먼저 늘리면, 시뮬레이션에서 각 2회 합계 4회 모두 롤링이 정체됐다.
  - 되돌릴 때도 api 롤링이 한 번 더 일어난다.
- 절감 규모(계산, 평시가 하루 종일이라는 가정, 노드 EC2만): 1~2대 × 24시간 × $0.118/h([[IMP-032]] 단가)로 하루 약 $2.8~5.7, 30일 약 $85~170이다.
- 다시 검토할 조건:
  - 실제 평시 트래픽(폴링 도착률, 동시 예매 규모)을 알게 됐을 때.
  - 예매 지연의 run 간 변동(DB 풀 대기로 추정)을 줄인 설계로 동거 효과를 다시 잴 수 있을 때.
  - 클라우드에서 전환 시간과 CA 축소를 확인할 수 있을 때.

## 6. 트레이드오프 / 다음 개선
- 시뮬레이션 측정 조건: 배치 가능성만 보며, 스케줄러 버전과 CA 단순화 등 [[IMP-037]]과 같은 조건이다(P3 재현에서는 실측보다 1대 많았다).
  - CA 축소 흉내는 근사다. 실제 CA는 내부 시뮬레이션으로 판단하고, 10분 대기와 빈 노드 일괄 삭제가 있다. "새로 만든 대기열부터 줄인다"도 근사다.
  - 정체된 순서(T-sim, T-q1st)의 되돌림은 실제 동작(정체 중 스펙을 되돌리는 롤아웃)을 흉내 내지 않아 판정에 쓰지 않았다.
- 평시 노드 3~4대는 CA 축소 흉내 결과이고, 처음 올린 직후는 4~5대였다. [[IMP-037]]의 S2 "평시 4"는 증설만 흉내 낸 값이라 이번과 정의가 다르다.
- 로컬 측정 조건: 로컬 상대 비교이고 도착률당 조건별 2회다. 평시 부하(300/s·1,000/s)는 가정이다. 예매 시나리오의 진입·상태 조회도 api 컨테이너로 보냈고(L3와 같은 조건), 동거로 바꿀 때 대기열의 코어 번호도 함께 바뀐다. 폴링 p95·p99는 연결 미리 맺기 요청을 포함한 k6 전체 지연이다.
- 적용 시 하네스 k8s 규칙 ⑩-b 관련해 함께 바꿀 것:
  - 메모리를 768Mi로 낮추는 형태(T-api1st)는 ⑩-b가 메모리 차이를 막으므로 규칙을 바꿔야 적용할 수 있다.
  - m1536도 그대로는 통과하지 않는다. ⑩-b는 api와 대기열의 CPU 요청이 다르면 대기열에 노드 단위 분산(hostname, maxSkew 1, DoNotSchedule, 대기열만 고르는 selector)을 짝으로 요구하는데, 지금 대기열에는 zone 분산만 있다.
  - 시뮬레이션은 이 분산 없이 돌렸다. 모든 단계에서 노드당 대기열은 1이었고, 축소 때 대기열 Pod가 옮겨진 적은 없다.

## 7. 배운 점 (면접 답변용 한 줄)
평시에만 요청량을 낮춰 노드를 합치는 운영을 검토하면서 한 바퀴 전체(평시 → 사전 확장 → 되돌림 → CA 축소)를 실제 스케줄러로 흉내 냈다. 사전 확장 PR 하나로 바꾸면 롤링이 노드 상한에 막히고 순서를 나누면 배치는 된다는 것을 보였고, 평시 동거 측정 결과와 절감액(하루 $3~6, 계산)을 함께 놓고 보류로 정리했다.
