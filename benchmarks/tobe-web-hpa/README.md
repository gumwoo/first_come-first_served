## 판정

**capacity knee가 600 rps 위로 올라갔다.** AS-IS에서 무너지던 지점(도착률 미달 551, 실패 4.06%,
p95 10초, drop 1,726)이 TO-BE에서는 **도착률 599 달성, 실패 0%, p95 123ms, drop 0**이다.

**개선의 원인은 web 확장으로 판단한다.** 근거:

- AS-IS의 실패는 전부 `TargetConnectionError`(ALB→web 연결)였고, TO-BE에서 그 수치가 0이 됐다
- web은 200 rps부터 4파드로 확장됐다(AS-IS는 2파드 고정)
- api는 오히려 **최대치를 9에서 7로 줄였는데도** 결과가 좋아졌다 — api가 병목이 아니었다는
  AS-IS 판단을 뒷받침한다

**Hikari pending은 TO-BE에서도 전 구간 0.** DB는 이 부하 범위에서 병목이 아니다.

## 한계와 이상치

⚠️ **200 rps 구간의 p99가 2,187ms로 튀었다**(서버 p99도 2,071ms). 같은 시점 api 파드가
3→7로 확장 중이었고 api CPU가 3.18 core로 이 측정에서 가장 높았다. **스케일아웃 과도기의
비용으로 추정**하지만 확인하지 않았다. 300 rps 이상에서는 파드가 이미 7로 안정되어 p99가
90~266ms로 내려간다.

⚠️ **100 rps에서 p95가 오히려 나빠졌다**(43ms → 113ms). api 파드가 AS-IS 7개 vs TO-BE 3개로
시작 상태가 달랐다. AS-IS 측정 직전에 다른 부하가 있어 이미 확장된 상태였기 때문이다 —
**같은 도착률이지만 시작 조건이 달랐다.** 이 한 줄만으로 저부하 성능이 나빠졌다고 볼 수 없다.

⚠️ **각 단계 1회씩만 측정했다.** AS-IS도 마찬가지다. 300 rps에서 p95 45ms, 450에서 109ms,
600에서 123ms인 것을 보면 단계 간 변동이 작지 않다.

⚠️ **web max 4로 충분한지는 이 부하로 확정되지 않았다.** 600 rps에서 web CPU 1.30 core
(4파드 = 파드당 약 0.33 core, requests 300m 대비 108%)로 아직 상한에 여유가 없다.
그 위 부하는 재보지 않았다.

## 이 수치를 어떻게 읽어야 하는가

AS-IS와 같다 — k6를 노트북에서 인터넷 경유로 돌렸고 클라이언트 p95에는 RTT·TLS·ALB·Next
프록시가 포함된다. **절대 성능이 아니라 동일 조건 before/after 비교**로만 쓴다.
