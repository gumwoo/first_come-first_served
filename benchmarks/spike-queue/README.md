# ③ 대기열 스파이크 — 정원 상한·순서 보존 실증 (2026-08-12)

티켓 오픈은 **정의상 스파이크다.** 평상시 0에서 순간 수천으로 튀는 그 순간을 위해 대기열이
존재한다. 이 측정은 그 순간에 대기열이 실제로 무엇을 보장하는지를 본다.

## 명제 셋

> ① **over-admit 0** — 도착량과 무관하게 동시 입장이 정원(100)을 넘지 않는다
> ② **순서 보존** — 늦게 온 사람이 먼저 입장하지 않는다
> ③ **나머지는 대기** — 입장 못 한 사람이 에러가 아니라 `WAITING`을 받는다

③이 특히 중요하다. **2,900명이 500을 받으면 "막았다"가 아니라 "터졌다"이다.**

## 설계

```
시드 계정 3,000개 (loadseed+*@example.com, DB 직접 삽입)
  → JWT 3,000개 사전 발급        ← 측정 구간에 로그인(bcrypt CPU)이 섞이지 않게
  → 정원의 30배가 동시에 대기열 진입
  → 진입 중 Redis admitcount를 200ms 간격으로 샘플링   ← 명제 ①
  → 종료 후 wait ZSET의 score 분포 확인                ← 명제 ②
```

**k6 executor는 `per-vu-iterations`(VU당 1회).** 1인 1토큰이라 VU와 사용자가 1:1로 고정되는데,
`shared-iterations`는 전체 iteration을 VU들이 나눠 가져 그 전제가 깨진다(#219에서 같은 실수를
했다).

구성은 Phase 1과 동일 — api HPA 3~7 / web HPA 2~4, 노드 t3.large × 3.
`queue.capacity=100`, `admit-interval-ms=1500`, `admit-ttl=300`.

## 결과

2회 독립 실행. 매 실행 전 Redis 대기열 상태를 비웠다.

| | run-1 | run-2 |
|---|---|---|
| iterations | **3,000** | **3,000** |
| 진입 200 | **3,000 / 0 실패** | **3,000 / 0 실패** |
| `WAITING` 또는 `ADMITTED` | **3,000** | 2,990 (10건 `EXPIRED`, 아래 §주의) |
| **5xx** | **0** | **0** |
| rank 부여됨 | 3,000 | 3,000 |
| 진입 p50 / p95 / max | 3,964 / 8,466 / 9,693ms | 2,988 / 7,453 / 8,148ms |
| 전체 소요 | 14.4s | 13.0s |

`iterations=3,000`이 찍힌 것이 **VU당 정확히 1회**가 보장됐다는 근거다.
원자료는 `run-{1,2}.json`.

### ① over-admit 0 — 부하 중 실시간 샘플

진입이 진행되는 동안 Redis를 200ms 간격으로 읽었다.

| | run-1 | run-2 |
|---|---|---|
| 유효 샘플 | 277 | 277 |
| **최대 `admitcount`** | **100** | **100** |
| 최대 `wait`(대기자) | 2,900 | 2,900 |

**두 실행 모두 277개 샘플 전부가 정확히 `100`이었다.** 3,000명이 도착해도 동시 입장은
정원에서 잘린다. 원자료는 `run-{1,2}-admitcount-samples.txt`(시각·admit·wait 그대로).

⚠️ **0→100 상승 구간은 샘플하지 못했다.** run-1 기준 `14:48:43 → 14:48:47`에 **4초 공백**이
있다(부하 중 `redis-cli` 응답 지연으로 **추정**하며 확인하지 않았다). 그 창 안의 순간적 초과가
있었다면 이 자료로는 잡히지 않는다. 말할 수 있는 것은 **관측된 277개 샘플 내내 정확히 100이었고
한 번도 넘지 않았다**까지다.

### ② 순서 보존 — 추월 0건

**먼저 잘못 쟀고, 그것을 기록해 둔다.** 처음에는 진입 응답의 `rank`로 재려 했고 "추월 51건"이
나왔다. 그 지표가 틀렸다 — `rankOf()`는 ZSet **위치**를 돌려주는데, 앞사람이 승격돼 빠지면
위치가 밀려 내려간다. 즉 **늦게 도착해도 낮은 rank를 볼 수 있다.** 도착 순번이 아니다.

도착 순번은 `score`다. `ISSUE_LUA`가 `INCR seq` 값을 ZADD의 score로 쓴다.

```lua
local seq = redis.call('INCR', KEYS[2])
redis.call('ZADD', KEYS[3], seq, ARGV[1])
```

승격은 `ZPOPMIN`(최소 score부터)이므로, **순서대로 뽑혔다면 남은 score는 앞쪽만 빠진 연속 구간**
이어야 한다. run-2 종료 후 `queue:wait` 전체를 스냅샷했다.

```
남은 토큰      2,800개
score 범위     201 ~ 3000
연속이라면 개수  2,800   /  실제 2,800
▶ 구멍 개수     0
▶ 앞에서 빠진 구간  1 ~ 200
```

**중간에서 먼저 빠져나간 토큰이 하나도 없다.** 빠진 것은 정확히 앞에서부터 200개(= 정원 100의
2회전)다. 요약은 `run-2-wait-scores.json`(토큰 값은 저장하지 않고 score 분포만 남겼다).

### ③ 나머지는 대기 — 5xx 0

run-1은 3,000건 전부 `200 + WAITING`이다. **2,900명이 정원 밖으로 밀렸지만 아무도 에러를 받지
않았다.** 이것이 이 시나리오의 핵심이다.

## 첫 실행의 5xx 45건 — 원인 특정

**이 측정의 첫 시도(12:10 UTC)에서는 5xx가 45건 나왔다.** 숨기지 않고 원인을 찾았다.
CloudWatch에서 해당 5분 구간을 떼어냈다.

| 시각(UTC) | ELB_5XX | **Target_5XX** | TargetConnectionError | RequestCount |
|---|---|---|---|---|
| **12:10** (첫 시도) | **45** | **0** | **45** | 5,508 |
| 14:40~14:55 (유효 3회) | 0 | 0 | 0 | — |

**`Target_5XX = 0`** — 애플리케이션은 5xx를 낸 적이 없다. 45건 전부 `TargetConnectionError`,
즉 **ALB가 web 파드에 연결하지 못한 것**이고 k6가 센 45와 정확히 일치한다.
AS-IS 측정(`../asis-web2pod/`)에서 본 web 티어 실패와 같은 서명이다.

같은 시점 파드 수:

| 시각 | api | web | 5xx |
|---|---|---|---|
| 12:10 | 7 | **2** (HPA 최소) | 45 |
| 14:52 | 7 | **3** | 0 |

**스파이크 순간 web이 아직 확장 전이어서 연결을 받지 못한 것으로 판단한다.**
⚠️ 다만 **통제된 A/B를 돌리지 않았다.** web 2파드에서 재현하고 3파드에서 소거하는 실험을 하지
않았으므로 인과는 확정이 아니다. 확실한 것은 **실패 지점이 앱이 아니라 ALB→web 연결 구간**이라는
것이다.

이 자체가 시사점이다 — **스파이크는 HPA가 반응하기 전에 끝난다.** run-2는 13초 만에 종료됐고,
HPA 평가 주기(15초)보다 짧다. 스파이크 대비는 확장이 아니라 **최소 파드 수**의 문제다.

## 주의 — run-2의 `EXPIRED` 10건

run-2에서 10명이 진입 시 `EXPIRED`(rank 0)를 받았다. `isReusable()`의 fallback 경로로
**추정**한다 — 실행 간 상태를 비울 때 `queue:token:*`은 지워졌는데 `queue:user:*` 키가
SCAN 경합으로 남아, 죽은 토큰이 재사용됐다는 시나리오다.

```java
// 아직 wait 등록 전인 '경합 중 신규 토큰'은 메타가 없어 EXPIRED로 보이므로
// 이 경우엔 true를 반환해 중복 발급을 막는다.
return !Boolean.TRUE.equals(redis.hasKey(QueueKeys.token(token)));
```

**확인하지 않았다.** run-1(같은 스크립트, 같은 정리 절차)에서는 0건이라 재현되지 않았다.
내 수동 Redis 정리가 만든 측정 아티팩트로 보지만 앱 버그 가능성을 배제하지는 못한다.
**이 항목은 미해결로 남긴다.**

## 측정 과정에서 깨진 것들 (기록)

같은 함정을 다시 밟지 않도록 남긴다. 앞선 회차들이 무효였던 이유다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 샘플러가 250개 전부 `admit=0` | `sh -c "…$REDIS_HOST…"` 를 큰따옴표로 써서 **바깥 bash가 먼저 확장** → 빈 값 → redis-cli가 localhost로 붙어 실패. `${A:-0}`이 그 실패를 0으로 위장 | 스크립트를 파일로 만들어 **stdin으로 주입** |
| k6가 `fatal error: runtime: cannot allocate memory` | `open()`은 init에서 **VU마다** 실행된다. 3,000 VU × JSON 파싱 | `SharedArray`로 전 VU 공유 |
| 3,000건 전량 `401` | `access-token-ttl: 1800`(30분). 재시도하는 사이 만료 | 발급 직후 측정 |
| 상태 조회 2,990건 전부 `HTTP 410` | k6 로그의 닫는 `"`까지 토큰에 딸려 들어감 | 파싱 수정 |
| "추월 51건" | `rank`를 도착 순번으로 착각(§②) | `score`로 재측정 |

**`admit=0`이 정상값처럼 보였다는 점이 가장 위험했다.** 실패를 0으로 덮는 기본값은
"측정이 안 됐다"를 "문제가 없다"로 바꿔 놓는다.

## 무엇을 증명했고 무엇을 안 했나

**증명한 것**

- 정원의 **30배**가 동시에 도착해도 동시 입장은 **정확히 100**에서 잘린다(277샘플 × 2회)
- **순서가 보존된다** — 남은 score가 완전 연속, 추월 0건
- 초과분 2,900명이 **에러가 아니라 `WAITING`**을 받는다. 5xx 0
- 이것이 **다중 파드(api 7개) 운영 환경**에서 성립한다 — IMP-004는 단일 워커 통합테스트였다

**증명하지 않은 것**

- ⚠️ **0→100 상승 순간을 못 봤다**(4초 공백). 순간 초과 가능성을 이 자료로는 배제 못 한다
- ⚠️ **3,000명이 상한이 아니다.** 30배에서 깨지지 않았다는 것이지, 10만 명을 시험한 게 아니다.
  이 규모는 k6를 노트북 1대에서 돌린 제약에서 왔다
- ⚠️ **"동시"의 정도를 재지 않았다.** 3,000 VU 진입이 13~14초에 걸쳐 퍼졌다. 진짜 동시가 아니라
  **13초 안의 3,000명**이다
- **진입 p95 7.5~8.5초는 느리다.** 정합성은 지켰지만 사용자 경험 관점의 목표(p95 300ms)와는
  거리가 멀다. 이 구간의 튜닝은 하지 않았다
- 승격 이후 경로(좌석 선택·결제)는 이 시나리오 밖이다. 매진 경합은 `../hold-contention/`

## 재현 절차

```bash
# 1) 시드 계정 3,000개 (DB 직접 삽입, 기준 계정의 bcrypt 해시 재사용)
# 2) JWT 사전 발급 — 30분 TTL이므로 발급 직후 측정할 것
node infra/k6/seed-issue-tokens.js /tmp/tokens3k.json 3000 12
# 3) 대기열 상태 초기화 후 실행
k6 run -e K6_BASE_URL=https://flow-ticket.com/api -e TOKENS=/tmp/tokens3k.json \
       -e EVENT_ID=<eventId> infra/k6/spike-queue.js
```

`RANKLOG=1`을 주면 VU별 진입 결과를 stdout으로 남긴다(순서 대조용).
시드 계정은 `loadseed+*@example.com` 패턴이라 사후 정리가 가능하다. **실사용 계정이 아니다.**
