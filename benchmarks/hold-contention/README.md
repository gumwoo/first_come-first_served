# ② 매진 경합 — 초과판매 0 실증 (2026-08-11)

**성능 시험이 아니다.** 초과판매는 지연이 아니라 사고다 — 5ms에 일어나든 5초에 일어나든
2명이 성공하면 시스템은 실패한다.

## 명제

> 잔여 **1석**에 **100명이 동시에** 달려들어도 정확히 1명만 성공하고, 나머지는 서버 오류가 아니라
> 정상 거절을 받는다. 이것이 **20회 연속** 성립한다.

## 설계

```
시드 계정 120개(DB 직접 삽입, bcrypt 해시 재사용)
  → JWT 사전 발급 120개          ← 측정 구간에 로그인(bcrypt CPU)이 섞이지 않게
  → 전원 대기열 진입
  → ADMITTED 100명 확보          ← 정원이 100이므로 이것이 구조적 상한
  → 라운드마다 새 좌석 1석에 100명 동시 HOLD
  → 20회 반복
```

**왜 1석인가**: `SeatService.hold()`의 `holdIfAvailable()`은 **전부 아니면 전무**다
(`held != seatIds.size()` 이면 `SOLD_OUT` 롤백). 1석으로 두면 "정확히 1"이라는 가장 단순하고
반박하기 어려운 단언이 된다.

**왜 20회인가**: 경합 버그는 한 번으로 나오지 않는다. 20회에 1회 깨지는 것이 가장 위험하다.

**왜 라운드마다 새 좌석인가**: `max-per-user: 4` 때문에 같은 좌석을 재사용하려면 홀드를 해제해야
하고, 그 해제 경로가 실험에 섞인다. 좌석을 바꾸면 각 라운드가 독립적이다.

**k6 executor는 `per-vu-iterations`(VU당 1회)**. 도착률이 아니라 **동시 출발**이 목적이다.

⚠️ 첫 시도는 `shared-iterations`였고 **그것은 이 실험에 맞지 않았다.** 전체 iteration을 VU들이
나눠 갖는 방식이라 빠른 VU가 여러 번 가져가고 어떤 VU는 한 번도 실행하지 않을 수 있다. 이 스크립트는
`exec.vu.idInTest`로 사용자를 고정하므로, 그 경우 **"서로 다른 100명이 각각 1번씩"이라는 전제가
깨진다**(같은 사용자가 두 번 쏘고 다른 사용자는 안 쏜다). 리뷰에서 잡혀 executor를 바꾸고
**20회를 전부 다시 돌렸다.** 아래 결과는 재실행분이다.

## 결과 — 20/20

| 회차 | 좌석 | iterations | 승자(200) | 패자(409 SOLD_OUT) | 그 외 응답 | 5xx |
|---|---|---|---|---|---|---|
| 1~20 | 160557~160576 | **각 100** | **각 1** | **각 99** | **0** | **0** |

전 회차 동일. `iterations=100`이 매 회차 찍힌 것이 **VU당 정확히 1회**가 보장됐다는 근거다.
원자료는 `round-{1..20}.json`.

**패자를 4xx가 아니라 `409 SOLD_OUT`으로 검증했다.** 단순히 4xx로 세면 인증 실패(401)·권한(403)·
잘못된 좌석(400)·rate limit(429)까지 "정상 거절"로 집계돼 **패자가 진짜 좌석 경합에서 진 것인지
알 수 없다.** `그 외 응답 = 0`이 그것을 배제한다.

## DB 불변식 (사후 검증)

응답 코드만으로는 부족하다. 20회가 끝난 뒤 DB를 직접 확인했다.

```sql
-- ① 좌석 상태
 status | count
--------+-------
 HELD   |    20        ← 20석 전부 HELD

-- ② 초과판매 검사: 한 좌석에 활성 홀드가 2건 이상인 경우
 좌석당_활성홀드_2건이상
                      0        ← 초과판매 0

-- ③ 홀드 아이템 총계
 홀드아이템_총계
              20        ← 정확히 20, 초과도 누락도 없음

-- ④ 승자 분포
 서로다른_승자수
              19
```

④는 **관측만 하고 판단하지 않는다.** 20회 승자가 19개 계정에 분산된 것은 사실이지만, 20회는
공정성을 논하기에 표본이 너무 작고 **이 실험은 애초에 공정성을 검증하도록 설계되지 않았다.**
편향 여부는 이 자료로 말하지 않는다.

## 무엇을 증명했고 무엇을 안 했나

**증명한 것**

- 실사용 API 경로(인증 → 대기열 → ADMITTED → HOLD)에서 **초과판매 0**
- 실패가 500이 아니라 **정상 거절**(4xx)로 나온다 — 거절 경로가 살아 있다
- 20회 반복에서 한 번도 깨지지 않았다
- 대기열 정원이 실제로 100에서 잘린다(120명 진입 → 100명 ADMITTED)

**증명하지 않은 것**

- ⚠️ **동시성 수준은 100이 상한이다.** 대기열 정원이 100이라 API 경로로는 그 이상을 만들 수
  없다. 이것은 제약이 아니라 **대기열을 둔 목적**이지만(좌석 DB에 10,000명이 그대로 몰리지 않게
  앞단에서 제한), "1,000명이 동시에 같은 좌석을" 같은 주장은 이 실험으로 할 수 없다.
  그 층위는 대기열을 우회한 **서비스 층 통합테스트**로 봐야 한다(`SeatInventoryIntegrationTest`).
- **"동시"의 정도를 재지 않았다.** `shared-iterations`로 100 VU를 동시에 출발시켰지만 실제
  요청이 서버에 도달한 시간 분포는 확인하지 않았다. 네트워크·k6 스케줄링으로 수십 ms 퍼졌을 수
  있고, 그렇다면 경합 강도가 의도보다 약했을 가능성이 있다.
- **1인 구매 한도(quota)·결제 멱등은 이 실험 범위 밖이다.** 별도 시나리오가 필요하다.

## 재현 절차

```bash
# 1) 시드 계정 120개 (DB 직접 삽입, 기준 계정의 bcrypt 해시 재사용)
# 2) JWT 사전 발급
node infra/k6/seed-issue-tokens.js /tmp/tokens.json
# 3) 대기열 진입 → ADMITTED 100명 추출
node infra/k6/seed-admit.js <eventId> /tmp/tokens.json /tmp/admitted.json
# 4) 라운드 실행
k6 run -e K6_BASE_URL=https://flow-ticket.com/api -e TOKENS=/tmp/admitted.json \
       -e EVENT_ID=<eventId> -e SEAT_ID=<seatId> infra/k6/hold-contention.js
```

시드 계정은 `loadseed+*@example.com` 패턴이라 사후 정리가 가능하다. **실사용 계정이 아니다.**
