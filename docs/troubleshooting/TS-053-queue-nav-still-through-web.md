# TS-053 · "대기열은 web을 건너뛴다"였는데 예매하기 → 대기열 화면 이동은 web을 거쳤다 — 그리고 측정 전에 반박된 keep-alive 쏠림 가설

- 날짜: 2026-10-17
- 영역: 프론트 서버(Next 라우팅·캐시)·부하 시험 범위
- 결과: **원인 확인 → 수정**(#436 — 대기열 화면 정적 경로·미리 받기·재조회 제거·디스크 캐시 끔). 로컬 프로덕션 빌드와 CI E2E로 검증했다. 클러스터에서 이 화면 이동 부하를 10만 규모로 재지는 않았다.
  같은 날 세운 "web의 연결 재사용 때문에 api 파드 일부로 요청이 쏠린다" 가설은 **측정 전에 코드로 반박**됐다(#435, §부록).
- 관련: [[ADR-024]](대기열 경로 Next 홉 우회), [[IMP-031]]·[[IMP-035]](10만 진입 판정 — 진입·상태 조회 API만 침), [[IMP-034]](예매 중 api CPU가 낮았던 관측), #436, #435

## 증상
- 설계상 대기열 진입·상태 조회 API는 web(Next)을 건너뛴다([[ADR-024]] — ALB가 대기열 경로를 web 없이 백엔드 파드로 바로 보냄, B 구성에서는 대기열 파드). 10만 진입 판정([[IMP-031]])도 이 두 API만 쳤다.
- 그런데 사용자가 실제로 거치는 **직전 단계**, 공연 페이지의 "예매하기" 클릭 → 대기열 화면 이동은 시험 범위에 없었다. 이 단계가 web을 거치는지 확인한 기록도 없었다.
- 로컬 프로덕션 빌드(`next build` → `next start`)에서 버튼을 누르고 네트워크를 보니 클릭 한 번에 이 요청이 나갔다(실측, 로컬):
  - `GET /events/1/queue?_rsc=…` — 대기열 화면이 동적 경로(`ƒ`)라 **web이 매번 서버 렌더**한 RSC
  - 대기열 화면 JS
  - `GET /api/events/1` — 대기열 화면이 공연 정보를 다시 불러 **web을 거쳐 api로**. 공연 상세는 실시간 랭킹 조회수도 올린다.
  - 진입 API(이것만 web을 건너뜀)

## 재현
- 로컬 환경: 임시 PostgreSQL·Redis + 로컬 api + web 프로덕션 빌드, 브라우저 네트워크 탭·`performance` 리소스 항목.
- 공연 상세 → "예매하기" 클릭 → 위 4종 요청 확인(수정 전 `main`).
- 규모 환산(계산, 미측정): 오픈 10초에 10만 명이 누르면 web에 초당 약 1만 건의 서버 렌더, api(B 구성에서 3개 고정)에 초당 약 1만 건의 공연 조회가 간다.

## 조사
- **왜 시험이 못 잡았나**: 부하 발생기는 진입 API와 상태 조회 API를 직접 부른다. 화면 이동(RSC)과 화면이 부르는 부가 API는 발생기 시나리오에 없다. "API가 web을 건너뛴다"는 사실이 "사용자 흐름이 web을 건너뛴다"로 넓게 읽혔다.
- **왜 동적 경로였나**: 대기열 화면은 전부 클라이언트 컴포넌트라 서버가 요청마다 그릴 내용이 없다. 그런데 `[id]` 동적 세그먼트에 정적 생성 설정이 없어 Next가 기본값으로 요청마다 렌더했다(빌드 출력 `ƒ (Dynamic)`).
- **왜 공연 정보를 다시 불렀나**: 대기열 화면이 제목·장소·일시를 보여 주려고 `useEvent(id)`를 불렀고, 기본 `staleTime`에서는 공연 페이지에서 받은 캐시가 있어도 다시 요청했다.
- **수정안이 만든 새 구멍(G1이 발견)**: 처음 요청 때 정적 생성(`dynamicParams = true`)으로 바꾸면, Next 기본값(`isrFlushToDisk: true`)에서 id마다 `.next/server/app/events/<id>/queue.{html,rsc,meta}`(약 18KB)를 디스크에 쓰고 지우지 않는다.
  - 아무 id(숫자가 아니어도)로 대량 요청하면 web 파드 디스크가 끝없이 는다. 리뷰어가 로컬 `next start`로 확인했고, 매니페스트에 `readOnlyRootFilesystem`이 없어 k8s에서도 막히지 않는다(매니페스트·Dockerfile 기준 — `USER nextjs`가 쓸 수 있는 standalone 디렉터리, 클러스터에서 확인하지는 않음).

## 근본 원인
"web을 건너뛴다"를 **API 단위**로 설계·검증했고, 그 API에 닿기까지의 **화면 이동 단계**는 설계·시험 범위 밖에 있었다. 그 단계에서 대기열 화면이 동적 경로(서버 렌더)였고, 이미 가진 공연 정보를 다시 불러 web → api 왕복을 만들었다.

## 해결(#436)
- **대기열 화면을 정적 경로로**: `page.tsx`를 서버 껍데기로 두고 화면은 `QueueView.tsx`("use client")로 옮겼다. `dynamic = "force-static"`, `dynamicParams = true`, `generateStaticParams() → []`. 빌드 출력이 `○ (Static)`이 됐다.
  - 라우트 세그먼트 설정은 클라이언트 컴포넌트 파일에 둘 수 없어서 파일을 나눴다.
- **공연 페이지에서 미리 받기**: `router.prefetch`로 대기열 화면을 미리 받는다. Next 14.2 클라이언트 라우터 캐시(`staleTimes.static` 기본 300초) 안에 누르면 web 요청이 없다. 공연 상태가 바뀌면 다시 부른다.
- **재조회 제거**: 대기열 화면은 `useEvent(id, { staleTime: Infinity })`로 공연 페이지의 캐시를 그대로 쓴다. 대기열 화면으로 바로 들어온 경우에만 한 번 받는다.
- **디스크 캐시 끔**: `experimental.isrFlushToDisk: false` — 메모리 캐시(`cacheMaxMemorySize` 기본 50MB LRU, Next 소스 확인)만 쓴다.
- 고르지 않은 대안: `experimental.staleTimes`로 미리 받기 유효 시간을 늘리기 — 만료돼도 서버 렌더 없는 정적 캐시 응답(로컬 첫 요청 80ms, 이후 3ms)이라 늘려서 얻는 것이 작다고 봤다(추론). 실험 옵션을 하나 더 늘리지 않으려는 이유도 있다 — 채택한 `isrFlushToDisk`도 Next의 experimental 옵션이다(리스크).

## 검증
- 로컬 프로덕션 빌드(실측, 로컬):

  | | 수정 전 | 수정 후 |
  |---|---|---|
  | 공연 페이지를 열 때 | `/api/events/1` | `/api/events/1` + 대기열 화면 미리 받기(RSC·JS) |
  | 예매하기 클릭 뒤 | 대기열 RSC(web 서버 렌더) + JS + `/api/events/1`(web → api) + 진입 API | **진입 API만**(+ 비로그인이라 생긴 토큰 갱신) |
  | 대기열 화면 직접 진입 | 서버 렌더 | 정적 200 + 공연 정보 1회 |

  - 수정 뒤 클릭 측정은 창 포커스 변화 없이 페이지 안 클릭만 일으켜 그 뒤 리소스 항목을 봤다(포커스 재조회와 분리).
  - 디스크 캐시를 끈 뒤: 같은 id 두 번째 요청 `x-nextjs-cache: HIT`, `123`·`abc` 요청 뒤에도 `.next/server/app/events/` 아래 파일이 생기지 않았다.
- CI: E2E(Playwright 풀스택)·프론트(하네스 → lint → build) 통과. web 단위 테스트 39건 통과(로컬).
- **검증하지 못한 것**: 클러스터에서 web·api 부하가 실제로 줄었는지. 같은 날 B 구성 10만 판정([[IMP-035]])도 진입·상태 조회 API만 쳤다.

## 남은 한계 — 공연 페이지 쪽 부하는 그대로
- 공연 상세의 "예매하기"는 오픈 전(`SCHEDULED`)에는 꺼져 있고, 화면에 상태를 자동으로 바꾸는 폴링·카운트다운이 없다. 오픈 전에 들어와 있던 사용자는 버튼을 켜려면 다음 중 하나를 거친다.
  - 창 포커스 재조회(react-query 기본 `refetchOnWindowFocus`): `/api/events/{id}`가 web → api로 간다.
  - 새로고침: `/events/[id]`는 동적 경로라 web 서버 렌더 + 공연 조회 web → api.
- 그래서 증상에서 계산한 것과 같은 크기의 부하(web·api 각각 초당 약 1만 건 — 계산)가 **오픈 순간 공연 페이지 쪽에 남는다.** #436은 "클릭 → 대기열 화면" 구간만 없앴다.
- 고치려면 공연 상태를 알리는 방식(정적 오픈 시각 + 클라이언트 카운트다운 등)을 바꿔야 한다 — 별도 과제.

## 재발 방지
- 부하 시험 범위를 적을 때 "어떤 API를 쳤나"와 함께 **"사용자 흐름의 어느 단계가 시험 밖인가"**를 쓴다. [[IMP-035]] §8에 공연 페이지 web 경유 부하를 시험 밖으로 명시했다.
- "web을 건너뛴다" 같은 경로 설계는 API 목록이 아니라 **브라우저 네트워크 기록**(프로덕션 빌드, 버튼 클릭 단위)으로 확인한다.
- 처음 요청 때 정적 생성을 쓰는 페이지를 새로 만들면 디스크 캐시 설정(`isrFlushToDisk`)을 함께 본다 — 현재 이 방식은 대기열 화면 하나뿐이다.

## 부록 — 측정 전에 반박된 가설: "web의 연결 재사용 때문에 api 파드 일부로 쏠린다"(#435)
- **배경**: [[IMP-034]] §6에서 예매 중 api CPU가 0.02~0.08코어로 낮았다. 파드 전체가 한가했는지 일부만 일을 받았는지는 기존 내보내기(경로별 요청 수만 있음)로 가를 수 없었다.
- **처음 세운 가설**: web(Next rewrite)이 api Service로 가는 연결을 재사용하면, kube-proxy는 연결 단위로 파드를 고르므로 요청이 일부 api 파드에 쏠린다.
- **반박(G1, 측정 전)**: Next 14.2.15의 외부 rewrite는 `proxyRequest`에서 agent 없이 http-proxy를 써서 요청마다 `Connection: close`로 새 연결을 연다(`next/dist/server/lib/router-utils/proxy-request.js`, 컴파일된 http-proxy 코드).
  - 로컬 재현: keep-alive 클라이언트 20요청 → 백엔드 연결 20개.
  - 운영 Node 20에서도 같다는 것은 추론이다(그 환경에서는 재현하지 않음).
- **순서**: 첫 커밋(`eb8b3b7`)은 이 가설을 전제로 질의를 넣었다(제목 "… 연결 재사용 쏠림 확인용"). 그 PR의 G1이 전제를 반박했고, 정정 커밋(`eab66a4`)에서 질의는 남긴 채 주석·PR 본문의 목적을 **분배 실측·AZ 거리 구분용**으로 고쳤다(커밋 제목은 히스토리를 다시 쓰지 않고 본문에서 정정).
- **그 뒤 관측**: [[IMP-035]]에서 대기열 진입(ALB → 대기열 파드 직결)은 6개 파드에 고르게 갔다(1분 rate 최댓값 369.8~370.7/s). 이건 web을 거치지 않는 경로다. 가설의 대상인 **web 경유 예매 분배는 아직 실측하지 않았다**(그 run에 예매 묶음이 없음).
- **배운 점**: 원인 후보를 코드에 박기 전에 그 전제(연결 재사용)가 실제 런타임 코드에서 성립하는지 먼저 확인한다. 이 경우 머지·측정 전에 반박돼, 측정 결과를 잘못된 전제로 읽어 "쏠림을 확인했다"고 결론 내리는 것을 미리 막았다. 다만 질의를 넣은 첫 커밋 시점에는 전제를 확인하지 않았다.
