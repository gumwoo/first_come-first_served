# TS-018 · 동기화가 500인데 데이터는 다 들어왔다 — ALB idle timeout에 끊긴 장시간 요청

- 슬라이스: S02(KOPIS) · S09(배포)
- 날짜: 2026-08-08
- 유형: 배포 환경 결함(API 설계) — **로컬에서는 재현되지 않음**
- 관련: [[TS-016]]·[[TS-017]](같은 배포에서 나온, 같은 성격의 결함)
- 상태: 원인 규명 완료 — **수정은 하지 않음**(§6)

## 1. 증상

배포 후 데모 데이터를 채우려고 관리자 동기화를 호출했다.

```
POST /api/admin/sync/kopis
→ 원격 서버에서 (500) 내부 서버 오류
```

**그런데 데이터는 들어와 있었다.**

```
GET /api/events → total: 1962   (실제 KOPIS 공연)
GET /api/events/1678/seats → 좌석 100석
```

## 2. 조사

**로그에 예외가 없었다.** 마지막 줄이 정상 완료 로그였다.

```
INFO KopisUpserter : [kopis] upsert 완료 1962건(수집 2129건, 조회 1회)
(이후 아무것도 없음 — 스택트레이스도, 시딩 실패 경고도 0건)
```

처음 확인했을 때 `event 1678`의 좌석은 **0석**이었는데, 잠시 뒤 다시 보니 **100석**이었다.
→ **요청이 끝난 뒤에도 서버는 계속 일하고 있었다.**

```
event 1 / 100 / 500 / 1000 / 1678  →  전부 좌석 100석, 시딩 실패 0건
```

## 3. 근본 원인

`POST /admin/sync/kopis`는 **동기 방식**으로 이 전부를 한 요청 안에서 처리한다.

```
KOPIS 수집 2129건 → upsert 1962건 → SeatSeeder가 1962개 이벤트에 좌석·가격 생성
                                     (이벤트당 100석 + 4가격 ≈ 20만 insert, db.t4g.micro)
```

**ALB의 기본 idle timeout은 60초다.** 그 안에 응답이 시작되지 않으면 ALB가 연결을 끊고
클라이언트는 5xx를 받는다. **서버 스레드는 그와 무관하게 계속 실행된다.**

즉 **"실패한 것처럼 보이지만 성공한" 요청**이다.

## 4. 왜 로컬에서는 안 드러나나

**로컬에는 ALB가 없다.** 브라우저나 curl이 직접 앱에 붙으므로 응답이 늦어도 그냥 기다린다.
프록시가 끼는 배포 환경에서만 나타난다.

> 이 배포에서 **세 번째로** "로컬에서 재현되지 않는" 결함이다 —
> [[TS-016]](Kafka 기동 의존), [[TS-017]](OAuth 콜백 미프록시)에 이어서다.
> 셋 다 **첫 배포 당일**에 나왔다.

## 5. 이 결함이 나쁜 이유 — 실패보다 애매하다

| | 이 경우 |
|---|---|
| 클라이언트 | 500을 받고 **실패로 판단** → 재시도할 수 있다 |
| 서버 | 계속 실행 → **중복 실행 가능** |
| 로그 | 예외가 없어 **원인을 찾을 단서가 없다** |
| 진행률 | 알 방법이 없다 |

실제로 재시도했다면 `SYNC_IN_PROGRESS`(409)로 막혔겠지만(`KopisSyncService`에 락이 있다),
**그건 우연히 막힌 것이지 이 문제의 해결이 아니다.**

## 6. 수정하지 않은 이유와, 고친다면

**이번 범위에서 고치지 않았다.** 데모 데이터는 이미 들어왔고, 고치려면 API 설계를 바꿔야 한다.

고친다면 방향은 셋이다.
1. **비동기 잡 + 상태 폴링** — `202 Accepted` + `GET /admin/sync/kopis/status`. 정석이지만 가장 크다.
2. **ALB idle timeout 상향** — `alb.ingress.kubernetes.io/load-balancer-attributes`로 늘린다.
   증상은 미루지만 원인은 그대로다(더 오래 걸리면 또 난다).
3. **작업 분할** — 좌석 시딩을 동기화에서 떼어 별도 엔드포인트/배치로.

**1번이 옳지만 지금 급하지 않다.** 이 엔드포인트는 관리자 전용이고 데모에서 한 번 부르면 된다.
열어 둔 상태임을 여기 남긴다.

## 7. 교훈

1. **"500을 받았다"가 "실패했다"는 아니다.** 프록시 뒤에서는 클라이언트가 보는 것과 서버가 한 것이 다를 수 있다 —
   **로그와 데이터로 확인해야 한다.** 이번엔 로그에 예외가 없다는 사실 자체가 단서였다.
2. **장시간 동기 요청은 프록시 앞에서 설계가 아니다.** 로컬에서 되니까 넘어간 것이 배포에서 드러났다.
3. **처음 본 좌석 0석이 "시딩 실패"가 아니라 "아직 도달 안 함"이었다.** 한 번의 관측으로
   단정했다면 없는 버그를 쫓았을 것이다 — 시간차를 두고 다시 본 것이 갈랐다.
