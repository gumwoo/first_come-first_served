## 1. 상황 (Context)
[[ADR-023]] §2로 대기 상태 전달을 폴링 주 경로로 옮겼다(대기열 SSE 제거 — #351). 그러면 대기자 전원이 상태 조회를 주기적으로 부른다.
대기 10만 명이 서버가 정한 간격(`retryAfterMs`, 앞쪽 2초 ~ 뒤쪽 30초)으로 물으면 약 3,500 req/s다(계산값 — #349).
같은 Redis(단일 스레드 `cache.t4g.micro`)가 진입 burst에서 이미 0.86~1.02코어였으므로([[IMP-027]]), 조회 1건의 비용이 대기 중 부하를 정한다.

## 2. 문제 정의 + 분류
상태 조회 1건(`GET /queue/status`)이 Redis를 6번 왕복한다 — 메타(HGETALL)·입장 키(EXISTS)·입장 만료(ZSCORE)·순번(ZRANK)·전체 수(ZCARD)·순번(ZRANK 한 번 더).
- 계층 분류: 캐시·외부 저장소 왕복(Redis) / 애플리케이션 코드(같은 값을 두 번 읽음)
- 근거: 코드 경로(`QueueService.status` → `statusOf`·`card`·`rankOf`), 측정한 명령 수 6.02/req(아래)

## 3. 증상 (측정된 증거)
- 측정 방법(사전 등록 `status-prereg.md`): 공개 ALB(상태 조회는 ALB → api 직결 — [[ADR-024]]), 노드 9·api 9(노드당 1)·web 2, HPA 고정.
  팔마다 새로 리셋한 공연에 30,000명을 1,000/s × 30초로 진입시켜(정원 100명 입장, 나머지 대기) 대기 토큰을 뽑고,
  그 토큰을 돌아가며 **3,000/s × 45초** 조회(`infra/k6/queue-status-rate.js`, 발생기 1대, 연결 미리 맺기 20초·VU 1,000 고정). 워밍업 1회 + 판정 3회.
  api CPU-ms/req 식은 [[IMP-025]] §3과 같다. Redis 메인 스레드는 `INFO cpu`(2초 간격), Redis 명령 수는 lettuce 명령 수 ÷ 서버 상태 조회 요청 수.

## 4. 가설 (원인 추측 — 검증 전)
- 가설: 같은 판정에 필요한 값을 한 Lua로 한 번에 읽으면 왕복(네트워크·직렬화·Lettuce 처리)이 줄어 api CPU와 Redis 메인 스레드 시간이 함께 준다.
  eventId를 알아야 이벤트 키를 만들 수 있어(Lua 안에서 키를 만들지 않는다는 규칙) 메타 조회 1회는 남는다 → 2왕복.

## 5. 검증 (도구로 확인 → 확정된 원인)
- 명령 분포(before): ZRANK 1.99 · HGETALL 1.00 · EXISTS 1.00 · ZCARD 1.00 · ZSCORE 0.99 /req — 코드 경로대로 6왕복이고, 순번을 두 번 읽는다.

## 6. 조치 (해결)
#349: `status()`는 HGET(eventId) + `STATUS_LUA`(입장 키 → admitExp 점수 > 지금 → 순번 → 전체 수, 판정 규칙은 기존과 같다 — TS-024).
재진입 응답도 같은 Lua를 쓴다. 응답에 `retryAfterMs`(다음 조회 최소 대기)를 더했다(필드 추가).

- 합격식(사전 등록): api CPU-ms/req 중앙값 개선 ≥ T = max(10%, 2 × before 범위 ÷ before 중앙값 = 5.0%) = **10%** → 24.1% 충족,

## 8. 트레이드오프 / 한계 / 다음 개선
- **조건 차이**: after 팔의 api 파드는 #349 반영으로 새로 떴다(대기자 준비 run의 api CPU 5.11 ms/req — before 0.83). before 파드는 앞선 run들로 예열된 상태였다.
  워밍업 1회 뒤에도 after의 api CPU는 r1 0.498 → r4 0.426으로 줄어 예열이 이어진 것으로 보인다(추론) — 예열 차이는 after에 불리한 쪽이다.
  r4는 토큰 수명 때문에 대기자를 다시 준비한 공연(1783)에서 쟀다.
- **측정 도구가 세 번 바뀌었다**: 1~3차 before 시도는 dropped로 무효였다(시작 시 연결 수립, 그리고 응답 순간 지연에 VU가 바닥나 k6가 VU·연결을 늘림 — #350).
  4차부터 연결 미리 맺기 20초·VU 1,000 고정으로 재고, 판정 run은 모두 4차 조건이다.
- **순간 지연**: 수십 초에 한 번 모든 요청이 100~300 ms 늦어지는 구간이 두 팔 모두에 있다(after r3는 VU 1,000으로도 흡수 못 해 무효). 원인은 확인하지 않았다 —
  사용자 결정: 측정 조건으로 p99와 함께 기록하고 최종 시험 뒤 판단.
- 3,000/s 한 rate만 쟀다(대기 10만 명 계산 부하 근처). 재진입·진입 경로는 이 측정과 무관하다.

## 9. 배운 점 (면접 답변용 한 줄)
대기 상태를 SSE에서 폴링으로 옮기면 조회 1건 비용이 곧 대기 중 부하가 되므로, 조회가 같은 값을 두 번 읽으며 Redis를 6번 왕복하는 것을 명령 분포로 확인하고 한 Lua로 2왕복으로 줄여 같은 조건 재측정으로 api CPU −24%·Redis 메인 스레드 −38%를 확인했다 — 측정 도구의 dropped 원인을 원시 데이터로 다시 가른 뒤에야 판정 가능한 조건이 나왔다.
