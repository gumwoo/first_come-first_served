# ADR-021 · 환불도 PG 호출을 트랜잭션 밖에서 한다

- 상태: **Accepted** (구현 완료 / 실 PG 실증은 미실시 — 아래 §한계)
- 날짜: 2026-09-21
- 슬라이스: S06(환불)
- 관련: [[ADR-020]](결제 쪽 같은 결정), [[TS-030]](동시 환불 멱등), [[ADR-011]](환불 정산), [[TS-021]](커넥션 풀), [[TS-028]](PG 타임아웃)

## 맥락

[[ADR-020]]에서 결제 승인을 트랜잭션 밖으로 뺐다. **환불은 그대로 남아 있었다.**

```
BEGIN
  markCancelled(PAID→CANCELLED)
  ── PG 취소 요청 ──────── 최대 10초 ────────
  refunds INSERT / 좌석 복구 / markRefunded
COMMIT
```

문제는 같다. PG 응답을 기다리는 동안 Hikari 커넥션을 쥔다(파드당 5, [[TS-021]]).

환불이 더 까다로운 이유는 [[TS-030]]의 불변식 때문이다. **상태 전이가 refunds INSERT보다 먼저**라,
동시 요청의 패자는 조건부 UPDATE가 0행을 받은 뒤 **승자의 refunds 행을 읽어** 같은 결과를 돌려줬다.
한 트랜잭션이던 때는 그 행이 이미 커밋돼 보였다. 사이에 PG 호출이 끼면 더 이상 그렇지 않다.

## 결정

```
TX1   검증 + 정책 계산 + 원자 전이 PAID→CANCELLED   ← 이 요청이 취소의 주인인지 여기서 갈린다
(밖)  PG 취소 요청
TX2   환불 기록 + 좌석 복구 + CANCELLED→REFUNDED
```

1. **전이가 기록보다 먼저라는 순서는 그대로다**([[TS-030]]). 달라진 것은 둘이 다른 트랜잭션이 됐다는 점이다.
2. **패자는 승자의 기록을 기다린다.** 주문이 CANCELLED인 동안만 기다리고, REFUNDED(다른 키로 끝남)나
   PAID(PG 거절로 되돌아감)가 되면 그 자리에서 환불 불가로 답한다. 상한은 결제와 같은 설정을 쓴다.
3. **PG가 거절하면 취소 전이를 되돌린다**(`revertCancel`). 예전에는 롤백이 대신하던 일이다.
   `markPaid`를 쓰지 않는다 — 그쪽은 `paidAt`을 지금으로 덮어써 결제 시각이 바뀐다.

## 새로 생긴 중간 상태 · CANCELLED

구간을 나누면 **주문이 CANCELLED인 채로 트랜잭션 밖에 놓이는 구간**이 생긴다. 여기서 프로세스가
죽으면 두 가지 모습이 남는다.

| 죽은 시점 | 남는 상태 | 누가 정리하나 |
|---|---|---|
| PG 취소 **뒤**, TX2 전 | 주문 CANCELLED · PG 취소됨 · refunds 없음 · 좌석 SOLD | 정산이 **이어서 끝낸다** |
| PG 취소 **전** | 주문 CANCELLED · PG 승인 살아 있음 | 정산이 **전이를 되돌린다** |

둘 다 [[ADR-011]]의 환불 정산이 맡는다. 그래서 이번에 정산을 두 군데 고쳤다.

- `RefundConverger`는 시작점으로 PAID뿐 아니라 **CANCELLED도 받는다.** 예전에는 조건부 UPDATE가
  0행이면 양보했는데, 그러면 위 첫 줄의 주문은 좌석이 SOLD인 채 영원히 묶인다.
- `RefundReconciliationService`는 PG에 **승인이 그대로 살아 있고**(DONE) 주문이 CANCELLED면
  전이를 되돌린다. 두 번째 줄이다.

**진행 중인 사용자 요청을 가로채지는 않는다.** 정산 후보는 시도 시각이 유예(기본 10분)를 넘긴
것뿐이고 PG 호출의 상한은 10초다([[TS-028]]). 10분째 CANCELLED면 그 요청은 이미 끝난 것이다.

## 고려한 대안

- **환불 시도 행(`refund_attempts`)에 상태를 두고 사가로 만든다.** 중간 상태를 주문이 아니라 시도
  행이 들고, 워커가 이어서 진행한다. 더 정석이지만 사용자 응답이 비동기가 된다(요청은 접수만).
  지금 필요한 것은 커넥션 점유 제거라 여기까지 가지 않았다.
- **PG 취소를 먼저 하고 전이를 나중에 한다.** 전이가 실패하면 되돌릴 수 없는 쪽(돈)이 먼저 움직인다.
  [[TS-030]]의 순서를 뒤집는 것이기도 해서 택하지 않았다.
- **패자를 기다리게 하지 않고 "처리 중"으로 답한다.** [[ADR-020]]에서와 같은 이유로 택하지 않았다 —
  더블클릭 UX가 바뀐다.

## 결과 / 한계 (정직)

- **동작은 한 가지만 바뀐다.** 패자가 승자를 기다리는 시간이 생긴다. 예전에도 조건부 UPDATE가
  승자의 행 락을 기다렸으므로 체감은 비슷하고, 그동안 DB 커넥션을 쥐지 않는다.
- **CANCELLED 중간 상태가 사용자에게 보인다.** 주문 목록에서 PG 취소 응답까지(최대 10초) "취소됨"인데
  환불 기록은 없는 구간이 생긴다. 화면 문구는 손대지 않았다.
- **정산이 만드는 환불 행과 사용자 요청이 만드는 행은 멱등키가 다르다.** 유예(10분) 덕분에 겹치지
  않지만, 겹치면 한 주문에 환불 행이 둘 생긴다. DB 제약으로 막지는 않았다.
- **커넥션 점유 감소는 측정하지 않았다.** [[ADR-020]]과 같다.
- **로컬에서 통합테스트를 돌리지 못했다.** Docker가 없어 동시성·복구 경로는 CI 결과로 판단한다.
