- 슬라이스: `S10`
- 날짜: 2026-10-07
- 유형: 정량(수치) — 용량 검증(before/after 개선 비교가 아니라 사전 등록한 합격식 판정)
- 관련 커밋/PR: 이미지 `2c01c0f`(#346까지 반영). 발생기 연결 미리 맺기 #347
- 벤치 파일: 레포 밖 `artifacts/loadtest/20261005-1440/` — 판정 `s9-burst-10k-{r1,r2,r3}`(워밍업 `s9-burst-10k-warm` 제외), 진단 `s9d-burst-10k-netdiag`·`s9w-burst-10k-warm30`, 사전 등록 `step6-prereg.md`, 운영 기록 `session.log`

## 1. 상황 (Context)
목표는 100,000 users arriving over 10 seconds(target 10,000 req/s)의 대기열 진입이다. [[IMP-025]]·[[IMP-026]]으로 진입 1건의 비용을 줄인 뒤,
api 파드 3개(노드당 1)로 4,000/s가 비포화·5,000/s가 중간이었다 → **R_pod ≈ 1,333 req/s/파드**(단계 6a, [[IMP-026]] §7).
사전 등록(`step6-prereg.md` 6b)대로 필요 용량을 계산하고 그 구성으로 10,000/s × 10초 burst를 재 판정했다(6c).

## 2. 문제 정의 + 분류
10,000/s 진입 burst에 필요한 api 파드·노드 수를 근거 있게 정하고, 그 구성에서 진입이 오류 없이 처리되는지 확인한다.
- 계층 분류: 애플리케이션 처리 용량(api CPU) / Redis(단일 스레드) / 부하 발생기(측정 도구)
- 근거: 6a 램프에서 api 노드 CPU가 먼저 차고(5,000/s 노드 0.69~0.72), Redis 메인 스레드 계산값이 10,000/s에 약 1코어(경계선)였다.

## 3. 증상 (측정된 증거)
- 6b 계산(계산값 — 측정 아님): api 파드 = ceil(10,000 ÷ 1,333 × 1.2) = 9 → 노드 9대(노드당 api 1, 노드 그룹 상한 AZ당 3·합 9 안).
  requests.cpu ≈ 0.70 ms/req × (10,000 ÷ 9) ÷ 1000 ≈ 0.78코어. Redis 메인 스레드 ≈ 0.099 ms/req × 10,000 ≈ 0.99코어.
- 구성(세션 한정 — Git 변경 아님): 노드 그룹 2a·2b·2c min=desired=max=3(m6i.large 9대), HPA api 9/9·web 2/2 고정,
  api Deployment에 노드 단위 분산(hostname maxSkew 1·DoNotSchedule) 패치 → api 노드당 1. `requests.cpu`는 300m 그대로(HPA를 고정해 burst 결과에 영향 없음).
- 부하: 공개 ALB, 진입 POST constant 10,000/s × 10초 = 100,000명, SSE 없음, 발생기 c6i.xlarge 3대(발생기당 사전 할당 3,334·최대 6,668 VU), START_AT 장벽.
  워밍업 1회(제외) 뒤 판정 3회, run마다 새 공연·리셋.

## 4. 가설 (원인 추측 — 검증 전)
- 가설 1: 9파드면 파드당 약 1,111 req/s로 R_pod(1,333) 안이라 api는 비포화다.
- 가설 2: Redis 메인 스레드가 1코어 가까이 차 지연이 늘 수 있다.

## 5. 검증 (도구로 확인 → 확정된 원인)
- 판정식(사전 등록 6c): 오류 0, dropped 0, p95 중앙값 ≤ 1s(잠정 — SLO 미정), 정합성 위반 0.
- Redis 메인 스레드는 `INFO cpu`(`used_cpu_*_main_thread`)를 2초 간격으로 샘플링해 부하 구간 사용률을 냈다.
- 도착은 k6 `entry_arrivals`(iteration 시작)와 송신 추정(`http_reqs` 시각 − `http_req_duration`, 레포 밖 분석 스크립트) 두 가지로 셌다 — §7에서 둘이 달랐다.

## 6. 조치 (해결)
코드 변경 없음. 6b 계산 구성(노드 9·api 9)을 세션 한정으로 사전 확장했다. 측정 중 드러난 발생기 문제는 #347(연결 미리 맺기)로 고쳤다.
사전 확장을 Git(HPA 하한·노드 그룹 desired)으로 고정하는 것은 [[ADR-023]] §1 (c)대로 단계 10에서 정한다 — 평시 9노드 유지는 비용 결정이라 이번에 하지 않았다.

## 8. 트레이드오프 / 한계 / 다음 개선
- **"10만 대응"이라고 쓰지 않는다** — [[ADR-023]] 시험 ⑤의 조건(ALB access log로 서버 도착 [T0, T0+10s) ≥ 100,000, 대기·입장·구매까지)을 아직 재지 않았다. 이 문서는 진입 POST만의 결과다.
- 판정 3회는 연결 지연으로 첫 1초 부하가 약 2천이었던 조건이다. 실제 10,000/s가 첫 1초부터 닿은 조건은 `s9w` 1회뿐이다(p95 331 ms) — 최종 시험에서 판정 3회로 다시 잰다.
- 연결 미리 맺기는 "오픈 직전 이미 페이지에 연결을 가진 사용자" 모델이다. 연결 수는 VU 수(약 1만)라 사용자마다 새 TLS 연결(10만 핸드셰이크)은 재지 않았다.
- Redis 메인 스레드가 85~100%였다(`cache.t4g.micro`, 단일 스레드). r2의 p95 368 ms는 Redis 100% 구간과 겹친다(상관 — 원인 확정 아님). 대기 상태 폴링이 더해지면 같은 Redis를 쓰므로 다음 한계 후보다 — 폴링 측정에서 함께 본다.
- 사전 확장(노드 9·api 9·노드 분산)은 세션 한정이었다. 운영 절차(Git 기반 사전 확장·종료 뒤 축소)는 단계 10에서 정한다.
- r1의 api CPU-ms/req(1.338)가 r2·r3(0.77~0.83)보다 높다. 원인은 확인하지 않았다(첫 판정 run — 예열 차이 가능성, 추론).

## 9. 배운 점 (면접 답변용 한 줄)
파드당 처리 한계에서 필요 파드 수를 계산해 10,000/s burst를 오류 없이 처리했지만, 원시 데이터를 다시 보니 "도착 곡선"이 발생기의 iteration 시작 시각이었고 실제 송신은 연결 수립에 막혀 첫 1초 2천이었다 — 지표가 무엇을 재는지 확인해 발생기를 고친 뒤에야 첫 1초부터 10,000/s가 닿은 조건을 쟀다.
