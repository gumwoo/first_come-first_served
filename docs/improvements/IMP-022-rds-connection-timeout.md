# IMP-022 · Hikari `connection-timeout` 30초 → 3초 — RDS 페일오버 AS-IS/TO-BE 비교

- 슬라이스: S09(EKS 배포) — 인프라·가용성
- 날짜: 2026-08-26
- 유형: 정량(장애 주입 AS-IS/TO-BE)
- 관련: [[TS-037]] §5(결함 후보 도출), §8(개선 실험 분리), [[ADR-012]] §10
- 상태: **측정 완료 · 채택 보류** — 개선이 아니라 **트레이드오프**로 판명(§5). 각 1회 측정
- 증거: `docs/evidence/imp-rds-conn-timeout/{as-is-30s,to-be-3s}/`

## 1. 배경

[[TS-037]]이 RDS 페일오버 중 앱 거동을 재면서 결함 후보를 하나 남겼다.

> `application.yml`의 hikari 블록에 `connection-timeout`이 없어 **Hikari 기본 30초**가
> 적용된다. 커넥션을 못 얻는 상황이 명백한데도 30초를 다 쓴 뒤 500을 준다.

그리고 같은 문서가 **"줄이면 낫다"는 아직 추론**이라고 못박고, 판정 기준 넷을 미리 정했다.

```
사용자 최대 대기시간 감소
+ 장애 구간 실패율이 허용 가능한가
+ DB 복구 후 자동 정상화 유지
+ Hikari가 장시간 고갈되지 않는가
```

이 문서가 그 실험이다.

## 2. 측정 방법

```
공통    EKS 1.35 · m6i.large × 3 · 클러스터 안 k6 · open model · 25 rps · 6분
        워밍업 45초로 기준선 0 확인 뒤 aws rds reboot-db-instance --force-failover
        부하: /events/{id}/seats (DB를 타는 조회)
        측정마다 파드를 새로 기동해 timeout_total을 0에서 시작

AS-IS   connection-timeout 미설정 → Hikari 기본 30초
TO-BE   SPRING_DATASOURCE_HIKARI_CONNECTION_TIMEOUT=3000
```

### 왜 이미지를 다시 굽지 않았나

`application.yml`에 `connection-timeout` 키가 **아예 없어** 처음에는 재빌드가 필요해 보였다.
그런데 Spring relaxed binding으로 환경변수가 그대로 먹는다. 100ms(= Hikari가 거부하는 값)를
넣어 **바인딩 자체를 확정**했다.

```
Property: spring.datasource.hikari.connection-timeout
Value: "100"
Origin: System Environment Property "SPRING_DATASOURCE_HIKARI_CONNECTION_TIMEOUT"
```

거부 메시지가 곧 바인딩 성공의 증거다. 기존 파드가 계속 서빙 중이라 중단은 없었다.
덕분에 CI 사이클 없이 두 조건을 같은 날 잴 수 있었다.

⚠️ ArgoCD `selfHeal: true`가 env 변경을 되돌리므로 실험 중 `automated`를 껐고, 끝난 뒤
원래 정책으로 복구했다.

## 3. 결과

| | AS-IS (30초) | TO-BE (3초) |
|---|---|---|
| 총 요청 | 8,369 | 8,584 |
| 실패 | **181 (2.16%)** | **400 (4.66%)** |
| p95 | 53ms | 3,012ms |
| p99 | 30,006ms | 30,004ms |
| 실패 대기 **총합** | **4,513.9초** | **1,341.1초** |
| 실패 평균 대기 | 24.9초 | **3.4초** |
| 30초 상한을 친 건수 | **146** | **3** |
| 실패 창 | 약 11초 | 약 37초 |
| 파드 재시작 | 0 | 0 |

### 실패 지속시간 분포 — 이 실험의 핵심

```
AS-IS   30초 상한  146건  ← 181건 중 81%
        5~29초       3건
        5초 미만    32건

TO-BE   30초 상한    3건
        5~29초      20건
        2.5~5초    339건  ← 400건 중 85%가 3초 부근
        2.5초 미만  38건
```

**AS-IS 실패 181건 중 146건(81%)이 약 30초를 기다린 뒤 실패했다.**

⚠️ **여기서 더 나가면 안 된다.** 초판은 이 대목을 *"30초를 기다려 성공한 요청은 하나도 없다 —
기다림이 사준 것이 없다"*고 적었는데 **현재 측정으로 증명되지 않는다.**
`rolling-availability.js`는 **실패한 요청만** `dur`을 개별 기록하고, 성공 요청은
`http_req_duration` 집계(p95/p99/max)로만 남는다. 그래서 *"30초 가까이 기다린 뒤 200으로
성공한 요청"*의 개수는 **셀 수가 없다.**

게다가 반대 가능성이 데이터에 실제로 보인다. 실패 요청의 **시작 시각**(`ts − dur`)을 복원하면
이렇다.

```
13:21:18 ~ 13:21:28 (11초)  실패 시작 143건
같은 창에 도착했을 요청     약 275건 (25 rps)
→ 약 132건은 같은 창에 도착했는데 실패하지 않았다
```

그 132건이 **빨리 성공한 것인지, 기다렸다가 커넥션을 얻어 성공한 것인지 구분할 수 없다.**
후자라면 30초 대기는 실제로 무언가를 사준 것이 된다.

**그래서 이 실험이 말할 수 있는 것은 "실패한 요청의 대기 시간"까지다.**
30초 대기가 일부 요청의 성공에 기여했는지는 **확인하지 못했다.**

### 커넥션 풀 — TO-BE에서야 관측이 됐다

```
AS-IS  13:20:29Z  세 파드 0
         ← 49초 공백 (샘플 없음)
       13:21:18Z  60 / 48 / 40

TO-BE  13:31:29Z  pending=22 timeout_total= 46 / 129 / 139
       13:32:01Z  pending= 0 timeout_total=114 / 142 / 142   ← 이후 증가 없음
```

⚠️ **AS-IS에서는 파드를 고정한 수집기로도 장애 구간을 담지 못했다.** 1초 간격인데 49초 동안
샘플이 없다. `/actuator/prometheus` 자체가 응답하지 못한 것으로 보이지만
(Tomcat 스레드가 DB 대기로 묶였을 가능성) **확인하지 못했다 — 추론이다.**

반면 TO-BE에서는 같은 수집기가 `pending=22`까지 잡아냈다. **타임아웃을 줄이자 관측 가능해진
것**은 부수 효과이지 이 실험이 노린 것이 아니다.

두 조건 모두 **풀은 스스로 회복했다** — `pending`이 0으로 돌아왔고 `timeout_total` 증가가
멈췄으며 파드 재시작은 0이었다.

## 4. 판정 — 기준 넷 대조

| 기준 | 결과 |
|---|---|
| 사용자 최대 대기시간 감소 | ✅ 30초 상한 146건 → 3건, 평균 24.9초 → 3.4초 |
| 장애 구간 실패율 허용 가능 | ❌ **2.16% → 4.66%** (2.2배), 실패 창 11초 → 37초 |
| DB 복구 후 자동 정상화 | ✅ 양쪽 파드 재시작 0, 사후 정상 |
| Hikari 장시간 고갈 없음 | ⚠️ **TO-BE만 판정 가능** — `pending` 22 → 0 복귀 관측. **AS-IS는 장애 구간 49초가 비어 판정 불가**(§3), 사후 정상화만 확인 |

**넷 중 하나가 명확히 나빠졌다. 그래서 "개선"이 아니라 트레이드오프다.**

한 축으로 요약하면 이렇다.

```
실패 건수      181 → 400   (+121%)
대기 시간 총합 4,514초 → 1,341초  (−70%)
```

**같은 장애에서 사용자가 태운 총 대기 시간은 70% 줄었지만, 실패를 본 사람 수는 2.2배가 됐다.**
어느 쪽이 나은지는 측정이 아니라 제품 판단이다.

## 5. ⚠️ 채택하지 않는 이유

수치는 3초 쪽이 우세해 보이지만 **지금 채택하지 않는다.**

- **각 1회 측정이다.** 같은 AS-IS 조건을 두 번 쟀는데 실패율이 **1.05%([[TS-037]] §3) →
  2.16%(이번)**로 두 배 차이가 났다. 조건도 달랐지만(노드 5대 → 3대), **이 편차 폭이
  AS-IS↔TO-BE 차이와 자릿수가 같다.** n=1로 4.66%와 2.16%를 비교하는 것은 위험하다.
- **실패 창이 11초 → 37초로 늘어난 이유를 설명하지 못했다.** 페일오버 소요는 두 번 다
  비슷했다(55초 / 45초). 3초 타임아웃이 재시도 압력을 만들었을 가능성을 의심하지만
  **확인하지 않았다 — 추론이다.**
- **TO-BE에서도 30초를 친 요청이 3건 남았다.** `connection-timeout`이 지배하지 않는 다른
  계층(JDBC 소켓 read timeout 등)이 있다는 뜻인데 **분리하지 않았다.**
- **3초라는 값 자체에 근거가 얇다.** 정상 시 p95가 53ms이므로 3초는 충분히 여유롭다는
  정도이고, 5초·10초와 비교하지 않았다.

그래서 `application.yml`은 **이번에 바꾸지 않는다.** 코드 변경 없이 문서와 증거만 남긴다.

## 6. 측정 도구 — AZ 필드는 수 분 지연된다

[[TS-037]] §6이 남긴 AZ 오판 문제의 후속이다. 이번 두 실행 모두 스크립트는
`2c → 2c`, `2b → 2b`로 **전환 없음**을 기록했다. 그런데 AWS 이벤트에는 둘 다 있었다.

```
13:21:19 failover started / 13:21:39 DB restarted / 13:22:14 completed
13:31:29 failover started / 13:31:46 DB restarted / 13:32:14 completed
```

첫 실행 뒤 AZ 필드를 확인했을 때는 여전히 `2c`였고, **약 8분 뒤 `2b`로 바뀌어 있었다.**
즉 `DBInstanceStatus=available`이 된 뒤에도 `AvailabilityZone`은 한참 옛 값을 준다.

**AZ 필드는 페일오버 판정의 1차 근거로 쓸 수 없다.** 이벤트가 근거다 —
스크립트가 "AZ 변경 **또는** `failover completed` 이벤트"로 판정하도록 이미 고쳐 둔 것이
이번에 두 번 다 실제로 구해줬다.

## 7. 한계

- **각 조건 1회**다(§5).
- **중앙값을 재지 않았다.** `handleSummary`가 k6 기본 요약을 대체해 p95·p99만 남는다.
- **AS-IS의 풀 시계열은 이번에도 비어 있다**(§3의 49초 공백).
- **부하 25 rps**다. 선착순 피크와 거리가 멀다.
- **성공 요청의 개별 대기 시간을 기록하지 않았다.** 그래서 *"오래 기다린 뒤 성공한 요청"*을
  셀 수 없고, 30초 대기의 효용을 판정할 수 없다(§3). **이 실험의 가장 큰 공백이다.**
- **재시도 정책을 함께 보지 않았다.** 빠른 실패의 가치는 클라이언트가 재시도하는지에
  크게 의존하는데, 그 경로를 재지 않았다.

## 8. 남은 것

- **성공 요청의 대기 시간을 기록하도록 하네스를 고친다** — §3의 공백을 메우는 유일한 길이다.
  느린 성공(예: `dur ≥ 5초`인 200)을 세는 Counter 하나면 *"기다림이 성공을 사줬는가"*에
  답할 수 있다. **반복 측정보다 이것이 먼저다** — 지금은 n을 늘려도 같은 질문에 답하지 못한다.
- **반복 측정(n≥3)** — §5의 편차 때문에 그다음이다.
- **값 탐색** — 3초 / 5초 / 10초 비교. 실패 창 증가가 값에 비례하는지 본다.
- **실패 창이 늘어난 원인** — 재시도 압력 가설 검증.
- **30초를 치는 잔여 3건** — `connection-timeout` 밖의 타임아웃 계층 분리.
- **Redis 쪽 동일 실험** — [[TS-037]] §8이 함께 남긴 항목이며 타임아웃 계층 분리가 선행이다.
