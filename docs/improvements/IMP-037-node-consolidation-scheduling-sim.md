# IMP-037 · 노드 합치기 스케줄링 시뮬레이션(kwok) — 요청량·분산 규칙 조합별 평시·사전 확장 노드 수

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-20(시뮬레이션 `artifacts/loadtest/kwok-20261020/`, 레포 밖)
- 유형: **시뮬레이션(배치 가능성만)** — 실제 kube-scheduler가 가짜 노드·Pod를 배치한다. 성능(지연·CPU 경합)은 재지 않는다. 노드 수는 시뮬레이션 값, 비용은 그 노드 수에 단가를 곱한 계산값이다.
- 관련: [optimization-targets.md](../deployment/optimization-targets.md)(대상과 제약), [[IMP-034]](P3 — 노드당 대기열 2개가 한 번도 생기지 않음), [[IMP-036]](예매 묶음 순간 CPU), [[ADR-025]](1100m·CA 연동), [[ADR-027]](분리 구조), [[IMP-032]](노드-시간 계산 방식)
- 벤치 파일: 레포 밖 `artifacts/loadtest/kwok-20261020/` — 시뮬레이터 `sim.mjs`, 시나리오 `scen/*.json`, 결과 `out/*.json`·`out/summary.json`, 렌더링한 매니페스트 `rendered.json`

## 1. 상황 (Context)
분리 구조(B)는 평시 노드 5~6대, 오픈 사전 확장 때 9대를 쓴다(IMP-033·034·035 실측). CPU 요청량 1100m 때문에 api·대기열 Pod가 노드를 하나씩 차지한다(m6i.large 할당 가능 1,930m — [[ADR-025]]).
요청량을 낮추면 노드를 합칠 수 있을 것 같지만, [[IMP-034]] P3(대기열 650m + 노드 단위 강제 분산)에서는 노드당 대기열 2개가 한 번도 생기지 않았다. AWS 비용 없이 "어떤 요청량·분산 규칙 조합이면 노드가 몇 대 필요한가"를 계산한다.

## 2. 문제 정의 + 분류
- 계층: 스케줄링(요청량·topologySpread·우선순위 선점)·자동 확장(CA).
- 질문: 성능 기준은 그대로 둔다고 할 때, 배치만으로 평시·사전 확장 노드를 몇 대까지 줄일 수 있는가. 그리고 P3가 왜 합쳐지지 않았는가.

## 3. 측정 방법
- **클러스터**: kwok 공식 이미지 `registry.k8s.io/kwok/cluster:v0.7.0-k8s.v1.33.0`(API 서버·실제 kube-scheduler·kwok 컨트롤러, 로컬 Docker). EKS는 1.35 — 스케줄러 버전이 다르다.
- **노드**: 실제 노드 명세 스냅샷(세션 20261015-nok `g1-pre-nodes-0016.json`)의 m6i.large 레이블·할당 가능량(CPU 1,930m·메모리 7,275,012Ki·Pod 29)을 그대로 쓴 가짜 노드.
- **시스템 Pod**: 실제 Pod 명세 스냅샷(같은 세션 `g1-pre-pods-0016.json`, 53개)에서 flowticket 밖 Pod — 데몬셋은 노드마다 1개를 직접 붙이고(aws-node·kube-proxy·ebs-csi-node·node-exporter, 노드당 요청 180m — 데몬셋의 노드 고정 nodeAffinity는 nodeName으로 대신), 나머지(ArgoCD·ESO·CA·LB 컨트롤러·coredns·metrics-server·Prometheus·Grafana 등)는 스케줄러가 배치. coredns의 분산 규칙은 #431의 노드 단위 강제 분산으로 **바꿨다**(스냅샷의 AZ 선호 규칙을 대체 — 실제 애드온에 AZ 규칙이 남아 있는지는 미확인).
- **Pod 명세에서 뺀 것**: 볼륨·probe·env/envFrom·서비스 계정·nodeName(배치와 무관하거나 가짜 Pod에서 만들 수 없는 것). 요청량·분산 규칙·우선순위·tolerations·affinity는 그대로.
- **앱 Pod**: 현재 main의 overlay 렌더링(`kubectl kustomize k8s/overlays/demo-local`)에서 api·대기열·web 템플릿(요청량·분산 규칙·web 우선순위 −1)을 가져와 시나리오별로 요청량·분산 규칙만 바꿨다.
- **CA 흉내**: AZ마다 노드 1대로 시작 → 약 4초마다(2.5초 대기 → 선점 Pod 재생성 → 1.5초 대기 뒤 판정) 노드가 정해지지 않은 Pod가 있으면 노드가 가장 적은 AZ에 1대 추가(`balance-similar-node-groups: true` — `k8s/cluster-autoscaler/values.yaml`) → 반복(AZ당 3, 합 9). 선점으로 지워진 Pod는 다시 만든다(Deployment가 다시 만드는 것을 흉내). 실제 CA는 Unschedulable 조건과 새 노드에 들어가는지를 따지므로, 이 흉내는 아직 스케줄 전인 Pod 때문에 1대를 더 늘릴 수 있다(§7).
- **순서**: 시스템 Pod → api 3 → web 2 → 대기열 2(평시)를 기다림 없이 연달아 만든다(스케줄러는 우선순위 → 생성 시각 순으로 처리). 평시 배치가 끝난 뒤 대기열을 6으로 늘린다(사전 확장). 스케줄러는 이미 놓인 Pod를 옮기지 않는다.

## 4. 시뮬레이터 검증 — 실측과 맞는가
| 구성 | 시뮬레이션 평시 / 대기열 6개일 때 노드 | 실측 | 맞는가 |
|---|---|---|---|
| 현재(V0 — api·대기열 1100m, 대기열 AZ 분산 선호) | 5 / 9 | 평시 5~6(IMP-034 시작 노드 5, IMP-033 6·5, 입력 스냅샷 6), 사전 확장 9(IMP-035) | 평시는 실측 범위의 하단. 9는 CA 상한(AZ당 3 × 3 — `loadtest.tfvars`)과 같은 값이라 근거로 약하다 |
| IMP-034 P3 재현(대기열 650m + 노드 단위 강제 분산) | 5 / **9**, 노드당 대기열 최대 1 | P3 두 run: 노드 5~**8**(폭증 중 HPA 최대 6), 노드당 대기열 2개 없음 | 노드당 대기열 1은 재현. **노드 수는 시뮬레이션이 1대 많다** — 실제 클러스터는 처음 배치가 달라 대기열 하나가 다른 Pod와 같은 노드에 들어갔을 것(추론) |

P3에서 대기열 노드마다 요청 830m만 차 있어 650m가 하나 더 들어갈 자리가 있었는데도 2개째가 놓이지 않았다. 대기열 명세에서 자원 외의 강제 조건은 노드 단위 강제 분산(`hostname`·`DoNotSchedule`·최대 차이 1) 하나뿐이고, Kubernetes 의미론상 이 규칙은 대기열을 받을 수 없는 api 노드도 "대기열 0개" 도메인으로 센다(nodeAffinityPolicy 기본 Honor — 대기열에 nodeAffinity가 없어 모든 노드가 도메인) — 대기열 노드에 2개째를 놓으면 2 대 0, 차이 2라서 허용되지 않는다.
IMP-034가 추론으로 남긴 원인과 **재현 결과·소거법·의미론이 일치한다**(이 규칙만 선호로 바꾼 반사실 run이나 FailedScheduling 메시지는 수집하지 않았다).

## 5. 결과 — 후보 구성 (시뮬레이션)
| 시나리오 | api 요청 | 대기열 요청 | 대기열 분산 | 평시 노드 | 사전 확장 노드 | 노드당 대기열 최대 | 평시 하루 노드 비용(상시 운영 가정, 계산) |
|---|---|---|---|---|---|---|---|
| V0 현재 | 1100m | 1100m | AZ 선호 | 5 | 9 | 1 | $14.16 |
| S1 | 500m | 1100m | AZ 선호 | 5 | 9 | 1 | $14.16 (0%) |
| S2 | 300m | 1100m | AZ 선호 | **4** | **8** | 1 | $11.33 (−20%) |
| S3 | 500m | 850m | AZ 선호 | 4 | 6 | 2 | $11.33 (−20%) |
| S4 | 300m | 850m | AZ 선호 | **3** | **5** | 2 | $8.50 (−40%) |
| S5 | 500m | 850m | AZ + 노드 단위 **선호** | 4 | 6 | 2 | $11.33 (−20%) |

api·대기열 메모리는 S1~S5에서 api만 768Mi로 낮췄다(메모리는 어느 시나리오에서도 노드 수를 정하지 않았다). 비용 = 평시 노드 × 24시간 × $0.118(m6i.large 서울 — IMP-032와 같은 단가), 이 프로젝트는 상시 운영하지 않으므로 가정 계산이다.

- **api만 500m로 낮추면(S1) 줄지 않는다.** 시스템 Pod와 api가 노드 3대에 먼저 퍼져 각 노드에 1,100m가 남지 않아, 대기열은 여전히 새 노드를 쓴다.
- **api 300m(S2)면 평시·사전 확장 각 1대가 준다.** 줄어든 이유는 대기열 1개가 api 노드에 같이 들어갔기 때문이다(`sim-2a-0` — api + 대기열 + 시스템 Pod 7개, 요청 1,750m). 대기열끼리는 여전히 노드당 1개.
- api 500m(S1)은 20m 차이로 줄지 않았다 — 가장 여유 있는 api 노드(`sim-2b-1`)에서 web을 밀어내도 빈 자리가 1,080m < 대기열 1,100m(나머지 api 노드는 1,000m·670m).
- **대기열 850m(S3·S4·S5)면 사전 확장 노드가 크게 준다** — 대신 노드당 대기열이 2개가 된다. 노드 단위 분산을 "선호"로만 두면(S5) 자리가 없을 때 2개를 막지 못한다.

## 6. 조치
설정은 바꾸지 않는다. 후보별로 검증해야 할 위험을 함께 기록한다.
- **S2(api 300m) — 절감이 있는 후보 중 바꾸는 값이 가장 적다(대기열 요청량·분산 규칙은 그대로).** 분리 구조에서는 api HPA가 3~3 고정이라(queue-split 컴포넌트 패치 — base는 3~9), 1100m를 둔 이유였던 "api 확장 = 노드 확장"(CA 연동, [[ADR-025]])이 api 쪽에서는 필요 없다. 이 전제는 **분리 구조일 때만** 성립한다 — 통합 구조(base)로 돌아가면 300m에서 CA가 동작하지 않던 ADR-025의 문제가 다시 생긴다.
  위험(추론): 줄어든 1대는 api와 대기열이 한 노드(2 vCPU)에 함께 놓인 결과다. 그 노드에서 예매 묶음(1초 최대 1.85코어 — [[IMP-036]], 로컬)과 폴링 폭증(대기열 1분 평균 최댓값 1.58~1.95코어 — 사후 분석)이 겹치면 경합하고, 그 노드 하나를 잃으면 api와 대기열이 함께 빠진다(G1).
  검증: 같은 코어 2개에 api와 대기열을 함께 두고 예매 묶음 + 폴링을 동시에 거는 로컬 실험 → 그 뒤 클라우드(G1 포함).
  **→ 후속 결과([[IMP-038]], 2026-10-20): 동거 시 폴링 p99가 수십 배, 예매 p95가 41~87% 나빠졌고(로컬, 조건당 2회), api–대기열 반친화성으로 동거를 막으면 S2도 5 / 9대로 절감이 사라졌다(시뮬레이션) — S2는 채택하지 않는다.**
- **S3·S4(대기열 850m, 노드당 2개) — 절감은 크지만 성능·가용성 위험이 크다.** 폴링 폭증 초반 대기열 Pod 하나가 1분 평균 최댓값으로 1.58~1.95코어를 썼다(사후 분석 — [optimization-targets.md](../deployment/optimization-targets.md) §2) — 2개가 한 노드(2 vCPU)를 나누면 그 구간에 포화된다(추론). 노드 하나를 잃으면 대기열 2개가 함께 빠진다(G1). HPA 기준(요청량의 60%)은 660m → 510m로 내려간다(계산) — 다만 IMP-034 §6은 650m인 P3에서 "더 일찍 확장"이 일관되게 관측되지 않았다고 적었다. 클라우드 검증 없이는 채택할 수 없다.
- **P3의 교훈을 수정안에 반영**: 노드당 2개를 허용하려면 노드 단위 강제 분산을 빼거나, 도메인 계산에서 대기열을 받을 수 없는 노드를 빼야 한다(예: 대기열 전용 노드 그룹·nodeAffinity로 도메인을 좁힘 — 미검증 설계 후보).

## 7. 트레이드오프 / 한계
- **배치 가능성만 본다.** 지연·CPU 경합·DB 풀은 시뮬레이션이 말하지 않는다.
- **노드 수가 실측보다 1대 많게 나올 수 있다** — P3 재현에서 대기열 6개일 때 9대(실측 최대 8). 이 편향은 S2(8)·S4(5) 등 후보에도 적용될 수 있다(추론 — P3 한 사례에서 나온 차이).
- 스케줄러 버전(1.33 vs EKS 1.35), CA를 단순화(노드가 정해지지 않은 Pod가 있으면 균형 있게 1대씩 추가 — Unschedulable 판정·expander·대기 시간·축소는 흉내 내지 않음, 과증설 가능), 배치 순서 의존, 시스템 Pod 구성은 10/15 스냅샷, PVC·볼륨의 AZ 제약은 뺐다.
- 보지 않은 것: web HPA 2~4 확장(web은 2개로 고정), 롤링 배포 때 추가 Pod(surge)가 들어갈 자리([[ADR-025]]는 surge가 CA 증설을 일으킨다고 적었다), 노드 하나를 잃었을 때 남은 노드로 다시 배치할 여유(G1).
- 같은 시나리오를 한 번씩 돌렸다. 스케줄러 점수가 같을 때의 선택에 따라 결과가 달라질 수 있다.
- 비용은 EC2 노드만, 상시 운영 가정이다. 실제 이 프로젝트는 시험할 때만 클러스터를 띄운다.

## 8. 배운 점 (면접 답변용 한 줄)
"요청량을 줄이면 노드가 합쳐진다"는 계산이 실제 클러스터(P3)에서 틀렸던 이유를, 실제 스케줄러로 같은 조건을 재현해 분산 규칙의 도메인 계산과 일치함을 보였다. 그 시뮬레이터로 후보 구성의 노드 수를 미리 계산해, 절감폭(평시 −20~−40%, 계산)과 그 대가(예매 순간 CPU 경합, 노드당 대기열 2개의 가용성 위험)를 함께 놓고 다음 검증 대상을 골랐다.
