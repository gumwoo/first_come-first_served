# IMP-018 · 사용자 요청이 외부 API 호출량을 증폭시키던 구조 제거

- 슬라이스: `S02` (공연) · `S09` (배포/운영)
- 날짜: 2026-08-10
- 유형: **정성(구조/장애 예방)** — 응답시간 개선은 **주장하지 않는다**(§7 참고)
- 관련 커밋/PR: `33b2d67`(before) → `9930e67`(after) · [PR #199](https://github.com/gumwoo/first_come-first_served/pull/199)
  (선행: [PR #193] 타임아웃, [PR #194] 계측, [PR #198] 레이트 리밋 · 후속: [PR #201] 목록 프로젝션)
- 측정: 클러스터 내부 k6 Job(`infra/k6/k6-job.yaml`) 50 VU / 60s, 파드 3 고정, 조건당 3회 반복

> 흐름: **문제 정의 → 증상(수치) → 가설 → 도구로 검증 → 해결 → 재측정 → 한계**.

## 1. 상황 (Context)

Phase 7 관측 스택을 붙인 직후, 대시보드의 "엔드포인트별 p95"에서 `/events/{id}` 하나만 다른
조회보다 높은 것을 발견했다. 부하 테스트를 하다 찾은 것이 아니라 **평상시 그래프를 보다가** 걸렸다.

## 2. 문제 정의 + 분류

**공연 상세 조회가 요청마다 외부 API(KOPIS)를 동기 호출해, 사용자 트래픽이 그대로 외부 API
호출량으로 증폭되고 있었다.**

- 계층 분류: **외부 API** (요청 경로에 놓인 동기 의존성)
- 왜 그 계층인가: 같은 DB·같은 파드를 쓰는 이웃 엔드포인트는 정상인데 이 경로만 느렸고,
  코드를 보니 `EventService.detail()`이 DB 조회 뒤 `kopisClient.fetchDetail()`을 호출하고 있었다.

**이것은 "상세 조회가 느리다"가 아니라 "부하가 외부 의존성을 증폭시킨다"는 구조 문제다.**
전자는 캐시로 완화되지만, 후자는 호출 주체를 바꾸지 않으면 남는다.

## 3. 증상 (측정된 증거)

- 측정 방법: 클러스터 **내부** k6 Job, 50 VU / 60s, 파드 3 고정.
- before 수치 (이미지 `33b2d67`):

  | 지표 | 값 |
  |---|---|
  | **부하 구간 KOPIS 호출** | **약 22,000건** (k6 실행 구간 약 64초) |
  | 같은 구간에 제한이 허용하는 양 | 초당 10회 × 64초 = **약 640건** |
  | 초과 배율 | **약 34배** |
  | 그중 400 차단 비율 | **99.7%** (별도 회차 실측: 8,105건 중 8,082건) |
  | HTTP 실패율 | **0%** |

  > 초당 환산값을 따로 적지 않는다 — Prometheus `increase` 창(90초)과 k6 실행 구간(약 64초)이
  > 달라 정확한 초당 호출률을 특정할 수 없다. **총량끼리 비교**하는 편이 안전하다.

**마지막 두 줄이 이 문서의 핵심이다.** 외부 호출이 거의 전부 차단됐는데 **HTTP 실패율은 0%**였다.
애플리케이션이 실패를 삼키고 상세 필드가 비어 있는 응답을 **200으로** 반환했기 때문이다.

```
겉보기        : HTTP 200, 에러율 0%
실제          : 외부 상세 수집 실패 → 상세 필드 누락 → degraded response
```

**silent degradation** — **HTTP 실패율만 보면 정상**이었고, 사용자가 받는 내용만 비어 있었다.
(외부 연동 지표를 붙인 뒤에는 400 실패가 드러났다. 바꿔 말하면 **그 지표가 없던 동안에는
어디에서도 보이지 않았다.**) [[TS-020]]·[[TS-017]]·[[TS-019]]에 이은 같은 계열의 실패다.

**유휴 상태와 대비하면 원인이 분명하다.**

```
유휴 시 순차 31회 → 31/31 성공 (평균 82.7ms)
부하 시(50 VU)    → 같은 구간 허용량의 약 34배 → 99.7% 차단
```

우리 트래픽이 곧 외부 호출량이었다.

## 4. 가설 (원인 추측 — 검증 전)

- 가설 1: `/events/{id}`가 요청마다 KOPIS를 호출한다.
- 가설 2: 그 호출량이 트래픽에 비례해 이용 제한을 넘겨 차단당한다.
- 가설 3: 차단이 사용자에게 보이지 않는다(폴백이 200을 반환).

## 5. 검증 (도구로 확인 → 확정된 원인)

- 사용 도구: 소스 추적, 파드 로그, Micrometer 커스텀 지표(`kopis.api.requests`), Prometheus, k6.

**가설 1·3은 확정**됐다. 1은 소스에서 직접 확인했고, 3은 같은 시각의 **HTTP 실패율 0%** 와
대조해 확인했다.

**가설 2는 "확정"이 아니라 "강하게 지지됨"이다.** 근거는 셋이다 — (a) 공식 문서의 이용 제한
(IP당 초당 10회), (b) 부하 구간에서 그 허용량의 약 34배가 나가며 HTTP 400이 집중된 것,
(c) 같은 시각 유휴 순차 호출은 31/31 성공한 것. 다만 우리가 붙인 `cause=http_400` 태그는
**"HTTP 400을 받았다"는 분류일 뿐**이고, KOPIS가 응답 코드·헤더로 "레이트 리밋 초과"라고
알려준 것을 확인한 것은 아니다. **레이트 리밋이 유일한 원인이라고 단정하지 않는다.**

계측이 없었다면 이 문제는 로그를 손으로 grep해야만 보였다. **지표를 붙이는 것이 원인 규명의
전제였다.**

## 6. 조치 (해결)

**캐시를 끼우는 대신, 사용자 요청 경로에서 외부 호출 자체를 제거했다.**

```
AS-IS  사용자 요청 → DB 조회 → KOPIS 상세 호출(동기) → 병합 → 응답
                                    ↑ 트래픽에 비례해 증가

TO-BE  동기화 배치 → KOPIS 상세(5 req/s 제한) → events 테이블 저장
       사용자 요청 → DB 조회 → 응답            (외부 호출 0)
```

- `V16` — `events`에 상세 5개 컬럼 추가(**nullable, 추가만** = Expand-Contract N단계).
- `KopisDetailSyncer` — 미수집(NULL) + 오래된 것을 **오래된 순**으로 회차당 300건 수집.
- `EventService`에서 **`KopisClient` 의존 자체를 제거**.

**lazy cache를 고르지 않은 이유**: 공연 수(1,972건)만큼 "첫 요청"이 있고, 오픈 직후 트래픽이
몰리면 수십 건이 동시에 밖으로 나간다. **트래픽 비례 구간이 그대로 남는다.**

**남은 호출자(배치)에는 레이트 리밋을 걸었다**(PR #198·#199). 실측으로 확인됐다 — 상세 300건
수집이 **60초 / 61초**로 설정값 5회/초와 정확히 일치했다(계산: 300 ÷ 5 = 60초).

## 7. 결과

### 7-1. 확정된 성과 (환경 교란과 무관)

| 지표 | before | after |
|---|---|---|
| **사용자 부하 중 KOPIS 호출**(k6 구간 약 64초) | **약 22,000건** | **0건** |
| 같은 구간 제한 허용량(약 640건) 대비 | **약 34배 초과** | 위반 없음 |
| 사용자 응답의 상세 필드 | 외부 호출 성공 여부에 좌우(400 차단 99.7%) | **사전 동기화된 값을 DB에서 제공** |
| 사용자 경로의 외부 의존 | 1개 | **0개**(`KopisClient` 의존 제거) |
| 외부 API 장애 시 영향 | 사용자 응답 품질 저하 | **이미 동기화된 데이터의 조회는 분리됨**(신규 공연의 최초 수집은 여전히 영향) |

**"트래픽이 늘어도 외부 호출은 늘지 않는다"** — 이제 호출량은 배치 실행량(회차 상한 × 실행
주기)으로만 정해진다.

### 7-2. 응답시간·처리량은 정량 성과로 주장하지 않는다

측정을 세 번 시도했고 **세 번 다 폐기했다.** 결과가 나빠서가 아니라, **측정 방법을 검증하다가
신뢰할 수 없는 데이터임을 확인**했기 때문이다.

```
1차) p95 -90%, 처리량 3배
     → 파드 수 3 vs 7, 워밍업 비대칭 발견 → 폐기

2차) 파드 3 고정, 워밍업 동일 → 상세 거의 변화 없음, 이웃 +59%
     → 조건당 1회 측정이라 편차와 구분 불가 → 폐기
     → "이웃이 느려진 건 TEXT 컬럼 때문"이라는 가설도 EXPLAIN으로 기각
        (쿼리 형태별 0.1~0.2ms, 전부 캐시 히트)

3차) 조건당 3회 반복
     → 동일 이미지·동일 파드 수인데 AS-IS 처리량이 591 rps(2차) ~ 1,613 rps(3차)로 요동
     → 30초 워밍업 후에도 1→2→3회차 계속 개선(912 → 1,531 → 1,613 rps)
        = steady state 도달 여부 불명확
     → 현재 환경에서 인과 비교 불가 판정
```

**현재 환경에서 확정할 수 있는 것은 여기까지다.**

- 같은 이미지·같은 파드 수인데 측정 세션에 따라 처리량이 **2.7배**까지 흔들린다.
- 30초 워밍업으로는 steady state에 도달하지 못한다.
- k6가 애플리케이션과 **같은 클러스터 자원을 공유**한다.
- 시간차 A/B라 JIT·캐시·노드 상태·AWS 환경·**KOPIS 차단 강도**를 고정할 수 없다.

**t3 버스터블이 원인이라고 단정하지 않는다.** CPU 크레딧 잔량은 76~91로 충분했고 앱 CPU도
1~3%였다. [[ADR-012]] §5가 부하테스트에 비버스터블을 요구하지만, **그것만으로 관측된 차이를
설명했다고 말할 근거는 없다.**

성능 수치가 필요하면 **측정 환경을 먼저 갖춰야 한다** — 비버스터블 노드, k6 격리, 충분한 워밍업.

## 8. 트레이드오프 / 한계 / 다음 개선

- **데이터가 최대 갱신 주기(기본 7일)만큼 낡는다.** 대상 필드(가격 안내·출연진·줄거리·시간
  안내)는 공연 전에 정해져 거의 바뀌지 않아 수용 가능하다. 실시간이어야 하는 좌석 재고는
  우리 DB가 원본이라 무관하다.
- **초기 채움에 여러 회차가 필요하다.** 회차당 300건(약 60초)이라 1,972건을 채우려면 7회차다.
  자동 스케줄만 기다리면 약 7일이므로, 배포 후 수동으로 여러 번 돌렸다.
- **영구 실패 시 굶주림 가능성.** 대상 정렬이 NULL을 앞에 두므로, 상세 조회가 영구적으로
  실패하는 공연이 회차 상한보다 많으면 뒤가 밀린다. "시도 시각"을 성공 시각과 분리해 기록해야
  하며 **아직 넣지 않았다.**
- **성능 측정 환경이 없다.** 이것이 이 프로젝트의 다음 과제다 — 비버스터블 노드 전환,
  부하 생성기 격리, 워밍업 기준 수립.

## 9. 배운 점 (면접 답변용 한 줄)

**"한 엔드포인트만 느린 것을 대시보드로 발견해 파고들었더니, 실제 문제는 지연이 아니라 사용자
트래픽이 외부 API 호출량으로 증폭되어 상대의 이용 제한 허용량을 약 34배 초과하고 있었고, 그 실패가
HTTP 200으로 가려져 사용자만 빈 응답을 받고 있었습니다. 외부 호출을 배치로 옮겨 요청 경로에서
제거했고, 응답시간 개선은 측정 환경의 변동이 결과 차이보다 커서 정량 성과로 주장하지
않았습니다."**

> 이 문서에서 가장 값어치 있는 부분은 §7-2다. 처음 나온 `-90%`를 그대로 실었다면 면접에서
> "파드 수는 같았나요?" 한마디에 무너졌을 것이다. **측정을 세 번 폐기한 것이 손실이 아니라
> 결과다.**
