# ADR-017 · 주문 SSE 구독은 단명 티켓으로 인가한다 — Bearer 대신 URL, 대신 좁고 짧게

- 상태: **Accepted** — 구현·회귀 테스트(`OrderSseTicketServiceTest`). 결정은 2026-08-20에 코드 주석으로
  남겼고, 이 문서는 그 주석과 커밋을 옮겨 정리한 것이다(대안 표의 "쿠키 인증" 행은 정리하면서 덧붙였다)
- 날짜: 2026-08-20
- 슬라이스: S05(결제) / S07(실시간)
- 관련: [ADR-002](ADR-002-queue-design.md)(대기열 토큰 = 자격증명), [ADR-008](ADR-008-kafka-event-backbone-dlq.md)(SSE는 트리거),
  [ADR-015](ADR-015-queue-status-sync-polling-cost.md)(재연결 복구), 커밋 `e715cdf`·`19b279a`

## 맥락

`GET /sse/orders/{id}`에 인가가 없었다. `id`는 순차 정수라 누구나 남의 주문 상태 변화
(`order.paid`, `payment.vbank.deposited`, `order.failed`)를 구독할 수 있었다.

Bearer 토큰을 요구하는 방법은 쓸 수 없다. 브라우저 `EventSource`는 요청 헤더를 붙이지 못한다.
fetch 기반 스트림으로 바꾸면 헤더는 붙지만 브라우저의 **자동 재연결**을 잃는데, 이 프로젝트의
끊김 복구(`onopen` 재조회, ADR-015)는 그 재연결 위에 서 있다.

## 결정

구독 전용 단명 티켓을 URL 쿼리로 싣는다.

```
POST /orders/{id}/sse-ticket   (Bearer 필요, 소유자만 발급)
GET  /sse/orders/{id}?ticket=… (티켓 검증 후 스트림)
```

대기열이 이미 같은 모양이다 — `/sse/queue/{token}`은 추측 불가능한 값 자체가 자격증명이다(ADR-002).

URL에 실리는 자격증명은 접근 로그·리퍼러에 남는다. 그래서 노출의 값을 세 가지로 낮춘다.

1. **전용 타입** — access token이 아니라 SSE 구독에만 쓰이는 JWT 타입(`TYPE_SSE`)이다.
2. **주문 하나에 묶음** — 클레임에 `orderId`를 박고, 검증에서 경로의 주문과 대조한다.
   대조하지 않으면 자기 주문 티켓 하나로 남의 주문을 구독할 수 있어 인가의 의미가 사라진다.
3. **짧은 TTL** — `jwt.sse-ticket-ttl`, 기본 300초.

### 검증 실패 응답

| 경우 | 응답 |
|---|---|
| 티켓 없음 · 서명/타입 불일치 · 만료 | 401 |
| 유효한 티켓이지만 다른 주문 | 403 |

둘 다 2xx가 아니라는 점이 중요하다. `EventSource`는 2xx가 아닌 응답을 받으면 재연결을 포기하고
`readyState`를 `CLOSED`로 바꾼다. 프론트(`useOrder`)는 `CLOSED`일 때만 새 티켓을 받아 다시 연다.
200으로 답하면서 스트림만 닫으면 브라우저가 만료된 티켓으로 끝없이 재시도한다.

일시적 단절(ALB idle timeout 등)은 `CONNECTING` 상태로 브라우저가 알아서 다시 붙으므로
프론트가 개입하지 않는다. 항상 개입하면 끊길 때마다 티켓을 새로 받게 된다.

## TTL이 뜻하는 것

티켓 검증은 **구독을 맺을 때만** 돈다. 티켓이 만료돼도 이미 성립한 스트림은 끊기지 않는다.

```
12:00 발급 → 12:04 연결 성공 → 12:05 티켓 만료 → 12:30까지 스트림 유지
```

즉 `jwt.sse-ticket-ttl`은 **새 구독을 시작할 수 있는 창**이지 노출 상한이 아니다. 성립한 스트림의
수명은 `seat.sse-timeout-ms`(기본 30분, 티켓 TTL의 6배)가 정한다. 배포 환경에서는 ALB idle
timeout(60초)에 연결이 자주 끊겨 재연결마다 티켓이 다시 검증되지만, 그것은 인프라의 부작용이지
이 설계가 보장하는 성질이 아니다 — 하트비트(ADR-015 ②)가 들어가 연결이 유지되면 30분까지 산다.

`userId`는 클레임에 남기지만 검증에서 대조하지 않는다. 발급 시점에 소유자를 확인했고, 서명된
티켓은 변조할 수 없으며, 구독 권한은 `orderId` 하나로 제한되기 때문이다. 누구에게 발급된
티켓인지 추적하는 용도다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| Bearer 헤더 요구 | `EventSource`가 헤더를 붙이지 못한다 |
| fetch 기반 스트림 + 헤더 | 자동 재연결을 잃어 ADR-015의 복구 경로가 사라진다 |
| access token을 쿼리로 | 로그에 남는 값이 전 API 권한을 가진다 — 노출의 값이 너무 크다 |
| 쿠키 인증 | 현재 access token은 메모리 보관(refresh만 httpOnly 쿠키)이라 인증 구조를 바꿔야 한다 |

## 뒤집는 조건

- 스트림 수명 동안의 노출을 제한해야 하는 요구가 생기면, 티켓 만료 시 서버가 스트림을 닫는
  방식이 필요하다(지금은 하지 않는다).
- 주문 외의 개인 데이터 스트림이 늘면, 스트림마다 티켓을 두기보다 공통 구독 인가를 다시 설계한다.
