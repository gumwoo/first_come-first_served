# IMP-033 · 대기열 전용 Deployment(B) vs 통합(A'), 폴링 폭증 중 예매 지연 비교(A'·B 각 2회)

- 관련: [[ADR-027]](대기열 전용 Deployment·A'/B 전환), [[IMP-031]](폴링 폭증이 api 전체를 3→9로), [[IMP-026]](판매 상태 캐시), [[IMP-030]](예매 E2E 시험),

## 1. 상황 (Context)
IMP-031에서 폴링 폭증(상태 조회 7,000/s)이 api 전체를 HPA 3→9로 늘렸다. 좌석·주문·결제를 처리하는 파드가 대기열 때문에 같이 늘고 같은 Tomcat을 나눠 쓴다.
ADR-027은 같은 이미지로 대기열 전용 Deployment를 두고(B), Service 대상만 바꿔 지금 구조(A')와 같은 날 비교할 수 있게 했다. 이 문서는 그 비교다.

## 2. 문제 정의 + 분류
폴링 폭증 중에도 좌석 선점·주문·결제 지연이 지켜지는가, 그리고 그 대가(대기열 지연·비용)는 얼마인가.
- 계층: 스레드·커넥션 풀·파드 확장(HPA·Cluster Autoscaler). 같은 파드 예산(9)을 어떻게 나누느냐의 문제다.

## 3. 측정 방법
- 같은 세션·클러스터·이미지(`2f1f7ff`)·Redis(`cache.m7g.large`, TS-049 조치)·판매 상태 캐시 TTL 1초. 파드 예산 9: A' api 3~9 / B api 3 고정 + 대기열 2~6.
- run 하나(T0 기준): 대기 인구 60,000 진입(1,000/s × 60초) → 전원 폴링 25분, 예매 ①(폭증 전 기준) 100명, 폴링 폭증 7,000/s × 480초, 예매 ②(폭증 중) 100명
  (booking-e2e: 입장→선점→주문→결제, 역할 6개, 결제는 세션 한정 mock). 정합성은 check-correctness(대기열)·check-booking(DB 13개 기대값).
- 1차 판정(사전 등록): run마다 `R = p95(②) / p95(①)`(hold·주문). v2는 가장 보수적인 쌍 `min(R_A') / max(R_B) ≥ 2`(hold·주문 둘 다)면 "B 개선".

## 4. v1: 측정 절차 점검(결과는 판정에 쓰지 않음)
| run | 정합성 | hold p95 ①→② | 주문 p95 ①→② | R hold/주문 |
|---|---|---|---|---|
| A' a1r | 판정 불가 | 1,067 → 702 | 1,130 → 1,076 | 0.66 / 0.95 |
| B b1r | 판정 불가 | 511 → 299 | 268 → 283 | 0.585 / 1.06 |
| A' a2 | 위반 없음 | 329 → 915 | 319 → 1,149 | 2.78 / 3.60 |
| B b2 | 위반 없음 | 292 → 248 | 211 → 218 | 0.85 / 1.03 |

같은 A'의 R이 0.66과 2.78로 갈려, 원시 데이터로 원인을 나눴다. 각 줄에서 관측(실측)과 원인 귀속(추론)을 구분한다.
- **a1r 예매 ①은 예매 경로 첫 실행**: 직전 hold 0건, JIT 7~9초/파드, Hikari 대기 8~35초 → ①이 3배 느려 R이 작아졌다.
- **a2 예매 ②는 폭증 대비 시점이 밀림**: 폭증 토큰 배포 89초로 폭증이 50초 늦게 시작 → ②(T0 고정)가 HPA 새 파드 Ready 직후에 걸려 R이 커졌다.
- **b1r 폭증 p95 483ms(b2 7ms)**: 폭증 +22초에 대기열 파드가 3→2로 줄었고(HPA 이벤트·ALB 대상별 요청, 실측), 남은 웜 파드 2개가 Tomcat busy 200·CPU 약 1.9코어였다.
  ALB 기준 지연은 Spring 타이머 밖(서블릿 진입 전)이었고 부하·Redis·GC는 같았다. 300초 축소 안정화 창이 끝나 축소가 폭증과 겹친 것이 주원인으로 본다(추론, 1회 관측).
- 도구 오류가 난 run(a1)은 판정에서 제외하고 다시 측정했다(a1r, 예매 k6 토큰 처리는 #401). a1r·b1r의 정합성 "판정 불가"는 드라이버의 리셋 간격·감시 시간 설정에서 나왔다.

## 5. v2: 보완한 절차로 잰 A'·B 각 2회(1차 판정)
바꾼 것(v1 분석을 반영해 다시 사전 등록): 시작 api 파드만 워밍업(폭증 중 새 파드는 그대로), 폭증 토큰 미리 배포·예매 ②는 폭증 실행 + 200초,

## 6. 원인 검증: A'의 폭증 중 예매 지연(실측)
Prometheus 파드별 서버 시간(예매 ② 구간: 폭증 실행 + 170~500초, hold·주문·결제 경로).
- 기존 파드·B 값과 구간 정의·처리량: `perpod-analysis.mjs`(`increase()` 방식, 세션 당시 실행).
- 새 파드 값: `increase()`는 새 시계열의 첫 수집 전 값을 세지 않으므로, 새 파드는 원시 누적 카운터로 셌다(새 파드는 폭증 뒤 생겨 누적값 = 받은 예매 요청 전체).
  명령과 출력은 `perpod-raw-counter.sh`로 보존했다.
출처: 세션 중 조회 결과를 `session.log`("[분석 — 파드별 예매 ②(실측)]")에 기록했다.
분모는 Spring이 센 예매 경로 요청(A' 288건, B 296건)이다(클라이언트 기준 비대기열 요청은 run마다 283건, 집계 정의가 다르다).
| | 새 파드(폭증 중 생성) | 기존 파드(워밍업됨) |
|---|---|---|
| A' v2-a1 | 새 파드 6개 중 예매를 받은 5개, 예매 요청 176건(약 61%), 서버 평균 197~1,289ms | 112건, 24~37ms |
| A' v2-a2 | 6개, 175건(약 61%), 242~891ms | 113건, 36~53ms |
| B v2-b1·b2 | 예매 파드는 늘지 않음, 0건 | 296건씩, 46~117ms |
→ A'에서는 폭증으로 늘어난 새 파드가 예매 요청의 약 61%를 받았고, 그 파드들의 서버 시간이 길었다. 새 파드가 JIT 전이라 느렸다는 해석은 v1 분석(a2 새 파드 JIT·Tomcat)에 근거한 추론이다.
B는 예매 파드가 고정이라 이 경로가 없다. B 예매 파드의 서버 평균(46~117ms)은 A' 기존 파드(24~53ms)보다 높다. B는 api 3개가 예매를 전부 받는다.
폭증 480초 서버 처리량(상태 조회, `sum(rate(http_server_requests_seconds_count{uri=~".*queue/status.*"}[480s]))`를 폭증 실행 + 500초 시점에 조회, `perpod-analysis.mjs`)은 네 run 모두 8,396~8,681/s로 비슷했다(기본 폴링 포함, 내보낸 `rate[1m]`의 구간 평균과는 방법이 달라 값이 다르다).

**사후 분석(2026-10-19)**: 새 파드가 느린 이유를 보존된 자원 지표로 좁혔다. 같은 v2 run의 내보내기(`prom/`, 10초 간격, CPU는 `rate[1m]`)와 당시 파드별 원시 카운터 출력(`perpod-raw-counter.sh`)을 맞춰 봤다(`v2-newpod-booking-moment.cjs` → `.txt`, 레포 밖 세션 폴더. 구간 평균판 `v2-newpod-resources.*`는 예매 순간을 희석하므로 쓰지 않는다).
- 예매 ② 요청은 구간 앞쪽에 몰려 있다. 예매 경로 `rate[1m]`가 0이 아닌 표본은 폭증 실행 + 209~259초뿐이다(두 run 모두). 그래서 구간 전체(+200~500초) 평균은 예매 순간을 희석하고, 아래는 예매 순간(+209~259초) 표본으로 본다.
- 관측(실측): 가장 느린 새 파드는 예매가 도착하던 그때 Ready가 된 파드였다(Ready 시점은 `pod_ready`가 처음 1인 표본, ±10초).

  | run | 새 파드 | Ready (폭증 실행 +초) | 예매 서버 평균 | +209초 Tomcat 연결 수 | 예매 순간 CPU (코어) |
  |---|---|---|---|---|---|
  | v2-a1 | swblr | 209 | 1,289ms | 2,527 | 0.65~1.28 (Tomcat 바쁨 스레드 +209초 200 = 기본 상한) |
  | v2-a1 | q79h4 | 209 | 824ms | 807 | 0.95~1.62 |
  | v2-a2 | w8bkm | 194 | 891ms | 1,671 | 표본 없음 |
  | v2-a2 | dvcl2 | 194 | 652ms | 1,572 | 표본 없음(+259초 0.21) |
  | v2-a1·a2 | 그 밖의 새 파드(예매를 받은 7개) | 74~149 | 197~405ms | 25~2,313 | 0.15~0.89 (3개는 표본 1~2개뿐) |
  | v2-a1·a2 | 기존 파드 3개 | 폭증 전 | 24~53ms | 25 | 0.46~0.68 |

  막 Ready가 된 파드에 연결이 한꺼번에 몰렸고(기존 파드는 25개로 일정), 그 순간 예매도 받았다. 다만 연결 수만으로는 갈리지 않는다. j9dc8(Ready +119초)도 +209초에 연결 2,313개였지만 197ms였다.
  v2-a1의 가장 느린 두 파드(swblr·q79h4)는 같은 시각 기존 파드 CPU 0.46~0.68코어보다 높은 값을 보였지만, 덜 느린 새 파드도 그 범위를 넘었다(gm8kn 0.89코어·247ms, q92lf 0.81코어·272ms). CPU만으로도 갈리지 않는다. 요청량은 1.1코어, limit 없음.
- 측정 조건: `hikaricp_connections_pending` 게이지(10초 표본)는 모든 run에서 0이었고, Hikari 대기 합 8~35초가 따로 측정된 v1 a1r에서도 0이었다. 대기 시간·JIT·파드별 RPS(`http_rps_by_uri`는 경로별 합)는 내보내지 않았다.
- 해석(추론): 가장 느린 새 파드에서는 콜드 스타트(첫 실행 비용, 간접 근거는 v1 a1r의 예매 경로 첫 실행 파드에서 관측한 JIT 7.2~9.2초/파드·Hikari 대기 합 8~35초)와 Ready 직후 몰린 대기열 연결 처리가 예매와 같은 순간 겹쳤다. 둘의 몫은 나누지 않았다.
- 참고: B의 예매 파드(api 3)는 같은 구간 Tomcat 바쁨 최대 0·CPU 0.01~0.02코어였다(v2-b1·b2). 3개가 합쳐 296건을 처리했는데도 10초 표본 Tomcat 게이지는 0이었고, 이 게이지는 예매 규모의 부하를 잡지 못한다.

## 7. 판정 결과 해석과 측정 조건
- **운영 관점의 비교**: 현재 설정(파드 예산 9·HPA 정책·구조별 기본 노드)대로 운영했을 때, 2회씩의 관측에서 폭증 중 예매 지연을 B가 지켰다.
  대기열 분리만의 순수 효과를 재려면 노드 수·확장 시점까지 같게 만든 별도 실험이 필요하다.
- **설계 방향(사전 명시)**: 시작 파드만 워밍업한 결정은 A'에 유리했던 왜곡(a1r)을 없애고, 새 파드를 그대로 둔 결정은 A'에 불리하게 작용하는 동작(a2)을 남긴다.
  두 결정 모두 근거가 있고(앞은 측정 절차의 왜곡, 뒤는 A' 구조의 실제 동작), 합치면 판정이 "B 개선" 쪽으로 기우는 설계다.
- **B의 대가**: 폭증 상태 조회 p95 A' 13~18ms vs B 259~523ms(대기열 HPA 상한 6 도달). p99는 양쪽 모두 0.9~2.2초. 노드 비용 약 +15~28%(계산, B는 기본 노드 1~2대 추가).
- B 두 run의 시작 노드는 6·5다. 대기열 파드 배치에 따라 5/6대에서 안정되고 CA가 더 줄이지 않는다.
- v1은 최종 판정에서 제외했다. v2 사전 등록은 첫 run 전에 확정했다(모든 v2 변경은 첫 run 전, 파일 수정 시각 기준).
- 표본은 구조별 2회다.

- **관측 설계(ADR-027)**: B에서 두 Service가 job `flowticket-api` 하나로 수집되고 이중 수집 없음, 대기열 경로 → 대기열 파드(ALB 대상 그룹 `api-queue`)(실측).

## 9. 다음 개선
- **B의 대기열 쪽**: 상한 6 도달·폭증 중 축소(b1r)·비용. 후보는 대기열 파드 CPU 요청 축소(노드당 여러 개), 대기열 파드 DB 풀 축소(DB 예산 안에서 상한 확대), 축소 정책이다. 다음 세션에서 현 B와 같은 세션 비교.
- **A'를 유지한다면**: 폭증 중 새 파드가 예매를 받기 전에 데우는 방법(readiness 워밍업 등)으로 이번 원인(§6)에 직접 대응한다.
- 이 측정 시점의 운영 기본값(Git main)은 A'였고, 전환은 대기열 쪽 개선 뒤 결정하기로 했다(ADR-027). 2026-10-17 갱신: 비용을 감수하고 B를 운영 기본값으로 정했다(B′ 조정 결과는 IMP-034, ADR-027).

## 10. 배운 점 (면접 답변용 한 줄)
같은 A'에서 R이 0.66과 2.78로 갈렸을 때, 원시 데이터로 "예매 경로 첫 실행"과 "폭증 대비 예매 시점"이라는 측정 절차의 왜곡을 찾아 사전 등록을 다시 하고 각 2회 재측정했다.
그 결과 A'에서 폭증 중 HPA가 새로 띄운 파드가 예매의 약 61%를 받았고, 그 파드들의 서버 처리 시간이 기존 파드보다 길었다는 것을 파드별 서버 시간으로 확인했다. 가장 느린 새 파드는 예매 도착과 같은 순간 Ready가 되어 연결이 몰린 파드였다(§6).
