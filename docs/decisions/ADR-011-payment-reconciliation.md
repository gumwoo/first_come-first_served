# ADR-011 · 결제 정산·보상 — 외부 PG ↔ 내부 주문 상태 불일치

- 상태: **Accepted** (S08 2단계 **구현 완료 · 통합테스트 통과** / **실 PG 실증은 미실시** — 아래 §한계)
- 날짜: 2026-07-31
- 슬라이스: S08(정합성 보강 — 2단계)
- 관련: [[ADR-010]](아웃박스·1단계), [[ADR-005]](결제 게이트웨이 포트), [[TS-011]](§7 즉시 보상·§한계), [[ADR-006]](상태 전이 원자화)

## 맥락
`payTx`는 **하나의 트랜잭션**에서 payment 행 생성 → `gateway.approve()` → 주문/좌석/홀드 확정을 처리한다.
여기엔 아웃박스로 닫을 수 없는 구멍이 남아 있다:

```
t0  gateway.approve() 성공          ← 외부 PG에 실제 승인(돈이 잡힘)
t1  좌석 확정 실패 or 프로세스 크래시
t2  트랜잭션 롤백 → payments 행까지 사라짐
    결과: PG=승인 / 우리 DB=흔적 없음(주문은 PENDING·EXPIRED)
```

TS-011 §7에서 `finalizePaid`에 **즉시 보상**(`gateway.refund`)을 넣어 1차 방어를 했지만, **승인 직후·보상
호출 전에 프로세스가 죽는 구간**은 여전히 열려 있다. 그리고 이건 [[ADR-010]] 아웃박스로 못 닫는다 —
아웃박스는 "**DB에 커밋된 사실**을 외부로 전달"하는 패턴인데, 여기선 트랜잭션이 롤백돼 **커밋된 사실도,
적재할 행도 없기** 때문이다. 종류가 다른 문제다.

## 결정
1. **주기적 정산(Reconciliation) 잡을 별도로 둔다.** `PaymentReconciliationService`가 스케줄로 돌며
   "우리는 미확정인데 PG엔 승인"인 **미아 승인**을 찾아 **취소(void)**한다. `@SchedulerLock`으로 단일 실행.
2. **후보는 `orders`에서 만든다.** payment 행은 롤백과 함께 사라지므로 신뢰할 수 없다. 주문은 결제 이전
   트랜잭션에서 이미 커밋돼 **항상 남는다** → `status IN (PENDING, EXPIRED)`인 주문이 후보.
3. **비용은 3중으로 바운드한다.** ① 유예(`grace`, 기본 10분): 결제 제한시각 직후는 아직 진행 중일 수
   있어 건드리지 않는다. ② 소급 한계(`lookback`, 기본 24h): 그 이전은 수동 정산 대상. ③ 배치 상한
   (기본 50): 틱당 PG 조회 수를 고정.
4. **포트에 조회를 추가한다.** `PaymentGateway.inquire(orderId)` → `Inquiry(approved, pgTid)`.
   Toss는 주문번호 조회 API(`/v1/payments/orders/{orderId}`)로 구현하고 **DONE만 승인으로 본다**
   (이미 CANCELED면 대상 아님). **조회 실패는 예외가 아니라 `none()`** — 없는 승인을 만들어내지 않는다.
   Mock은 항상 `none()`이라 평시 데모·테스트에서 아무것도 취소하지 않는다(결정론).
5. **트랜잭션을 걸지 않는다.** 우리 DB를 바꾸지 않고 건별 외부 호출만 하므로, 네트워크 I/O가 DB
   트랜잭션을 붙잡지 않게 한다. 취소 성공 후에도 주문 상태는 그대로 둔다 — 이미 미확정이고 좌석·홀드도
   풀린 상태라 추가 전이가 필요 없다.
6. **실패는 삼키고 다음 틱에 재시도.** 조회·취소 실패 시 주문이 후보로 남아 자연히 재시도된다(멱등).

## 고려한 대안
- **의도 로그(intent log)를 별도 트랜잭션으로 선기록**: PG 호출 전에 `REQUIRES_NEW`로 "시도" 행을 남기면
  후보를 정확히 좁힐 수 있다. 그러나 **결제 핫패스에 쓰기가 하나 늘고**, 그 쓰기 자체가 실패하는 창이 또
  생긴다. 주문이라는 durable 신호가 이미 있으므로 추가 쓰기 없이 후보를 만들 수 있다 → 기각(규모가 커져
  PG 조회 비용이 문제되면 재검토).
- **정산 파일(settlement) 대조**: 실무 정석이지만 PG 계약·파일 포맷·배치 인프라에 의존한다. 데모 범위
  밖 → 기각(운영 전환 시 이 잡을 파일 대조로 승격).
- **아웃박스에 통합**: 대상이 다르다(롤백돼 DB에 없는 외부 부수효과). 억지로 묶으면 "아웃박스가 뭘 보장하는
  패턴인지"가 흐려진다 → 별도 메커니즘으로 분리.
- **즉시 보상만 유지(정산 없음)**: 프로세스 크래시 구간이 영구히 열린 채 남는다. 실 PG라면 돈이 잡힌 채
  방치 → 기각.

## 결과 / 한계 (정직)
- 검증: `PaymentReconciliationIntegrationTest` — 미확정 주문에 PG 승인이 남아 있으면 취소, 승인이 없으면
  무취소, **PAID 주문은 조회조차 하지 않음**(정상 결제 오취소 방지), 유예 안의 최근 주문 미개입.
- **감사 이력 없음**: 취소 사실은 로그로만 남는다(PG 측에는 취소 기록이 남음). 금전 감사 추적이 필요하면
  `payment_reconciliations` 테이블 + 관리자 화면으로 승격해야 한다 — 현재 범위 밖.
- **PG 조회 API 의존**: Toss 주문번호 조회를 전제한다. Mock 구간에서는 항상 "승인 없음"이라 이 경로의
  실제 동작은 실 PG 배선 시에만 확인된다(테스트는 스텁으로 검증).
- ⚠️ **구현과 실증은 다르다 — 이 잡이 실제 미아 승인을 잡아 취소하는 것을 아직 보지 못했다.**
  통합테스트는 게이트웨이를 스텁으로 바꿔 분기를 검증한 것이고, 실 PG에서는 한 번도 돌지 않았다.
  실증하려면 **실 카드 결제로 승인을 낸 뒤 커밋 전에 프로세스를 죽여** 미아 승인을 만들고, 다음 틱에
  `inquire → DONE → refund`가 실제로 일어나는지 봐야 한다(실제 돈이 잡히므로 소액·즉시 취소 전제).
  카드 결제 자체는 이미 실물로 성공시켜 봤으므로(S09 DoD) 배선은 살아 있다.
- **소급 한계 밖은 미처리**: 24시간을 넘겨 발견된 미아 승인은 자동 정산되지 않는다(수동 대상).
- **가상계좌(vbank)**: 입금 완료 후 롤백된 경우의 "보상"은 환불 의미가 달라(입금 반환) 별도 검토 대상.
- **잔여 창**: 정산 주기(기본 10분)만큼은 미아 승인이 PG에 남아 있다 — 완전 실시간이 아니라 **탐지·보상
  지연이 유한하다**는 보장이다.

## 추가 결정 (2026-09-21) · 반대 방향 — 미아 취소

### 맥락

위 §맥락은 "우리는 미확정인데 PG엔 승인"만 다뤘다. **반대 방향이 남아 있었다.**

`refundTx`도 하나의 트랜잭션에서 상태 전이 → `gateway.refund()` → 환불 기록 → 좌석 복구 →
확정을 처리한다. PG 취소가 성공한 뒤 뒤쪽 DB 쓰기가 실패하면 트랜잭션 전체가 롤백돼 주문이
PAID로 돌아간다. 고객은 돈을 돌려받았는데 우리 화면에는 결제 완료로 남는다.

```
PG      = 취소됨
DB      = PAID (환불 흔적 없음, 좌석 SOLD)
```

돈이 이미 고객에게 갔으므로 되돌릴 수 있는 쪽은 우리뿐이다. 미아 승인은 PG를 취소해서 맞추고,
미아 취소는 우리 상태를 환불로 맞춘다.

### 결정

1. **`PaymentGateway.Inquiry`가 상태를 구분한다.** `boolean approved` 하나로는
   "승인 없음"·"이미 취소됨"·"조회 실패"가 모두 같은 값이었다. 그 계약 위에 환불 정산을 올리면
   **PG 조회가 잠깐 죽은 동안 멀쩡한 결제를 환불 처리한다.** `PgStatus`(DONE / CANCELED /
   PARTIAL_CANCELED / NOT_FOUND / UNKNOWN)와 실제 취소 금액을 함께 돌려준다.
2. **`RefundReconciliationService`가 PAID 주문을 후보로 PG에 묻는다.** 환불 시도는 롤백되면
   흔적을 남기지 않으므로 다른 후보 축이 없다. 취소(`CANCELED`/`PARTIAL_CANCELED`)일 때만
   수렴하고, `UNKNOWN`에서는 아무것도 하지 않는다.
3. **금액은 PG 값을 그대로 기록한다.** 환불 시점의 `RefundPolicy`를 사후에 복원할 수 없어
   다시 계산하면 또 어긋난다. 수수료는 결제금액에서 취소금액을 뺀 나머지로 남긴다.
4. **PG 취소 요청에 멱등키를 전달한다.** 사용자 재시도·보상 취소·정산 잡이 같은 승인을 두 번
   취소할 수 있는 경로다. 키는 사용자 환불이 그 요청의 멱등키, 보상·정산은 승인 단위(`void-<pgTid>`).
5. **후보는 마지막 조회 시각으로 돌린다.** 정상 주문은 PG에 물어봐도 PAID로 남는다. 결제 시각
   정렬이면 매 틱 같은 앞쪽 묶음만 다시 뽑혀, 후보가 배치보다 많을 때 뒤쪽 주문은 소급 한계 밖으로
   밀려날 때까지 **한 번도 조회되지 않는다**(starvation). `orders.refund_checked_at`(V19, nullable)에
   조회 시각을 남기고 NULLS FIRST로 정렬해 순회한다. PG 조회에 실패한 건도 표시한다 — 표시하지
   않으면 그 주문이 매 틱 선두로 돌아와 뒤쪽을 다시 굶긴다.
6. **쓰기는 `RefundConverger`로 분리한다.** PG 조회는 트랜잭션 밖, 수렴 쓰기만 짧은 트랜잭션.
   전이 순서는 `RefundService`와 같다(조건부 UPDATE → 환불 기록 → 좌석 → 확정).

### 고려한 대안

- **환불 시도를 먼저 기록하고 그 행만 후보로 삼는다(persisted attempt).** 조회 비용이 환불
  건수에 비례해 훨씬 싸다. 채택하지 않은 이유는 `refunds`의 멱등키 UNIQUE와 상태 전이 순서가
  [[TS-030]]의 동시 환불 불변식을 떠받치고 있어, 그 순서를 바꾸면 같이 재검증할 범위가 커지기
  때문이다. 결제량이 커지면 이쪽으로 옮긴다.
- **PG 웹훅으로 취소를 받는다.** 우리가 만든 취소의 결과를 다시 받는 구조라 순환이고, 웹훅
  유실 시 보장이 사라진다. 정산은 웹훅이 있어도 필요하다.

### 결과 / 한계 (정직)

- **후보가 PAID 전체다.** 유예·소급 한계(24시간)·배치 상한(50)으로 묶었지만 조회 비용이 결제
  건수에 비례한다. 현재 규모에서는 문제가 없고, 커지면 위 대안으로 옮긴다.
- **한 바퀴 도는 시간이 후보 수에 비례한다.** 순회로 starvation은 없앴지만, 후보 500건이면
  배치 50 · 주기 10분 기준 한 바퀴에 100분이 걸린다. 탐지가 늦어질 뿐 누락되지는 않는다.
  재조회 하한(기본 60분)은 같은 주문을 계속 묻지 않게 하는 값이라 이 시간과 함께 봐야 한다.
- **같은 starvation이 `PaymentReconciliationService`에도 있다.** EXPIRED 주문도 조회 후 상태가
  그대로라 후보가 배치를 넘으면 앞쪽만 반복된다. 이 PR에서는 건드리지 않았다(별도 작업).
- **실 PG 실증은 여기서도 미실시다.** 통합테스트는 게이트웨이를 스텁으로 바꿔 분기를 검증한
  것이다. Mock은 항상 `Inquiry.none()`이라 이 경로는 실 PG 배선에서만 실제로 돈다.
- **결제금액을 넘는 취소는 자동 수렴하지 않는다.** 우리 계산으로 설명되지 않는 값이라 ERROR
  로그만 남기고 사람이 본다.
- **감사 이력은 여전히 로그다.** 정산이 만든 환불 행은 `reason`("정산 복구(PG 취소 확인)")과
  멱등키(`recon-refund-<orderId>`)로 구분되지만, 별도 감사 테이블은 없다.
- **잔여 창**: 정산 주기(기본 10분)만큼은 불일치가 남는다.
