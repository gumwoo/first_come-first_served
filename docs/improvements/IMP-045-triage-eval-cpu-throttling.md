## 1. 상황 (Context)
1차 평가([[IMP-044]])에서 AI는 CPU 장애 6회를 모두 다른 원인으로 판정했고, 정상 run 3회를 판단 불가로 냈다. 다음 세 가지를 바꾸고 새 run으로 다시 평가했다.
- 요약에 api 컨테이너가 CPU 할당량에 막힌 주기 비율을 넣었다. cgroup `cpu.stat`(`nr_periods`·`nr_throttled`)을 호스트 cgroup 이름공간의 별도 컨테이너에서 1초마다 읽는다(`api.cgroup.throttled_period_ratio`, 초 단위 최댓값 `throttled_period_ratio_max`).
- 규칙 분류기는 이 비율이 0.2를 넘으면 Redis·DB 갈래보다 먼저 app_cpu로 판정한다. 0.2는 개발용 run(정상 0~0.1, CPU 장애 0.75·1.0)으로 정했다.
- 대조기는 참·거짓 근거를 1·0으로 대조한다. 프롬프트 v4는 새 필드의 뜻과 "근거는 숫자 필드만"을 적고, 정상 기준을 정상 run 9회(cgroup 항목은 6회)의 범위로 넓혔다.
  새 필드 설명에는 할당량에 막힌 컨테이너는 CPU 사용량이 낮게 보이고, CPU 부족은 사용량보다 이 비율로 판단하며, 앱이 CPU를 못 받으면 Redis·DB 지표가 같이 오를 수 있다는 해석(요지)을 함께 넣었다. 4.1의 AI 결과는 이 설명을 받은 상태의 결과다.

## 2. 문제 정의 + 분류
- 계층: 운영 도구(분석). 서비스 코드와 무관하다.
- 질문: 바꾼 뒤 같은 요약에서 AI와 규칙 분류기가 각각 원인을 얼마나 맞히는가. 정상 run을 원인으로 잘못 판정하지 않는가.

## 3. 측정 방법
- 판정 기준은 측정 전에 등록했다(`prereg-eval2.md`, 2026-10-22 14:29:43). 채점 방식과 판정 기준은 1차와 같다.
- 실험실 구성·부하·장애 주입은 1차와 같다(redis 지연 30·60ms, PostgreSQL CPU 0.05·0.03코어, api CPU 0.4·0.25코어).
- 계획: 장애 3종 × 강도 2 × 3회 = 18회, 정상 6회. 실행 순서는 1차와 다른 무작위 순서다. 1차 평가 run과 개발용 run은 쓰지 않았다.
- run마다 직전에 디스크 확인(10초 프로브 중앙값 5ms 이하)을 통과한 뒤 시작했다.
- 채점: 판정이 라벨과 같으면 정답. 판단 불가는 오답으로 세되 따로 집계한다. AI는 유효 run 전부에 불렀고, 근거 수치 대조에 실패한 답은 판단 불가로 처리한다.

측정 경과(`runs.txt`, 14:33~15:30):
- 유효 run 22회: 장애 16회(redis 6, cpu 6, db 4), 정상 6회.
- db 강도 2의 두 칸은 각각 3회 모두 "api 누적 지표가 분석 구간을 감싸지 못한다"로 무효라, 사전 등록대로 결과에서 뺐다. 같은 조건의 나머지 한 칸(ea0d6c11)은 유효였다.
- 측정 환경 사유로 무효였던 run 1회(디스크 프로브 중앙값 20ms)와 측정 대상 쪽 무효 1회(db 강도 1)는 같은 조건으로 한 번 더 찍어 유효였다.
- 사전 등록에 없던 추가 채점: 같은 22회 요약을 모델만 Sonnet 5.5로 바꿔 한 번 더 채점했다(`TRIAGE_MODEL`). 판정 대상이 아니라 참고로만 적는다(4.4).

### 4.1 CPU 장애
- CPU 장애 6회의 할당량에 막힌 주기 비율은 0.23~0.69, 초 단위 최댓값은 6회 모두 1이었다. 정상 run 6회는 비율 0~0.05였다.
- AI는 6회 모두 app_cpu(확신도 high)로 판정했다. 6회 모두 할당량에 막힌 주기 비율과 초 단위 최댓값을 근거로 들었다. 낮은 CPU 사용량은 5회에서 반대 지표 칸에 적으면서 "할당량에 막혀 사용량이 눌린 것"으로 해석했고, 1회(604a72fe)는 근거 칸에 적었다.
- 규칙은 6회 중 5회를 맞혔다. 이 중 2회(2c3f772c, 4fbff263)는 할당량 갈래가 없으면 각각 redis(Redis 명령 완료 평균 5.39ms)·db(PostgreSQL 활성 평균 0.64)로 판정된다(같은 요약에서 cgroup 항목을 빼고 규칙을 다시 돌려 확인).
- 규칙이 놓친 1회(f7c9a769, 강도 1)는 비율 0.23으로 할당량 기준(0.2)을 넘었지만, 예매 p95 중앙값이 1,408ms로 이상 판단 기준(1,500ms)보다 낮아 규칙이 "정상"으로 끝냈다. 파이프라인은 규칙이 정상이면 AI를 부르지 않으므로 이 run도 정상이다.

### 4.2 정상 run 오탐 1회
- 03b615d3에서 AI가 app_cpu(확신도 medium)로 판정했다. 주된 근거는 할당량에 막힌 주기 비율의 초 단위 최댓값 0.55(정상 기준 0~0.18)와 평균 0.05(정상 기준 0~0.02), 같은 초(s=2)의 Tomcat 바쁜 스레드 68·Hikari 대기 스레드 56이었다. 커넥션 획득 대기 평균 278.1ms(정상 상한 253)도 근거로 들었다.
- 이 run의 예매 p95 중앙값은 539ms로 정상 기준 안이고, 규칙은 이상 판단 단계에서 정상으로 판정했다.
- 정상 기준의 cgroup 항목은 정상 run 6회의 범위라, 같은 초에 요청이 몰리는 예매 묶음에서 1초 동안 할당량에 막히는 경우를 덜 담았을 수 있다(추론).

### 4.3 1차 평가 대비(참고)

## 5. 조치
- 원인 판정은 규칙 분류기를 기준으로 두고, AI는 판정과 함께 근거·반대 지표·확인 항목을 정리하는 데 쓰는 경계([[ADR-029]])를 유지한다. 파이프라인(규칙 → AI)의 결과는 장애 15/16, 정상 오탐 0이다.
- 요약에 할당량에 막힌 주기 비율을 넣고, 규칙에 할당량 갈래를 먼저 두는 변경을 채택한다(4.1).
- 기본 모델은 Haiku 5.5로 둔다. Sonnet 5.5 참고 채점은 장애 정답이 같고 비용이 약 12배였다(4.4).
- `eval.mjs`의 공개 단가 표에 Sonnet 5.5를 더해, 모델을 바꿔 채점해도 비용이 계산되게 했다.

## 6. 트레이드오프 / 다음 개선
- 측정 조건: 로컬 상대 비교다. 장애는 세 종류이고, 각 장애를 하나씩만 주입했다. db 강도 2는 1회만 유효였다.
- 다음 개선 후보(각각 새 평가 run으로 다시 잰다):
  - 할당량 갈래를 이상 판단(p95 중앙값 1,500ms)보다 먼저 볼지(4.1의 f7c9a769).
  - 정상 기준의 cgroup 항목을 더 많은 정상 run으로 잡고, 초 단위 최댓값을 근거로 쓸 때 지속 시간도 함께 보게 할지(4.2).
- 기준값과 프롬프트는 이번 평가 run을 보기 전에 고정했다. 위 후보는 이번 run에 맞춰 바꾸지 않았다.

## 7. 배운 점 (면접 답변용 한 줄)
AI가 CPU 장애를 놓친 run의 근거를 추적해 "할당량에 막힌 컨테이너는 사용량이 낮게 보인다"는 빠진 지표를 찾았고, cgroup 통계를 요약에 넣은 뒤 새로 찍은 22회를 사전 등록한 방식으로 채점해 AI가 CPU 장애 6회를 모두 맞힌 것을 확인했다(1차 0/6과는 다른 run 묶음이라 참고 비교).
