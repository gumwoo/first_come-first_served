# IMP-038 · 예매 api와 대기열 동거 경합(로컬) — api 300m 후보의 노드 절감은 동거에서 나왔고, 동거는 경합을 만든다

- 슬라이스: `S10`(부하·확장)
- 날짜: 2026-10-20(로컬 실험 `artifacts/loadtest/local-20261020-l3/`, 시뮬레이션 `artifacts/loadtest/kwok-20261020/` — 레포 밖)
- 유형: 정량(로컬 실측, 조건당 2회) + 시뮬레이션 1건. **같은 로컬 환경 안의 상대 비교**다.
- 관련: [[IMP-037]](노드 합치기 시뮬레이션 — S2 api 300m 후보), [[IMP-036]](예매 묶음 순간 CPU), [optimization-targets.md](../deployment/optimization-targets.md)
- 벤치 파일: 레포 밖 `artifacts/loadtest/local-20261020-l3/` — 사전 등록 `prereg-L3.md`, 구성 `compose.yml`, 실행 `run-l3.sh`, 수집기 `sampler2.mjs`, 요약 `summarize-l3.mjs`, 결과 `out/`(실행 기록 `out/runs.log`). 시뮬레이션 `kwok-20261020/scen/S2a.json`·`out/S2a.json`

## 1. 상황 (Context)
[[IMP-037]]에서 예매 api 요청량을 300m로 낮추면(S2) 평시 5 → 4대, 사전 확장 9 → 8대가 됐다(시뮬레이션). 줄어든 1대는 api와 대기열이 한 노드(2 vCPU)에 함께 놓인 결과였다. 대기열 폴링 폭증과 예매 묶음이 겹칠 때 이 동거가 서로를 얼마나 느리게 하는지 AWS 비용 없이 확인한다.

## 2. 문제 정의 + 분류
- 계층: CPU 공유(같은 노드의 두 Pod) — CPU limit이 없어 요청량은 예약일 뿐, 순간에는 실제 코어를 나눠 쓴다.
- 질문: 동거 시 예매·폴링이 얼마나 느려지는가, 그리고 동거를 막으면 노드 절감이 남는가.

## 3. 측정 방법
- 같은 이미지 컨테이너 2개(예매 api, 대기열), 메모리 상한 2Gi. **분리** = api 코어 2·3 / 대기열 12·13, **동거** = 둘 다 2·3. 조건 전환은 `docker update --cpuset-cpus`로 재시작 없이(JIT 상태 유지). PostgreSQL 6·7, Redis 4, 폴링 k6 5개 코어(8~10·14·15), 예매 k6 1개 코어(11).
- 부하: 대기열에 상태 조회 3,000/s × 90초(대기 토큰 5,000개), 시작 +35초에 예매 api로 입장자 100명 예매 묶음([[IMP-030]]과 같은 `booking-e2e.js` — 이 시나리오의 진입·상태 조회도 api 컨테이너로 보냈다).
- 예열: 본 run 전 같은 부하 1회(결과 제외). 첫 예열에서 폴링 k6가 dropped 535건 → **판정 run 전에** 폴링 k6 코어 3 → 5개, 사전 할당 VU 1,500 → 3,000으로 고치고 `prereg-L3.md`에 시각과 함께 덧붙였다(판정식은 그대로). 두 번째 예열은 예매 공연 좌석이 첫 예열에서 소진돼 예매 없이 폴링만 돌았다(예매 경로 예열은 첫 예열 1회 — 예열이 충분했는지는 확인하지 않았다).
- 판정 run: 분리 I1 → 동거 C1 → 동거 C2 → 분리 I2(교차), 회마다 새 공연·다른 사용자 100명.
- 판정(사전 등록): 동거 쪽 예매 p95(선점·주문·결제 세 단계 p95의 중앙값) 또는 폴링 p99가 짝지은 분리 run(I1–C1, C2–I2)보다 **두 쌍 모두 30% 이상** 나쁘면 "경합 있음". 엇갈리면 "판단 불가".

## 4. 결과 (로컬 실측)

| run | 조건 | 예매 p95 선점·주문·결제(선점은 409 경합 응답 포함, 결제는 의도된 실패 제외) | 세 단계 중앙값 | 폴링 p95 / p99 | 대기열 Tomcat 바쁨 최대 | 예매 구간 12초 CPU 평균 api / 대기열 | 1초 CPU 합 최대 |
|---|---|---|---|---|---|---|---|
| I1 | 분리 | 1,877 · 1,657 · 1,464ms | 1,657ms | 4.8 / 13.1ms | 24 | 0.49 / 1.47코어 | 3.90코어 |
| C1 | 동거 | 2,899 · 2,343 · 1,112ms | 2,343ms | 93 / 1,270ms | **200** | 0.38 / 1.23코어 | 2.22코어 |
| C2 | 동거 | 1,485 · 1,321 · 989ms | 1,321ms | 304 / 587ms | **200** | 0.26 / 1.28코어 | 2.15코어 |
| I2 | 분리 | 775 · 705 · 616ms | 705ms | 4.4 / 10.6ms | 15 | 0.29 / 1.39코어 | 3.69코어 |

모든 run 5xx 0. 폴링 요청 약 273,000건(연결 미리 맺기 3,000건 포함 — 상태 조회만은 약 270,000건, C1만 271,393건 — 지연이 커져 발생기가 1,607건을 보내지 못했다, dropped). 2xx만으로 다시 계산해도 판정은 같다.

- **판정: 예매·폴링 모두 "경합 있음"**(두 쌍 모두 30% 이상 악화).
  - 예매 세 단계 중앙값: I1 1,657 → C1 2,343ms(+41%), I2 705 → C2 1,321ms(+87%).
  - 폴링 p99: I1 13.1 → C1 1,270ms, I2 10.6 → C2 587ms(수십 배) — **90초 전체의 p99**다. 동거 시 대기열 Tomcat 바쁨이 200까지 찼고, 두 컨테이너 CPU 1초 합은 2.15~2.22코어(2를 넘는 것은 측정 간격 오차로 본다)로 코어 2개에 묶였다.
  - 대기열 바쁨 급증은 예매 묶음 밖에서도 나왔다(C1 +35초 68·+48초 133 — 그때 api CPU 0.14코어 이하, C2는 예매 진입 단계인 T0 − 19~−17초에도 200). 폴링 악화를 "예매 묶음과 겹친 탓"으로만 볼 수는 없다 — 코어를 나눈 것 자체의 효과와 예매 묶음과 겹친 효과는 이 설계로 가를 수 없다(§7).
- 같은 분리 조건끼리도 예매 지연이 크게 달랐다(I1 1,657 vs I2 705ms, I1의 예매 api Hikari pending 최대 38 vs I2 4). 예매 쪽 판정은 이 변동 폭 안에서 두 쌍이 모두 같은 방향이었다는 것까지다. 폴링 쪽 차이는 변동 폭보다 훨씬 크다.

## 5. 동거를 막으면 절감이 남는가 (시뮬레이션)
[[IMP-037]] 시뮬레이터에 S2(api 300m) + **api–대기열 노드 단위 반친화성**(`podAntiAffinity` required, hostname)을 넣었다(`scen/S2a.json`).
- 결과: 평시 **5대**, 사전 확장 **9대** — 현재 구성과 같다. S2의 절감 1대는 전부 동거에서 나왔다.

## 6. 조치
- **api 300m(S2) 후보는 채택하지 않는다.** 노드 절감은 api와 대기열이 한 노드를 나눌 때만 생기고(시뮬레이션), 그 동거는 폴링 폭증과 예매 묶음이 겹친 조건에서 폴링 p99를 수십 배, 예매 p95를 41~87% 나쁘게 했다(로컬, 조건당 2회 — 코어 공유 자체의 효과와는 이 설계로 가를 수 없다, §4). 동거를 막으면 절감이 사라진다.
- 시뮬레이션 S2 배치에서는 사전 확장 때 대기열 6개 중 1개만 api 노드에 놓였으므로, 실제 영향은 그 몫으로 제한될 수 있다(추론). 그래도 절감 1대(평시 노드 비용 −20%, 상시 운영 가정 계산)와 맞바꿀 근거는 없다고 판단한다.
- 노드 합치기의 남은 후보는 대기열끼리 합치는 S3~S5(대기열 850m)뿐이고, 이것은 대기열 두 개가 2 vCPU를 나누는 같은 종류의 경합이 예상된다(추론) — 이번 결과로 보면 클라우드 검증 없이 진행할 근거가 더 약해졌다.

## 7. 트레이드오프 / 한계
- 로컬 상대 비교다. 2 vCPU 노드를 코어 고정으로 흉내 냈을 뿐 실제 노드에는 시스템 Pod도 있고, DB 왕복이 AWS보다 짧다. 폴링 3,000/s는 로컬 대기열 컨테이너를 약 1.2~1.5코어(분리 조건, 폴링만 도는 1초 값 중앙값 1.3 내외) 쓰게 하는 부하로 골랐다(AWS 폭증 초반 1분 평균 최댓값 1.58~1.95코어와 같은 규모라는 것은 추론).
- 조건당 2회, 분리 조건끼리의 예매 변동이 크다(§4) — 시간에 따라 빨라지는 흐름이 있었다면 두 번째 쌍의 +87%는 부풀고 첫 쌍의 +41%는 줄어든다(교차 설계라 평균에서는 상쇄).
- 폴링 p95·p99는 연결 미리 맺기 요청(전체의 1.1%)을 포함한 k6 전체 지연이다 — p99가 이 요청들에 민감하다(분리 쪽이 과대 추정됐을 가능성이 커, 실제 배수는 더 클 수 있다 — 추론).
- **동거 조건에서 예매 없이 폴링만 돈 대조 run이 없다** — "코어를 나눈 효과"와 "예매 묶음과 겹친 효과"를 가를 수 없다.
- 동거로 바꿀 때 대기열의 코어 번호도 12·13 → 2·3으로 함께 바뀐다(Docker Desktop의 cpuset은 VM vCPU 기준 — 추정).
- 예매 시나리오의 진입·상태 조회도 api 컨테이너로 보냈다(실제 B에서는 대기열 Pod로 간다) — api 쪽 부하가 실제보다 조금 크다.
- 시뮬레이션(§5)은 [[IMP-037]]의 한계(배치 가능성만, 스케줄러 버전, CA 단순화, 실측보다 1대 많게 볼 수 있음)를 그대로 갖는다.

## 8. 배운 점 (면접 답변용 한 줄)
요청량을 낮춰 노드 1대를 줄이는 후보가 나왔을 때, 그 1대가 "어떤 Pod들이 같은 노드에 앉았기 때문인지"를 배치 결과에서 찾고, 그 동거를 로컬에서 그대로 재현해 폴링 p99가 수십 배 나빠지는 것을 확인한 뒤, 동거를 막으면 절감이 사라진다는 것까지 시뮬레이션으로 보여 후보를 기각했다.
