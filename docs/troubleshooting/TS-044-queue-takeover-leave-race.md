# TS-044 · 재발급·이탈 경합으로 한 회원이 대기열에 두 번 설 수 있었다 — TAKEOVER는 확인 없이 덮어쓰고, 이탈은 유저키를 무조건 지웠다

- 슬라이스: S03(대기열) — 플랫폼 검증 뒤 코드 리뷰에서 발견
- 날짜: 2026-10-09
- 유형: 동시성 결함(확인 후 행동 사이 경합) — 코드 근거로 확인, 운영 재현은 하지 않음
- 관련: `QueueService.issue`·`TAKEOVER_LUA`·`leave`, [[TS-043]](같은 리뷰), [[ADR-002]], 도메인 규칙 S03(1인 1토큰)
- 상태: **해결** — TAKEOVER·이탈에 유저키 CAS, 이탈을 한 Lua로, 통합 테스트로 확인

## 1. 증상 (코드 근거)
1인 1토큰은 발급 때 유저키 `SET NX`로 지킨다. 그런데 이 키를 **덮어쓰거나 지우는** 두 경로가 확인 없이 움직였다.
- **재발급(TAKEOVER)**: 유저키의 토큰이 죽었으면(입장창까지 지나 대기열에 없음) 새 토큰으로 바꾼다. `TAKEOVER_LUA`는 유저키를
  **아까 읽은 값인지 확인하지 않고** `SET`했다. 같은 회원의 요청 여럿이 동시에 "죽은 토큰"을 보면 각자 새 토큰을 만들어 대기열에 넣었고,
  유저키는 마지막 것만 가리켰다 → 나머지 토큰은 주인 키 없이 줄에 남아 **한 회원이 여러 번 섰다**.
- **이탈(leave)**: 메타를 읽은 뒤 슬롯 반환·대기열 제거·메타 삭제를 따로 하고 마지막에 유저키를 **무조건** `DEL`했다.
  그 사이 같은 회원이 새 토큰을 받았으면 새 토큰의 유저키가 지워져, 다음 진입이 `SET NX`에 성공해 활성 토큰이 둘이 됐다.

## 2. 해결
- `TAKEOVER_LUA`: 유저키가 호출부가 읽은 값(없었으면 빈 값)일 때만 덮어쓴다(CAS). 지면 0을 돌려주고, `issue()`가 처음부터 다시 판정한다
  (이긴 요청의 살아 있는 토큰을 그대로 돌려받는다). 재시도 상한 5회 — 한 번 지려면 그 사이 다른 요청이 유저키를 바꿔야 해서 정상 상황은 1~2회다.
  옛 토큰 정리에 대기열 원소 제거(`ZREM`)도 넣었다.
- `LEAVE_LUA`: 슬롯 반환(또는 대기열 제거)·admit 키·메타 삭제·유저키 삭제를 한 원자 단위로 하고, 유저키는 **아직 이 토큰을 가리킬 때만** 지운다.
  슬롯 이중 차감 방지(admitExp에서 실제로 뺀 요청만 감소)는 그대로다.

## 3. 검증
- 통합 테스트(Testcontainers Redis) `QueueTokenRaceIntegrationTest`
  - 죽은 토큰을 30개 요청이 동시에 재발급 → 모두 같은 새 토큰, 유저키도 그 토큰, 대기열 원소 1개, 옛 메타 정리.
  - 이탈 직전 유저키가 바뀐 상황(결정적 재현) → 이탈 뒤에도 바뀐 유저키 유지.
  - 이탈과 재발급을 30회 동시에 겹침 → 회원별 대기 토큰 ≤ 1, 대기 중인 토큰은 항상 유저키가 가리킨다.
- 기존 대기열 테스트(동시 발급 1토큰, 동시 이탈 카운트 음수 없음, 죽은 토큰 회수 재발급, 이탈 후 재발급)는 그대로 통과해야 한다(CI).

## 4. 영향·한계
- 이탈은 Redis 왕복이 메타 1 + Lua 1 = 2로 줄었다(예전: 메타 1 + Lua 1 + 대기열 제거 0~1 + 메타·유저키 삭제 2 = 4~5). 재발급은 경합 때만 재시도가 생긴다. 부하 시험(IMP-029·031)은
  이 변경 전 이미지 결과이며 재측정하지 않았다(이탈·재발급은 진입 burst 경로가 아니다 — 추론).
- 대기 토큰 수명주기(메타가 만료된 토큰이 대기열에 남아 승격되는 문제)는 별도 수정 대상이다. 이 PR은 경합만 다룬다.
