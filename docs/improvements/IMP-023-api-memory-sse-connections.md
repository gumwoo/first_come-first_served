# IMP-023 · api 메모리 한도 1Gi → 2Gi (SSE 대기 연결이 정하는 메모리)

- 슬라이스: 인프라(100K 부하 검증 측정 세션)
- 날짜: 2026-10-06
- 유형: 정량(수치)
- 관련 커밋/PR: `ee6d340`(before) → 이 PR(after)
- 원시 데이터: `artifacts/loadtest/20261005-1440/`(레포에 커밋하지 않는다 — [loadtest-100k-plan §7](../testing/loadtest-100k-plan.md))
- 상태: **after 측정 완료 — OOM은 사라졌으나 단계 6 판정 장애는 그대로**(재시작 원인이 liveness 실패로 이동, §7)

## 1. 상황 (Context)
100K 부하 검증 계획([loadtest-100k-plan](../testing/loadtest-100k-plan.md))의 측정 세션 `20261005-1440`에서
단계 6(S-10K 보호 검증)을 걸었다. 대기열 진입 1만 명(1,000 arrivals/s × 10초, Constant)과 그 대기 토큰의
SSE 연결(50초 유지)을 기본 구성(api HPA 3~7, web HPA 2~4, `m6i.large` 노드 3대 시작·최대 9대)에 걸었다.

## 2. 문제 정의 + 분류
S-10K(단계 6)에서 api 컨테이너가 메모리 한도(1Gi)에 닿아 **OOMKilled**됐고, 재시작한 파드의 감사 로그가
사라져 단계 6의 사후 정합성(실효 입장 초과·대기열 순서)을 판정할 수 없었다. 이 개선의 목표는 **단계 6을 판정 가능한
조건으로 만드는 것**이다. 메모리를 S-10K의 최초 병목으로 확정한 것은 아니다(§5).

- 계층: 애플리케이션 런타임 자원(컨테이너 메모리)
- 1차 근거: 진입 처리 수(1만 건 모두 200)는 손실이 없었는데 SSE 연결 실패와 파드 재시작이 함께 났다.
- 단, OOM(15:18:02·08Z)보다 먼저 진입 지연 p50이 약 2s→5.8s로 오를 때 api CPU 0.10~0.14 core, Hikari pending 0,
  톰캣 바쁜 스레드 200(상한)이었다 — 스레드가 무엇을 기다렸는지는 확인하지 못했다.

## 3. 증상 (측정된 증거)
측정 방법: 발생기 `c6i.xlarge` 1대(클러스터 밖, ALB 공인 경로), k6 2.1.0 + `infra/loadgen/sse-hold.mjs`.
메모리·종료 사유는 Prometheus(kube-state-metrics·cAdvisor)를 run마다 내보낸 값이다.

**단일 Pod(api 1 · web 4 고정, 진입 200/s, SSE 50초 유지)** — 계획서 §6 단계 4 SSE

| 동시 SSE 연결(목표) | 열림 / 시도 | api working set 최대 | OOM |
|---|---|---|---|
| 1,000 | 1,000 / 1,000 | 778MiB(앞 run들을 받은 파드) | 없음 |
| 2,000 | 2,000 / 2,000 | 821MiB | 없음 |
| 3,000 | 3,000 / 3,000 | 1,009MiB(한도 1,024MiB) | 없음 |
| 4,000 | 3,757 / 3,760 | OOM 전 점 356~377MiB — 최고점은 10초 간격 수집에 잡히지 않음 | **OOMKilled**(run 중 — 그 시점 동시 연결은 서버 게이지 마지막 점 3,294, 클라이언트 기준 약 3,493. 진입 burst 중 톰캣 바쁜 스레드 200) |

3,000 연결 run에서 힙 사용 최대 606MiB(힙 한도 742MiB), non-heap 190MiB, 스레드 228, 열린 FD 3,039였다.
**어느 run에서도 힙 사용이 힙 한도에 닿지 않았다**(3,000: 606MiB, 4,000 마지막 점: 559MiB, S-10K OOM 파드 마지막 점: 321·402MiB) —
OOM은 JVM 힙 소진이 아니라 컨테이너 메모리 한도 초과였다.

**S-10K(기본 구성, 진입 1,000/s × 10초, SSE 50초 유지)** — 계획서 §6 단계 6, run `step6-10k_constant-r1`

| 지표 | 값 |
|---|---|
| 진입 | 시작 10,000 · 처리 10,000(전부 200) · dropped 0 |
| 진입 지연 | p50 7.19s · p95 14.26s · p99 16.59s |
| SSE | 열림 9,111 / 시도 10,000(실패 889) |
| api OOMKilled | 3개 중 2개(run 중) |
| 사후 정합성 | 판정 불가(2) — 승격 감사 줄 0건(재시작한 컨테이너의 로그가 수집되지 않음, 추론), run 중 재시작 2 |
| SSE 서버 쪽 | 게이지 최대 5,507 → 재시작 뒤 2,256(클라이언트 "유지" 9,111과 다름) |
| 초과판매 | 0 — 단, 진입 발생기가 입장자를 좌석·주문으로 내려보내지 않아 사실상 검증되지 않음 |
| 실시간 정합성 | 감시기 위반 없음, 사후 재확인(over-admit·초과판매) 위반 없음 |

## 4. 가설
- 가설 1: 연결마다 쥐는 메모리(서블릿 비동기 컨텍스트·응답 버퍼·`SseEmitter`)가 쌓여 1Gi로는 파드당 3,000 연결 안팎이 한계다.
- 가설 2: 끊긴 연결을 서버가 정리하지 않아(같은 세션에서 클라이언트가 닫은 뒤에도 서버 게이지가 수 분 유지 — 실측) 앞 run의
  연결이 메모리를 계속 쥔다. 이 세션에서는 run 사이에 그런 파드를 재생성해 이 효과를 뺐다.

## 5. 검증
- 단일 Pod 사다리에서 연결 수만 바꾸고(진입률·유지 시간 고정) working set이 연결 수와 함께 올라 3,000에서 한도 직전,
  4,000 목표 run에서 약 3,300~3,500 연결 시점에 OOM이었다. 확인된 것은 **"연결 수와 working set이 함께 오르고, 1Gi에서
  3,000 안팎이 한계"까지**다. 힙이 한도에 닿지 않았으므로(§3) 메모리가 힙과 네이티브(스레드 스택·소켓 버퍼 등) 중
  어디에 쌓이는지는 **미확인**이다 — 가설 1의 메커니즘(힙 객체)은 확인하지 못했다. 1,000 run(778MiB)은 앞 run들을 받은
  파드 값이라 깨끗한 점이 아니다. 경계(3,000·4,000)는 각 1회 측정이라 반복이 필요하고, 연결당 메모리 값은 따로 재지 않았다.
- 가설 2(미정리 연결)는 결함 후보로 따로 다룬다(TS로 정리 예정). 이 PR의 범위가 아니다.
- **S-10K에서의 원인 귀속은 확인하지 못했다.** 파드별 SSE 연결 수·OOM 직전 working set 최고점이 기록되지 않았고, OOM 전에
  진입 처리 스레드 포화가 먼저 관측됐다. 그래서 "S-10K의 최초 병목 = 메모리"는 추론이다. 계획서 §3.2의 knee 판정도 아니다.

## 6. 조치
`k8s/base/api-deployment.yaml`: `limits.memory` 1Gi → **2Gi**, `requests.memory` 768Mi → **1536Mi**.
`JAVA_OPTS=-XX:MaxRAMPercentage=75`라 힙 최대는 약 1.5GiB가 된다(계산값).

- 근거와 순서: 단계 4 SSE(단일 Pod)에서 메모리 한도 1Gi가 OOM 지점으로 실측됐고, 단계 6이 그 OOM 재시작 때문에 판정 불가였다.
  계획서 순서상 단계 8은 단계 7(knee) 뒤지만, 단계 7은 단계 6 완료가 전제라 이 조치를 앞당겼다(사용자 승인, 2026-10-06).
- 노드 예산: 변경 전 노드 메모리 예약은 노드당 25~42%(allocatable 약 6.9GiB, `kubectl describe nodes` 한 시점 — 다른 시점 조회는
  25~35%)였다(실측). api 3개 예약이 약 2.3GiB 늘고, HPA 최대 7개면 10.5GiB라 노드 증설(Cluster Autoscaler, `m6i.large`
  최대 9대 안)이 필요할 수 있다(계산값).
- Kafka 브로커 3개는 requests·limits가 없고 실사용이 브로커당 약 0.85~1.0GiB다(검증자 `kubectl top`, 실측). 예약에 잡히지 않는
  메모리라, 예약 기준으로 한 노드에 api 여러 개가 몰리면 실사용 합이 노드 메모리를 넘을 수 있다(계산값). requests를 올려도
  노드 단위 OOM 위험이 사라지지는 않는다 — 요청/한도 비율은 75%로 전과 같고 그 차이는 파드당 256Mi에서 512Mi로 커진다.

## 7. 결과 (재측정 — before와 동일 조건)
같은 workload(S-10K, Constant 1,000/s × 10초, SSE 50초, 발생기 1대·VU 사전 할당 8,000)를 메모리 2Gi 배포 뒤 다시 걸었다
(run `step9-10k_constant-r1`, 측정 세션 20261005-1440, 실측).

| 지표 | before(1Gi, step6) | after(2Gi, step9) | 변화 |
|---|---|---|---|
| api OOMKilled | 3개 중 2개 | 0 | 사라짐 |
| api 재시작 | 2(OOM) | **3(liveness probe 실패)** | 원인만 바뀜 |
| api working set 최대 | (OOM으로 최고점 미기록) | 1,356MiB(한도 2,048) | — |
| 진입 지연 p50 / p95 | 7.19s / 14.26s | 10.71s / 23.04s | 악화 |
| SSE 열림 | 9,111 / 10,000 | 8,941 / 10,000 | 감소 |
| 단계 6 사후 정합성 | 판정 불가 | 판정 불가 | **개선 없음** |

- 재시작 원인(Kubernetes 이벤트): 15:47:34~35Z `Liveness probe failed … context deadline exceeded` → `failed liveness probe, will be restarted`.
  api 3개 모두 종료 코드 143·137. HPA가 api를 7개까지 늘렸다.
- **결론: 메모리 한도는 OOM을 없앴지만 단계 6 판정 장애는 그대로다.** 판정을 막는 재시작이 liveness 실패로 옮겨 갔다.
  후속 조치와 원인 진단(스레드 덤프)은 [IMP-024](IMP-024-api-liveness-under-redis-wait.md).

## 8. 트레이드오프 / 한계 / 다음 개선
- 메모리 예약이 늘어 같은 노드에 들어가는 api 파드가 줄고, HPA 최대까지 늘면 노드가 더 필요하다. 데모 상시 운영 비용도 늘 수 있다.
- 한도를 올리면 `MaxRAMPercentage=75`에 따라 힙 한도도 함께 커져, 늘어난 여유를 힙 확장이 먹을 수 있다(추론). 재시험에서
  힙 committed를 함께 남기고, 한도 증설과 `MaxRAMPercentage` 조정 중 무엇이 맞는지 다시 본다.
- SSE 연결 수에 맞춘 값이지 용량 산정이 아니다. 단계 10(right-sizing)에서 연결당 메모리를 재서 다시 정한다.
- 미정리 SSE 연결(가설 2)을 고치지 않으면 연속된 대기열 이벤트에서 메모리가 누적될 수 있다(추론).
- SSE 유지 50초는 ALB idle timeout(60초 추정, 미확인)을 피하려고 둔 측정 조건이다. 결과는 50초 이하 유지에서만 성립한다.
- 클라이언트 쪽 유지 수(sse-hold)는 서버 쪽 소실을 감지하지 못한다(4,000 run에서 죽은 컨테이너에 붙어 있던 연결도 "유지"로 기록됨) — 유지율·팬아웃 지연은 아직 잴 수 없다.

## 9. 배운 점
진입 처리 건수는 잃지 않았지만(1만 건 모두 200, 다만 진입 p95 14.26s로 SLO 밖) SSE 연결과 함께 컨테이너 메모리가 한도에 닿아 파드가 죽었고, 그 재시작이 정합성 판정의 근거(감사 로그)까지 지웠다 —
연결 수만 바꾼 단일 Pod 사다리로 한계 지점을 먼저 나눈 뒤에야 "메모리 한도"를 고칠 대상으로 지목할 수 있었다.
