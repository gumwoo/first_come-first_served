# ③ 대기열 스파이크 — 정원 상한·순서 보존 (2026-08-12)

티켓 오픈은 **정의상 스파이크다.** 평상시 0에서 순간 수천으로 튀는 그 순간을 위해 대기열이
존재한다. 이 측정은 그 순간에 대기열이 실제로 무엇을 보장하는지를 본다.

## 명제 셋과, 이 측정이 실제로 말할 수 있는 것

| 명제 | 이 자료로 말할 수 있는 것 |
|---|---|
| ① over-admit 0 | **관측된 모든 샘플에서 `admitcount` ≤ 100** (샘플 최대 = 100) |
| ② 순서 보존 | **종료 스냅샷에서 추월 흔적 0** |
| ③ 나머지는 대기 | 3회 중 2회는 3,000/3,000. **1회에서 10건이 깨졌고 원인을 확정했다**([[TS-024]]) |

**표현을 이렇게 제한하는 이유**는 아래 각 절에 적었다. 요약하면 200ms(또는 100ms) 샘플링은
**샘플 사이의 순간값을 배제하지 못하고**, 종료 스냅샷은 **승격을 event-by-event로 캡처한 것이
아니다.** 정합성이 지켜졌다는 정황은 강하지만, "0임을 증명했다"와 "관측 범위에서 0이었다"는
다른 문장이다.

## 설계

```
시드 계정 3,000개 (loadseed+*@example.com, DB 직접 삽입)
  → JWT 3,000개 사전 발급        ← 측정 구간에 로그인(bcrypt CPU)이 섞이지 않게
  → 정원의 30배가 동시에 대기열 진입
  → 진입 중 Redis admitcount 샘플링                    ← 명제 ①
  → 종료 후 wait ZSET의 score 분포 확인                ← 명제 ②
```

**k6 executor는 `per-vu-iterations`(VU당 1회).** 1인 1토큰이라 VU와 사용자가 1:1로 고정되는데,
`shared-iterations`는 전체 iteration을 VU들이 나눠 가져 그 전제가 깨진다(#219에서 같은 실수를
했다).

구성은 Phase 1과 동일 — api HPA 3~7 / web HPA 2~4, 노드 t3.large × 3.
`queue.capacity=100`, `admit-interval-ms=1500`, `admit-ttl=300`.

**매 실행 전 대기열 상태를 비웠고, run-3부터는 정리 직후 잔존을 직접 감사했다.**

```
정리직후 user키=0  token키=0  admit키=0  admitcount=(없음)  wait=0  seq=(없음)
```

## 결과 — 3회 독립 실행

| | run-1 | run-2 | run-3 |
|---|---|---|---|
| iterations | **3,000** | **3,000** | **3,000** |
| 진입 200 | 3,000 / 실패 0 | 3,000 / 실패 0 | 3,000 / 실패 0 |
| `WAITING`/`ADMITTED` | **3,000** | **2,990** (10건 `EXPIRED`) | **3,000** |
| **5xx** | **0** | **0** | **0** |
| 진입 p50 / p95 | 3,964 / 8,466ms | 2,988 / 7,453ms | 4,791 / 11,538ms |
| 샘플 간격 | 200ms | 200ms | **100ms** |

`iterations=3,000`이 매번 찍힌 것이 **VU당 정확히 1회**가 보장됐다는 근거다.
원자료는 `run-{1,2,3}.json`.

### ① 관측된 over-admit 0 — 샘플 최대 100

진입이 진행되는 동안 Redis `queue:admitcount`를 반복 조회했다. **원자료 그대로:**

| | run-1 (200ms) | run-2 (200ms) | run-3 (100ms) |
|---|---|---|---|
| 유효 샘플 | 277 | 277 | 563 |
| `admit=37` | — | **1건** | — |
| `admit=100` | 277건 | 276건 | 563건 |
| **최대값** | **100** | **100** | **100** |
| 최대 대기자 | 2,900 | 2,900 | 2,900 |

**run-2에서 상승 구간의 `admit=37` 샘플 1건을 관측했고, 이후 모든 샘플은 100을 유지했다.**
세 실행 어느 샘플에서도 100을 초과하지 않았다.

```
14:51:54 admit=37  wait=669     ← 상승 중간값(run-2에서만 포착)
14:51:55 admit=100 wait=2225
14:51:56 admit=100 wait=2304
```

⚠️ **"over-admit이 0이다"라고 쓰지 않는다.** 이 방식이 증명한 것은
**관측된 모든 시점에서 `admitcount` ≤ 100**이다. 샘플 사이(100~200ms)에 순간적으로
`101 → 100`이 됐는지는 이 샘플링으로 배제할 수 없다. 그 층위를 닫으려면 Redis 명령 단위 추적이나
승격 경로의 불변식 검사(예: `INCRBY` 직후 값 검증)가 필요하고, **하지 않았다.**

또한 run-1·run-3은 첫 유효 샘플이 이미 100이라 **0→100 상승 구간 자체를 못 봤다**
(run-1 기준 `14:48:43 → 14:48:47`에 4초 공백. 부하 중 `redis-cli` 응답 지연으로 **추정**하며
확인하지 않았다). 상승 구간을 실제로 잡은 것은 run-2의 `admit=37` 한 점뿐이다.

원자료는 `run-{1,2,3}-admitcount-samples.txt`(시각·admit·wait 그대로).

### ② 종료 스냅샷에서 추월 흔적 0

**먼저 잘못 쟀고, 그것을 기록해 둔다.** 처음에는 진입 응답의 `rank`로 재려 했고 "추월 51건"이
나왔다. 그 지표가 틀렸다 — `rankOf()`는 ZSet **위치**를 돌려주는데, 앞사람이 승격돼 빠지면
위치가 밀려 내려간다. 즉 **늦게 도착해도 낮은 rank를 볼 수 있어 도착 순번이 아니다.**

도착 순번은 `score`다. `ISSUE_LUA`가 `INCR seq` 값을 ZADD score로 쓴다.

```lua
local seq = redis.call('INCR', KEYS[2])
redis.call('ZADD', KEYS[3], seq, ARGV[1])
```

승격은 `ZPOPMIN`(최소 score부터)이므로, **순서대로 뽑혔다면 남은 score는 앞쪽만 빠진 연속 구간**
이어야 한다. 종료 후 `queue:wait` 전체를 스냅샷했다.

| | run-2 | run-3 |
|---|---|---|
| 남은 토큰 | 2,800 | 2,900 |
| score 범위 | 201 ~ 3000 | 101 ~ 3000 |
| 연속이라면 개수 / 실제 | 2,800 / **2,800** | 2,900 / **2,900** |
| **구멍(중간 이탈)** | **0** | **0** |
| 앞에서 빠진 구간 | 1 ~ 200 | 1 ~ 100 |

**중간에서 먼저 빠져나간 토큰이 하나도 없다.** 빠진 것은 정확히 앞에서부터다.

⚠️ **"순서 보존을 증명했다"가 아니라 "종료 스냅샷에서 추월 흔적이 0"이다.**
실시간 승격 순서를 event-by-event로 캡처한 것이 아니라 **끝난 뒤 남은 집합의 모양**을 본 것이다.
현재 코드에서 대기열 제거가 앞쪽부터 일어난다는 정황으로는 강하지만, 승격 순간의 순서를 직접
관측한 증거는 아니다. 요약은 `run-{2,3}-wait-scores.json`(토큰 값은 저장하지 않고 score 분포만).

### ③ 나머지는 대기 — 3회 중 2회 성립, 1회에서 결함 발견

run-1·run-3은 3,000건 전부 `200 + WAITING`이다. **2,900명이 정원 밖으로 밀렸지만 아무도 에러를
받지 않았다.**

**그러나 run-2에서 10명이 `EXPIRED`를 받았고, 이 명제는 그 실행에서 깨졌다.**
처음에는 내 측정 절차 탓(수동 정리 시 `queue:user:*` 잔존)으로 **추정**했으나,
**검증해보니 틀렸다** — 정리 직후 잔존은 0이다. 원인은 애플리케이션에 있다.

`QueueAdmissionService.admit()`의 원자 구간이 `ZPOPMIN`에서 끝나고,
"입장했다"를 나타내는 `queue:admit:{token}` 키는 **Lua 밖 Java 루프**에서 만들어진다.
그 사이 토큰은 wait에도 없고 admit 키도 없어 `statusOf()`가 `EXPIRED`로 떨어진다.
전말은 **[TS-024](../../docs/troubleshooting/TS-024-queue-admit-visibility-gap.md)**.

**정합성 결함은 아니다**(정원·순서는 그대로다). 그 사용자는 실제로 승격됐고 잠시 뒤 조회하면
`ADMITTED`다. 틀린 것은 **상태 스냅샷 하나**다. 그래도 진입하자마자 "만료"를 보는 것은
대기열의 계약을 어기는 응답이므로 **미해결로 남기고 Phase 4를 완료 처리하지 않는다.**

## 첫 시도의 5xx 45건 — 실패 지점 특정

**이 측정의 첫 시도(12:10 UTC)에서는 5xx가 45건 나왔다.** 숨기지 않고 원인을 찾았다.

| 시각(UTC) | ELB_5XX | **Target_5XX** | TargetConnectionError | RequestCount |
|---|---|---|---|---|
| **12:10** (첫 시도) | **45** | **0** | **45** | 5,508 |
| 14:40~15:20 (유효 3회) | 0 | 0 | 0 | — |

**`Target_5XX = 0`** — 애플리케이션은 5xx를 낸 적이 없다. 45건 전부 `TargetConnectionError`,
즉 **ALB가 web 파드에 연결하지 못한 것**이고 k6가 센 45와 정확히 일치한다.
AS-IS 측정(`../asis-web2pod/`)에서 본 web 티어 실패와 같은 서명이다.

같은 시점 파드 수:

| 시각 | api | web | 5xx |
|---|---|---|---|
| 12:10 | 7 | **2** (HPA 최소) | 45 |
| 14:52 | 7 | **3** | 0 |

⚠️ **인과는 확정하지 않았다.** web 2파드에서 재현하고 3파드에서 소거하는 통제 실험을 하지
않았다. 확실한 것은 **실패 지점이 앱이 아니라 ALB→web 연결 구간**이라는 것뿐이다.

다만 시사점은 남는다 — run-3은 12초 만에 끝났고 **HPA 평가 주기(15초)보다 짧다.**
**스파이크 대비는 확장이 아니라 최소 파드 수의 문제**로 보인다.

## 측정 과정에서 깨진 것들 (기록)

같은 함정을 다시 밟지 않도록 남긴다. 앞선 회차들이 무효였던 이유다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 샘플러가 250개 전부 `admit=0` | `sh -c "…$REDIS_HOST…"`를 큰따옴표로 써서 **바깥 bash가 먼저 확장** → 빈 값 → redis-cli가 localhost로 붙어 실패. `${A:-0}`이 그 실패를 0으로 위장 | 스크립트를 파일로 만들어 **stdin으로 주입** |
| k6가 `fatal error: runtime: cannot allocate memory` | `open()`은 init에서 **VU마다** 실행된다. 3,000 VU × JSON 파싱 | `SharedArray`로 전 VU 공유 |
| 3,000건 전량 `401` | `access-token-ttl: 1800`(30분). 재시도하는 사이 만료 | 발급 직후 측정 |
| 상태 조회 2,990건 전부 `HTTP 410` | k6 로그의 닫는 `"`까지 토큰에 딸려 들어감 | 파싱 수정 |
| "추월 51건" | `rank`를 도착 순번으로 착각(§②) | `score`로 재측정 |
| **"277샘플 전부 100"으로 잘못 서술** | 분포를 `tail`로만 봐서 **run-2의 `admit=37` 1건을 놓쳤다** | 전체 분포로 재확인·수정 |

**`admit=0`이 정상값처럼 보였다는 점이 가장 위험했다.** 실패를 0으로 덮는 기본값은
"측정이 안 됐다"를 "문제가 없다"로 바꿔 놓는다. 마지막 항목도 같은 종류다 —
**요약만 보고 원자료를 안 보면 유리한 쪽으로 틀린다.**

## 무엇을 확인했고 무엇을 안 했나

**확인한 것**

- 정원의 **30배**가 동시에 도착해도 **관측된 모든 샘플에서 동시 입장 ≤ 100** (3회, 총 1,117샘플)
- 상승 구간 중간값 `admit=37`을 실제로 1건 포착 — 정원까지 차오르는 과정이 관측됐다
- **종료 스냅샷에서 추월 흔적 0** — 남은 score가 완전 연속(2회 확인)
- 초과분 2,900명이 **에러가 아니라 `WAITING`** (3회 중 2회 3,000/3,000, 5xx는 3회 모두 0)
- 이것이 **다중 파드(api 7개) 운영 환경**에서 성립한다 — IMP-004는 단일 워커 통합테스트였다
- **부하 시험이 실제 결함을 찾아냈다** — [[TS-024]]

**확인하지 않은 것**

- ⚠️ **샘플 사이의 순간 초과는 배제하지 못한다.** 100~200ms 간격 샘플링의 구조적 한계다
- ⚠️ **승격 순서를 실시간으로 캡처하지 않았다.** 종료 후 집합의 모양으로 역추론했다
- ⚠️ **[[TS-024]]가 미수정이다.** 명제 ③은 현재 코드에서 언제든 다시 깨질 수 있다
- ⚠️ **3,000명은 상한이 아니다.** 30배에서 안 깨졌다는 것이지 10만 명을 시험한 게 아니다.
  이 규모는 k6를 노트북 1대에서 돌린 제약에서 왔다
- ⚠️ **"동시"의 정도가 약하다.** 3,000 VU 진입이 12~14초에 퍼졌다. 진짜 동시가 아니라
  **12초 안의 3,000명**이다
- **진입 p95 7.5~11.5초는 느리다.** 정합성은 지켰지만 목표 지연(p95 300ms)과 거리가 멀고,
  이 구간 튜닝은 하지 않았다
- 승격 이후 경로(좌석 선택·결제)는 이 시나리오 밖이다. 매진 경합은 `../hold-contention/`

## 재현 절차

```bash
# 1) 시드 계정 3,000개 (DB 직접 삽입, 기준 계정의 bcrypt 해시 재사용)
# 2) JWT 사전 발급 — 30분 TTL이므로 발급 직후 측정할 것
node infra/k6/seed-issue-tokens.js /tmp/tokens3k.json 3000 12
# 3) 대기열 상태 초기화 → **잔존 감사** → 실행
k6 run -e K6_BASE_URL=https://flow-ticket.com/api -e TOKENS=/tmp/tokens3k.json \
       -e EVENT_ID=<eventId> infra/k6/spike-queue.js
```

`RANKLOG=1`을 주면 VU별 진입 결과를 stdout으로 남긴다(순서 대조용).
시드 계정은 `loadseed+*@example.com` 패턴이라 사후 정리가 가능하다. **실사용 계정이 아니다.**
