# ADR-026 · 피크에도 배포·복구할 여유와, 배치 정책을 requests에서 떼어 내기 — 제안(미적용, 검증 계획 포함)

- 상태: **Proposed** — 설계만. 운영 설정은 바꾸지 않았다(클러스터 철거 상태라 검증할 수 없어서 — 사용자 결정 2026-10-09)
- 날짜: 2026-10-09
- 슬라이스: S10(부하·확장)
- 관련: [[ADR-025]](api 1100m·HPA 3~9·Git 사전 확장 — 이 ADR이 다시 보는 대상), [[ADR-012]](노드그룹·비용), [[IMP-031]](통합 판정 run),
  [[IMP-021]](CA 실측), [[TS-035]](롤링 배포 502)

## 맥락 — 판정을 통과한 정책에 남은 운영 위험
[[IMP-031]]은 ADR-025 정책으로 7축을 판정 3회 충족했다. 그러나 "그 조건에서 동작했다"는 증거이지, 자원 배치·확장·배포 정책이 운영에 안전하다는 증거는 아니다.
리뷰에서 나온 세 가지를 같은 용량 문제로 묶어 다시 본다.

1. **최대 확장 상태에서는 배포가 멈춘다** — api `maxSurge 1`·`maxUnavailable 0`, HPA 상한 9, 노드그룹 상한 AZ당 3(합 9, `loadtest.tfvars`),
   노드당 api 하나(1,100m × 2 > 1,930m). api 9개가 떠 있으면 surge 파드가 10번째 노드를 얻지 못하고 롤아웃이 진행되지 않는다(ADR-025 대가에 적은 계산).
   피크 중 배포를 금지할 수는 있어도 **긴급 보안 패치·장애 수정까지 막을 수는 없다**.
2. **배치 정책이 requests 값에 얹혀 있다** — "노드당 api 하나"와 "api 확장 = Pending = CA 노드 추가"가 `requests.cpu: 1100m`의 부수 효과다.
   1100m는 burst 실측 비용에서 계산한 값이라 근거 없는 과대 설정은 아니지만, 평상시에도 노드 하나를 api 하나가 예약하고(평상시 노드 3 → 4 가능 — 계산, ADR-025),
   CPU HPA의 분모가 그대로 이 값이다. 자원 예약과 배치·분산을 한 숫자로 함께 풀었다.
3. **web을 밀어내서 api 자리를 만든다** — 사전 확장 9가 web 노드에 막히자 web PriorityClass −1로 api가 web을 선점하게 했다(ADR-025 보충).
   선점 중 PDB는 최선 노력일 뿐이라(Kubernetes 문서) web `minAvailable 1`이 선점 상황에서 보장되지 않는다. 대부분의 화면·API는 web을 지난다.

## 선택지
### A. 배포 여유 — 피크 중에도 surge 자리를 하나 남긴다
| 안 | 내용 | 대가 |
|---|---|---|
| A1 노드 상한 +1 | AZ 하나의 상한을 4로(합 10) — **피크(api 9)에서 surge 자리를 실제로 만드는 것은 이 안뿐이다**(노드당 api 하나라 10번째 노드가 있어야 한다, 계산) | 측정 프로파일은 vCPU 쿼터 32 중 30 사용(노드 9 × 2 + 발생기 3 × 4, 계산) → 10대면 32로 꽉 찬다. 모든 AZ를 4로 올리면 12 × 2 + 12 = 36 > 32. 발생기가 없는 프로파일은 10 × 2 = 20 ≤ 32(계산). 레포 기본 프로파일(AZ당 2 = 6노드)에서는 HPA 9 자체가 불가하다 |
| A2 여유 노드 예약(overprovisioning) | 우선순위가 가장 낮은 자리 지킴 파드(pause)로 노드 하나를 비워 둔다 — surge·긴급 파드가 오면 자리 지킴이 밀려나고 CA가 그 자리를 다시 만든다. 자리 지킴 파드 우선순위는 web(−1)보다 낮고 CA expendable 기준(−10) 이상이어야 한다(−2~−10) — CA는 −10 미만을 expendable로 보아 그 파드를 위해 노드를 만들지 않는다 | 노드 한 대 비용 상시. **노드 상한 안에서는 피크 배포를 풀지 못한다** — 비워 둔 노드도 상한(합 9)에 들어가 9번째 api가 그 자리를 쓰고, 밀려난 자리 지킴 파드는 상한 때문에 새 노드를 얻지 못한다(계산). 피크 배포용이면 A1과 함께여야 한다. 평상시의 surge·web 확장 지연(CA 대기)을 줄이는 데는 단독으로 효과가 있다 |
| A3 피크 배포 절차 | HPA 상한에 닿았을 때만 `maxSurge 0`·`maxUnavailable 1`로 바꾸는 긴급 배포 PR(용량 1/9 ≈ 11% 일시 감소, 계산) | 피크 중 용량을 줄인다. 절차를 사람이 지켜야 한다 |

### B. 배치 정책을 requests에서 떼어 내기
| 안 | 내용 | 대가 |
|---|---|---|
| B1 노드당 하나를 명시 규칙으로 | hostname 기준 anti-affinity(required) 또는 hostname topologySpread(maxSkew 1·DoNotSchedule — IMP-027에서 세션 한정으로 쓴 선례). requests는 실제 필요량(예: HPA 목표 지점의 평균 사용량)으로 낮춘다 | requests가 바뀌면 **HPA 사용률의 분모가 바뀐다** — 목표 60%가 의미하는 처리량이 달라져 ADR-025 계산과 IMP-031 결과를 다시 재야 한다. 평상시 롤링에도 surge 파드는 api 없는 노드가 필요하다. CA는 스케줄러 조건(파드 간 anti-affinity 포함)을 모의해 노드를 붙이는 것이 문서상 동작이지만 이 구성에서는 실측하지 않았다 |
| B2 zone topology spread + requests 하향 | base의 zone spread(지금 `ScheduleAnyway`)를 `DoNotSchedule`로 바꿔 AZ 균등만 강제하고, 노드당 개수는 제한하지 않는다 | burst 때 한 노드에 api가 둘이면 CPU를 나눠 쓴다(노이지 네이버) — 진입 burst에서 노드 CPU가 먼저 찬 측정(ADR-023 ①, IMP-027)이 다시 날 수 있다(추론) |
| B3 현행 유지(1100m) | 근거(요청당 비용 × 목표 처리량)가 있고 판정 3회를 통과했다 | 위 맥락 2의 결합이 남는다 |

### C. web을 지키면서 api 자리 만들기
| 안 | 내용 | 대가 |
|---|---|---|
| C1 워크로드별 노드그룹(테인트) | web·기타용 소형 노드그룹을 따로 두고 api 노드그룹은 api만 | 노드그룹이 늘어 AZ별 × 역할별 관리, 최소 노드 비용 증가. 측정 프로파일은 쿼터 여유가 2 vCPU뿐이라(32 − 30) A1과 함께 쓰면 32를 넘는다 — 발생기를 줄이거나 쿼터를 늘려야 한다(계산) |
| C2 사전 확장 때 web 용량도 함께 예약 | 사전 확장 PR이 api 하한과 함께 노드 여유(A2)를 올린다 | 사전 확장 비용 증가. A2와 같은 이유로 노드 상한 9 안에서는 api 9와 web 자리를 함께 만들 수 없다 — 상한을 함께 올려야 한다(계산) |
| C3 현행 유지(선점) | 판정 3회에서 web Ready 2를 확인했다 | 선점 중 PDB 최선 노력 — web 가용성 보장 없음 |

## 제안(Proposed — 검증 뒤 결정)
- 운영 설정을 바꾼다면 **A1 + A2(노드 상한 +1과 여유 노드 예약) + B1(노드당 하나 명시 규칙, requests 재산정) + C1 또는 C2**를 먼저 검증할 후보로 둔다.
  "용량 상한·용량 예약·배치 규칙·우선순위"를 각각 독립 변수로 만들어, 한 숫자(1100m)가 여러 역할을 하던 결합을 푼다. A1이 빠지면 surge 자리는 생기지 않는다 — 그때 피크 배포는 A3(용량 1/9 감소)로만 가능하다(계산).
  상한을 올릴 수 없는 환경이면 A3(피크 배포 절차)을 함께 둔다.
- 측정 프로파일(발생기 3대)에서는 A1·C1이 vCPU 쿼터 32를 넘을 수 있어, 발생기 수나 쿼터를 먼저 정해야 한다(검증 계획 4).
- **지금은 바꾸지 않는다**(B3·C3 유지). 바꾸면 ADR-025의 계산과 IMP-031의 결과가 새 설정에 그대로 적용되지 않는데, 클러스터가 없어 다시 잴 수 없다.

## 검증 계획(클러스터를 다시 올릴 때)
1. **피크 배포**: HPA 9·노드 9 상태에서 이미지 롤아웃 → 현행은 surge Pending으로 멈추는지(재현), A2·A3에서 끝나는지와 그 사이 5xx(ALB 알람 스택 포함).
2. **B1 재산정**: anti-affinity + requests 후보(예: 600m·800m)에서 같은 진입·폭증 부하로 HPA 확장 시점·CA Pending → Running·응답 꼬리를 IMP-031과 비교(사전 등록).
3. **web 가용성**: 사전 확장 중 web Ready 수와 web 경로 5xx를 1초 단위로(C1·C2 대 C3).
4. 쿼터: 측정 프로파일(발생기 포함)과 운영 프로파일(발생기 없음)을 나눠 vCPU 예산을 다시 적는다.

## 결과·대가
- 문서만 바뀐다. 이 ADR이 Accepted가 되기 전까지 ADR-025가 운영 정책이다.
